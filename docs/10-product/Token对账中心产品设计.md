# Token 账单与人工对账中心产品设计

## 1. 文档目标

本文定义仅 `root` 最高管理员可见的 Token 账单与人工对账工作台。系统只读查询当前业务已经写入数据库的计费事实，生成可查看、筛选和导出的账单；`root` 根据这些账单在系统外与上游人工核对。

本功能不是上游成本系统，不是自动对账引擎，也不是上游调用取证系统。

## 2. 核心结论

1. 账单的唯一事实来源是现有业务数据库中的消费与退款记录。
2. 账单中的 Token、额度、模型、渠道、用户和组织维度均从已有数据库事实派生，不新建平行计量口径。
3. 与上游的对账由 `root` 手工完成；系统不连接、同步、抓取或保存上游账单。
4. 系统不计算上游成本，不展示毛利，不尝试将重试、取消或测试请求归因为上游成本。
5. 账单读取路径与 Relay、渠道选择、上游请求、流式响应、预扣、结算和退款主流程完全解耦。
6. 账单功能不得为采集数据而在主链路中新增函数调用、数据库写入、网络请求、密钥指纹或状态机。
7. 如果账单事实缺失或错误，应修复原有业务事实的落库逻辑，而不是由账单模块建立第二套事实。
8. 页面提供三个只读视角：“客户账单”回答每个客户被计费和退款了多少；“渠道用量”回答每个渠道及其模型产生了多少 Token 与计费额度；“按上游”按渠道当前有效 API 地址与渠道共同汇总。
9. 切换细分维度不得丢失一级对账主体：客户视角中的模型和渠道必须与客户共同分组，渠道视角中的模型必须与渠道共同分组。

## 3. 业务边界

### 3.1 账单包含的事实

首版账单汇总和展示：

- `LogTypeConsume` 客户消费记录；
- `LogTypeRefund` 退款记录；
- 实际结算的 quota；
- 账单事实中已记录的输入、输出 Token；
- 用户、组织、客户 Token、模型和渠道等现有日志维度；
- 流式标记、请求 ID、上游请求 ID 等现有日志已保存的辅助字段；
- 异步任务已经进入现有计费事实的最终结算结果。

### 3.2 明确不包含

本功能不包含：

- Provider Usage/Cost API 连接器；
- 上游账单、用量、成本或日志自动同步；
- CSV/JSON 上游账单导入；
- 上游成本、毛利和成本归因；
- 网关 retry 次数和传输子尝试记录；
- 客户取消后的上游成本跟踪；
- 渠道测试或系统轮询的成本记录；
- 自动匹配、自动差异判定、自动处置或自动关账；
- 影子采集、采集节点、采集水位和采集缺口；
- 新建 `rec_attempts`、`rec_usage_records` 或其他平行账本。
- `LogTypeSystem` 操作日志：当前权威写入路径只记录注册赠送、签到、安全验证等操作文本，不写入可计费 `quota`，因此不得仅根据日志类型把它虚构为“系统调整账单”。

## 4. 人工对账工作流

1. `root` 选择账单时间范围。
2. 系统从现有数据库实时汇总账单。
3. `root` 先选择客户账单、渠道用量或按上游视角，查看当期总体用量与额度。
4. `root` 在当前对账主体内继续细分：客户、客户 × 模型、客户 × 渠道、渠道、渠道 × 模型、API 地址 × 渠道或上游 × 模型。
5. `root` 点击汇总行后先查看该主体的上下文与次级汇总，再追溯原始账单记录。
6. `root` 导出当前视角与筛选条件下的账单。
7. `root` 在系统外与上游账单手工核对。
8. 如发现本系统账单记录错误，按原计费业务的缺陷流程修复；账单页面不提供改写事实的功能。

## 5. 账单口径

### 5.1 金额与 quota

账单金额以现有业务已结算的 `quota` 为准。页面可按系统现有的 quota 换算规则展示金额，但不重新执行模型定价或用当前价格重算历史账单。

现有权威写入路径中，消费和退款的 `quota` 都以正数保存，业务影响由日志类型共同表达。因此账单投影将消费显示为正数、退款显示为负数，且 `净额 = 消费原始 quota 合计 - 退款原始 quota 合计`。这只是对现有“类型 + quota”事实的账单表达，不回写数据库。

### 5.2 Token

Token 字段只展示当前账单事实中已经保存的数值。系统不在查询时伪造缺失类别，不从金额反推 Token，不使用上游数据覆盖客户账单。

### 5.3 请求数

请求数是账单记录数或现有业务已定义的计数，不是网络发包数、渠道 retry 数或 Provider SDK 重发数。

### 5.4 客户账单视角

- 同时纳入消费和退款记录；
- 顶部总览展示净计费额度、账单记录数、输入 Token、输出 Token 和 Token 合计；
- 汇总表支持“按客户”“客户 × 模型”“客户 × 渠道”；
- 模型细分的唯一粒度是 `user_id + model_name`，渠道细分的唯一粒度是 `user_id + channel_id`，不得出现跨客户合并的纯模型或纯渠道账单；
- 退款在净额中为负，不修改数据库中正数保存的退款原始值。

### 5.5 渠道用量视角

- 只统计现有 `LogTypeConsume` 消费事实，按渠道或模型汇总记录数、输入 Token、输出 Token、Token 合计和已计费 `quota`；
- 汇总表支持“按渠道”“渠道 × 模型”；模型细分的唯一粒度是 `channel_id + model_name`，不得出现跨渠道合并的纯模型用量；
- 该视角表示“系统数据库中已记录、且路由到某渠道的消费用量”，供人工与上游核对；
- 其中的金额是现有客户计费 `quota`，不是 Provider 成本、采购价或上游账单金额；
- 不减去客户退款，因为退款是客户资金事实，不能反向证明上游用量消失；
- 不补算 retry、渠道测试或未写入账单日志的上游请求。

### 5.6 按上游视角

- 只统计现有 `LogTypeConsume` 消费事实，并通过日志中的 `channel_id` 关联主数据库的渠道配置；
- 默认一级汇总粒度是“当前有效 API 地址 × 渠道”，即 `current_api_address + channel_id`；同一 API 地址下的不同渠道不得合并成一行；
- 可切换到“上游 × 模型”，其完整粒度是 `current_api_address + channel_id + model_name`；“上游”仍表示 API 地址与渠道的共同主体，不能退化为纯 API 地址 × 模型；
- API 地址使用 `Channel.GetBaseURL()` 的当前有效值，并将末尾 `/` 归一化后分组；无法关联已删除渠道或当前地址为空的记录统一进入“未知 API 地址”；
- 点击某个“API 地址 × 渠道”行后，先按“上游 × 模型”展示该渠道的次级汇总，再加载原始账单记录；点击“上游 × 模型”行则直接查看该地址、渠道、模型交集内的原始账单；
- 现有日志没有保存请求发生时的 API 地址快照，因此该视角明确展示“按渠道当前配置重算的历史用量”。渠道地址后来变更时，历史记录会随当前配置重新归组，不能把该视角解释为历史发送地址证据；
- 额度仍是客户已计费 `quota`，不是 Provider 成本或上游账单金额，也不补算 retry。

## 6. 已选页面方案（方案 2：Audit Worksheet）

更新后的对账主体视觉基准：[`../90-ui-ux/uis/token-bill-reconciliation-subjects.png`](../90-ui-ux/uis/token-bill-reconciliation-subjects.png)。

侧边栏保留一个 `root` 专属入口：“Token 账单”。页面为单一工作台，不再展示数据源、采集健康、差异处置、关账或同步任务。

页面采用一张“总体优先、按需下钻”的连续审计工作表，不使用多子页、看板卡片或自动对账流程。桌面端从上到下固定为：

1. 标题“Token 账单”和说明“基于数据库账单事实进行人工核对”；
2. 本月、上月、自定义账期与起止日期；
3. 唯一主操作“导出当前账单”；
4. 客户账单 / 渠道用量 / 按上游三个一级视角切换；
5. 账单类型（仅客户视角）、组织、模型、渠道和 Request ID 筛选；
6. 总体用量指标：额度、记录数、输入 Token、输出 Token 与 Token 合计；
7. 汇总表：客户视角支持客户、客户 × 模型、客户 × 渠道；渠道视角支持渠道、渠道 × 模型；按上游支持 API 地址 × 渠道、上游 × 模型；
8. 点击汇总行后在右侧抽屉中显示完整复合上下文和原始账单，首屏不常驻明细表；按上游详情先保留地址与渠道上下文，再查看模型和原始记录。

移动端保持相同阅读顺序：标题与导出操作先显示，时间、视角与筛选控件换行，先看总体指标再看汇总表，明细在抽屉内横向滚动。

页面显式说明“本页面只读，不会连接上游服务商”，避免用户误解为自动上游对账。

所有图表、汇总和明细必须来自同一组查询条件，不允许前端另行重算口径。

## 7. 筛选与下钻

首版支持：

- 起止时间，默认当前自然月；
- 账单类型：消费、退款；
- 组织；
- 模型；
- 渠道；
- Request ID，同时精确匹配本地 `request_id` 或已有 `upstream_request_id`，仅用于人工查找。

渠道用量和按上游视角固定只查消费记录，不展示账单类型筛选。

单次交互查询范围默认不超过 92 天；更长时间范围应拆分导出，避免影响日志数据库。

## 8. 导出

导出是账单查询的另一种输出形式，不是独立计算流程。

- 导出使用与页面相同的视角、筛选条件和服务端口径；
- 首版支持 CSV；
- 导出包含汇总和明细所需字段，不包含密钥、请求正文、提示词或模型输出；
- 导出不创建对账快照、不改写原账单、不发起上游请求。

## 9. 权限与安全

- 前端入口仅对 `ROLE.SUPER_ADMIN` 展示；
- 后端账单接口统一使用 `middleware.RootAuth()`；
- 不向普通管理员、组织管理员或客户暴露跨用户账单；
- 账单页面不提供修改、删除或补录账单事实的操作；
- 不展示客户或上游 API Key 明文。

## 10. 空数据与不完整数据

- 没有账单记录时显示明确空状态，不显示“已对平”。
- 当前 `LogConsumeEnabled` 关闭时，页面必须显示“账单可能不完整”的阻断级警告，不得将缺失的消费记录解释为零用量。该状态只能说明当前配置，无法证明历史账期从未关闭过记录。
- 现有 `Log` 的 Token 字段为非空整数，页面原样展示数据库中的数值；历史记录中的 `0` 无法区分“真实为零”和“旧链路未记录”，页面不反推、不补算。
- 汇总和明细不一致视为账单查询缺陷，必须修复同一数据源上的口径差异。
- 账单不对上游是否完整、是否延迟或是否对平作自动判定。

## 11. 验收标准

- 账单总额与在同一筛选条件下直接查询现有账单数据库的结果一致；
- 汇总、分组、明细和 CSV 导出口径一致；
- 页面首先展示总体指标和分组汇总，明细只在用户点击汇总行后加载；
- 客户视角的净额纳入退款，渠道用量与按上游视角只统计消费事实；
- 渠道视角的渠道、模型、Token、额度汇总与同条件 `LogTypeConsume` 直接查询一致；
- 客户 × 模型和客户 × 渠道任何一行都不得混入其他客户；渠道 × 模型任何一行都不得混入其他渠道；
- 按上游默认以“当前 API 地址 × 渠道”为行粒度，同一地址下的不同渠道不得合并；“上游 × 模型”以地址、渠道、模型三者为行粒度；点击后明细使用完整交集过滤；
- 消费为正、退款为负，净额与直接按日志类型查询数据库的结果一致；
- 功能不依赖任何上游配置或网络可用性；
- 启用或关闭账单页面不改变 Relay、计费、退款或异步任务行为；
- 代码中不存在为账单功能新增的上游发送边界调用；
- 代码中不存在 `rec_attempts`、Provider Connector、自动同步、影子采集或成本归因路径。
- 页面结构、交互层级和信息密度与已评审的方案 2 一致。
