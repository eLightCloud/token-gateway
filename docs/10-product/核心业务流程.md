# 核心业务流程

完整产品边界见 [组织与账单产品设计](./组织与账单产品设计.md)。

## 个人账号与扣费流程

系统真实扣费主体始终是个人用户账号。

```text
请求 -> Token -> User -> 个人钱包/订阅 -> 预扣 -> 结算/退款 -> Log
```

组织归属可以影响请求计价，但不会改变个人钱包或订阅的资金主体；组织账单查询不会触发扣费。代理客户使用个人钱包，代理采购账单独异步入账。

## 创建组织

系统管理员在 `/admin/organizations` 创建组织：

1. 输入组织名称。
2. 后端创建 `Organization`，状态默认为启用。
3. 不创建任何 `OrganizationMember`。

创建组织不会让任何用户加入组织，也不会修改用户账号、余额、订阅、Token 或 `group`。

## 添加组织成员

系统管理员或组织 Admin 可以把已有用户加入组织：

1. 在组织成员页点击 `Add member`。
2. 搜索并选择一个已存在的启用用户。
3. 选择角色。
4. 后端校验该用户当前不属于其他组织。
5. 后端创建 `OrganizationMember`，记录 `joined_at`，写入 `billing_start_at = joined_at`，并保持 `left_at = 0`。

角色规则：

- 只接受 `admin`、`member`。
- `admin` 可以管理组织信息、成员和角色，并查看完整组织账单。
- `member` 只能查看自己的组织内用量。

## 移除组织成员

移除成员只结束组织成员关系：

1. Admin 触发二次确认。
2. 当前操作者可以移除自己，但如果自己是最后一个活动 Admin，则拒绝操作。
3. 后端在同一事务中校验组织仍有活动 Admin 并设置 `left_at`，不物理删除成员关系。

移除成员不删除用户账号，不修改 Token，不影响个人余额、订阅、充值、退款或历史日志。

## 组织账单查询

组织账单只解释已经发生的个人消费日志：

```text
Organization -> OrganizationMember.UserId -> Log.UserId
```

统计范围按成员有效期过滤：

- `effective_billing_start = billing_start_at > 0 ? billing_start_at : joined_at`
- `Log.CreatedAt >= effective_billing_start`
- `OrganizationMember.LeftAt = 0` 或 `Log.CreatedAt < OrganizationMember.LeftAt`

新成员默认从加入时间开始统计。经系统管理员或组织 Admin 确认后，可以通过“预览 → 应用”把当前成员的账单归属起点向前扩展，纳入仍保留的加入前消费；成员离开后，组织仍可查看其账单窗口内产生的历史消费。

## 历史账单归属回填

1. 管理员选择候选账单归属起点。
2. 后端预览相对当前窗口新增的请求数、quota、Token、日志范围和窗口冲突。
3. 管理员确认业务归属和新增金额。
4. 应用请求携带预览返回的当前起点作为乐观锁预期值。
5. 后端在事务内重做 CAS、同组织窗口不相交校验和增量计算，再更新 `billing_start_at` 并写审计。
6. 前端刷新 Summary、各维度、Logs、导出和 Invoice。

该流程不修改 `joined_at`、个人余额、订阅、Token 或原始消费日志。当前只允许向前扩展，不允许调晚起点截断已纳入消费。

## 组织 Invoice

```text
成员账单窗口
  -> 消费 Log.Quota
  -> 按成员、完整模型、北京时间月份聚合
  -> 模型分类
  -> 应用组织月度结算系数
  -> Invoice 页面与专用 CSV
```

Invoice 默认当前北京时间自然月。模型交叉表按消费事实聚合；账户财务摘要还读取入账、调整、退款和余额等事实。结算系数只改变组织结算报表的展示金额，不参与个人请求的预扣、结算或退款。

## 个人使用日志

1. 使用日志按当前账号和已有可见范围查询。支持游标的关系型部署启用个人最新页后，用户可刷新最新明细、顺序翻页或按请求 ID 定位。已保存的页码链接及 ClickHouse 部署沿用原分页。
2. 读取繁忙或失败时提示重试。空结果只表示当前筛选下无可见记录；请求刚完成但尚无日志时，可按原请求 ID 稍后核对已落库结果。
3. 历史统计和导出继续使用原入口。独立实时指标和本月卡片的交付状态见[路线图](../50-planning/路线图.md#log-release)。

## 用户摘要与管理员通知

1. 每日任务在北京时间 06:00 后分批处理前一自然日。个人只在有消费、已采集错误或符合余额/订阅风险规则时收到摘要；无使用的默认零余额账号静默。摘要区分历史消费与生成时的余额、订阅状态，消费或请求统计缺失时显示不可用或不完整。
2. 管理员从同一日批次收到运维日报，了解已采集的调用、异常、渠道、任务和资源情况。每日开关控制两类日报，默认关闭并保留预览模式。应急与恢复邮件独立开关，只投递给配置的管理员。
3. 用户可从摘要的前一日明细链接进入自己的使用日志，仍受原权限约束。已有即时余额提醒独立工作。测试和启用步骤见[运维手册](../40-operations/运维手册.md#运维通知预览与启用)。

## 专题流程

- 配置消费倍率：管理员保存规则 → 完成全局迁移切换 → 请求按实际渠道解析用户、组织或系统倍率；见[实时模型折扣](用户与组织实时模型折扣产品设计.md)。
- 代理分销：平台开通代理 → 代理开通及授权名下客户 → 客户调用、即时扣费 → 代理采购事件异步入账；见[代理分销](代理分销与用户专属倍率产品设计.md)。
- 人工对账：Root 选择客户、渠道或上游视角 → 查看已记录消费与退款 → 导出相同范围；见[Token 对账中心](Token对账中心产品设计.md)。

## 文本流客户断开后的结算流程

按 Token 计费的文本生成流已建立上游连接后，客户侧 Context 结束不再立即终止上游读取：

```text
客户侧 Context 结束
  -> 记录 client_gone，停止向客户写入
  -> 在空闲和绝对上限内继续读取已建立的上游文本流
       -> 协议成功终态 + 完整 usage：经原结算入口结算一次
       -> 失败、异常 EOF、usage 缺失或超时：进入现有错误/退款路径
```

只有完整、权威的上游 usage 可通过结算门。本地估算不得伪装成“已与上游对齐”；续读失败但上游已产生的成本由网关承担，不事后补收客户、不人工改账。该行为不适用于图片、视频、音频等非文本流，也不改变非流式请求和响应头返回前取消的既有行为。
