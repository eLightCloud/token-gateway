# 组织与账单产品设计

组织成员的新增实时消费定价目标见[用户与组织实时模型折扣产品设计](./用户与组织实时模型折扣产品设计.md)，已接入代码；实际启用取决于主库迁移阶段。该能力按模型配置单倍率与渠道范围，个人覆盖优先；本文既有组织统计、Invoice 和结算系数保持原职责，不新增组织钱包或让统计接口执行扣费。

## 产品结论

系统采用“个人扣费、组织汇总、模型分类”的账单模型：

```text
个人账号 = 唯一真实扣费主体
组织      = 成员集合 + 报表权限 + 汇总视图
模型      = 消费分析维度，不是账号或付款主体
```

组织能力服务于企业用量治理，不改变现有个人钱包、订阅、API Key、预扣、结算和退款链路。

## 当前状态

本仓库提供组织管理、用量统计、历史归属、Invoice 和结算系数。关系型日志库可使用后台用量快照，ClickHouse 保留兼容用量查询。统计结果生成中或数据不完整时，页面需区分等待、旧结果和失败。生产发布与验收见[路线图](../50-planning/路线图.md#organization-release)。

## 个人账单能力

个人账号持有并承担：

- 钱包额度、已用额度和请求次数。
- 充值订单、兑换码充值和管理员补单。
- 订阅套餐、订阅实例、订阅额度及额度重置。
- `subscription_first`、`wallet_first`、`subscription_only`、`wallet_only` 四种扣费偏好，默认 `subscription_first`。
- API Key 额度限制和用量统计；API Key 仍归属于个人用户。
- 消费、退款、充值和管理日志。

模型倍率、固定价格和表达式阶梯计费决定个人请求的实际 `quota`；组织报表只读取已经形成的消费事实。

## 组织产品边界

组织负责：

- 组织名称和启用/停用状态。
- 成员关系及其有效期。
- Admin、Member 两类组织角色。
- 按成员、模型、渠道、日期和日志明细汇总用量。
- 在权限范围内查看和导出组织消费日志。
- 为系统管理员和组织 Admin 提供按模型类别、账号生成的 Invoice，并按组织自己的月度结算系数计算展示金额。

组织不负责：

- 余额、充值、订阅、付款客户、发票或退款。
- API Key、Token 归属或请求时的组织选择。
- 部门、团队、项目、成本中心或跨组织切换。
- 独立组织消费流水，或改写个人历史扣费事实。

`group` 继续表示用户分组、模型可用性、路由和倍率，不得在产品文案或界面中解释为组织。

## 生命周期

### 创建组织

系统管理员先创建空组织，只填写名称。创建后不会自动把创建人或任何用户加入组织。

### 添加成员

系统管理员在组织详情中搜索现有启用用户，并以 Admin 或 Member 身份添加到组织。

一个用户同一时间只能有一个活动组织成员关系。注册、登录、创建 Token、充值、订阅和 API 请求都不会自动加入组织。

新成员的账单归属起点默认等于真实加入时间。添加成员本身不自动吞并加入前的历史消费。

### 调整历史账单归属

系统管理员或组织 Admin 可以为当前活动成员显式向前调整账单归属起点：

- 先预览候选起点将新增纳入的消费请求数、quota、Token 和日志时间范围，再确认应用。
- 候选起点必须为正数、不得位于未来，也不得晚于当前生效起点；当前能力只补历史，不允许通过调晚起点截断已经纳入的消费。
- 同一用户在同一组织内的多段成员账单窗口不得重叠，避免同一日志重复统计；跨组织窗口可以重叠，各组织是独立报表视角。
- 历史日志已经被 TTL、清理任务或人工操作删除时，只汇总仍保留的事实，不生成估算数据。
- 调整只改变组织报表对日志的解释，不改写成员加入时间、个人余额、订阅、Token 或历史消费日志。

### 调整角色

- 系统管理员可维护所有成员关系。
- Admin 管理组织名称、成员和角色，并查看完整组织账单。
- Member 只查看自己在成员有效期内的用量，不查看其他成员。

### 移除成员

移除成员只结束成员关系并记录 `left_at`，不删除用户或历史日志，也不改变个人余额、订阅和 Token。

## 组织账单口径

组织账单按成员关系有效期解释个人日志：

```text
Organization -> OrganizationMember.UserId -> Log.UserId

effective_billing_start =
  billing_start_at > 0 ? billing_start_at : joined_at
```

- 未调整历史归属时，加入组织前的消费不进入组织账单。
- 管理员确认并向前调整账单归属起点后，起点至加入时间之间仍保留的消费进入组织账单。
- 成员有效期内的消费进入组织账单。
- 离开组织后仍保留其有效期内的历史汇总。
- 默认用量视图只统计消费日志。
- 对账口径可分别纳入退款和系统调整，不能把不同类型静默合并成净额。
- 消费金额由已落库的 `Log.Quota` 换算，是汇总、用户、模型、渠道、趋势和明细的首要账单指标；原始 quota 同时保留用于审计。
- 渠道名称、渠道 ID 和渠道维度用量属于运营信息，仅对 Admin 和系统管理员可见；Member 不可通过页面、JSON 或 CSV 获取渠道信息。
- 消费金额始终按真实货币展示：站点为 USD、CNY 或自定义货币时沿用其汇率，站点为 TOKENS 时使用 USD 等值，避免“金额”和原始额度重复。
- 模型同时展示当前计价规则；它只解释当前固定价格、倍率或阶梯计费配置，不重算历史消费。

### Invoice 与结算系数

Invoice 是组织用量分析之外的客户结算视图：

- 账期统一按北京时间，默认当前自然月，并支持最长 24 个自然月的自定义日期范围。
- 第一张表按模型类别 × 账号展示折前金额、类别合计、结算系数和结算后金额；第二张表按完整模型 × 账号展示折前金额和占比。
- 系数是组织级、按北京时间自然月生效的独立变量，默认 `1.0000`；允许 `0.0000` 至 `10.0000`，其中 `0.0000` 明确表示免费/结算豁免。
- 配置页只列出该组织成员账单窗口中实际产生过消费的模型类别；未知模型使用稳定的单模型 fallback 类别。
- 计算使用原始整数 quota，在类别 × 月份粒度应用四位定点系数，最终展示时再舍入；不得使用页面已格式化单元格反算。
- 修改历史月份会重新呈现组织 Invoice。个人余额、订阅、Token 和消费日志仍使用请求结算时的事实；Invoice 以已入账用量应用独立的月度结算系数。

Invoice 的标准模型类别先使用确认清单精确匹配，再使用无歧义的品牌/家族前缀归类。匹配前统一去除模型名首尾空格并转为小写，不使用任意子串推断：

当前类别为 Claude、GPT、Gemini、Minimax（阿里云）、Deepseek、Kimi（阿里云）、GLM（阿里云）、Qwen（阿里云）和向量。模型清单和匹配规则以[分类目录](../../model/organization_invoice_category_catalog.go)为准，详见[架构说明](../20-architecture/组织与组织账单架构设计.md#模型分类与结算)。未匹配模型按单模型归类；未配置结算规则时统一按 `1.0000`，参考系数不自动预置。

## 当前实现范围

- 管理员可以创建空组织、设置状态并维护成员。
- 成员角色只接受 Admin、Member。
- 活动成员关系在 SQLite、MySQL 和 PostgreSQL 上都保持单用户唯一。
- 新成员默认从加入时间开始统计；历史账号可通过“预览 → 应用”显式向前扩展账单归属窗口，成功与失败尝试都保留管理审计。
- Admin 的完整组织账单权限与 Member 的个人范围隔离。
- 汇总、趋势、成员、模型、渠道和明细使用同一组服务端筛选口径。
- 组织账单不触发任何预扣、个人扣费结算、退款，也不改写历史消费事实。
- 独立 Invoice 默认显示当前北京时间自然月，页面查询和专用 CSV 导出复用同一聚合与结算算法。
- Invoice 专用 CSV 面向财务对账：文件头输出组织名称、账期、币种，必要时附金额说明；两张交叉表以 `users.username` 作为稳定账号列，并在其上方输出一一对应的“真实姓名”行。真实姓名取 `display_name`，为空时保留空单元格，不能替代账号列；页面与 JSON API 继续使用脱敏显示名。
- Invoice 账号集合以成员计费窗口与账期的时间交集为准，不以是否有消费为准。零消费、未登录、只入账未消费和账期内已离开的账号均展示并导出；多段成员关系按用户去重。消费严格按成员计费窗口归属，充值和调额对已入选账号按完整自然账期统计，以覆盖先入账后加入组织的流程。
- Invoice 页面和 CSV 共享同一账号财务摘要。CSV 展示用户上期余额、当期流入金额、当期消费金额和当前余额；有退款或异常时另列退款和待核对信息；当期流入金额包含支付充值、管理员正向调额和其他已识别正向入账。首次查询发现组织期初基线缺失时，后台任务会先回放账期前事实生成真实上期余额，不将未知期初当作零。
- 新管理员调额以 `user_quota_adjustments` 为权威事实。对上线前仅有旧管理审计日志的正向调额，期初基线或月度汇总首次构建时自动识别精确的结构化旧格式和更早的中文审计格式并计入；后续查询只读 `ready` 汇总，不重复扫描旧日志。CLI 仅保留为预览和事实固化工具，不是查账前置条件。当前余额是查询或导出时的即时 `users.quota`，不是账期末历史余额。
- Invoice CSV 不输出组织 ID 元数据、时区、内部时间戳、规则明细和原始 quota；金额均为无货币符号的六位小数，账期消费聚合与结算算法不因导出投影改变。
- 导出复用当前筛选条件；Billing 页面使用新增完整账单端点，汇总、用户、模型、渠道、趋势和明细都包含可计算的消费金额、币种和原始 quota，模型额外包含当前计价规则。
- Logs 页面使用独立的展示型日志导出端点，提供北京时间、用户、模型、消费金额、币种及输入/输出 Token；既有日志导出端点继续保持原始列结构和文件名。
- Member 的组织账单、日志和导出均不包含渠道 ID、渠道名称和渠道用量；Admin 和系统管理员仍可在对应页面和导出中查看渠道维度。前端根据角色停止请求渠道用量，后端强制清零 Member 的渠道筛选参数并返回空渠道数据。
- Logs 导出和 Billing 完整导出的明细均按有界批次流式输出，不再固定截断为 10,000 行。
- 展示型日志导出不包含请求标识和内容；兼容日志导出与完整账单导出仍属于管理员级排障导出。

## 验收标准

- 系统管理员和组织 Admin 能维护授权范围内的成员和账单；Member 只看本人，不能通过筛选、明细或导出探测渠道。
- 同一账期和筛选下，明细、页面汇总与导出使用同一账单范围；成员退出后仍保留其有效窗口的历史消费。
- 历史归属预览能说明新增范围；应用不修改原始消费、个人余额或订阅，冲突后需重新预览。
- Invoice 包含账期内有归属交集的零消费账号；按月应用结算系数，页面与 CSV 保持同一消费口径。未知余额或不完整账务必须明确显示状态。

完整断言见[验收标准](验收标准.md)，测试数据与命令见[组织模块开发与验证指南](../30-engineering/组织模块开发与验证指南.md)，接口和依赖见[架构设计](../20-architecture/组织与组织账单架构设计.md)。
