# 验收标准

## 验收结论

基础组织管理、Billing 和 Logs 已完成验收并上线；历史归属起点和 Invoice 候选版本已完成自动化验收，仍待真实数据库、ClickHouse 和生产规模验证。以下条目是生产版本必须持续保持的回归合同。

## 组织管理

- 管理员能只输入组织名称创建空组织。
- 创建组织后不会自动添加任何用户。
- 管理员能将未加入组织的启用用户加入指定组织。
- 添加或修改成员角色时只接受 Admin、Member，其他角色必须被拒绝。
- 组织 Admin 能在用户侧成员页添加成员、修改角色和移除成员。
- Admin 能查看完整组织账单，Member 只能查看自己的组织内用量。
- Member 的账单查询只能覆盖自己在组织成员有效期内的用量，且前端必须提供对应的受限用量视图。
- 未加入组织的用户不显示组织入口，直接访问组织页面时显示未加入组织的空状态。

## 无侵入边界

- 管理员创建组织和创建系统用户时都不能隐式加入组织；如需加入组织，必须通过组织成员接口完成。
- 注册、登录、创建 Token、充值、订阅和 API 请求不会自动加入组织。
- 组织功能不修改用户 `group`、个人余额、个人订阅、Token 归属、扣费、退款或日志写入链路。
- UI 不出现组织余额、组织充值、组织订阅、组织 API Key、Header 组织归属或项目成本中心。

## 文本流断开续读

- 客户侧在终态 usage 到达前断开后，网关立即停止客户侧写入，但在有界时间内继续读取已建立的上游文本流。
- 同一请求可同时记录 `end_reason=client_gone` 和独立的 `upstream_result`，后续上游成功不覆盖客户先断开的事实。
- 只有协议成功终态且 usage 完整时才进入原成功结算路径，且只结算一次。
- 协议失败、usage 缺失、异常 EOF、读取/解析错误、空闲超时和续读绝对超时不得进入普通成功消费日志路径。
- 本地估算 usage 不得通过“完整上游 usage”结算门；续读仍失败时不事后补收客户。
- 流式改造不影响正常完成、非流式、图片、视频和音频请求。
- Chat Completions、Claude Messages、OpenAI Responses 和 Gemini 的 max-tokens 类字段越界时返回 HTTP 400 `invalid_request`；请求体过大保持 HTTP 413，且拒绝请求不进入渠道选择、预扣或上游重试。

## 成员关系与账单

- 一个用户同一时间只能属于一个组织。
- 添加成员时必须拒绝已属于其他组织的用户。
- 移除成员只设置 `left_at`，保留历史成员关系。
- 组织账单按成员账单归属窗口汇总现有个人消费日志；旧成员 `billing_start_at = 0` 时回退 `joined_at`。
- 新成员的账单归属起点默认等于加入时间，因此未显式回填时，加入前历史消费不进入组织账单。
- 系统管理员和组织 Admin 可以先预览、再向前调整当前成员的账单归属起点；Member 不可操作。
- 回填应用必须校验候选时间、同组织窗口不重叠和 `expected_billing_start` 乐观锁；相同值重复应用保持幂等。
- 回填后 Summary、Members、Models、Channels、Trend、Logs、Billing 导出和 Invoice 使用同一成员窗口，且不修改个人余额、订阅、Token 或原始消费日志。
- 成员离开组织后，组织仍能查看其成员有效期内产生的历史消费。
- 组织明细导出复用当前筛选条件。
- 既有 `billing/logs/export` 保持单表日志 CSV、原始列顺序和文件名；完整账单通过新增 `billing/export` 提供。
- Logs 页面通过独立 `billing/logs/display-export` 导出可读时间、消费金额、币种、原始 quota 和合计 Tokens，不暴露请求标识与内容。
- 页面汇总、用户、模型、渠道、趋势和消费明细均以消费金额为首要指标，同时保留原始 quota。
- TOKENS 展示模式下消费金额使用 USD 等值，不得与原始 quota 重复。
- 导出的所有账单区块均包含纯数值消费金额、币种和原始 quota；模型区块额外包含当前计价规则。
## 组织账单渠道隔离

- Member 的组织账单页面不展示渠道筛选项和渠道用量面板。
- Member 不发起渠道用量请求；前端 `canViewOrganizationBillingChannels(role)` 对 `member` 返回 `false`。
- Member 调用 `/api/organization/current/billing/channels` 时返回空数组。
- Member 的账单日志 JSON 不包含 `channel` 和 `channel_name` 字段。
- Member 的原始日志 CSV 和完整账单 CSV 不包含渠道列、渠道用量区块或渠道名称。
- Admin 和系统管理员仍可通过用户侧/管理端渠道接口、页面和导出查看渠道维度。
- 后端在建立账单范围时强制清零 Member 提交的渠道筛选参数；前端可见性只负责用户体验，不作为最终安全边界。

## Invoice 与结算规则验证

- Invoice 默认按北京时间当前自然月查询，只统计消费日志，并按模型类别 × 月份应用组织结算系数。
- Invoice 标准类别必须先使用确认的完整模型名清单精确匹配，再使用目录显式声明的无歧义品牌/家族前缀；匹配前只执行首尾空格清理和小写归一化，不得使用任意子串推断。
- 标准类别固定为 `claude`、`gpt`、`gemini`、`minimax`、`deepseek`、`kimi`、`glm`、`qwen` 和 `vector`；向量类别必须包含 `text-embedding-3-large`、`text-embedding-3-small`、`text-embedding-v4`、`ctg-ac-ultra-latest`、`ctg-og-ultra-latest`。
- `gpt-4o`、`glm-5-turbo` 等命中明确家族前缀的型号必须归入对应标准类别；未命中精确清单或明确前缀的模型必须使用稳定的单模型 `model.<sha256>` fallback 类别。
- 所有新旧标准类别和 fallback 类别在没有已生效规则时都必须返回 `1.0000`；代码、迁移、发布脚本和测试数据不得自动写入财务参考系数。
- 页面、系数配置和 CSV 的中文标准类别名必须一致，其中云供应模型显示 Minimax（阿里云）、Kimi（阿里云）、GLM（阿里云）、Qwen（阿里云），向量类别显示“向量”。
- 结算系数必须以四位定点精度计算，允许 `0.0000` 至 `10.0000`；更新使用版本 CAS，冲突不得静默覆盖。
- Invoice 页面与专用 CSV 必须复用同一消费聚合结果。CSV 文件头只保留组织名称、账期和币种；用户名账号行与未脱敏真实姓名行严格一一对应，真实姓名缺失时保留空单元格。
- Invoice CSV 不包含组织 ID、内部时区/时间戳、规则明细、原始 quota、日志内容、IP、请求 ID、上游请求 ID 或 `other`；金额为无货币符号的六位小数。
- “用户当期成功充值订单金额”和“用户导出时剩余金额”只位于模型归类合计行之后，账号列顺序与表头一致，尾部结算列为空，AI 模型消费汇总不重复输出。
- 当期充值及直接调额净额统计账期内 Stripe、Creem、Waffo、Waffo Pancake 的成功钱包充值与管理员直接调额；增加为正、扣减为负、覆盖取新旧余额差额，并排除订阅订单、EPay、未知渠道、空渠道、非成功订单、兑换码、退款和奖励。
- 上线前管理员直接调额只有完成可信回填后才能计入；没有原始数值事实时必须按数据不完整处理，不得解析格式化审计文案或把零值解释为完整结果。
- 导出时剩余金额必须读取主数据库即时 `users.quota` 并换算为 USD，不读缓存、不伪装为账期末余额；Invoice 账号在主库中缺失时导出失败，不得以零值掩盖。
