# ADR-0002: 组织渠道折扣

取代 [ADR-0001: 组织合同计费](./0001-组织合同计费.md)。合同模型（名称、全局倍率、版本状态机、创建/归档生命周期、成员入口）从未进入提交主干，业务实际需要的能力收敛为：系统管理员为组织配置按渠道独立的折扣，计费请求固定使用开始时的折扣事实，并保留不可变历史供审计。

## Context

- 组织成员在现有用户组倍率之上需要组织级优惠，且不同上游渠道成本不同，需要按渠道配置独立折扣。
- 既有基础设施：`BillingSession` 统一预扣/结算/退款、`PriceData` 请求级价格数据、`TaskPrivateData.BillingContext` 异步结算快照、全局渠道倍率与用户组倍率。
- ADR-0001 的合同实现引入了名称、全局倍率、生效区间、active/archived 状态机、渠道确定后二次查库与 `Reserve` 补扣交互，生命周期与展示概念超出业务需要，且把计费复杂度扩散到同步、异步、WebSocket、任务与 Midjourney 各路径。
- 折扣严格不大于 `1.0`，渠道确定后的目标费用不会超过未打折预扣额，因此不需要补扣路径。

## Decision

1. **领域模型**：每个组织只有一份当前折扣配置。`Organization.CurrentDiscountSnapshotId` 是唯一权威，同时作为乐观锁令牌；无名称、无状态机、无生效区间、无版本号。
2. **存储**：追加式快照表 `organization_discount_snapshots`（`organization_id` 普通索引，主键 `Id` 兼作历史顺序与并发令牌）。`ChannelDiscounts` 用跨数据库兼容的 `TEXT` 保存 JSON 映射，键为渠道 ID，值为定点整数倍率（缩放基数 `1_000_000`）；输入必须精确到最多六位小数，序列化上限 65,535 字节；`1.0` 在保存时归一化为未配置，空映射表示无折扣。
3. **计费关系**：`现有基础计费 × 现有全局渠道倍率 × 组织渠道折扣`。不新增组织全局倍率，不修改用户组倍率与充值价格；未配置渠道按 `1.0`。
4. **请求一致性**：请求首次进入计费解析时通过组织当前指针一次性读取并解析完整折扣快照，固定在 `PriceData.DiscountSnapshot`（快照 ID + 完整内存渠道映射）；无组织或无快照显式记为已解析且折扣为 `1.0`。渠道确定、重试、结算、退款只查该内存映射，不再访问数据库；首次加载或解析失败必须阻断请求，不得降级为默认 `1.0`。
5. **双额度**：`PriceData.QuotaToPreConsume` 为未应用组织折扣的准入/预扣额度，`PriceData.Quota` 为应用实际渠道折扣后的最终额度；`OtherRatios`（时长、分辨率等）对两个值独立生效，不得从彼此反推。`BillingSession` 用未打折额度创建，按折后额度结算并退回差额；不使用 `BillingSession` 的旧 MJ 路径按未打折额度做余额准入、只扣减和记录折后额度。
6. **异步任务**：`TaskBillingContext` 只持久化快照 ID、实际渠道 ID 和已应用倍率（`TaskBillingDiscount`），不保存完整渠道映射；轮询结算、失败退款和 token 差额只使用提交时事实。
7. **管理 API**：仅 Root 可访问，独立挂载 `RootAuth()` 路由组，不进入 `AdminAuth()` 组织管理组：`GET/PUT /api/admin/organizations/:id/discount` 与 `GET .../discount/history`。保存为完整批量替换：单事务内追加新快照并以 `WHERE current_discount_snapshot_id = expected_snapshot_id` 条件更新组织指针，`RowsAffected != 1` 即回滚并返回 `409`，不依赖各数据库互不相同的重复键错误。
8. **历史**：快照只追加、不可变，无编辑/删除/归档/恢复；历史按 `Id DESC` 分页，每份快照与同组织上一份快照比较派生渠道变更，分页额外读取当前页最旧记录的前一份快照避免边界误判；只有组织的第一份快照以空配置作为变更前状态。
9. **审计**：`Log.Quota` 记录已应用折扣的最终额度，Invoice 直接聚合 `Log.Quota` 不再二次折扣；消费日志 `admin_info.organization_discount` 记录 `snapshot_id`、`channel_id`、`ratio`。
10. **数值安全**：倍率定点整数存储；quota 转换继续使用 `common.QuotaFrom*Checked` 饱和保护系列，禁止裸 `int()` 转换；保存前校验渠道为正、真实存在、无重复且倍率在 `(0, 1]`。

## Consequences

- 收益：核心链路删除渠道二次查库、补扣交互与 `ContractChannelBaseQuota` 跨层传递；字段、分支与数据库查询数量低于合同实现；账单正确性唯一依赖请求固定的快照与实际应用倍率。
- 已接受取舍：按未打折价格预扣，用户额度低于未打折预扣额时即使足够支付折后费用，请求仍可能被拒绝；不提供组织全局折扣、免费倍率 `0`、加价、草稿、预约生效、归档或恢复。
- 权限边界收紧：折扣配置与历史仅 Root 可见可改，普通 Admin 即使直接请求 API 也得到 `403`；组织成员不获得折扣配置入口，只看到账单最终结果。
- 旧合同实现与测试表不迁移、不保留兼容层（均为测试数据）；旧表由明确的开发/测试清理步骤移除，不进入应用启动路径。
- 管理员在请求期间保存新折扣只影响之后首次解析计费的请求；并发保存以 `expected_snapshot_id` 条件更新串行化，冲突方整体回滚、不残留失败快照。

## Alternatives Considered

- **组织合同模型（ADR-0001，已取代）**：名称、版本状态机、全局倍率与归档生命周期超出业务需要；渠道确定后的二次查库与补扣交互把复杂度扩散到所有计费格式，且全局倍率带来预扣不足风险。
- **修改用户 `group` 字段实现折扣**：混淆用户分组、路由与模型可用性语义，无法表达渠道级折扣。
- **把折扣逻辑写入渠道适配器**：每个上游渠道重复实现，重试切换渠道时容易重复叠加或遗漏折扣。
- **只在 Invoice 阶段打折**：请求级预扣、准入与日志额度口径与发票金额脱节，无法审计单请求折扣事实。
- **按最低可能折扣预扣**：可在额度临界时放行更多请求，但引入按渠道查库与补扣交互，违背请求固定快照与简化目标，已明确拒绝。
