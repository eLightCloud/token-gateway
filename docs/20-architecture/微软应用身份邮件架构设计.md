# 微软应用身份邮件架构设计

## 系统边界与实现状态

本文维护邮件配置和发信的技术合同。产品交互以[产品设计](../10-product/微软应用身份邮件产品设计.md)为准，早期 SMTP 方案与验证记录见[实施方案](../80-dev/2026-11-05-微软应用身份邮件实施方案.md)。Microsoft 365 模式已切换到 Graph，真实租户已受理网关测试邮件。

业务邮件和设置页测试共用邮件基础设施。租户管理员负责 Entra 应用和发件邮箱授权，网关负责配置、凭据保护、Token 生命周期与邮件提交。用户会话、MFA、验证码和账户恢复仍由现有安全模块管理。

## 当前设计与目标取舍

- 已有 `common/email.go` 提供 STARTTLS／隐式 TLS 和 SMTP 提交；`common/email_ntlm_auth.go` 提供现有认证选择，均无 XOAUTH2。
- 已有邮件配置 UI 使用 `useUpdateOption` 按 key 顺序保存；数据库批量写工具存在，但不能据此推定内存发布、版本冲突和多实例读取已经原子化。
- `GetOptions` 按敏感字段名过滤，新的复合配置必须显式排除；不能把包含密钥的 JSON 当普通设置返回。
- Microsoft 365 使用 Client Credentials 和 Graph `sendMail`。现有 SMTP 模式使用所配置的 SMTP 服务。
- 首版用 Client Secret，支持 UI 管理；证书、联合凭据、用户委托及多云端点不预建抽象。

复用根模块已有 `golang.org/x/oauth2`，优先采用其 Client Credentials 与 TokenSource；若它的错误响应或刷新策略不满足本合同，在外层做有限封装，不引入通用 OAuth 平台。JSON 操作全部使用 `common.*`，`relaykit/` 不参与。

## 配置权威源与持久化

新增受保护 Option 键 `EmailDeliveryConfig`，单行 TEXT JSON 保存完整邮件配置和 `revision`，成为首次专用保存后的唯一权威源。不存在该行时，以现有 SMTP options 生成只读 `revision=0` 的 legacy 快照；仅此条件允许兼容读取。旧 TLS 布尔项在数据库中缺失时保留现有环境变量及别名默认值；数据库显式 false 优先，首次保存固定该快照。行已存在但无法解密或解析时报告不可用，不能回退旧配置。

内部配置包含：

| 字段 | 合同 |
| --- | --- |
| `revision` | 非负整数，每次成功保存递增；用于乐观并发与缓存隔离 |
| `auth_mode` | `legacy` 走现有 SMTP，`microsoft_oauth2_app` 走 Microsoft Graph。缺少新配置时为 legacy |
| `legacy` | 对应原 SMTP 主机、端口、账号、发件地址、TLS 和兼容选项；密码凭据在新行中加密 |
| `options.microsoft.tenant_id/client_id/mailbox` | 租户 GUID、应用 GUID、单个合法发件邮箱；不接受 CR/LF 或额外收件地址 |
| `client_secret_ciphertext` / `legacy_password_ciphertext` | 带版本的认证加密密文，绝不作为读取 DTO 字段 |

Microsoft 模式使用固定的国际版 Graph HTTPS 端点和证书校验，`mailbox` 填写发件邮箱的 Microsoft 365 登录地址。已有 Microsoft 配置沿用同一模式值和加密凭据。两套配置可同时保存，发送时只使用当前模式。

专用保存 API 在一笔 GORM 事务内创建或更新配置行，检查 `expected_revision`。并发首建需处理唯一冲突，更新用版本条件确保冲突返回 409；采用悲观锁时只用 `lockForUpdate(tx)`。严禁“先读后无条件覆盖”。成功提交后发布一个完整不可变快照；数据库失败不发布。请求从开始到结束只读取一个版本。

通用 `GetOptions` 显式排除新复合键；通用单项／批量配置写入口禁止绕过专用合同修改新键或原 SMTP keys。旧 SMTP keys 保留为升级前基线，不作为新配置的镜像写回。专用读取接口提供兼容字段和配置标志。若存在仍读取旧 SMTP 配置的其他消费者，实施前逐一迁移到快照；不能同时维护两套有效配置。

多实例继续沿用已有 `SyncOptions` 周期，但必须一次解码／校验／发布邮件快照，不逐字段改写运行变量。保存节点提交后立即生效，其他节点在现有同步周期内收敛；UI 不能宣称全节点瞬时切换。每个节点维护自己的 Token 缓存；配置版本变化时替换来源，不共享或持久化 Token。测试 API 从主库确认所请求版本，并在该请求中使用对应完整快照；节点本地仍是旧版本时不能测试旧配置后返回新版本成功。保存提交后的内存发布异常须报告失败并从主库重建，不能用旧运行快照伪装保存成功。

## 配置与测试 API 合同

以下接口已实现；GET 返回 `revision/options` 与 configured 标志，PUT 请求体为 `{intent, legacy_password, client_secret}`，其中 intent 包含整组非秘密配置、expected_revision 与凭据动作：

| 方法与路径 | 请求／响应 |
| --- | --- |
| `GET /api/option/email_delivery` | 脱敏完整配置、`revision`、`legacy_password_configured`、`client_secret_configured`、`storage_key_ready`；`Cache-Control: no-store` |
| `PUT /api/option/email_delivery` | `expected_revision`、完整非秘密配置、凭据动作；成功返回新版本脱敏配置 |
| `POST /api/option/email_delivery/test` | `expected_revision`、一个 `recipient`；使用已保存版本发送固定内容测试邮件，不接收应用密钥或自定义邮件内容 |

凭据写入分别使用 `legacy_password_action`、`client_secret_action`，枚举统一为 `keep/replace/clear`；只有 replace 可携带非空新值，keep/clear 不允许同时提交值。空白输入由 UI 转成 keep，不能作为清除。Tenant／Client ID 改变必须 replace；活动 Microsoft 模式禁止 clear；legacy 切回时按现有 SMTP 语义校验，可显式保留免认证中继。

UI 表单保存独立的已读取版本基线，保存与测试均绑定该版本；后台查询发现新版本时保留当前草稿，禁用保存与测试并提示显式重新读取。重新读取或本次保存成功后才更新基线，避免显示旧值却测试新版本。

保存和测试沿用现有 `success/data/code/message` 响应风格。测试报告附关联 ID 和脱敏结果。Graph 返回 HTTP 403 时，报告提供 `reason=GRAPH_ACCESS_DENIED`，界面提示核对应用的发件邮箱授权。

Root 会话授权在服务端执行。写入与测试启用现有 `SessionCookieOriginGuard`、请求体限制及限流；敏感证明使用 `X-Security-Proof`，新增 scope `email.delivery.settings.write` 和 `email.delivery.test.send`，绑定本次规范化操作上下文并按现有框架一次消费。保存 scope 的 context 为 expected_revision、完整非秘密配置及两种凭据动作；测试 scope 的 context 为 expected_revision 与规范化 recipient。服务端使用同一规范化函数分别处理验证请求和执行请求，按现有框架绑定其摘要。秘密值不进入验证 context、证明或可公开摘要；UI 在发起验证前冻结本次待提交对象，任何草稿修改都取消该次提交。证明缺失、过期、重放或上述非秘密上下文变化时拒绝执行，不能以 Root 角色代替证明。

测试采用系统级和操作者级限流，目标初始上限为每操作者每分钟 3 次、全系统每分钟 10 次；所有节点共享计数，不能把 SMTP 提供方限流当作应用限流。Redis 缺失时按现有单实例降级能力限流，并明确多节点部署要求；限制在网络调用前执行。

测试结果包含配置版本、服务端时间、关联 ID 和阶段。Microsoft 模式报告 `config/token/graph_submit`，现有 SMTP 报告 `config/token/connect_tls/auth/submit`，其中 SMTP 的 Token 阶段为 `skipped`。阶段状态为 `passed/failed/skipped/unknown`。提交结果未确认时报告 `EMAIL_DELIVERY_UNKNOWN`。

## Token 与发送控制流

```text
业务邮件／Root 测试邮件
  → 统一发送流程（测试限定 expected_revision）
  → 一份配置快照
  → legacy：现有 SMTP 连接和认证 → MAIL FROM / RCPT TO / DATA
  → microsoft_oauth2_app：缓存 Graph Token → POST /v1.0/users/{mailbox}/sendMail
  → 邮件服务已受理／失败／结果不确定
```

应用身份向 `https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token` 请求 `grant_type=client_credentials`，Scope 固定为 `https://graph.microsoft.com/.default`。Graph 请求使用 Bearer Token，提交 HTML 正文并设置 `saveToSentItems: false`。HTTP 202 表示 Graph 已受理邮件。

Token 有效期采用服务返回值并预留刷新余量；并发刷新合并，网络请求不持有缓存互斥锁。每个调用者可独立取消等待，最后一个等待者退出时取消实际 HTTP 请求，共享请求最长 15 秒。缓存按配置版本和租户／应用／邮箱隔离。旧版本正在刷新的结果不能写回新版本来源。过期 Token 或刷新失败不能继续发信，也不能降级 Basic／匿名。Token HTTP 客户端只访问固定端点、拒绝跨主机重定向，设置超时并限制响应大小；SMTP 连接、TLS 握手和读写均设置有界超时。

Graph 提交客户端拒绝重定向并设置超时。只有首次 HTTP 401 会刷新 Token 并重试一次。网络断开和 HTTP 5xx 按提交结果不确定处理，调用方先查收件箱。SMTP 在 DATA 后遇到不确定结果时也不自动重发。

## 凭据、安全与失败策略

新增部署密钥 `EMAIL_DELIVERY_STORAGE_KEY`，要求 Base64 解码后恰好 32 字节，用于 AES-256-GCM、随机 nonce、版本化密文及字段用途 AAD。主密钥位于数据库之外，所有副本一致；已保存凭据遇到缺失、非法或错误密钥时，接口返回 503／`EMAIL_ENCRYPTION_UNAVAILABLE`，UI 提示在所有实例恢复原密钥并重试，不提供清空或自动换钥。密钥不可用时拒绝新配置中秘密的保存或解密，不明文落库，不临时生成替代密钥。不能复用或改造现有 MFA／登录密码加密生命周期。更换主密钥必须先停写、使用旧密钥解密重加密并验证备份恢复，不能直接替换环境变量。

旧配置首次接入时，已有 SMTP 密码也转成新行中的密文，原历史 option 作为兼容基线留存；不声称旧表和历史备份已消除明文。旧数据清理属于单独受审操作。界面及 GET DTO 永远不包含新旧密码、Token 或密文。表单密钥不进入 URL、localStorage、sessionStorage、查询缓存或持久 mutation 缓存；使用 `gcTime: 0` 并及时清除携密对象。

邮件配置能重定向身份邮件，属于敏感安全操作。审计记录操作者、操作、配置版本、字段名、成功／失败和关联 ID；不记录凭据、证明、验证码、邮件正文或 Token 响应。受限日志可记录经过白名单处理的 Entra/SMTP 错误码，不记录完整认证报文。

安全基线为 OWASP ASVS 5.0.0，适用领域包括 OAuth、会话与再认证、访问控制、配置与秘密管理、TLS、错误与日志。已核对稳定版条目并在实施方案记录访问控制、TLS、浏览器秘密保护和日志错误处理的验证映射；真实租户授权和多实例验收尚未完成，本文不宣称整体合规。Client Credentials 无浏览器授权回调，因此不新增 PKCE／state 登录流程；管理界面现有会话的 CSRF 与敏感证明仍需验证。

## 验证策略与发布边界

- 单测覆盖完整 SMTP 协议及 Token 缓存、配置失败和隐私合同；优先扩展现有 suitable 测试，完整列表见实施方案。
- 配置持久化涉及数据库行为，必须跑真实 SQLite、MySQL、PostgreSQL，验证旧版本数据库升级、并发保存、冲突、回滚和重复启动。
- UI 与 API 联调必须走真实保存、二次验证、刷新和测试按钮，而不是仅用 curl 证明后端可用。
- 真实 O365 租户需要同时验证可发送和越权邮箱不可发送；尚无租户凭据时可继续本地实施，但真实租户验收仍是未完成门禁。
- 旧二进制不理解新配置，代码回滚前应先在新版本显式切回已验证 legacy 配置并停发／协调所有副本；不能自动把新行解密导出或默默退回旧密码。若 legacy 已不可用，采取前向修复，不承诺旧二进制可继续 OAuth 发信。
