# 架构概览

## 分层结构
系统遵循 Router -> Controller -> Service -> Model 的分层结构。

## 主要模块
- `router/`：HTTP 路由入口，包含 API、relay、dashboard 与 web 路由。
- `controller/`：请求处理与接口响应。
- `service/`：业务逻辑与跨模块编排。
- `model/`：GORM 数据模型与数据库访问。
- `relay/`：AI API 代理与 provider 适配。
- `setting/`、`common/`、`dto/`、`types/`：配置、公共工具、数据结构与类型定义。
- `web/default/`：默认前端。

## 组织扩展边界

详细设计见 [组织与组织账单架构设计](./组织与组织账单架构设计.md)。

组织模块是现有个人账号体系之上的扩展，与个人计费有两个接触面：

```text
个人扣费链路：请求 -> Token -> User -> 个人钱包/订阅 -> Log
折扣接触面：组织渠道折扣作为计价乘数进入请求计价（请求开始固定快照，复用 BillingSession 预扣/结算）
组织汇总链路：OrganizationMember.UserId -> Log.UserId -> 组织报表与 Invoice 月度汇总
```

组织模块维护：

- `Organization`：组织基本信息与当前折扣快照指针。
- `OrganizationMember`：成员、角色和成员有效期。
- `OrganizationDiscountSnapshot`：按渠道独立的组织折扣/加价快照（追加式不可变历史）。
- 组织报表权限。
- 按成员有效期汇总的组织账单视图与 Invoice 派生月度汇总。

组织没有自己的资金路径：预扣、结算、退款、充值和订阅始终由用户自身链路执行，组织折扣只改变计价乘数。组织不参与 Token 鉴权，现有 API 请求不会携带或选择组织，组织归属只由当前登录用户的有效成员关系推导。

## 接口分层

- 用户侧组织接口使用 `current` 语义，后端根据当前用户唯一有效成员关系找到组织。
- 管理员组织接口使用显式组织 ID，供系统管理员跨组织维护和排查。
- 组织账单接口只读现有日志，不写账务数据。

## 文本流生命周期

已建立的按 Token 计费文本流将“客户侧输出”与“上游读取”分为两个正交状态。客户断开后停止写出，但在有界时间内继续取得协议终态与 usage；只有成功终态与完整权威 usage 同时成立才通过原结算入口。详细设计见 [文本流断开续读架构设计](./流式断开续读架构设计.md)。
