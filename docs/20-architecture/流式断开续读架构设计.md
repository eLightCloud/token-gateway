# 文本流断开续读架构设计

## 系统边界

本设计只适用于“按 Token 计费、上游流已建立、客户侧在协议终态 usage 到达前结束”的文本生成流。它不改变正常完成、非流式、响应头返回前取消，也不适用于独立图片、视频和音频端点。

核心边界是将客户侧输出生命周期与上游读取生命周期分离，同时继续复用原预扣、结算、退款和消费日志路径；不建第二套账本、异步核销 worker、pending 表、attempt 树或上游账单连接器。

## 当前控制流

```text
已建立的上游文本流
  -> 客户侧在线：沿用原扫描、写出、timeout 和 fallback 语义
  -> 客户侧结束：SetEndReason(client_gone)
       -> 停止 SSE/PING/终态响应写出
       -> 继续解析上游事件与 usage
       -> 协议成功终态 + usageComplete
            -> upstream_result=terminal_success
            -> ValidateTextStreamCompletion 通过
            -> 原结算入口执行一次
       -> 失败终态 / usage 缺失 / 异常 EOF / 读取或处理错误 / 超时
            -> 记录独立 upstream_result
            -> 结算门拒绝普通成功结算
```

`end_reason` 使用首次写入语义，`client_gone` 不会被后续上游成功或错误覆盖。`StreamStatus` 通过并发安全访问器独立保存 `upstream_result` 与 `upstream_error`，消费日志将两个维度写入同一条 `other.stream_status`。

## 上游结果与结算门

断开后上游结果使用固定语义：

- `terminal_success`：协议成功终态已确认；仍须 `usageComplete=true` 才可结算。
- `protocol_failure`：上游明确失败终态。
- `usage_missing`：到达终态，但缺少完整权威 usage。
- `incomplete_eof`：传输结束时没有完整协议终态或 usage。
- `scanner_error` / `handler_error`：读取或协议处理错误。
- `idle_timeout`：断开后长时间没有有效业务事件。
- `drain_timeout`：从 `client_gone` 起计的不可重置绝对上限到期。

`ValidateTextStreamCompletion` 是文本流唯一成功结算门：只有 `terminal_success && usageComplete` 通过。`ResponseText2Usage` 等本地估算只能作降级证据，不能被标记为权威上游 usage。

## 超时与资源释放

断开后续读同时受两个边界控制：

- 空闲超时只由有效业务事件重置；空行、注释、PING 和无效数据不续期。
- 绝对上限从 `client_gone` 起计且不可重置。第一版复用 `STREAMING_TIMEOUT`；有效值小于等于 0 时使用 300 秒安全上限并记录配置告警。

请求处理函数等待上游结束或超时后再返回，不将 Gin Context 交给脱离请求生命周期的后台任务。所有终止路径都必须关闭对应 HTTP body、SDK event stream 或 WebSocket，并等待读取 goroutine 退出。

## 传输适配

业务规则不按 Provider、域名、渠道 ID 或模型分支，但传输层按各自机制窄接入：

- 共享 scanner 和同步直接 scanner 的 HTTP 文本流；
- Cohere/Zhipu 的 scanner + channel；
- AWS Bedrock SDK event stream；
- 讯飞 WebSocket + channel；
- PaLM buffered whole-body read。

协议 handler 各自负责判定成功终态与 usage 完整性，共享生命周期不重新实现协议解析。Dify/Coze 在部分 usage 与本地估算分界上的已知遗留见 [流式断开续读 dify/coze 遗留缺陷](../50-planning/流式断开续读-dify-coze-遗留缺陷.md)。

## 失败策略与保持不变项

- 客户已断开时无法再接收错误，但网关仍记录上游结果并经现有错误/退款路径收口。
- 续读失败且上游已产生的无法证明 Token 成本由网关承担，不事后补收、不人工改账。
- 不按 api02、渠道、模型或传输类型建立不同客户计费政策。
- 不增加数据库迁移、后台核销、人工数据导入或第二条消费日志路径。

## 验证策略

确定性回归覆盖共享 scanner、直接 scanner、scanner + channel、SDK event stream、WebSocket 和 buffered read，并验证成功终态、usage 缺失、协议失败、异常 EOF、读取/处理错误、空闲/绝对超时、停止客户写入和资源释放。

已配置的真实 Claude Messages 和 OpenAI Responses 断开样本均取得非零终态 usage；Claude 缓存样本保留缓存读取分项，消费日志可同时表达 `client_gone + terminal_success`。未配置真实账号的传输以协议级可控流回归验证，不外推为所有供应商已完成线上验收。
