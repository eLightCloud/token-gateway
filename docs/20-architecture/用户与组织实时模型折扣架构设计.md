# 用户与组织实时模型折扣架构设计

## 系统边界

本设计定义待实施的用户与组织实时消费倍率合同。业务唯一见 [产品设计](../10-product/用户与组织实时模型折扣产品设计.md)，交互见 [UI设计](../90-ui-ux/用户与组织实时模型折扣UI设计.md)，实施、未决项和证据见 [实施方案](../80-dev/2026-11-05-用户与组织实时模型折扣实施方案.md)。本文不代表新模型或 API 已存在。

实时消费定价归属宿主计费层，组织 Invoice 仍为统计层，不负责资金副作用。路由授权、代理采购记账、钱包/订阅资金来源及协议转换保留原职责；`relaykit/` 不依赖宿主的用户、组织或数据库。

## 当前设计与既有配置边界

已有用户配置 `ResellerModelConfig` 以用户、模型、渠道逐项保存倍率；普通用户读取会过滤倍率 1。已有组织 `OrganizationDiscountSnapshot` 仅按渠道保存倍率，部分实时路径先乘该组织倍率，再乘个人倍率；组织折扣预扣还保留低于 1 时按原价准入的策略。这些现状不能直接实现本专题。

既有组织渠道倍率作为独立旧配置保留，不自动改成 1，也不改写历史；它不是本专题组织继承规则的数据源。新有效消费倍率只从新增实时规则解析一次。迁移期间，旧倍率按原语义属于系统基础费用的一部分，日志分开记录；运营希望没有旧因素影响时，须显式将旧配置置 1。Invoice 结算系数继续仅影响其既有统计结果，不参与新实时预扣。

因此“用户与组织不叠加”指本专题两种实时消费来源互斥，不表示自动取消旧配置。上线前必须列明非 1 旧配置及其影响，禁止宣称所有旧配置只在事后生效。已有发票、历史任务及请求继续按原快照恢复。

## 职责与依赖

- 独立领域模型维护主体、模型、倍率、适用渠道、主体配置总版本和不可变历史；控制器使用新 DTO 和独立接口。旧消费写端点的过渡处理见切换合同，不静默改变旧请求含义。
- 独立计价解析模块是用户/组织/系统优先级的唯一 owner；预扣、结算、任务和价格展示共同消费其结果，不各写一个 fallback。
- 渠道选择仍依赖既有启停、分组、Token 限制、授权、亲和与重试。折扣渠道集合不得注入 `ChannelConstraints` 当作授权过滤。
- 代理客户原授权仍限制候选；消费倍率规则不能扩大授权、改写代理采购倍率或从客户折后费用反推代理成本。
- 复用 `BillingSession`、资金事务、journal 和任务恢复入口，不创建另一套钱包扣退链路。

## 数据模型

拟定实时规则拥有“主体类型、主体 ID、精确模型名、模型摘要键、定点倍率、非空渠道集合、配置版本”。具体表名和 DTO 在实施评审固定。

- 数据库保证 `(主体类型, 主体 ID, 模型键)` 唯一；同模型的渠道范围放在该规则内或独立关联表，不在各渠道重复保存可独立修改的倍率。
- 使用关联表时保证 `(规则 ID, 渠道 ID)` 唯一，并在规则、关联、版本及历史同一事务提交；使用 TEXT 集合时需验证长度上限及三库序列化行为，不用依赖方言的 JSON 列。
- 长模型名使用摘要索引时保留原文并校验完整名称，不用截断制造唯一性。摘要碰撞、重复规则、非法倍率及损坏数据均报错。
- 用户和组织倍率均以十进制字符串输入，范围 `(0, 5]`、最多两位小数，保留现有百万分制定点单位，新配置存储 `10000..5000000` 且必须是 10000 的整数倍。显式 1 保存为 1000000；个人规则用 `disabled` 表示停用，存量规则缺省为启用。停用保留倍率和渠道范围，删除规则也恢复继承。空渠道集合不是有效规则。禁止自动四舍五入或截断超精度输入，不额外引入另一套倍率单位。旧快照合法范围及精度按原版本解释，新规则校验不得直接拒绝旧快照。
- 配置主体及归属由服务端权限边界确认，不信任请求中的用户或组织标识授予权限。

### 主体总版本与保存事务

为每个 `(主体类型, 主体 ID)` 维护持久配置头 `revision`。整份保存提交 `expected_revision`，条件更新配置头后在同一事务替换规则/渠道集合、追加历史并提交；任一步失败整体回滚。单规则版本可以用于追溯，不能替代整份保存的总版本。

删除最后一条规则仍保留配置头且递增版本；重建不从零开始，避免旧页面在删后重建时误通过。并发修改不同模型同样返回 409；响应返回当前总版本，不自动覆盖或合并草稿。写入成功返回本次提交版本的结果，不在事务外无条件重读而冒充本次保存结果。

组织配置、候选、历史及默认折扣预览仅 Root。组织预览仅读取组织配置版本并解析组织草稿。用户配置沿用现有资源权限，不能通过组织 API 修改个人规则。

### 个人历史分页与管理差异

个人脱敏历史接口 `/api/reseller/personal/history` 返回每条记录的 `cursor`，客户端将最后一条游标原样作为下一页的 `cursor` 查询参数，单页最多 50 条。新旧历史按生成时间、计价版本、各自版本号降序合并；游标包含三者的定位事实，不能用两套独立的 `revision` 共享同一个 `before` 截断。所有游标查询仍必须绑定当前用户，游标不授予主体访问权。

旧阶段继续支持 `before`；启用后带正数 `before` 的请求明确返回非法参数，要求使用 `cursor`，不以成功响应掩盖漏页。非法游标同样拒绝。新旧阶段均返回可继续翻页的游标。计价版本和原版本号不改写。

管理历史响应增加 `previous_items` 和 `operator_name`；服务端多取一条历史以提供本页最后一项的前态，前端据此展示倍率与渠道差异，用户名不可得时保留操作者 ID。该响应仍受管理资源权限约束，不能用于最终用户的脱敏历史接口。

### 请求与任务快照

请求首次解析固定当前组织关系及相关模型的用户、组织规则版本，包含未配置事实和不可变渠道集合。不在每次重试重新查询当前配置，不要求复制全平台矩阵。

以上读取必须在主库同一一致性快照事务完成：MySQL/PostgreSQL 使用 Repeatable Read，SQLite 使用同一 Serializable 读事务；所有查询显式复用同一个 `tx`，禁止中途调用使用全局 DB 的读取函数。组织关系、配置头、规则和渠道集合都在此边界内读取，包括无组织、无规则事实。若旧组织渠道倍率进入基础费用，其相关快照也在该事务固定。首次读取失败则整体失败，不复用部分读取结果拼接重试。

新消费规则与组织关系不依赖事务外旧缓存；模型广场与管理员预览可单独创建一致快照，不能混入某个执行中请求的定价快照。原安全停用校验继续独立执行。

实际选中渠道后保存生效结果：`source=user|organization|system`、倍率、模型、实际渠道、关联规则/版本及必要组织标识。system 明确为 1。任务仅持久化执行所需的确定结果及原费用基数，不保存整个组织配置矩阵。

历史任务没有新字段时保持原快照路径，不以缺字段为理由查新配置重算；新增格式需要显式版本，避免把旧快照解释成继承指令。

## 数据与控制流

1. 鉴权及原资格检查后，读取并冻结当前请求模型的相关规则、版本和组织关系；合法缺失表示继承，数据库错误或损坏数据阻断计价，不能伪装为无配置。
2. 原路由选择实际渠道，原引擎计算不含本专题实时倍率的预估基础费用。
3. 解析器依次判断已启用的用户模型规则是否覆盖渠道、组织模型规则是否覆盖渠道，否则取 system/1。只输出一个有效倍率。
4. 通过统一 quota 安全转换得到折后预扣目标，按下文信任策略检查资金与受限 Token 后发送；非信任请求真实预扣。不得先用未折扣金额拒绝再补应用倍率。
5. 换渠道时用同一冻结规则重新匹配目标；非信任请求更高目标先补扣，不足不发送；更低目标可沿原流程在最终结算释放，避免重试中反复扣退。信任请求沿下文免预扣策略。
6. 成功结算对实际基础费用应用执行渠道的冻结倍率一次；任务、失败、退款和恢复使用既有资金入口及原累计事实，保持幂等。

### 信任免预扣

保留原 `shouldTrust` 资格条件，不因倍率来源或显式 1 改变资格。符合条件时实际预扣与 Token 暂扣沿原规则可为零，最终按本次冻结倍率结算；非信任请求才真实预扣折后目标。代理客户、订阅和强制预扣任务沿用原旁路限制，不新增免预扣情形。

免预扣前的余额准入仍使用折后目标，不先按原价拒绝。信任请求重试沿原资金策略处理，不将“更高目标补扣”解释为强制取消原免预扣；非信任请求必须补扣成功再发送。两种路径都保存结算所需来源、倍率、基数及生命周期事实，免预扣不得跳过任务恢复或最终记账。Midjourney 在请求发送前固定 `wallet_only` 并设置强制预扣，避免订阅直到上游受理后才被任务持久化合同拒绝；提交 journal、结算与退款沿原钱包路径。其消费日志从本次请求冻结事实写入个人倍率、来源及版本。

### 旧个人消费规则迁移与切换

使用一次受控切换，不运行双写或按缺失自动读旧个人倍率的长期 fallback：

1. 部署具备旧/新快照识别能力的版本到所有处理请求及任务的实例；尚不启用新规则读取。盘点旧接口消费者、模型多倍率及新精度冲突，未解决不切换。
2. 在所有实例停止消费倍率配置写入，保留调用与旧快照结算；取得配置版本和可恢复备份，再次核验写入已停止。若与代理授权共用接口，对混合写入在切换窗口整体拒绝，不能部分保存。
3. 仅把仍存在、未软删除的非代理消费主体的旧个人倍率聚合成新规则，SQL NULL 身份列按普通用户纳入。软删除、硬删除和孤立主体的旧记录保持不变且不参与启用校验，不自动清理或恢复。同模型不同倍率、不能精确转换到百分制或范围不合法的记录必须先经明确处理。保留授权、采购倍率和历史原数据，不在其上做自动清理。
4. 校验迁移前后规则数量、渠道集合、显式 1、权限与价格对照，持久化迁移完成事实；所有实例通过同一个生效边界启用新读取，禁止新旧实例各自决定。一旦无法确保一致切换，先停止新请求准入，处理完再恢复，不让同一配置被随机计价。
5. 切换后新请求只读取新消费规则，旧个人倍率不再额外乘入；旧请求/任务依据快照版本走原结算。普通用户的旧个人消费写入口所有请求均返回迁移冲突，包括空列表删除，不能成功写入已不生效的旧倍率；授权/采购入口若共用则先拆分对应职责，新 UI 只调用新消费端点。旧 API 拒绝写入属于需要登记和验证的兼容变化，不以改字段含义掩盖。

迁移前失败不启用新读取，回到旧配置写入需确认未提交新配置；迁移成功但未启用时失败可清理仅本次迁移产物后重做。启用后不得直接回滚到不能解释新快照的旧二进制或恢复旧数据库覆盖新资金事实；应暂停配置写入，保留快照兼容版本修复并恢复。确需反向切换时必须另行生成数据对照和回退方案，不能在普通启动中自动执行。

## 约束与取舍

- 系统价格、用量计算、原有分组及旧配置规则继续决定基础费用；本专题不修改表达式语言，不把同一倍率再次加入 `OtherRatios`。
- 显式 1 与未配置不可合并。用户规则覆盖其他渠道不阻断组织继承；同一模型不同实际渠道可有不同最终倍率。
- 请求固定的组织身份只用于本次定价，不代替原有安全停用检查；配置变更不能撤销已产生的消费事实。
- 全选保存明确渠道集合，不动态覆盖未来渠道。渠道失效不自动重写财务配置，路由仍不得选失效渠道。
- 旧快照、账单、代理授权/采购合同继续保留；不能为合并 UI 顺带重构它们。与 ADR-0002/0003 有关的生效、基数和预扣差异，在实施前补充必要决策说明，不将本设计当成旧决策已实施的证明。

## 验证策略

覆盖来源选择、显式 1、部分覆盖、规则删除、相同倍率不同范围、同模型重复规则、折后准入、换渠道补扣、配置/成员变更、异步与历史任务恢复、零费用、溢出及退款守恒。价格展示与真实结算使用同一解析器。

涉及持久化的实现必须在真实 SQLite、MySQL、PostgreSQL 上验证新建和代表性升级，启动两次证明幂等，保留原数据及唯一约束；共享日志路径覆盖独立日志库。具体版本、命令和结果记录于实施方案，不用单元测试或编译代替数据库矩阵。
