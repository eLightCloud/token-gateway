# New API HK-SG 多实例部署架构

## 业务目标

### 目标用户

- 主要服务中国大陆地区用户。
- 所有用户使用同一个公网域名，统一从中国香港（HK）入口访问。

### 访问与出口目标

- New API 控制台、静态网站和管理 API 始终由 HK 节点提供，优先保障中国大陆用户的访问速度。
- DeepSeek 等适合从 HK 访问的模型，转发到 HK New API，使用 HK 网络出口。
- GPT 等需要境外网络出口的模型，由 HK 入口通过云内点对点网络转发到新加坡（SG）New API。
- 客户端无需选择 HK/SG 域名，入口根据 Relay 请求中的 `model` 自动选择节点。

### 架构约束

- HK 和 SG 均部署完整的 New API 实例。
- PostgreSQL 和 Redis 部署在 HK；HK 和 SG New API 共享这套权威数据面。
- HK-SG 跨区域访问使用 CEN 私网跨地域连接；SG 访问 HK 数据面产生的跨区延迟见 [数据面放置与延迟预算](#数据面放置与延迟预算)，上线前必须实测达标，不以“可接受”作为默认假设。
- 不部署独立的模型路由服务；由 HK OpenResty 在 Nginx 请求处理阶段完成模型解析和 upstream 选择。
- 单个 Relay 请求只能由一个 New API 实例完成鉴权、渠道选择、预扣、结算和日志落库。
- SG New API 不提供公网入站服务，只接受 HK OpenResty 通过 HK-SG 私网发起的请求；SG 仅需通过受控公网出站访问模型上游。

## 最终方案

### 使用 OpenResty（最推荐，无需编译）

OpenResty 是基于 Nginx 和 LuaJIT 的高性能 Web 平台，已经集成 `ngx_http_lua_module` 和常用 Lua 库。本方案使用 OpenResty 替代 HK 入口的标准 Nginx，不增加独立路由服务。

**是否需要编译：**不需要。Ubuntu、Debian 和 RPM 系发行版可以通过 OpenResty 官方软件仓库直接安装 `openresty` 包，无需手动编译 Nginx 或 Lua 模块，常规环境通常几分钟即可完成安装。

**实施步骤：**

1. 按操作系统添加 OpenResty 官方软件仓库，安装 `openresty` 包。
2. 执行 `openresty -v` 验证安装；如果命令不在 `PATH` 中，使用 `/usr/local/openresty/bin/openresty -v`。
3. 在 `nginx.conf` 中使用 `access_by_lua_block`、`access_by_lua_file` 或 `content_by_lua_block` 等指令加载 Lua 逻辑。
4. 本场景需要在 `proxy_pass` 之前选择 upstream，因此实际路由使用 `access_by_lua_file`；`content_by_lua_block` 主要用于由 Lua 直接生成响应。
5. 执行 `openresty -t` 检查配置，通过后再 reload。

OpenResty 官方安装说明：<https://openresty.org/en/installation.html>

### OpenResty 可靠性判断

- 本方案继续使用 OpenResty。标准 Nginx 本身不能直接执行 Lua；要使用 `access_by_lua_file`，仍需额外安装或自行编译 `ngx_http_lua_module`、LuaJIT 及配套库。
- OpenResty 是将 Nginx、LuaJIT、`ngx_http_lua_module` 和配套补丁一起验证、发布的发行版。相较于在标准 Nginx 上自行拼装 Lua 动态模块，它减少了模块 ABI、版本兼容和安全更新不同步的风险。
- 可靠性边界主要不在 OpenResty 软件本身，而在入口高可用和自定义 Lua 逻辑。生产环境固定到经过预发布验证的官方包版本，不自动跨版本升级；升级必须经过配置检查、协议回归、灰度和可回滚发布。
- 生产路由 Lua 只做本地、确定性的模型解析和表查询，不访问网络或数据库，不记录请求体，并避免长耗时或无上限的阻塞操作。路由规则、请求体上限和解析失败策略必须有自动化回归测试。
- 单台 HK OpenResty 仍然是单点。要求高可用时，应在 HK 部署至少两个无状态 OpenResty 实例，由云负载均衡提供健康检查和故障摘除；这项措施比将 OpenResty 换成自行组装 Lua 模块的标准 Nginx 更直接地提升可用性。

### 已知机器与容量判断

一期机器规格保持不变：

| 节点 | 实例规格                          | 部署组件                              | 容量判断                                                                             |
| ---- | --------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------ |
| HK   | `ecs.g9i.xlarge`，4 vCPU / 16 GiB | OpenResty、New API、PostgreSQL、Redis | 算力和内存可作为一期起步配置；风险主要是四个组件资源争抢和整机单点，不是实例规格过低 |
| SG   | `ecs.c9i.xlarge`，4 vCPU / 8 GiB  | New API                               | 对纯 Relay 节点通常足够；主要关注长连接、跨区数据面延迟和公网出站，而不是内存容量    |

- 月消费金额不能直接换算为 QPS；模型单价、平均输入/输出 Token、流式时长和图片/音视频占比都会显著改变实际负载。是否足够必须以峰值 QPS、并发流式连接数、峰值 Token/s 和日志写入速率压测确认。
- HK 机器上 PostgreSQL 建议从约 3–4 GiB `shared_buffers` 起步，Redis 设置明确的 `maxmemory`（初始可取 1–2 GiB），其余内存留给 New API、OpenResty、内核页缓存和峰值请求体；最终参数以监控和压测结果为准。
- PostgreSQL 数据不得只依赖系统盘。使用独立 ESSD 数据盘，初始容量至少 200 GiB 并保留在线扩容空间；启用定时快照、WAL 归档或等价的时间点恢复能力，并实际演练恢复。
- 消费日志会持续增长。必须定义日志保留期和批量清理策略；当日志达到千万级或明显影响业务事务时，通过 `LOG_SQL_DSN` 将日志库拆到独立 PostgreSQL 或 ClickHouse。
- 原计划的 HK 5 Mbps 公网出口和 SG 2 Mbps 公网出口不纳入机器规格约束，按下面的网络容量要求单独调整。

## 部署拓扑

```text
中国大陆用户
  |
  | HTTPS（唯一公网入口）
  v
HK OpenResty
  | TLS / 前端 / API 入口
  | Lua 解析 model 并选择 HK/SG
  |
  +-- 控制台、管理 API ------> HK New API Master
  |
  +-- DeepSeek 等 HK 模型 --> HK New API Master --> HK 适配上游
  |
  +-- GPT 等 SG 模型 ------> HK-SG CEN 私网跨地域连接
                                  |
                                  v
                            SG New API Slave
                            （无公网入站）
                                  |
                                  +--> NAT/EIP 公网出站 --> GPT 等 SG 适配上游

HK New API Master --------+
                          +--> PostgreSQL + Redis（HK 本机数据盘）
SG New API Slave -- CEN --+

HK 和 SG New API 通过云内网络共享同一套业务状态。
```

## 节点职责

### HK OpenResty

- 作为用户日常访问的唯一公网入口。
- 负责 TLS 终止、前端静态资源、控制台 API 反向代理和 Relay 模型路由。
- 从 JSON Body、URL 路径或 Query 中提取 `model`，按单一规则集选择 HK 或 SG upstream。
- 不执行 New API 鉴权、渠道选择和计费逻辑。

### HK New API

- 处理登录、用户、Token、渠道、日志和其他 New API 控制面功能。
- 处理分配到 HK 的 Relay 请求。
- 作为唯一 New API 主节点，执行数据库迁移和后台定时任务。
- 部署 PostgreSQL 和 Redis，通过本机或 HK 私网端点向 HK/SG New API 提供共享状态。

### SG New API

- 处理分配到 SG 的 Relay 请求。
- 设置 `NODE_TYPE=slave`，不执行数据库自动迁移和主节点后台任务。
- 不绑定公网服务端口、不接受公网入站，只允许 HK OpenResty 经 HK-SG 私网访问 New API 监听端口。
- 通过 HK-SG 私网访问 HK PostgreSQL 和 Redis；通过 NAT 网关或受控 EIP 出站访问模型上游。

## OpenResty 路由设计

### 路由决策顺序

OpenResty 按以下顺序解析模型：

1. WebSocket/Realtime 等协议优先读取 Query 中的 `model`。
2. Gemini 原生协议从 `/v1beta/models/{model}:action` 路径中提取模型。
3. `application/json` 请求解析 JSON 顶层的 `model`。
4. 无法提取模型或模型未命中规则时，默认转发到 HK。

控制台、`/api/*` 和前端资源不进入模型路由，始终转发到 HK New API。

### 模型规则

- 模型规则必须有且只有一份，由 OpenResty Lua 配置管理。
- 优先使用精确模型名或受控前缀，不使用宽泛的子串匹配。
- 新增或重命名模型时，发布流程必须同时更新路由规则。
- 路由结果只决定 New API 执行节点，不代替 New API 内部的模型权限和渠道校验。

示例规则：

```text
# HK：国内模型，可用受控前缀
deepseek-*   -> HK
qwen-*       -> HK
doubao-*     -> HK

# SG：OpenAI 家族，使用精确模型名
# 单独的 gpt- 前缀会漏掉 chatgpt-4o-latest；o1-/o3- 会漏掉无尾连字符的 o1、o3、o4-mini
gpt-4o, gpt-4o-mini, gpt-4, gpt-4-turbo, gpt-3.5-turbo, gpt-5 -> SG
chatgpt-4o-latest                                              -> SG
o1, o1-mini, o1-preview, o3, o3-mini, o4-mini                  -> SG

未命中                                                          -> HK
```

### Lua 路由示例

以下为最小可行示例。生产环境应将规则拆分到独立 Lua 配置文件，并为每个受支持的 Relay 协议增加回归用例。

`/usr/local/openresty/nginx/lua/model_router.lua`：

```lua
local cjson = require "cjson.safe"

local model = ngx.var.arg_model or ""
local uri = ngx.var.uri or ""
local parse_error = ""

if model == "" then
    model = uri:match("/models/([^/:]+)") or ""
end

if model == "" then
    local content_type = ngx.var.http_content_type or ""
    if content_type:find("application/json", 1, true) then
        ngx.req.read_body()
        local body = ngx.req.get_body_data()

        if not body then
            local body_file = ngx.req.get_body_file()
            if body_file then
                local file = io.open(body_file, "rb")
                if file then
                    body = file:read("*a")
                    file:close()
                else
                    parse_error = "body_file_open_failed"
                end
            end
        end

        if body then
            local request, err = cjson.decode(body)
            if type(request) == "table" and type(request.model) == "string" then
                model = request.model
            elseif err then
                parse_error = "invalid_json"
            end
        end
    end
end

if #model > 256 then
    model = ""
    parse_error = "model_too_long"
end

-- SG 出口模型清单：使用精确模型名，不依赖宽泛前缀。
-- 例如单独 "gpt-" 会漏掉 "chatgpt-4o-latest"，"o1-"/"o3-" 会漏掉无尾连字符的 "o1"、"o3"、"o4-mini"。
-- 生产环境把该清单拆到独立配置文件，并随模型增删同步更新。
local sg_models = {
    ["gpt-3.5-turbo"] = true,
    ["gpt-4"] = true,
    ["gpt-4-turbo"] = true,
    ["gpt-4o"] = true,
    ["gpt-4o-mini"] = true,
    ["gpt-5"] = true,
    ["chatgpt-4o-latest"] = true,
    ["o1"] = true,
    ["o1-mini"] = true,
    ["o1-preview"] = true,
    ["o3"] = true,
    ["o3-mini"] = true,
    ["o4-mini"] = true,
}

local target = "newapi_hk"
if sg_models[model] then
    target = "newapi_sg"
end

ngx.var.relay_backend = target
ngx.var.routed_model = model
ngx.var.route_parse_error = parse_error
```

`nginx.conf` 关键配置：

```nginx
worker_processes auto;

events {
    worker_connections 4096;
}

http {
    lua_code_cache on;

    log_format relay escape=json
        '$request_id $remote_addr "$request" $status '
        'model="$routed_model" node="$relay_backend" '
        'parse_error="$route_parse_error" request_time=$request_time';

    upstream newapi_hk {
        server 10.10.0.10:3000;
        keepalive 128;
    }

    upstream newapi_sg {
        server 10.20.0.10:3000;
        keepalive 128;
    }

    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      '';
    }

    server {
        listen 443 ssl http2;
        server_name api.example.com;

        # TLS 证书配置略。

        # 控制台和管理 API 固定转发到 HK。
        location /api/ {
            proxy_pass http://newapi_hk;
        }

        # Relay 请求由 Lua 提取 model 后选择 HK/SG。
        location ~ ^/(v1|v1beta)/ {
            set $relay_backend newapi_hk;
            set $routed_model "";
            set $route_parse_error "";
            access_by_lua_file /usr/local/openresty/nginx/lua/model_router.lua;
            access_log logs/relay-access.log relay;

            proxy_pass http://$relay_backend;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header X-Request-ID $request_id;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;

            # SSE/流式响应不缓冲。
            proxy_buffering off;
            proxy_cache off;
            proxy_read_timeout 3600s;
            proxy_send_timeout 3600s;

            # 请求一旦选定节点，禁止跨节点自动重试。
            proxy_next_upstream off;
        }

        # 前端页面固定转发到 HK。
        location / {
            proxy_pass http://newapi_hk;
        }
    }
}
```

### 请求体与协议边界

- Lua 读取 JSON Body 后才能选择 upstream，因此这类请求在入口会先被缓冲；这不影响上游响应的 SSE 流式传输。
- `client_max_body_size`、`client_body_buffer_size` 和 Lua 可读取上限必须与 New API 请求体限制协调，防止大 Body 占用过多内存。
- 上述最小示例在请求体落盘后使用同步 `io.open` 和 `read("*a")`；生产使用前必须设置严格的请求体上限并完成并发压测。高并发场景应让需解析的 JSON Body 在受控上限内驻留内存，或明确拒绝超出路由解析上限的请求，禁止无上限读取临时文件。
- multipart 上传、压缩 JSON、异步任务查询和回调可能不携带可直接解析的 `model`；必须为这些路径定义固定节点、显式路由标记或任务粘滞策略。
- 不得用字符串正则直接搜索 JSON 中的 `model`；必须进行 JSON 解析，避免在 prompt 文本中误命中。
- 如果 Lua 解析失败，记录请求 ID、路径和失败原因，不记录完整请求体。

## 数据面放置与延迟预算

- 权威 PostgreSQL 与 Redis 部署在 HK，与主要用户入口、控制面和高频 HK 模型同区；HK New API 的鉴权、计费和日志路径不承担跨区数据面延迟。
- SG New API 处理的 Relay 请求需要跨 HK-SG 私网访问 HK PostgreSQL 和 Redis。云内点对点网络不能消除物理 RTT，而鉴权、Token/用户/分组读取、渠道选择、`FOR UPDATE` 预扣、结算和日志落库中存在串行操作，因此单请求控制面可能累计数倍 RTT。
- 上线前必须测得并记录：SG→HK PostgreSQL 与 Redis 的稳定 RTT、P99 RTT、典型 SG Relay 请求的 DB/Redis 调用次数、首 Token 前控制面耗时和结算耗时；设定明确延迟预算，未达标不切换。
- 不在 SG 建立独立可写数据库或 Redis 以规避延迟，避免双写、配额不一致和重复扣费。优先通过合理连接池、本地只读缓存和减少不必要往返缓解；若 SG 长期成为主要流量区，再重新评估权威数据面位置和应用架构。

## 共享数据要求

- 两个实例的 `SQL_DSN` 指向同一个稳定、可写的 PostgreSQL 端点。
- 两个实例的 `REDIS_CONN_STRING` 指向同一个 Redis 兼容端点。
- 两个实例使用相同的 `SESSION_SECRET`、`CRYPTO_SECRET`、`TZ` 和应用版本。
- 每个实例使用唯一 `NODE_NAME`，例如 `hk-master-01` 和 `sg-relay-01`。
- PostgreSQL 是业务数据的权威数据源，Redis 用于共享缓存、Session 和限流状态。
- 不使用默认的 `SQL_MAX_OPEN_CONNS=1000` 直接上线。两节点可分别从 `SQL_MAX_OPEN_CONNS=50`、`SQL_MAX_IDLE_CONNS=10` 至 `20` 起步，结合 PostgreSQL `max_connections`、峰值并发和事务耗时压测调整；总连接预算必须为管理、迁移和故障恢复保留余量。
- SG 跨区 Redis 连接池可从 `REDIS_POOL_SIZE=20` 至 `50` 起步，根据 Redis 命令 P99、池等待和超时率调整。连接池不能只因 RTT 增加就无上限调大。
- 预扣/结算走 `FOR UPDATE` 行锁（见 `model/main.go` 的 `lockForUpdate` 约束）。跨区 RTT 会拉长锁持有时间、放大争用；须监控锁等待，必要时缩短事务范围或评估将权威库迁至高频区。

## 网络与安全

- HK 和 SG 之间使用 CEN 私网跨地域连接。私网隔离不等同于端到端加密；如合规或威胁模型要求链路加密，应在 CEN 上叠加 WireGuard/IPsec，或为 HK→SG Relay、SG→HK PostgreSQL/Redis 分别启用 TLS/mTLS。
- 若 HK 只部署一台 OpenResty，则它是公网入口单点；其不可用将导致整个服务对外中断，尽管 SG 实例健康。生产环境应优先采用双实例加云负载均衡；如果仍采用单实例，必须明确接受风险，并在故障演练中覆盖 HK 入口不可用场景。
- HK 是唯一公网入站区域。HK 公网出口从 50 Mbps 起步；持续利用率超过 60% 或峰值频繁超过 80% 时扩容。若包含图片、音频或视频响应，须按实际响应字节重新计算。
- SG ECS 优先不分配公网 IP，仅通过 NAT 网关或等价 SNAT 提供稳定公网出站地址；如必须绑定 EIP，安全组仍拒绝所有公网入站。SG 公网出站峰值从 50 Mbps 起步，并保留提升到 100 Mbps 的能力。
- SG 的“无公网入站”不等于“不需要公网带宽”：SG 仍需向模型上游发起 HTTPS 连接并接收该连接的返回流量。公网带宽容量按请求体上传、上游响应和并发任务实测确定。
- HK-SG CEN 跨地域连接从 50 Mbps 起步，禁止使用仅供连通性测试的带宽；监控达到阈值后扩到 100 Mbps。公网带宽和 CEN 带宽是两套独立容量，不能相互替代。
- SG 安全组只允许 HK 私网 CIDR 访问 New API 端口；HK PostgreSQL 和 Redis 只允许本机及 SG 私网 CIDR 访问。管理入口通过堡垒机、VPN 或云助手，不开放数据库、Redis 或 SG New API 公网端口。
- SG 仅放行访问模型上游及必要基础设施的出站流量，优先限制为 HTTPS、DNS 和时间同步所需目的与端口；NAT/EIP 出站地址用于上游白名单。
- OpenResty 必须传递真实客户端 IP、`X-Forwarded-For`、`X-Forwarded-Proto` 和请求 ID。
- SG New API 只信任 HK OpenResty 所在的代理网段，不信任公网来源伪造的转发头。
- 密钥、DSN、Redis 密码和上游凭据不得写入镜像、代码库或日志。
- Lua 只记录解析后的模型名和路由结果，不记录 prompt、文件或完整请求体。

## 发布顺序

1. 备份 PostgreSQL、OpenResty 配置、Lua 模型规则和生产密钥配置。
2. 先升级 HK 主节点，完成数据库迁移并验证 HK 控制面、Relay、PostgreSQL 和 Redis。
3. 再升级 SG 从节点，确保两节点使用相同应用版本，并验证 SG→HK 数据面连接。
4. 在预发布环境验证 OpenResty 配置、模型规则、SG 无公网入站和 SG 公网出站。
5. 执行 `openresty -t`，通过后 reload OpenResty。
6. 验证控制台、普通 Relay、流式 Relay、WebSocket/Realtime（含 `http2` 监听下的握手）、计费、日志和跨区域路由。

## 可观测性

- 为每个请求记录请求 ID、解析后的模型、目标节点、上游状态码和总耗时。
- 分别统计 HK/SG 请求量、错误率、P95/P99 延迟和首 Token 时间。
- 监控 HK-SG 点对点网络的 RTT、丢包、重连和可用性。
- 监控 HK 公网出口、SG 公网出站和 HK-SG CEN 三条独立链路的吞吐、利用率、丢包和 P95/P99 延迟。
- 监控 SG→HK PostgreSQL 与 Redis 的 RTT、连接池利用率与饱和次数，以及计费路径锁等待时长。
- 监控 HK 主机各进程的 CPU、RSS、磁盘 IOPS/时延、PostgreSQL WAL/数据盘空间、Redis `used_memory` 和淘汰数；任一组件不得依靠抢占其他组件资源维持峰值。
- 监控 Lua 解析失败数、未命中模型数和默认路由到 HK 的请求数。
- 使用 `NODE_NAME` 在 New API 日志和账单中识别最终执行节点。

## 验收标准

- 中国大陆用户只需使用 HK 公网入口即可访问前端、管理功能和 Relay API。
- 控制台和非 Relay API 在所有情况下均命中 HK New API。
- DeepSeek 等 HK 模型稳定命中 HK New API，GPT 等 SG 模型稳定命中 SG New API。
- JSON Body、Gemini URL 模型和 Realtime Query 模型均能正确路由。
- 未知模型、缺失模型和解析失败场景按规定默认转发到 HK，并产生可查询记录。
- 普通和流式 Relay 请求不出现重复调用、重复扣费或重复日志。
- 响应流式输出不被 OpenResty 缓冲，客户端可持续接收 SSE/WebSocket 数据。
- HK 和 SG New API 可同时访问同一 PostgreSQL 和 Redis，两节点数据一致。
- PostgreSQL、Redis 和 SG New API 公网端口不可访问；SG New API 只能从 HK 私网访问，但可经受控 NAT/EIP 出站访问模型上游。
- HK 公网、SG 公网出站和 HK-SG CEN 在目标峰值压测下均无持续带宽打满、异常排队或流式断连。
- 完成 PostgreSQL 备份恢复演练，并验证日志保留与清理不会阻塞在线计费事务。
- 完成 OpenResty 配置错误、Lua 解析异常、HK-SG 网络中断、New API 节点不可用、HK 公网入口不可用、PostgreSQL 不可用和 Redis 不可用的故障演练。
