# New API HK-US 多实例部署架构

## 业务目标

### 目标用户

- 主要服务中国大陆地区用户。
- 所有用户使用同一个公网域名，统一从中国香港（HK）入口访问。

### 访问与出口目标

- New API 控制台、静态网站和管理 API 始终由 HK 节点提供，优先保障中国大陆用户的访问速度。
- DeepSeek 等适合从 HK 访问的模型，转发到 HK New API，使用 HK 网络出口。
- GPT 等需要美国网络出口的模型，由 HK 入口通过云内点对点网络转发到美国（US）New API。
- 客户端无需选择 HK/US 域名，入口根据 Relay 请求中的 `model` 自动选择节点。

### 架构约束

- HK 和 US 均部署完整的 New API 实例。
- 两个实例共享同一个 PostgreSQL 和同一个 Redis。
- HK-US 跨区域访问使用云内加密点对点网络；跨区数据面（DB/Redis）延迟对 HK 请求控制面的影响见 [数据面放置与延迟预算](#数据面放置与延迟预算)，上线前必须实测达标，不以“可接受”作为默认假设。
- 不部署独立的模型路由服务；由 HK OpenResty 在 Nginx 请求处理阶段完成模型解析和 upstream 选择。
- 单个 Relay 请求只能由一个 New API 实例完成鉴权、渠道选择、预扣、结算和日志落库。

## 最终方案

### 使用 OpenResty（最推荐，无需编译）

OpenResty 是基于 Nginx 和 LuaJIT 的高性能 Web 平台，已经集成 `ngx_http_lua_module` 和常用 Lua 库。本方案使用 OpenResty 替代 HK 入口的标准 Nginx，不增加独立路由服务。

**是否需要编译：**不需要。Ubuntu、Debian 和 RPM 系发行版可以通过 OpenResty 官方软件仓库直接安装 `openresty` 包，无需手动编译 Nginx 或 Lua 模块，常规环境通常几分钟即可完成安装。

**实施步骤：**

1. 按操作系统添加 OpenResty 官方软件仓库，安装 `openresty` 包。
2. 执行 `openresty -v` 验证安装；如果命令不在 `PATH` 中，使用 `/usr/local/openresty/bin/openresty -v`。
3. 在 `nginx.conf` 中使用 `access_by_lua_block`、`access_by_lua_file` 或 `content_by_lua_block` 等指令加载 Lua 逻辑。
4. 本场景需要在 `proxy_pass` 之前选择 upstream，因此实际路由使用 `access_by_lua_file`；`content_by_lua_block` 主要用于由 Lua 直接生成响应。
5. 执行 `openresty -t` 检查配置，通过后再 reload。

OpenResty 官方安装说明：<https://openresty.org/en/installation.html>

## 部署拓扑

```text
中国大陆用户
  |
  | HTTPS（唯一公网入口）
  v
HK OpenResty
  | TLS / 前端 / API 入口
  | Lua 解析 model 并选择 HK/US
  |
  +-- 控制台、管理 API ------> HK New API Slave
  |
  +-- DeepSeek 等 HK 模型 --> HK New API Slave --> HK 适配上游
  |
  +-- GPT 等 US 模型 ------> HK-US 加密云内点对点网络
                                  |
                                  v
                            US New API Master
                                  |
                                  +--> GPT 等 US 适配上游

HK New API Slave ----+
                     +--> PostgreSQL + Redis（US 节点）
US New API Master ---+

HK 和 US New API 通过云内网络共享同一套业务状态。
```

## 节点职责

### HK OpenResty

- 作为用户日常访问的唯一公网入口。
- 负责 TLS 终止、前端静态资源、控制台 API 反向代理和 Relay 模型路由。
- 从 JSON Body、URL 路径或 Query 中提取 `model`，按单一规则集选择 HK 或 US upstream。
- 不执行 New API 鉴权、渠道选择和计费逻辑。

### HK New API

- 处理登录、用户、Token、渠道、日志和其他 New API 控制面功能。
- 处理分配到 HK 的 Relay 请求。
- 设置 `NODE_TYPE=slave`，不执行数据库自动迁移和主节点后台任务。

### US New API

- 处理分配到 US 的 Relay 请求。
- 作为唯一 New API 主节点，执行数据库迁移和后台定时任务。
- 部署 PostgreSQL 和 Redis，向 HK/US New API 提供共享状态。
- New API、PostgreSQL 和 Redis 的节点间访问只通过云内网络开放。

## OpenResty 路由设计

### 路由决策顺序

OpenResty 按以下顺序解析模型：

1. WebSocket/Realtime 等协议优先读取 Query 中的 `model`。
2. Gemini 原生协议从 `/v1beta/models/{model}:action` 路径中提取模型。
3. `application/json` 请求解析 JSON 顶层的 `model`。
4. 无法提取模型或模型未命中规则时，默认转发到 HK。

控制台、`/api/*` 和前端资源不进入模型路由，始终转发到 HK New API。

### 模型规则

- 模型规则必须有且只有一份，由 OpenResty Lua 配置管理。
- 优先使用精确模型名或受控前缀，不使用宽泛的子串匹配。
- 新增或重命名模型时，发布流程必须同时更新路由规则。
- 路由结果只决定 New API 执行节点，不代替 New API 内部的模型权限和渠道校验。

示例规则：

```text
# HK：国内模型，可用受控前缀
deepseek-*   -> HK
qwen-*       -> HK
doubao-*     -> HK

# US：OpenAI 家族，使用精确模型名
# 单独的 gpt- 前缀会漏掉 chatgpt-4o-latest；o1-/o3- 会漏掉无尾连字符的 o1、o3、o4-mini
gpt-4o, gpt-4o-mini, gpt-4, gpt-4-turbo, gpt-3.5-turbo, gpt-5 -> US
chatgpt-4o-latest                                              -> US
o1, o1-mini, o1-preview, o3, o3-mini, o4-mini                  -> US

未命中                                                          -> HK
```

### Lua 路由示例

以下为最小可行示例。生产环境应将规则拆分到独立 Lua 配置文件，并为每个受支持的 Relay 协议增加回归用例。

`/usr/local/openresty/nginx/lua/model_router.lua`：

```lua
local cjson = require "cjson.safe"

local model = ngx.var.arg_model or ""
local uri = ngx.var.uri or ""
local parse_error = ""

if model == "" then
    model = uri:match("/models/([^/:]+)") or ""
end

if model == "" then
    local content_type = ngx.var.http_content_type or ""
    if content_type:find("application/json", 1, true) then
        ngx.req.read_body()
        local body = ngx.req.get_body_data()

        if not body then
            local body_file = ngx.req.get_body_file()
            if body_file then
                local file = io.open(body_file, "rb")
                if file then
                    body = file:read("*a")
                    file:close()
                else
                    parse_error = "body_file_open_failed"
                end
            end
        end

        if body then
            local request, err = cjson.decode(body)
            if type(request) == "table" and type(request.model) == "string" then
                model = request.model
            elseif err then
                parse_error = "invalid_json"
            end
        end
    end
end

if #model > 256 then
    model = ""
    parse_error = "model_too_long"
end

-- US 出口模型清单：使用精确模型名，不依赖宽泛前缀。
-- 例如单独 "gpt-" 会漏掉 "chatgpt-4o-latest"，"o1-"/"o3-" 会漏掉无尾连字符的 "o1"、"o3"、"o4-mini"。
-- 生产环境把该清单拆到独立配置文件，并随模型增删同步更新。
local us_models = {
    ["gpt-3.5-turbo"] = true,
    ["gpt-4"] = true,
    ["gpt-4-turbo"] = true,
    ["gpt-4o"] = true,
    ["gpt-4o-mini"] = true,
    ["gpt-5"] = true,
    ["chatgpt-4o-latest"] = true,
    ["o1"] = true,
    ["o1-mini"] = true,
    ["o1-preview"] = true,
    ["o3"] = true,
    ["o3-mini"] = true,
    ["o4-mini"] = true,
}

local target = "newapi_hk"
if us_models[model] then
    target = "newapi_us"
end

ngx.var.relay_backend = target
ngx.var.routed_model = model
ngx.var.route_parse_error = parse_error
```

`nginx.conf` 关键配置：

```nginx
worker_processes auto;

events {
    worker_connections 4096;
}

http {
    lua_code_cache on;

    log_format relay escape=json
        '$request_id $remote_addr "$request" $status '
        'model="$routed_model" node="$relay_backend" '
        'parse_error="$route_parse_error" request_time=$request_time';

    upstream newapi_hk {
        server 10.10.0.10:3000;
        keepalive 128;
    }

    upstream newapi_us {
        server 10.20.0.10:3000;
        keepalive 128;
    }

    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      '';
    }

    server {
        listen 443 ssl http2;
        server_name api.example.com;

        # TLS 证书配置略。

        # 控制台和管理 API 固定转发到 HK。
        location /api/ {
            proxy_pass http://newapi_hk;
        }

        # Relay 请求由 Lua 提取 model 后选择 HK/US。
        location ~ ^/(v1|v1beta)/ {
            set $relay_backend newapi_hk;
            set $routed_model "";
            set $route_parse_error "";
            access_by_lua_file /usr/local/openresty/nginx/lua/model_router.lua;
            access_log logs/relay-access.log relay;

            proxy_pass http://$relay_backend;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header X-Request-ID $request_id;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;

            # SSE/流式响应不缓冲。
            proxy_buffering off;
            proxy_cache off;
            proxy_read_timeout 3600s;
            proxy_send_timeout 3600s;

            # 请求一旦选定节点，禁止跨节点自动重试。
            proxy_next_upstream off;
        }

        # 前端页面固定转发到 HK。
        location / {
            proxy_pass http://newapi_hk;
        }
    }
}
```

### 请求体与协议边界

- Lua 读取 JSON Body 后才能选择 upstream，因此这类请求在入口会先被缓冲；这不影响上游响应的 SSE 流式传输。
- `client_max_body_size`、`client_body_buffer_size` 和 Lua 可读取上限必须与 New API 请求体限制协调，防止大 Body 占用过多内存。
- multipart 上传、压缩 JSON、异步任务查询和回调可能不携带可直接解析的 `model`；必须为这些路径定义固定节点、显式路由标记或任务粘滞策略。
- 不得用字符串正则直接搜索 JSON 中的 `model`；必须进行 JSON 解析，避免在 prompt 文本中误命中。
- 如果 Lua 解析失败，记录请求 ID、路径和失败原因，不记录完整请求体。

## 数据面放置与延迟预算

- 权威 PostgreSQL 与 Redis 部署在 US，HK 实例跨 HK-US 访问。选择 US 而非 HK 作为数据面位置的理由：**（待填写，例如现有托管数据库、数据驻留或合规要求）**；如无明确理由，应优先与高频流量区（HK）同区部署。
- 物理约束：HK-US 往返延迟通常在 ~100–200ms 量级，即便走云内点对点网络也无法消除。HK 实例处理的每个中继请求，其控制面操作（鉴权、Token/用户/分组读取、渠道选择、`FOR UPDATE` 预扣、结算、日志落库）多为串行，单请求累计可达数倍 RTT 的额外延迟。
- 高频国内模型（DeepSeek/Qwen/Doubao）经 HK 实例处理，是跨区延迟的主要承担者；这与“优先保障中国大陆访问速度”的目标存在张力，必须在上线前用实测数据确认可接受。
- 上线前必须测得并记录：HK→US PostgreSQL 与 Redis 的稳定 RTT、P99 RTT、典型中继请求的 DB/Redis 调用次数与端到端控制面耗时；设定明确延迟预算（例如控制面新增延迟不超过 N ms），未达标不切换。
- 缓解手段：按高 RTT 调整 `SQL_MAX_OPEN_CONNS`/`SQL_MAX_IDLE_CONNS` 并关注计费路径锁持有时间（详见 [共享数据要求](#共享数据要求)），评估只读副本或本地缓存以减少跨区读。

## 共享数据要求

- 两个实例的 `SQL_DSN` 指向同一个稳定、可写的 PostgreSQL 端点。
- 两个实例的 `REDIS_CONN_STRING` 指向同一个 Redis 兼容端点。
- 两个实例使用相同的 `SESSION_SECRET`、`CRYPTO_SECRET`、`TZ` 和应用版本。
- 每个实例使用唯一 `NODE_NAME`，例如 `hk-relay-01` 和 `us-master-01`。
- PostgreSQL 是业务数据的权威数据源，Redis 用于共享缓存、Session 和限流状态。
- 跨区链路下连接占用时长上升，须按 HK-US RTT 调大 `SQL_MAX_OPEN_CONNS` 与 `SQL_MAX_IDLE_CONNS`（默认 1000/100，见 `model/main.go`），并监控连接池利用率，防止排队与耗尽。
- 预扣/结算走 `FOR UPDATE` 行锁（见 `model/main.go` 的 `lockForUpdate` 约束）。跨区 RTT 会拉长锁持有时间、放大争用；须监控锁等待，必要时缩短事务范围或评估将权威库迁至高频区。

## 网络与安全

- HK 和 US 之间使用加密的云内点对点网络。
- HK OpenResty 是唯一公网入口，属于单点；其不可用将导致整个服务对外中断，尽管 US 实例健康。需明确兜底策略（如 DNS 切换、备用入口或显式接受该风险），并在故障演练中覆盖 HK 入口不可用场景。
- US New API、PostgreSQL 和 Redis 不暴露公网端口。
- 防火墙仅允许 HK OpenResty/HK New API 访问必要的 US 私网端口。
- OpenResty 必须传递真实客户端 IP、`X-Forwarded-For`、`X-Forwarded-Proto` 和请求 ID。
- US New API 只信任 HK OpenResty 所在的代理网段，不信任公网来源伪造的转发头。
- 密钥、DSN、Redis 密码和上游凭据不得写入镜像、代码库或日志。
- Lua 只记录解析后的模型名和路由结果，不记录 prompt、文件或完整请求体。

## 发布顺序

1. 备份 PostgreSQL、OpenResty 配置、Lua 模型规则和生产密钥配置。
2. 先升级 US 主节点，完成数据库迁移并验证服务。
3. 再升级 HK 从节点，确保两节点使用相同应用版本。
4. 在预发布环境验证 OpenResty 配置和模型规则。
5. 执行 `openresty -t`，通过后 reload OpenResty。
6. 验证控制台、普通 Relay、流式 Relay、WebSocket/Realtime（含 `http2` 监听下的握手）、计费、日志和跨区域路由。

## 可观测性

- 为每个请求记录请求 ID、解析后的模型、目标节点、上游状态码和总耗时。
- 分别统计 HK/US 请求量、错误率、P95/P99 延迟和首 Token 时间。
- 监控 HK-US 点对点网络的 RTT、丢包、重连和可用性。
- 监控 HK→US PostgreSQL 与 Redis 的 RTT、连接池利用率与饱和次数，以及计费路径锁等待时长。
- 监控 Lua 解析失败数、未命中模型数和默认路由到 HK 的请求数。
- 使用 `NODE_NAME` 在 New API 日志和账单中识别最终执行节点。

## 验收标准

- 中国大陆用户只需使用 HK 公网入口即可访问前端、管理功能和 Relay API。
- 控制台和非 Relay API 在所有情况下均命中 HK New API。
- DeepSeek 等 HK 模型稳定命中 HK New API，GPT 等 US 模型稳定命中 US New API。
- JSON Body、Gemini URL 模型和 Realtime Query 模型均能正确路由。
- 未知模型、缺失模型和解析失败场景按规定默认转发到 HK，并产生可查询记录。
- 普通和流式 Relay 请求不出现重复调用、重复扣费或重复日志。
- 响应流式输出不被 OpenResty 缓冲，客户端可持续接收 SSE/WebSocket 数据。
- HK 和 US New API 可同时访问同一 PostgreSQL 和 Redis，两节点数据一致。
- PostgreSQL、Redis 和 US New API 公网端口不可访问。
- 完成 OpenResty 配置错误、Lua 解析异常、HK-US 网络中断、New API 节点不可用、HK 公网入口不可用、PostgreSQL 不可用和 Redis 不可用的故障演练。
