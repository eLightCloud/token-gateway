# 组织模块开发与验证指南

## 适用范围

修改以下任一内容时使用本指南：

- `model/organization.go`
- `model/organization_invoice.go`
- `model/organization_invoice_export*.go`
- `controller/organization.go`
- `controller/organization_invoice.go`
- `controller/organization_invoice_csv.go`
- `router/api-router.go` 中的组织路由
- `web/src/features/organizations/`
- 组织侧边栏、路由、国际化和账单导出

业务和架构真源分别见 [组织与账单产品设计](../10-product/组织与账单产品设计.md) 与 [组织与组织账单架构设计](../20-architecture/组织与组织账单架构设计.md)。本文件只说明以后如何安全修改和验证。

## 不可破坏的不变量

1. 个人用户始终是唯一扣费主体；组织查询不能进入预扣、结算、退款或 Token 鉴权。
2. 一个用户同一时间只能有一个活动组织成员关系。
3. 组织角色只允许 Admin、Member；旧 Owner/Billing 数据必须在迁移时归一。
4. 移除成员必须保留历史记录并清空 `current_key`。
5. 组织日志必须同时受成员有效期、角色范围和查询筛选限制。
6. Member 查询必须由后端覆盖为当前用户，不能信任客户端提交的 `user_id`。
7. 历史金额以 `Log.Quota` 为准，当前模型价格不能重算历史。
8. 主库和日志库不得假设可跨库 join。
9. 数据模型和查询必须兼容 SQLite、MySQL、PostgreSQL；日志聚合还需保留 ClickHouse 分支。
10. 导出必须复用与页面相同的权限和筛选条件。
11. `JoinedAt` 是成员审计事实，`BillingStartAt` 是报表归属起点；旧行零值必须回退 `JoinedAt`，不得自动吞并历史。
12. Invoice 消费依据结算后的用量事实，账户财务摘要还读取主库资金事实。账单按已确认消费的整数 quota 汇总。
13. Invoice CSV 的财务补充信息只允许在已授权导出路径从主数据库读取；不得扩大页面或 JSON API 的未脱敏字段，也不得把充值或余额查询接入个人计费链路。

## 后端修改顺序

### 成员关系

- 在 GORM 事务中读取组织、校验用户、检查活动关系并写成员。
- 活动关系写 `CurrentKey = strconv.Itoa(userId)`；离开时同时写 `left_at` 和 `current_key = nil`。
- 新成员同时写 `BillingStartAt = JoinedAt`；历史回填必须经过预览、`expected_billing_start` CAS、同组织窗口不相交校验和管理审计。
- 归属起点当前只允许向前扩展。不要新增绕过校验的“直接改时间”接口，也不要把 `JoinedAt` 改成历史日期。
- 不使用物理删除，不通过 `users.group`、Token 或请求 Header 表达组织。

### 账单查询

- 用量快照走 `controller/organization_usage.go` 和 `model/organization_usage_*.go`；旧维度、日志和 ClickHouse 兼容路径分开验证。
- 重算通过 `controller/organization_recalculation.go` 接受版本凭据；测试过期凭据不覆盖新结果，失败不伪造空账单，GET 不接受旧 `refresh=1`。

- 先从主库读取成员关系段，再用 `effectiveBillingStart`、`logMembershipBounds` 和 `applyOrganizationLogFilters` 在 `LOG_DB` 应用统一窗口。
- Summary、Members、Models、Channels、Trend、Logs 的筛选语义必须保持一致。
- 退款或系统调整必须通过显式类型参数进入查询，不能改变默认消费口径。
- 聚合下推日志库；不要把全量日志取回 Go 后再过滤或按天分组。
- 明细分页必须先过滤组织范围，再全局排序和分页。
- Invoice 在日志库按成员、完整模型和北京时间月份聚合，再由 Go 完成模型分类、规则选择和交叉表构造；禁止把原始日志下载到前端计算。
- 北京时间月份使用 Go 生成的 Unix 边界，不依赖数据库会话时区或单一数据库日期函数。

### API 与权限

- 用户侧继续使用 `/api/organization/current/*`，不要接受任意组织 ID。
- 管理员跨组织接口继续放在 `/api/admin/organizations/:id/*` 并使用 `AdminAuth`。
- UI 可见性只是体验优化，权限必须由控制器和模型重复校验。
- `billing-start` 预览/应用和 Invoice 规则更新只允许系统管理员或组织 Admin；Member 必须由服务端拒绝。
- 结算规则更新使用 `expected_version` CAS；相同系数幂等返回，冲突返回 409 且不得覆盖新版本。
- 修改组织状态语义前先决定它是否只是标签，还是要阻断成员查询、管理或个人 API 消费；不能只改一个入口。

### 导出

- 兼容日志 CSV 和完整六区块 CSV 是排障型导出，包含敏感字段。扩展客户导出时新建明确的列白名单，不要复用全量日志序列化。
- `billing/logs/export` 是兼容端点，必须保留原始单表列、列顺序和 `billing-logs.csv` 文件名；不能用完整账单替换它。
- Logs 页面调用独立的 `billing/logs/display-export`，按页面列导出可读时间、消费金额、币种、原始 quota 和合计 Tokens；浏览器通过 `timezone_offset` 传入显示时区偏移。
- 完整六区块账单使用新增 `billing/export`；Billing 页面调用完整账单端点。
- Logs 与 Billing 明细使用固定大小批次和成员游标直接流式写入响应，内存占用不得随总日志数线性增长，也不得静默截断为固定行数。
- Invoice 使用独立 CSV（两张交叉表及必要的异常提示），只输出结算所需白名单字段；查询与导出必须调用同一消费聚合和账户财务摘要。组织名称和未脱敏真实姓名只能在授权后的导出上下文中补充；Invoice JSON 可向组织 Admin 和系统管理员返回脱敏账户财务摘要。
- 账号列必须取 `users.username`，真实姓名行取 `display_name` 并与账号严格对齐；真实姓名为空时输出空单元格，不得回退为脱敏显示名。CSV 不得重新加入组织 ID、内部时区/时间戳、规则明细或原始 quota。
- 模型归类合计行之后展示“用户上期余额”、“用户当期流入金额”、“用户当期消费金额”和“用户当前余额”，并以成员计费窗口与账期相交的全部 `invoice.Accounts` 为范围；账号缺少消费时仍输出零值。上期余额取账期期初余额；充值金额取账期内全部已识别正向入账，包含支付充值、管理员加额及其他已识别入账。缺少期初基线时，后台任务先回放账期前事实并原子生成真实基线；缺少月度 `ready` 汇总时，后台构建兼容读取精确匹配的旧 `user.quota_add` 和中文管理员加额日志。基线或汇总发布后，日常查询不再扫描旧日志。
- 充值查询必须使用成功状态、半开账期边界和 Stripe/Creem/Waffo/Waffo Pancake 白名单，并以数据库侧 `NOT EXISTS` 排除相同 `trade_no` 的订阅订单。不得纳入 EPay，或用创建时间、日志文本、订单号和模糊规则猜测账期或金额。
- 渠道金额按现有入账字段语义显式换算并使用 decimal 累计；未知渠道静默排除，已知渠道异常字段排除并记录告警。余额从主数据库批量读取，不读 Redis；缺失账号必须报错，禁止以零值兜底。
- 流开始前的失败返回 JSON；流开始后的数据库或客户端错误只能终止响应并记录服务端错误。
- 任何脱敏、安全和权限修复必须同步覆盖用户侧与管理员侧导出。

## 前端修改规则

- 技术栈以 `web/AGENTS.md` 和 `components.json` 为准：React 19、TanStack Router、React Query、Base UI/shadcn 组合、Hugeicons、Tailwind CSS。
- API 与类型留在 `features/organizations/api.ts`、`types.ts`；页面组合位于该 feature，路由文件保持薄层。
- 查询 key 必须包含接口范围、组织 ID、当前认证用户 ID、筛选和分页；成员变更后失效 self、members、billing、invoice 与管理员列表/详情相关查询。
- 登录用户变化或退出时移除组织 feature 的受保护缓存，避免同角色账号切换后短暂显示上一账号数据。
- 可见文案用 `t()`；只维护 en、zh。若运行 `bun run i18n:sync`，检查并移除它对遗留语言产生的新增键。
- 表格保留横向滚动、空状态、loading、禁用和错误反馈；图标按钮必须有可访问名称。
- 高风险操作使用确认对话框；角色修改失败必须恢复可理解状态。
- 产品目标与当前实现不一致时，在 UI 设计文档记录差异，不要把后端已经收紧的权限在前端扩大。

## 测试矩阵

### 后端行为

- 创建空组织，不自动创建成员。
- 添加启用用户并拒绝禁用/不存在用户。
- 并发或重复添加时仍只有一个活动组织。
- 添加和修改成员时只接受 Admin、Member，拒绝其他角色。
- 当前用户在存在其他活动 Admin 时可以移除自己；最后一个活动 Admin 不能退出或降级。
- 成员添加、移除和角色变更必须在组织行锁保护的同一事务中维护 Admin 不变量。
- 成员离开和重新加入时，账单只覆盖各自有效期。
- `billing_start_at = 0` 回退加入时间；回填只纳入候选起点之后的保留日志，并拒绝同组织窗口重叠、陈旧 CAS 和向后截断。
- Summary、成员、模型、渠道、北京时间日趋势和跨成员日志分页结果一致。
- Member 查询被强制限制为自己。
- Invoice 覆盖默认/继承/多月规则、零系数、最大系数、非法系数、北京时间月边界、fallback 类别、负 quota 防护和规则首次创建并发。
- Invoice GET 与 CSV 的消费合计一致。核对账户、分类、模型与交叉明细的整数 quota，以及失效快照的重建状态。
- Invoice CSV 验证组织名称白名单、真实姓名/账号严格对齐、补充行位置和尾部空列；充值查询覆盖四个支持渠道、成功状态、账期最后一秒、订阅排除、未知渠道与 EPay 排除、多订单累计，余额查询覆盖主库即时值和账号缺失失败。
- 独立日志库和 ClickHouse 排序/日期桶分支保持正确。

组织模型已有的行为回归集中在 `model/organization_test.go`、`model/organization_billing_start_test.go` 和 `model/organization_invoice_test.go`；`controller/organization_e2e_test.go` 保护 HTTP 权限、历史回填与 Invoice 合同，`controller/organization_export_test.go` 保护导出金额和旧日志 CSV 兼容合同。新增测试必须保护上述业务合同，使用 `testify/require` 和 `testify/assert`，不要锁定私有实现细节。

### 前端行为

- 未加入组织时无侧边栏入口，直达页面显示空状态。
- Admin/Member 两类角色分别验证菜单和页面。
- Member 只能看到自己的受限用量。
- 管理员可创建空组织、维护角色、预览/应用历史归属起点并查看 Members、Billing、Invoice、Logs。
- 筛选、刷新、分页和导出使用同一参数。
- Billing、Logs 和 Invoice 日期按北京时间日边界解释，用户、模型、渠道、趋势和明细都同时展示消费金额与 raw quota。
- Invoice 默认当前北京时间自然月；动态账号列、横向滚动、多档系数、规则冲突刷新和零系数确认必须可用。
- 消费金额必须使用账单专用格式化：即使全局额度展示为 TOKENS，也显示 USD 等值，不能与 raw quota 重复。
- 模型价格列只标识当前计价规则；固定价格需要货币格式，不能暗示它是历史请求价格。
- CSV 的消费金额保持纯数值并单列币种，避免带符号或缩写后的字符串破坏 Excel 汇总。
- 桌面、窄屏、键盘焦点、空数据和请求失败状态可用。

## 实时模型折扣迁移与回归

从仓库根目录运行下列检查。用 SQLite、新建及发布基线升级的 MySQL、PostgreSQL 各复跑，设置 `RT_TEST_DIALECT`、`RT_TEST_DSN` 到隔离实例或文件；已有发布版夹具时用 `RT_TEST_UPGRADE_RELEASE=1` 核对重复迁移及原数据保留。

```bash
go test ./model ./controller ./service -run 'TestRealtime(Pricing|Midjourney)' -count=1 -v
```

1. 分别准备活跃主体、旧身份列为 NULL 的普通用户、已删除主体、同模型跨渠道多倍率和精度冲突。核对冻结阻断旧消费配置写入，冲突时不自动选值，启用前可恢复 legacy。
2. 以显式 `1×`、未覆盖渠道及组织继承验证优先级。构造折后额度才可准入及高价重试失败场景。由已持久快照完成在途任务与退款，核对改规则、退组、重启或恢复后金额一致。
3. 使用两个窗口同时编辑，检查 revision 冲突、清空后版本仍前进、保留草稿、成员预览的权限和渠道切换后的生效来源。重新查询后核对实际规则和日志。

## 手动回归与取证

1. 从隔离环境开始，记录应用提交、数据库版本、基础数据和时间。准备 Root、平台 Admin、组织 Admin、Member、组织外用户与禁用账号。保存初始余额、Token、成员窗口、账单和邮件配置修订。测试账号和邮件仅使用受控样本。
2. 先查拒绝路径，再做真实页面操作和失败恢复。组织用量在同一账期比对各维度，Invoice 抽查未知期初、退款、即时余额、CSV 脱敏和大批量尾行。邮件和通知按[运维手册](../40-operations/运维手册.md#microsoft-graph-发信验证)执行，并验证版本冲突、取消敏感验证、未知投递和跨日。
3. 用 `Pass`、`Fail`、`Blocked` 或 `N/A` 记录每个场景。写明执行人、北京时间、实际结果、请求 ID/配置 revision、脱敏证据与缺陷编号。单独记录 UI、协议受理和目标环境收件。原始导出与邮件保存在仓库外。
4. 前置条件具备后重跑阻塞用例。权限、资金、秘密泄露、错收件人或重复扣退存在缺陷时停止放量；修复后复验失败用例及关联链路。
