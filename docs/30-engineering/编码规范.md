# 编码规范

## 组织账单渠道可见性

- 后端是渠道信息的最终安全边界；前端 `canViewOrganizationBillingChannels(role)` 只控制 UI，不能替代后端鉴权。
- 普通组织成员（`member`）的渠道筛选参数必须在服务端清零，不能通过已知或猜测的渠道 ID 差异探测账单。
- 成员视角的账单日志 JSON、原始日志 CSV 和完整账单 CSV 均不得包含渠道 ID、渠道名称或渠道用量区块；Admin 和系统管理员视角保留渠道维度。
- 渠道维度接口对成员返回空数据，组织管理员和系统管理员的渠道能力保持不变。

## 额度数值类型与转换

必须显式区分三类 quota，禁止混用类型：

| 类型 | Go 类型 | 数据库类型 | 用途 | 转换入口 |
|---|---|---|---|---|
| Charge quota | `int` | `INT` | 单次请求预估、预扣、结算、退款、单条日志 | `common.QuotaFromFloatChecked` / `QuotaRoundChecked` / `QuotaFromDecimalChecked` |
| Balance quota | `int64` | `BIGINT`（SQLite `INTEGER`） | 用户钱包、Token 余额、邀请额度、调额流水、充值/兑换码 | `common.QuotaBalanceFromDecimalStrict` |
| Aggregate quota | `int64` | 聚合结果按 `int64` 接收 | 账单/Invoice 的 `SUM(quota)`、多维汇总 | 每次加法后检查溢出 |

- `common.MaxQuota`（`math.MaxInt32`）继续保护单次计费；单次请求费用不得因钱包扩宽而放大。
- 钱包/Token 余额上限为 `common.MaxWalletQuota`（`500_000_000_000_000`），下限为 `common.MinWalletQuota`（`math.MinInt32`）；`common.MaxTokenQuota = common.MaxWalletQuota`。
- 禁止对未经验证的 quota 使用裸 `int(...)` 转换；禁止把 `int64` 余额反向窄化为 `int` 再参与计费。
- `common.QuotaBalanceFromDecimalStrict` 先截断到整数，再按 `[min, max]` 拒绝；越界时返回错误，不得饱和发放或把订单标记成功。

## 数据库迁移

- 热表列类型扩宽必须放在独立迁移模块（如 `model/quota_balance_bigint_migration.go`），`model/main.go` 只保留不可避免的注册调用。
- 迁移必须幂等：通过 `Migrator().HasColumn` 和实际列类型检查决定是否执行 DDL，重启不得重复改列。
- 必须按数据库方言显式分支，未识别方言直接失败，不静默跳过；SQLite 不支持 `ALTER COLUMN`，该分支只验证列可读。
- 扩列后执行 schema readiness check：任一必要列仍非 64 位时阻止开放大额余额，不依赖 `AutoMigrate` “自动补救”。
- 不得使用仅单一数据库支持的部分索引、JSON 运算或生成列；跨库唯一约束优先使用可空字段和事务检查。

## 余额调整与缓存

- 管理员调额、充值发放、兑换码和订阅转余额必须使用同一 balance 边界，不得各自写一套上限。
- 余额调整应在同一主库事务中完成：锁定用户行、读取 `int64` 旧余额、边界检查、更新 `users.quota`、写入不可变调额流水；任何一步失败不得产生部分写入。
- 优先使用 `WHERE` 范围谓词让数据库原子完成边界检查与算术（参考 `model/wallet_balance.go`）；使用 `lockForUpdate(tx)` 时必须符合 GORM v2 用法，禁止 `tx.Set("gorm:query_option", "FOR UPDATE")`。
- 事务成功后才更新 Redis 缓存；提升 `userCacheSchemaVersion` 时必须验证版本不匹配回源、旧 hash 中 `Quota` 字段行为和 auth-version fence。
- 清理或失效 Redis 用户缓存前，必须确认 quota batch store 已完整刷入主库，避免丢失未持久化的余额增量。

## 账单与发票

- `Log.Quota` 保持 `int` 单条消费事实；`SUM(quota)` 和组织维度聚合必须使用 `int64` 接收。
- 组织 Invoice 直接聚合已折后的 `Log.Quota`，不得在发票阶段再次应用请求级折扣或倍率。
- 合同/折扣若进入计费链路，必须在请求/任务开始时生成不可变快照，后续合同变更不影响已开始的请求和已提交的异步任务。
