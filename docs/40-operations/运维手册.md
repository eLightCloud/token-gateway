# 运维手册

## 文本流断开续读

该能力对每个已升级实例的按 Token 计费文本生成流统一生效，没有按渠道、Provider 或模型分配的运行时开关。图片、视频、音频和非流式请求不在此发布边界内。

发布前：

1. 用确定性协议流回归共享 scanner、直接 scanner、scanner + channel、AWS event stream、WebSocket 和 buffered read。
2. 使用短于端到端首事件时间的客户侧上限复现真实文本流，确认客户按预期结束，网关从同一上游流取得完整 usage。
3. 记录 `client_gone` 到上游终态的 tail，确认显著小于当前 300 秒绝对上限。
4. 确认消费日志可同时表达 `client_gone + terminal_success`，且缓存分项、输入与输出 usage 完整。
5. 轮换任何曾在对话、截图或测试记录中暴露的受控测试密钥。

发布时先放量单个实例，观察连接数、总处理时长、空闲/绝对超时、上游错误分布和 goroutine；验证稳定后再滚动发布全部实例。人工查看上游账单页只用于最后验收或客诉解释，不导入数据、不补扣、不退款、不改写消费日志。

若出现连接无法释放、goroutine 增长、空闲/绝对超时异常、上游错误未及时结束或重复结算，立即停止放量并回滚到上一已验证版本。回滚恢复“客户结束后关闭上游资源”的旧行为，不涉及数据库迁移、历史账单或人工调账。

## 组织账单变更发布

组织历史归属起点、Invoice、结算规则和流式导出会扩大日志查询范围，但不会修改个人扣费事实。发布前必须确认：

- 主库已备份，并记录当前应用版本、数据库版本和回滚镜像。
- MySQL、PostgreSQL 或 SQLite 的 GORM 迁移可以新增 `organization_members.billing_start_at` 和 `organization_billing_settlement_rules`。
- 独立 `LOG_DB` 或 ClickHouse 的连接、日志保留策略和最早可查询时间已确认。
- 所有网关实例使用同一代码版本和主库；滚动期间要求管理员暂停规则写入和历史归属回填，避免不同版本实例同时处理新写请求。
- 已选取内部组织作为灰度对象，并保存默认系数 `1.0000` 下 Billing 与 Invoice 的同边界对账结果。

推荐发布顺序：

1. 备份主库并记录日志库最早保留时间。
2. 先在测试环境或内部灰度实例发布候选版本并执行迁移；当前版本没有独立 Invoice 功能开关。
3. 验证组织成员、只读 Invoice、Billing、Logs 和个人请求链路没有退化。
4. 使用同一组 Unix 边界对比 Billing gross quota 与 Invoice gross quota；任何差异必须归因到成员窗口、日志类型、时区边界或日志保留。
5. 验证系统管理员、组织 Admin、Member 的权限矩阵。
6. 完成灰度后滚动发布全部生产实例；滚动完成前继续暂停结算规则配置和历史归属回填。
7. 在接近生产的数据量下验证页面 P95、同步 CSV 时长、网关超时和日志库负载，再通知管理员恢复写操作。

## 历史账单归属回填

### 操作前确认

只对经业务负责人确认属于目标组织的历史账号执行回填。逐成员记录：

| 字段 | 用途 |
|---|---|
| 组织、用户、成员记录 | 确认操作对象 |
| `joined_at` | 保留真实成员加入时间 |
| 当前生效 `billing_start_at` | 作为乐观锁预期值 |
| 候选归属起点 | 业务确认的历史边界 |
| 最早保留日志 | 判断日志库实际可恢复范围 |
| 新增请求数、quota、Token、日志范围 | 对账和审批 |
| 窗口冲突 | 阻断同组织重复统计 |

不得仅因为账号存在或日志仍保留，就把账号创建时间或最早日志时间批量写入所有成员。

### 预览与应用

当前组织 Admin 使用：

```text
POST /api/organization/current/members/:user_id/billing-start/preview
POST /api/organization/current/members/:user_id/billing-start
POST /api/organization/current/billing/billing-start/preview-batch
```

系统管理员使用对应的 `/api/admin/organizations/:id/...` 路径。

执行步骤：

1. 提交候选 `candidate_billing_start` 获取只读预览。
2. 核对新增请求数、quota、Token、最早/最晚日志、最早保留日志及 `conflict=false`。
3. 由业务负责人确认新增金额和归属边界。
4. 应用时同时提交候选值和预览返回的 `current_billing_start` 作为 `expected_billing_start`。
5. 成功后立即刷新 Summary、Members、Models、Channels、Trend、Logs、Billing CSV 和 Invoice。
6. 核对个人 `Quota`、`UsedQuota`、订阅、Token 和消费日志行数未变化，并保存管理审计记录。

同值重复应用是幂等操作。CAS 冲突时必须重新预览，不得用旧预览重试。已被 TTL 或清理任务删除的日志不能通过本流程恢复或估算。

### 错误回填处置

当前 API 只允许把归属起点向前扩展，不允许调晚起点；因此错误回填不能通过同一接口直接撤销。

- 立即停止该组织的后续规则调整和对外账单导出。
- 保存回填审计、预览结果和回填前后对账数据。
- 优先发布经过评审、具备审计和并发保护的修复能力；不要绕过服务层直接修改数据库。
- 若必须恢复备份，应进入维护窗口，先评估备份时间点之后其他主库写入的恢复影响，再执行完整恢复方案。
- 处置完成后重新校验全部账单维度、Invoice、个人计费事实和审计链路。

## Invoice 与结算规则验证

- 默认账期必须是北京时间当前自然月，自定义账期最长 24 个自然月。
- 未配置类别显示 `1.0000`；`0.0000` 明确显示免费/结算豁免。
- 历史、当前、未来月份规则分别验证，跨月账期应展示多档系数。
- 规则更新的 `expected_version` 冲突必须返回 409，不能覆盖新版本。
- Invoice GET 与专用 CSV 的账号顺序、类别合计、模型合计、折前金额和结算后金额必须一致；CSV 的账号行必须使用用户名，真实姓名行与账号严格一一对应。
- CSV 文件头只允许组织名称、账期和币种；不得出现组织 ID、内部时区/时间戳、规则明细、原始 quota、日志内容、IP、请求 ID、上游请求 ID 或 `other`。
- 模型归类合计行之后只展示“用户上期余额”、“用户当期充值金额”、“用户当期消费金额”和“用户当前余额”，账号列对齐且尾部结算列为空。“用户上期余额”使用账期的期初余额；“用户当期充值金额”使用账期内全部已识别正向入账，包含支付充值、已确认管理员加额及其他已识别入账。期初基线缺失时，首次查账的后台任务自动回放账期前事实，不得用人工零基线替代。旧管理员加额在首次构建基线或该月汇总时自动读取，无需先执行 CLI；只有旧格式无法精确解析时才应停止构建并排查。
- 以主库订单抽查充值金额中的支付部分：只接受 Stripe、Creem、Waffo、Waffo Pancake 的成功订单，完成时间采用 `[账期开始, 账期结束 + 1 秒)`，相同 `trade_no` 的订阅订单必须排除。EPay、未知渠道、空渠道、非成功订单和账期外订单不得计入。
- 当前余额应与导出时主数据库 `users.quota / QuotaPerUnit` 一致；它不是账期末余额，同一账期稍后重导可能变化。
- Billing/Logs 的明细导出必须按有界批次持续输出，不得固定截断；大账期仍需关注反向代理超时和客户端连接时长。

### Invoice 财务补充行对账排查

出现差异时按以下顺序检查，不通过日志文本或订单号猜测补数：

1. 先确认用户是否出现在 Invoice 交叉表账号集合中；账期内无消费的组织成员不会新增为 CSV 列。
2. 核对订单 `status`、`complete_time`、`payment_provider` 和账期半开边界；账期最后一秒计入，下一秒不计入。
3. 用 `trade_no` 检查是否存在订阅订单；订阅购买和余额购买订阅都不属于钱包充值。
4. 按渠道字段语义复算：Stripe 取 `Money`，Waffo/Waffo Pancake 取 `Amount`，Creem 取 `Amount / QuotaPerUnit`。EPay 和不在白名单的渠道按合同不计。
5. 余额差异应以 CSV 生成时刻的主库值为准，排除导出后继续充值、消费或退款造成的变化。
6. 若支持渠道的字段异常，检查服务端告警；系统会排除异常订单，不会猜测金额。若账号已从主库缺失，导出应失败而不是输出零。

## 额度余额 64 位迁移

用户钱包、API Key 余额和相关累计值已迁移到 `int64` / `BIGINT`，单次请求费用仍保持 `int32` 上限。迁移由 `model/quota_balance_bigint_migration.go` 自动执行。

### 发布前检查

- 记录 `users`、`tokens`、`user_quota_adjustments`、`redemptions` 的行数和当前列类型，确认备份可恢复。
- 检查当前最大/最小余额、NULL 数量和异常负值；迁移不自动修数据，异常值需先行处理。
- 确认所有应用实例使用同一代码版本；滚动期间暂停大额调额、充值发放和余额调整类写操作。
- 停止写入后，确认 quota batch store 已完整刷入主库，再主动失效 Redis 用户缓存；未刷盘时不得直接清理缓存。
- 验证 `common.MaxWalletQuota`（`500_000_000_000_000`）、`common.MinWalletQuota`（`math.MinInt32`）和 `quota_per_unit` 已通过 `/api/status` 等能力端点同步给前端。

### 迁移行为

- 迁移在普通 `AutoMigrate` 之前执行，幂等地扩宽 MySQL/PostgreSQL 的相关列：
  - PostgreSQL：`ALTER TABLE ... ALTER COLUMN ... TYPE BIGINT USING ...::BIGINT`。
  - MySQL：`ALTER TABLE ... MODIFY COLUMN ... BIGINT [NOT NULL] [DEFAULT ...]`，保留原 `NOT NULL` 和 default。
  - SQLite：`INTEGER` 本身为 64 位有符号存储，迁移只验证列存在和数据可读，不改列。
- 启动时 `verifyQuotaBalanceSchema()` 检查所有列已是 64 位；任一列仍为 32 位时拒绝开放大额余额。
- 重复运行迁移不得重复产生 DDL；新库建表直接为 `BIGINT`。

### 推荐发布方案

- **短维护窗口（默认）**：停止写入 → 备份 → 单节点执行迁移 → 部署 64 位版本 → 刷盘并失效 Redis → 小额调额/扣费/Invoice 冒烟 → 恢复流量 → 观察一个完整业务周期后再提高业务上限。
- **零停机备选**：先部署只写 `MaxInt32` 范围的兼容版，全部实例升级并完成列扩宽后，再部署提高上限的开放版；开放版必须做 schema readiness check。
- 一旦任一 balance 字段写入超过 `MaxInt32` 的值，旧应用就不再是安全回滚目标；此时只能关闭大额写入开关并保留 64 位版本修复问题，不得降级列或截断余额。

### 停止发布条件

满足以下任一条件时立即停止发布：

- 任一数据库的必要列未完成 bigint 迁移。
- 数据库余额、Redis 余额和 API 返回值不一致。
- 出现负扣费、超额充值被标记成功、调额部分写入或退款重复。
- Invoice GET、CSV 或充值流水与钱包变化无法对账。
- 重启时仍产生重复 DDL 或尝试缩小列类型。

### 观测与对账

- 监控迁移耗时、DDL 失败、调额失败、余额越界、Redis 解析失败和账单聚合失败。
- 抽样对账：DB 余额、Redis 余额、`user_quota_adjustments` 流水、Invoice 补充行和充值订单金额。
- 观察窗口内未发现窄化、负扣费、重复充值、缓存不一致或账单差异后，再开放大额调额。

## 回滚

Invoice 和结算规则没有独立运行时功能开关。需要应用级回滚时：

1. 停止规则写入和历史归属回填操作。
2. 滚动部署到上一个已验证版本。
3. 保留新增列、结算规则表和历史规则版本，不删除审计事实。
4. 验证旧版本忽略新增表后，个人请求、Billing 和 Logs 仍正常。
5. 不清理或改写原始消费日志。

如果回滚原因是错误的成员归属起点，按“错误回填处置”执行；单纯回滚应用版本不会自动恢复已经写入的 `billing_start_at`。
