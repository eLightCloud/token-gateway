# 运维手册

## 发布前通用检查

记录应用版本、主库与日志库版本、迁移实例、各节点配置差异和回滚版本。涉及数据库行为的变更先完成真实 SQLite、MySQL、PostgreSQL 验证；受影响的独立日志路径一并验证。确认备份可恢复、灰度停止条件明确后，再按下方专题操作。

## Vantage 接入配置变更

由超级管理员在 **系统设置 → 运维 → Vantage 接入** 操作；配置含义见[环境配置](./环境配置.md#vantage-专用接入配置)。所有实例需已发布包含该功能的版本，并使用相同主库。功能首次发布后默认关闭，通过页面完成初始化后启用；此后的配置变更无需重启网关。

- 首次设置：生成并复制专用口令，安全保存到 Vantage 后端；填写允许的 IPv4，启用并保存。已保存口令不再显示。
- 出口 IP 更换：先将新 IPv4 加入现有列表，口令留空保存；确认 Vantage 从新出口调用成功，再移除旧地址。多个有效出口可同时保留。
- 口令更换：生成并复制新口令，协调更新 Vantage 后端和网关页面；保存后新请求只接受新口令。没有双口令过渡期，切换期间失败的幂等管理操作由 Vantage 原恢复路径重试。
- 暂停接入：关闭启用开关并保存。新接入管理请求返回 503；此动作不撤销已发放的模型 Key，员工停用仍须执行既有凭据撤销流程。
- 保存失败：页面保留当前编辑内容供重试，服务端保留原配置；重新加载可查看已提交的启用状态、来源列表及口令是否已设置。

白名单按 TCP 对端执行；验收从允许/不允许的入口发送请求，分别确认成功/403，错误口令为 401，伪造转发头不能改变结果。HTTPS、反代及应用直连端口边界须在实际环境验收。不要通过直接修改数据库或通用配置接口绕过专用校验。

## 文本流断开续读

该能力对每个已升级实例的按 Token 计费文本生成流统一生效，没有按渠道、Provider 或模型分配的运行时开关。图片、视频、音频和非流式请求不在此发布边界内。

发布前：

1. 用确定性协议流回归共享 scanner、直接 scanner、scanner + channel、AWS event stream、WebSocket 和 buffered read。
2. 使用短于端到端首事件时间的客户侧上限复现真实文本流，确认客户按预期结束，网关从同一上游流取得完整 usage。
3. 记录 `client_gone` 到上游终态的耗时，确认低于实际配置的续读上限；默认 300 秒。
4. 确认消费日志可同时表达 `client_gone + terminal_success`，且缓存分项、输入与输出 usage 完整。
5. 轮换任何曾在对话、截图或测试记录中暴露的受控测试密钥。

发布时先放量单个实例，观察连接数、总处理时长、空闲/绝对超时、上游错误分布和 goroutine；验证稳定后再滚动发布全部实例。人工查看上游账单页只用于最后验收或客诉解释，不导入数据、不补扣、不退款、不改写消费日志。

若出现连接无法释放、goroutine 增长、空闲/绝对超时异常、上游错误未及时结束或重复结算，立即停止放量并回滚到上一已验证版本。回滚恢复“客户结束后关闭上游资源”的旧行为，不涉及数据库迁移、历史账单或人工调账。

## 组织账单变更发布

组织历史归属起点、Invoice 与流式导出使用成员窗口解释源日志。发布前检查以下条件。

- 主库已备份，并记录当前应用版本、数据库版本和回滚镜像。
- 在目标数据库版本验证启动迁移及重复启动，核对 `organization_members.billing_start_at`、期间汇总唯一索引、`legacy_rule_publication` 审计列和存量数据。
- 独立 `LOG_DB` 或 ClickHouse 的连接、日志保留策略和最早可查询时间已确认。
- 网关、前端和账单工作者使用经核验的同批版本。切换窗口暂停受影响的账单交付和历史归属回填，确认旧工作者退出后开放下载。
- 选取内部组织灰度，保存 Billing 与 Invoice 在相同账期和成员窗口内的已确认消费对账结果。

### 发布顺序

1. 备份主库，记录日志库最早保留时间，并完成下方旧规则与原版 CSV 盘点。
2. 先在测试环境或内部灰度实例发布候选版本并执行迁移；当前版本没有独立 Invoice 功能开关。
3. 验证组织成员、只读 Invoice、Billing、Logs 和个人请求链路没有退化。
4. 使用同一组 Unix 边界对比 Billing 和 Invoice 的消费额度，逐项核对成员窗口、任务费用、日志类型、时区边界和日志保留导致的差异。
5. 验证系统管理员、组织 Admin、Member 的权限矩阵。
6. 灰度通过后完成切换。验证旧工作者停止发布且新节点返回一致的消费口径，再恢复账单下载和交付。
7. 在接近生产的数据量下验证页面 P95、同步 CSV 时长、网关超时和日志库负载，再通知管理员恢复相关操作。

### 旧规则与原版 CSV 盘点

1. 按组织盘点非 `1×` 的旧渠道规则和月度规则、受影响账期、CSV 下游及须继续履行的条款。以实际交付记录识别原版 CSV，按组织、账期和交付版本留存原始文件并演练恢复。系统的 `finalized` 状态只表示已完成汇总。
2. 复核账期快照的消费整数额度是否在总计、账户、分类、模型和交叉单元完整且勾稽。在 `organization_invoice_period_summaries` 同时盘点待重新认领的 `rule_recalc_payload` 和已转存的 `legacy_rule_publication`，核对原始字节、账期与归档索引。源证据缺失的账期登记待核。
3. 由产品与财务确认旧条款已结束或已由实时规则承接。需承接条款时，按[实时消费倍率切换](#实时消费倍率切换)启用，逐项配置并核对实际扣费。财务确认无需承接的条款可在 `legacy` 阶段切换 Invoice。
4. 切换前用候选版发布的快照演练回滚，确认旧读端能否读取。若存在不兼容，暂停受影响账单交付并前向修复。历史价差以原版账单和请求账务事实核对，财务批准的调账单独留痕。

## 历史账单归属回填

### 操作前确认

只对经业务负责人确认属于目标组织的历史账号执行回填。逐成员记录：

| 字段 | 用途 |
|---|---|
| 组织、用户、成员记录 | 确认操作对象 |
| `joined_at` | 保留真实成员加入时间 |
| 当前生效 `billing_start_at` | 作为乐观锁预期值 |
| 候选归属起点 | 业务确认的历史边界 |
| 最早保留日志 | 判断日志库实际可恢复范围 |
| 新增请求数、quota、Token、日志范围 | 对账和审批 |
| 窗口冲突 | 阻断同组织重复统计 |

不得仅因为账号存在或日志仍保留，就把账号创建时间或最早日志时间批量写入所有成员。

### 预览与应用

当前组织 Admin 使用：

```text
POST /api/organization/current/members/:user_id/billing-start/preview
POST /api/organization/current/members/:user_id/billing-start
POST /api/organization/current/billing/billing-start/preview-batch
```

系统管理员使用对应的 `/api/admin/organizations/:id/...` 路径。

执行步骤：

1. 提交候选 `candidate_billing_start` 获取只读预览。
2. 核对新增请求数、quota、Token、最早/最晚日志、最早保留日志及 `conflict=false`。
3. 由业务负责人确认新增金额和归属边界。
4. 应用时同时提交候选值和预览返回的 `current_billing_start` 作为 `expected_billing_start`。
5. 成功后立即刷新 Summary、Members、Models、Channels、Trend、Logs、Billing CSV 和 Invoice。
6. 核对个人 `Quota`、`UsedQuota`、订阅、Token 和消费日志行数未变化，并保存管理审计记录。

同值重复应用是幂等操作。CAS 冲突时必须重新预览，不得用旧预览重试。已被 TTL 或清理任务删除的日志不能通过本流程恢复或估算。

### 错误回填处置

当前 API 只允许把归属起点向前扩展，不允许调晚起点；因此错误回填不能通过同一接口直接撤销。

- 立即停止该组织的后续规则调整和对外账单导出。
- 保存回填审计、预览结果和回填前后对账数据。
- 优先发布经过评审、具备审计和并发保护的修复能力；不要绕过服务层直接修改数据库。
- 若必须恢复备份，应进入维护窗口，先评估备份时间点之后其他主库写入的恢复影响，再执行完整恢复方案。
- 处置完成后重新校验全部账单维度、Invoice、个人计费事实和审计链路。

## 用量与 Invoice 重算

先检查源日志投递、筛选范围和后台任务状态。关系型日志库的 Billing 快照使用当前快照 ID 与修订提交重算；ClickHouse 用量使用兼容接口。Invoice 重算使用当前查询返回的 `expected_token`。两者都走各自的版本校验 POST；普通读取及轮询不带 `refresh=1`。结果生成中保留明确状态，生成完成后使用同一筛选重新导出。接口见[组织账单架构](../20-architecture/组织与组织账单架构设计.md#api-契约)。

## Invoice 与消费对账验证

- 默认账期必须是北京时间当前自然月，自定义账期最长 24 个自然月。
- 比较曾使用旧系数的历史账期和跨切换账期。按整数 quota 核对账户、分类、模型及交叉单元，比较平台端、组织端和 CSV。历史账期重下载使用实际入账消费，原版交付文件从独立归档恢复。
- 验证快照失效后的重建、重算期间暂停导出、费用待核对时的已确认消费小计，以及退役规则路由返回 404。抽查在途任务补结算、退款和迟到日志。核对查询、刷新和下载前后的钱包、Token 和原始消费日志。
- Invoice GET 与专用 CSV 的账号顺序、类别合计、模型合计和消费合计必须一致；CSV 的账号行必须使用用户名，真实姓名行与账号严格一一对应。
- CSV 文件头包含组织名称、账期、币种和必要的金额说明；不得出现组织 ID、内部时区/时间戳、规则明细、原始 quota、日志内容、IP、请求 ID、上游请求 ID 或 `other`。
- 模型归类合计行之后展示“用户上期余额”、“用户当期流入金额”、“用户当期消费金额”和“用户当前余额”，各项金额与账号列严格对齐。“用户上期余额”使用账期的期初余额；“用户当期流入金额”使用账期内全部已识别正向入账，包含支付充值、已确认管理员加额及其他已识别入账。期初基线缺失时，首次查账的后台任务自动回放账期前事实，不得用人工零基线替代。旧管理员加额在首次构建基线或该月汇总时自动读取，无需先执行 CLI；只有旧格式无法精确解析时才应停止构建并排查。
- 以主库订单抽查充值金额中的支付部分：只接受 Stripe、Creem、Waffo、Waffo Pancake 的成功订单，完成时间采用 `[账期开始, 账期结束 + 1 秒)`，相同 `trade_no` 的订阅订单必须排除。EPay、未知渠道、空渠道、非成功订单和账期外订单不得计入。
- 当前余额应与导出时主数据库 `users.quota / QuotaPerUnit` 一致；它不是账期末余额，同一账期稍后重导可能变化。
- Billing/Logs 的明细导出必须按有界批次持续输出，不得固定截断；大账期仍需关注反向代理超时和客户端连接时长。

### Invoice 财务补充行对账排查

出现差异时按以下顺序检查，不通过日志文本或订单号猜测补数：

1. 先核对成员计费窗口是否与账期相交。相交账号即使零消费也进入账号集合；已离开账号保留在其有效账期。
2. 核对订单 `status`、`complete_time`、`payment_provider` 和账期半开边界；账期最后一秒计入，下一秒不计入。
3. 用 `trade_no` 检查是否存在订阅订单；订阅购买和余额购买订阅都不属于钱包充值。
4. 按渠道字段语义复算：Stripe 取 `Money`，Waffo/Waffo Pancake 取 `Amount`，Creem 取 `Amount / QuotaPerUnit`。EPay 和不在白名单的渠道按合同不计。
5. 余额差异应以 CSV 生成时刻的主库值为准，排除导出后继续充值、消费或退款造成的变化。
6. 若支持渠道的字段异常，检查服务端告警；系统会排除异常订单，不会猜测金额。若账号已从主库缺失，导出应失败而不是输出零。

## 额度余额 64 位迁移

用户钱包、API Key 余额和相关累计值已迁移到 `int64` / `BIGINT`，单次请求费用仍保持 `int32` 上限。迁移由 `model/quota_balance_bigint_migration.go` 自动执行。

### 发布前检查

- 记录 `users`、`tokens`、`user_quota_adjustments`、`redemptions` 的行数和当前列类型，确认备份可恢复。
- 检查当前最大/最小余额、NULL 数量和异常负值；迁移不自动修数据，异常值需先行处理。
- 确认所有应用实例使用同一代码版本；滚动期间暂停大额调额、充值发放和余额调整类写操作。
- 停止写入后，确认 quota batch store 已完整刷入主库，再主动失效 Redis 用户缓存；未刷盘时不得直接清理缓存。
- 验证 `common.MaxWalletQuota`（`500_000_000_000_000`）、`common.MinWalletQuota`（`math.MinInt32`）和 `quota_per_unit` 已通过 `/api/status` 等能力端点同步给前端。

### 迁移行为

- 迁移在普通 `AutoMigrate` 之前执行，幂等地扩宽 MySQL/PostgreSQL 的相关列：
  - PostgreSQL：`ALTER TABLE ... ALTER COLUMN ... TYPE BIGINT USING ...::BIGINT`。
  - MySQL：`ALTER TABLE ... MODIFY COLUMN ... BIGINT [NOT NULL] [DEFAULT ...]`，保留原 `NOT NULL` 和 default。
  - SQLite：`INTEGER` 本身为 64 位有符号存储，迁移只验证列存在和数据可读，不改列。
- 启动时 `verifyQuotaBalanceSchema()` 检查所有列已是 64 位；任一列仍为 32 位时拒绝开放大额余额。
- 重复运行迁移不得重复产生 DDL；新库建表直接为 `BIGINT`。

### 推荐发布方案

- **短维护窗口（默认）**：停止写入 → 备份 → 单节点执行迁移 → 部署 64 位版本 → 刷盘并失效 Redis → 小额调额/扣费/Invoice 冒烟 → 恢复流量 → 观察一个完整业务周期后再提高业务上限。
- **零停机备选**：先部署只写 `MaxInt32` 范围的兼容版，全部实例升级并完成列扩宽后，再部署提高上限的开放版；开放版必须做 schema readiness check。
- 一旦任一 balance 字段写入超过 `MaxInt32` 的值，旧应用就不再是安全回滚目标；此时只能关闭大额写入开关并保留 64 位版本修复问题，不得降级列或截断余额。

### 停止发布条件

满足以下任一条件时立即停止发布：

- 任一数据库的必要列未完成 bigint 迁移。
- 数据库余额、Redis 余额和 API 返回值不一致。
- 出现负扣费、超额充值被标记成功、调额部分写入或退款重复。
- Invoice GET、CSV 或充值流水与钱包变化无法对账。
- 重启时仍产生重复 DDL 或尝试缩小列类型。

### 观测与对账

- 监控迁移耗时、DDL 失败、调额失败、余额越界、Redis 解析失败和账单聚合失败。
- 抽样对账：DB 余额、Redis 余额、`user_quota_adjustments` 流水、Invoice 补充行和充值订单金额。
- 观察窗口内未发现窄化、负扣费、重复充值、缓存不一致或账单差异后，再开放大额调额。

## 实时消费倍率切换

1. 确认所有处理请求和任务的实例能识别旧、新快照；备份配置并盘点旧个人规则中的多倍率及精度冲突。根据商业条款盘点记录准备须在 `active` 后人工维护的组织规则。
2. Root 使用专用迁移接口提交 `freeze`，核对当前阶段为 `frozen`；此前受理的请求和任务继续按原快照处理。
3. 提交 `activate`。有冲突时保持冻结并检查返回清单；未启用时可用 `resume` 恢复 legacy。启用后由 Root 配置须履行的组织模型和渠道规则，随后核对显式 1、组织继承、系统兜底、渠道重试、任务和账单。存量配置保留作核账资料。
4. 异常时停止放量并保留能读取当前快照的版本；不要直接回滚到不识别已提交快照的旧二进制。详见[迁移合同](../20-architecture/用户与组织实时模型折扣架构设计.md#旧个人消费规则迁移与切换)。

首次启用优惠渠道准入时，先暂停优惠和采购配置写入，盘点旧配置并核对本次空优惠发布基线。确认 API、任务和 WebSocket 入口均已升级，再由 Root 冻结并启用。验收显式 1 限制、撤权导致空交集、清空后恢复以及旧任务结算。排查 `pricing_channel_unavailable` 时，以请求 ID 关联 `pricing channel unavailable` 日志，并核对授权、计价范围及渠道状态。需要回退到不认识渠道范围的版本时，先隔离受影响的新请求，保留数据库与账务事实。

## 模型广场筛选发布

1. 在所有实例部署支持 `/api/pricing/catalog` 和厂商归属 API 的版本，再切换广场前端。用访客检查默认国内厂商，用有海外优惠及无优惠的客户检查目录和详情直链。用管理员账号验证厂商归属预览、保存及清除覆盖。
2. 新配置同步后，通过另一窗口聚焦或重新打开广场核对生效。恢复某类账号的原目录时，在「系统管理 → 运营设置 → 系统行为」关闭对应筛选。回退专用目录服务前，先回退前端查询入口。

## 人民币表达式定价发布

保存 `v2:` 人民币报价前，先升级所有执行计价表达式的节点。用受控模型核对原币报价、美元预览、实际扣费与历史快照。调整汇率后重新对账，同一批有快照明细的历史人民币净额应保持原值，无快照明细的历史列应留空。

## Microsoft Graph 发信验证

1. 在所有发信节点配置同一 `EMAIL_DELIVERY_STORAGE_KEY`。确认目标租户、应用和发件邮箱后，由 Root 在邮件设置保存新修订并完成敏感验证。改租户或应用时同时替换凭据；记录修订和关联 ID。
2. 用已保存版本向受控邮箱发测试邮件，依次核对配置、Token、Graph 提交。验证授权邮箱实际收件，并用受控样本验证未授权邮箱拒绝。再用真实业务触发器验证一类身份邮件。HTTP 202 记录为受理，收件用邮箱或租户投递记录核实。
3. 在 Token 刷新后再次发送。轮换应用凭据后逐节点对照配置修订、同步时间和实际发送，确认目标租户及邮箱授权均有效。记录脱敏证据。
4. 未知结果先查收件箱与租户投递记录。需要回退时，在当前版本显式切回经验证的旧 SMTP，协调停发、核对所有节点和旧二进制读取的配置，再决定回退；旧通道不可用时停发并前向修复。配置合同见[邮件架构](../20-architecture/微软应用身份邮件架构设计.md)。

## 运维通知预览与启用

1. 确认系统邮件可达、收件地址受控，先开启每日功能并保持仅预览。北京时间 06:00 后检查前一自然日的任务、两类日报预览、数据缺口和筛选。对照有消费、出错、订阅临期、静默账户和禁用账户。
2. 发布前在受控环境演练跨日、低负载与暂停恢复，检查聚合和连接等待。覆盖消费账户上限跳过整期、单页订阅超限跳过受影响账户，以及重复运行不重发。聚合超时或跳过时检查 `operations_daily` 的结果和警告。
3. 容量和送达达到发布条件后，取消仅预览并观察投递。应急开关独立操作，使用隔离负载和受控收件人验证触发及恢复。生产容量尚未验收时维持预览或关闭。
4. 仅对当前可处理的日报执行人工重试。提交结果未知时先核对实际收件，再明确确认重试。发送压力、数据异常或错收件时开启仅预览或关闭相应开关，记录已受理邮件及受影响范围。

## 使用日志灰度

1. 检查实际 `LOG_SQL_DSN`、应用与后台连接池和任何外部清理任务。保留生产禁删配置，核对 ClickHouse 当前有效 TTL，并确保旧版本回退仍有独立的保留措施。
2. 按[路线图](../50-planning/路线图.md#log-release)取证稳定的端到端纯写入基线。用同一拓扑复跑混合组，核对资金和日志、数据库等待、读取退让及最老积压。配置见[环境配置](环境配置.md#使用日志读取与保留)。
3. 达到门槛后在具备签名一致性的关系型部署小范围启用 `PERSONAL_LOG_CURSOR_ENABLED`。验证最新一页、按请求 ID 定位、连续翻页与旧深页链接。同步观察旧列表、统计和导出是否按预算退让。
4. 未达门槛时保持关闭；灰度中出现资金、日志或写入尾延迟异常时停止放量并关闭游标。保留原始日志、共享读取保护和结算恢复，核对旧入口可在同等预算下承载回退用户。分离日志库短时故障时核对恢复器按原操作幂等补投。

## 回滚

Invoice 随应用版本切换。需要应用级回滚时执行以下检查。

1. 暂停相关计价配置写入、历史归属回填和受影响账单交付。
2. 核对旧版本读取新版快照、处理在途任务以及是否重新应用旧组织渠道倍率的实际影响。实时计价已激活时，按实时计价迁移合同处理恢复。
3. 保留新增列、旧规则、旧审计负载和全部源账务记录。仅在兼容性及对账验证通过后恢复交付；旧账单读端无法读取新版快照时继续暂停交付并前向修复。

如果回滚原因是错误的成员归属起点，按“错误回填处置”执行；单纯回滚应用版本不会自动恢复已经写入的 `billing_start_at`。
