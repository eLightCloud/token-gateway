# 代理分销阶段实施计划

## 目标、依据与当前状态

本计划把已确认的一期代理功能拆成可实施、可测试、可停止和可追溯的交付阶段。依据为[产品设计](../10-product/代理分销与用户专属倍率产品设计.md)、[架构设计](../20-architecture/代理分销与用户专属倍率架构设计.md)、[技术实施方案](../80-dev/2026-11-03-代理分销与用户专属倍率实施方案.md)及 [ADR-0003](../20-architecture/decisions/0003-代理额度异步记账与用户专属倍率.md)。业务与技术合同仍由对应设计文档拥有，本文不重新定义价格或权限。

截至 2026-11-04，S0 已执行源码核对、本地基线、隔离三库及目标 PostgreSQL 18.4 主库迁移验证，当前待验收（基线有失败），未标记已验收；结果见下方 S0 执行记录。S1 已完成本阶段实现与验证，保持待验收；S2 已完成本阶段实现与验证，保持待验收；S3–S6 已完成实现及下述隔离验证，保持待验收；S7、S8 未开始实施。阶段完成日期、执行人和测试结果不得预填。本文唯一维护阶段执行状态、验收证据与发布结论；80-dev 保留技术接线、工作包和测试说明，不再另列一套执行状态。

一期交付包含普通用户专属倍率、一级专用代理、单客户授权配置、完整消费与退款记账、代理批量汇总、全用户安全补齐、当前 UI 调整和导出。容量按单 A 持续 500 QPS、连续数小时设计；不能因代理账务积压暂停调用。实际资金、身份转换、客户转移、跨客户批量配置和额度池不进入阶段范围。

范围说明以产品设计为准：上游商务对账和客服退款决策、人工入口不纳入本期；违规扣费沿现有系统配置记账，部分退款只保留底层计算与幂等验证。S0-G5 据此关闭，不再作为 S3 前置或技术验收阻塞。下方早期 S0 复验记录中关于 G5 待确认的文字保留历史语境，当前状态以本段及 S0-G5 条目为准。

## 拆分原则与执行纪律

1. **代码合入与业务开放分开**：前期可交付加法式 schema、受限 API 和安全 UI，不向真实客户开放尚未闭环的 B 调用。阶段测试只用隔离账号与数据库，不为半成品默认放开权限。
2. **按完整行为验收**：价格配置、预扣、持久事实、结算、退款和恢复必须一起形成可验收调用闭环；只有函数或页面不算阶段通过。
3. **三库验证前移**：任何阶段发生数据库行为变更，该阶段必须执行真实 SQLite、MySQL、PostgreSQL 验证，不能等到 S7 才补。S7 再验证完整升级与运行组合。
4. **共享入口最小接线**：主体实现放专用新模块；不借阶段拆分重构原计费、组织、首页或插件系统。每个交付列明旧文件的必要改动及兼容验证。
5. **状态以证据变更**：待实施 → 实施中 → 待验收 → 已验收；缺环境记为“验证受阻”，不能标完成。真实业务开放另记发布状态。
6. **阶段粒度不等于测试文件粒度**：优先扩展现有合适测试，一份共享 fixture 支撑端到端场景；不为每个阶段或每一调用层机械复制测试。新 Go 测试遵守 testify 规则。
7. **完整性优先于日期承诺**：执行人、部署环境和 S0 取证完成后才估工期。不以日历到期代替退出条件，不把真实业务范围裁剪成只支持最容易的协议后宣称一期完成。

## S0：建立可执行基线与验收环境

### 进入条件

产品、架构和 UI 合同已有稳定入口；工作树现有用户改动已识别，记录实施起点提交与未提交差异，不覆盖本轮文档或其他用户改动。

### 实施与交付

- S0.1 逐项列出实际文件、函数及调用顺序：身份/角色、模型渠道候选、共同基数、预扣、补预扣、同步结算、任务提交、零差额完成、退款、恢复及 journal 清理。输出入口清单，不仅列包名。
- S0.2 盘点目标部署开放协议和任务类型；每项登记当前启用状态、能否授予 B、实现阶段和验证责任。普通用户现有入口也记录，避免只测代理而破坏兼容。
- S0.3 固定新增 DTO、错误语义、操作 ID、生命周期版本、基数精度、事件时间、余额与占用守恒、分页及导出快照合同。区分实际资金发生时间、确认时间和后台处理时间。
- S0.4 建立真实三库测试环境和发布版升级样本，记录引擎/驱动版本、字符集、日志库分离及 Redis 开关。核对 MySQL 最低版本索引容量，不能只使用 SQLite fixture。
- S0.5 创建确定性的共享业务 fixture、可控上游和邮件接收环境；补齐可重复执行的阶段验证入口。新建命令或脚本必须在本阶段实际提交、执行后登记，不能把本计划中的名称当成已有工具。
- S0.6 核对最新稳定 OWASP ASVS、适用 requirement ID 与实现责任，形成认证、会话、授权、CSRF、秘密存储和恢复控制矩阵。人工恢复规程列出待落实责任人。
- S0.7 运行受影响基线测试和构建；记录既存失败、触发条件及对本专项的影响。固定容量环境、测量边界、请求时延与错误率验收阈值，阈值在压测前确定，不在失败后静默放宽。

交付物进入本计划的证据记录及对应代码测试资源，不再创建多份平行业务规范。测试资产不得包含生产凭证、实际客户正文或真实支付信息。

### 测试与退出条件

- T0.1 现有 Go/前端基础命令可运行，成功与失败均有退出码；被测行为不可用时明确受阻，不把零测试匹配当通过。
- T0.2 现有用户、渠道和钱包基线 fixture 能在三库创建、清理和重建，不污染其他数据库；尚不存在的新代理 schema 使用固定输入与期望规格，实际持久化验证归 S1，不要求 S0 先实现新业务表。
- T0.3 可控上游能确定性返回成功、用量、流式中断、任务待处理/完成/失败；邮件环境能检验单次激活链接。
- T0.4 所有目标入口、精度、事件状态及安全控制均有归属；未知项落实为实施前阻塞任务，不允许带未知资金语义进入 S3。

退出必须具备环境清单、基线记录、入口矩阵、可执行验证入口及固定验收参数。若真实三库或关键恢复证据缺失，可继续只读取证，但不得宣称 S0 完成。

2. 开发审批责任角色为独立 root 测试操作者；普通管理员必须显式取得 `account_security.recover`，A 没有此能力。审批人不能恢复自己；普通管理员不能处理同级/更高角色，独立 root 可按相同核验流程恢复其他 root，并需用现有因素重新验证。UI 与服务端要求核验确认和记录；证明绑定目标、用途和工单，邮箱变更还绑定新地址。
3. 必须先向原邮箱成功通知再重置；SMTP 故障不执行因素移除。启用全局策略前保留至少两名独立审批操作者，root 恢复码分别离线保管；只剩一个 root 且所有恢复码遗失时，不提供绕过核验的在线后门。资金与调用 Key 不随普通 MFA 恢复改变，事务记录恢复编号和鉴权版本；会话全部撤销后，申请人重新登录并完成因素配置。
4. 只有确认消费凭证泄露时才选择独立撤销消费 Key，默认关闭。此时在主库禁用 Key，使用既有缓存 mutation fence 清理旧认证快照；不以普通 MFA 重置代替泄露处置。
5. 演练使用真实回环 SMTP 接收器、合成管理员和客户；验证无权限/无证明/重复证明失败、通知产生、因素移除、恢复记录唯一、旧会话无效、正常 Key 有效及显式泄露处置后 Key 无效。生产人员姓名、工单系统和实际身份材料不在开发测试中虚构；S8 上线时须将这些开发角色绑定到真实责任人与批准流程。

- S7.3 单独执行消费器暂停 10 分钟后恢复场景，恢复期间继续 500 QPS；记录积压、消费速率及追平时间。10 分钟是故障测试条件，不是运行时停用阈值。
- S7.4 注入消费器/请求节点重启、Redis 故障、日志库故障、主库事务失败和重复投递；并验证全局安全补齐及 MFA 恢复期间既有 Key 连续调用。
- S7.5 从主库备份恢复身份、配置、持久请求状态、事件和投影；不重放上游调用，只恢复原账务，验证客户端重试的幂等边界。

### 可测量退出条件

- T7.1 常态段实际完成吞吐达到持续 500 QPS，不以客户端“计划发送”代替完成；无非预期业务错误，P50/P95/P99 符合 S0 冻结阈值。
- T7.2 正常消费器下，稳态观察窗口内积压无持续增长；停止负载后待处理事实可全部处理，最终占用仅对应真实未完成请求。
- T7.3 故障测试恢复后处理速率持续高于同期事件产生速率并最终追平；追平时限在 S0 固定。若无法追平，应优化再测，不能用积压停用降流通过。
- T7.4 全量对账满足下文守恒式、每操作入账至多一次、无遗漏事件和无法解释的余额差异；抽样正确不替代全量聚合对账。
- T7.5 故障期错误按类别记录：消费器/日志库故障不能冒充主库失败；主库无法提交时不得放行上游，预期错误与常态段分开统计。
- T7.6 所有引擎功能兼容有证据，目标部署容量有独立证据；SQLite 正确性通过不等于其能达到相同吞吐。
- T7.7 记录磁盘与事件表增长、锁等待、CPU/内存/I/O、批次及请求耗时，具备持续数小时以上的存储与恢复余量。

退出交付容量/故障报告、数据库矩阵、备份恢复及全量对账结果。未满足硬指标不得进入 S8；不得通过丢事件、关审计或跳过资金写入提高数字。

### 黄金账本 G1：预扣、结算与全退

初始 A 已结算采购余额 10000、占用 0，B 钱包 1000；A 倍率 0.8、B 倍率 0.9；下表为消费器处理到该事件之后的结果：

| 步骤 | 折前基数 | B 钱包 | A 已结算余额 | A 占用 | A 可用额度 | 累计客户消费/采购支出/差额 |
|---|---|---|---|---|---|---|
| 初始 | — | 1000 | 10000 | 0 | 10000 | 0 / 0 / 0 |
| 预扣 | 100 | 910 | 10000 | 80 | 9920 | 未最终确认 |
| 最终结算 | 60 | 946 | 9952 | 0 | 9952 | 54 / 48 / 6 |
| 已结算全退 | 原交易全部 | 1000 | 10000 | 0 | 10000 | 0 / 0 / 0 |

预扣和最终结算是同一消费生命周期，不把 90 与 54 再次相加。退款发生在下一账期时，消费 54/48 留在原账期，退款 -54/-48 进入新账期，净额守恒。若消费器延迟，B 仍实时变化，A 保留旧投影并标明更新时间，不伪造同步完成。

### 黄金账本 G2：零差额与负差额

- 预扣基数和最终基数均为 100：B 最终扣 90，A 最终支出 80，占用归零；即使 B 余额没有结算差额，也必须有最终完成事实。
- 另一独立请求，基数 100、A 0.8、B 0.7：采购支出 80、客户消费 70、差额 -10，不能因亏损拒绝；全退后两边精确冲回原值。
- 基础费用为零：专属倍率仍要求正数，但保留原计费零费用语义，不强行扣最小单位。

### 黄金账本 G3：高价渠道重试不足

独立 B 初始钱包 95；渠道甲 rB=0.9、乙 rB=1.1，两渠道预估基数均 100，均在有效授权内。甲预扣 90 后钱包 5；甲明确失败且无可计费服务，切乙需补 20，但余额不足，因此乙上游调用次数必须为 0。沿原失败退款后 B 回到 95，A 占用归零，无实际采购支出。另测补足成功及乙未授权两条分支。

### 全量对账不变式

1. B 当前钱包 = 初始钱包 + 所属 A 净调额 − 当前生命周期已扣净额；该净额包含尚未结算的实际暂扣，不能再把最终消费重复减一次。
2. A 已结算采购余额 = 初始采购余额 + 管理员净调额 − 已入账净采购支出；退款在净支出中为冲销。
3. A 可用额度 = 已结算采购余额 − 已入账处理中占用；占用释放和支出确认不可双扣。
4. A 净计费差额 = 已确认客户净消费 − 对应净采购支出；待确认请求不计实际差额，待入账与业务完成分别标记。
5. 每个资金操作的代理事实至多生效一次，重复处理、事务回滚、进程崩溃和 journal 清理不改变最终结果；每笔退款能追溯原交易及原倍率。

对账使用持久事件、请求状态与权威钱包数据，不靠当前折扣反推，不只比较可清理日志。部分退款和小额度另设精度用例检验舍入，不以黄金大整数掩盖误差。
