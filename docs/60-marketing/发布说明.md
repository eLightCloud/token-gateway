# 发布说明

## 2026-08-25：组织 Invoice 财务对账摘要

组织 Invoice 新增按账户的余额对账视图，并强化任务计费预留：

- Invoice 页新增财务摘要表：按账户展示用量、期初余额、充值、管理员增调/减调、其他流入流出与期末余额，统一按美元呈现；每行标注对账状态（生成中、推导、已对账、不完整），CSV 导出同步附带。
- 汇总改由后台任务生成并持久化，跨月账单自动补齐历史月份；未生成完成时先展示推导值，不阻塞页面。
- 账户口径覆盖成员在组织内外的完整有效期，充值入账数据自动补齐；账本启用前的历史管理员调额可核对后固化为事实记录，支撑余额闭合（期初 + 流入 − 扣减 = 期末）对账。
- 统一任务每次上游尝试前确保完成额度预扣预留；重试复用同一计费会话，仅补足更高的预扣目标。
- 个人钱包、订阅、API Key 与请求计费流程不变；本说明覆盖提交 `1eecd31c`。

## 2026-08-24：组织渠道倍率支持加价

组织渠道折扣扩展为组织渠道倍率，在保持折扣能力的同时支持加价：

- 有效范围调整为大于 `0` 且小于 `10`，最多六位小数；例如 `0.8` 按原价的 80% 计费，`1.5` 按原价的 150% 计费，未配置渠道仍按 `1.0`。
- 倍率大于 `1` 时，系统在渠道确定后使用现有预扣机制补足已知加价；最终账单仍按实际用量和请求开始时固定的渠道倍率结算，多退少补。
- 同步请求、WebSocket、分层计费和统一任务跨渠道重试使用同一规则；全局渠道倍率、用户组倍率、账单聚合和退款机制不变。
- 配置和历史仍仅 Root 可访问，保存方式、乐观锁和不可变历史均保持不变。
- 如需回滚到仅支持不超过 `1` 的旧版本，必须先将所有大于 `1` 的组织渠道倍率调整为不超过 `1` 或清空；否则旧版本会拒绝解析这些快照。

## 2026-08-24：组织渠道折扣上线

本次版本上线组织渠道折扣：系统最高管理员（Root）可以为每个组织按上游渠道设置优惠折扣，组织成员的请求自动按折后价格计费，账单与消费记录直接体现折后金额。同时提升了账单结算的可靠性，进程异常或轮询遗漏导致的未完成扣费和账单记录会在约 15 秒内自动补齐，不会丢失或重复。

### 重点新增

#### 组织渠道折扣

- 折扣按渠道独立设置：同一组织在不同渠道可以有不同的折扣；未设置的渠道按原价计费。
- 折扣取值必须大于 0 且不超过 1，最多六位小数，例如 `0.8` 表示按原价的 80% 计费；设为 `1` 等同于未设置，清空全部渠道即取消折扣。
- 组织管理页新增“渠道折扣”页签：可一次编辑多个渠道后统一保存生效；如果其他人刚保存过，页面会提示先查看最新配置再重试，不会互相覆盖。
- 折扣只影响组织成员请求的最终计费金额；用户分组倍率、渠道倍率、充值价格等既有价格体系均不变，个人钱包、订阅、API Key、充值和退款流程也不变。
- 请求开始后折扣即固定：结算、渠道重试、退款都按请求开始时的折扣计算；保存新折扣只影响之后发起的新请求。

#### 折扣记录与对账

- 每次保存都会留下一份不可修改的历史记录，可查看保存时间、操作人，以及相比上一份记录每个渠道折扣的新增、调整和移除情况。
- 消费日志和组织 Invoice 直接体现折后金额，不再二次打折，方便对账；如需核查单笔请求的折扣依据，可查看日志中附带的折扣记录信息。

#### 账单结算可靠性提升

- 扣费、用量统计和账单记录统一完成，避免出现“已扣费但无账单”或“有账单但未扣费”的中间状态。
- 因进程重启、异常退出或任务轮询遗漏而未完成的结算和日志，系统会自动补齐；账单记录不会丢失，也不会重复写入。
- 失败任务的退款与额度回收一次性完成，不再分步处理。

### 使用说明

- 折扣配置与历史仅 Root 账号可查看和修改，普通管理员访问会提示无权限；组织成员没有折扣入口，只在账单中看到折后金额。
- 预扣按未打折价格执行：用户余额低于原价预扣额时，即使余额足以支付折后费用，请求仍可能被拒绝；属本次接受的取舍，如遇相关客诉可按此口径解释。
- 回滚到旧版本后折扣自动失效（所有请求按原价计费），无需额外数据处理。
- 建议发布时先完成数据库备份，并在测试组织上验证折扣配置、账单金额和历史记录后再对生产组织开放。
- 本说明覆盖 `main` 分支自上一份发布说明截止提交 `95654213` 以来的 2 个提交（含 1 个纯文档提交），功能截止提交 `e428d461`。

## 2026-08-22：本周功能更新（08-19 至 08-22）

本周版本聚焦组织账单数据隔离与额度余额容量扩容：组织管理员现在可以控制成员是否能在组织账单中看到渠道信息；同时，用户钱包、API Key 余额和调额流水已迁移到 64 位，解决管理员无法向零余额用户发放大额额度的问题。

### 重点新增

#### 组织账单渠道可见性控制

- 系统管理员可为每个组织独立设置“组织成员是否可在账单中看到渠道信息”。
- 关闭可见性后，组织普通成员在账单列表、明细和导出 CSV 中均不再看到渠道名称、渠道 ID、上游请求地址等敏感字段；组织管理员和系统管理员仍保持完整视图。
- 在渠道信息隐藏模式下，后端会主动剥离日志和 CSV 中的渠道字段，避免通过前端简单隐藏被绕过的风险。
- 覆盖组织账单查询、组织 Invoice CSV 导出、成员用量明细等路径；现有默认行为保持不变，需由管理员显式启用隐藏。

#### 额度余额 64 位迁移

- 将钱包余额、API Key 余额、兑换码额度、调额流水等累计/发放类额度字段从 32 位整数迁移到 64 位（`BIGINT`），覆盖 `users.quota`、`users.used_quota`、`users.aff_quota`、`users.aff_history`、`tokens.remain_quota`、`tokens.used_quota`、`redemptions.quota`、`user_quota_adjustments` 的 delta 与 balance 字段。
- 新增独立迁移模块 `model/quota_balance_bigint_migration.go`，按 SQLite / MySQL / PostgreSQL 分别执行幂等扩宽，重启时不会重复改列，并在迁移后校验所有目标列确为 64 位。
- 区分“单次计费额度（charge quota）”与“钱包余额（balance quota）”：单次请求的预扣、结算、退款和消费日志仍保持 32 位饱和保护，避免大额余额导致单次巨额扣费或回绕为负；充值、调额、兑换、订阅转余额等发放入口统一使用 64 位严格转换边界。
- Redis 用户缓存结构升级到 schema version 3，`UserBase.Quota` 和上下文读取改为 `int64`，大额余额在缓存与主库间往返不再窄化。
- 管理员调额保留同一事务内的 `FOR UPDATE` 行锁、余额写入和不可变调额流水；结果超过业务上下限时整笔事务回滚，不产生部分写入。

### 文档与方案

- 新增《组织合同计费方案》，明确组织级合同倍率、渠道折扣、快照计费与发票不重复折扣的长期设计口径。
- 新增《额度余额 64 位迁移实施方案》，完整记录边界盘点、数据库迁移、缓存升级、发布窗口和回滚条件。

### 使用说明

- 组织账单渠道可见性只控制信息展示范围，不改变成员的扣费主体、余额或请求计费逻辑。
- 64 位迁移开放的是“余额可保存多大”而非“单次请求可扣多少”；单次请求仍受现有 32 位计费上限保护。
- 升级后若数据库中已写入超过 `MaxInt32` 的余额值，不可回滚到旧版本；发布前需完成可验证备份并按迁移方案执行维护窗口。
- 本说明覆盖 `main` 分支在 2026-08-20 00:00 至 2026-08-22 23:59（UTC+8）的 2 个提交，截止提交 `95654213`。

## 2026-08-09：本周功能更新（08-03 至 08-09）

本周版本重点补齐了 Token 账单人工对账、组织 Invoice 模型分类和流式请求断开后的 Token 结算能力，同时合入上游 `v1.0.0-rc.24`，并对渠道管理、兑换码、首页、账号安全和发布流程进行了优化。

### 重点新增

#### Token 账单与人工对账中心

- 为 `root` 最高管理员新增“Token 账单”只读工作台，账单数据直接来自现有消费与退款记录，不连接上游服务商，也不会改变 Relay 或计费流程。
- 支持客户账单、渠道用量、按上游三个视角；可按账期、账单类型、组织、模型、渠道和 Request ID 筛选。
- 提供额度、记录数、输入 Token、输出 Token 和 Token 合计汇总，并支持按客户、模型、渠道及当前 API 地址分组下钻到原始账单。
- 支持导出当前筛选条件下的 CSV；单次查询账期最长为 92 天。
- 消费日志关闭时会提示账单可能不完整，避免将缺失记录误判为零用量。

#### 组织 Invoice 模型分类

- 为组织 Invoice 增加统一模型类别目录，覆盖 Claude、GPT、Gemini、Minimax、Deepseek、Kimi、GLM、Qwen 和向量模型。
- 模型名称经过规范化后优先精确匹配，再按明确的模型家族前缀归类；未收录模型会进入稳定的单模型兜底类别，避免不同模型被错误合并。
- Invoice 页面增加类别名称本地化，类别分组和结算系数展示更加一致。

#### 流式请求断开后的 Token 结算

- 当客户侧在文本生成流结束前超时或断开时，网关会立即停止向客户写入，但在有界时间内继续读取已建立的上游流，尽量取得完整终态 usage。
- 覆盖共享 HTTP 流、AWS Bedrock 事件流、讯飞 WebSocket，以及 Cohere、智谱、PaLM 等不同流式传输路径。
- 客户断开原因与上游最终结果分别记录；只有取得成功终态和完整 usage 时才复用原结算链路，读取失败、usage 缺失或续读超时仍进入既有错误与退款路径，不使用无法证明的估算值补账。

### 功能与体验优化

- 渠道模型拉取：扩充并细化模型分类规则，改善 OpenAI、Anthropic、Gemini、DeepSeek、Qwen、Mistral、Meta、Cohere、图像和视频等模型的归类展示。
- 兑换码：修复编辑兑换码额度时因展示精度截断造成的额度损失，并让输入步进与当前货币精度保持一致。
- 首页：恢复本地首页的完整样式，并降低主要操作按钮的色彩强度，提升视觉一致性。
- 账号数据一致性：访问令牌轮换改为仅更新令牌字段，邀请奖励改为数据库原子累加，降低并发更新覆盖余额、邀请额度等字段的风险。
- 高风险操作保护：为访问令牌生成和邀请额度转移增加按用户限流，减少重复请求与滥用风险。

### Relay 与兼容性改进

- 为可重放的上游请求补充 `GetBody`，使 HTTP/2 在上游流重置时能够透明重试请求体；重放元数据同时收敛到请求体存储对象，覆盖文本、Embedding、图片、重排和任务等 Relay 路径。
- 渠道测试对 Claude 和 Gemini 端点改用各自原生请求格式，降低因兼容格式差异导致的误判。
- 同步上游 `v1.0.0-rc.23` 与 `v1.0.0-rc.24` 的功能和修复。

### 发布流程

- GitHub Release 同步至 GitCode 的流程改为手动指定标签触发。
- 支持只同步发布说明，发布附件改为可选项；已有附件会自动跳过，减少重复上传和发布等待。

### 使用说明

- Token 账单中的渠道和按上游金额是系统已记录的客户计费额度，不代表供应商成本；按上游视角使用渠道当前 API 地址归组，不是历史请求地址快照。
- 组织 Invoice 的模型分类和结算系数只影响组织报表展示，不改变个人钱包、订阅、API Key、预扣、结算或退款。
- 本说明覆盖 `main` 分支在 2026-08-03 00:00 至 2026-08-09 23:59（UTC+8）的 15 个提交，截止提交 `6722d12a`。

## 2026-07-15：组织管理与组织账单正式上线

eLight 已上线组织管理与组织账单能力，帮助企业和团队在不改变个人账号扣费方式的前提下，集中管理成员并分析 AI 消费。

### 主要能力

- 系统管理员创建和维护组织，组织 Admin 管理成员与角色。
- Admin 查看组织完整账单，Member 查看本人在组织有效期内的用量。
- 按成员、模型、渠道和日期分析消费金额、原始 quota、请求数与 Token 用量。
- 提供趋势、消费明细和账单导出，保留可审计的历史消费事实。
- 支持组织成员加入、离开和历史有效期口径，组织外消费不会混入组织账单。

### 兼容性说明

个人账号仍是唯一扣费主体。组织不持有余额、订阅、充值订单或 API Key，也不参与请求预扣、结算和退款；现有个人钱包、订阅、Token 和日志链路保持不变。
