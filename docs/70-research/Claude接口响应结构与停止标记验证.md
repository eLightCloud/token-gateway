# Claude 接口修复后的测试结果

**上游已经修好了一部分问题，但还没有全部修好。剩下的主要问题是：AI 已经按指定标记停止回答，却把“为什么停止”告诉错了。**

直接访问上游也会出现这个问题，应先让上游修复。普通聊天受影响较小；客户如果靠这个结束说明来决定下一步做什么，程序就可能判断错误。因此，目前还不能向客户确认“返回结果与官方完全一致”。

停止标记结论来自 **2026 年 10 月 14 日下午**的实际测试；错误签名结论来自当天 **19:37** 的新增直连上游测试。测试针对 `claude-fable-5-1` 及上游的 `ccmax/` 路线。

## 一个例子看懂问题

AI 返回的结果有两部分：**给人看的回答**，以及**给客户程序看的说明**。这次问题出在后面的说明上。

测试时，我们要求 AI 输出：

```text
ALPHA|END|OMEGA
```

同时设置一条规则：**遇到 `|END|` 就停止，标记和后面的内容都不要返回。** 所以客户应该只收到 `ALPHA`。

我们既测试了“一次返回完整回答”，也测试了“边生成边返回回答”。它们通常分别叫**非流式**和**流式**。

| 检查内容 | 正确结果应是什么 | 我方 lightingtheword 实际结果 |
| --- | --- | --- |
| 客户看到的回答 | 只返回 `ALPHA` | 两种方式都只返回 `ALPHA`，这一项正确 |
| 告诉客户程序为什么停止 | 因为遇到了指定的停止标记 | 两种方式都说成“回答自然结束”，这一项错误 |
| 告诉客户程序遇到了哪个标记 | `\|END\|` | 一次返回的结果是空值；边生成边返回的结果缺少这一项 |

也就是说，**回答停在了正确的位置，但结束说明填错了，还漏掉了触发停止的标记。** 官方要求把“自然结束”和“遇到指定标记而结束”分别报告。[官方说明](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

“已经停止发送内容”也不等于“结束说明正确”。目前两种方式都能结束返回，所以单看聊天画面可能发现不了这个问题。

## 是谁的问题

客户平时的访问过程是：

```text
客户 → 我方 lightingtheword 转发服务 → 上游 AI 服务
```

为了判断问题在哪一方，我们又绕过我方服务，直接访问上游。

| 怎么测试 | 测试结果 | 能说明什么 |
| --- | --- | --- |
| 通过我方 lightingtheword 访问 | 回答正确停止，结束说明错误 | 客户目前仍能遇到这个问题 |
| 直接访问上游的 ccmax 模型 | 一样是回答正确停止，结束说明错误 | 上游返回的结果本身已经有问题 |

**应先由上游修复，我方负责核对实际使用的上游路线，并在上游修好后再次测试客户访问地址。** 现有结果不能确定上游内部哪段代码写错了，也不能据此认定 Anthropic 官方模型有问题。

另外，直接访问上游不带 `ccmax/` 前缀的模型时，“一次返回完整回答”甚至没有按标记停止，完整返回了 `ALPHA|END|OMEGA`。因此，换成这个模型名称不能作为解决办法。

## 对客户有多大影响

| 客户怎么用 | 可能有什么影响 | 怎么处理 |
| --- | --- | --- |
| 普通聊天，只看回答内容 | 本次网关测试中，回答已在正确位置停止；不使用停止标记的对照也正常 | 这个问题对这种用途影响较小 |
| 程序根据结束说明决定下一步 | 程序可能把“到达指定边界”误当成“全部回答完成”，从而跳过后续步骤 | 如果客户主要功能依赖这种判断，需要优先修复 |
| 客户要求与 Claude 官方返回格式完全一致 | 当前结束说明错误，且有信息为空或缺失 | 这项验收目前不能通过 |

例如，客户程序规定：“遇到标记后，进入下一步处理；自然结束时，直接结束任务。”现在接口把两种情况都报告成“自然结束”，程序就可能提前结束任务。这个例子用于说明可能的影响，并不代表已经观察到某个客户发生了故障。

**所以，它对普通聊天影响较小，对依赖结束说明的自动流程可能很严重。** 应让客户开发人员确认：程序是否设置了停止标记、是否根据结束原因决定下一步。

## 错误签名也能正常回答 已在上游复现

`signature` 是 AI 思考信息附带的校验信息。客户把上一轮结果交回去继续对话时，官方要求保留它，用于核对这段思考信息。

这次完全绕过 lightingtheword，直接访问上游 `https://api-zl.numspirit.com/v1/messages`，使用 `ccmax/claude-fable-5-1`。先取得上游新返回的真实签名，然后保持其他内容不变，分别测试：

| 交回给上游的签名 | 一次返回完整回答 | 边生成边返回回答 |
| --- | --- | --- |
| 上游原样返回的签名 | 正常回答 | 正常回答 |
| 只改动其中一个字符 | 仍正常回答，没有签名错误 | 仍正常回答，没有签名错误 |
| 换成随意填写的字符串 | 仍正常回答，没有签名错误 | 仍正常回答，没有签名错误 |

**错误签名的 4 次请求全部返回了预期答案，问题已在上游接口侧复现。** 按官方说明，被修改或损坏的思考签名应报请求错误；当前已测路线没有表现出这一检查。[官方签名错误说明](https://platform.claude.com/docs/en/build-with-claude/thinking-troubleshooting)

上游可能忽略了签名，或在转发前丢掉了相关思考信息；具体原因需要上游检查内部处理。正常回答不代表错误签名有效。上游不带 `ccmax/` 前缀的模型在起始请求中返回服务错误，本轮没有完成那条路线的签名对照。

测试请求都成功返回，也能被官方开发工具读取。但这只说明“能收到、能读懂格式”，不能证明里面的结束说明符合实际情况。

## 接下来怎么处理

1. **让上游修正结束说明。** 遇到指定标记停止时，应明确报告这个原因，并返回实际触发停止的标记。两种返回方式都要修。
2. **我方核对线上转发配置。** 确认 lightingtheword 实际使用哪条上游路线，避免测试和客户访问走到不同路线。
3. **上游发布修复后，重新从 lightingtheword 测试。** 回答应为 `ALPHA`，结束说明应为“因指定标记停止”，标记应为 `|END|`。
4. **同时检查正常结束。** 删除停止规则后，应返回完整的 `ALPHA|END|OMEGA`，并说明是自然结束，避免修复后把所有回答都误判成标记触发。

可将下面这段话发给上游：

> 2026 年 10 月 14 日的复测发现，指定 `|END|` 为停止标记后，lightingtheword 和直连上游 ccmax 模型都能把正文停在 `ALPHA`，但结束原因仍返回 `end_turn`，命中标记返回空值或缺失。请在非流式和流式中都修正为 `stop_reason: "stop_sequence"`、`stop_sequence: "|END|"`，并保留正常结束时的正确行为。另请检查无前缀模型的非流式调用没有按标记停止的问题。

### 复现请求

```json
{
  "model": "claude-fable-5-1",
  "max_tokens": 128,
  "stream": false,
  "messages": [{
    "role": "user",
    "content": "Output exactly this literal string and nothing else: ALPHA|END|OMEGA"
  }],
  "stop_sequences": ["|END|"]
}
```

流式测试只把 `stream` 改为 `true`；上游主要对照只把模型改为 `ccmax/claude-fable-5-1`；无标记对照只删除 `stop_sequences`。

### 正确值与实际值

以下均为关键字段摘录，省略了其他消息字段和用量。

非流式应该返回：

```json
{"content":[{"type":"text","text":"ALPHA"}],"stop_reason":"stop_sequence","stop_sequence":"|END|"}
```

网关与上游 ccmax 非流式实际返回：

```json
{"content":[{"type":"text","text":"ALPHA"}],"stop_reason":"end_turn","stop_sequence":null}
```

流式的结束增量应该包含：

```text
event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"stop_sequence","stop_sequence":"|END|"}}
```

网关与上游 ccmax 流式的结束增量实际包含：

```text
event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"}}
```

实际流式能收到 `message_stop`，但该事件仅表示消息关闭。官方示例的 `message_start.message` 包含 `stop_reason: null`、`stop_sequence: null`；当前已测网关及上游开始事件省略这两项。[官方流式格式](https://platform.claude.com/docs/en/build-with-claude/streaming)

### 定位线索与后续验证

本地原生 Claude 非流式处理使用 `responseData = data` 返回上游数据；原生流式处理用量后发送事件。参见 [Claude 响应处理代码](../../relay/channel/claude/relay-claude.go) 中 `HandleClaudeResponseData` 和 `HandleStreamResponseData`。这提供辅助证据，不能替代线上路由确认。

上游转换时可能丢失了“自然结束”和“命中标记”的区别，需要结合内部日志确认。我方不能仅因请求中带有停止标记，就强行把所有 `end_turn` 改成 `stop_sequence`，因为回答可能在命中标记前自然结束。

修复后，还应增加多标记、未命中标记的测试，并回归 `max_tokens` 和 `tool_use`，核对流式开始的空值字段。错误签名的新增对照结果见下节；已有思考信息不等于签名校验已经生效。
