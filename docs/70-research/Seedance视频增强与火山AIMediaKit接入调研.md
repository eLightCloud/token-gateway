# Seedance 视频增强与火山 AI MediaKit 接入调研

已整理为 [方案与界面简图](../80-dev/2026-10-15-Seedance视频增强方案.md) 和 [实施计划](../50-planning/2026-10-15-Seedance视频增强实施计划.md)。本文保留官方资料与调研过程；后续实施按方案的已确认范围与明确标注的设计建议推进，不把早期备选项视为新增范围。

调研日期：2026-10-15（北京时间）。范围：官方公开文档与当前仓库静态核对；未使用真实凭据提交付费任务，未验证实际画质、耗时、音轨及账单。本文件为讨论材料；用户已明确采用独立增强模型入口的方向，完整实施方案仍待确认。

## 用户给定的目标

1. 在 Seedance 视频相关渠道增加“是否开启视频增强”选项。
2. 增强同一来源视频，例如 sd mini 720 → sd mini 1080、sd fast 720 → sd fast 1080、sd2 720 → sd2 2K。
3. 使用火山 AI MediaKit，重点调研 `enhance-video-generative`。
4. 先保存调研资料，再讨论产品与技术方案，包括是否增加 OSS 对象存储（用户起初写作 SSO，后续已澄清）。

用户后续明确：渠道开启增强能力后，为支持的基础模型增加一个增强模型，例如保留 `sd-2-mini`，另外提供 `sd-2-mini-enhance`，用户通过模型名直接选择增强服务。因此，渠道开关表示是否提供增强模型，调用增强模型表示请求执行生成与增强。上述名称为用户示例，不是火山官方模型 ID。

用户已确认：保留一个 `基础模型名-enhance` 入口，通过 `resolution` 选择最终输出 `1080p` / `2k`，不为这两个分辨率分别增加模型名。

用户已确认：第一期统一使用 MediaKit 大模型版 `enhance-video-generative`，渠道暂不开放四种增强版本的选择，以保持相同增强模型的服务含义稳定。其他版本的资料和价格保留用于后续评估，不构成第一期开放范围。

用户已确认第一期范围：Seedance 2.0 系列（标准版、fast、mini）及 2.5；只为 runyyitd 与火山官方接入增强能力，暂不为 CodeYY、Zapgogo 或其他供应商新增增强入口。现有其他渠道的普通模型能力保持不变。测试先使用火山官方，用户已表示测试 Key 之前提供过。

用户已确认：原片生成成功后，如果增强失败，由平台内部自动重试增强；原片保留在内部，不向客户暴露原片或内部重试细节。增强总共最多尝试 3 次，即首次尝试加最多 2 次重试；任一次成功即停止重试。重试期间不向客户报告终态失败，3 次均失败后才将公开任务标为最终失败并报告原因。

用户已确认：增强任务最终失败时，全额退还客户费用，不收取原片生成费或内部重试费用；已发生的生成与增强上游成本由平台承担。该客户退款决定不表示上游服务也会退款。

用户已澄清：此前的 SSO 指 OSS 对象存储；用户已有对象存储，明确使用阿里云 OSS。用户要求先评估接入必要性；如有必要，可在后台管理相关配置中增加配置页面，由用户之后填写参数，不要求现在提供密钥或地域。

用户最新限定：OSS 保存期限、清理和其他存储策略暂不讨论，不作为本次方案推进的阻塞项；此前提出的 7 天/30 天只是建议，未获确认，不作为实施默认值。

模型与供应商范围已确认，剩余业务项主要是成功任务的定价方式。重试间隔、参数缺省值、协议适配等给出工程建议，不逐项要求用户确认。OSS 地域、Bucket 与凭据由用户在后台配置时填写；存储策略另行讨论。本文将用户已明确的方向与下面的建议分别记录。

## 可行性与能力边界

**结论：官方接口能力支持上述三个分辨率转换方向，实际效果与生产接入仍待验证。**

MediaKit 接收已生成的视频，生成式增强会修复并合成细节。官方将其用于 AIGC 视频后处理，并提供低清生成后增强的工作流。因此可以保持同一来源视频、同一生成模型身份，但不能承诺人物、文字、纹理等逐帧完全不变，也不能把增强结果宣传为模型原生高分辨率直出。[画质增强开发指南](https://docs.volcengine.com/docs/Intelligentprocessing/Imagequalityenhancement-largemodels?lang=zh)

当前方舟创建任务文档列出的原生分辨率：Seedance 2.0 mini / fast 为 480p、720p；Seedance 2.0 为 480p、720p、1080p、4k。后处理增强的输出档位与生成模型的输入参数是两套能力。[方舟创建视频生成任务](https://docs.volcengine.com/docs/ark/create-video-generation-task-api?lang=zh)

据此，用户示例可以落为以下组合能力；具体增强配置仍待确认，不能据此扩充火山原生模型规格：

| 用户示例 | 原始生成任务 | 后处理输入 → 输出 | 对外需要保留的身份 |
| --- | --- | --- | --- |
| sd mini 720 → 1080 | 同一 mini 任务 | 该任务的 720p 原片 → 1080p | mini + 原任务来源 + 增强标识 |
| sd fast 720 → 1080 | 同一 fast 任务 | 该任务的 720p 原片 → 1080p | fast + 原任务来源 + 增强标识 |
| sd2 720 → 2K | 同一 sd2 任务 | 该任务的 720p 原片 → 2k | sd2 + 原任务来源 + 增强标识 |

这里没有 mini → fast、fast → sd2，也没有使用相同 prompt 重新生成视频。“相同模型”与“相同原片”都应可追溯。上表只覆盖用户给定示例，不代表已授权支持任意模型、任意视频或全部输出档位。

## 独立增强模型入口分析

### 对用户提议的判断

建议保留用户提出的 `基础模型名-enhance` 入口。对只允许填写模型名的 SDK 和第三方客户端，这种方式容易使用；普通模型与增强模型可分别展示能力、授权、限流和价格。渠道开关仅增加增强服务入口，普通模型继续走原生成流程。

该模型名代表网关提供的组合服务：一次调用内部先使用同一基础模型生成原片，再增强该原片。上游生成请求仍使用真实基础模型 ID，MediaKit 请求则使用其工具端点。不能把 `-enhance` 名称直接发送给方舟，也不能仅靠普通 `model_mapping` 去除后缀，就认为已经具备增强能力。

需要特别区分：分别调用一次 `sd-2-mini` 和一次 `sd-2-mini-enhance`，通常会产生两次独立生成，不能保证是同一条视频。本方案能保证的是一次增强请求内部沿用自己的原片。如果还要求“普通模型已经生成的某条视频，随后追加增强”，那是另一项历史任务增强能力，当前未确认纳入。

### 最小产品合同分析（区分已确认与建议）

1. **一个基础模型增加一个增强入口，第一期版本已确认。** 统一使用大模型版，不同时开放四种算法对应的四个公开模型，也不提供渠道侧版本选择。实际效果仍需验证；模型说明应明确版本、源分辨率、目标范围与帧率策略。
2. **模型入口与目标选择已确认。** 采用 `model=sd-2-mini-enhance` 这一形式，让该模型的 `resolution` 表示最终交付分辨率，支持 `1080p` / `2k`。原片固定为经过验证的 720p、缺省目标固定且公开、冲突参数在提交前拒绝，仍为待确认建议。
3. **明确两种分辨率。** 原片生成分辨率与增强输出分辨率分别保存；不能将最终的 2k 直接传给不支持它的 mini 生成接口。生成价格依据实际生成规格，增强价格依据实际增强规格。普通模型请求的 resolution 保持既有含义。
4. **失败处理、次数与退款已确认。** 原片生成成功后仅内部保留，客户不获取原片或内部重试细节。增强总共最多尝试 3 次（首次加最多 2 次重试），不重新生成原片；在重试耗尽前，公开任务维持处理中，成功后交付增强结果，3 次均失败后才标为最终失败并报告原因，同时全额退还客户费用，上游成本由平台承担。具体错误响应仍待确认。
5. **身份、路由与费用保持完整。** 对外查询与日志保留客户请求的增强模型名；内部保留基础模型与两个上游任务 ID。增强入口必须参与插件候选识别、渠道匹配、模型列表与权限校验，不能在渠道选中后才临时识别后缀。
6. **配置固定到任务。** 原模型、增强版本、目标分辨率、码率/帧率策略、凭据配置引用及价格快照在提交时固定。禁止由相同名字在不同渠道随意代表不同增强合同；关闭开关后禁止新建增强任务，已提交任务仍按固定配置完成。原片已产生后，不允许跨渠道重试整条生成链。

上述建议不要求在第一期增加新的客户端自定义增强参数，也不建议把版本、分辨率、帧率、风格的全部组合展开成公开模型名。若未来客户需要主动选择成本/画质档位，再发布含义明确的独立服务入口，并保留旧入口的既定含义。

### 内部重试的边界

已确认的重试对象是同一原片的增强阶段，客户端不需要重新提交整条生成请求。尝试上限为 3，包含首次；成功即停止，不执行后续尝试。保留原片的用途包括后台重试与排查，不等于对客户提供原片下载。客户在最终失败前看到的仍是原公开任务的处理中状态；最终收到失败与原因，不收到中间失败事件。

实施建议（未确认）：区分提交超时等“是否已创建上游任务未知”的情况与“上游增强任务明确失败”。前者应先查明原任务或用同一幂等键重试提交，避免重复创建；后者如需新建一次增强，应关联新的尝试编号与幂等键。不能对已经明确失败的任务反复查询并将其算作新的增强尝试。该业务重试次数也不等于 MediaKit 回调通知的重试次数。

最终错误建议保留可操作的原因类别和公开任务 ID；详细上游错误、各次尝试和上游请求 ID 留在内部排查记录，不向客户输出凭据、内部地址或原片链接。是否对参数错误、权限错误等不可恢复原因提前终止，以及每次尝试与整条任务的超时上限，仍需明确。

### 当前实现的适配约束

现有 [插件合同](../plugin-api/v1.md) 已区分 `ctx.model`（客户模型身份）和 `ctx.upstreamModel`（映射后的机器身份）；`relay/relay_task.go:225` 在请求校验前映射模型，`:261` 选择任务计费表达式。但现有 `plugins/local/doubao.js:788` 校验的是生成模型的 resolution，不能直接拿来校验组合服务的最终分辨率。实施需要独立的组合服务边界，保留两套实际规格，再做窄范围接线，不能简单把 mini 的原生分辨率数组加上 2k。

用户已确认客户按最终成片秒数统一收费，秒价包含生成与增强；此前“生成 tokens + 增强秒数”的混合售价建议已被替代。增强模型单独配置完整按秒价格合同，经既有正式入口预扣、结算和退款；原片 tokens、各次增强用量与费用只作内部成本核算。实施前还需验证独立按秒 schema 的兼容方式，别名映射不会自动切换计量合同。具体售价后配；用户要求时长计量遵循火山官方，已核实为毫秒级，详见方案“如何计价”。

## 火山可调用的视频增强版本

这里的“模型”需分为 Seedance 生成模型与 MediaKit 增强工具版本。当前 MediaKit 对视频增强公开的是以下四种服务版本、三个提交端点，未在这些接口中要求传入独立增强模型的 `model` ID。

| 增强版本 | 提交端点（均为 POST，省略 `/api/v1/tools`） | 选择方式 | 官方定位 | 输入 / 输出范围 |
| --- | --- | --- | --- | --- |
| 极速版 | `/enhance-video-fast` | 独立端点 | 轻量超分，速度优先 | 输入最高 2K；输出 240p–4k 的枚举档位 |
| 标准版 | `/enhance-video` | `tool_version=standard`（默认） | 兼顾速度与画质；支持 `scene=aigc` | 输入最高 2K；输出 240p–8k 的枚举档位 |
| 专业版 | `/enhance-video` | `tool_version=professional` | 更强增强，影视制作；可配置色深和编码 | 输入最高 2K；输出 240p–8k 的枚举档位 |
| 大模型版 | `/enhance-video-generative` | 独立端点 | Diffusion 生成式细节修复，AIGC 后处理 | 输入最高 1080p SDR；输出 720p / 1080p / 2k / 4k |

证据：[极速版 API](https://docs.volcengine.com/docs/Intelligentprocessing/submit-image-quality-enhancement-lite-task-api?lang=zh)、[标准版与专业版 API](https://docs.volcengine.com/docs/Intelligentprocessing/SubmitimagequalityenhancementtaskAPI?lang=zh)、[大模型版 API](https://docs.volcengine.com/docs/Intelligentprocessing/submit-image-quality-enhancement-large-model-version-task-api?lang=zh)。表中最高分辨率仅为摘要，实际仍受长短边限制；240p–8k 不是允许任意字符串，也不表示所有原片都可达到该输出效果。

标准版和专业版都支持 `enhance_style=hd|natural`；`scene=aigc` 在当前 API 中仅对标准版生效。`bitrate_level=high` 是码率档位，不是在这四个版本之间选择。专业版的色深、编码组合另有约束，不能把 `professional` 与大模型独立端点混为一谈。[标准/专业参数说明](https://docs.volcengine.com/docs/Intelligentprocessing/SubmitimagequalityenhancementtaskAPI?lang=zh)

第一期选型已确认：使用大模型版。其他版本仅保留调研信息，后续如需比较成本与画质，可用相同原片对照标准版 AIGC 模板，再按目标评估极速或专业版；比较不应自动改变现有公开增强模型的合同。任何版本均不据此保证逐帧内容不变。

补充辨别：火山 VOD 的场景化增强另有 Pro Medium（≤1080p）、Premium（2K）、Ultimate（≥4K）的说明，以及各档 RTF 估时；当前核对的 MediaKit 请求参数没有对应的独立 `model` 选择字段，不能把这些名称直接当作本次 API 的可传值，也不能把 VOD 的闲时价格套用于 MediaKit。[VOD 场景化增强](https://docs.volcengine.com/docs/video_on_demand/Scene-basedimagequalityenhancement?lang=zh)

## 官方接口事实

### 提交与参数

服务地址为 `https://mediakit.cn-beijing.volces.com`，提交端点为 `POST /api/v1/tools/enhance-video-generative`，使用 `Authorization: Bearer <API Key>`，异步返回任务 ID。

| 参数 | 当前文档约定 |
| --- | --- |
| `resolution` | `720p`（默认）、`1080p`、`2k`、`4k` |
| `bitrate_level` | `low` / `medium`（默认）/ `high` |
| `bitrate` | 10–150000 kbps；显式设置时优先于档位 |
| `fps` | 15–120；不传时沿用原片帧率 |
| `client_token` | 幂等凭证，最多 64 个可打印 ASCII 字符 |

这些参数来自当前[增强 API 参数表](https://docs.volcengine.com/docs/Intelligentprocessing/submit-image-quality-enhancement-large-model-version-task-api?lang=zh)（页面更新于 2026-09-17）。`high` 控制码率档位，不能等同于更高分辨率或无损。

### 输入来源与限制

输入可使用公网 HTTP(S)、`mediakit://` 上传文件、`vod://` 或 `tos://` 资源；后两者涉及跨服务授权。带签名的公网 URL 也必须在 MediaKit 拉取时有效；需要网关 API Token 才能下载的地址，不能直接视为公网输入。[多源媒体输入](https://docs.volcengine.com/docs/Intelligentprocessing/multisource-media-input-and-local-upload?lang=zh)

大模型版要求 SDR，输入短边 360–1080、长边 360–1920；快速入门建议文件不超过 10 GB。该建议不等于所有上传入口的硬限制：本地上传指南另列单文件最大 5 GB。[视频后处理快速入门](https://docs.volcengine.com/docs/Intelligentprocessing/QuickStartVideoGenerationPost-Processing?lang=zh)、[本地上传限制](https://docs.volcengine.com/docs/Intelligentprocessing/multisource-media-input-and-local-upload?lang=zh)

工程推论：判定能否增强应读取实际文件规格，不能只信模型名称或请求中的 `720p` 标签。已经是 2K/4K 的产物不符合该增强工具当前的输入尺寸限制。

### 查询、幂等与吞吐

提交成功后轮询 `GET /api/v1/tasks/{task_id}`。当前查询 API 的状态枚举为 `running`、`completed`、`failed`；`success` 只表示查询操作成功，最终产物位于 `result.video_url`，同时返回时长、分辨率、帧率等。查询范围为创建后 30 天；默认产物链接从生成时刻起固定 24 小时有效，重新查询不能续期。[查询任务 API](https://docs.volcengine.com/docs/Intelligentprocessing/QuerytaskinformationAPI?lang=zh)

默认异步任务幂等窗口为成功提交后的 24 小时；同一次重试应沿用 `client_token`，明确重做时使用新的 token。官方当前列出主账号维度异步接口总 QPS 默认 40、同时处理任务默认 20，项目和队列共享并发上限。[基础概念及准备工作](https://docs.volcengine.com/docs/Intelligentprocessing/Basicconceptsandpreparationwork?lang=zh)（更新于 2026-10-09）

工程推论：业务任务 ID 与增强幂等键需要持久关联；网关重启、超时和重复轮询不能造成重复增强。上述吞吐为默认配额，账号实际额度与排队耗时仍需核实。

### 回调

支持任务完成回调；当前官方文档明确暂不支持回调签名鉴权。接收方需返回 HTTP 200，失败最多重试 3 次，间隔为 5、10、30 秒。[事件回调](https://docs.volcengine.com/docs/Intelligentprocessing/Eventcallback?lang=zh)

候选做法：第一期沿用轮询；若采用回调，将通知作为触发凭据查询的信号，通过服务端查询确认状态后再交付或结算。此项为工程建议，尚未选型。

### 时长计量补充核验：毫秒级，不按整秒或整分钟进位

用户要求查询火山官方，并按官方规则执行。2026-10-15 查询到[视频工具计费](https://docs.volcengine.com/docs/Intelligentprocessing/video-tool-billing?lang=zh)的通用计费规则，以及[计费常见问题](https://docs.volcengine.com/docs/Intelligentprocessing/billing-faqs?lang=zh)关于不足一分钟的说明，均明确以毫秒记录实际时长，汇总后换算成分钟计费。官方用 90 秒对应 1.5 分钟说明该换算。

因此此前“时长粒度未确认”已消除：本服务按毫秒记录最终成片时长，客户按 `duration_ms / 1000` 的小数秒付费。10.2 秒不变成 11 秒或一分钟，10.234 秒也保留为 10.234 秒。消费日志应展示对应小数秒，内部失败尝试不叠加客户计费时长。

按大模型版 ≤30fps 刊例公式推算，10.2 秒 1080p 增强为 `10.2 / 60 × 5 = 0.85` 元，2K 为 `10.2 / 60 × 10 = 1.70` 元。这仅为单次增强理论费用，不含生成、OSS、流量、实际折扣及客户综合服务加价。不能把分钟报价理解为最低收费一分钟，也不能把增强成本当成整项服务售价。

上述官方页面未明确亚毫秒到毫秒的转换方向、账单金额舍入细则或失败/取消任务收费。保留原始时长回包，实施时通过官方支持或实付账单补齐这些证据，不擅自套用其他产品的向上取整或四舍五入规则。

## 结果保存与 OSS 对象存储

**用户已明确使用现有的阿里云 OSS，配置参数之后在后台填写。评估建议：第一期接入 OSS，作为增强服务的持久保存与交付基础。** 该建议依据已确认的原片内部保留、后台增强重试和最终失败退款要求；后台配置页及存储代码尚未实现。

| 名称 | 本次讨论中的含义 | 与增强接入的关系 |
| --- | --- | --- |
| 阿里云 OSS | 用户明确选择的视频对象存储 | 保存内部原片与最终增强版，支撑重试和下载交付 |
| S3 | 常见对象存储 API / 兼容接口 | 仓库存在预留接口，但当前没有可用存储实现 |
| TOS / VOD | 火山对象存储 / 视频点播 | MediaKit 官方支持直接写入的产物存储目标 |

MediaKit 支持用 `media_output_destination` 写入 TOS/VOD，需先授权。当前 TOS 写回仅支持 `cn-beijing`，可以指定目录前缀，最终文件名由服务生成。返回的 `tos://` / `vod://` 是内部资源引用，不能直接播放；需另行取得 HTTPS 访问地址。写回功能本身免费，后续存储与使用由对应服务计费。[产物写入 TOS/VOD](https://docs.volcengine.com/docs/Intelligentprocessing/process-products-stored-to-vod-or-tos?lang=zh)（更新于 2026-10-10）

对比后建议采用网关转存到阿里云 OSS；其他方案保留为研究对照：

| 方案 | 需要补齐的能力 | 适用条件 |
| --- | --- | --- |
| 临时 HTTPS 链接交付 | 展示到期时间并约定下载责任 | 用户明确接受 24 小时下载期限 |
| MediaKit 直接写 TOS/VOD | 云服务授权、资源引用解析、下载地址生成、生命周期与费用管理 | 希望由火山完成落盘，接受其地域与服务依赖 |
| 网关转存到自选对象存储 | 下载上传、重试恢复、访问控制、限额与清理 | 需要统一跨供应商保存，愿意承担额外工程与流量成本 |

### 为什么本需求值得接入 OSS

调用 MediaKit API 本身并不强制要求 OSS。如果只做演示、接受临时链接且不保证重试恢复，直接使用源站地址即可。但本需求已经要求原片内部保留、最多 3 次增强尝试、客户只看到最终结果；依赖上游签名链接或单台机器临时文件，会把恢复能力绑在源站链接有效期及机器存活上。

| 需求 | 仅保存上游 URL 的缺口 | 接入 OSS 后的作用 |
| --- | --- | --- |
| 同一原片重试 | URL 到期或源站失效后，不能可靠重试原片 | 持久保存字节，按需为处理端签发新地址 |
| 重启与多实例恢复 | 本地临时文件可能丢失或只存在一台机器 | 各实例通过持久对象引用恢复同一任务 |
| 原片内部保留 | 无法由平台决定实际保留期限 | 私有原片仅供后台处理和排查 |
| 客户成片交付 | 默认 MediaKit 产物下载链接固定 24 小时有效 | 在约定保存期限内，可重新签发成片下载地址 |

因此，建议做这条增强链路所需的最小 OSS 接入，不在第一期扩展为通用文件管理器、多存储厂商管理或全站媒体迁移。原片保留、成片保留和单条签名 URL 有效期是三个不同配置，不能混为一个“有效期”。

### 阿里云 OSS 的处理与交付方案（建议）

MediaKit 当前增强 API 的 `media_output_destination` 只列 TOS/VOD，没有直接写入阿里云 OSS 的参数。接入 OSS 时，由网关处理跨云转存，不能把 `oss://` 填入该字段并假定可用。[增强 API 的输出目标](https://docs.volcengine.com/docs/Intelligentprocessing/submit-image-quality-enhancement-large-model-version-task-api?lang=zh)

建议流程：生成成功 → 原片存入私有 OSS → 为 MediaKit 签发原片 HTTPS 地址 → 增强（最多 3 次尝试）→ 将增强成片转存 OSS → 公开任务成功。原片链接不进入客户响应或公开 artifacts；客户只通过任务所属权校验后的既有下载入口取得成片。上游若只提供带鉴权的下载接口，由服务端取回原片并上传，不将渠道凭据交给 MediaKit。

阿里云 Go SDK V2 支持为私有对象生成临时 GET 地址，签发身份需具备对应对象的 `oss:GetObject` 权限；V4 签名上限 7 天。持久记录应保存对象引用，而非仅保存一次性签名 URL。给 MediaKit 的 URL 必须公网可访问，不能使用仅阿里云内网可达的 Endpoint；不要求额外自定义请求头。[OSS Go SDK 临时下载地址](https://www.alibabacloud.com/help/en/oss/developer-reference/v2-presign-download)

存储与处理失败须分开：上传原片失败只重试原片转存；增强已成功但成片上传失败只重试成片转存，不重新生成或重复增强。这两类网络/存储重试不占用 3 次真正的增强尝试，但必须有各自的时间上限。若最终仍无法交付，按已确定的最终失败全额退款原则处理；详细超时与错误分类待实施方案明确。

原片与成片可使用同一私有 Bucket 中的独立业务前缀，保存到期后清理。阿里云生命周期支持按前缀/标签配置过期删除；第一期不自动改写用户现有 Bucket 的全局生命周期，以免影响其他文件。应用保存自身的到期时间，运行中的原片不因清理策略提前删除，Bucket 生命周期可作为延迟清理兜底。[OSS 生命周期说明](https://help.aliyun.com/zh/oss/user-guide/overview-54/)

费用需覆盖存储、请求和公网流出：MediaKit 每次从 OSS 拉取原片、客户下载成片都可能形成公网流出；不能因“上传不收流入流量费”就认定整个跨云链路免费。具体金额按之后配置的地域、对象大小与实际下载量计算。[OSS 计费概述](https://help.aliyun.com/zh/oss/billing/)、[OSS 流量费用](https://help.aliyun.com/zh/oss/traffic-fees)

### 后台配置页范围（建议）

用户已授权必要时增加后台配置入口；建议放入现有“系统设置 → 运维设置”，新增“对象存储”子页。存储连接配置为全局基础设施，渠道仅控制是否开放增强模型，避免每条渠道重复保存 OSS 凭据。第一期提供阿里云 OSS 实现即可；现有 S3 预留字段不代表已有 OSS 后端。

| 配置内容 | 第一阶段建议 |
| --- | --- |
| 启用状态 | 可先保存未启用配置，用户之后填写并测试 |
| 地域、Endpoint、Bucket | 配置时校验匹配；区分服务端访问地址与供 MediaKit 使用的公网签名地址 |
| 凭据 | 独立 RAM 身份或受支持的角色凭据；按业务前缀授予读写与清理所需最小权限；密钥不回显、不落日志 |
| 对象前缀 | 隔离本功能的原片、增强版和测试对象，不触及 Bucket 其他文件 |
| 保存期限、清理策略（暂缓） | 用户明确暂不关心；本轮不决定默认天数，也不自动修改现有 Bucket 的生命周期规则 |
| 下载签名有效期 | 客户成片链接建议默认 15 分钟，鉴权后可重新签发；MediaKit 取原片的签名时长单独覆盖排队、处理及容错窗口 |
| 配置测试 | 测试专用前缀中的写入、读取和清理，展示具体失败阶段，不暴露密钥 |

建议发布时允许 OSS 未配置，普通模型照常可用；OSS 和 MediaKit 凭据未就绪时，不开放可调用的增强入口，并在服务端提交前检查，不能等原片生成、产生费用后才发现存储不可用。就绪后即可由管理员开启渠道增强。配置变更需保留进行中任务使用的存储引用，不能因换 Bucket 或密钥而丢失已有任务的原片与成片。

现有 `web/src/features/system-settings/operations/section-registry.tsx` 提供子页注册机制；`components/settings-section.tsx`、`components/settings-form-layout.tsx`、`components/settings-page-context.tsx` 已覆盖设置页布局和保存交互，可直接组合。新增能力缺口是 OSS 连接、凭据保存与测试、对象写入及交付，已有设置组件无需另造一套。实现主体应放入独立存储模块与独立设置功能目录，旧页面仅做注册接线。

后续实施必须验证真实 OSS 写入/读取/签名/清理、原片不对客户暴露、重启恢复及配置修改后的在途任务；未提供 Bucket 与凭据前，只能完成本地实现和协议级验证，不能声称真实 OSS 接入已验证。本轮完成的是评估与文档更新。

存储策略延期后的范围说明：先完成连接配置、原片与成片写入、签名读取和交付；不将自动过期清理、存储分层或保留天数作为第一阶段的新增功能。上文生命周期资料保留为后续参考，不要求用户现在决定。

本节依据当前仓库实现，不把代码里的供应商能力当成线上渠道清单。本地 `one-api.db` 已以只读方式核对，未发现 models 中声明 Seedance 的渠道，`task_plugins` 也无安装记录；因此无法从该本地库确认线上实际启用了哪些 Seedance 渠道。核对未读取或输出渠道密钥。

用户收窄范围后，下表中的 CodeYY、Zapgogo、标准 Videos 与跨网关能力仅保留为既有实现背景，不意味着第一期需要为它们增加增强入口。第一期供应商以火山官方与用户所称 runyyitd 为准。

### runyyitd 身份与测试准备

当前插件 `plugins/local/doubao.js:1475` 的注释提到 Runy 样本确认过终态 token 用量，但仓库未检索到 `runyyitd` 的独立 profile、域名或接口文档。该注释不能证明 runyyitd 等于 CodeYY、Zapgogo 或标准 Videos，也不能据此确定模型名、下载鉴权、取消能力和用量合同。后续按真实渠道配置或供应商官方接口文档确认；不影响先使用火山官方验证增强工具。

测试凭据现状：本轮可见的用户 cURL 示例中 Bearer 为空；进程的常见 Ark/MediaKit/火山 Key 环境变量未设置，本地 `.env` 也未找到可识别的对应凭据项。只检查了存在状态和变量名，没有回显密钥，尚未提交真实测试任务。需要用户指出此前凭据的可读取位置；不要求用户重新在聊天中粘贴密钥。Ark 生成权限与 MediaKit 增强权限分别验证，不假定同一把 Key 能调用两个服务。

### 可由实现方案直接处理的事项

- **默认生成与输出建议：** 增强服务内部先用同一基础模型生成 720p；未传最终 resolution 时默认 1080p。传 2k 时只改变 MediaKit 输出，不改变 Seedance 生成分辨率。不增加帧率插值，保留时长、比例和音轨；音轨保留必须实测。以上为工程建议，不能回写成用户已确认的具体规格。
- **模型声明与别名：** 当前插件除 2.0 mini / fast / 标准版外，还声明 2.5、1.5 和 1.0 系列。用户已选择第一期只为 2.0 系列与 2.5 提供增强；1.0、1.5 不新增增强别名。别名必须关联明确的基础模型和能力，不能通过任意名称末尾加 `-enhance` 来放宽能力，未知接入点 ID 需先有可识别的映射。普通模型和 Seedream 图片模型不受影响。
- **三个客户入口：** 插件原生任务接口、`/v1/videos`、`/v1/responses` 都存在。推荐复用它们的既有格式，使增强模型可从原有入口调用；查询、列表、content、Responses 结果及公开 artifacts 均只投影增强任务状态和最终成片，不能在生成阶段把原始响应里的 URL 泄漏出去。
- **两阶段终态与退款：** `service/task_polling.go:629` 的终态入口会结算或退款，不能在原片成功时先对外成功结算，再在增强失败时另造退款逻辑。公开增强任务应等最终可交付状态再收尾，内部保留原片实际用量，客户按可信成片时长和最终规格结算。增强模型缺少成片计量时进入 `usage_pending`，仅缺生成 tokens 不阻塞客户结算；普通模型原用量对账不变。
- **实际分辨率与用量：** 生成成本的 resolution 是原片规格，客户综合秒价使用最终成片规格，两者必须分开。CodeYY/Zapgogo 已有的原生 1080p 不表示其 1080p 请求需要再次增强；只有增强模型才走组合流程。成功任务不得按三次增强重复向客户收费。
- **重试和超时：** 明确上游任务失败才新建下一次增强尝试；提交结果未知先恢复原任务。各次尝试共用同一原片，处理超时、转存重试和增强尝试数分别记录，不能机械套用当前轮询连续失败次数。具体间隔与总时限可由实现方案统一确定，保留项目已有外层超时保护。
- **取消、草稿等特殊能力：** 当前原生 Ark 有删除/取消与草稿引用，Videos 扩展 profile 对取消则明确报能力错误。第一期增强模型建议只接受能产生最终视频的请求；不直接复用已完成原片的取消接口来假装取消正在运行的 MediaKit 任务。无法可靠取消的阶段返回明确能力错误，普通模型原行为保持不变。
- **增强凭据配置：** 建议 MediaKit 使用全局独立配置（API Key、可选 queue_id），与全局 OSS 配置分开管理；火山官方与 runyyitd 生成渠道只启用增强能力并绑定已有模型，不重复存储同一套增强/存储凭据。

### 真正需要继续讨论的业务项

1. **范围已确认：** 第一阶段支持 2.0 系列与 2.5，仅火山官方和 runyyitd；不再要求用户确认是否加入旧版或其他供应商。runyyitd 的实际接口合同需通过配置或文档补齐，不能凭名称推测。
2. **成功任务计量已确认：** 用户选择统一按最终成片秒数收费，以便客户理解；综合秒价包含生成与增强，内部生成 tokens 不再另向客户收费，失败尝试也不额外收费。完整按秒价格合同在后台维护，具体单价可后配，缺价时禁止产生付费上游任务。时长计量按用户要求遵循火山官方毫秒规则，不按整秒或整分钟向上取整。

其余参数缺省值、幂等、任务恢复、原片隐藏和退款回归属于实现责任，不继续拆成大量产品确认问题。视觉质量与音轨等必须通过实际样片验证，不能靠用户口头确认代替证据。

## 待讨论的产品语义与风险

增强模型入口及通过 resolution 选择最终 1080p / 2K 已由用户明确；以下为其余待定事项：

- **增强规格：** 第一期开启增强后统一使用大模型版；仍需明确源分辨率，以及未传 resolution 时默认哪一档。
- **操作者与范围：** 用户已确定渠道开启后新增增强模型，第一期限定 2.0 系列、2.5 以及火山官方/runyyitd；继续按相同公开模型名保持一致增强合同。历史任务补做尚未纳入。
- **分辨率语义：** 增强模型的 resolution 表示最终输出已经确认。普通模型保持原义；不能静默把普通模型客户明确要求的原生 1080p 改成 720p 后处理。
- **保真标准：** 允许哪些细节变化？人物身份、字幕、Logo、产品纹理、运镜与镜头时序如何验收？音轨、时长、比例和帧率是否必须保留？
- **重试细节：** 已确认原片内部保留、增强最多尝试 3 次（首次加 2 次重试）、耗尽后向客户报告最终失败和原因。仍需明确重试间隔、可重试错误、各次与整条任务超时；不能重新生成原片。
- **计费与交付：** 最终失败全额退款、成本由平台承担已确认。成功按成片秒数统一收费已确认，消费日志建议展示成片时长、综合秒价和最终净消费。具体售价后配，时长粒度已核实为官方毫秒规则；两个阶段内部成本记录、交付失败判定和迟到结果处理仍需落实，避免重复扣费、重复退款或退款后继续消耗。
- **存储：** 用户明确使用现有阿里云 OSS、后台参数之后配置；评估建议第一期接入并增加运维设置子页。保存期限、清理及存储分层策略暂缓，不作为当前讨论或实施方案的阻塞项；原片不对客户暴露。
- **安全边界：** MediaKit 凭据应独立配置在服务端；增强源应由有权访问的任务解析，避免接受任意地址绕过来源限制。若增加鉴权或回调代码，再按 AGENTS.md 完成对应 OWASP 阅读和安全验证。

1. 以用户已明确的独立增强模型入口、最终分辨率参数及大模型版为前提，确认原片规格、缺省目标和“同样的视频”的验收含义；将阿里云 OSS 的后台配置、原片与成片持久保存纳入方案，地域与凭据留待用户配置时填写。
