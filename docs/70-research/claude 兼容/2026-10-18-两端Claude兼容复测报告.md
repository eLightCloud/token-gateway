### 两端当前实际返回了哪些字段

普通 JSON 和带签名工具 JSON 的选定样本，外层字段集合均为：

```text
id, type, role, model, content,
stop_reason, stop_sequence, stop_details,
usage, context_management
```

这些样本的 `usage` 字段集合均为：

```text
input_tokens, output_tokens,
cache_creation_input_tokens, cache_read_input_tokens, cache_creation,
output_tokens_details, iterations, service_tier, inference_geo
```

流式不是一次返回这个对象，而是分次交付：

```text
message_start：消息身份、开始时为空的结束信息、初始 usage
content_block_start / delta / stop：正文、思考签名、工具 JSON 分片
message_delta：delta 内是最终结束信息；同级还有 usage、context_management
message_stop：本次消息结束
```

**本次复核发现，原测试脚本的聚合摘要漏收了 `message_delta` 同级的 `context_management`。两端原始流中实际都有 `{"applied_edits":[]}`。这是本地测试摘要的遗漏，不是已证实的上游或 Lighting 丢字段。** 本次另外生成了按原始事件核对的字段清单，保留原记录，未用修正摘要覆盖原始证据。

`container`、`diagnostics`、`server_tool_use` 等需要按是否使用对应能力及冻结合同判断。本轮没有启用相关能力，不能仅因某个官方示例带这些字段，而我们的普通回复没带，就直接判失败；也不能据 SDK 接受省略就宣布原始报文完全相同。扩展字段存在也不等于伪造，例如 `iterations` 在官方 beta/多次尝试合同中有定义；仍须由实际执行记录证明内容真实。[官方 Usage 类型](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/usage.py)、[官方 beta Messages 合同](https://platform.claude.com/docs/en/api/beta/messages/create)

## 重点二：签名要分四层验收

这里的签名指 **Claude 思考块里的 `signature`**，用于把原有思考带回后续对话，不是调用接口的 API Key。

| 验收层次 | 本轮证据 | 当前结论 |
| --- | --- | --- |
| 1. 是否正确返回签名 | JSON 有字符串；SSE 的 `signature_delta` 在思考块结束前出现，重组值与原始事件一致 | **已测通过** |
| 2. 签名损坏是否拒绝 | 各端分别测试 JSON/SSE 的改一字、随机、截断、清空、删除，共各 10 个负例，全部 400；原样回传成功 | **基本拒绝行为通过**，但错误格式不通过 |
| 3. 签名是否按规则绑定旧对话 | 改动签名前的用户消息，并显式要求 `error`，两端仍为 200；`drop_block` 也没有变换记录 | **本轮未按官方显式绑定合同执行** |
| 4. Lighting 转发时是否原样保存 | 当前是分别直连两端的独立请求，没有同一次请求的两侧抓包 | **尚未证明逐跳无损**；也未证明 Lighting 修改了签名 |

**签名长度不同本身不是故障。** 上游本轮 JSON/SSE 为 1188/1200 字符，Lighting 为 1204/1208 字符，来自四次独立生成，不要求相等。应比较“同一个思考块经过转发前后”的签名，而不是比较两次生成的签名。签名外观、长度和拒绝文案都不能单独证明实际模型来源。

“只改空的 `thinking` 文字，保留原签名后成功”也不能判签名失效：本轮为 omitted 模式，官方明确回传时从签名恢复思考，填入的显示文字被忽略。[官方思考与签名规则](https://platform.claude.com/docs/en/build-with-claude/thinking)

要补齐第 4 层，我方应在一笔可关联请求上比对：① 上游响应与 Lighting 对客户响应中的同一签名；② 客户下一轮回传与 Lighting 发给上游的同一签名。按思考块顺序比较解码后的字符串，可在受控日志中记录长度和 SHA-256，不把完整签名写入普通日志。SSE 先还原同一块的签名；JSON 空白、属性顺序和等价转义无需逐字相同。**当前“原始 SSE 与本地重组一致”的检查只验证采集过程，不替代这项网关转发检查。**

本批也没有验收跨入口回传、真实号池账号轮换及故障切换。补测前须明确模型、账户和路由绑定条件，跨路线签名被拒绝不能直接归因为 Lighting 改签名。绑定缺陷已经直连上游重现，应先由上游解释并修复；我方同步核对 beta 头、`thinking.block_binding` 及返回字段的实际转发。

## 对客户有什么影响

普通聊天和已测工具流程可以运行，但客户如果使用零上限预热、根据错误类型恢复，或依赖会话绑定处理历史，就可能得到不符合预期的行为。**“错误签名已经会拒绝”不能替代整套 API 的验收。**

本轮仍不能确认模型自动发现、号池账号轮换、故障切换和长会话等完整功能。上游模型列表的问题，可能影响直接接号池的客户端；Lighting 已提供部分 Claude 格式适配，但仍需核对能力信息。

## 面向蒸馏采集的问题严重程度

这里把“做蒸馏”理解为采集教师模型输出，形成回答、工具轨迹或可见思考摘要训练数据。**协议兼容、教师模型来源可信和训练样本合格是三个不同结论，当前测试不能相互替代。** 以下等级是本次数据用途下的影响判断，不是已经观察到模型训练效果下降的实验结果，也不是通用安全漏洞评级。

| 等级 | 判定标准 |
| --- | --- |
| S0 阻断 | 所需训练信号根本不可获得，或样本来源/输入输出对应关系无法确认，不能按该目标验收 |
| S1 高 | 可能静默改变生成条件或多轮轨迹，批量入库前必须解决或隔离受影响样本 |
| S2 中 | 影响采集控制、失败恢复、成本或长度管理，需显式处理；不等于所有正常回答已损坏 |
| S3 低 | 主要影响发现和追踪；已固定模型、可靠关联的采集仍可能运行 |

S 等级表示蒸馏场景的影响，和兼容要求中的 P0/P1 交付优先级分开。未验证风险不是已经确认发生的数据污染。

| 问题或能力边界 | 证据状态 | 严重程度 | 对蒸馏的具体影响与处理 |
| --- | --- | --- | --- |
| 若要求取得完整原始思维链 | 官方能力边界，不是本轮发现的代理故障 | **S0，仅针对完整思维链目标** | omitted 只有空显示文字和协议签名，summarized 只有摘要；两者都不能宣称交付了原始思维链。最终答案蒸馏、工具轨迹采集及摘要监督需要分别定义目标 |
| 教师模型的实际来源和版本尚未独立确认 | 未验证；没有证据证明假模型，也没有同批官方直连或供应商执行链证明 | **S1；若交付条件要求指定官方教师来源，则是 S0 证据门槛** | 不能靠 `model` 字符串、签名长度或拒绝文案认证来源。需供应商可关联执行记录；在此之前不能把样本标为“已认证官方教师” |
| 显式绑定 `error` 不拒绝改过前缀的旧思考；drop 无变换记录 | 两端原始报文已确认 | **S1，多轮/工具轨迹场景** | 无法确认输出基于原上下文、丢弃思考后的上下文还是其他转换结果；禁止把此类回传样本直接作为忠实轨迹。单轮最终答案不因此自动作废 |
| 不支持的 `thinking: enabled` 请求仍成功 | 两端已确认参数负例得到 200；单字段归因仍有测试限制 | **S1，生成配置/思考监督场景** | 采集配置与实际执行行为可能不一致，不能把“已发送 enabled”标成“教师按 enabled 执行”。使用合同合法的 adaptive，并补单变量负例 |
| 错误类型为 `<nil>`/`new_api_error` | 两端已确认 | **S2；若采集器因此把错误当答案，则升 S1** | 失败分类和重试会出错。非 2xx、错误对象不能进入正常答案集；不能只依赖错误类型或 HTTP 200 |
| 生成前的 JSON 错误标成 SSE | 两端已确认 | **S2；若采集器因此丢错或写入伪空样本，则升 S1** | 流式采集可能解析失败或漏掉拒绝原因；需按状态、响应头与正文共同判断，不补造成功终态 |
| `max_tokens: 0` 仍生成 `pong`、报告输出 4 tokens | 两端普通及缓存样本已确认 | **S2** | 预热被变成生成，会污染预热/样本计数并增加意外用量。零上限请求单独分类，不能混入训练答案；未证明其余正数上限均失效 |
| `/v1/messages/count_tokens` 为 404 | 两端已确认 | **S2，长度预算场景** | 无法使用该端点安排教师上下文预算。学生训练 token 数仍应由学生 tokenizer 另算；该缺失不是所有回答不可用的证据 |
| 上游模型列表非 Claude 合同；标准追踪 ID 缺失 | 上游列表及两端追踪差异已确认 | **S3；若无法确认来源或关联重试，按前述来源门槛处理** | 已固定模型的调用不一定受阻，但自动选模、审计及重试去重不完整。私有 ID 可辅助关联，不冒充标准 ID |
| 上游独立 1h 缓存补测出现两份空正文 refusal | 已确认合法拒绝状态；原因是否异常未确定 | **S2，样本可用性风险** | 不能把空正文当成功答案，也不能未经验证把 refusal 认定为代理错误；保存拒绝标签，避免只保留成功样本而隐藏筛选偏差 |
| 同次请求逐跳保存、真实账号轮换、长流断流及完整 summarized 工具链 | 未验证 | **S1 风险，尚非已证实故障** | 在这些流程中缺少证据证明内容、上下文和标签保持一致；不应直接扩大到长期批量轨迹采集 |

思考能力边界依据 [官方 Thinking 说明](https://platform.claude.com/docs/en/build-with-claude/thinking)：`thinking` 文字是摘要，`signature` 用于多轮协议连续性，不能当成可解读的训练推理正文。公开 API 也没有因本轮签名测试就交付教师逐 token 概率；如果目标还要求 logprobs/logits，须另做能力确认，不能用 usage 数字替代。

官方将 preserved thinking 描述为防蒸馏机制的一部分。**完整兼容包括遵守其模型、账户和前缀绑定行为，不包括关闭、绕过绑定，或把“被保护的请求也能得到 200”作为号池优势。** 当前显式绑定差异是需要修复的合同问题。[官方 preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)

### 当前可以给出的用途结论

- **最终答案采集**：已测普通 JSON/SSE 和工具样例可作为小批质量评估输入；还需问题答案质量评测和逐条过滤，不能由接口样例推出“大规模训练数据合格”。
- **多轮工具轨迹或摘要监督**：绑定差异、配置拒绝差异及未验证范围尚未关闭，当前不能作为完整兼容的正式交付。
- **完整原始思维链蒸馏**：当前公开 API 不提供所需训练信号，不能承诺通过修复网关获得它；签名存在、用量包含思考 tokens 都不能改变这一点。

入库要求见 [接口兼容要求中的蒸馏采集附加验收](上游号池与ClaudeCode接口兼容要求.md#蒸馏采集附加验收)。以上用途判断不证明实际教师身份或某个数据集已经达到了训练质量目标。

### 复现请求与错误摘录

零上限最小请求，两端仅替换地址及凭据：

```json
{"model":"claude-fable-5-1","max_tokens":0,"stream":false,"messages":[{"role":"user","content":"Reply with exactly: pong"}]}
```

两端均返回 `content` 中的 `pong`、`stop_reason: end_turn`、`usage.output_tokens: 4`。加入足长的缓存前缀仍得到相同输出，不能解释成仅预热缓存。

本轮 `thinking: enabled` 负例还设置了 `budget_tokens: 1024`、`max_tokens: 128`，因此不是严格的单变量测试。返回 200 的参数合同差异成立，但不能仅凭此确定 enabled 被哪一层接受或预算字段如何处理。后续应在其他参数合法的条件下只改变思考模式；当前报告不把这项样本当成“教师实际使用 enabled”的证据。

流式签名错误的关键形式，两端相同：

```text
HTTP 400
Content-Type: text/event-stream

{"type":"error","error":{"type":"<nil>","message":"...Invalid `signature` in `thinking` block..."}}
```

模型列表：上游顶层字段为 `data/object/success`，条目为 OpenAI 风格的 `object/created/owned_by`；Lighting 顶层为 `data/first_id/has_more/last_id`，条目为 `type/id/created_at/display_name`。后者具备基本 Claude 列表形式，但没有据此宣布能力、生命周期信息和全部分页行为已等价。
