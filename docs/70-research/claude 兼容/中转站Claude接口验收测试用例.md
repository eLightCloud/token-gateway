# 中转站 Claude 接口验收测试用例

本文是后续各中转站 **Claude Messages / Claude Code 兼容验收的测试执行入口**，汇总本会话已有测试、历史回归、未覆盖项目和蒸馏采集检查，共 **64 个用例组**。每组可包含 JSON/SSE、不同路线和多个负例，因此用例组数不等于实际请求数。

协议要求仍以 [接口兼容要求 R01–R12](上游号池与ClaudeCode接口兼容要求.md) 为准；本文只集中维护操作步骤和验收断言，不另建第二套协议。历史执行结果见 [10 月 18 日复测报告](2026-10-18-两端Claude兼容复测报告.md)、[早期回归记录](Claude接口响应结构与停止标记验证.md)、[原始报文索引](2026-10-18-原始报文/索引.md)。**本文不是任何站点已经通过测试的证明。** OpenAI、Gemini 等其他协议需增加对应协议用例，不能用本文件替代它们的完整验收。

## 1. 开始前必须固定的信息

### 1.1 测试对象

| 标识 | 测试对象 | 作用 |
| --- | --- | --- |
| U | 直连被验收的中转站或号池 | 判断其公开入口的行为 |
| G | 客户实际使用的网关入口，例如 Lighting | 判断最终客户得到的结果 |
| O | 可用的官方参考环境 | 同模型、版本和平台合同下的对照；没有时记录缺失 |
| F | 受控响应 fixture 或故障注入环境 | 确定性验证分片、断流、重试等转发行为，不冒充真实模型能力 |

U/G 分别调用是独立重放，不是同一次请求的逐跳抓包。若中转站本身就是客户入口，U/G 可以只有一个对象，但应明确拓扑。O 不可用时结论写“官方文档对照实测”，不能写“官方直连完全一致”。AWS Bedrock 等平台按其合同冻结预期，不能直接套用其他平台的账号/模型绑定行为。

每个站点的主路线、备用路线、模型别名及实际可调度账号分别登记；禁止只测一条路线后覆盖整站。测试配置至少包含：

| 配置 | 必填内容 |
| --- | --- |
| 运行信息 | 批次 ID、执行人、北京时间及 UTC、用例文档版本或文件 SHA-256 |
| 站点 | HTTPS 根地址、路径前缀、U/G/O/F 身份、部署版本 |
| 模型 | 请求模型、映射规则、实际版本及来源证明状态、上下文及输出限制 |
| 路由 | 分组、路线/脱敏账号、区域、主备关系、是否允许自动切换 |
| 客户端 | Claude Code/SDK/HTTP 客户端版本、插件和配置模式 |
| 合同 | `anthropic-version`、beta 集合、模型能力表和官方参考页快照/获取时间 |
| 运行边界 | 请求/连接/流空闲超时、允许输出、最大请求体、并发和费用预算、终止条件 |
| 鉴权 | 使用的头部名称和凭据来源，仅记录脱敏标识，不记录凭据值 |

### 1.2 运行维度与顺序

默认顺序为：**端点及基础响应 → 停止与参数 → 工具与思考 → 签名及绑定 → 缓存与用量 → 故障和号池 → 真实客户端 → 蒸馏数据验收**。依赖项失败时不要人工拼造正例继续判通过。

除仅适用 GET、计数或客户端操作的用例外，生成及错误语义默认分别执行 `stream: false` 和 `stream: true`。需要改动的字段每次只改一个，先取得相同配置下的有效正例。两个对象之间只允许预先声明的域名、凭据和模型映射差异；签名和工具 ID 使用各自本轮生成的真实值。

任意模型输出都不能仅靠提示保证触发。提示未形成目标行为时记录 `INCONCLUSIVE`，不当作协议通过；限制重试次数并保留每次尝试。使用 F 能证明解析或转发正确，不能证明 U 的真实模型会执行该能力。

## 2. 分级和统一通过标准

| 字段 | 含义 |
| --- | --- |
| P0 | 核心兼容交付必须覆盖；存在适用的失败或未完成项，不能宣布该范围通过 |
| P1 | 完整交付或所声明扩展能力必须覆盖；可以签署缩小范围的结果，但不能称全部兼容 |
| S0 | 特定目标被阻断，例如要求公开 API 提供完整原始思维链 |
| S1 | 高影响，可能静默改变配置、内容或多轮轨迹 |
| S2 | 中影响，采集控制、失败恢复、预算或长度处理出现差异 |
| S3 | 低影响，主要影响发现或追踪 |

P 表示测试优先级，S 表示失败的影响；按实际用途记录 S 等级及理由，不因所有失败都阻止“完整一致”就统一判 S0。蒸馏场景的具体分级见 [复测报告](2026-10-18-两端Claude兼容复测报告.md#面向蒸馏采集的问题严重程度)。

后续执行优先级以本文件 TC 条目为准。原 T 编号是需求追溯，历史矩阵中的 P 分级不再作为独立执行清单；例如显式绑定、零上限和严格解析已列入本文件 P0，避免它们在采集前被漏测。这不把官方可选能力改成所有模型的必选能力。

结果只能填 `PASS`、`FAIL`、`BLOCKED`、`INCONCLUSIVE`、`NOT_RUN`、`N/A`。其中 `BLOCKED` 表示前置环境不具备；`N/A` 必须有模型/平台合同依据和已声明交付范围，不能把承诺支持但未实现的能力标为不适用。未测试不是通过，旧版通过也不能自动带到新站点或新版本。

所有用例除专属断言外，还要检查：

1. HTTP 状态、Content-Type、响应头、原始正文、SDK 聚合和语义分别给出结论；HTTP 200/SDK 可读不是总通过。
2. JSON 属性顺序、空白、等价转义不要求相同；字段名、类型、数组顺序、`null`、零值及语义必须按冻结合同检查。
3. 完整成功 SSE 必须有真实终态。生成前的 HTTP 错误不要求出现成功流事件；流中错误或断开不能补成正常结束。
4. 不用独立请求的文本、签名、响应 ID 或 token 数逐字相等来认证模型来源；检查它们是否符合各自合同。
5. 可选字段按能力判断；上游已返回的信息不得被代理丢失，不造字段补外观。

## 3. 公共请求和证据夹具

### 3.1 最小 JSON 请求 B

`MODEL` 是运行配置中的模型 ID 占位符；提交前必须替换。默认发往 `POST /v1/messages`，版本头按配置，Content-Type 为 `application/json`。认证采用测试对象支持的方式，不能把 G 的 Key 发给 U/O。

```json
{
  "model": "MODEL",
  "max_tokens": 128,
  "stream": false,
  "messages": [{"role": "user", "content": "Reply with exactly: pong"}]
}
```

B 的 JSON/SSE 变体只改 `stream`。提示遵从与协议结论分别记录；没有按提示输出 `pong` 不自动证明响应结构错误。

### 3.2 停止夹具 S

将 B 的提示改为 `Output exactly this literal string and nothing else: ALPHA|END|OMEGA`。命中测试加 `stop_sequences: ["|END|"]`，自然结束对照删除该字段。多标记、未命中分别从同一基础派生。只有确认形成了目标生成路径，才断言正文应停在 `ALPHA`。

### 3.3 工具夹具 T

使用仅作用于测试数据的本地工具 `lookup_validation_value`，JSON schema 至少覆盖以下已知对象：

```json
{
  "label": "acceptance-tool",
  "count": 0,
  "enabled": false,
  "details": {"text": "中文、引号\"、反斜杠\\与换行\n", "items": [1, 2]}
}
```

schema 使用对应的 string/integer/boolean/object/array 类型，声明必填字段。提示要求调用工具；Fable 5.1 使用合法 `tool_choice: {"type":"auto"}`，不能强制调用非法 `any/tool` 后期待成功。未得到目标工具调用时记未触发，不自行伪造 `tool_use`。

接续时把模型返回的 assistant `content` 整体原样放回消息历史；新增 `role: user` 的 `tool_result`，`tool_use_id` 使用该轮真实值，结果正文为该批唯一、可核对的验证字符串。签名测试中继续使用相同工具定义、system 和前序消息。

### 3.4 思考及签名夹具 Q

对支持 adaptive 的冻结模型，使用 `thinking: {"type":"adaptive","display":"omitted"}`，合法 effort 和足够的 `max_tokens`，提示先解决最大公约数等问题，再调用 T。Fable 5.1 可用 `max_tokens: 4096` 作为初始测试配置，仍受模型上限和预算约束。

分别从 JSON 和 SSE 新生成的实际响应取得带签名的思考块。没有得到真实块时，后续签名用例记 `BLOCKED` 或未触发；不得复制历史签名或随机填一个块充当有效正例。summarized 变体只改 `display`，另取得新的有效响应。

### 3.5 缓存夹具 C

为每个冷写测试创建带批次标识的固定长前缀，长度超过冻结模型缓存门槛，保留模板及内容哈希。5m/1h 和 U/G 冷写隔离试验分别使用独立前缀；重复读取在同一对象内保持前缀、模型和缓存作用域不变。

跨 U/G 使用相同前缀的配对测试另行执行，观察真实共享边界。首次请求已经命中不能算冷写失败，也不能从中直接推断账号、租户泄漏或服务端造数。当前 Fable 5.1 的公开门槛为 512 tokens，正式验收须按冻结资料复核。

### 3.6 每次调用保存的 E 证据

每个原子变体使用独立目录名，例如 `批次/U/主路线/TC32/one_char/seed-json/request-sse/attempt-01/`，包含：

| 文件或字段 | 内容 |
| --- | --- |
| 请求 | 实际方法、路径/非秘密 query、非认证能力头、请求体；凭据仅留脱敏引用 |
| 响应 | 状态、必要头、原始 JSON/SSE 字节和采集时间；GET 无另存原文时明确注明 |
| 传输 | 开始/首字节/终态/结束时间、超时及退出原因、每段接收时间；无 HTTP 响应不能写 HTTP 0 |
| 解析 | SDK 名称/版本、完整字段检查、事件聚合、协议错误与语义断言 |
| 关联 | 逻辑请求 ID、attempt ID、G/U 标准和私有请求 ID、实际已确认路线 |
| 完整性 | 文件 SHA-256、签名块的长度/受控哈希、原件和脱敏副本的对应关系 |

原件可能含可回传签名、测试上下文和工具结果，受控保存，不纳入普通 Git 提交。不得重写 `.raw` 来修正聚合器错误；新增审计结果另存。采集脚本默认不得输出认证头、完整环境变量或客户源代码。

## 4. 端点与基础结构

### TC01 路线可用性与模型映射（P0，T01/T15/T21）

**前置与步骤：** 固定站点、主备路线和模型映射，分别发送 B；对每个公开别名独立调用，登记实际命中路线。已有证据中的 `ccmax/` 仅是历史路线名称，不默认对新 Key 可用。

**通过与证据：** 状态和模型行为符合公布能力；不可用路线明确失败，不伪造其他模型成功。保留 E 和供应方路由证明。S1；只有探测到 503 时报告该路线不可用，不推断整站模型失效。

### TC02 正确凭据及认证头模式（P0，T01/T17）

**前置与步骤：** 使用专用测试凭据，分别单独以 `x-api-key` 和 Bearer 调用 B；只测试站点承诺支持的模式，避免其他登录来源干扰。

**通过与证据：** 支持的模式可用，实际身份和路线正确，G/U 各用自身凭据。E 不含秘密值。S1；一个头成功不能证明另一个也支持。

### TC03 缺失、无效及无权限凭据（P0，T17）

**前置与步骤：** 在隔离测试身份上分别去掉凭据、使用无效凭据，以及使用对目标模型无权限的有效凭据。每次只改认证或权限条件。

**通过与证据：** 按合同拒绝，不发生成功生成；错误状态/分类正确，不泄露凭据。保存 E 及执行侧拒绝证据。认证/权限绕过为 S1，本目录分级不替代安全漏洞评级。

### TC04 标准路径、beta 查询及错误路径（P0，T01/T14）

**前置与步骤：** 对比 `/v1/messages`、`/v1/messages?beta=true`；另外调用单数 `/v1/message`。根地址不重复加 `/v1`。必要时记录 `HEAD /api/hello` 启动探测。

**通过与证据：** 两个标准变体正确路由；错误路径明确失败，启动探测不混入推理统计。保存 E。S2；传输超时和 404 分开记录。

### TC05 模型列表、分页和能力元数据（P1，T21）

**前置与步骤：** GET `/v1/models`，按冻结合同检查条目；使用小页大小和游标遍历，另测试空页/无效游标/不同权限。启用网关模型发现时再用真实客户端查看。

**通过与证据：** Claude 格式、游标、可见模型和能力声明真实；不以 OpenAI 外层替代完整 Claude 列表。不额外伪造未知能力。保存每页 E。通常 S3，若导致暗换模型则 S1。

### TC06 不存在或被禁止的模型（P0，T17/T21）

**前置与步骤：** 固定有效凭据，将 B 的模型分别改为不存在的 ID、当前身份被禁止的 ID；其他内容不变。

**通过与证据：** 按冻结合同报资源/权限错误，不自动改用便宜模型。保存 E 和路由记录。S1。

### TC07 版本、beta 及扩展头透传（P0，T01/T14）

**前置与步骤：** 使用一个确实受支持的能力头/字段组合，比较 G 入站和 U 出站；覆盖多 beta 值、头大小写及新增合法扩展。无效版本或不支持组合单独做负例。

**通过与证据：** 合法能力完整到达，非法配置真实失败；不靠删除 beta 或字段换取 200。未知扩展透传用 F 或实际受支持扩展验证，不能要求服务器接受任意垃圾字段。保存逐跳 E。S1。

### TC08 基础非流式消息（P0，T01/T18/T22）

**前置与步骤：** 发送 B，分别核对原始响应与 SDK 对象。

**通过与证据：** 消息类型、角色、模型、内容数组、停止信息及 usage 符合冻结 schema；使用 `stop_reason`，不能以 `stopReason` 替代。提示遵从另判。保存 E。S1。

### TC09 基础流式消息（P0，T02/T22）

**前置与步骤：** B 改 `stream: true`，逐事件保存时间和字节，再用 SDK 聚合。

**通过与证据：** event/type 对齐、内容 index 关联、块闭合、最终增量及 `message_stop` 完整；开始的停止字段按合同为 null；不使用 OpenAI `[DONE]` 替代终态。保存 E。S1。

### TC10 字段类型、空值、零值及扩展保留（P0，T18/T22）

**前置与步骤：** 使用包含真实扩展字段的成功 JSON/SSE；另以 F 固定合法 null、空数组、显式 0/false 和新增字段，比较代理两侧。

**通过与证据：** 必需字段正确，可选字段按能力出现；不吞显式零值、不删真实扩展。字段顺序不判失败。E 区分真实模型与 fixture。S1。

### TC11 系统块、消息形式及 Unicode（P0，T14/T18）

**前置与步骤：** 在合法情况下分别用字符串/块数组 system 和 content，包含中文、引号、换行及反斜杠；对支持模型追加中途 system 消息。检查 Claude Code attribution 块的位置。

**通过与证据：** 原始内容和块顺序无损，不把 system 数组合并后丢信息，不将中途 system 移到开头。保存解码后逐字段比较及 E。S1。

### TC12 常规多轮历史（P0，T07）

**前置与步骤：** 用受控数据建立至少两次连续问答，第二轮只能追加消息；再验证保存并恢复同一完整历史。

**通过与证据：** 返回可核对的历史信息，原始消息没有被代理截去或重排。提示不遵从与已证实删历史分别记录。保存 E 和历史快照。S1。

## 5. 停止语义

### TC13 自然结束及无停止规则对照（P0，T03/T05）

**前置与步骤：** 用 S 的提示但不设置 `stop_sequences`，JSON/SSE 分别执行。

**通过与证据：** 未触顶且自然完成时为 `end_turn`，不存在命中标记；不能从上一测试残留停止配置。正文目标串和结束信息一起保存。S1。

### TC14 输出上限截断（P0，T03）

**前置与步骤：** 在合法配置下请求长输出，仅缩小 `max_tokens` 以形成实际触顶。不要同时设置过大的 thinking budget；先确认该组合在目标模型合法。

**通过与证据：** 触顶为 `max_tokens`，不能标成完整自然结束；JSON/SSE 含义一致。未触顶不算本用例通过，记录未形成对照。保存 E。S1。

### TC15 自定义停止命中（P0，T04）

**前置与步骤：** S 加入 `stop_sequences: ["|END|"]`，分别运行 JSON/SSE。

**通过与证据：** 在确认目标生成的对照中，正文为 `ALPHA`，原因 `stop_sequence`，命中值 `|END|`；不包含标记及尾文。三个断言分别记录 E。S1。

### TC16 未命中停止标记（P0，T05）

**前置与步骤：** S 的目标正文不变，停止规则改为不在正文中的固定标记。

**通过与证据：** 自然完成仍为 `end_turn`，标记值为空而不是请求中的任意标记；不因携带 stop 参数而误报。保存 E。S1。

### TC17 多个停止标记（P0，T05）

**前置与步骤：** 请求输出含两个已知标记的字面串，并提供两个停止候选；交换候选数组顺序重新执行，其他内容保持不变。

**通过与证据：** 返回实际先命中的标记，不能固定取数组第一项；正文正确截断。没有形成目标串时保留未触发结果。保存 E。S1。

### TC18 停止标记跨分片边界（P0，T05/T16）

**前置与步骤：** 使用 F 或供应方可控上游，把标记拆在相邻生成文本分片，并改变分片边界；再验证真实路线的可触发样本。

**前置与步骤：** 在最小配置通过后启用客户实际配置，覆盖会话恢复、后台模型、模型发现/手动选择；声明支持的 Agent SDK/编辑器入口独立测试。

**通过与证据：** 配置及认证来源正确，后台请求也走约定模型和根地址；bare 通过不自动覆盖插件、长会话或其他入口。保存脱敏启动/网络记录。S1。

### TC59 官方 SDK 与 C# 原始响应对照（P0，T22）

**前置与步骤：** 使用冻结的 Python/TypeScript SDK 严格验证及 SSE 聚合；对最初 C# 反馈，分别保存原始 HTTP 和应用对象重新序列化结果。

**通过与证据：** 字段结构可读且语义断言单独通过；能识别 SDK/本地聚合器自己的字段遗漏或命名变化。通过的旧 SDK 不能证明最新版扩展通过。保存版本和 E。S1/S2。

### TC60 同次请求逐跳无损与归因（P0，T14/T18/T22）

**前置与步骤：** 在同一可关联请求取得 G 入站/U 出站及返回两侧证据，比较 model 映射、消息、扩展、签名及实际允许的 usage 补充；下一轮回传也比对。

**通过与证据：** 每个合法改动有明确规则，其余数据不丢；签名按同一块解码后比较。独立 U/G 调用、SSE 自聚合一致都不能替代本用例。没有逐跳证据标 BLOCKED，不猜唯一根因。S1。

## 11. 蒸馏采集与证据可信度

### TC61 训练信号和用途适配（P0，蒸馏附加验收）

**前置与步骤：** 在调用前声明目标为最终答案、工具轨迹、可见摘要或其他信号；检查真实 API 提供的字段和实际输入输出样本。

**通过与证据：** 数据类型没有错标；omitted、summarized 和不透明 signature 不能称完整原始思维链，usage 不代替 logits/logprobs。若目标必须取得公开 API 不提供的信号，结果为 S0 目标不满足，不要求中转站绕过保护。保存能力依据。

### TC62 样本过滤、尝试去重与训练侧检查（P0，蒸馏附加验收）

**前置与步骤：** 将小批正常、refusal、截断、工具调用、零上限、错误、断流及重复尝试送入实际采集器；检查入库类型、选择规则、会话切分及学生 tokenizer 长度。

**通过与证据：** 异常不混入普通答案正例，工具轨迹不串号，重复尝试可追溯；按题目/会话划分训练评估集。记录拒绝/过滤数量及答案/任务质量评估，而非只算 HTTP 200。误入库 S1。

### TC63 教师来源和版本证明（P0，T15/T21，蒸馏附加验收）

**前置与步骤：** 向供应方取得可关联的执行路线与实际模型版本记录；有 O 时做同批可比对照，无 O 明确标文档对照。

**通过与证据：** 已认证与未知来源分开标；模型名、ID 外观、签名长度和相同拒绝文案不作为来源认证。证据缺失不等于已证实假模型，但不能通过“指定官方教师已认证”门槛。S1 风险，指定来源为交付前提时 S0 阻断。

### TC64 小批运行边界及证据完整性（P1，全部用例）

**前置与步骤：** 按事先固定的低并发、时间和费用预算执行小批组合，统计每种情况、重复和过滤结果；抽核原始文件哈希、证据完整性及脱敏副本。

**通过与证据：** 首字节/完成/失败等指标只描述实际测量范围，不用小批宣称生产 SLA；样例数、HTTP 数、SDK 可解析数与训练合格数分开。无记录的性能或稳定性结论不能通过。普通证据遗漏 S2，来源对应失真 S1。

### 13.2 站点验收结论

最终报告必须给出：测试对象与版本、已声明能力、适用的原子变体清单及各状态数量、实际 API 请求数、HTTP/SDK/语义检查结果、失败严重程度、未完成范围、证据索引、修复责任和重测范围。不同抽样结果不得合成一个模糊“兼容率”。

- **基础接入可用**：仅说明指定模型/路线的基础请求通过，不覆盖扩展、号池或蒸馏。
- **声明范围验收通过**：该范围全部适用 P0/P1 原子变体通过；N/A 有合同依据，不把缺失的承诺能力排除。
- **完整验收未通过**：适用项存在失败或未完成；可以同时说明已改善或已验证的部分。
- **蒸馏采集验收**：除协议结果外，TC61–TC64 和对应轨迹用例独立给结论；接口通过不等于数据质量或教师来源通过。

新模型、号池/网关发布、路由策略、模型映射、默认请求/错误处理或 Claude Code 版本变化，均需执行受影响组和基础 P0 回归；签名/工具/上下文改动还需重建本轮 seed。修复记录不能覆盖失败原件，也不能靠网关伪造字段掩盖真实上游语义。
