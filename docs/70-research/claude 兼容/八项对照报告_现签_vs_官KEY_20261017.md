## 一、检测方法

让模型先思考、再调用工具，拿到一个带签名的 thinking 块，然后在第二轮请求里把它原样回传，每次只改一个地方，观察服务端的反应。

签名由 Anthropic 服务端下发并校验，第三方无法伪造。因此**篡改类请求是否被拒，直接反映签名有没有原样到达官方**。

非流式与流式各取一次，分别测试。所有项均连跑多轮，全部轮次结果一致才判通过。

## 四、第 8 项专项：为什么是 200，不是 400

这是本报告的核心问题。答案分三层。

### 第 1 层：官方校验清单里没有"块自己的文字"

AWS Bedrock 官方文档《Preserved thinking》列出回放 thinking 块时检查的三项，逐字：

| Check | Description（官方原文） |
|---|---|
| **Model** | The model reading the block is allowed to read the producer's thinking. A model cannot read another model's thinking unless the two are explicitly compatible. |
| **Conversation prefix** | **The top-level system prompt, tools, and all message content before the block are unchanged from the request that produced it.** |
| **Organization** | The thinking block was produced by the same AWS account, or an account in the same customer group. |

注意 `Conversation prefix` 的措辞：**`all message content before the block`**——块**之前**的内容。

校验范围是：

```
system 系统提示词
  + tools 工具列表
  + 该 thinking 块之前的所有消息
```

**不包括 thinking 块自己的文字。** 一个字都不包括。

第 8 项只做了这一个动作：

```python
th["thinking"] = th.get("thinking", "") + "\n(这一句是检测时改动加入的)"
```

改动位置在块**内部**，`system`、`tools`、块之前的消息一个字没动 → prefix 校验通过 → 请求正常返回 **200**。

### 第 2 层：返回的 thinking 是"摘要"，签名里装的是"全文"

这一层是理解第 8 项的关键。

AWS 官方文档原文：

> With extended thinking enabled, the Messages API for Claude 4 models **returns a summary of Claude's full thinking process**.

再看签名里装的是什么：

> **Full thinking content is encrypted and returned in the signature field.**

两句话合起来：

| 字段 | 内容 |
|---|---|
| `thinking`（看得到的文字） | 完整思考过程的**摘要** |
| `signature`（看不到的密文） | 完整思考过程的**全文**（加密） |

**摘要 ≠ 全文，两者本来就不相等。**

所以服务端**在物理上不可能**拿回传的 `thinking` 摘要去和签名里的全文做逐字比对——它们从一开始就不是同一份东西。服务端要做的是另外两件事：

1. 把签名解出来，恢复模型的推理状态（让模型接着往下想）
2. 校验这个签名本身有没有被动过

第 1 件事跟 `thinking` 字段里的文字无关。第 2 件事跟 `thinking` 字段也无关，只看签名。

### 第 3 层：真正触发硬 400 的只有"签名本身出事"

官方文档在同一页有一句加粗 Note，逐字：

> **A thinking block whose signature has been altered or cannot be decrypted always returns a 400, regardless of these checks or the beta value.**

注意 `altered or cannot be decrypted`（被改动，或解不开）——说的对象是 **signature**，不是 thinking 文字。

这就把八项里两种 400 彻底分开了：

| 动了什么 | 触发哪条规则 | 结果 | 对应项 |
|---|---|---|---|
| 改签名里的字符 | `signature altered` → 硬 400 | **400** | 第 4、5 项 |
| 清空签名 | `cannot be decrypted` | **400** | 第 6 项 |
| 删掉签名整个字段 | 结构必填校验 | **400** | 第 7 项 |
| 只改 thinking 文字，签名不动 | 不触发任何一条 | **200** | 第 8 项 |

### 一句话总结

> **签名是"印章"，不是"指纹"。** 印章盖在块**之前**那一摞文件上，块自己那张纸不盖。在自己那张纸上补一句话，印章仍然有效——因为印章从来就不管这张纸。

### 一个反直觉但很硬的佐证

在 AWS Bedrock 官转通道上实测，返回的 thinking 正文**长度是 0**：

```
轮1: 签名848 字符  原文0字→改后15字  回传返回 200
轮2: 签名848 字符  原文0字→改后15字  回传返回 200
轮3: 签名848 字符  原文0字→改后15字  回传返回 200
轮4: 签名848 字符  原文0字→改后15字  回传返回 200
```

也就是说：**从一个空字符串，改成 15 个字，再带上原签名回传，AWS Bedrock 照样返回 200。**

如果服务端真拿 thinking 文字去校验签名，空串改成 15 字是最激进的改法，必然 400。它没有 400——直接证明 thinking 文字不在校验范围内。

## 五、结论

### 1. numspirit 与 AWS 官转，八项返回是否相同

**是。八项逐一相同。**

| 项 | 两边返回 |
|---|---|
| 1、2 | 都返回签名 ✅ |
| 3 | 都 200 ✅ |
| 4、5 | 都 400 ✅ |
| 6、7 | 都 400 ✅ |
| 8 | **都 200** ✅ |

### 2. 第 8 项 200，和 AWS 一致吗

**一致。** 而且不是"碰巧和 AWS 一样"，是**实现的正是官方规定的那一种改法**：只改块内文字、签名原样、前缀原样。这个改法在官方规则下就该 200。

反过来讲，如果这一项测出 400，才说明有问题——要么签名被服务端重新签过，要么中间层对 thinking 块做了额外改写。

### 3. 为什么是 200 不是 400

三句话：

1. 官方校验清单只有三项：**模型 / 对话前缀 / 组织**，其中前缀的范围是 `all message content **before** the block`，**块自己的文字不在里面**
2. 返回的 `thinking` 文字是**摘要**，签名里加密的是**全文**，两者本来就不相等，服务端不可能也不会拿它们互相比对
3. 硬 400 只由 `signature altered or cannot be decrypted` 触发，**改文字不碰签名，就不触发**

### 4. 由此推出的两条判定纪律

- **判"签名有没有真透传到官方"，只看第 4~7 项是否 400。** 这四项是签名校验的正面证据，四组四轮全 400，铁证。
- **第 8 项的 200 不能作为异常信号。** 任何把第 8 项 200 标成"掺水/异常"的检测表，都把那格的口径写错了，需要更正。
