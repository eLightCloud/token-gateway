# 组织账单模型分组补充方案

## 方案结论

本次只调整组织 Invoice 的模型归类逻辑，不在代码、迁移或发布脚本中写入业务提供的参考系数。

- 所有未配置的类别继续使用现有默认结算系数 `1.0000`。
- 上线后由组织 Admin 或系统管理员在“配置系数”中，按生效月份手动录入参考系数。
- 不修改个人预扣、结算、退款、余额、订阅、Relay 或日志写入链路。
- 不新增数据库字段或表，不生成或回填默认结算规则。
- 保留已存在的组织月度结算规则，标准类别的现有 `category_key` 不变。

## 问题与目标

组织 Invoice 已按“模型类别 × 账号”汇总折前金额，再按北京时间自然月应用组织结算系数。当前代码仅定义 Claude、GPT、Gemini、MiniMax、Deepseek 和 Kimi 六个标准类别，且依赖宽泛的模型名前缀归类。

新的账单口径补充了标准类别中的具体模型，并新增 GLM、Qwen 和“向量”类别。财务参考系数需由用户上线后手动确认与配置，避免发布动作自动改变历史或当期账单金额。

### 目标

1. 按经确认的模型清单和无歧义品牌/家族前缀，将消费日志稳定归入标准账单类别。
2. 新增 GLM、Qwen 和向量类别，并在 Invoice、系数配置和 CSV 中使用同一类别语义。
3. 保持未配置系数为 `1.0000`，不自动应用财务参考值。
4. 未命中精确清单或明确家族前缀的未知模型继续使用稳定的单模型 fallback 类别。
5. 保持查询、页面和专用 CSV 的分类与金额一致。

## 非目标

- 不把第二张表的 `0.99`、`0.89`、`1.09`、`1.04` 写成系统默认值。
- 不为所有组织预生成结算规则。
- 不改变结算系数允许范围、四位定点精度、按月生效、继承和版本 CAS 语义。
- 不改变“配置页只展示该组织已产生消费的类别”的现有产品合同。
- 不自动迁移旧 fallback 类别上的手动结算规则。

## 当前实际情况

截至 2026-08-08，本文方案已完成代码、自动化测试、七语言文案和本地 SQLite 人工验收数据接入。Invoice 汇总、已使用类别查询、系数配置和 CSV 现已共用“精确清单优先 + 无歧义家族前缀”的分类目录；未配置类别仍统一返回 `1.0000`，没有新增迁移或自动写入财务参考系数。

## 分类与结算规则

### 标准类别

- 同一完整模型名只能属于一个标准类别。
- 启动测试必须检查清单内没有归一化后重复的模型名。
- 明确家族前缀固定为：Claude `claude-`；GPT `gpt-`、`chatgpt-`；Gemini `gemini-`；MiniMax `minimax-`；Deepseek `deepseek-`；Kimi `kimi-`、`moonshotai/kimi-`；GLM `glm-`、`chatglm-`、`chatglm_`；Qwen `qwen`；向量 `text-embedding-`。
- 标准类别键保持稳定；已存在的 `claude`、`gpt`、`gemini`、`deepseek`、`minimax` 和 `kimi` 的 `category_key`、基础名和排序均与上线前一致。
- 作为本次有意的前端展示调整，`minimax`、`kimi` 及新增的 `glm`、`qwen` 展示名追加"（阿里云）"供应渠道标识；`claude`、`gpt`、`gemini`、`deepseek` 展示名不变。
- 新增类别使用 `glm`、`qwen` 和 `vector`。

### 未知模型

- 未命中精确清单和明确家族前缀的模型继续使用 `model.<sha256>` 稳定 fallback 键。
- fallback 类别仍按单模型分开展示，默认系数为 `1.0000`。
- 命中明确前缀的家族型号（例如 `gpt-4o`、`glm-5-turbo`）直接并入标准类别；品牌归属不明确的型号仍须显式加入清单。

### 结算系数

- 无已生效组织规则时，所有标准类别和 fallback 类别都返回 `1.0000`。
- 用户手动配置的规则按现有逻辑优先，并从所选北京时间自然月开始生效。
- 用户为历史月份增加或修改系数后，该月及其继承月份的 Invoice 按现有规则重新展示，不改写原始 `Log.Quota`。
- 第二张表中的参考值只用于上线后人工操作，不作为程序回退值。

## 优化方案

### 后端

遵守最小入侵约束，将模型分类主体放入新文件，现有 Invoice 聚合仅保留必要调用接线。

建议新增：

- `model/organization_invoice_category_catalog.go`
  - 定义标准类别键、展示名、排序、精确模型清单和无歧义家族前缀。
  - 在包初始化时构建归一化模型名到类别的索引，检查重复归属。
  - 提供标准类别查找与现有稳定 fallback 生成能力。

现有 `model/organization_invoice.go` 仅作最小调整：

- Invoice 聚合和“已使用类别”查询复用新的分类入口。
- 仅保留分类目录显式声明的无歧义家族前缀，不使用任意前缀或子串推断。
- 结算规则解析仍使用统一默认值 `OrganizationSettlementFactorScale`，不增加分类默认系数。

不改变：

- `OrganizationBillingSettlementRule` 数据结构和唯一索引。
- Invoice 聚合 SQL、账期切分、四位定点计算和金额格式化。
- 规则查询、更新、版本 CAS、审计和 CSV API 合同。

### 前端

建议新增独立的类别展示模块，避免在现有大型 Invoice 组件中继续扩展分支：

- `web/src/features/organizations/invoice-category.ts`
  - 将 `category_key` 映射到可国际化的展示名。
  - 中文按业务截图显示 `Deepseek`、`Minimax（阿里云）`、`Kimi（阿里云）`、`GLM（阿里云）`、`Qwen（阿里云）` 和“向量”。
  - 其他语言使用对应的本地化名称，但不省略 Alibaba Cloud 供应商标识。
  - fallback 类别继续展示服务端返回的原始类别名。

现有 `invoice.tsx` 仅改为导入并调用独立模块。新增用户可见文案后，使用项目 i18n 同步工具补齐 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru` 和 `vi`。

## 兼容性与数据影响

### 保持不变的数据

- 已配置在 `claude`、`gpt`、`gemini`、`deepseek`、`minimax` 和 `kimi` 上的结算规则保留并继续生效。
- 未配置结算规则的类别在上线前后都以 `1.0000` 结算。
- 个人消费日志、原始 quota、用户余额和订阅数据不受影响。

### 会发生变化的解释

- `gpt-4o`、`glm-5-turbo` 等品牌归属明确的旧模型按家族前缀进入标准类别，不再误入 fallback。
- GLM、Qwen 和向量清单中的模型会从原单模型 fallback 类别合并到新标准类别。
- 折前总额永远不变：它等于 `Log.quota` 之和，与归类无关。
- 结算后金额只在历史月份存在人工系数、且归类进出改变了"系数作用的模型集合"时才会变；从未配过系数的历史月（全 `1.0000`）只有类别标签变化，金额不变。
- 对已有 GPT、Claude、Gemini、Deepseek、MiniMax、Kimi 家族型号，明确前缀延续原类别语义，避免因精确清单漏项导致历史规则作用范围意外缩小。GLM、Qwen 和向量型号从 fallback 进入新类别的规则影响见下文“旧 fallback 规则”。
- `minimax`、`kimi` 展示名追加"（阿里云）"标识属于纯展示变化，不影响 `category_key`、结算规则和金额；六个现有类别的 `category_key`、基础名和排序均与上线前一致。

### 旧 fallback 规则

若组织曾对某个即将归入 GLM、Qwen 或向量类别的 fallback 键手动配置系数，上线后该规则不会自动迁移到新类别键。本次不做自动迁移，发布前通过只读查询确认是否存在这类规则；如存在，由账单管理员在上线后按生效月份重新配置。

## 用户操作流程

1. 新版本上线后，系统根据新清单展示该组织已产生消费的标准类别。
2. 组织 Admin 或系统管理员打开“配置系数”。
3. 选择北京时间生效月份。
4. 根据财务表手动录入类别系数并保存。
5. 刷新 Invoice，核对分类模型、折前合计、结算系数、结算后金额和 CSV。

现有页面只展示已产生过消费的类别。某类别尚无消费时不能预先配置；首次产生消费后可选择当月并配置，当月 Invoice 将按既有月度规则重新计算。

## 发布与回滚

### 发布前

- 用生产只读查询确认新标准类别对应模型是否存在旧 fallback 结算规则（进入方向）。
- 用生产只读查询确认明确家族前缀归入标准类别的旧 fallback 是否存在人工规则；如存在，按账期导出上线前结算后金额基线并交账单管理员复核。
- 对固定账期导出上线前基线 CSV，用于对比归类变化、折前总额与结算后总额。
- 确认账单管理员已获得目标生效月份和人工配置系数。

### 发布后

- 首先确认所有新类别的未配置值为 `1.0000`。
- 由账单管理员对已产生消费的类别逐类选择生效月份并手动配置系数（无消费的类别按现有合同暂不可预配置，待首次消费后再配置）。
- 重新导出同一账期，核对折前总额不变，结算后总额与分类系数计算一致。
- 查看管理审计日志，确认每次系数修改均有组织、类别、生效月份、原值、新值和版本。

### 回滚

本次没有数据库迁移。如需回滚代码，恢复上一版分类逻辑即可；用户已写入的 `glm`、`qwen` 和 `vector` 规则保留在主库中，上一版不会在未命中这些类别时应用它们。再次上线新分类逻辑后，这些规则会按原生效月份继续生效。
