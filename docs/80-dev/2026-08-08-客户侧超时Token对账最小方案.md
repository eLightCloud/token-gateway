# 客户侧超时 Token 对账最小方案

本文是当前业务目标下的唯一实施方案。线上事实、跨系统请求证据和受控测试结果见[输出 Token 为 0：日志事实分析](2026-08-07-输出Token为0日志事实分析.md)。此前的[输出 Token 为 0：代码业务目标、问题分析与优化方案](2026-08-07-输出Token为0代码业务优化方案.md)覆盖取消传播、异步结算、责任矩阵和渠道治理等更宽范围，现仅作为备选设计，不作为本次实施依据。

本文统一使用以下链路角色：

- **客户侧**：调用网关的用户应用、CLI/SDK 及其网络或代理链路；
- **网关**：承接客户侧请求并转发上游的 API 网关；
- **上游**：网关转发请求的服务，本次对账对象为 `api02.ananops.com`。

## 问题与目标

### 业务决策

本次方案采用以下已确认业务目标：

> 问题本质是客户侧等待时间短于请求的端到端首事件时间。客户侧超时属于客户侧需要修复的问题；网关的核心责任不是替客户侧掩盖超时，而是在问题发生后能够按请求 ID 对齐上游与网关的 Token 账单，并向客户提供可解释证据。

该规则只适用于已经确认属于客户侧超时，或符合业务约定的客户侧 Context 结束请求。`client_gone` 是重要证据，但不自动证明所有历史记录都由同一个 SDK 超时造成；如果已有更早的网关超时、处理错误或内部取消证据，不按本规则自动归为客户责任。

### 唯一核心目标

当客户侧超时导致网关没有取得终态 usage，而上游事后形成 Token 账单时，网关能够：

1. 用 `upstream_request_id` 确定性关联网关日志与上游账单；
2. 对齐未缓存输入、缓存读取、缓存创建和输出 Token；
3. 明确展示网关原记录、上游账单记录及差异原因；
4. 证明请求在终态 usage 到达前因客户侧 Context 结束；
5. 告知客户调整自身超时或等待边界；
6. 保留原始证据，不把本地估算伪装成上游账单 Token。

本文只对齐 Token 数量和 Token 类型，不对齐金额、单价、倍率、汇率或供应商成本。第一版目标是“可确定性对账和解释”，不自动重写客户余额、预扣、消费日志或历史账单；如需依据对账结果调整账务，由人工审批处理，不由对账器直接执行。

### 范围

第一版只处理同时满足以下条件的请求：

```text
end_reason = client_gone
upstream_request_id 非空
上游账单记录唯一
上游账单 Token 分项完整
没有已知多 attempt 歧义
```

正常完成请求继续使用 New API 现行同步结算，不进入本方案。

### 非目标

以下内容不属于本次实施范围：

- 修改 Claude、Responses 或其他协议的流式 handler；
- 建立通用 `StreamUsageEvidence`、Provider Hook、Strategy 或 Registry；
- 将客户侧 Context 绑定上游请求或治理取消传播；
- 重做完整责任归属状态机；
- 完善 tool/reasoning 本地 Token fallback；
- 建设长期 pending、预扣接管或异步自动结算 worker；
- 为所有请求建立完整 attempt 树；
- 建立渠道 SLO、自动降权、上下文上限或 `/compact` 策略；
- 修复已停用渠道仍被路由命中的配置问题；
- 自动补扣、退款或覆盖原消费日志；
- 对没有确定关联键的记录做时间、模型或 Token 数量模糊匹配。

这些事项可以作为独立可靠性或计费项目评估，但不能阻塞本次最小对账能力。

## 当前实际情况

### 问题机制已经确认

受控复现已经证明以下链路成立：

```text
端到端首事件时间超过客户侧等待边界
  -> 客户侧 Context 结束
  -> 网关记录 client_gone
  -> 网关停止读取上游流
  -> 网关没有取得终态 usage
  -> Claude 使用本地输入估算并得到 0 输出
  -> 上游仍可能事后形成包含输出和缓存分项的账单
```

这不是网关把已经收到的输出错误计数为 0，而是网关在客户侧离开后没有继续取得终态 usage。

### 原关联请求已经具备人工对账证据

网关日志中的 `upstream_request_id` 与上游账单请求 ID 相同：

```text
202608071431478508552328268d9d6CaRSU7ju
```

两端记录如下：

| 来源 | 未缓存输入 | 缓存读取 | 缓存创建 5m | 输出 | 证据性质 |
| --- | ---: | ---: | ---: | ---: | --- |
| 上游账单 | 2 | 721,216 | 5,422 | 6 | 按请求 ID 展示的上游账单分项 |
| 网关日志 | `prompt_tokens=280,287`，无法可靠拆分 | 未记录 | 未记录 | 0 | 本地估算，不是终态 usage |

因此该请求的对账结论已经明确：上游账单输出不是 0，网关的 `280,287 / 0` 不能替代上游账单的缓存和输出分项。对账工具必须保留两份原始记录，不能把两种语义压成同一个 `prompt_tokens` 后直接相减。

### 已具备的条件

- 上游账单 Token 数据存在；
- 原关联请求可按同一请求 ID 确定性匹配；
- 上游账单展示未缓存输入、缓存读取、缓存创建和输出；
- 网关日志已经保存部分请求的 `upstream_request_id`；
- 固定快照中 175 条输出为 0 的记录有 159 条保存了上游请求 ID；
- 正常完成请求的同步 usage 和现行结算可保持不变；
- 当前工作不需要修改 `relaykit` 或协议转换逻辑。

159 条记录只是“存在关联键”的候选集合，不等于全部已经确认是客户侧超时，也不等于上游详情都能批量取得。

### 当前缺口

1. 已验证的 `/api/log/token` 只返回最近日志，不支持请求 ID 精确过滤，不能直接作为账单详情接口；
2. 尚未检查截图页面实际使用的详情接口、认证方式、分页、保留期和账单终态；
3. 没有上游请求 ID 的请求无法确定性关联；
4. 当前只保存单个上游请求 ID，多 attempt 请求可能存在歧义；
5. 网关没有统一的只读 Token 对账输出格式；
6. 对账结果尚未形成客户支持可直接使用的证据摘要。

### 最小入侵边界

第一版不进入请求热路径，不改变：

- `relay/channel/api_request.go` 的请求 Context；
- Claude/Responses handler；
- `PostTextConsumeQuota`；
- `BillingSession`；
- 正常预扣、结算和退款；
- 客户余额和现有消费日志；
- 路由、重试和渠道选择。

因此第一版不会修改 New API 原有业务逻辑，也不会产生同步结算与异步结算两套实现。

## 优化方案

### 1. 建立独立只读对账器

主体实现放在新的独立文件或管理命令中，仅使用现有日志和外部账单输入。现有 New API 文件不增加 Hook、注册器或协议分支。

对账器输入分为两部分。

#### 网关记录

- `gateway_request_id`；
- `upstream_request_id`；
- 用户、令牌、模型和渠道引用；
- `end_reason`、`frt`、`RetryIndex`；
- `prompt_tokens`、`completion_tokens`；
- `local_count_tokens`、`usage_billing_path`；
- 原日志创建时间。

#### 上游账单记录

- 上游请求 ID；
- 模型和账单时间；
- 未缓存输入；
- 缓存读取；
- 缓存创建 5m/1h；
- 输出；
- 账单完成标识或稳定版本。

第一版可以使用人工提供的结构化 JSON/CSV 记录验证流程；不得把截图 OCR 作为生产数据源，也不得在配置或数据库中保存上游账号密码、API Key、原始 prompt 或模型输出。

### 2. 使用确定性匹配，不做模糊归因

唯一自动匹配条件是：

```text
gateway.upstream_request_id == upstream.request_id
```

以下情况不自动得出客户账单结论：

- 网关没有上游请求 ID；
- 同一上游请求 ID 返回多条冲突记录；
- 上游记录尚未稳定；
- Token 分项缺失；
- `RetryIndex > 0` 或存在多 attempt 证据；
- 已出现更早的网关错误或内部取消。

这些情况统一进入人工审核，不使用时间接近、模型相同、Token 数量相似等模糊匹配。

### 3. 固定 Token 对账口径

Claude/api02 第一版输出以下分项：

```text
input_uncached_tokens
cache_read_input_tokens
cache_creation_input_tokens_5m
cache_creation_input_tokens_1h
output_tokens
```

网关现有聚合 `prompt_tokens` 如果无法还原为上述分项，应原样保留并标记为 `local_estimated_aggregate`，不能拆分或分摊到缓存字段。

对账结果状态固定为：

| 状态 | 含义 |
| --- | --- |
| `matched` | 两端相同语义分项一致 |
| `component_mismatch` | 已确定关联，但 Token 分项不一致或网关只有聚合估算 |
| `upstream_missing` | 有上游请求 ID，但尚未取得对应账单记录 |
| `gateway_id_missing` | 网关没有上游请求 ID |
| `ambiguous` | 重复记录、多 attempt 或其他无法唯一判断的情况 |
| `upstream_not_final` | 上游记录尚未达到稳定账单状态 |

### 4. 输出可供客户支持使用的对账摘要

每个结果至少包含：

- 网关请求 ID 和上游请求 ID；
- 客户侧结束证据；
- 网关原 Token 记录及证据来源；
- 上游账单 Token 分项；
- 差异类型；
- 是否可确定为客户侧超时责任；
- 建议客户提高超时或等待边界；
- 无法自动判断时的原因。

原关联请求的预期摘要是：

```text
关联：matched by upstream_request_id
结束：client_gone，网关未取得终态 usage
网关：local_estimated_aggregate=280,287，output=0
上游：uncached=2，cache_read=721,216，cache_create_5m=5,422，output=6
结果：component_mismatch
责任：客户侧超时（以客户侧日志或既定业务规则为准）
处置：客户调整超时；如需调整账务则进入人工审批
```

### 5. 调整实施阶段

#### 阶段零：确认账单详情数据源

1. 检查上游账单详情页面的网络请求；
2. 确认按请求 ID 查询、Token 分项、账单终态、认证、分页和保留期；
3. 如果暂时没有可调用接口，使用脱敏结构化人工导入完成第一批验证；
4. 不通过保存登录密码或页面抓取绕过接口能力限制。

#### 阶段一：实现只读对账最小版本

1. 只支持 Claude/api02；
2. 只支持 `client_gone + upstream_request_id 非空 + 单 attempt`；
3. 使用原关联请求作为固定验收样本；
4. 再抽取一批具备上游账单详情的候选请求验证唯一匹配率；
5. 只输出报告，不修改任何账务数据。

#### 阶段二：固化客户问题处置流程

1. 客户提供网关请求 ID 或问题时间；
2. 支持人员取得对应上游请求 ID 并运行对账；
3. 对账成功后向客户说明客户侧 Context 先结束及上游账单 Token；
4. 要求客户根据实际端到端首事件时间提高超时；
5. 需要账务调整时进入人工审批，不由对账器直接写账。

达到阶段二即完成当前业务目标，不继续自动进入异步结算、取消传播或通用协议改造。

#### 后续扩展触发条件

只有出现明确新增目标时才扩展：

| 新需求 | 扩展条件 |
| --- | --- |
| 批量自动取得上游账单 | 详情接口稳定且权限、分页、限流已确认 |
| 自动补扣或退款 | 业务明确要求自动改账，并完成幂等、审计和报表设计 |
| 覆盖响应头前取消 | 上游支持预置客户关联 ID |
| 覆盖多 attempt | 线上证明确有实质规模，且网关保存每次 attempt ID |
| 支持第二个上游 | 第二个上游具备真实账单查询需求后再抽象接口 |
| 传播客户侧取消 | 作为独立资源治理项目评审，不并入对账项目 |

### 6. 测试方案

新增确定性测试，仅保护对账行为：

- 原关联请求输出上游 `2 / 721,216 / 5,422 / 6`、网关 `280,287 / 0` 和 `component_mismatch`；
- 相同语义分项一致时返回 `matched`；
- 无上游请求 ID 返回 `gateway_id_missing`；
- 查询不到上游记录返回 `upstream_missing`；
- 重复上游记录、`RetryIndex > 0` 或多 attempt 返回 `ambiguous`；
- 上游记录未稳定时返回 `upstream_not_final`；
- 网关聚合 prompt 不会被伪拆成缓存分项；
- 全部只读路径不会修改余额、预扣、消费日志和原始账单。

文档和实现完成后执行：

```bash
go test <新增对账模块所在包>
task docs:check
```

### 7. 验收标准

- [ ] 原关联请求能够按同一上游请求 ID 确定性对账。
- [ ] 对账结果完整展示未缓存输入、缓存读取、缓存创建和输出。
- [ ] 网关本地聚合估算与上游账单分项不会被混为同一语义。
- [ ] 没有确定关联键、存在多 attempt 或上游记录未稳定时不自动给出客户账单结论。
- [ ] 对账器对 New API 请求热路径、余额、预扣、消费日志和历史账单零写入。
- [ ] 正常完成请求的协议输出和现行结算完全不变。
- [ ] 支持人员可以根据报告向客户说明原因并要求调整超时。
- [ ] 不引入通用 Provider 抽象、完整责任状态机、pending worker 或协议 handler 改造。

### 8. 发布与回滚

第一版作为独立只读工具发布，不挂入在线请求链路，不定时自动修改账务。回滚只需停止使用该工具；不得删除或改写原始网关日志、上游账单记录和已经形成的人工审批记录。

若后续业务目标扩大到自动调账、响应头前关联或多 attempt 核销，必须另行评审并更新本文状态，不从当前只读方案隐式扩张。
