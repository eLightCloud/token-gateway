# 客户断开续读接口回归问题分析

本文记录客户侧断开后继续读取上游文本流改造的本地真实接口回归、缺陷修复结果和剩余运行边界。历史线上事实见[输出 Token 为 0：日志事实分析](2026-08-07-输出Token为0日志事实分析.md)，当前实现目标和验收口径见[客户侧超时后获取上游 Token 的通用方案](2026-08-08-客户侧超时Token对账最小方案.md)。

本文只分析文本生成流生命周期及本轮接口测试发现的非图片问题。图片生成尺寸、图片参数兼容、图片计费、前端页面和 UI 均不在本文范围。

## 问题与目标

本轮测试需要回答三个问题：

1. 客户侧在协议终态 usage 到达前断开后，网关是否停止向客户写入、继续读取已建立的上游流，并只沿用一次现有结算入口；
2. Claude Messages、OpenAI Chat Completions 和 OpenAI Responses 的正常文本、流式终态、工具调用及断开场景是否仍能取得非零真实 usage；
3. 当前接口、消费日志和文档是否完整表达“客户已断开”和“上游最终成功或失败”两个正交结果。

测试使用本地后端 `http://localhost:3200`。`http://localhost:3201` 是前端开发服务器，访问 `/v1/models` 返回 HTML，不是本地 API Base URL。受控测试密钥不写入本文或仓库；由于密钥曾在对话中明文出现，测试后必须轮换。

本轮不验证未配置真实渠道的 Gemini、AWS Bedrock、Cohere、Zhipu、讯飞、PaLM 等传输，也不通过真实供应商强制制造 `usage_missing`、`incomplete_eof`、`scanner_error`、`idle_timeout` 或 `drain_timeout`。这些边界由确定性协议级测试覆盖，仍不能由本轮已配置文本模型的真实接口结果外推为所有供应商的线上验收。

## 当前实际情况

### 核心回归已通过

当前本地实现已经改变修复前“客户 Context 结束后立即关闭上游响应体”的行为。三个真实断开样本均在客户侧结束后继续取得终态 usage，并且每个请求只记录一条消费日志：

| 场景 | 客户侧结果 | 网关最终 Token | 缓存分项 | 网关证据 | 请求 ID |
| --- | --- | ---: | ---: | --- | --- |
| Claude Messages，1 秒断开 | `curl 28`，0 字节 | 输入 49，输出 23 | 读取 0，创建 0 | `client_gone + terminal_success`，FRT 3,707ms | `202608080850371293250008268d9d61rve8lY6` |
| OpenAI Responses，1 秒断开 | `curl 28`，收到 2,792 字节部分事件 | 输入 323，输出 12 | 读取 0 | `client_gone + terminal_success`，FRT 890ms | `202608080850047224730008268d9d6ncPaGcZ7` |
| Claude 缓存命中，1 秒断开 | `curl 28`，0 字节 | 未缓存输入 30，输出 8 | 读取 25,004，创建 0 | `client_gone + terminal_success`，FRT 3,047ms | `202608080854317755540008268d9d6UWz1vH8G` |

Claude 缓存样本先通过请求 `202608080854275995740008268d9d6D4Am8N5z` 创建 25,004 个 5 分钟缓存 Token，再执行客户侧断开请求。第二个请求最终记录了 25,004 个缓存读取 Token，证明断开后续读不仅恢复输出 Token，也保留了协议返回的缓存分项。

从客户侧 1 秒上限到网关请求结束的额外等待约为 0.8～3 秒，显著小于当前 300 秒断开后绝对上限。现有证据支持以下结论：

- 原问题不再固定落为本地估算输入和 0 输出；
- 客户侧仍按自己的等待边界结束，网关没有向已离开的客户补写终态；
- 网关从同一上游流取得终态 usage，并沿用原消费日志和结算路径；
- Claude 的未缓存输入、缓存读取、缓存创建和输出分项能够分别落库；
- 当前已配置的 Claude Messages 和 OpenAI Responses 真实路径均验证了断开后续读。

### 问题一已修复：消费日志持久化上游结束结果

修复前，三个断开样本的后端文本日志都有 `upstream_result=terminal_success`，但 `/api/log/token` 返回的 `other.stream_status` 只有 `status`、`end_reason` 和 `end_error`。消费日志因此不能区分“客户先离开、续读成功”和“客户先离开、续读随后失败”。

当前实现从并发安全的 `GetUpstreamResult()` 取得上游结果，并将非空的 `upstream_result`、`upstream_error` 写入同一条消费日志。重启后的真实 Claude 断开请求 `202608080907410245190008268d9d6KruLjCiU` 最终记录输入 46、输出 18，并返回：

```json
{
  "status": "error",
  "end_reason": "client_gone",
  "end_error": "context canceled",
  "upstream_result": "terminal_success"
}
```

这保留了“客户侧先结束”的事实，同时独立表达上游最终成功。单元测试还覆盖上游错误、正常完成和结果尚未确定三类组合；实现没有新增第二条消费日志或第二套结算路径。

### 问题二已修复：请求边界校验返回 HTTP 400

修复前，请求校验能够拒绝越界输入，但 `GetAndValidateRequest` 返回的普通错误被默认包装为 HTTP 500。修复后结果如下：

| 接口与字段 | 测试值 | 修复前 | 修复后 |
| --- | ---: | ---: | ---: |
| Chat Completions `max_completion_tokens` | 1,073,741,824 | 500 | 400 |
| Claude Messages `max_tokens` | 1,073,741,824 | 500 | 400 |
| OpenAI Responses `max_output_tokens` | 1,073,741,824 | 500 | 400 |

控制器现在通过唯一映射入口把普通请求解析和边界校验错误包装为 HTTP 400 `invalid_request`，并标记为不可重试；请求体过大仍保持 HTTP 413。控制器回归覆盖 Chat、Claude、Responses、Gemini、畸形 JSON 和请求体过大，真实接口复验确认上述三个已配置文本入口均返回 400，且请求没有进入上游调用。

## 优化方案

### 1. 已实施：补齐消费日志的双维状态

`service/log_info_generate.go` 现在通过独立文件中的状态映射逻辑读取现有 `GetUpstreamResult()`，并在存在时写入：

```json
{
  "status": "error",
  "end_reason": "client_gone",
  "end_error": "context canceled",
  "upstream_result": "terminal_success"
}
```

若存在上游错误，会写入独立的 `upstream_error`。`end_reason=client_gone` 保留客户侧先结束的事实，不会被终态成功覆盖，也不从非零 Token 反推上游一定成功。

回归直接断言消费日志映射结果，而不只断言后端文本日志：

- `client_gone + terminal_success` 同时存在；
- `client_gone + scanner_error` 同时保留客户错误和上游错误；其他上游枚举由同一通用字段无分支持久化；
- 正常完成请求仍为 `end_reason=done + upstream_result=terminal_success`；
- 上游错误信息不覆盖客户侧 `end_error`；
- `upstream_result` 仅写一处，不新增第二条消费日志或第二套结算路径。

真实接口已确认消费日志查询能够返回 `client_gone + terminal_success`。

### 2. 已实施：统一文本请求校验错误的 HTTP 状态

请求体过大保持 413；其他 `GetAndValidateRequest` 校验错误统一包装为带 `http.StatusBadRequest` 和 `SkipRetry` 的 `invalid_request`。状态映射位于独立控制器文件，没有在每个字段校验点增加重复分支。

回归已经覆盖：

- Chat `max_tokens/max_completion_tokens` 越界返回 400；
- Claude `max_tokens/max_tokens_to_sample` 越界返回 400；
- Responses `max_output_tokens` 越界返回 400；
- Gemini `maxOutputTokens` 越界返回 400；
- 畸形 JSON 保持 400，请求体过大保持 413；
- 所有这些请求均不选择渠道、不预扣、不写普通消费日志，也不触发上游重试。

真实接口同时验证 Chat、Claude 和 Responses 的越界请求均返回 400。

### 3. 已实施：把历史基线和修复后事实分开表达

现有两份文档已经按主题收敛，且保留修复前证据：

1. 将 2026-08-07 的 175 条、原关联请求和受控取消结果明确标为“修复前固定快照”；
2. 在事实文档增加本轮三个真实断开样本，说明当前版本已能取得输入、缓存和输出 usage；
3. 将实施方案中的“当前失败机制”改为“修复前失败机制”；
4. 只使用已有代码、确定性测试、构建或真实接口证据更新验收状态；
5. 将本文作为当前接口回归和剩余问题的证据入口，避免把实施方案写成调试流水账。

### 4. 后续运行边界

当前可以判定：Claude Messages、OpenAI Responses 的真实客户断开续读、Claude 缓存分项、消费日志双维状态和文本请求边界状态码均已通过本地验收。本次范围内未发现仍待修复的代码缺陷。

发布和持续运行仍应观察：

- 真实 api02 原问题样本或等价大上下文样本的断开后 tail 显著小于 300 秒；
- 未配置真实供应商的各传输类型在接入对应渠道时补做真实接口验收；当前确定性协议级测试、全量相关包测试和构建均已通过；
- 持续监控 `usage_missing`、异常 EOF、scanner/handler 错误、空闲和绝对超时，确认其不会进入普通成功消费日志；
- 持续观察失败路径的上游资源和 goroutine 是否稳定释放；
- 保持正常完成、非流式和客户仍在线时的现行 timeout/fallback 语义不变；
- 发布前轮换曾在对话中明文出现的受控测试密钥。

这些事项是发布观测和外部凭据管理边界，不是本轮仍未修复的代码问题。已配置文本协议的本地结果不能表述为“所有供应商均已完成线上验收”。
