# 组织账单渠道信息权限隔离

## 问题与目标

组织账单同时面向组织管理员和普通成员。普通成员应当能够查看自己的消费汇总、趋势、模型用量和账单日志，但渠道名称、渠道 ID 及渠道维度用量属于内部运营信息，不应向普通成员公开。

修复前，普通成员虽然已被后端强制限定为本人账单范围，但仍存在以下渠道信息暴露面：

- 组织账单页面展示“渠道”筛选项和“渠道用量”面板；
- 前端会请求当前组织的渠道用量接口；
- 普通成员可以直接请求 `/api/organization/current/billing/channels`；
- 账单日志响应包含渠道字段；
- 原始日志 CSV 和完整账单 CSV 包含渠道列、渠道用量区块及渠道名称；
- 普通成员可携带 `channel` 参数筛选账单，从结果差异间接探测渠道使用情况。

目标权限边界如下：

| 身份 | 可见账单范围 | 可见渠道信息 |
| --- | --- | --- |
| 普通组织成员 `member` | 仅本人 | 否 |
| 组织管理员 `admin` | 当前组织 | 是 |
| 系统管理员 | 管理端指定组织 | 是 |

本次修复只收紧渠道信息可见性，不改变普通成员查看本人账单的能力，也不改变组织管理员和系统管理员的既有账单权限。

## 当前实际情况

### 已验证事实

1. 当前组织账单统一通过 `scopedCurrentOrganizationBillingFilters` 建立访问范围。普通成员的 `user_id` 会被服务端强制覆盖为当前登录用户，不能通过查询参数查看其他成员账单。
2. 普通成员的渠道筛选参数会被服务端清零，无法通过已知或猜测的渠道 ID 对账单进行差异探测。
3. `/api/organization/current/billing/channels` 对普通成员返回空数组；组织管理员仍可获得当前组织的渠道用量。
4. 普通成员的账单日志响应使用不含 `channel` 和 `channel_name` 的专用响应结构，渠道字段不会进入 JSON 响应。
5. 普通成员下载原始日志 CSV 时，文件不包含 `channel_id`、`channel_name` 或对应数据列。
6. 普通成员下载完整账单 CSV 时，文件不包含“渠道用量”区块，消费明细也不包含渠道列。
7. 组织管理员通过当前组织接口、系统管理员通过 `/api/admin/organizations/:id/billing/channels` 管理接口，仍可查看渠道信息。
8. 前端直接根据组织角色派生渠道可见性，不为普通成员发起渠道用量请求，也不渲染渠道筛选项和渠道用量面板。

## 优化方案

### 一、前端按角色隐藏并停止请求

新增 `canViewOrganizationBillingChannels(role)` 作为前端唯一渠道可见性判断：

- `admin` 返回 `true`；
- `member` 或尚未取得角色时返回 `false`。

组织账单页面据此执行以下行为：

- 普通成员不展示渠道筛选项；
- 普通成员不展示渠道用量面板；
- 普通成员不启用渠道用量 React Query；
- 普通成员点击刷新时不会手动触发渠道查询；
- 筛选选项查询键包含渠道可见性，避免不同权限的数据共用同一缓存；
- 组织账单日志页不请求不需要展示的渠道筛选选项。

前端控制只负责正确的用户体验，不作为最终安全边界。

### 二、后端执行强制权限隔离

后端在建立当前组织账单范围时记录本次请求是否允许查看渠道。普通成员请求执行以下强制规则：

1. 始终使用当前用户 ID 限定账单范围；
2. 忽略客户端提交的渠道筛选参数；
3. 渠道维度接口直接返回空数组；
4. 日志接口转换为不含渠道字段的响应 DTO；
5. 原始日志导出使用无渠道列的 CSV 表头和行结构；
6. 完整账单导出不查询渠道维度，不生成渠道区块，消费明细不写渠道列。

组织管理员继续走原有当前组织账单实现，系统管理员继续走独立的管理端接口，因此二者的渠道查看能力不受影响。

### 三、回归验证

后端端到端测试覆盖以下合同：

- 普通成员仍只能看到本人账单；
- 普通成员提交渠道筛选后，账单结果不发生渠道维度收窄；
- 普通成员渠道接口返回空数据；
- 普通成员日志 JSON 不存在渠道字段；
- 普通成员两类 CSV 导出均不包含渠道字段、渠道区块或渠道名称；
- 组织管理员和系统管理员仍能获得渠道数据。

前端单元测试覆盖 `admin`、`member` 和未取得角色三种渠道可见性结果。
