# 额度余额 64 位迁移实施方案

## 问题与目标

当前站点默认 `QuotaPerUnit = 500000`，管理员给零余额用户增加 `5000 USD` 时，前端会转换为 `2,500,000,000 quota`。该值超过当前 `users.quota` 有符号 32 位整数上限 `2,147,483,647`，因此管理员调额事务在写库前返回 `user quota adjustment result is out of range`。

本方案的目标是：

1. 让单个用户钱包和 API Key 能安全保存超过 `MaxInt32` 的累计余额，至少覆盖 `5000 USD` 场景。
2. 继续保护单次请求的预扣、结算和退款，不放宽现有 32 位单次计费上限。
3. 保持 SQLite、MySQL >= 5.7.8 和 PostgreSQL >= 9.6 三库一致，避免 SQLite 可写、MySQL/PostgreSQL 越界的分叉。
4. 保持充值、兑换码、订阅、管理员调额、Redis 缓存、组织 Invoice 和 CSV 导出的金额口径一致。
5. 通过可分阶段启用、可观测、有明确回滚门槛的迁移流程完成修复。

## 当前实际情况

### 已验证事实

1. [`common/constants.go`](../../common/constants.go) 默认定义 `QuotaPerUnit = 500 * 1000.0`。
2. [`model/user.go`](../../model/user.go) 将 `User.Quota`、`UsedQuota`、`AffQuota` 和 `AffHistoryQuota` 声明为 Go `int` 且数据库类型为 `int`。
3. [`model/token.go`](../../model/token.go) 中 `Token.RemainQuota` 和 `UsedQuota` 仍是 `int`，它们与用户钱包共同参与预扣和结算。
4. [`model/user_quota_adjustment.go`](../../model/user_quota_adjustment.go) 中调额值、差额、调整前余额和调整后余额均为 `int`，并显式拒绝超出 `math.MinInt32...math.MaxInt32` 的结果。
5. [`common/quota_math.go`](../../common/quota_math.go) 将单次 quota 换算饱和到 `MaxInt32/MinInt32`，并通过 `QuotaClamp` 记录溢出。这是防止单次费用回绕为负扣费的现有安全不变量。
6. [`model/user_cache.go`](../../model/user_cache.go) 使用 Redis `HINCRBY` 接受 `int64` delta，但缓存对象和读取函数仍把余额解析为 `int`。
7. [`model/utils.go`](../../model/utils.go) 中批量更新记录和内存累加值使用 `int`。即使单次扣费未越界，一个批次的累计值仍需要防止 32 位溢出。
8. 用户余额、API Key 余额和请求单次费用当前混用 `int`，例如 `GetUserQuota`、`RelayInfo.UserQuota`、`BillingSession` 和 `DecreaseUserQuota`。
9. 组织 Invoice 的部分累计结果已使用 `int64`，但组织 Billing 的 Summary、Dimension 和 Trend DTO 仍存在 `int` 聚合接收值。
10. 前端 [`web/src/features/users/components/user-quota-dialog.tsx`](../../web/src/features/users/components/user-quota-dialog.tsx) 会将显示货币金额换算为 quota，但未根据当前余额和后端上限限制输入。
11. JavaScript `number` 只能精确表示不超过 `Number.MAX_SAFE_INTEGER = 9,007,199,254,740,991` 的整数。后端即使使用 `BIGINT`，对外返回的 quota 也不应无限接近 `MaxInt64`。
12. 当前 `userCacheSchemaVersion = 2`。版本不匹配时 `GetUserCache` 会回源主库，但 `writeUserCache` 为了不用可能滞后的 DB 快照覆盖 Redis quota 增量，对已存在的 `Quota` 字段不会重写。因此仅提升 schema version 不等于“删除旧 quota 并从 DB 完全重建”。
13. 现有 `/api/user/manage` 失败响应使用 HTTP 200 + `success: false` + `message`。直接把调额越界改为 HTTP 400 会改变已有 API 错误语义。
14. API Key 创建和编辑当前通过 `int(1000000000 * QuotaPerUnit)` 生成上限，默认结果为 `500,000,000,000,000 quota`，已远超当前 Token 数据库列的安全范围，且存在 float 到 `int` 的裸转换。
15. ClickHouse `logs.quota` 是 `Int32`，符合单条 charge quota 边界；但 ClickHouse `sum(Int32)` 的结果可超过 32 位，当前 `Stat.Quota` 和部分组织聚合接收结构仍为 `int`。
16. 充值和余额发放路径仍存在 `int(decimal.IntPart())` 等窄化转换。现有 `common.QuotaFromDecimal*` 是单次 charge quota 转换，不能直接承担 64 位 balance quota 发放。

### 已接受决策

1. 采用“方案 2”：将钱包余额和累计值扩展到 64 位。
2. 单次请求费用、预扣费用和单条消费日志不随之放宽，继续使用现有 32 位饱和与审计规则。
3. 不通过删除越界检查、拆分多次调额、降低 `QuotaPerUnit` 或仅改 SQLite 来绕过问题。
4. 迁移采用显式业务上限，不将 `MaxInt64` 直接暴露为可调整余额。
5. 已有 `/api/user/manage` 保持 HTTP 200 失败合同；稳定错误码和边界数据以新增响应字段的方式提供。
6. balance quota 的 decimal 转换采用 strict fail-closed 语义；超界时不饱和发放、不标记订单成功。
7. ClickHouse 的单条 `logs.quota Int32` 保持不变，仅将 `SUM(quota)` 等 aggregate 接收与 API DTO 扩展为 `int64`。

### 实施前待确认项

1. **最大钱包余额及来源**：产品需要给出 USD 等值上限，技术实现将其固化为 quota 整数。`Number.MAX_SAFE_INTEGER` 只是技术硬上限，不是推荐业务值。首版建议使用编译期或启动期固定上限，不开放运行时动态修改；候选值应按真实最大客户余额加安全余量确定，不直接使用 `10^15` 或 `2^53-1`。
2. **负余额下限**：当前管理员“减少”允许余额变为负数。第一阶段建议保持 `MinInt32` 下限，不在本次迁移中同时扩大用户债务范围。
3. **API Key 额度上限**：建议与钱包一同迁移，否则用户可持有大额钱包却无法分配给单个 Key。
4. **发布方式**：本方案默认推荐短维护窗口。如果必须零停机，需要额外的双版本兼容发布。
5. **对外精度合同**：钱包和 Key 余额的旧 JSON 字段保持 number 以维持兼容，因此业务上限必须小于等于 `Number.MAX_SAFE_INTEGER`。对可能超过安全整数的跨用户聚合，需决定是增加精确字符串镜像字段，还是仅以后端 decimal 金额/导出为财务权威值。

**WP0 阻断条件**：上述 1、2、3、5 未形成明确决策时，不进入 WP1。

## 优化方案

### 一、建立两类 quota 边界

不再用一个 `MaxQuota` 同时表示“单次费用”和“钱包余额”。

| 领域 | 含义 | Go 类型 | 数据库类型 | 上限策略 |
| --- | --- | --- | --- | --- |
| Charge quota | 单次请求预估、预扣、结算、退款、单条日志 | `int` | `INT` | 保持 `MaxInt32` |
| Balance quota | 用户余额、Key 余额、累计已用额度、累计调额 | `int64` | `BIGINT` / SQLite `INTEGER` | 新增显式业务上限 |
| Aggregate quota | 账单期间汇总、组织维度汇总 | `int64` | SQL `SUM` 扫描到 `int64` | 每次加法检查溢出 |

建议在公共边界中明确定义：

```go
const MaxChargeQuota = math.MaxInt32

// MaxWalletQuota / MinWalletQuota 的 int64 值由 WP0 决策固化，
// 进程启动后不支持在线动态修改。
```

为降低一次性重构风险，业务字段直接使用 `int64`，不强制新建遍布全项目的自定义数字类型。但函数名、参数名和注释必须区分 balance 与 charge。

`common.QuotaFromFloat*`、`QuotaRound*` 和 `QuotaFromDecimal*` 继续返回单次 charge quota，不得因钱包扩容改为 `MaxInt64` 饱和。

新增 balance 专用转换边界，例如：

```go
func QuotaBalanceFromDecimalStrict(
    value decimal.Decimal,
    min int64,
    max int64,
) (int64, error)
```

该函数必须先按已有发放合同明确“截断还是舍入”，再检查 `int64` 和业务上下限。越界时返回有类型错误并中止事务，不得饱和到上限后继续充值或把订单标记成功。如需审计，记录该 strict 失败，不复用“可成功饱和”的 charge `QuotaClamp` 语义。

### 二、数据模型迁移范围

#### 必须迁移

| 模型/结果 | 字段 | 目标 | 原因 |
| --- | --- | --- | --- |
| `User` | `Quota` | `int64` + `BIGINT` | 用户当前钱包余额 |
| `User` | `UsedQuota` | `int64` + `BIGINT` | 用户生命周期累计消费可超过 32 位 |
| `User` | `AffQuota`, `AffHistoryQuota` | `int64` + `BIGINT` | 可转入钱包的累计额度 |
| `Token` | `RemainQuota`, `UsedQuota` | `int64` + `BIGINT` | 大额钱包向 Key 分配后不能再被 32 位截断 |
| `UserQuotaAdjustment` | `DeltaQuota`, `BalanceBefore`, `BalanceAfter` | `int64` + `BIGINT` | 不可变调额事实必须精确记录大额差值 |
| 调额 API | `ManageRequest.Value` 及结果 DTO | `int64` | 允许传入 `2,500,000,000` |
| Redis 用户缓存 | `UserBase.Quota`、get/set 函数 | `int64` | Redis 自身已支持 64 位，但 Go 接收类型必须一致 |
| 批量更新 | store value、批次累加和写库 delta | `int64` | 防止多个合法单次 charge 在批次内溢出 |
| Relay 余额上下文 | `RelayInfo.UserQuota` 及鉴权 context | `int64` | 余额比较不能向下窄化 |
| Billing 累计 DTO | Summary、Dimension、Trend 的 `TotalQuota` | `int64` | SQL `SUM` 结果可超过 32 位 |
| Invoice 调额聚合 | 调额 `SUM(delta_quota)` 接收值 | `int64` | 保持调额流水与财务补充行一致 |
| ClickHouse/独立日志库聚合 | `SUM(quota)`、`Stat.Quota`、组织聚合行 | `int64` | 单条列是 `Int32` 不代表汇总值是 32 位 |

#### 根据语义保持 32 位

| 模型/路径 | 字段 | 理由 |
| --- | --- | --- |
| `Log` | `Quota` | 单条已结算消费事实，应受单次 charge 上限保护 |
| `Task`, `Midjourney` | 单任务 `Quota` | 单次任务费用，不应因钱包变大而允许超大扣费 |
| `BillingSession` | reserve/settle 的 `actualQuota` | 单次计费量，继续使用 `common.QuotaFrom*` 保护 |
| `PriceData` | 单次价格计算结果 | 避免单请求巨额扣费和溢出回绕 |
| 图片数量、视频时长、token 数 | 用户可控乘数 | 继续使用现有上限，不属于钱包容量问题 |

#### 必须逐项复核

`Redemption.Quota`、充值订单的 quota 中间值、订阅余额购买、`QuotaData`、`UsedataFlow`等字段需按“是单次费用还是累计/发放额度”分类。任何能一次向钱包发放超过 `MaxInt32` 的入口，其 request DTO、decimal 转换、服务参数和数据库字段必须一起扩展；不得在中途使用裸 `int(...)` 窄化。

### 三、余额算术和事务不变量

#### 管理员调额

`ApplyAdminUserQuotaAdjustment` 继续在同一主库事务中：

1. 通过 `lockForUpdate(tx)` 锁定用户行；
2. 读取 `int64` 旧余额；
3. 在加法/减法前使用界限式检查，不先计算再判断；
4. 同时写入 `users.quota` 和不可变 `user_quota_adjustments`；
5. 事务成功后更新 Redis 缓存；
6. 任何一步失败都不得产生部分写入。

安全加法形式：

```text
add:      value <= MaxWalletQuota - previous
subtract: previous >= MinWalletQuota + value
override: MinWalletQuota <= value <= MaxWalletQuota
```

不得使用“`current := previous + value` 后再检查”的方式，因为在边界设置错误时可能先发生 `int64` 回绕。

第一阶段若采用 `MinWalletQuota = math.MinInt32`，则 subtract 导致结果低于该下限时必须拒绝；override 可以将余额精确设置为该下限，但不能设置得更低。本次迁移只扩大正向钱包容量，不扩大负债范围。

#### 消费和退款

1. 单次 charge 先通过现有 `QuotaFrom*Strict/Checked` 边界。
2. 在通过检查后，显式转为 `int64` 与 balance 计算。
3. 预扣、结算、退款仍使用同一 `BillingSession` 生命周期，不得为大额余额新增第二套扣费实现。
4. 余额不足检查使用 `int64 balance` 与 `int64(charge)` 比较。
5. 单次 charge 饱和事件仍写入 `admin_info.quota_saturation`，不得因 balance 扩容而移除。

#### 累计值

`used_quota`、组织 Billing 聚合和批量更新可由多个合法单次 charge 累积而成，所以必须使用 `int64` 累加并检查边界。不能因为每条 `Log.Quota` 是 32 位就用 `int` 接收 `SUM(logs.quota)`。

#### Redis 缓存迁移

1. `UserBase.Quota`、get/set 函数和 Gin context 读取改为 `int64`。
2. `userCacheSchemaVersion` 从 2 提升到 3，作为新旧版本混用的拒绝栅栏，但不把“版本号变化”误当成 quota 已删除。
3. 维护窗口内先停止写入，等待或显式刷新 quota batch store 到主库，再失效用户 hash；未刷盘时删除 Redis 可能丢失余额增量。
4. 增加版本不匹配且旧 hash 仍含 `Quota` 的回归测试，明确返回值、DB fallback、hash 更新和旧 quota 字段的真实行为。
5. 不允许缓存清理绕过 auth-version fence；如改变 Redis key 命名空间，必须同时验证认证限制性更新。

### 四、数据库迁移设计

#### 迁移形式

主实现新建在独立文件，例如：

```text
model/quota_balance_bigint_migration.go
```

`model/main.go` 仅增加不可避免的迁移调用。迁移必须：

- 幂等，重启时不重复改列；
- 在普通 `AutoMigrate` 之前执行，避免模型已改成 `bigint` 但旧表仍是 `int` 时出现不可控的自动改表；
- 使用 GORM Migrator 读取列类型，仅对已存在且仍是 32 位的列执行迁移；
- 对每种数据库显式分支，未识别方言直接失败，不静默跳过。
- 增加 schema readiness check：显式迁移遗漏任一必要列时，不依赖后续 `AutoMigrate` “自动补救”，而是阻止开放大额余额。
- 用三库集成测试实测模型已为 `int64` + `type:bigint` 但旧列仍是 `INT` 时的 `AutoMigrate` 行为、DDL 和锁影响；不以 GORM 推测作为发布证据。

#### PostgreSQL

将相关 `INTEGER` 列改为 `BIGINT`，保留 `NOT NULL` 和 default。类型扩宽前先确认表锁影响和行数。迁移语句使用 PostgreSQL 双引号标识符，不与 MySQL/SQLite SQL 共用。

#### MySQL

将相关 `INT` 列改为有符号 `BIGINT`，完整保留 `NOT NULL` 和 default 属性。不得误改成 `UNSIGNED`，因为当前钱包可能为负余额。

#### SQLite

SQLite `INTEGER` 本身使用有符号 64 位存储，不使用 SQLite 不支持的 `ALTER COLUMN`。迁移分支只验证列存在和数据可读，不为类型名而重建用户或 Token 热表。

#### 迁移前预检

1. 记录三张热表的行数和当前列类型：`users`、`tokens`、`user_quota_adjustments`。
2. 检查当前最大/最小值、NULL 数量和异常负值，不在迁移中自动修数据。
3. 生产数据库完成可验证备份，并实测恢复命令。
4. 停止写入后确认 quota batch store 已完整刷入主库，再主动失效 Redis 用户缓存。清理前 Redis 增量可能领先主库，因此既不把 Redis 当作最终事实源，也不得在未刷盘时直接删除。
5. 确认所有实例版本和数据库迁移节点，避免多个节点同时改表。

### 五、API、前端与配置合同

#### 后端

1. `ManageRequest.Value` 改为 `int64`，后端对 add/subtract/override 都执行最终余额检查。
2. 所有充值、兑换码、订阅转钱包入口在写入前调用同一个 balance 边界，不得各自写一套上限。
3. 返回给前端的 quota 仍保持 JSON number，但 `MaxWalletQuota` 必须小于等于 `Number.MAX_SAFE_INTEGER`。
4. 后端能力端点需返回已固化的 `max_wallet_quota`、`min_wallet_quota` 和 `quota_per_unit`，让前端使用后端权威边界；首版不提供在线修改该上下限的管理设置。
5. 已有 `/api/user/manage` 越界响应保持 HTTP 200 + `success: false` + `message`，避免破坏客户端。以加法式响应字段增加稳定错误码，建议语义名为 `quota_adjustment_out_of_range`，并在 `data` 中返回 `max_wallet_quota`、`min_wallet_quota` 和 `max_allowed_delta`。
6. 新建独立 API 时才可按新合同使用 HTTP 400；不在本次迁移中顺便改写旧管理端点的 HTTP 语义。
7. API Key 上限去掉 `int(1000000000 * QuotaPerUnit)` 的独立逻辑，改为复用后端权威 balance/key 上限及 strict 转换。

#### 前端

1. 调额弹窗使用后端返回的 quota 上下限计算 add/subtract/override 范围。
2. add 模式的最大可输入金额是 `(MaxWalletQuota - currentQuota)` 换算后的显示货币；override 使用总余额上限。
3. 输入及时显示可回复的本地化错误，确认按钮在无效时禁用。
4. 预览只用于交互；后端仍在行锁内以最新余额重新判断，防止并发调额绕过上限。
5. 所有新错误、标签和帮助文案通过 `useTranslation()` 调用，并补齐 en、zh、zh-TW、fr、ja、ru、vi。
6. 钱包和 Key 的 quota number 只在后端声明的安全整数上限内参与 `Math.round`、加减和货币换算；不使用前端自行猜测的 `MaxInt64`。

### 六、实施工作包

#### WP0：边界盘点与产品上限

- 列出所有 quota 字段、Go 类型、数据库类型、写入入口和消费者。
- 将每个字段标记为 charge、balance、aggregate 或 unrelated。
- 确认 `MaxWalletQuota`、`MinWalletQuota`、API Key 额度上限及它们的固定初始化来源。
- 确认 JSON number 的安全范围，以及跨用户 aggregate 超过安全整数时的精确响应合同。
- 检查当前已同步 upstream/目标 RC 是否已有同类 bigint 改动，记录 `User`、`Token`、缓存和计费边界的预期冲突点。
- 评估并在进入 WP1 前记录 balance/charge 分离的 ADR，实施过程仍由本文档跟踪。
- 输出可评审的类型边界清单，未完成前不改模型。

**完成门槛**：每个会写入或累计 quota 的入口都有唯一分类，没有“待定类型”；上限、下限、配置来源和 JSON 精度合同已形成可实施决策。

#### WP1：数据库和模型扩宽

- 新增独立迁移模块和幂等列检测。
- 将已确认的 balance 字段改为 `int64` / `BIGINT`。
- 更新 `UserQuotaAdjustment` 索引与财务聚合接收类型。
- 增加 SQLite、MySQL、PostgreSQL 从旧表结构升级的迁移测试。

**完成门槛**：三库可从 32 位基线升级，旧数据及默认值不变，重复运行迁移无额外 DDL；schema readiness 能识别全部必需宽列，实测证明后续 `AutoMigrate` 不会重复改列或把 `BIGINT` 缩回 `INT`。

#### WP2：钱包、Key、缓存与批量更新

- 更新余额读写 API、Redis 缓存结构和 context 传递类型。
- 批量累加 store 使用 `int64`，保持每个单次 charge 输入仍是已验证 32 位值。
- 修正余额不足判断、余额通知和显示格式化中的隐式窄化。
- 将 Redis cache schema version 从 2 提升到 3，并验证版本不匹配回源、quota hash 保留、auth-version fence 和维护窗口主动失效行为。
- 实现“先停写/刷新 batch store，再失效 Redis”的可验证运维步骤，不直接清理未刷盘 quota。

**完成门槛**：主库和 Redis 往返读写 `2,500,000,000` 以上余额不窄化，缓存关闭时行为一致。

#### WP3：充值、兑换、订阅和管理员调额

- 使用一个权威 balance 边界实现处理所有发放入口。
- 保持管理员调额的行锁、余额写入和调额事实同事务。
- 新增 `QuotaBalanceFromDecimalStrict` 等 fail-closed balance 转换边界，先固化各发放路径的舍入/截断语义，再转 `int64` 并检查业务上下限。
- 清理所有 decimal/float 到 balance 的裸 `int(...)`，尤其是充值、API Key 上限、兑换码和订阅转余额路径。
- 失败时不改用户余额、不写调额事实、不标记充值订单成功。

**完成门槛**：每个发放入口至少有一个超过 `MaxInt32` 的成功用例和一个超过 `MaxWalletQuota` 的无部分写入失败用例。

#### WP4：单次计费安全回归

- 确认 `common.QuotaFrom*`、`PriceData`、`BillingSession`、任务结算和违规费仍保持 32 位单次上限。
- 对每个 balance 扣减边界显式执行 `int -> int64` 扩宽，不允许反向窄化。
- 保留预扣失败、quota saturation 审计、差额结算和任务退款的原有契约。
- 验证 `unlimited_quota=true` 时只跳过 Token 余额不足检查，其 `UsedQuota` 累计仍使用 `int64`，单次 charge 仍受 `MaxChargeQuota` 保护。

**完成门槛**：钱包大于 `MaxInt32` 时，超大单次请求仍在预扣前失败；普通请求扣费、结算和退款数值与迁移前一致。

#### WP5：账单、Invoice 和导出

- SQL `SUM(quota)` 及组织维度结果使用 `int64`。
- 覆盖 SQLite/MySQL/PostgreSQL 主日志库和 ClickHouse 独立日志库；保持 ClickHouse 单条 `quota Int32`，将 `Stat.Quota`、组织 aggregate 及所有 `SUM(quota)` 扫描值改为 `int64`。
- Invoice 当期调额、成功充值、导出时余额和 CSV 金额换算支持 64 位。
- 金额换算继续使用 decimal，不将大额 quota 先转 float 再生成财务结果。
- 保持 Invoice 账期边界、币种、结算因子和导出列合同不变。

**完成门槛**：当期充值和调额合计超过 `MaxInt32` 时，Invoice GET 与 CSV 仍完全一致。

#### WP6：前端和 i18n

- 接入后端权威上下限，不在前端复制 Go 常量。
- 为 add/subtract/override 分别计算有效范围。
- 使用者输入 `5000 USD` 时能看到正确预览并成功提交。
- 超过业务上限时在客户端及时提示，后端仍作最终拒绝。
- 按 `i18n-translate` 技能流程补齐全部语言。

**完成门槛**：组件交互测试覆盖成功、越界、并发后端拒绝和错误文案；i18n 同步、typecheck、lint 和 build 通过。

#### WP7：发布和观测

- 按下文的分阶段发布方案执行。
- 对迁移耗时、DDL 失败、调额失败、余额越界、Redis 解析失败和账单聚合失败建立监控。
- 抽样对账 DB 余额、Redis 余额、调额流水和 Invoice 补充行。

**完成门槛**：观察窗口内没有窄化、负扣费、重复充值、缓存不一致或账单差异。

### 七、测试与验收矩阵

#### 单元和事务测试

1. 零余额 add `2,500,000,000 quota` 成功。
2. 非零余额 add 后精确等于预期，无 float 误差。
3. subtract 和 override 覆盖正数、零、负数下限。
4. 结果超过 `MaxWalletQuota` 时用户和调额表都不写入。
5. 两个并发 add 经过行锁串行化，最终余额和两条流水一致。
6. 一个成功、一个越界的并发调额不产生丢更新或部分流水。
7. Redis 中 `2,500,000,000+` 余额读写、增减和 DB fallback 一致。
8. 批量内多个合法 charge 合计超过 `MaxInt32` 时不回绕。
9. 并发测试使用 goroutine + channel/barrier 精确协调事务到达锁竞争点，不使用 `time.Sleep`、执行耗时断言或概率性竞态。
10. MySQL/PostgreSQL 集成测试验证真实 `FOR UPDATE` 串行化；SQLite 只验证其支持的事务原子性，不声称具有相同行锁语义。

#### 计费回归

1. 大额余额用户的普通文本请求正常预扣和结算。
2. 请求估算大于 `MaxChargeQuota` 时仍在预扣前失败。
3. 任务初始预扣、轮询补扣、失败退款和重试不改变语义。
4. 信任额度、订阅扣费、违规费和 tiered expression 的原有回归通过。
5. 任何 quota clamp 仍能出现在管理日志和后端警告中。
6. unlimited Token 在大额用户钱包下仍累计 64 位 `UsedQuota`，且不放宽单次 charge 上限。

#### 数据库矩阵

| 场景 | SQLite | MySQL | PostgreSQL |
| --- | --- | --- | --- |
| 新库建表为 64 位 balance | 必须 | 必须 | 必须 |
| 旧库 `INT` 升级 | 验证无需重建 | 必须 | 必须 |
| 重复运行迁移 | 必须 | 必须 | 必须 |
| `2,500,000,000` 余额往返 | 必须 | 必须 | 必须 |
| 负余额下限 | 必须 | 必须 | 必须 |
| 并发调额 | 事务语义验证 | 行锁 | 行锁 |
| Invoice 和 `SUM` 大于 32 位 | 必须 | 必须 | 必须 |

ClickHouse 作为独立日志库时额外验证：单条 `quota Int32` 保持不变，`SUM(quota)` 超过 `MaxInt32` 时 `Stat`、Token Bill、Organization Billing 和 Invoice 相关扫描不窄化。

#### 前端验收

1. USD 模式输入 `5000` 显示正确预览并成功。
2. CNY、自定义货币和 TOKENS 模式使用同一 quota 上限反向换算。
3. 当前余额变化后，add 模式的最大可输入值同步变化。
4. 越界、NaN、Infinity、超长小数和负数不会进入后端有效调额。
5. 后端因并发更新拒绝时，弹窗保留用户输入并刷新当前余额。
6. 旧管理端点越界时仍返回 HTTP 200 + `success: false`，前端使用新增稳定 `code` 和 `data.max_allowed_delta` 展示精确提示。

### 八、发布方案

#### 推荐：短维护窗口

这是修改用户和 Token 热表时风险最低的方式。

1. 发布前保持 `MaxWalletQuota = MaxInt32`，新代码已能读写 64 位，但尚未开放大额输入。
2. 停止应用写入或进入维护模式，等待正在进行的请求和异步结算完成。
3. 执行并验证数据库备份。
4. 单节点执行显式 bigint 迁移，记录每个列的迁移前后类型。
5. 部署已支持 64 位 balance 但仍使用旧业务上限的版本。
6. 确认 quota batch store 已刷入主库，再主动失效旧 Redis 用户缓存；验证 schema version 3、auth-version fence 和 DB 回源后，做小额调额、扣费、退款和 Invoice 冒烟。
7. 恢复流量，保持旧上限观察一个完整业务周期。
8. 在第二次独立发布中提高 `MaxWalletQuota`，开放 `5000 USD` 调额，并完成大额实际验收。

#### 零停机备选

如必须滚动发布，需要额外拆为两个兼容版本：

1. **兼容版**：Go 读取和中间传播改为 `int64`，仍只写 `MaxInt32` 范围，不开放前端。
2. 所有实例升级兼容版后，由单独迁移任务扩宽数据库列。
3. **开放版**：所有列验证为 bigint 后才提高后端上限和前端输入上限。
4. 开放版启动时必须做 schema readiness check；任意必要列仍是 32 位时拒绝开启大额余额。

零停机方案必须验证旧实例不会在重启 `AutoMigrate` 时尝试把 `BIGINT` 改回 `INT`。在未证明该点前，不采用混合版本长时间运行。

### 九、回滚、停止条件和恢复

#### 回滚边界

- 数据库从 `INT` 扩展到 `BIGINT` 本身不破坏旧数据，在尚未写入超过 32 位的值时，可回滚应用且保留宽列。
- 一旦任何 balance 字段已写入超过 `MaxInt32` 的值，旧应用就不再是安全回滚目标，不得直接降级列或启动旧版本。
- 该时只能关闭新的大额写入开关，保留 64 位读写版本，再修复业务问题。
- 不通过截断、饱和或拆分用户余额来强行回到 32 位。

#### 立即停止发布的条件

1. 任一数据库的必要列未完成 bigint 迁移。
2. 数据库余额、Redis 余额和 API 返回值不一致。
3. 出现负扣费、超额充值被标记成功、调额部分写入或退款重复。
4. Invoice GET、CSV 或充值流水与钱包变化无法对账。
5. 重启时仍产生重复 DDL 或尝试缩小列类型。

## 不采用的修复方式

1. **删除 `MaxInt32` 检查**：MySQL/PostgreSQL 仍会在 `INT` 列写入时失败，SQLite 则形成数据库分叉。
2. **将 `common.MaxQuota` 直接改为 `MaxInt64`**：会放宽单次计费上限，破坏预扣和 quota saturation 安全不变量。
3. **把 `QuotaPerUnit` 改小**：会改变全站已有余额的货币价值和计费换算，不是存储扩容。
4. **拆成多次添加**：最终余额仍会超过 32 位上限。
5. **只改 `users.quota`**：API Key、Redis、调额流水、批量累加和账单仍可窄化，会把显性错误变成难发现的账务不一致。
6. **只依赖 `AutoMigrate`**：不能充分控制三种数据库的热表改列、锁影响、幂等性和回滚门槛。
