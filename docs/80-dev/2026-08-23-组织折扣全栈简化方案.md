# 组织折扣全栈简化方案

## 问题与目标

### 问题

当前组织计费功能以“合同”为核心，包含合同名称、组织全局倍率、渠道倍率、创建与归档、当前合同与历史合同、预览接口及成员只读入口。实现已经扩散到数据模型、路由、计费快照、同步与异步结算、日志和前端页面。

这些生命周期和展示概念并不是当前业务所需。真正需要保留的业务能力只有：系统管理员为组织配置按渠道独立的折扣，计费请求固定使用开始时的折扣事实，并保留不可变历史供审计。

### 目标

1. 全栈移除用户可见及代码领域中的“合同”概念，统一改为“组织折扣”。
2. 每个组织只有一份当前折扣配置；折扣按渠道独立配置，未配置渠道按 `1.0`。
3. 保留现有全局渠道倍率，不新增组织全局倍率；组织折扣只作为现有计费链路上的额外渠道级乘数。
4. 管理员批量修改后一次保存、原子生效；旧配置以不可变快照保留。
5. 请求开始时固定折扣快照，异步完成、渠道重试和后续改价均不得改变该请求的计费结果。
6. 在满足计费正确性的前提下执行最小入侵改造：主实现进入新的专用模块，现有上游文件只保留必要字段、注册和调用点调整。

### 非目标

- 不支持组织所有者或成员查看、创建或修改折扣。
- 不支持组织全局折扣、免费倍率 `0`、组织层加价、草稿、预约生效、归档或恢复。
- 不强制管理员填写变更原因。
- 不修改现有全局渠道倍率、用户组倍率、充值价格或 Invoice 聚合口径。
- 不迁移现有合同及合同历史；当前数据均为测试数据，不建立兼容 API 或双轨模型。

### 已确认产品决策

| 决策点 | 结论 |
| --- | --- |
| 领域名称 | 仅使用“组织折扣”，全栈删除“合同”概念 |
| 配置粒度 | 每个渠道独立折扣；未配置为 `1.0` |
| 既有倍率 | 全局渠道倍率保持不变 |
| 权限 | 仅 Root 可查看和修改折扣及历史；普通 Admin 不具备折扣权限 |
| 修改方式 | 多项编辑后整批保存、原子生效 |
| 历史 | 保存完整、不可变快照；不可编辑、删除、归档或恢复 |
| 审计字段 | 自动记录操作人、时间和变更前后；原因非必填 |
| 倍率范围 | `0 < ratio <= 1`；`0.8` 表示按原价的 80% 计费 |
| 请求一致性 | 首次计费解析时一次性加载完整快照；异步任务和重试继续使用同一快照，不再按渠道查库 |
| 并发 | 使用当前快照 ID 作为乐观锁令牌；过期提交返回冲突，不允许静默覆盖 |
| 预扣 | 按未打折价格预扣，渠道确定后按实际折扣结算差额 |
| 旧数据 | 仅测试数据，不迁移，不保留兼容层 |

## 优化方案

### 1. 最小入侵原则

1. 新的组织折扣主实现分别放入专用文件或模块，例如：
   - `model/organization_discount.go`
   - `service/organization_discount.go`
   - `controller/organization_discount.go`
   - `web/src/features/organizations/discount-api.ts`
   - `web/src/features/organizations/discount-types.ts`
   - `web/src/features/organizations/discount-panel.tsx`
2. 现有核心文件只允许做不可避免的窄改动：模型注册、字段接入、路由注册、快照传递和单一调用点替换；不重构任务框架、渠道适配器或全局倍率系统。账务完整性复审只将现有 `BillingSession` 的资金与令牌预扣合并为一个事务，不改计价公式或生命周期。
3. 当前专用于合同的新增文件直接删除或由新的折扣模块替代，不保留 `Contract` 到 `Discount` 的别名、适配器、废弃接口或兼容 DTO。
4. 沿用现有计费基础设施：`BillingSession`、`PriceData`、任务计费上下文、quota 饱和保护和日志生成入口保持唯一权威实现。
5. 保持 Router → Controller → Service → Model 分层；折扣规则不得下沉到渠道适配器，也不得散落在各计费格式中。
6. 不在应用启动的通用 `AutoMigrate` 中自动删除旧表。旧合同测试表由明确的开发/测试清理步骤移除，避免把破坏性删除带入正常启动路径。
7. 改造完成后，组织计费在核心链路中的字段、分支和数据库查询数量必须低于当前合同实现；删除渠道二次查库、补扣交互和 `ContractChannelBaseQuota` 跨层传递，不以等量重命名冒充简化。

### 2. 目标领域模型

业务上只有“当前组织折扣配置”，数据库使用追加式快照保存事实：

```text
Organization
└── CurrentDiscountSnapshotId

OrganizationDiscountSnapshot
├── Id
├── OrganizationId
├── ChannelDiscounts
├── CreatedBy
└── CreatedAt
```

删除以下合同字段和状态机：

- `Name`
- `Status`
- `GlobalRatioScaled`
- `EffectiveFrom`
- `EffectiveTo`
- `ActiveContractId`
- active/archived 状态及归档操作

`Organization.CurrentDiscountSnapshotId` 是当前配置的唯一权威，同时也是乐观锁令牌。历史表不设置独立版本号、可变状态和 `UpdatedAt`，任何修改只能追加新快照；历史按 `Id DESC` 分页。

### 3. 折扣快照存储

为减少模型和事务分支，`ChannelDiscounts` 使用跨数据库兼容的 `TEXT` 保存完整 JSON 映射，键为渠道 ID，值为定点整数倍率：

```json
{
  "12": 800000,
  "35": 950000
}
```

规则：

- 缩放基数固定为 `1_000_000`，避免 SQLite、MySQL 和 PostgreSQL 的浮点差异。
- 所有 JSON 编解码使用 `common.Marshal` / `common.UnmarshalJsonStr`，不得直接调用 `encoding/json`。
- 输入倍率必须可精确转换到最多六位小数；禁止静默截断超出精度的输入。
- `1.0` 在保存时归一化为未配置，减少冗余；空映射表示组织没有渠道折扣。
- 保存前统一校验渠道 ID 为正数、渠道真实存在、无重复项且倍率位于 `(0, 1]`。
- 序列化后的 JSON 不得超过 MySQL `TEXT` 的 65,535 字节上限；超过时以 `400` 拒绝，不得依赖数据库截断。
- `TEXT` JSON 属于新存储路径，必须验证整数键 map、空 map、损坏 JSON 失败关闭和三数据库实际建表/读取行为；当前只能判定为低风险，不能视为天然无风险。
- 快照表为 `organization_id` 建普通索引；主键 `Id` 同时承担历史顺序和并发令牌，不再增加组织与版本号的复合唯一索引。

### 4. 批量保存与乐观锁

折扣更新使用完整替换语义，不提供单渠道即时写接口。建议请求体：

```json
{
  "expected_snapshot_id": 21,
  "channel_discounts": [
    { "channel_id": 12, "ratio": "0.8" },
    { "channel_id": 35, "ratio": "0.95" }
  ]
}
```

单个数据库事务内完成：

1. 创建新的完整快照，取得新快照 ID。
2. 使用 `WHERE id = organization_id AND current_discount_snapshot_id = expected_snapshot_id` 条件更新组织当前指针。
3. `RowsAffected != 1` 时回滚新快照并返回 `409 Conflict`。
4. 条件更新成功时提交事务，新快照成为当前配置。

首次保存使用 `expected_snapshot_id = 0`。不得先更新旧快照、逐渠道生效或在事务外切换当前指针。该方案不依赖三种数据库各不相同的重复键错误归一化，只以条件更新的 `RowsAffected` 判定冲突。

### 5. 管理 API

只保留四个 Root 管理接口：

```text
GET /api/admin/organizations/:id/discount
PUT /api/admin/organizations/:id/discount
GET /api/admin/organizations/:id/discount/history
GET /api/admin/organizations/:id/discount/channel-options
```

四个接口不得直接沿用现有 `/api/admin/organizations` 的 `AdminAuth()` 路由组，必须注册为独立的 Root 子域：

```go
discountRoute := apiRouter.Group("/admin/organizations/:id/discount")
discountRoute.Use(middleware.RootAuth())
```

现有组织管理接口继续使用 `AdminAuth()`，只把折扣接口和前端折扣页签收紧到 Root。

接口约束：

- `GET discount`：没有快照时返回 `snapshot_id: 0` 和空折扣集合。
- `PUT discount`：接收完整集合并生成新快照；空集合用于清除全部组织折扣。
- `GET history`：分页返回不可变快照、操作人和时间；每份快照与同组织上一份快照比较后派生变更，不单独维护第二套事件日志。
- `GET channel-options`：从全局渠道表返回轻量选项，不依赖消费日志或账单聚合。
- 历史分页必须额外读取当前页最旧记录的上一份快照，避免把分页边界误判为空配置；只有组织的第一份快照以空配置作为变更前状态。
- `400` 表示渠道或倍率无效，`403` 表示非 Root，`404` 表示组织不存在，`409` 表示乐观锁冲突。
- 删除当前组织成员合同 API、合同预览、合同创建、合同归档及合同历史接口。

### 6. 管理界面

组织管理详情中将“合同”页签替换为“折扣”，不再提供独立的组织成员合同路由。

主区域只包含：

- 当前渠道折扣列表；
- 添加渠道；
- 修改倍率；
- 删除渠道折扣；
- 统一“保存”按钮；
- 未保存修改提示和提交中状态。

历史放在次要区域或抽屉中，只展示保存时间、操作人和派生的渠道变更，不展示合同名称、合同状态、激活、归档或恢复操作。`snapshot_id` 只作为提交令牌和问题排查字段，不作为页面重点。

折扣页签必须按 Root 角色隐藏；普通 Admin 即使手工请求折扣 API 也必须得到 `403`。

所有新增文案必须使用 `useTranslation()` 和 `t()`，并通过项目 i18n 工具补齐 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。

### 7. 请求计费流程

最终计费关系保持为：

```text
现有基础计费 × 现有全局渠道倍率 × 组织渠道折扣
```

组织折扣流程：

1. 请求首次进入计费解析时，通过组织当前指针一次性读取并解析完整折扣快照，将快照 ID 和渠道折扣 map 固定在 `PriceData`；没有快照时显式记为已解析且折扣为 `1.0`。
2. 渠道确定后只从请求内存快照 map 查找倍率；未配置时返回 `1.0`，不得再次访问数据库。
3. `PriceData.QuotaToPreConsume` 表示未应用组织折扣的准入/预扣额度，`PriceData.Quota` 表示应用实际渠道折扣后的最终额度。
4. 时长、分辨率等 `OtherRatios` 必须分别作用于 `QuotaToPreConsume` 和 `Quota`，两者不得从彼此反推，避免舍入和重算漂移。
5. 使用 `QuotaToPreConsume` 创建 `BillingSession`，使用 `Quota` 结算并退回差额。
6. 不使用 `BillingSession` 的旧 MJ 路径使用 `QuotaToPreConsume` 做余额准入检查，成功后只按 `Quota` 实际扣费和记账。
7. 渠道重试只查同一内存快照 map 中的新渠道倍率，不重新读取组织当前快照。
8. 管理员在请求期间保存新折扣，只影响之后首次解析计费的请求。

由于组织折扣严格不大于 `1.0`，渠道确定后的目标费用不会超过未打折预扣额，不新增组织折扣专用补扣路径，并删除 `ContractChannelBaseQuota`。已接受的取舍是：用户额度低于未打折预扣额时，即使额度足够支付折后费用，请求仍可能被拒绝。

### 8. 异步任务、重试与退款

- `TaskBillingContext` 使用组织折扣快照命名，只持久化快照 ID、实际渠道 ID 和已应用倍率，不把完整渠道 map 写入任务数据。
- 异步提交前若已确定渠道，同时固化实际折扣；轮询结算、失败退款和差额日志只使用提交时事实。
- 重试切换渠道时仍从原请求快照解析新渠道折扣，不读取最新组织配置。
- Midjourney、统一异步任务和 token 差额路径继续复用现有资金来源、令牌、分组倍率和退款逻辑，仅替换组织折扣乘数与快照字段。
- 首次加载或解析快照失败必须阻断请求，不得降级成默认 `1.0`；首次加载成功后，渠道选择、重试、结算和退款不得再依赖折扣数据库读取。

### 9. 日志与账单审计

`Log.Quota` 继续记录已经应用组织折扣的最终消费额度，Invoice 继续直接聚合 `Log.Quota`，不得再次应用折扣。

管理员日志从 `admin_info.contract` 改为：

```json
{
  "organization_discount": {
    "snapshot_id": 21,
    "channel_id": 12,
    "ratio": "0.8"
  }
}
```

账单正确性的唯一依据是请求固定的快照和实际应用倍率，不依赖当前组织配置。组织用户不获得折扣配置与历史接口，只看到现有账单最终结果。

### 10. 文件级改造边界

| 类型 | 允许动作 | 禁止动作 |
| --- | --- | --- |
| 新折扣模块 | 在新文件中承载校验、快照、API、前端表单与历史主逻辑 | 把主逻辑继续堆进 `organization.go`、`quota.go` 或组织巨型页面 |
| 现有核心计费文件 | 替换快照字段、复用 `QuotaToPreConsume`/`Quota` 双值、调用新的 service、移除合同乘数 | 新增第三个 quota 字段、重写 BillingSession、重排计费层级、顺带统一其他倍率系统 |
| 现有组织模型/迁移 | 增加当前折扣快照指针并注册新模型 | 引入生产数据兼容分支或启动时自动删除旧表 |
| 现有路由 | 删除旧合同路由，注册独立 `RootAuth()` 折扣路由组 | 把折扣接口留在现有 `AdminAuth()` 组织组，或同时保留合同与折扣两套 API |
| 前端组织管理 | 增加一个折扣页签接入点，主页面逻辑留在新组件 | 重构整个组织管理页面或替换其他页签 |
| 合同专用文件 | 确认无引用后删除 | 保留重定向、别名或无调用代码 |

### 11. 实施工作包

#### A. 模型与事务

- 新增不可变组织折扣快照模型和精确倍率解析。
- 增加组织当前快照指针。
- 实现完整保存、当前读取、携带跨页前态的历史分页和内存 map 解析。
- 覆盖空配置、重复渠道、无效渠道、倍率边界、原子提交和乐观锁冲突。

#### B. 计费快照替换

- 将 `OrganizationContractSnapshot` 替换为 `OrganizationDiscountSnapshot`。
- 删除组织全局倍率，只保留渠道折扣。
- 使用 `QuotaToPreConsume` 保存未打折额度、`Quota` 保存折后最终额度；不得新增第三个共享 quota 字段。
- 首次解析加载完整 map，删除渠道确定阶段的数据库查询、Reserve 补扣和 `ContractChannelBaseQuota`。
- 接入普通请求、分层计费、WebSocket、任务、Midjourney、退款和日志路径。
- 验证同一请求跨重试使用同一快照，且组织折扣只乘一次。

#### C. 管理 API 与权限

- 新增独立挂载 `RootAuth()` 的四个 Root-only API（当前折扣、整批保存、历史、渠道选项）。
- 删除当前组织合同接口、预览、创建和归档接口。
- 增加权限、错误码、完整替换和冲突行为测试。

#### D. 前端替换

- 新增独立折扣 API、类型和面板文件。
- 组织管理页只增加最小页签接入。
- 删除合同路由、合同面板、合同 API/类型及侧边栏入口。
- 补齐七语言翻译、保存冲突提示、未保存状态和只读历史。

#### E. 清理与事实文档同步

- 全仓搜索并清除业务代码中的 `contract`、`ContractSnapshot`、合同 API 路径和合同 i18n 文案。
- 删除无调用测试和合同专用测试，替换为直接保护组织折扣计费契约的回归测试。

## 验证与验收

### 后端行为测试

必须直接保护以下契约：

1. 无组织或无折扣快照时倍率为 `1.0`。
2. 未配置渠道时倍率为 `1.0`；已配置渠道使用精确倍率。
3. `0`、负数、`>1`、超精度、重复渠道和不存在渠道被拒绝。
4. 批量保存要么全部生效，要么全部回滚。
5. 两个 Root 基于同一 `expected_snapshot_id` 提交时，只允许一个成功，失败事务不得残留历史快照。
6. 请求开始后修改折扣，不改变该请求及其重试、异步结算或退款。
7. 普通请求和按次任务均使用 `QuotaToPreConsume` 预扣、`Quota` 结算；`OtherRatios` 对两个值一致生效。
8. 旧 MJ 路径按未打折额度做准入检查，但只扣除和记录折后额度。
9. 首次加载完整 map 后，渠道选择、重试和结算不再查询折扣数据库。
10. 历史分页边界仍能取得真实前态，只有第一份快照以前态为空配置。
11. 全局渠道倍率继续生效，组织折扣恰好乘一次。
12. `Log.Quota`、任务日志和管理员审计字段使用同一个最终倍率事实。
13. 首次数据库加载或 JSON 解析失败不能降级为无折扣。
14. 普通 Admin 无法看到折扣页签，直接请求四个接口得到 `403`。

新建或重写的 Go 测试使用 `testify/require` 和 `testify/assert`，不添加只验证内部常量或文件布局的测试。

## 风险与约束

| 风险 | 控制措施 |
| --- | --- |
| 只改名称但残留两套计费语义 | 以新折扣快照为唯一实现；切换完成后删除合同模块和兼容字段 |
| 请求期间改价导致账单漂移 | 请求开始固定快照；日志和异步上下文持久化实际倍率 |
| 并发保存丢失修改 | 以 `expected_snapshot_id` 条件更新当前指针，`RowsAffected != 1` 时整体回滚 |
| 渠道重试重复叠加折扣 | 每次从未应用组织折扣的请求基准计算，复用同一内存快照 map |
| 按次预扣与最终扣费混用 | 复用 `QuotaToPreConsume`/`Quota` 双值并对 `OtherRatios` 做成对回归测试 |
| TEXT 容量或 JSON 兼容问题 | 保存前限制为 65,535 字节并执行三数据库、整数键 map 和损坏 JSON 测试 |
| 普通 Admin 获得改价权限 | 折扣路由独立挂 `RootAuth()`，前端按 Root 隐藏页签并增加 403 测试 |
| 预扣高于折后费用导致请求被提前拒绝 | 已接受的简化取舍；不得改为不安全的最低折扣预扣 |
| quota 转换溢出或精度漂移 | 倍率使用定点整数；quota 转换继续使用 `common.QuotaFrom*Checked` 系列 |
| 工作树已有未提交改动被覆盖 | 只修改明确相关文件；实施前后逐文件审查 diff，不执行 reset/checkout |
| 旧测试表残留 | 不影响运行；由明确的测试环境清理步骤处理，不加入启动时破坏性迁移 |
