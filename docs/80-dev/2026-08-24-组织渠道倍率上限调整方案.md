# 组织渠道倍率上限调整方案

## 问题与目标

当前组织渠道折扣仅允许 `(0, 1]`。业务需要允许倍率超过 `1`，用于组织渠道加价，同时继续满足：

1. 最终账单准确，折扣、加价、重试和异步恢复使用同一请求快照；
2. 未配置渠道仍按 `1.0`；
3. 全局渠道倍率保持不变，组织倍率仍是现有计费结果上的额外乘数；
4. 只复用 new-api 现有预扣、`BillingSession.Reserve` 和结算机制，不建立第二套账务逻辑；
5. 保持最小入侵，不恢复合同、组织全局倍率或渠道二次查库。

## 已确认口径

| 项目 | 口径 |
| --- | --- |
| 有效范围 | `0 < ratio < 10` |
| 最大可保存值 | `9.999999`，继续保留六位小数精度 |
| 默认值 | 未配置和显式 `1.0` 都按 `1.0`，保存时继续归一化为未配置 |
| 示例 | `0.8` 按原价的 80% 收费；`1.5` 按原价的 150% 收费 |
| 最终计费 | `现有实际费用 × 组织渠道倍率` |
| 全局倍率 | 保持现有计算和配置，不修改、不替换 |
| 权限 | 仅 Root 可查看和修改 |
| 历史 | 继续保存不可变快照，不提供恢复、修改或删除 |
| 信任额度 | 保持 new-api 现有钱包信任旁路；最终仍按实际费用结算 |
| MJ | 当前未使用，不纳入本次实施与验收 |

倍率超过 `1` 后，产品含义已经同时包含折扣和加价。为避免大范围重命名，后端模型、接口和快照字段继续使用现有 `discount` 命名；管理界面应将倍率含义写清楚，不开展领域模型重构。

## 当前实际情况

现有最终结算公式和 quota 安全转换可以处理大于 `1` 的正倍率，快照使用 `1_000_000` 定点整数和 `TEXT` JSON，保存 `9.999999` 不需要修改数据库结构或迁移数据。

需要修正的是原方案的预扣前提：倍率不大于 `1` 时，组织倍率本身不会额外扩大预估费用；倍率大于 `1` 后，只按原价预扣会产生一个已知的组织加价缺口，可能让有限额度令牌或订阅在结算时额度不足，使结算记录持续待处理。预扣仍然只是对已知费用的估算；客户端未提供 `max_tokens` 或实际用量超过估算等既有差额，继续由 new-api 原有结算处理，不在本次扩展范围内。

统一任务存在跨渠道重试：首次尝试预扣后，后续尝试会重新选择渠道、重新钉住组织倍率并重算价格，但当前不会再次进入首次预扣分支。因此任务从低倍率渠道重试到高倍率渠道时，也必须通过现有 `BillingSession.Reserve` 补足更高的已知预扣目标。

## 优化方案

### 1. 统一倍率校验

修改 `model/organization_discount.go` 中唯一的倍率边界：

- 定点整数有效范围改为 `1..9_999_999`；
- `ParseOrganizationDiscountRatio`、保存校验和快照反序列化共同使用该边界；
- 拒绝 `0`、负数、`10` 及更大值，以及无法精确表示为百万分之一的输入；
- 损坏或越界快照继续失败关闭，不降级为 `1.0`；
- `1.0` 继续归一化为未配置。

“六位小数”指倍率必须能精确表示为 `1 / 1_000_000` 的整数倍，而不是单纯限制输入字符串长度。后端可接受不改变数值的尾随零，例如 `9.9999990`；前端表单保持最多六位小数的规范化输入格式。两端执行相同数值边界，后端仍是最终权威。

前端输入框上限设为 `9.999999`，提交前验证 `(0, 10)` 和规范化输入格式，并更新所有语言的验证提示。

### 2. 统一预扣不变量

非信任会话与强制预扣任务采用两个清晰公式：

```text
预扣目标 = 未应用组织倍率的预估费用 × max(1, 当前渠道组织倍率)
最终费用 = 实际费用 × 当前渠道组织倍率
```

含义如下：

- 倍率小于等于 `1`：继续按原价预扣，结算时退回折扣差额；
- 倍率大于 `1`：按加价后的预估金额预扣；
- 最终费用始终按实际用量计算，不以预扣金额作为账单事实；
- 预扣目标只覆盖渠道确定时已知的组织加价，不承诺覆盖未知实际用量。

钱包信任用户保持 new-api 现有语义：命中信任旁路后不执行实际预扣，`Reserve` 也不补扣，最终仍由既有结算 journal 按实际费用扣费。该例外只适用于同步钱包信任会话；订阅不使用信任旁路，统一任务设置 `ForcePreConsume` 后也不使用信任旁路。接受的业务取舍是组织倍率可能把信任钱包的授信敞口放大到接近 10 倍，但不改变最终账单金额。

所有 quota 乘法和整数转换继续使用 `common.QuotaFrom*Checked` 或相应严格转换入口，保留现有溢出阻断与审计标记，不新增本地转换函数。

### 3. 同步请求的最窄接入

请求开始时仍只加载一次完整组织折扣快照。渠道确定后：

1. 从请求内存快照读取当前渠道倍率，不访问数据库；
2. 从未应用组织倍率的预估额度计算预扣目标；
3. 仅当目标高于当前预扣时，调用现有 `BillingSession.Reserve`；
4. Reserve 失败则在调用上游前拒绝请求；
5. 请求完成后仍由现有 `BillingSession.Settle` 按实际费用结算，多退少补。

不得新增组织折扣专用资金操作、补扣表或恢复器，也不得修改 `BillingSession` 的结算公式。

非分层同步请求的唯一接点固定在 `controller/relay.go` 中 `ApplyOrganizationDiscountForChannel` 之后、调用上游之前；WSS 经过同一接点，不在 WSS 内增加第二套逻辑。

分层计费继续使用已有的 `PrepareTieredBillingForSelectedGroup` Reserve 入口，只把组织倍率纳入该入口的目标额度。非分层接点必须跳过分层请求，确保同一目标不会被两条路径重复计算或 Reserve。

渠道重试时必须始终从未应用组织倍率的原始预估基数计算新目标，不得在上一次倍率结果上继续相乘。`BillingSession.Reserve` 只补足更高目标；最终按实际成功渠道和固定快照结算，多余预扣由现有结算退回。

### 4. 统一任务跨渠道重试

统一任务在每次上游尝试前都已确定渠道。保持 `ModelPriceHelperPerCall` 的共享计价职责不变，在 `relay/relay_task.go` 现有价格计算和 `OtherRatios` 应用完成后，计算当前尝试的预扣目标：

```text
Quota             = 应用组织倍率后的最终额度
target            = max(未应用组织倍率的预估额度, Quota)
```

在现有预扣判断处执行：

```text
Billing == nil  → PreConsume(target)
Billing != nil  → Billing.Reserve(target)
```

首次尝试仍只创建一个 `BillingSession`；跨渠道重试只补足更高目标，不重复创建会话。倍率降低时不立即退款，最终由 `Settle` 按实际成功渠道多退少补。目标始终从本次尝试未应用组织倍率的预估额度计算，不得在上一次渠道结果上继续相乘。

该修改只落在统一任务现有预扣分支，不改变共享 `ModelPriceHelperPerCall` 的预扣语义，不新增第三个额度字段，不改任务提交、结算 journal、退款或扫尾恢复。

### 5. MJ 明确排除

MJ 当前完全未使用，不纳入本次实施和验收：

- 不修改 `relay/mjproxy_handler.go`；
- 不增加 MJ Reserve、倍率用例或回归测试；
- 不为 MJ 调整共享按次计费 helper；
- 不以 MJ 为理由增加字段、兼容分支或抽象。

倍率值域属于组织配置的统一规则，因此共享快照解析仍会接受大于 `1` 的倍率；这不代表本次承诺 MJ 预扣行为。未来重新启用 MJ 前，必须单独复审其完整计费链路。

### 6. 管理界面

管理界面保留现有整批保存与乐观锁。最小修改包括：

- 接受 `0.000001` 到 `9.999999`；
- 输入 `10`、非数字或精度超限时禁止保存，并显示明确错误；
- 在字段说明中展示 `0.8` 和 `1.5` 的计费示例，避免把加价误解为折扣；
- 不改变历史、操作人、渠道选择和 Root-only 权限结构。

## 验证要求

### 倍率边界

- `0.000001`、`1`、`1.000001`、`1.5`、`9.999999` 可以保存并正确读取；
- `0`、负数、`10`、大于 `10`、无法精确表示为百万分之一的数值和非数字被拒绝；
- 后端接受不改变数值的尾随零，前端保持最多六位小数的规范化输入；
- `1.0` 仍被归一化为未配置；
- 越界快照读取返回错误，不按原价静默计费。

### 计费正确性

- 普通、分层、WSS 和统一任务对 `0.8`、`1`、`1.5` 都得到正确最终 quota；
- 非信任同步会话和强制预扣任务在上游调用前覆盖已知组织加价；
- 有限额度令牌和订阅不会因为已知加价差额在结算期才首次发现额度不足；
- 同步请求和统一任务跨渠道重试都会补足更高目标，不会重复叠加组织倍率，最终账单只采用实际成功渠道的固定快照倍率；
- 钱包信任会话继续免预扣，最终仍完整结算实际费用；
- `Log.Quota` 保存最终费用，Invoice 直接聚合且不二次乘倍率；
- 异步失败退款和结算恢复继续使用提交时固定的倍率事实。

## 完成标准

1. 全栈统一执行 `(0, 10)` 数值边界，前端只额外约束规范化输入格式；
2. 除既有钱包信任旁路外，倍率超过 `1` 时，预扣在调用上游前覆盖已知的组织加价；
3. 统一任务从低倍率渠道重试到高倍率渠道时复用现有 Reserve 补足目标；
4. 最终账单仍由现有实际结算和日志唯一确定；
5. MJ 未被修改，也不作为本次完成条件；
6. 没有新增合同、补扣系统、兼容层、数据库迁移、quota 字段或异步状态机；
7. 相关测试、构建、i18n 和三数据库验证通过后，才能把本文状态改为 `done`。
