# 豆包视频南向协议扩展方案

## 问题与目标

当前豆包 Seedance 视频任务的南向实现固定使用火山方舟任务协议。需要增加 OpenAI Videos 兼容协议，使同一模型能够同时配置直连方舟渠道和提供 `/v1/videos` 的兼容上游渠道。

另一个已明确的问题是媒体下载出口：用户部署链路为“HK 本服务 → NGINX → 上游”，上游禁止 HK IP 访问。渠道 API 地址指向 NGINX 后，创建和查询任务可经 NGINX 转发，但下载上游返回的 `content.video_url` 时未经过该 NGINX。该运行现象来自用户反馈；代码路径已静态核对，尚未检查实际部署配置或抓取网络证据。

北向指客户端到本网关，南向指本网关到上游服务。本方案保持现有北向路由和已有合法请求的兼容行为，由渠道配置决定南向协议，以独立本地扩展和必要接线满足 new-api 最小入侵要求。文件输入等新增能力不默认承诺，按第 4 节的合同与范围决策处理。

本方案将“视频南向协议”和“媒体下载出口”作为两个独立能力设计。媒体出口采用渠道级可选开关，复用渠道 API 地址作为 NGINX 媒体转发入口的基址；解决当前下载问题无需等待整个 Videos 南向扩展完成。这里的 NGINX 位于本服务的出站链路，不是客户端到本服务的入口代理；HK/SG 入口按模型分流不作为本问题的修复方案。

本次仅记录方案，不代表功能已实现、上游兼容性已验证或部署已完成。

目标：

- 新建和编辑豆包相关渠道时可以选择“视频上游协议”。
- 未配置的新旧渠道继续使用火山方舟原生协议。
- 创建、查询、结果解析、视频下载和用量提取采用一致的南向合同。
- 已提交任务固定使用提交成功时的协议，后续渠道设置变更不改变该任务的协议。
- 渠道编辑提供默认关闭的“视频下载经渠道 API 地址转发”开关；未启用时保持现有下载行为。
- 启用媒体转发后，独立视频资源及其重定向请求均经 NGINX 访问，转发失败不回退 HK 直连。
- 原始媒体 URL 保留在任务中；下载时使用渠道当前的媒体转发配置，使历史任务也能受益。
- 复用现有任务插件、配置存储和任务状态机制，不新增渠道类型或数据库列。

## 优化方案

### 1. 渠道级“视频上游协议”配置

建议在现有渠道 `setting` JSON 内增加：

```json
{
  "video_upstream_protocol": "openai_video"
}
```

| 值               | 界面文案                   | 行为                                                           |
| ---------------- | -------------------------- | -------------------------------------------------------------- |
| 未设置或空值     | 火山方舟原生               | 兼容历史渠道，规范化为`ark`                                  |
| `ark`          | 火山方舟原生               | 调用方舟任务接口                                               |
| `openai_video` | OpenAI Videos 兼容（预留） | 后续调用已确认合同的 Videos 上游；当前保存与新任务提交拒绝此值 |

配置只影响该渠道的视频任务，不改变聊天、图片等其他能力。首期在豆包视频、火山引擎渠道，以及绑定 `doubao` 的任务插件渠道中按适用条件展示；后端同时校验渠道与协议组合。未知非空值应明确拒绝，不能静默降级为方舟协议。

前端使用新增独立选择组件，现有渠道表单只增加字段接入、回填和序列化。需覆盖创建、编辑、复制渠道及类型切换后的字段处理，避免丢失设置或携带无效配置。新增文案按项目 i18n 规范覆盖所有语言。

选择依据是上游合同，而非模型名称、域名或北向请求路径。不要在业务请求失败后自动切换协议再次提交，避免重复任务及重复费用。

### 2. 一个插件身份，两个南向实现

```text
北向 Videos / Responses / 豆包原生 / 旧版通用入口
                         ↓
                 现有 doubao 插件身份
                         ↓
               选定渠道的视频上游协议
                   ↙             ↘
              方舟原生          Videos 兼容
                         ↓
               现有任务持久化、轮询和结算
```

优先采用新增完整本地覆盖插件，继续使用 `doubao` key，通过现有覆盖机制发布。插件的主体转换逻辑放在新文件中，保留原有项目身份和作者归属。允许为隔离本地能力保留适度重复，不改造内置 Sora 插件，也不引入 JS 动态模块加载。

同 key 覆盖作用于整个插件身份，不能只保留新协议：覆盖插件必须同时保留原生模式和现有北向合同。发布时需确认覆盖开关、版本和各运行节点的一致性；兼容模式未安装或未激活时应拒绝启用或使用该模式，不能继续按原生协议发送。

不推荐新增同时声明相同 Seedance 模型的第二个插件。在保留现有模型名、渠道类型和北向入口的前提下，同 key 本地覆盖可以复用现有扩展机制，减少宿主改动；这是本方案的工程选择，不宣称其为代码机制上的唯一解。

路由约束应准确区分：模型索引中的大小写冲突检查不能解释成“所有插件的同名模型都硬拒绝”；共享协议绑定另有检查及 `legacyProviders` 兼容分支。第二个插件仍需面对渠道类型、原生路由和协议归属等约束。本方案不为绕过这些约束修改路由规则或新增渠道类型，也不把现有兼容分支当作引入平行实现的理由。

组件隔离不要求拆成两个注册插件。协议转换集中在新增完整本地覆盖文件中，原内置文件保留；允许适度重复，但不为拆文件新增 JS 动态加载或构建框架。覆盖插件不承担 NGINX 转发、网络代理认证或宿主持久化策略。

宿主只向插件传递经校验的协议枚举，不传整个渠道对象、任意设置或额外敏感字段。具体上下文字段名和新增文件路径在实施时按现有约定确定。

### 3. 任务生命周期固定协议

提交阶段读取实际选中渠道的配置；若原有重试机制选择另一个渠道，应重新从北向规范化输入构造本次请求，不能复用上一渠道的南向请求体。

创建成功后，将成功请求使用的协议写入现有 `PluginState`，示意如下：

```json
{
  "video_upstream_protocol": "openai_video"
}
```

协议状态由覆盖插件自身构造和维护。宿主整体序列化、存取和替换状态，不执行字段级合并。凡返回持久化新状态的钩子，都由插件显式保留协议字段；轮询不需要变更状态时可以不返回 `state`，不要求每个钩子机械回传。Responses 渲染事件的观察状态不等同于任务持久化 `PluginState`，不能混用。

| 场景                                               | 协议来源                                |
| -------------------------------------------------- | --------------------------------------- |
| 新任务提交                                         | 实际选中渠道的协议配置                  |
| 提交响应解析                                       | 本次提交已确定的协议                    |
| 任务查询、轮询和状态解析                           | 任务`PluginState`                     |
| 视频内容下载                                       | 任务`PluginState`                     |
| 已确认来自旧实现、无协议字段的历史任务             | 按历史事实使用`ark`                   |
| 来自新双协议实现但缺失协议字段，或来源无法可靠识别 | 视为状态异常，明确失败，不猜测为`ark` |
| 存在未知协议值的任务                               | 返回明确错误，禁止尝试另一协议          |
| 关联原任务的操作                                   | 校验并沿用原任务的渠道及协议语义        |

插件配置需覆盖提交响应解析的上下文，不能只在请求构造时可见。必须验证服务重启后仍可恢复协议，以及渠道配置修改后存量任务的查询、下载不受影响。

#### 3.1 有界状态与提交后失败边界

当前状态大小限制为 1 MiB，但提交和轮询的超限语义不同：

| 情况                         | 当前宿主行为                 | 对本方案的影响                                       |
| ---------------------------- | ---------------------------- | ---------------------------------------------------- |
| 提交状态超限                 | 丢弃整份状态，仍返回提交结果 | 若后续无条件按`ark` 兜底，会误处理已创建的兼容任务 |
| 轮询未返回状态，或新状态超限 | 不更新已有状态               | 原协议字段不会仅因这一次超限而自动消失               |
| 轮询返回合法新状态           | 整体替换旧状态               | 插件遗漏协议字段会覆盖掉已有协议事实                 |

最小入侵的首选防护是让本地插件的状态结构天然有界：新任务无论使用 `ark` 还是 `openai_video`，均显式写入经验证的协议枚举；首期只保存协议及确有必要的固定小字段。不把客户端 metadata、文件数据、完整上游响应或不断累积的轮询记录放入状态，也不盲目展开未知对象作为新状态。原始响应仍使用既有任务数据合同。

把协议字段放在 JSON 最前面不能防止超限丢失，因为宿主不是按字节截断。为豆包引入宿主全局自动合并、第二份协议存储或放宽状态上限，也不属于本方案的修复路径。实施验收应证明巨大请求/响应不会使本地插件的状态增长，且所有返回新持久化状态的钩子保留协议字段。

历史兼容必须基于可核实的生产者信息制定规则，优先复用现有任务执行快照中的插件 key/version，而非当前渠道配置、模型名或猜测任务 ID。现有资源上下文已有 `producerVersion`，查询上下文尚未暴露同一信息；若实现需要，只补充必要的只读上下文接线，不把生产者版本当作另一份协议真值。实施前列出旧生产者版本/无执行快照任务的合法历史范围，并确认新发布版本可区分；不能仅凭“没有 state”判定为旧任务。无法区分时，此项仍为待解决门槛。

不要把“提交状态超限”简单改为普通 5xx 错误：此时上游可能已经创建任务，现有重试逻辑仍可能再次提交，造成重复任务或遗失上游任务 ID。`LocalError` 本身也不能保证所有 5xx 不重试。首期通过受控的小状态避免引入此路径；若需修复宿主的通用提交后状态失败语义，应作为独立缺陷工作包，先明确已创建任务的 ID 保留、恢复及禁止重提机制，再实施有证据的最小修复，不顺带重构全局重试框架。

#### 3.2 协议快照与当前运维配置

本方案只固定协议；上游地址和凭据仍遵循现有任务机制，不据此宣称任意地址变更也能保持旧任务可用。

协议固定不等于媒体出口固定：`PluginState` 保存协议事实，媒体转发开关和转发基址在每次下载开始时从任务所属渠道读取，并在该次下载及所有重定向中保持一致。不要把这个运维开关固化到新任务状态中，否则不能直接修复历史任务的下载出口。

### 4. 完整南向适配合同

| 环节     | 方舟原生                                               | Videos 兼容                                                         |
| -------- | ------------------------------------------------------ | ------------------------------------------------------------------- |
| 创建     | `POST /api/v3/contents/generations/tasks`            | `POST /v1/videos`                                                 |
| 查询     | `GET /api/v3/contents/generations/tasks/{id}`        | `GET /v1/videos/{id}`                                             |
| 主要输入 | `model`、`content[]`、`duration`、`resolution` | `model`、`prompt`、`seconds`、`size`、参考输入              |
| 状态     | `queued`、`running`、`succeeded`、`failed` 等  | 按合同映射`queued`、`in_progress`、`completed`、`failed` 等 |
| 内容     | 查询结果中的资源 URL                                   | `/v1/videos/{id}/content`，以目标上游合同为准                     |
| 用量     | 方舟任务返回的 token 用量                              | 按目标上游的实际用量字段解析                                        |

不能只替换 URL。两种模式分别处理请求编码、任务 ID、错误响应、终态、视频内容及用量，并转换回既有北向响应格式。豆包原生北向查询也要在 Videos 南向模式下转换为方舟风格响应，不能直接透出 Videos 任务数据。

协议转换实现前必须指明目标兼容上游，并取得脱敏的上游请求、成功响应、失败响应和完成响应样例，明确：

- JSON 与 multipart 的支持情况，`seconds` 类型，`size` 与分辨率/比例映射。
- 图片 URL、文件上传、多图、视频引用、首尾帧和草稿任务的表达方式。
- 下载是否提供 GET/HEAD、Range、重定向，以及资源地址的鉴权方式。
- 用量字段、缺失用量的语义、状态终态及错误结构。

对上游无法表达的豆包能力，应在提交前明确报错，不能静默删除参数。不要自动下载 URL 转文件或无条件透传全部 `metadata`；如需这些行为，应先根据真实合同补充设计。请求可选字段需区分缺失与显式零值，并遵循现有校验规则。

#### 4.1 参考输入与文件上传的范围决策

“保持现有北向接口”指已有路由及合法请求的兼容性，不等于预先承诺新增文件上传，也不等于可以忽略上游要求。双向能力差异都必须处理：

| 上游合同与需求                          | 首期决策                                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------------- |
| 上游支持现有 URL 参考输入               | 沿用现有输入方式，在本地覆盖插件中明确字段映射                                              |
| 某项能力只接受文件，但不是首期必需能力  | 明确不支持该能力；提交前报错，不扩大北向合同                                                |
| 首期必需能力只接受文件                  | 列为显式范围决策；合同确认后仅在本地覆盖插件中支持必要文件字段，复用宿主已有 multipart 能力 |
| 只有 URL 输入，却要求自动下载并上传文件 | 不默认实施；另核对媒体获取、校验、容量及出口需求后决定                                      |

确需文件支持时，北向解码只负责受控字段的解析与规范化；实际选中渠道后，在构造和发送上游请求前校验该协议是否支持该输入。拒绝不支持的字段不能延迟到上游已经创建任务之后。不能为让解码器提前知道最终渠道而改造通用路由/分发顺序，也不放宽宿主的全局解码规则。

需要单独验证 URL、文件、多图及显式零值等输入的接受/拒绝矩阵，证明原生模式旧请求不退化，兼容模式不会静默丢弃参数。文件大小、类型、数量及必要 multipart 字段以已确认合同和现有宿主限制为准，未确认前保持待决状态。

#### 4.2 下载方式与运维差异

方舟模式在现有统一下载入口中也是由网关获取并转发媒体字节，`credentialless` 只描述上游请求的凭证要求，不代表向客户端发送 302。Videos `/content` 可能使用带凭证请求，但两种模式均应复用现有下载控制器，不另建一套 Videos 下载链路。

合同核对需分别记录“直接返回媒体字节 / 返回资源 URL / 返回 HTTP 重定向”。运维评估关注资源签名有效期、凭证与跨域规则、首部和空闲超时，以及新增 NGINX 跳点的带宽与连接成本；不能按“原来网关不承担视频流量、现在开始承担”估算。目标上游与 NGINX 的真实行为尚待样例及链路测试确认。

Remix、列表、删除、取消不纳入首期默认承诺。仅有 `/v1/videos` 路径不等于支持这些能力。若首期确需其中一项，须补齐上游合同和独立验收项。

### 5. 可选媒体转发与 NGINX 出站合同

#### 5.1 根因与修复范围

当渠道 Base URL 指向 NGINX，而未配置覆盖媒体访问的正向代理或网络出口时，当前请求路径是：

```text
创建、查询：HK 本服务 → 渠道 Base URL / NGINX → 上游 API
媒体下载：  HK 本服务 → content.video_url 指向的上游/CDN → HK IP 被拒绝
```

反向代理只处理实际发到它的请求，不会自动接管响应 JSON 中绝对 URL 的后续访问。仅替换媒体 URL 的域名也不充分：原视频可能位于不同 CDN，NGINX 现有 API 反代规则不知道应访问哪个媒体源。

Videos 南向下载若使用 `Base URL + /v1/videos/{id}/content`，第一跳会经过 NGINX，但只有该接口直接返回视频字节时才能据此确认媒体出口；返回外部 URL 或跨域重定向仍需单独处理。方舟原生模式也必须覆盖，不能只修复新兼容模式。

#### 5.2 渠道开关与生效规则

建议文案为“视频下载经渠道 API 地址转发”，避免“原 API 地址”与“原视频地址”混淆。以下字段为拟新增设计，不代表现有可用配置：

```json
{
  "video_upstream_protocol": "ark",
  "media_via_base_url": true
}
```

| 场景                                   | 行为                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------ |
| 字段缺失或为`false`                  | 保持现有下载行为，仍遵循渠道`proxy` 和现有环境代理规则；不强制改为直连 |
| 为`true`                             | 无凭证的独立 HTTP(S) 媒体下载经渠道 API 地址上的约定入口转发             |
| 已有带凭证`/content` API 请求        | 继续经渠道 Base URL 调用，不重复封装为无凭证媒体请求                     |
| `data:` 等内嵌资源                   | 保持本地处理，不调用 NGINX                                               |
| NGINX 不可用、目标被拒绝或转发配置错误 | 明确失败，不回退直连、不切换协议、不重新提交生成任务                     |
| 修改开关或渠道 API 地址                | 下一次下载采用新配置，包括历史任务；已开始的下载沿用本次配置             |

首期作用于本方案覆盖的豆包渠道及其视频、尾帧图片等无凭证资源，不默认开启其他插件的媒体转发。保存时验证字段类型、渠道适用范围以及显式配置的 HTTP(S) API 基址，拒绝带 userinfo、查询串或 fragment 的基址。启用要求该地址已经部署媒体入口；不能因已有 API 创建调用成功，就认定它支持媒体转发。

Base URL 和正向代理 `proxy` 不互相替代。两者同时启用时，链路为“本服务 → 渠道正向代理 → NGINX 媒体入口 → 媒体源”；默认保留现有 `proxy` 语义，不隐式忽略它。具备合适的 HTTP CONNECT/SOCKS 正向代理时，现有渠道 `proxy` 也是可单独采用的出口解决方式，普通 NGINX 反代地址不能直接填作正向代理。

#### 5.3 本服务与 NGINX 的媒体转发约定

推荐在渠道 Base URL 下增加固定入口 `/_newapi/media`，通过内部请求头 `X-NewAPI-Media-URL` 携带完整原始目标。入口和请求头名称为本方案建议，实施时两端必须保持一致。

假设渠道地址是 `http://example.com`，原视频是 `https://cdn.vendor.example/videos/a.mp4?token=abc&expires=123`，本服务发给 NGINX 的请求示意为：

```http
GET /_newapi/media HTTP/1.1
Host: example.com
X-NewAPI-Media-URL: https://cdn.vendor.example/videos/a.mp4?token=abc&expires=123
Range: bytes=0-1048575
```

```text
HK 本服务
  │ 渠道 API 基址 + 固定媒体入口；内部请求头携带原媒体 URL
  ▼
NGINX
  │ 校验目标；按原 scheme、host、path、query 请求媒体源
  ▼
媒体源 / CDN
  │ 视频字节或重定向响应
  ▼
NGINX → HK 本服务 → 客户端（最终媒体响应）
```

`http://example.com` 仅为地址示意，公网部署应使用 HTTPS。若 Base URL 包含 `/gateway`，入口定义为 `/gateway/_newapi/media`；保留合法基址路径，只在拼接处处理尾部斜杠，不能用会丢失基址路径的绝对路径解析方式。

目标 URL 不拼到外层查询串或路径中，避免再次编码和混入常规请求日志。解析 URL 用于验证，但转发时保留原始转义路径、原始查询串、重复参数及其顺序；不能把 `%2F`、`+` 或签名参数重新归一化。两端应明确内部请求头的长度上限，并与现有媒体 URL 长度限制协调；超限返回错误，不截断、不回退直连。

NGINX 应新增独立 location，和已有 API 反代规则分开。以下是待实施合同，不是可直接部署的完整配置：

| 方面       | NGINX 端要求                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 动态目标   | 校验后才用于变量`proxy_pass`；配置可信 DNS resolver，不把任意客户端头无条件用作上游                                                 |
| 上游身份   | Host 指向原媒体目标；HTTPS 设置正确 SNI 并开启证书验证及可信 CA                                                                       |
| 允许方法   | 只允许 GET/HEAD，保持请求方法，不附带请求体                                                                                           |
| 请求头     | 采用明确允许列表传递 Range、If-Range、If-None-Match、If-Modified-Since；内部目标头、转发鉴权信息、客户端令牌和渠道 API Key 不发给 CDN |
| 响应       | 保留媒体类型、长度、范围及缓存校验相关响应头；正确传递 200、206、304、416 和错误状态，不用 HTML 错误页替换                            |
| 缓冲与缓存 | 媒体响应采用`proxy_buffering off`、`proxy_cache off`，避免全文件缓冲和未经设计的私有媒体共享缓存                                  |
| 重定向     | `proxy_redirect off`，原样传回 Location，由本服务进行下一跳处理；不通过 error_page 等机制悄悄改写媒体目标                           |
| 超时       | 根据首部等待和读写空闲时间配置，并与本服务超时协调；不是按视频生成时长设置单一超时                                                    |
| 访问控制   | 限制为获准的本服务调用，使用私网/来源限制或专用认证；媒体目标使用受控域名、scheme、端口及出站网络限制                                 |
| 日志       | 记录请求 ID、状态、目标域名和耗时；不记录完整签名 URL、内部目标头或凭证                                                               |

NGINX 对变量 `proxy_pass` 的 URI 处理、resolver、Host/SNI、响应缓冲及重定向指令的语义，参见 [NGINX proxy 模块官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。普通 API 反代配置不能直接推导为上述媒体入口已具备。

#### 5.4 每一次重定向都必须经过 NGINX

推荐本服务负责重定向，NGINX 每次只转发一跳：

1. 本服务把原媒体 URL 封装为 NGINX 媒体入口请求。
2. NGINX 获取上游响应；若为 301/302/303/307/308，原样传回状态及 Location。
3. 本服务相对于本跳的原媒体 URL 解析 Location，检查新目标、跨域凭证规则、方法和跳转次数。
4. 下一跳仍通过相同 NGINX 媒体入口发送，直至获得最终媒体响应。
5. 最终媒体字节流式返回客户端；转发失败或重定向被拒绝时返回明确错误。

必须区分“逻辑目标 URL”和“实际传输到 NGINX 的 URL”。例如原 CDN 返回 `../final.mp4`，必须相对于原 CDN 解析，不能相对于 `example.com/_newapi/media` 解析。只把第一次请求 URL 改成 NGINX 地址、仍让默认客户端直接访问后续 Location，会重新从 HK 出站。

实现可采用请求级 HTTP transport 包装：对逻辑请求创建发往 NGINX 的副本，保留外层客户端对原始目标的认知，使每一次重定向都经过同一包装。不要修改共享全局客户端，不破坏取消、流式关闭、首部超时或连接复用；首期无需在 NGINX 中实现递归下载。

现有有凭证请求的跨域拒绝规则保持有效，不能为支持 Videos `/content` 的 302 而自动清除凭证并改成无凭证模式。此类上游需提供明确合同，或在 NGINX/上游侧直接返回媒体字节；未核实前不承诺支持。

#### 5.5 宿主实现边界与目标校验

推荐将媒体出口主体放在新增独立宿主文件，在 `proxyTaskMedia` 选取客户端处增加最小接线；豆包插件继续返回原 `content.video_url` 和 `credentialless: true`。转发封装应覆盖统一资源入口与旧版视频下载入口，避免某一路径继续直连。

不要让插件自己添加内部转发头，也不要为此放宽 `credentialless` 禁止请求头和请求体的约束。内部头由宿主完成逻辑请求校验后生成，只存在于到 NGINX 的传输副本中。两层地址分开校验：NGINX 地址属于管理员配置的渠道目标，媒体地址属于上游提供的外部资源；不能因为第一跳是可信 NGINX 就跳过原媒体 URL 的 SSRF 检查。

每次重定向仍验证媒体目标；NGINX 侧还须限制实际解析结果和可访问网络，不能仅依赖 HK 的 DNS 校验推断远端连接安全。不允许访问本服务自身、媒体转发入口形成的循环或不在许可范围内的目标。代理认证与媒体认证分离，专用代理认证信息不得复用上游 API Key 或传递给媒体源。

原始媒体 URL、`Task.Data`、结果数据和任务 ID 保持原合同。转发地址不持久化到任务、不作为视频结果暴露给客户端；开关变化只改变后续下载的网络出口，不改变任务状态、已完成计费或协议快照。

#### 5.6 北向下载与运维相关检查

本次 NGINX 是出站代理，不要求修改 HK/SG 入口模型分流。后台轮询本来就按渠道 Base URL 和 `proxy` 访问上游；媒体开关不应影响提交、查询、Responses SSE 或计费流程。若另外存在入口 NGINX，它的规则作为独立链路验收，不能替代南向出口验证。

北向验收同时覆盖 `/v1/videos/{id}/content`、`/v1/tasks/{id}/artifacts/{key}/content` 和已有旧版下载入口。`TaskPublicAddress`/`ServerAddress` 必须生成正确的公网域名和路径前缀；修改 Host 或 X-Forwarded-Proto 不能替代这两个设置。

已有部署文档示例使用 `$request` 记日志，而任务资源 URL 中的 `access` 是稳定下载授权签名。若该示例用于实际入口，应改为只记录方法、`$uri`、状态和请求 ID，或针对敏感查询参数做可靠脱敏；转发时仍保留 `access`。该问题来自 [部署架构示例](../20-architecture/部署架构.md) 与 [资源授权实现](../../service/task_artifact_access.go) 的交叉检查，属于相关运维风险，不是本次媒体绕过出站 NGINX 的根因。

实际 NGINX 配置、媒体域名清单、认证方式、DNS/证书设置、签名及重定向样例齐备后，才能形成可部署配置并验证。当前仅确定推荐合同，尚未完成环境验证。

### 6. 计费与兼容边界

南向采用 Videos 编码不意味着模型变成 Sora，也不意味着切换到 Sora 按秒计费。继续使用当前模型配置的计费规则，分别解析两种上游返回的用量。

兼容上游缺少实际 token 用量时，必须在实施前核对现有结算行为并确定依据；不能把缺失用量解释为零费用，也不能虚构实际用量。涉及表达式计费改动时先阅读 `pkg/billingexpr/expr.md`。

验证完整链路：请求数量与时长校验 → 预估和预扣 → 完成用量 → 结算或失败退款。所有新增参数入口沿用项目规定的界限及饱和审计机制，不因协议转换绕过校验。

媒体转发失败是资源获取失败，不得重新提交生成任务、重复扣费或把已成功任务改成失败并退款。代理出口无法修复已过期签名；签名过期与 IP 拒绝应保留可区分的诊断信息，但日志不暴露签名。

### 7. 改动边界与工作包

#### 7.1 组件职责与依赖边界

最小入侵以对现有 new-api 宿主行为和代码的影响为准，不以新增文件最少为目标。新增业务主体集中在独立本地组件，现有文件只保留不可避免的字段声明、注册、配置读写和调用点；不把主体分散到通用 controller、路由或插件引擎中。

| 组件             | 拥有的职责                                   | 输入与输出边界                                                   | 不承担的职责                                         |
| ---------------- | -------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| 本地豆包覆盖插件 | 双协议转换、能力校验、协议状态维护、用量解析 | 北向规范化输入和受控协议枚举 → 上游请求、任务结果及有界私有状态 | NGINX 内部头、代理认证、宿主持久化合并策略           |
| 渠道配置扩展     | 协议/开关默认值、适用性和配置校验            | 渠道设置 → 经校验的必要配置                                     | 上游响应解析、网络传输、计费                         |
| 宿主媒体转发扩展 | 将独立媒体请求逐跳经 NGINX 发送              | 宿主选定的出口配置和媒体请求 → HTTP 响应流                      | 解析豆包响应、读取协议状态、修改任务结果、计费或退款 |
| NGINX 媒体入口   | 受控目标访问及媒体 HTTP 转发                 | 内部转发请求 → 媒体响应或原始重定向                             | 模型路由、任务状态、业务协议转换和计费               |
| 前端独立组件     | 协议选择及可选媒体开关交互                   | 表单值、回填和校验结果                                           | 决定真实网络出口、推断上游能力                       |

由宿主接线读取任务所属渠道并决定扩展是否启用，媒体组件不接收任意完整渠道对象来自行解析业务。插件可描述独立媒体 URL 或 API 下载请求，出口组件只处理约定适用的请求；两者通过既有媒体描述符和必要配置连接，不互相依赖具体实现。

本方案不改造通用路由归属、不新增全局插件状态合并、不调整通用重试策略、不新增平行任务表或第二份协议真值，也不为模块划分引入新的插件框架。发现宿主通用缺陷时单独记录、证明影响并安排修复；确实阻塞本功能安全实现的缺陷需先解决，不能用“最小入侵”掩盖未闭合风险。

### 9. 发布、回退与待收敛事项

媒体转发发布顺序：先部署并验证 NGINX 专用媒体入口，再发布宿主支持和渠道开关，确认所有处理下载的节点支持该配置后按渠道启用。不能仅因开关保存成功就认为 NGINX 配置完成。媒体修复可先于 Videos 南向扩展发布。

先部署能够处理两种协议的后端及覆盖插件，确认所有相关节点加载相同版本，再开放前端选项并启用兼容渠道。

媒体转发回退与协议回退分开处理。关闭媒体开关会恢复原下载路径，在 HK 被禁场景下会重新导致下载失败；它不是保持可用性的无损回退。应优先回退到兼容的媒体转发版本，或先准备并验证替代出口，再关闭开关；不要回退成忽略已启用开关、悄悄直连的旧后端。保留存量视频下载所需的 NGINX 入口和日志诊断能力。

回退时先停止新的兼容模式任务进入，保留能够查询和下载已提交兼容任务的实现。不能直接删除覆盖插件或关闭覆盖开关，让旧兼容任务交由仅支持方舟的内置插件处理；还需考虑已完成视频的后续下载保留期。

方案实施并验证后，再将确定的配置、架构和运维行为同步到对应事实文档。当前不更新长期事实、不新建已定稿 ADR、不移动任何文件到归档目录。

## 2026-09-23 评审修复与验证记录

### 修复范围

- **协议启用边界**：保留预留枚举，但禁用前端 `openai_video` 选项；保存与豆包新任务提交共用可用协议校验。已有错误配置明确报错，不静默退回方舟；其他任务插件保持原合同，查询/下载不依赖新任务协议门禁。此改动没有实现双协议转换或任务协议固定。
- **媒体出口隔离**：可信渠道入口使用既有渠道出站客户端，允许私网 NGINX；原始媒体目标与每个跳转仍按媒体 SSRF 策略验证。配置了渠道正向代理时保留原代理客户端。
- **配置合同**：保存和下载共用媒体配置校验；开启但渠道范围或地址非法时明确失败。通用任务插件必须同时满足类型 61 与 `doubao` 绑定，不能只凭 key 扩展任意渠道。入口拼接保留转义路径。
- **重定向**：直接关闭重定向响应体，避免无超时地读取无关正文；移除无实际调用的带凭据分支和单次客户端包装方法。保留现有逐跳结构，不改造共享下载器。
- **NGINX 合同**：默认拒绝非授权入口访问；关闭原请求头/请求体透传；显式传递媒体允许头；分别提取 Host authority 与 TLS 主机名，覆盖查询串、端口与方括号 IPv6。真实验证脚本直接使用运维文档配置，避免维护第二套入口配置。
- **前端错误反馈**：新增字段纳入高级设置错误定位，开关展示字段错误；存量不支持协议必须纠正后保存。仅更新 en/zh 文案。另修复阻断类型检查的既有侧栏重复属性，将账单与任务插件恢复为两个独立的超级管理员入口。
