# 视频媒体北向交付形态决策分析

## 问题与目标

前案与现行方案均默认"由网关拉取媒体字节并转发"。本需求评审对该默认提出质疑：为什么网关自己访问 `content.video_url`，而不是把 URL 直接交给客户端；并进一步提出"只返回 URL、视频不经过网关"的方向。本文把该讨论收敛为可决策的交付形态对比、风险结论与待决项。

本文只记录分析结果和决策依据，不表示任何北向合同、下载入口或渠道配置已经改变。

已确认的需求澄清（2026-09-23）：

- "上游"指上游 API 提供商（火山方舟/兼容上游服务），不包含其 CDN、对象存储等分发基础设施。
- 客户端不得与上游 API 提供商产生任何联系，不得获得任何可用于调用上游 API 的凭证。
- 下载以 URL 形式交付；客户端直接从媒体地址获取字节可接受。

## 当前实际情况

### 北向交付的代码事实

以下为 2026-09-23 工作区静态核对结果。

| 范围 | 当前事实 | 依据 |
| --- | --- | --- |
| 交付分层 | 提交/查询阶段返回 JSON 中的 URL 字段；下载阶段返回视频字节。两者是不同端点，异步性只存在于任务创建与轮询，与"谁去取字节"无关 | [任务查询](../../relay/relay_task.go)：`GetTask` |
| 旧版/通用北向 | 查询响应 `url`/`ResultURL` 直接返回任务存储的原始 URL；豆包任务存的就是上游 `content.video_url`，该合同下客户端本可直连 CDN | [任务查询](../../relay/relay_task.go)：`GetResultURL`、[任务模型](../../model/task.go) |
| Videos 北向 | 任务对象没有任何下载 URL 字段，取视频唯一途径是带鉴权调用 `GET /v1/videos/{id}/content` | [Videos 渲染](../../relay/channel/task/jsplugin/adaptor.go)：`ConvertToOpenAIVideo` |
| artifacts 北向 | `/v1/tasks/{id}/artifacts/{key}/content?access=...` 是网关自签的裸链接，无需鉴权头即可下载，但字节仍经网关中转 | [资源地址生成](../../service/task_artifact_access.go)、[任务路由](../../controller/task.go)：`BuildTaskArtifactContentURL` |
| 网关中转实现 | `proxyTaskMedia` 由网关向上游发起请求，`io.Copy` 把上游响应体逐块写入客户端响应：边收边发的流式转发，不落盘、不整体读入内存；搬运的是视频字节而非 URL，原始 URL 只出现在网关发出的请求行和任务数据中 | [下载入口](../../controller/video_proxy.go)：`proxyTaskMedia` |
| `credentialless` 语义 | 仅表示网关拉取时不携带插件凭证（只允许 GET/HEAD、无自定义头、无请求体），不代表把 URL 重定向给客户端 | [下载入口](../../controller/video_proxy.go)、[JS 任务适配器](../../relay/channel/task/jsplugin/adaptor.go) |
| 网关代理的设计原因 | 北向只暴露网关地址与自签 `access` 签名，下载鉴权、限流、日志留在网关；上游签名 URL 不下发，避免授权外泄；网关地址在任务保留期内稳定，上游 URL 会过期或分散在不同 CDN | 前案 [豆包视频南向协议扩展方案](2026-09-22-豆包视频南向协议扩展方案.md) §5 |

### Videos 合同的事实与弹性

- OpenAI Videos 合同的任务对象（`id`/`object`/`status`/`progress`/`model`/`created_at`/`completed_at` 等）没有下载 URL 字段；`/v1/videos/{id}/content` 是客户端拿到视频的唯一途径。严格按该合同，"URL 形式下载"无法成立——这是合同形态，不是网关实现选择。
- 但合同只要求"网关应答下载端点"，不要求"字节必须经网关中转"：网关对 content 请求返回 302 指向媒体地址，客户端 HTTP 层自动跟随，北向 URL 形态与鉴权方式不变。重定向兼容性：openai-python 显式启用跟随重定向，openai-node 遵循 fetch 默认 `redirect: 'follow'`；跨域 302 按规范剥离 Authorization，媒体地址也不需要它。剩余不兼容面只有显式禁用重定向或检查 `status === 200` 才读响应体的客户端，需以实际客户群实测。
- artifacts 端点是本项目自定义的北向扩展，交付形态完全由我们决定，不受 OpenAI 合同约束。

## 交付形态对比

| 形态 | 网关字节流量 | 客户端接触面 | 下载鉴权/审计 | URL 裸链接 | 兼容性 |
| --- | --- | --- | --- | --- | --- |
| 网关中转（现状） | 全量过网关 | 仅网关 | 网关 `access` 签名控制 | artifacts 已提供 | 与 OpenAI 官方行为逐字节一致 |
| 出口修复（渠道正向代理或专用媒体入口） | 全量过网关；不减少带宽，只修 HK IP 被拒的出站腿 | 仅网关 | 同现状 | 同现状 | 同现状 |
| URL 直传 / content 302 | 零（URL 可覆盖的路径） | 媒体地址（CDN）；无任何凭证关系 | 丢失，上游签名 URL 即下载凭证 | 是（上游签名，有效期由上游定） | 302 依赖客户端跟随重定向；直传要求客户端改用响应 URL |

结论：出口修复方案（[收敛方案](2026-09-23-豆包视频兼容南向实现与原生代理收敛方案.md) §5）与交付形态正交——它解决"HK 出站被拒"，不减少网关带宽；URL 直传/302 同时消除带宽与 HK 出站问题，但放弃下载侧控制。

### 风险结论

| # | 命题 | 结论 |
| --- | --- | --- |
| 1 | 返回签名 URL 会泄漏上游账号/API 凭证 | 不成立。签名 URL 是单资源、单动作、限时的下载凭证：不能调用上游任何 API，不携带渠道 API Key。残余风险有界：到期前该文件可被任意持有者重复下载（带宽计上游侧）、无法吊销、暴露上游 CDN 身份。与 S3 presigned URL 同一风险模型，风险可控 |
| 2 | 上游 URL 过期不负责 | 合同上可辩护（文档明示"临时地址、有效期不保证"即可），但过期风险两种形态对称——网关代理同样救不回死链（前案 §6"代理出口无法修复已过期签名"）。真实差异是事后可修复性：中转形态可集中更换出口并覆盖历史任务；直传形态死链在客户端手里，服务端无任何补救手段 |
| 3 | 只返回 URL，层级更少、出错更少 | 大方向成立。"只"做不到：`data:` 内嵌资源与上游不返回 URL 的场景必须保留网关代理；Videos 合同客户端只会调用 content 端点 |

### 无法直传的残留路径

- `data:` 内嵌资源（base64 正文，没有 URL 可给）。
- 上游任务成功但未返回任何 URL 的场景。
- 严格 Videos 合同下不跟随重定向的客户端（若选 302）。

这些路径无论选择哪种形态都保留网关代理，其出口仍按渠道 `proxy` 处理。

## 决策与待决项

按已确认的需求澄清（上游不含 CDN），结论如下：

| 北向入口 | 交付形态结论 |
| --- | --- |
| 旧版/通用北向 | 已是 URL 直传（查询响应返回上游原始 URL），无需改动；过期与可达性按 best-effort 文档化 |
| 豆包原生北向 | 方舟合同的任务查询响应含 `content.video_url`，同为 URL 形式 |
| Videos 北向 | 合同给不了 URL，三选一待决：a) 继续网关中转（逐字节一致，网关承担该部分带宽）；b) content 端点 302（零字节，接受极少数不跟随重定向的客户端）；c) 响应增加扩展字段指向网关签名裸链接（标准客户端忽略未知字段，不破坏合同兼容，但字节仍过网关） |

URL 直传/302 方向若被选中，采纳前必须核实（当前均为未验证项）：

- 上游签名 URL 的实际有效期是否覆盖客户端轮询延迟与下载保留预期。
- 上游 CDN 是否拒绝目标客户端所在区域（本案上游拒绝 HK，客户端区域可达性未实测）。
- 上游 ToS 是否接受终端用户直连下载。
- 媒体地址对 GET/HEAD/Range 的支持。
- 放弃下载鉴权、限流与审计的正式接受。

与现行方案的关系：本文不改变 [收敛方案](2026-09-23-豆包视频兼容南向实现与原生代理收敛方案.md) 的工作包与移除方向；网关仍需中转的路径（`data:`、无 URL 场景、待决的 Videos 形态）继续按其 §5 正向代理方案解决 HK 出口。若最终确定 Videos 选择 302 或全面直传，需先修订前案 §4.2/§5 与收敛方案 §4 中"由网关获取并转发媒体字节""`credentialless` 不代表 302"的约束，再实施，不保持两套并行。
