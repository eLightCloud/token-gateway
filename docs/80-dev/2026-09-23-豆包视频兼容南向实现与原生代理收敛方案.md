# 豆包视频兼容南向实现与原生代理收敛方案

## 问题与目标

本方案承接 [豆包视频南向协议扩展方案](2026-09-22-豆包视频南向协议扩展方案.md)，按本次需求重新确定后续实施方向：

1. 实现豆包模型的 OpenAI Videos 兼容南向协议，重点保证请求参数、任务状态、媒体内容和用量语义匹配。
2. 优先使用 new-api 已有渠道“代理地址”解决 HK 出口受限问题。正向代理满足需求并通过验证后，移除本次新增的专用媒体转发实现，不长期维护两套出口机制。
3. 协议转换归本地任务插件，网络出口归现有 HTTP 客户端，保持组件隔离和对 new-api 的最小入侵。

本文是新的实施依据；前案保留前期设计与验证记录，其中“新增媒体转发开关作为目标能力”的方向由本文的原生代理优先方案调整。本文只新增分析文档，不表示已经实现兼容协议、删除现有代码或切换生产配置。

这里的“OpenAI 南向代理”指网关把请求转换成目标上游的 Videos 协议；界面上的“代理地址”指网络正向代理。两者独立：配置代理不会让方舟请求自动变成 `/v1/videos` 请求，实现 Videos 协议也不会自动改变媒体下载出口。

## 优化方案

### 1. 架构决策与组件边界

目标链路：

```text
客户端 → 网关北向解码 → 本地豆包双协议插件 → 现有 HTTP 客户端
                                               ↓ setting.proxy
                                          正向代理出口
                                               ↓
                                  上游任务 API / 独立媒体域名
```

| 组件 | 应负责 | 不承担 |
| --- | --- | --- |
| 本地豆包覆盖插件 | 北向输入归一化、Ark/Videos 参数转换、协议状态固定、响应与资源解释 | 建立代理连接、NGINX 专用头、代理失败兜底 |
| 现有任务宿主 | 选渠道、执行描述符、持久化状态、调度与计费；补充必要只读上下文 | 豆包专属参数转换、整套协议框架重构 |
| 现有 HTTP 客户端和下载入口 | 渠道代理、流式传输、URL 校验、重定向及凭据边界 | 解释 `duration`、`resolution`、`content[]` |
| 正向代理节点 | 对允许的目标建立连接，使目标看到可接受的出口 | 转换视频协议、改写签名 URL、理解任务业务 |

继续使用同 key 的本地 `doubao` 完整覆盖插件，保留 Ark 能力及现有北向声明。复用已有插件加载方式，不新增同模型的平行插件身份，不改变模型路由规则。JS 引擎禁止 `import`，首期用独立插件文件承载完整实现，不为共享少量函数改造引擎或内置 Sora 插件。

既有 Go 文件只做字段或上下文接线；协议相关新增逻辑放在已有本地扩展文件或新的专用文件。`relaykit` 只提供独立 DTO/基础校验，不能反向依赖根模块的插件注册器。协议可用性若需检查运行时插件，放在根模块本地接线层，不向 `relaykit` 引入运行时依赖。

### 2. OpenAI Videos 南向实现：先冻结目标合同

“OpenAI 兼容”不是足够的参数规范。仓库 Sora 实现只能作为机制参考；目标上游可能采用 URL、引用对象或文件上传，不能根据接口名推定。

本次查阅的 [OpenAI 创建视频参考](https://developers.openai.com/api/reference/resources/videos/methods/create) 将 `input_reference` 描述为引用对象，包含互斥的 `image_url` / `file_id`，并给出特定模型的时长、尺寸范围。仓库 Sora 插件另外实现了文件 multipart 构造。因此不能沿用“兼容 Videos 就必需上传文件”的假设，也不能把 Sora 的模型、默认值或枚举当成 Seedance 的合同。官方页面核对日期为 2026-09-23；第三方上游以其明确版本的合同和实测样例为准。

正式编码前需取得以下最小证据；同时可以独立开展原生代理验证和移除准备：

| 合同项 | 必须确认的内容 |
| --- | --- |
| 创建 | 完整 URL、鉴权、JSON/multipart、模型真实名称、必填字段、默认值、显式零值含义 |
| 参考输入 | URL 字符串/引用对象/上传文件/文件 ID；数量、角色、媒体类型和大小限制 |
| 尺寸与时长 | 每模型合法尺寸、宽高比组合、时长类型和取值；是否支持自动时长等特殊语义 |
| 生命周期 | 创建成功 ID、运行中/成功/失败响应、取消/过期状态、错误格式 |
| 内容 | `/content` 返回字节还是跳转、是否提供独立 URL、鉴权、有效期、GET/HEAD/Range |
| 用量 | 成功、失败、用量缺失的样例；tokens、seconds 的含义与最终计费口径 |

用脱敏的真实样例形成插件合同测试夹具。不得先开放 `openai_video`，再靠失败响应猜测字段或自动切回 Ark 重提。

### 3. 参数归一化与映射规则

#### 3.1 统一入口，按实际渠道构造请求

现有入口包括豆包原生 `content[]`、Videos JSON/multipart 和 Responses 输入。各入口先保留业务含义，最终选中渠道后再生成对应南向请求。跨渠道重试必须从同一份原始归一化输入重新构造，不复用前一渠道改写过的请求体。

当前原生解码器已把 `content[]` 的文本按顺序组合进 `prompt`，原始字段保留在 `metadata`；Videos 解码器尚未完整归一化 `image` / `input_reference`，且拒绝上传文件。新实现应修正本地覆盖插件内的归一化，不能假设这几种入口已经等价。

| 业务参数 | 现有来源 | 兼容南向规则 |
| --- | --- | --- |
| 模型 | 北向 `model`、渠道模型映射 | 使用实际渠道的 `ctx.upstreamModel`；不硬编码 Sora 模型，不被 `metadata.model` 覆盖 |
| 文本 | 原生 `content[].text`、Videos `prompt`、Responses 文本 | 保留顺序与有效文本；已归一化时不得重复追加。并存字段有冲突时明确拒绝，不靠任意优先级吞掉内容 |
| 时长 | `seconds`、`duration`、`metadata.duration` | 验证所有被消费入口；一致值可归一，冲突拒绝。按目标合同输出数字或字符串；不用 `parseInt` 把 `5.5`、`5abc` 静默截断 |
| 尺寸 | `size`、`resolution`、`metadata.resolution`、宽高比 | 区分“像素尺寸”和“分辨率档位”。仅按合同定义的模型映射表组合；缺少宽高比且合同无默认值时拒绝，不能把 `720p` 固定解释为横屏 |
| 单图参考 | `images[]`、`image`、`input_reference`、原生图片内容项 | 归一化时保留类型和角色；按合同生成 URL、引用对象或文件 part，不把对象字符串化为 `[object Object]` |
| 多图/首尾帧 | 多个图片项与 `role` | 只有目标合同支持对应数量和角色才映射；不只取第一张，不把尾帧降成首帧 |
| 视频/音频参考 | 原生 `content[]` 的视频、音频项 | 需要目标明确支持的扩展字段；缺乏对应能力则在提交前报不支持，不丢弃后改成文生视频 |
| 草稿、续作与 remix | 草稿任务引用、动作、原任务 ID | 三者不默认等价；沿用宿主任务归属与来源解析，再按已确认合同转换。不能把公网任务 ID 当上游任务 ID |
| seed、watermark、音频开关等 | 原生字段或 `metadata` 扩展 | 逐项白名单；保留合法显式 `0` / `false`。未支持且影响生成语义的显式参数拒绝，不静默忽略 |
| metadata | 混合了原生请求字段的对象 | 只取本地协议映射需要的字段；不能把整个对象直接作为上游 `metadata`，也不能把整个北向请求展开透传 |
| 上传文件/文件 ID | multipart 文件引用或引用对象 | 复用宿主文件引用机制；文件 ID 必须符合目标合同的归属要求，不假定可跨渠道使用，不自行增加上传 API |

时长、数量等继续使用项目既有上限；最大任务时长受 `relaycommon.MaxTaskDurationSeconds` 约束，目标上游更窄的范围再取交集。省略参数与显式非法参数必须区分：缺省采用已确认默认值；`0`、负数、非有限值、超限不能被 `|| default` 掩盖。若目标支持 `-1` 等自动时长，需要另行确定预扣规则，不直接突破既有计费边界。

Go 中新增可选标量 DTO 使用指针和 `omitempty`，JSON 使用 `common` 包装函数。JS 显式判断字段存在性，不用真假值决定参数是否存在。规则由本地插件集中实现，不为所有提供商增加通用参数转换层。

#### 3.2 映射示例与反例

以下仅用于说明验收方式，不是目标上游已经确认的请求：假定某模型合同明确接受 5 秒、`1280x720`，并明确 `720p + 16:9 → 1280x720`，原生输入中的文本、`duration: 5`、`resolution: "720p"`、`ratio: "16:9"` 应完整映射为对应 `prompt`、`seconds`、`size`。`seconds` 是 `5` 还是 `"5"` 由合同决定。

- 合同只接受 4/8/12 秒时，输入 5 秒必须拒绝，不能取整或改成默认 4 秒。
- 只有 `720p` 且合同没有默认宽高比时，不能猜测为 `1280x720`。
- 两张首尾帧进入只接受一张参考图的上游时，必须报能力不匹配。
- `watermark: false` 若被支持必须原样传递；若不支持且用户显式指定，应明确拒绝。

#### 3.3 北向文件输入的决策

保持已有合法北向请求可用，但不把“完全不允许扩展北向字段”作为硬限制。只有目标合同证明需要文件输入时，才在本地覆盖插件放开对应字段并复用宿主上传机制；解码时保存文件引用，最终选定渠道后按协议验证能力。Ark 渠道仍拒绝自身不支持的文件输入。

若客户仅提供 URL，而上游只收文件，两者存在真实能力缺口。首期明确拒绝并要求符合合同的输入；不能暗中新增服务端 URL 下载再上传流程。后者需要单独明确大小限制、超时、SSRF、代理覆盖和重试语义，不能夹带在参数改名中。

### 4. 生命周期、任务固定与计费

| 阶段 | 目标实现 |
| --- | --- |
| 创建 | 根据实际渠道选择 Ark 或 Videos，正确构造路径、鉴权和 body；只接受合同规定的任务 ID 字段 |
| 查询 | 使用已保存的上游任务 ID 和任务协议；路径参数编码，处理未知状态和错误，不把未知状态当成功 |
| 北向响应 | Videos、Responses、豆包原生分别按既有北向格式渲染；兼容南向结果不能直接冒充方舟原始响应 |
| 资源声明 | 成功任务按实际能力声明 video/last_frame；不虚构兼容上游没有的尾帧资源 |
| 内容下载 | 根据目标合同生成带鉴权 `/content` 描述符或无凭证绝对 URL，统一交给宿主下载，不增加第二个下载控制器 |
| 用量 | 按确定的单位提取并沿用现有模型计费规则；不能把 seconds 冒充 tokens，缺失用量不解释为免费 |

南向返回独立 URL 时保留原始签名 URL；只有带凭证内容接口时，北向需要地址的字段使用既有网关资源访问地址，复用 `TaskPublicAddress` / `ServerAddress` 与资源授权机制，不构造新的公开下载旁路。现有有凭证下载拒绝跨域重定向；若目标 `/content` 必须跳转 CDN，应列为明确合同缺口，先确定不泄漏凭据的最小方案，不能直接放宽所有插件的重定向规则。

任务创建成功后，插件在 `PluginState` 固定 `{ "protocol": "ark" | "openai_video" }` 等少量有界状态。提交按渠道配置选协议，查询、下载按任务状态选协议；渠道之后的协议修改只影响新任务。网络代理仍按任务所属渠道当前配置读取，因此历史任务可直接获得新的出口。

宿主整体存取状态，不自动合并。插件每次返回新持久化状态必须保留协议字段；没有更新需求的轮询不必回传。禁止把巨大请求、响应、媒体或任意 metadata 塞入状态。提交超过 1 MiB 会丢弃整个状态，协议字段放在最前面不能防止丢失；不能简单通过“抛出 5xx”修复，因为上游任务可能已经创建，宿主仍可能重试并重复计费。

历史无状态任务仅在已核实的旧生产者范围内按 Ark 处理；新生产者缺少协议、未知协议明确报错。复用任务执行快照中的插件版本识别历史范围，必要时给查询上下文补充已有的生产者信息；资源上下文已有 `producerVersion`。合法历史范围、版本唯一性和缺失快照的处理须在启用前验证，不能无条件“没有 state 就 Ark”。

计费验收覆盖校验、预扣、完成结算、失败退款和用量缺失。若上游仅返回 seconds 而当前模型按 tokens 计费，必须先确认现有估算/结算政策是否足够；不足则列为独立待决项，不能为获得兼容效果擅改计费单位、费率或全局结算实现。

### 5. 原生“代理地址”能否解决 HK 出口问题

**代码层面可以。前提是该地址提供可用的正向代理服务，且其出口可访问目标 API 和媒体。** 原有下载入口已经读取任务渠道的 `setting.proxy`，不会因为媒体 URL 是绝对地址就绕过显式配置的代理。

| 实际部署 | 能否填入已有“代理地址” | 处理 |
| --- | --- | --- |
| HTTP/HTTPS 正向代理，支持 HTTPS 目标所需的 CONNECT | 可以 | 填入真实代理地址，按服务需要配置认证 |
| SOCKS5/SOCKS5H 代理 | 可以 | 填入真实 SOCKS 地址，验证域名解析和目标连通性 |
| 普通 NGINX `location + proxy_pass` API 反向代理 | 不能仅换个地址就使用 | 它提供目标 API，不等价于通用正向代理 |
| 已部署且验证支持 CONNECT 的 NGINX 正向代理入口 | 满足上述合同即可 | 核实版本、模块、监听端口和访问策略，不按软件名称判断 |

普通反向代理的语义依据：[NGINX Reverse Proxy](https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/)。这不意味着 NGINX 在所有版本/模块组合下都不能提供正向代理。

推荐配置分工：

- **API 地址**：实际上游 API 基址；现有 API 反向代理有独立用途时也可保留，但要确认正向代理到它的可达性。协议路径由插件按基址约定追加，测试尾部 `/`、已有 `/v1` 前缀，避免重复路径。
- **代理地址**：例如 `http://proxy.example:3128` 或 `socks5h://proxy.example:1080`，示例仅代表格式，不是已部署服务。
- **新增媒体开关**：迁移验证时关闭；原生代理验证通过后从产品与代码移除。

最终下载路径是 `HK 网关 → 正向代理 → content.video_url`，无需 `/_newapi/media` 或自定义 URL 请求头。代理同时作用于渠道任务 API，不能声称它只代理视频下载；若部署要求“API 必须直连，仅媒体换出口”，单一渠道代理字段不表达这种分流，应先确认该附加要求，而不是静默改变路由。

显式配置代理的请求失败时应返回失败，不能捕获后换无代理客户端。现有媒体 URL/端口/IP 校验仍生效，凭据跨域限制仍保留。SOCKS 远端解析并不保证本地完全不解析域名，URL 安全校验也可能触发解析；在 HK DNS 受限环境需要实测，不能以关闭 SSRF 校验作为解决办法。

### 6. 新增媒体转发代码的移除范围

#### 6.1 移除门槛

原生代理验证与 Videos 协议实现可独立推进，无需等待兼容上游合同才修复 Ark 媒体出口。满足以下条件即可执行移除：

1. 已清点启用 `media_via_base_url` 的渠道、节点和实际使用方。
2. 在真实 HK 网关上，关闭媒体开关、仅配置渠道代理，创建、轮询、历史/新任务下载均成功。
3. 上游或受控目标观测到代理出口，所有媒体重定向均经过代理；阻断 HK 对目标的直接访问后仍成功。
4. 代理断开、认证失败、目标拒绝访问时明确失败，未出现 HK 直连回退。
5. 所有运行节点配置已生效，未留仍依赖专用入口的任务下载方。

如果暂时没有正向代理，结论是“部署条件未满足”，不是“已有客户端没有代理能力”。此时可以先准备删除补丁，不能先撤掉仍在使用的唯一可用出口；优先补齐标准代理部署。若环境明确禁止正向代理，需重新评估专用媒体入口的必要性，不假装移除条件已经满足。

协议验收至少覆盖：

- 三种北向入口的等价文本、时长、尺寸与单图请求生成相同业务含义的南向请求；JSON/multipart 类型匹配合同。
- 参数缺省、显式 `0/false`、冲突值、非法字符串、时长上限、无法转换的档位/宽高比、多图/角色丢失全部有确定性断言。
- Ark 行为回归；重试换渠道后按该渠道重新构造；创建成功后修改渠道协议不影响旧任务查询/下载。

- 普通用户只能访问授权资源；文件引用、跨渠道原任务引用和资源 URL 沿用宿主边界。

网络验收至少覆盖：

- 关闭专用媒体开关，仅填已有代理；对实际使用的代理类型完成创建、轮询、绝对媒体 URL、新旧任务资源下载。
- HTTPS CONNECT 或 SOCKS 连接、鉴权、证书/SNI、签名 URL 查询串与转义路径不变；不向目标泄漏代理凭据。
- 同域/跨域及多跳媒体重定向；保留有凭证跨域拒绝、循环/超限跳转拒绝、私网目标限制。
- GET、HEAD、Range 及 200/206/304/416；大文件持续流式下载、客户端取消和超时；不转为整文件内存缓冲。
- 阻断 HK 直连目标仍成功；停止代理或给出无效认证后明确失败；以目标连接记录证明出口，而非仅以返回 200 判断。
- 日志证据脱敏，不记录 API Key、代理密码或完整媒体签名 URL。

实现阶段按改动执行相关 Go 测试、根模块构建；涉及 `relaykit` 时执行 `cd relaykit && GOWORK=off go build ./...`。前端使用 Bun 执行受影响测试、类型检查、lint/build，文案遵循项目 i18n 规则。Go 测试使用 testify，验证实际合同，不锁定私有函数布局。持久化行为变化需真实 SQLite、MySQL、PostgreSQL 实例，记录版本、命令及结果；不能引用前次通过结果代替新改动验证。

发布顺序：先让标准代理在旧版本中生效并关闭专用媒体开关，再确认全部节点和下载请求已迁移，随后发布删除专用路径的版本，最后退役专用 NGINX 入口。原生代理配置是回退时仍须保留的运行条件；不能通过清空代理恢复版本，以免重新暴露 HK 出口问题。
