# 豆包 ModelArk 完整北向、双协议南向适配与结果交付方案

## 问题与目标

豆包渠道以 **ModelArk（方舟原生）视频任务接口为核心，北向提供完整的 ModelArk 视频任务合同**。客户端按 ModelArk 的请求、响应和任务管理方式调用；网关南向可以使用 ModelArk 原生接口，也可以适配标准 OpenAI `/v1/videos` 及 CodeYY、Zapgogo 扩展。南向响应统一转换回 ModelArk 北向格式。协议转换继续由本地任务插件承担，宿主负责渠道选择、任务持久化、轮询、计费和权限边界。

本文中的“双协议”指两类南向协议；完整北向以本次豆包视频任务领域的 ModelArk 合同为准，不能用 OpenAI Videos 的字段和动作子集裁剪它。实现以最小入侵、遵循目标版本 new-api 任务插件架构为前提。URL 是按南向实际结果映射的交付形态：南向返回 URL 时，北向仍按 ModelArk 协议返回 URL；不要求所有上游强制提供同名 `content.video_url` 字段，也不把 URL 设为所有任务的必填项。

本文合并并替代以下三份增量文档，作为本主题唯一的实施方案与验证记录；原文中的有效约束、未完成事项和验证边界已按主题收敛，旧版本由 Git 历史保留：

- `2026-09-22-豆包视频南向协议扩展方案.md`
- `2026-09-23-豆包视频兼容南向实现与原生代理收敛方案.md`
- `2026-09-23-视频媒体北向交付形态决策分析.md`

OpenResty 模型入口路由分析、Rc40 上游合并记录不属于本次合并范围。

### 已确认的需求与取舍

1. **北向为完整 ModelArk 视频任务接口，南向适配 ModelArk 或 OpenAI Videos。** `/v1/videos` 是本方案要兼容的南向接口。完整 ModelArk 北向、标准 Videos 南向与供应商扩展分别定义、分别验收；客户端不需要随渠道更换请求格式。
2. **逐条对账以该任务上游返回的 `usage` 为准。** 账单的账期、结算日和汇总金额属于账单层；不能替代单条任务的用量依据，也不能从账单金额倒推并覆盖该任务返回的 `usage`。
3. **北向始终遵循 ModelArk；南向返回 URL 时，北向也以 URL 交付。** 上游的 `url`、`metadata.url` 等字段由插件映射到 ModelArk 对应字段，视频结果通常为 `content.video_url`，不能把 OpenAI 响应原样返回。不得将“有 URL 则映射”扩大为所有上游必须提供直传 URL 的准入门槛；没有 URL 时按实际结果与 ModelArk 合同处理，不虚构 URL。本次不新增视频字节转发或下载再上传流程。
4. **URL 映射保留可用性与凭证边界。** 不把渠道 API 凭证传给客户端；URL 是媒体地址还是需鉴权的下载 API，按上游实际合同核实，不能仅凭字段名或路径判断可直接访问。
5. **保持现有 Ark 合法请求与存量任务可识别。** 新任务固定提交时的南向协议及必要扩展配置，渠道后续修改不让存量任务被另一协议解释。
6. **最小入侵并遵循 new-api 现行插件架构。** 主体放在独立本地插件扩展中，复用原生路由、驱动钩子、任务持久化、轮询和计费。已有文件只做不可避免的注册、配置及调用点接线；只有已证明的合同缺口才扩展宿主，不新增平行任务系统、第二套计费引擎或下载控制器。

以上是本次功能的目标决策，不代表代码已经实现或生产配置已经切换。返回 URL 的路径无需网关下载视频；实际可用性仍需客户端验证。

### 3. 评审发现与本次处理

| 发现 | 证据与影响 | 合并后的处理 |
| --- | --- | --- |
| P1：URL 与 API 下载端点混淆（高置信度） | CodeYY 的 `metadata.url` 指向带鉴权 API，尚未证明客户端可直接使用 | 映射前核实访问合同，不下发渠道凭证、不伪造可用链接；不将所有上游强制提供直传 URL 作为统一准入条件 |
| P1：Ark 能力表不能代表兼容上游（高置信度） | Zapgogo Fast/Mini 支持 1080p，当前 Ark 校验及 schema 不支持 | 为实际目标能力定义明确映射，同时校验请求、用量 schema 和完成事实 |
| P2：标准兼容缺少独立基线（中置信度） | 原计划主要等待某一目标上游，文件及引用能力长期待决 | 明确为南向 Videos 合同及扩展的独立验收；不据此把核心北向改成 Videos |
| P2：实施清单过时（高置信度） | 工作区缺少旧文档所称已实现的配置及专用转发文件 | 重建当前改动清单，保留历史证据的时效边界，不执行旧删除矩阵 |
| 逐条用量与账单混淆 | 原评审过度依赖供应商账单说明来确定单条依据 | 按本次用户澄清，逐条用量以返回 `usage` 为准；账单差异另行核对 |
| 媒体要求被扩大 | 将南向 URL 的北向映射扩大为所有上游 URL-only 准入及全入口改造 | 改为条件映射：南向有 URL，ModelArk 北向也返回 URL；本次不建设媒体转发，不为此强改既有其他入口 |
| 北向核心解释错误 | 把 OpenAI Videos 解释为客户端统一接口，会裁剪 ModelArk 参数和任务管理能力 | 按 2026-09-24 用户澄清，完整 ModelArk 是北向权威；Videos 及两家扩展是南向适配目标 |

本次既不新建视频 content 中转，也不以“缺少直传 URL”为由笼统排除整个南向提供商。缺口按具体操作和结果记录；无法按 ModelArk 合同交付的场景明确报告未支持，不伪装成成功交付。

## 优化方案

### 1. 单插件身份与职责边界

```text
客户端 / 业务前端：完整 ModelArk 视频任务接口
                       ↓
        网关：保留 ModelArk 请求语义，按渠道适配
                       ↓
        ┌──────────────┼─────────────────┐
        ↓              ↓                 ↓
   ModelArk 原生   OpenAI Videos    CodeYY / Zapgogo 扩展
        └──────────────┼─────────────────┘
                       ↓
        网关：按 ModelArk 协议呈现结果及 usage
                       ↓（南向返回 URL 时）
        ModelArk 对应 URL 字段 → 客户端访问媒体地址
```

| 组件 | 职责 |
| --- | --- |
| 本地 `doubao` 完整覆盖插件 | 完整 ModelArk 北向合同、保留原生输入语义、南向 Ark/Videos 构造、供应商扩展、原生响应与错误映射、`usage` 解释、媒体 URL 提取 |
| 任务宿主 | 渠道选择、受控上下文、任务持久化、轮询、授权、既有结算入口和资源投影 |
| 现有 HTTP 客户端 | 上游任务 API 的连接、超时与渠道代理；不承担本方案的视频字节交付 |
| 客户端与媒体源 | 南向返回可访问 URL 时，客户端使用 ModelArk 响应中的对应 URL 下载或播放 |

继续复用同 key 覆盖机制，不新增同模型的平行插件身份。覆盖的是完整 `doubao` 插件，必须保留 Seedream 图片、已有 Videos/Responses 兼容入口、原生路由、已有 `new_api` 上游种类及合法历史行为。已有兼容入口不能反向决定 ModelArk 核心合同或要求 ModelArk 客户端改写请求。JS 引擎禁止 `import`；使用独立完整插件文件，不为少量复用引入引擎改造或修改 Sora 插件。

#### 1.1 遵循目标版本插件合同，限制宿主改动

架构依据为目标分支的 [Task Plugin API v1](../plugin-api/v1.md)、[manifest schema](../plugin-api/v1.schema.json)、[类型声明](../plugin-api/v1.d.ts)及实际宿主实现。本文静态核对基线为 `cd2dbbefa`，不把它宣称为上游最新发布版本；实施前按届时目标版本重新核对扩展点，优先复用已经具备的能力，不为本方案另建旧式 Go 渠道适配器。

- **ModelArk 北向**使用 `meta.routes` 与 `native` 解码/呈现。已有 OpenAI 北向兼容使用 `meta.protocols` / `protocols`；南向选择 Videos 并不要求注册新的 OpenAI 北向入口。
- **南向驱动**通过既有提交、查询、结果解析钩子返回请求描述及任务事实，由宿主执行 HTTP。驱动只按南向配置/任务快照分支，不按客户端路径或北向协议分支。
- **任务与资金**沿用宿主模型、轮询、执行版本快照、`state` 及结算入口；插件只报告用量事实，不自行管理数据库、扣费或后台轮询。
- **URL 呈现**优先利用原生 presenter 从 `task.data` 返回提供商 URL 的现有能力。仅为 ModelArk 返回 URL，不需要改写全局 artifacts、Responses 或 content 下载合同。
- **已知合同缺口**：当前 intent 只有 submit/query，声明 DELETE 方法不等于已经具备取消动作，query 也不等于完整分页列表。先核对目标版本；确需补齐时，只为缺失操作/受控配置增加必要的通用宿主扩展，供应商字段转换仍在插件内。同步更新 API 文档、schema、类型声明及合同测试，按现有版本与 capability 机制声明兼容性，不虚构当前不存在的钩子。

每处宿主改动必须对应明确的现有能力缺口；如果原生插件已能完成，则不增加控制器、持久化字段或公共协议分支。已有图片及其他北向兼容保持原合同，不要求为本次视频南向改造整体重写。

现有模型路由保持权威；标准南向不要求把 Seedance 绑定到 Sora 模型。`new_api` 表示上游是另一个网关，不能自动等同于 Videos 协议，也不能向标准 `/v1/videos` 路径盲目追加 `/doubao`。

### 2. 渠道选择、扩展与模型能力

优先复用目标版本已有的渠道/插件配置能力。以下是待实现的配置语义，不代表当前钩子已能读取这些字段；确无现成扩展点时，在既有 setting JSON 中增加最少配置及受控上下文接线，不新增数据库列、不暴露整个渠道配置或凭证对象：

| 配置 | 目标含义 |
| --- | --- |
| `video_upstream_protocol` | 缺省或 `ark` 为方舟原生；`openai_video` 为 Videos 南向；未知非空值拒绝 |
| `video_upstream_profile` | Videos 扩展合同选择：缺省为 `standard`；本次已知扩展为 `seedance_codeyy`、`seedance_zapgogo`。Ark 不接受不适用的扩展值 |

扩展配置只表达两份已提供资料中的真实差异，不建立通用可编程映射平台。具体实现先验证两家可复用的共同字段；不同编码、默认值、输出能力、URL 和 `usage` 提取规则只在必要处区分。不能依据域名、模型前缀或某次失败响应自动猜测或切换扩展。

三类身份必须分别保留：北向展示/计费模型 `ctx.model`、渠道映射后的上游模型 `ctx.upstreamModel`、已选定协议/扩展对应的能力合同。向上游发送 `ctx.upstreamModel`，不让 `metadata.model` 覆盖它。若需要直接接受 `dreamina-*` 北向模型，显式登记模型及用量 profile；若通过 `doubao-* → dreamina-*` 映射接入，也必须验证最终能力选择。

能力规则同时作用于输入校验和用量 schema：不能仅放开 Fast/Mini 的 1080p 请求，却让宿主拒绝其 1080p 用量事实；也不能全局扩宽 Ark 限制。复用当前 `usageProfiles` 机制，按已声明实际模型定义可用用量枚举，并核对最终上游模型与北向别名的选择顺序。不能用客户端模型的 Ark profile 悄悄替代兼容上游能力。

业务前端按 ModelArk 合同组织请求与显示结果，不随南向切换成 `prompt/seconds/size` 表单合同。管理后台的协议/扩展选项只控制渠道南向，不切换北向协议。UI、保存校验、运行时可用性要一致；只有目标插件实现并通过该上游合同验收后才开放配置。`relaykit` 仅提供独立 DTO/基础校验，不能依赖根模块注册器。前端复用已有组件，文案只维护 en/zh，创建、编辑、复制和渠道类型切换均需覆盖。

### 3. 完整 ModelArk 北向与南向映射

#### 3.1 北向权威合同与完整性

ModelArk 视频任务的操作、请求字段、响应字段、错误格式、状态、分页/筛选和任务管理语义共同组成北向验收范围。不能将“完整”降为创建和单任务查询，也不能把当前插件已实现的子集当作完整协议。

| ModelArk 北向能力 | 本方案要求 |
| --- | --- |
| 创建任务 | 保留 `model`、原生 `content[]` 及其文本/媒体类型、顺序、角色和原生生成参数，按选定合同版本逐字段验收 |
| 查询任务 | 返回 ModelArk 的任务标识、状态、结果 `content`、`usage`、错误与其他合同字段；使用网关公共任务 ID，南向任务 ID 留在私有数据 |
| 查询任务列表 | 实现原生列表响应、分页/筛选和用户任务可见范围；查询不得暴露渠道账号下其他用户的任务 |
| 取消或删除任务 | 按 ModelArk 对不同任务状态的语义处理，区分停止生成与删除记录；不能用本地隐藏记录冒充上游取消成功 |
| ModelArk 参数与模型能力 | 按锁定的 ModelArk 视频合同建立完整字段/动作清单；模型支持范围单独校验，不按 Videos 最小公分母删除北向字段 |

官方参考包含[视频任务列表](https://docs.byteplus.com/en/docs/ModelArk/1521675)及[取消或删除任务](https://docs.byteplus.com/en/docs/ModelArk/1521720)，2026-09-24 核对到对应操作页面。本次网页读取未取得完整参数正文；实施前仍须固定目标 ModelArk 版本的完整 schema、状态规则和样例，不能凭本文概括宣称全部字段已经核实。

当前网关原生入口使用 `/doubao/api/v3/contents/generations/tasks` 命名空间；`/doubao` 属于网关路由前缀，应通过 SDK/API 基址配置适配，不能把接口方法、请求体和响应改为 OpenAI 格式。验收要包含真实 ModelArk 客户端的基址和路径组合，不要求客户端改调用 `/v1/videos`。

#### 3.2 完整北向与南向能力缺口

ModelArk 原生南向负责其完整原生合同。OpenAI Videos 及第三方扩展按实际能力承接同一份 ModelArk 请求，并将响应转换回来：原生 `content[]`、角色、参数及任务管理含义不能在转换中丢失。

完整北向不意味着每个第三方上游自动具备 ModelArk 的全部能力。对确实不能映射的请求或操作，返回明确的 ModelArk 风格能力错误；不静默丢字段、不制造成功响应、不在已提交后改换协议重提。能力矩阵应逐项列出“直接支持、可等价映射、上游不支持、待验证”，不得将“不支持”从北向合同清单删除。

CodeYY、Zapgogo 当前资料只证明部分创建、查询和下载合同，列表、取消/删除及其状态语义仍需核实。网关已有任务数据可用于构建本用户任务列表，但必须验证分页、筛选和删除后的可见性与 ModelArk 合同一致；取消生成需要明确的上游动作，不得仅停止本地轮询。现有插件路由/驱动合同不能承接的操作属于宿主最小接线缺口，应显式列入实现，不能因此裁剪北向。

标准南向的 `/content` 路径是协议事实，不能据此推导所有结果均有 URL，也不能要求所有提供商增加 URL 扩展。结果形态和 ModelArk 可表达性逐项验证，未覆盖的媒体交付场景明确记录。Videos 的 remix/edits/extensions 等动作不自动等价于 ModelArk 草稿或续作；只有可证明等价时才映射。

#### 3.3 以 ModelArk 为核心的参数映射

内部业务输入以完整 ModelArk 请求语义为核心，保留原始结构及合法扩展。现有其他北向兼容入口转换进入这一语义后再选南向；不能先压缩为 OpenAI `prompt/seconds/size` 而丢失原生信息。重试换渠道时从同一份未被改写的业务输入重新构造，不复用上一渠道改写过的 body；不因响应失败自动切协议重新创建任务。

| 参数 | 归一化与南向输出规则 |
| --- | --- |
| 文本 | 北向保留 `content[]` 的结构和顺序；仅在构造 Videos 南向时生成 prompt，不重复追加，不丢失混合输入含义 |
| 时长 | 北向使用 ModelArk 原生时长字段；南向映射为 `seconds` 或 `metadata.duration`。已有其他兼容入口的别名仍校验冲突、单位与上限，不用 `parseInt` 截断 `5.5/5abc` |
| 原生尺寸 | 北向保留 ModelArk 的 `resolution/ratio`；南向需要 `size` 时依据目标模型合同转换为像素尺寸，不把 720p 固定解释为横屏 |
| 供应商尺寸 | 将原生分辨率/比例映射到 CodeYY/Zapgogo 已确认的 metadata 字段；供应商输入别名及优先级不反向成为 ModelArk 北向参数要求 |
| 图片参考 | 从原生 `content[]` 图片项映射到标准 `input_reference.image_url` 或供应商 `images[]`；保留类型、数量和角色，不能只取首图或把对象字符串化 |
| multipart/文件参考 | 属于目标南向或已有兼容入口的能力差异；不为迁就它们要求 ModelArk 客户端更换输入格式。确有宿主 FileReference 时按目标能力构造，不假设 URL 示例证明文件上传支持 |
| 文件 ID | 只有可证明等价且归属正确时才映射为目标 file_id；不把本网关文件 ID 当上游 ID，不新增隐式上传 API |
| 多图/首尾帧 | 目标支持才映射；不能只取首图或把尾帧降为首帧 |
| 视频/音频参考 | 保留 ModelArk 原生内容项类型及角色；视频参考可按已知合同映射到 Zapgogo 的 `metadata.content[].video_url`，其他能力未明确时不得伪装支持 |
| 草稿/续作/remix | 不默认等价；复用宿主原任务权限、渠道固定和 ID 解析，不直接把公网任务 ID 当上游 ID |
| seed、水印、音频开关 | 按目标白名单处理，保留合法显式 `0/false`；显式但不支持的生成参数提交前拒绝 |
| 原生扩展与南向 metadata | ModelArk 原生合同字段在北向完整保留；仅按目标映射生成南向 metadata，不把整个请求或内部字段展开给第三方 |

时长上限复用 `relaycommon.MaxTaskDurationSeconds`，再与模型范围取交集；数量等乘数遵守[计费规则](../../.agents/rules/billing.md)。缺省值与非法零值、负值、非有限值分别处理，自动时长等特殊值未定义预扣规则前不支持。Go 可选标量用指针及 `omitempty`，JSON 编解码使用所属模块包装函数。

ModelArk 客户提供 URL 而目标只接受文件时，明确返回该渠道能力不匹配；本次不引入服务端下载参考素材再上传的隐式流程。验收夹具以 ModelArk 请求和响应为起止点，分别断言 Ark、标准 Videos、供应商扩展的南向报文，不能只测试 OpenAI 请求进入网关。

### 4. 生命周期与任务协议固定

创建成功后由插件生成少量有界状态，例如：

```json
{"protocol":"openai_video","profile":"seedance_zapgogo"}
```

Ark 新任务也显式固定协议。查询、状态解析、用量解释及媒体 URL 提取按任务保存值执行；渠道之后修改协议/扩展只影响新任务。渠道地址与凭据仍遵循现有任务机制，不宣称任意更换提供商仍能查询旧任务。

只接受目标合同明确的任务 ID；路径参数正确编码。Videos 的 `queued/in_progress/completed/failed` 等南向状态转换为 ModelArk 对应状态，例如运行中和成功分别呈现为其原生 `running/succeeded`；未知状态遵循明确错误及宿主轮询失败合同，不冒充成功。创建、查询、列表、取消/删除及错误均按 ModelArk 北向合同渲染，不能直接透出 Videos 原始数据。取消/删除与轮询、资金结算的竞争必须按同一任务状态协调，不能把客户端停止轮询等同于已取消生成。

`Task.Data` 会被新轮询响应覆盖，跨轮次必须保留的事实放入有界私有状态或既有受控持久化位置。每次返回新的 `PluginState` 都保留协议/扩展；不更新时可省略 state，不把媒体、巨大 metadata、完整请求或响应塞入其中。提交超限会丢失整份状态，字段顺序无效；普通 5xx/LocalError 也不能证明提交后不会重试，必须保留已创建任务 ID，避免重复生成和计费。

历史无状态任务只在已确认旧生产者范围内解释为 Ark；复用执行快照 key/version，必要时补充查询只读上下文。新版本无状态、未知协议或来源无法可靠识别时明确报错。发布、重启和回退都必须保留存量任务的查询与 URL 提取能力。

### 5. 按南向结果映射，北向固定为 ModelArk

#### 5.1 URL 是条件映射，不是统一必填项

硬性约束是 **北向协议始终为 ModelArk**。南向结果有 URL 时，插件将其映射到 ModelArk 对应的 URL 字段，保持 URL 交付，不将它下载成视频字节或改成 OpenAI 响应。`content.video_url` 是 ModelArk 视频结果的映射位置，不是要求所有南向采用的字段名，也不是所有状态、动作和响应都必须携带的字段。

| 南向实际结果 | ModelArk 北向处理 |
| --- | --- |
| Ark 原生结果携带 `content.video_url` | 按原生合同保留该 URL，仍使用宿主公共任务 ID、状态及既有权限检查 |
| Videos / 扩展通过 `url`、`metadata.url` 等已确认字段返回视频 URL | 由插件映射到 ModelArk 视频结果 URL 字段，同时转换状态、错误及 usage；不直接透出 OpenAI 外层响应 |
| 排队、运行、失败、取消等按合同没有视频 URL 的结果 | 按 ModelArk 对应状态和字段返回，不强行补 `content.video_url` |
| 完成结果没有 URL，或媒体形态尚未明确 | 核对实际回包及 ModelArk 合同的可表达方式，不构造下载地址、不声明已支持；确不能映射的场景明确报告兼容缺口，不以一个缺口排除整个提供商 |
| 返回需要渠道密钥的下载 API 地址 | 不把它冒充客户端可用的媒体链接，也不附带渠道密钥；记录该场景的交付能力缺口，不新增 content 代理或隐式下载上传兜底 |

当前 CodeYY 的 `metadata.url` 示例指向需鉴权的 `/content`，Zapgogo 资料只证明鉴权下载接口，尚需真实完成回包核实各自 URL 的访问方式。不能将“字段名为 url”当作可播放的证明，也不能将“文档未给出直传 URL”改写为整个渠道不得接入。

上游返回 URL 时保留原签名参数、路径及有效期语义；客户端可用性依据实际访问合同核实，不只按域名或 `/content` 路径判定。不得泄露渠道凭证，日志避免记录完整签名 URL。过期或不可用链接不能触发重新生成、重复扣费或把成功生成自动改为失败退款；生成状态、媒体交付和 usage 结算分别处理。

#### 5.2 复用原生呈现，避免扩大改造范围

现有任务插件合同允许原生 query presenter 从 `task.data` 呈现提供商 URL，应优先在豆包插件的 ModelArk 响应转换中完成映射。宿主继续承担任务归属、公共任务 ID 和生命周期；插件处理供应商字段。已有 `content.video_url` 不需要为了架构统一改成另一套资源地址。

“不转发 content”指本次不新增视频文件字节代理，不是删除 ModelArk 请求或响应中的 JSON `content`。南向有 URL 的 ModelArk 路径直接返回 URL；不要求客户端额外调用 `/v1/videos/{id}/content`，也不要求先经过网关 302。

已有 Videos、Responses、artifacts 和历史下载入口保持各自插件/宿主合同，纳入受影响范围的回归即可；本次不再强制把它们全部改成外部 URL 或 302，不全局禁用已有下载能力。如果实施发现某个既有调用点确实阻止 ModelArk 返回 URL，只对该调用点做最小接线并证明必要性。

### 6. `usage`、逐条对账与结算

#### 6.1 用量与账单分层

| 层次 | 权威依据 | 不得替代为 |
| --- | --- | --- |
| 预扣 | 经校验的请求参数、已冻结价格/倍率及有界估算 | 已确认实际用量 |
| 单条任务实际用量及对账 | 同一上游任务终态返回的 `usage`，按目标合同归一单位和字段 | 时长×像素估算、提示词 tokens、供应商日/月账单或后台金额 |
| 本网关单条金额 | 实际 `usage` 配合提交时冻结的本网关定价及折扣规则，经既有结算入口计算 | 供应商页面售价、账单金额倒推或 Sora 按秒价格 |
| 账期、结算日与供应商账单核对 | 账单层记录及明确的账期规则 | 对已保存原始 `usage` 的覆盖或伪造 |

本次不改账单日期规则、不采集供应商管理后台、不把 Zapgogo 的价格表写入本地内置定价。账单与逐条用量有差异时记录差异供核查，原始返回用量仍保留。

#### 6.2 提取、校验与恢复

1. 以目标合同明确 `usage` 所在位置、字段、单位、累计/增量语义和终态完整性。Ark 当前提取 `completion_tokens`、再考虑 `total_tokens` 的实现只能作为 Ark 现状；不能不经合同核对复制给两个兼容服务。
2. 关联公共任务 ID、上游任务 ID、渠道、实际模型和生产者版本，保存受控的原始 `usage` 证据及归一结果。不得把用量与完整媒体响应混存进无界 PluginState，也不能只保留会被下一次轮询覆盖的临时数据。
3. 实际用量必须是合法、有限、非负且在项目边界内的数量；区分字段缺失、非法值与合同允许的显式零。总量与分量不能重复相加，秒数不能冒充 tokens，视频生成 tokens 不能换成提示词 tokens。
4. 缺失或不完整 `usage` 时，不把该条标为已按实际用量对账，不将估算量标作实际量，也不解释为免费。保留预扣及异常证据，进入待核对/待补用量处理；补齐后通过现有幂等结算入口完成差额，不重新生成任务。
5. “待核对”是目标业务语义，当前代码是否能持久表达及恢复必须在实施中闭合。现有完成事实覆盖机制会保留遗漏的估算值，需要在本地视频接入处明确阻止其冒充最终用量；如现有状态/恢复入口不足，先补最小必要能力，再开放对应渠道，不顺带重写全局计费。
6. 失败、退款、超时和重复终态沿用既有资金安全与幂等规则；媒体 URL 交付失败不触发生成失败退款。明确覆盖“任务成功但 usage 未齐”“usage 已齐但 URL 不可用”两种独立场景。

两份资料都没有完整证明终态 `usage` 合同：下一步是获取逐条真实回包并写合同测试，不以“供应商要求看账单”为理由推迟或替换逐条 `usage` 对账。

所有实现遵循[计费规则](../../.agents/rules/billing.md)和[表达式系统](../../pkg/billingexpr/expr.md)：校验 → 预扣 → 实际用量 → 结算/退款全链路有界；金额使用项目统一安全转换，饱和事件进入关联审计，不能裸 cast 溢出或产生负扣费。数值 usage schema 的 description 使用“计费对象＋单价”，单位放 `unit`，不混入供应商价格或计量细节。

### 7. 原生代理与旧媒体方案的处理

`setting.proxy` 继续只作为需要时的网络出口配置，不能解决协议不兼容、缺少 `usage` 或缺少直传 URL。API 创建/轮询若仍受 HK 出口限制，可以复用已经支持的 HTTP CONNECT/SOCKS 正向代理；普通 NGINX API 反代不等同于正向代理。显式代理失败不能悄悄回退直连。

本方案不再建设或恢复 `media_via_base_url`、`/_newapi/media`、`X-NewAPI-Media-URL`、网关视频流式中转或“代理媒体下载失败兜底”。此前专用媒体方案的目标是修 HK 的媒体出站腿，仍承担全部视频带宽；URL 交付使客户端直连媒体源，已改变该问题的处理路径。客户端所在区域能否访问 CDN 仍必须实测。

工作区当前缺少相关专用代码，不执行旧文档的批量删除矩阵。线上或其他发布分支的历史媒体部署与存量任务按既有合同继续处理；本次方案不把停用、退役或强制 URL 迁移列为南向适配的前置工作。后续如需迁移，另以实际依赖和验收结果决定。

旧[NGINX 媒体转发参考](../40-operations/NGINX媒体转发入口配置.md)保留历史材料属性，不作为当前新部署目标。普通任务 API 反代、其他业务的网络代理及下载能力不在本次删除范围。

### 11.1 实现边界

- 豆包本地实现位于 [本地插件](../../plugins/local/doubao.js)，通过 `plugins.Source("doubao")` 的同 key 内置源码覆盖接入原有注册器。管理员安装的覆盖插件仍按原有优先级生效。上游 `plugins/tasks/doubao/plugin.js` 保持基线内容，后续合并上游行为时仍须评估本地覆盖的差异。
- 渠道新增表单位于独立 `video-upstream-fields.tsx`，复用现有 Form/Select 组件；南向设置方法位于 relaykit 独立文件，原文件仅保留字段与接线。
- 北向保持 ModelArk JSON。Ark 与 Videos 查询、列表共用宿主终态投影，取消、超时不再永久呈现旧 queued 快照。列表接受 `page_size` 1–500，支持 model/service_tier 和明确区分的失败状态；先排除已删除、图片及不匹配记录，再计算 total/offset。为兼容三种数据库，JSON 条件按有界批次读取后过滤；大量历史任务的列表开销仍需生产规模观测。
- 原生 Ark 支持 `duration=-1`，只在预扣估算时按模型最大时长保留额度。Videos 对不能表示的音频、标准视频参考、尾帧等语义明确拒绝，避免静默丢参。CodeYY Fast/Mini 1080p 纳入联合 usage schema，提交时仍执行所选提供商的能力校验。
- URL 保留原签名，不以长度或通用 `/content` 后缀误拒。已证实需要渠道凭据的 CodeYY 下载地址不作为客户端直传 URL；缺口写入插件 state 并通过 `X-NewAPI-Media-Delivery: unavailable` 报告，不新增二进制代理、不伪造 ModelArk 错误或改变成功生成状态。

### 11.2 usage 与资金恢复

任务成功时，在终态 CAS 内一并持久化 `tasks.usage_pending` 和 `private_data.usage_reconciliation`，保存原始预扣额及归一化事实。缺失/异常 usage 保留预扣；后台每任务至少间隔 60 秒按任务已固定的协议查询，重启后继续。取得实际 usage 后先持久化证据，再通过既有幂等结算 journal 进行差额处理，完成后记录 `settled_at` 并清除待核对标记。对账仍以实际返回 usage 为准，账单周期按实际结算日，未补齐前不把估算标为实际结算。

恢复使用提交时表达式/折扣快照；旧 token 计价和按次计价保留原有计费语义。已成功生成的任务即使后续查询 404、URL 不可用，也不重新生成或退款；上游始终不给有效 usage 时保留待核对，不能宣称已完成该条对账。修复前已进入成功终态且没有核对标记的历史行不自动追溯补扣；需要先核实原账单与上游证据后再纳入核对，避免猜测性收费。原生查询/列表用 `X-NewAPI-Usage-Reconciliation: pending` 提示此状态。删除仅合并结果不可取标记，不覆盖并发写入的 usage 证据；核对写入同样保留删除标记。

已补业务断言：上游取消成功后的状态/进度/完成时间与退款、退款重放不重复记账、轮询先赢 CAS 后取消返回 409 且不退款、终态删除保留账单行、删除与 usage 写入互不覆盖、缺失 usage 到补齐的持久化恢复、结算已完成但确认未写入时的重放幂等、核对阶段 404 保留成功和预扣。合法零用量仍沿用宿主既有合同；当前两家 Seedance 扩展的成功零 token 未获上游合同证实，保守进入待核对。
