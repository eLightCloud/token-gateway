# Seedance 视频增强方案

## 问题与目标

为现有 Seedance 视频渠道增加可选增强服务：管理员开启后，客户通过 `基础模型名-enhance` 调用一次“生成原片、增强、交付成片”的组合服务。用户无需了解两个上游任务、原片或内部重试过程。

本文记录已确认的方案和本次实现。核心代码、界面及本地回归已完成；真实 MediaKit 样片、OSS 转存及预签名下载已验证，Runy 2.0 已完成真实生成与 1080p 增强交付，正式价格、其他模型与主服务 DNS 环境仍待处理，未部署上线；具体已验证范围见实施计划文末。[实施计划](../50-planning/2026-10-15-Seedance视频增强实施计划.md)负责工作包与验证状态；[调研资料](../70-research/Seedance视频增强与火山AIMediaKit接入调研.md)保留官方来源与备选方案。本文中“已确认”来自用户，其余明确标为设计建议；不将建议冒充用户决策或当前生产事实。

### 已确认的业务边界

| 项目 | 已确认内容 |
| --- | --- |
| 模型 | Seedance 2.0 标准版、fast、mini，以及 2.5；不新增 1.0/1.5 增强入口 |
| 生成供应商 | 仅火山官方与 runyyitd；已有其他供应商普通能力不变 |
| 增强工具 | 第一阶段统一使用火山 MediaKit `enhance-video-generative` |
| 客户入口 | 保留原模型，增加一个 `-enhance` 模型；`resolution` 选择最终 `1080p` / `2k` |
| 重试 | 同一原片最多 3 次增强尝试，首次加最多 2 次重试，成功即停止 |
| 客户状态 | 内部重试期间仍为处理中，最终失败后才报告原因 |
| 增强任务原片 | 存入 `sd/` 并仅内部保留，不向客户提供链接、下载或公开 artifact |
| 普通生成交付 | 所有通过 doubao 生成驱动识别的 Seedance 视频存入 `sd/`，客户获取 OSS 预签名 URL；增强成片存入 `sd-enhance/` |
| 成功收费 | 增强模型整项服务统一按最终成片秒数收费，让客户容易理解；原片 tokens 仅用于内部成本核算 |
| 时长粒度 | 遵循火山 MediaKit 官方规则，按毫秒记录实际成片时长，以小数秒计算客户金额，不向上取整为整秒或整分钟 |
| 失败收费 | 最终失败全额退款，上游已发生费用由平台承担 |
| 对象存储 | 使用阿里云 OSS，在系统设置页面维护配置；本地已保存加密凭据与 `sd`、`sd-enhance` 两个前缀 |
| 存储策略 | 保存期限、自动清理、分层等暂缓，不在本次确定默认天数 |
| 验证顺序 | 先火山官方，runyyitd 接口合同明确后再验证该供应商 |

### 本方案给出的默认建议

增强流程内部固定生成 720p；未传最终 resolution 时默认 1080p；不主动插帧，保留原片时长、比例、帧率与音轨。以上规格需要样片验证，不是已有成功证据。720p 原片不满足工具实际长短边或 SDR 限制时，在增强前给出明确错误，不能仅按请求标签判定可处理。

成功任务按用户已确认的“最终成片秒数 × 综合单价”收费，不再向客户拆收生成 tokens 和增强费。具体售价之后由管理员填写；时长计量遵循用户要求的火山官方毫秒规则，不按整秒或整分钟向上取整，也不将示例价格写入生产。

## 优化方案

### 系统边界与实现方向

建议新增独立的增强编排模块，组合既有生成适配器、MediaKit 客户端和 OSS 存储边界。客户只有一条公开任务和一个计费会话，内部保存阶段与各次增强尝试。原生成插件仍负责真实供应商的生成合同。

不在这里锁定未经验证的插件加载技巧。实施 P0 必须先证明以下接线可行：增强别名能在渠道选择前被识别；生成上下文使用基础模型；计费上下文始终使用增强模型和完整 schema；查询各入口不会提前暴露原片。只有 P0 通过，才进入正式编码。

优先采用宿主侧专用编排/适配器包装，主体放在新模块中。不能注册另一个占用相同 legacy `channelTypes` 的插件；不能通过内部 HTTP 调用普通模型接口来重复鉴权或重复扣费；不能仅用后缀裁剪加 `model_mapping` 代替组合服务。

### 普通 Seedance 视频的 OSS 交付

全局“将所有 Seedance 生成视频存入 OSS”开关独立于增强服务；本地已开启。范围是 `doubao` 驱动中原始模型名或映射后的上游模型名以 `doubao-seedance-`、`dreamina-seedance-` 开头的普通生成任务，包含既有 1.0/1.5 与 2.0/2.5；这不扩大 `-enhance` 的四个精确模型白名单。未匹配到 Seedance 身份的自定义模型名需通过模型映射明确身份，不能按渠道名称猜测。

提交前确认 OSS 可写并冻结配置版本。生成成功后，先转存到 `sd/<公开任务 ID>/video.mp4`，再进入既有公开成功及结算流程；转存重试复用同一对象键，不重新生成、不调用 MediaKit、不增加额外扣费链。上游返回的状态补丁与宿主保存的 OSS 绑定合并，不能覆盖冻结版本。普通模型保留既有生成计价与用量对账。

ModelArk 单任务与列表中的 `content.video_url`、任务视频 artifact，以及 Responses 的视频产物地址统一返回 OSS 预签名 URL，有效期 24 小时；每次查询从固定对象引用重新签名，数据库旧快照中的过期 URL 不作为交付依据。OpenAI Videos 元数据保持原协议格式，下载入口重定向到 OSS 预签名地址。转存尚未完成时不向客户返回上游视频 URL；转存错误由既有轮询失败阈值与退款机制处理。

增强原片位于 `sd/<任务 ID>/source.mp4`，仅内部使用；增强成片位于 `sd-enhance/<任务 ID>/enhanced.mp4`，同样以 OSS 预签名 URL 交付。已提交或历史任务继续读取原冻结版本，旧版本单一前缀的对象仍可访问；调整新前缀不迁移既有对象。

### 模型身份和渠道匹配

#### 适用渠道类型

本方案覆盖下列现有渠道载体，不新增一个独立的“MediaKit 渠道类型”。业务范围仍只限火山官方和 runyyitd 的 Seedance 2.0 系列及 2.5；渠道类型符合不代表自动获得增强能力。

| 类型编号 | 当前渠道类型 | 增强接入条件 |
| --- | --- | --- |
| 54 | Doubao / 豆包视频 | 使用既有 doubao 生成驱动，实际生成供应商属于确认范围，并声明支持的基础模型 |
| 45 | VolcEngine / 火山引擎 | 同上；只对符合范围的视频模型开放，不影响该渠道的文本或其他普通模型 |
| 61 | Task Plugin / 任务插件 | 绑定 `doubao` 插件，且实际生成供应商、协议与模型合同均已核实 |
| 60 | New API | 绑定 `doubao` 任务扩展，核实上游普通基础模型合同；由本网关执行增强时，上游只生成原片，防止重复增强 |

54/45 来自当前 doubao 插件的 `meta.channelTypes`；61 通过 `task_plugin_key` 绑定，60 通过既有插件绑定/扩展列表接入，不能把 60/61 追加到插件的 legacy `channelTypes`。以上四类接线已由 P0 合同回归验证；不表示真实供应商调用已经验收。

runyyitd 是供应商身份，不是当前代码中独立的渠道类型编号；本地新渠道 117 采用类型 54，真实 2.0 已验证 Ark / standard，不将其套入 CodeYY 或 Zapgogo profile。其他载体和模型仍需对应合同证据。普通 OpenAI、自定义、其他视频厂商及绑定其他插件的渠道不因具有视频能力而自动纳入。

每个载体仍须同时满足渠道开启增强、模型/供应商合同匹配、完整价格及 MediaKit/OSS 就绪、当前调用方有权限，才发布可调用的增强别名。MediaKit 是这几类渠道共用的全局后处理服务。

#### 当前 ModelArk 支持的代码核对

当前实际加载的是 `plugins/local/doubao.js`：`plugins/embed.go` 的 `Source("doubao")` 明确返回本地覆盖源。不能仅依据上游工厂插件判断改造后的能力。

四类渠道均可承载该插件的 ModelArk 请求，但需区分客户入口与上游协议：

- 客户原生入口统一为 `/doubao/api/v3/contents/generations/tasks`，支持提交、列表、单任务查询及有能力边界的删除/取消；当前插件没有声明去掉 `/doubao` 前缀的客户原生路由。
- 54/45 通过 `meta.channelTypes: [54, 45]` 归属 doubao；61/60 通过保存的插件绑定匹配。`middleware/distributor.go` 与 `model/channel_constraint.go` 在后端区分这两种选择方式。
- `video_upstream_protocol=ark`（空值也默认 ark）时，54/45/61 向 `<base_url>/api/v3/contents/generations/tasks` 请求；60 的 `ctx.upstream.kind=new_api` 令路径变为 `<base_url>/doubao/api/v3/contents/generations/tasks`，因此 60 应指向提供该原生入口的上游网关，不能当作直连火山的同义类型。
- 设置为 `openai_video` 时，四类都改向 `<base_url>/v1/videos`，不增加 `/doubao`，并根据 standard、CodeYY、Zapgogo 合同转换参数。客户仍可使用本地 ModelArk 入口，结果由 `native.taskCreated/taskStatus/taskList` 转回 ModelArk 形态；这不表示上游也使用 ModelArk，亦不保证所有 ModelArk 特有参数可转换。
- 提交时将上游协议/profile 固定到任务状态，后续查询按固定值执行。删除/取消钩子仅接受固定为 ark 的任务，Videos 通路会返回能力错误。
- `VideoUpstreamFields` 已对 54、45、绑定 doubao 的任务插件及包含 doubao 的扩展渠道展示 `Ark native (ModelArk)` / `OpenAI Videos compatible` 选项。

2026-10-15 已运行现有针对性测试并通过：`./plugins` 的原生路由/legacy 归属、New API 路径、三种 Videos 请求映射、协议固定、ModelArk 投影及删除能力；`./relay/channel/task/jsplugin` 的 `TestTaskAdaptorChainsDoubaoThroughNewAPIUpstream`。这是本地合同和模拟上游验证，不是实际火山/runyyitd 调用证据，也不证明新增增强流程已经实现。现有驱动支持范围与第一期增强供应商范围分别判断。

火山官方示例映射如下；公开别名保留完整版本号，避免升级基础模型时改变同名服务含义。

| 客户增强模型 | 真实生成模型 |
| --- | --- |
| `doubao-seedance-2-0-260128-enhance` | `doubao-seedance-2-0-260128` |
| `doubao-seedance-2-0-fast-260128-enhance` | `doubao-seedance-2-0-fast-260128` |
| `doubao-seedance-2-0-mini-260615-enhance` | `doubao-seedance-2-0-mini-260615` |
| `doubao-seedance-2-5-260628-enhance` | `doubao-seedance-2-5-260628` |

runyyitd 按核实后的既有客户模型名派生别名，不擅自改成火山模型名。模型映射、分组权限、Token 模型限制、渠道权重和优先级仍参与选择；不能因为基础模型有权限就绕过增强模型的单独授权。

渠道配置建议在已有 setting JSON 中增加隔离的 `video_enhance` 扩展，包含启用状态和明确的生成供应商身份。使用独立解析/校验模块，保留未知配置和其他字段；现有 `video_upstream_protocol/profile` 仍描述原生成协议，不把“增强版本”塞进它们。是否需要扩展公共 DTO，须在 P0 证明本地扩展无法满足后再决定；`relaykit` 不得依赖宿主服务。

别名由“已声明基础模型 ∩ 允许供应商 ∩ 渠道增强配置”派生，不直接接受任意 `*-enhance`。管理员可先保存配置草稿；只有凭据、OSS、基础能力和完整价格都就绪时，别名才进入可执行路由。元数据可展示“未就绪”，`/v1/models` 只列当前调用方有权且可用的模型，不能先放流量再发现配置缺失。

关闭开关阻止新建增强任务；进行中任务沿用固定配置。普通模型不自动增强，已有 CodeYY/Zapgogo 等渠道的普通能力不被删除。

### 请求与任务状态

```text
客户提交 model=...-enhance，resolution=1080p 或 2k
  → 校验合同、权限、完整价格、凭据及 OSS
  → 固定渠道/模型/配置/价格快照，预扣一次
  → 生成 720p 原片
  → 原片转存私有 OSS
  → 提交增强尝试 1 → 失败时尝试 2 → 失败时尝试 3
  → 成片转存 OSS → 公开成功 → 一次最终结算
  → 若最终失败 → 公开失败及安全原因 → 全额退款
```

建议内部阶段为 `generating / source_storing / enhancing / output_storing / succeeded / failed`；客户只看到原有协议的处理中/成功/失败。原生查询、列表、Videos content、Responses 和公开 artifacts 必须一致，不允许任何入口穿透返回原片 URL。原片和配置秘密不放进对外 `task.data`。

只对已明确失败的增强任务创建新尝试；提交超时先用同一 `client_token` 恢复，不自动换 token 产生重复费用。每次真实新尝试有独立持久编号和幂等键。原片转存或成片转存失败只恢复对应存储阶段，不占 3 次增强尝试、不重新生成。各阶段有有限超时，重启后由既有任务调度恢复。

原片成功不得调用公开任务完成结算入口；最终失败与退款后，迟到成功不能再次扣费或恢复客户成功状态。增强模型缺少可信成片时长或价档事实时，沿用 `usage_pending` 机制等待对账，不用估算冒充实际用量。原片 tokens 缺失只影响内部成本对账，不阻塞已有可信成片用量的客户结算；普通模型原有 tokens 对账不变。最终失败仍必须退款，不能被缺失用量对账阻塞。

### 持久化建议

使用新扩展模型保存组合任务，避免把整个新状态机塞入原 Task 或插件的大段 JSON。建议一张增强执行表（公开 task ID 唯一）及一张尝试表（执行 ID + 尝试号唯一）：

- 执行表：基础模型、生成渠道、生成任务 ID、固定合同及价格引用、阶段、对象引用、真实生成用量、最终增强规格、下次执行时间及租约/版本字段。
- 尝试表：尝试号、幂等 token、上游增强任务 ID、阶段/错误、实际结果规格、已知成本及对账状态。
- 只保存凭据配置引用，不把 API Key 或 OSS Secret 复制到每条任务；更换配置需保证在途任务仍可取得原对象与所需权限。

跨实例通过持久租约/CAS 和上游幂等实现恢复，网络调用不放在长数据库事务内。使用 GORM、跨库整数/文本类型和唯一索引；不使用数据库特有 JSON 类型或私有锁语法。新增迁移必须通过真实三库 fresh/upgrade/二次启动验证后才能上线。

## 如何计价

### 已确认：整项服务按最终成片秒数收费

用户已确认统一按成片秒数收费，原因是让客户更容易理解。此决策替代此前“生成 tokens + 增强秒数”的混合售价建议；普通模型原计价不变。

```text
客户成功金额（USD）
  = 最终成片计费秒数 × 对应增强模型及最终输出规格的综合单价（USD/秒）

最终额度 = 现有安全舍入(客户成功金额 × QuotaPerUnit × 生效请求倍率)
最终失败金额 = 0
```

综合秒价覆盖视频生成与增强，客户不另付原片 tokens 费用。计费量只计最终交付的一条成片，不累计等待、处理耗时和失败尝试时长；第二或第三次成功不能乘尝试次数。现有分组等生效倍率由原计费链施加一次。

每个增强模型独立保存完整价格表达式，管理员按最终分辨率、实际输出帧率档位及合同明确区分的参考视频条件配置综合秒价。供应商不同的内部计量方式不改变公开的按秒合同；内部成本差异应纳入定价评估。具体单价、利润率由管理员填写，缺价和显式零价必须区分，不能运行时读取普通模型价格再临时加收费用。

### 时长粒度：按火山官方毫秒计量

用户要求遵循火山官方计费规则。2026-10-15 核对的 [MediaKit 视频工具计费](https://docs.volcengine.com/docs/Intelligentprocessing/video-tool-billing?lang=zh)通用规则及[计费常见问题](https://docs.volcengine.com/docs/Intelligentprocessing/billing-faqs?lang=zh)均明确：按分钟报价，底层记录毫秒级实际时长，再将累计时长换算成分钟出账。该规则直接适用于视频工具，不是从其他火山产品外推。

本服务据此按毫秒保存可信成片时长，客户以秒为展示和定价单位：`seconds = duration_ms / 1000`。10.2 秒对应 10200 毫秒，计费 10.2 秒；10.234 秒对应 10234 毫秒，计费 10.234 秒。不向上取整为 11 秒，不按不足一分钟补足一分钟。

应保留原始回包时长与规范化毫秒值，估算、结算、日志使用同一规则。秒数显示最多三位小数，可省略末尾零；金额显示舍入不能反向作为计费依据，最终额度仍沿用项目既有安全转换。官方未在上述文档说明亚毫秒到毫秒的转换方向、账单金额舍入或任务级与周期级金额舍入的差异；这些属于实施核验项，不能编造“官方四舍五入”或“向上取整”规则，也不据此推迟已明确的毫秒粒度决策。

采用官方时长计量规则不等于把 MediaKit 单项增强成本直接用作客户综合售价。客户仍购买生成与增强的一次完整服务；本次没有将“按官方的来”扩展为自动覆盖现有价格、改币种或按成本出售。

### 计量字段与 schema

以下是待实现的增强合同，不是当前 doubao 插件已经具备的字段：

| 字段 | 类型/单位 | 来源与作用 |
| --- | --- | --- |
| `seconds` | number / second | 最终成功交付成片的毫秒级时长除以 1000；由可信成功结果校验，不向上取整为整秒 |
| `output_resolution` | enum：1080p、2k | 最终交付分辨率，用于综合秒价档位 |
| `fps_tier` | enum：le30、le60、le120 | 按实际输出 fps 分档，而非仅信请求值 |
| `video_input` | enum：none、video | 仅在合同明确区分参考视频价格时参与选档 |

最终模型名选择本模型的价格表达式；秒数是计费量，分辨率、帧率和参考视频条件用于选档。实际输出必须满足请求合同，不能因上游产出更高规格便擅自收取更高价；规格不符按交付异常处理。

原片 tokens、原片 720p 规格、每次增强的处理量与成本在内部保存，不放入客户售价 schema，也不写入公共 `usage_facts`。numeric description 遵循插件规范，使用 `Video generation unit price` / `视频生成单价`，`unit` 为 `second`；编辑界面说明该价包含增强，不在 description 中写价格或协议限制。

目前 `UsageForModels(mappedModel, originModel)` 可能先选中基础模型 schema。必须在增强合同边界明确选择按秒 schema，并让价格保存校验、预览、预扣、后台轮询、最终结算使用同一份定义。不能因基础生成模型按 tokens 计费而把增强模型也结算成 tokens；不得以跳过 schema 校验解决。

### 表达式示例与算例

现有任务表达式直接返回美元，秒价不需要除以百万，也不使用任务表达式禁止的 `fixed()`。下面仅示意无参考视频、≤30fps 的两个价档，数字是假设售价，不是官方价格或生产建议：

```text
u("output_resolution") == "2k"
  ? tier("2k", u("seconds") * 0.04)
  : tier("1080p", u("seconds") * 0.02)
```

生产表达式必须覆盖实际开放的 fps 分档及参考视频条件；在进入表达式前校验允许的枚举，不能让未知分辨率落入示例兜底。以 10 秒与 10.2 秒成片为例：

| 情况 | 计费时长 | 假设综合单价（USD/秒） | 客户金额（USD，倍率前） |
| --- | ---: | ---: | ---: |
| 1080p，首次成功 | 10 秒 | 0.02 | 0.20 |
| 1080p，第三次成功 | 10 秒 | 0.02 | 0.20 |
| 1080p，小数秒成功 | 10.2 秒 | 0.02 | 0.204 |
| 2K，成功 | 10 秒 | 0.04 | 0.40 |
| 三次均失败 | 不按成功成片收费 | — | 0；退还全部预扣 |

本表为算术示例。此前对混合售价表达式的引擎验证不再适用于本版方案；当前按秒合同、结算与退款已运行本地回归；实际验证见实施计划，算例本身不代替执行证据。

### 预扣、结算与退款

1. 提交前确认增强模型按秒表达式及 schema 可用；不允许回退成基础模型的纯生成价。
2. 按请求的预期成片时长和最终价档预扣一次，冻结合同、用量估算、表达式和既有请求倍率；不再按生成 tokens 估算客户金额。
3. 自动时长等情况按已验证时长上界预留；没有可靠上界时，第一阶段拒绝该请求，不能零预扣放行。参考视频时长只在实际合同决定成片时长时参与估算，不另计一份参考视频秒数。
4. 原片成功仅记录内部生成用量，保留客户预留，不触发普通模型结算。
5. 增强和 OSS 交付成功后，以真实成片时长及合同价档，经 `RecalculateTaskQuota` / 正式任务结算链处理差额。成片计量缺失时进入对账，不以请求时长冒充实际值；仅缺生成 tokens 不阻塞客户结算。
6. 任一最终失败沿 `RefundTaskQuota` 及持久 journal 全额退还钱包/订阅和 Token 对应预留；重复通知、重启和 CAS 竞争不能重复退费。

已知成片时长将超过预留时，沿正式预留入口补足资金校验。最终结算沿既有 accounting 合同处理，不通过裸写余额或第二条扣费链完成。计费时长必须为有限、有效且符合项目上限的值；tokens 等内部成本字段也要验证，但不能重新成为客户收费乘数。校验覆盖 metadata、JSON/multipart、映射及参数覆盖路径，使用 checked quota 转换和饱和审计。

### 消费日志展示建议

消费日志的设计随按秒合同调整，以下为待实现展示建议，不表示现有页面已支持。客户只看到增强模型和整项服务金额，不拆生成费用与增强费用。

```text
消费详情
  模型          sd-2-mini-enhance
  任务 ID       task_xxx
  成片规格      1080p / 25fps
  计费时长      10.2 秒
  视频单价      0.02 USD / 秒（示例）
  金额          0.204 USD（示例，倍率前）
  生效折扣      按现有规则展示
  最终消费      按正式结算结果展示
```

客户不展示原片链接、生成 tokens、内部阶段、增强尝试次数或供应商原始错误。最终失败显示安全原因、最终净消费 0 和真实退款状态；退款未完成显示“退款处理中”，资金恢复后才显示“已全额退还”。

现有任务计费会分别记录预扣消费、差额补扣或退款。第一期保留这些财务流水，以同一公开 task ID 关联，并明确各条是预扣、补扣还是退款；任务详情汇总最终净消费，不能把多条流水当成多次服务，也不能将每条流水金额都标为最终总价。处理中状态在任务日志展示，预扣金额不得冒充已确认的最终消费。

管理员可查看内部原片用量、尝试状态、成本与安全错误摘要；上游任务 ID 等诊断沿既有 root 权限边界。现有详情会枚举公共 `usage_facts`，因此只放客户计费所需的秒数和规格，内部信息放持久私有字段或已有 `admin_info` / `root_info` 分区，后端按角色投影。不得仅靠前端隐藏，原始响应和错误 Content 也须检查，避免漏出原片或秘密值。

### 平台成本与官方增强价

平台成本单独记录：生成实付成本 + 所有实际计费的增强尝试 + OSS/流量等成本。失败尝试是否被火山收费尚无实付账单证据，不能全部按零算，也不能仅凭发起次数就认定每次已收费。

官方大模型版对输出 ≤30fps 的 1080p、2K 刊例价分别为 5、10 元/分钟；>30–60fps 翻倍，>60–120fps 为四倍。因此 10 秒理论增强成本分别为 0.8333、1.6667 元，不含生成与存储、折扣及未核实的账单金额舍入。时长粒度已核实为毫秒，不按整分钟进位。[MediaKit 官方计费](https://docs.volcengine.com/docs/Intelligentprocessing/video-tool-billing?lang=zh)

例如 10.2 秒、≤30fps 的单次增强，按刊例公式计算，1080p 为 `10.2 / 60 × 5 = 0.85` 元，2K 为 `10.2 / 60 × 10 = 1.70` 元；这是增强单项理论成本，不是生成与增强服务的客户总价，也不是已核对的实付账单。

官方成本是人民币，任务表达式售价为美元；不要直接把“5 元/分钟”填成“5 USD/秒”。成本报表如需换算，必须记录汇率来源、时间与固定快照；客户售价本身由管理员以合同币种配置，不能跟随实时汇率在同一任务内变化。资源包与折扣只影响实际成本，不自动重写客户表达式。

runyyitd 真实生成计费单位、usage 字段与价格需要其官方合同确认；内部按真实单位记录成本，不编造 token 换算。其客户增强模型仍按成片秒数收费，成本用量缺失单独对账，不改写公开计费单位。

## 约束、风险与验证

新增实现主体使用独立文件/模块；既有入口只做必要接线。不得扩大原插件原生分辨率数组，不得将本地能力下沉到 `relaykit` 并引入宿主依赖，不改首页、普通模型的生成与计价合同、原有供应商合同或组织只读账单的职责；普通 Seedance 仅增加已确认的 OSS 交付环节。

后台凭据配置复用现有管理员授权与会话保护；服务端落实权限、CSRF 防护、秘密值不回显/不入日志及必要的加密保存。实施时按 [OWASP ASVS 5.0.0](https://owasp.org/projects/asvs)、[认证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[秘密管理](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)建立适用控制与回归；本方案不声称已经符合这些要求，也未杜撰 requirement ID。

实现完成门槛、三库矩阵、真实 OSS 与官方样片验证见实施计划。真实 MediaKit 与 OSS 凭据已通过测试并保存于本地加密配置。官方方舟生成测试返回 401 / `AuthenticationError`，旧 runyyitd 凭据返回 401；最新 runyyitd 凭据已完成 2.0 普通生成与 1080p 增强交付，并在隔离网关验证 4.042 秒结算。本机系统 DNS 对视频源返回 `198.18.0.0/15` FakeIP，生产 SSRF 防护按预期拒绝；隔离测试进程采用公共 DNS 后，原片和超分 MP4 的真实 OSS 转存通过，未修改系统网络或放宽 SSRF。主服务仍需处理 FakeIP 解析并配置正式售价；其他模型与规格的验收不由单个 2.0 样片替代。
