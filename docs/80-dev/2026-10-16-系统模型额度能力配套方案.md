# 系统模型额度能力配套方案

## 一、问题与目标

本文件由 [Vantage 配套方案原稿](/Users/randy/code/elight/vantage-ai-center/docs/80-dev/2026-10-16-系统模型额度能力配套方案.md)复制到本系统，并按本次用户明确的业务边界重新评估。外部原稿保留在文末，仅作为需求来源；下述本系统口径优先。原稿关联的[双方对接协议草案](/Users/randy/code/elight/vantage-ai-center/docs/80-dev/2026-10-16-系统模型额度双方对接协议草案.md)也仍是提案，不能直接视为本系统已接受或已发布的合同。

### 1.1 已明确的业务边界

- Vantage 的企业对应本系统原生 `User`；企业共享资金就是该 `User` 的钱包额度。
- Vantage 的员工在本系统以原生 `Token/Key` 调用；本系统按 Token 及所属 User 执行已有准入、预扣、结算和退款。
- Vantage 负责企业、人员、成员关系及管理员权限。本系统只检查集成调用权限、目标 Token 的原生归属和可操作状态，不建设企业人员业务模型。
- 员工不查看、不管理 Key，本期不提供企业员工 Key 轮换。服务端在新操作和旧操作恢复前统一拒绝企业凭据轮换（`409 enterprise_rotation_unsupported`），避免已有轮换入口产生不限额 Token；个人凭据轮换保留。不扩展稳定人员生命周期账本。
- 额度以本系统的 User/Token 为事实边界；不新增独立成员钱包、成员累计消费账本、成员关系状态机或 Vantage 专属扣费链。
- 外部引用可以继续经既有集成绑定解析到 User/Token。该解析只承担受控寻址和归属校验，不成为新的业务决策来源。

本轮已按下述边界实现网关配套代码、机器合同和本地验证；真实部署与付费模型联调尚未执行。实现遵守 [AGENTS.md](../../AGENTS.md) 的最小接线要求及[计费规则](../../.agents/rules/billing.md)。

### 2.1 必须明确的字段语义

同一 Token 内，原生预扣/结算通常同时反向调整 `RemainQuota` 与 `UsedQuota`，因此二者之和可表达已配置的额度总量；提高额度只需调整原生剩余额度，保留原生使用量。不因自然月变化重建 Token 或清零使用量。

但 `UsedQuota` 在预扣时已经增加，并不始终等于最终已结算消费。不能把它无条件投影成“已结清消费”，也不能通过费用列表求和替代原生 Token 的准入余额。已结算、预扣占用、待核算与未知只能依据现有事实区分；依据不足就返回明确状态或未知值。

这是一项网关原生字段口径，不是 Vantage 人员的终身消费定义。人员退出重入、身份合并、跨企业历史与换发其他 Token 后的累计策略由 Vantage 处理，本期不在本系统新增承接机制。

## 三、优化方案与最小实施范围

### 3.1 原稿需求裁剪

| 原稿诉求 | 本系统实施边界 |
| --- | --- |
| 企业共享资金 | 读取和执行既有 User 钱包；不按员工充值或划拨 |
| 员工累计限额、跨月连续 | 同一原生 Token 的有限额度及累计使用字段；不设置月度重置 |
| 新员工默认 0 | 专用企业凭据首建事务内设置 `UnlimitedQuota=false`、`RemainQuota=0`、`UsedQuota=0`；个人路径不变 |
| 重复确保不重置 | 已有 Token 恢复原事实，不补零、不清消费、不重新分配额度 |
| 上限配置 | 在锁定原生 Token 后设置绝对总额度，并据原生占用计算剩余额度；不转账、不修改 User 钱包 |
| 修订、幂等、操作恢复 | 仅增加额度配置所需的修订和操作事实，绑定原生 User/Token；不得承载企业人员生命周期或第二套余额 |
| 用户/成员列表 | 专用接口按既有绑定安全投影 Token 列表，带有限分页；不建设人员目录 |
| 费用明细 | 从原生计费/日志查询做安全投影，按 User/Token 归属过滤；不复制费用账本 |
| Key 轮换后独立人员累计 | 不纳入本期合同；服务端拒绝企业凭据轮换，个人路径保留 |
| 成员撤权、退出重入及重新归属 | 业务决策属于 Vantage；网关只执行原生 User/Token 状态与已有明确调用 |
| 严格不可超支、每次上游尝试费用、所有未知费用 | 逐条核对原生能力后明确实际支持程度；不能借本次对接重写中转计费行为 |

### 3.2 独立文件与允许接线

实现已按以下粒度落地，旧文件只保留注册、初始化和响应接线。机器合同位于 `pkg/vantagequota/native-token-quota-1.openapi.json`，经既有专用认证下的 `/quota-contract` 提供。

| 层 | 独立实现候选 | 既有文件允许的窄接线 |
| --- | --- | --- |
| model | `model/vantage_token_quota.go`：原生 User/Token 范围读取、Token 上限调整、必要修订/操作事实与事务裁决 | `model/main.go` 仅登记必要的新配置事实；企业 Token 首建处仅调用默认额度规范化 |
| service | `service/vantage_token_quota.go`：金额校验、安全 DTO、原生归属和错误映射 | 原有错误映射仅接入企业轮换拒绝；账户停用统一复用 `409 account_not_active` |
| controller | `controller/vantage_token_quota.go`：严格解析、幂等头校验、成功/拒绝/查询结果外壳 | `vantageRespondProvision` 接入政策生效证据；复用既有受控响应和认证，不额外暴露秘密 |
| router | `router/vantage_token_quota.go`：独立额度/费用路由注册 | `router/vantage_integration.go` 增加一次注册调用 |
| verification | 优先扩展既有 Vantage 回归文件，集中保护默认零、调整与查询合同 | 不按调用层次散建测试文件 |

不预先增加成员额度表、额度用量投影表、Token 关联预算字段，也不修改 Token 缓存 schema。本轮保持原生预扣、退款、未知费用保留、重试、任务轮询和结算策略不变。若接口承诺需要这些改变，应作为明确的网关计费能力变化独立评估，不能藏在 Vantage 接线里。

### 3.3 配置事务与并发

1. 使用既有专用应用认证解析受管 User/Token，校验真实 `Token.UserId` 归属；调用方不能用任意内部 ID 或角色认领其他账户。
2. 在数据库事务中用 `lockForUpdate(tx)` 锁定目标 Token 和对应配置事实，读取当前原生占用与政策修订。
3. 同操作同目标同输入先恢复原结果；相同操作标识复用不同输入/目标明确冲突。政策修订只随配置变化，不随消费变化。
4. 根据请求的绝对总额度更新原生 `RemainQuota`，保留 `UsedQuota`；不修改 User 钱包。绝对额度低于当前原生占用的情形，在正式合同中给出明确的拒绝或接纳政策，不由 Vantage 计算。
5. 配置副作用与操作结果同事务提交；事务失败不产生半生效结果。提交后按现有 Token 变更机制处理缓存 fence/失效。
6. 耗尽状态恢复只处理额度耗尽，人工停用及到期仍按原生状态执行；不能用设置额度绕过凭据有效性。

“上限配置”保证的是原生 Token 政策正确、操作可恢复。它不额外承诺每笔实际上游费用均不超过预估，也不改变已发生费用入账规则。

### 3.4 金额与安全合同

- API 必须声明 `currency`、十进制字符串精度、quota 换算与舍入。显示币种配置及汇率变化不能偷偷改变一次已记录配置操作的含义；正式合同未冻结前不发布伪确定样例。
- 企业资金和 Token 可用额度由网关按原生事实返回；Vantage 只展示，不据资金快照代替网关准入。
- 无法证明的已结算金额或待核算金额返回未知和原因，不补零、不默认无限额。
- 用户列表、费用分页和操作查询必须限定受管 User/Token；游标绑定账户与过滤条件。操作查询不跨账户恢复别人的结果。
- 查询响应与错误排除 Key 明文、集成口令、prompt、客户正文和完整 `Other` 内容。员工和浏览器不持有网关 Key 或集成认证。
- 沿既有安全边界执行专用服务端认证、来源约束和不可缓存响应。涉及凭据有效性时遵守项目要求的 OWASP Authentication / Session Management 指引，不由请求中的 `actor_ref` 或 `is_admin` 赋权。

## 五、实施结果与验证记录

### 5.1 已实施能力与合同

- 企业 Token 首建事务内为原生有限零额度；个人构造器不变，已有企业 Token 恢复不覆盖额度与使用量。
- 两张新增表仅为 `VantageTokenQuotaConfig`（TokenId、修订、政策摘要）和 `VantageTokenQuotaOperation`（配置意图及原操作结果），不保存第二套余额、消费或人员归属。
- 原生 `UsedQuota + RemainQuota` 表达有限 Token 总额度；上限设置为绝对值，保留原生使用量，不改 User 钱包。低于当前 `UsedQuota`（含原生预扣占用）明确记录为拒绝。
- 配置写入和操作结果在同一事务提交；相同操作恢复原结果，输入或目标不同则冲突。UUID 统一小写，金额规范化后计算请求指纹。消费不推进配置修订；观察到原生后台修改额度或不限额政策时推进修订，使旧草稿不能覆盖新政策。
- 因零额度落为 exhausted 的 Token，在剩余额度转正且未过期时可恢复；人工停用、到期、删除不会被额度配置启用。修改前后复用原有缓存 fence/失效机制，缓存写入失败不提交新配置。
- 确保企业凭据的响应追加 `quota_setup`，独立表达政策状态和原生额度投影。存量不限额 Token 返回 `not_ready`，不自动补零；管理员可经明确调整设置有限额度。
- 金额合同为网关原生 USD，输出六位小数字符串、明确 `quota_per_unit`，输入要求精确映射为原生整数 quota，越界拒绝。它与页面显示币种、人民币汇率独立；已提交操作保留当时的金额与换算比例，恢复不依赖当前换算配置。
- Token `accounted_amount` 明确包含原生预扣占用；通用最终消费/预留拆分证据不足，`spent_amount`、`reserved_amount` 保持 `null`，`usage_state=unknown`，不补零。费用记录带账户与既有凭据引用；未绑定集成凭据的原生日志，其 `credential_ref` 为 null。费用列表仅为原生消费/退款日志投影，`completeness=recorded_logs_only`，不构成最终账单或全量计费证明。

以下路径相对 `/api/integrations/vantage/v1`，均复用既有专用口令、TCP 来源约束和不可缓存响应。操作的 `actor_ref` 只记录责任，不授予本系统管理员角色。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /quota-contract` | 获取提供方机器合同 `native-token-quota-1`（OpenAPI 3.1） |
| `GET /enterprise-accounts/:tenant/funds` | 原生 User 钱包及当前可用资金投影 |
| `GET /enterprise-accounts/:tenant/token-quotas` | 按既有凭据绑定分页投影原生 Token，不新增员工目录 |
| `GET /enterprise-accounts/:tenant/credentials/:credentialRef/quota` | 原生 Token 总额度、占用、可用额度和配置修订 |
| `PUT /enterprise-accounts/:tenant/credentials/:credentialRef/quota` | 绝对额度配置，正文与 `Idempotency-Key` 标识同一操作 |
| `GET /enterprise-accounts/:tenant/quota-operations/:operationID` | 查询本账户原操作及其 applied/rejected 结果 |
| `GET /enterprise-accounts/:tenant/usage` | 原生日志分页投影，可按凭据、模型、起止时间筛选 |

配置请求包含 `operation_id`、`expected_revision`、`currency=USD`、`limit_amount`、`actor_ref`。HTTP 200 表示操作投递成功，必须检查 `operation.status`；`rejected` 不表示额度已生效。拒绝原因包括旧修订、原生凭据不可用、目标总额度低于原生已占用额度。

操作记录无自动过期清理，主库查询读取已提交事实；单次 404 不能排除仍在途的 PUT。费用/Token 分页默认 50、最大 100，HMAC 游标绑定账户和过滤条件，按记录 ID 上界及递增位置翻页；数值是实时投影，不承诺跨页事务快照，晚到/修正记录需重新刷新。起始时间包含，结束时间不包含，时间筛选使用整秒 RFC3339。

## 三、优化方案

### 3.1 稳定用户归属

Vantage 专用集成继续使用既有应用命名空间、企业外部引用、用户外部引用和成员关系引用解析真实对象。上游内部账户 ID、Token ID 和管理员角色不由调用方任意指定。

累计额度由稳定业务身份拥有，员工 Key 只提供受控调用身份。轮换、撤销旧代次、响应丢失后恢复等情形不能产生新的个人额度周期。当前成员关系失效必须停止后续企业调用；历史费用保留原归属。

成员离开后重新加入、个人迁入企业和历史费用修正的连续累计范围，需要提供方在正式合同中明确。Vantage 只消费这些结果，不按用户名、手机号或 Key 用量猜测归属。

### 3.2 新企业用户默认零额度

在 Vantage 专用企业员工开通路径中落实默认累计限额 0，并确保首次可能付费调用前政策已经有效。不能先发一个无限额 Key，等 Vantage 后续异步补写 0 才达到目标。

现有账号或凭据幂等确保必须恢复原对象，不重置已调整限额或历史消费；轮换不重新执行初始额度分配。接口需提供零额度政策已生效的安全证据，不能只返回 Key 为 active。

如尚不能完成该政策，专用能力应明确未就绪，不能对 Vantage 宣称零额度已生效。已有不限额企业成员的接入、历史消费起点和初始上限应有独立迁移范围；不对生产历史默认补零或清账。

### 3.3 累计上限配置

管理接口设置 **绝对累计上限**，例如从 500 元改到 800 元，不解释成再增加 800 元。历史消费由原有可信事实保留；提高上限不产生钱包转账。

同一配置操作绑定稳定目标、请求指纹、预期配置修订和操作标识。同操作同请求重放恢复原结果；不同请求复用同标识明确冲突；并发管理员修改不能相互静默覆盖。

配置修订表达限额政策变化，不应因每笔费用结算就把所有管理员草稿机械判成政策冲突。结算与调整之间的并发金融语义仍由 Lighting 定义和执行。

降低到已消费金额以下、存在待核算费用时调整、零上限与临时停用的关系，由提供方给出可解释的接纳或拒绝结果。这里不替提供方定义新的金额政策。

### 3.4 专用查询与安全投影

按[唯一对接草案](/Users/randy/code/elight/vantage-ai-center/docs/80-dev/2026-10-16-系统模型额度双方对接协议草案.md)提供企业资金摘要、用户额度列表 / 详情、费用明细及配置操作结果。原始内部钱包、账单、Token 和供应商结构不直接作为外部 DTO。

每个数值带明确币种、金额表示、来源、时间和适用范围。零、未提供、待核算及查询不可用能被区分；未知费用不能投影成零。可用额度必须由 Lighting 返回，而非要求 Vantage 根据上限减去某个缓存消费值。

用户列表、费用列表和操作查询限定应用命名空间与企业范围，带稳定分页。相同操作标识不能跨企业取到其他操作。响应和错误不能包含 Key、集成口令、prompt、客户正文或上游原始敏感信息。

### 3.5 计费边界和调用错误

真实模型调用继续使用 Lighting 当前可信调用与计费链。预留、付费重试、取消 / 断连后的费用、未知及对账修正由 Lighting 处理，其行为不能依赖 Vantage 页面在线或预先查一次余额。

Lighting 向现有标准协议返回安全且可区分的账户不足、用户上限不足、成员失效和模型不可用等原因。具体金融承诺和费用结果由提供方证据说明；Vantage 仅映射错误，不对未知结果补做扣费或释放。

### 4.1 提供方必须覆盖的验证

1. 两个用户共享一个企业资金账户，调整其中一人的上限不划拨资金，也不修改另一人的上限。
2. 新用户 0、提高绝对上限、跨月不重置；重复开通不覆盖已有上限和消费。
3. Key 多次轮换、旧代次失效、轮换响应丢失后恢复，累计归属一致。
4. 同操作同请求重放、同标识不同输入、相同预期修订并发修改及结果查询均可区分。
5. 模型断连 / 超时 / 取消和晚到费用的状态真实；Vantage 下线不会解除资金或个人约束。
6. 费用明细和查询分页不重复放大消费，跨应用 / 企业 / 成员关系访问被拒绝。
7. 提供方错误及观察事件不含凭据和客户正文；接口未提供的金额显示未知而非补零。

## 五、未决事项与交接顺序

双方需先冻结：外部金额口径及精度、累计起点 / 重新入企规则、降低上限的提供方政策、配置操作查询的一致性和保留期、新合同版本标识及存量接入方式。需要财务语义确认的事项由 Lighting 维护者决定，Vantage 不通过用户访谈另定一套计费规则。
