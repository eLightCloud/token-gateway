# 组织计费用量与日志查询优化方案

## 1. 问题与目标

组织详情的“计费”页出现趋势有数据、汇总为 `$0`、成员与渠道用量为空；“日志”页显示“暂无数据”。本方案处理这些入口在千万级日志下的可用性、统计一致性及可恢复查询。

推荐采用：**计费用量按北京时间分片，后台生成可复用的多维原始日志汇总，页面各区域读取同一份已发布快照；日志明细采用有界、可追溯的游标分页。** 复用计费账单已有的任务框架、类型内租约、单次查询预算及版本发布方法；跨统计任务的资源许可尚待建设，不能当作现成接线点。

本文件是待实施方案。本轮仅只读核查和编写文档，未修改业务代码、数据库配置、索引或数据，未重启服务。以下本地实测不能当成生产环境诊断或生产验收；线上千万级容量是设计与待验收要求。

### 1.1 与已有方案的关系

- 本文负责“计费”的原始日志用量、渠道用量和日志查询；不重新定义最终费用、退款、钱包或人工结算。
- Invoice 业务口径继续以[组织账单实际消费汇总与加载修复方案](./2026-10-17-组织账单历史调额兼容修复方案.md)为准。
- 后台机制参考[组织账单性能与账务完整性优化方案](./2026-10-16-组织账单性能与账务完整性优化方案.md)，现有实现以本轮代码核查为准，不能把其中历史版本描述当成当前代码。
- 筛选选项与[结算系数设置加载优化方案](./2026-10-17-组织账单结算系数设置加载优化方案.md)可共享已证明覆盖的原始模型集合依据，但两个入口的范围、资格及失效依赖必须分别核对。该专题的历史模型准备目前只有方案，未实施，不作为本方案现成依赖。

### 1.2 评审结论与实施前置

综合评审结论为：保留总体架构，P0 可先实施；P1 新缓存及后台构建须先补齐并验证以下三项合同，不将文档修订等同于代码已具备能力：

1. 各日志来源的失效责任、可靠投递／重试及重启恢复依据，覆盖日志成功而失效确认失败的情形，见 3.5.1。
2. 跨统计任务共用的数据库资源许可及失租行为，在新重任务上线前生效，见 3.8。
3. 当前日快照的固定推进、查询复用与手动刷新行为，见 3.4.1。

日片有效性粒度在表结构／缓存键定稿前确定；快照退役、容量上限及生产验证在上线前完成。两项均为设计与交付要求，尚不是已发生的新缓存故障。普通用量与 Invoice 继续各守原有业务口径，不新增统计平台或第二套费用计算权威。

## 2. 当前实际情况

### 2.1 已验证环境与直接故障

2026-10-17 核查了当前工作区运行的后端及 `new-api-dev-pg`。连接凭据和真实成员信息不写入文档。

| 检查项 | 实测结果 | 证据边界 |
| --- | --- | --- |
| 数据库 | PostgreSQL 18.4；数据库约 16 GB | 本地开发环境 |
| 日志规模 | `pg_stat_user_tables.n_live_tup` 为 12,829,991 | 统计估值，并非重新全表 COUNT |
| 日志存储 | 表约 12 GB，索引约 3,825 MB | 说明访问与索引成本，不直接推导查询耗时 |
| 组织成员 | 组织 1 有 174 段关系，涉及 174 个用户 | 包含历史关系；各账期实际有效范围需取交集 |
| 容器共享内存 | `HostConfig.ShmSize=67108864`，即 64 MB | `/dev/shm` 独立于普通数据盘 |
| PostgreSQL 参数 | `dynamic_shared_memory_type=posix`，`max_parallel_workers_per_gather=2` | 多个并发重查询可能叠加共享内存需求 |
| 普通数据盘 | 容器所见文件系统约 770 GB 可用 | 不能将错误解释为普通磁盘已满 |
| 实际数据库错误 | 后端日志在故障时段记录 33 次 `SQLSTATE 53100` | 包括汇总、成员、模型、渠道、趋势和日志计数 |

PostgreSQL 容器原始报错：

```text
could not resize shared memory segment "/PostgreSQL.…"
to 12615680 bytes: No space left on device
```

错误明确指向并行查询的动态共享内存分配失败。查询退出后空间释放，因此事后 `df /dev/shm` 有余量，不否定故障时已耗尽。

对应本地证据：[后端日志](../../logs/dev/backend.log)第 2151 行为渠道 GROUP BY 失败，第 1397 行为汇总失败，第 1487 行为日志 COUNT 失败。日志文件会轮换，本文保留错误、入口和范围作为可复查摘要，不把本地文件当永久审计存储。

### 2.2 渠道确有数据

以北京时间 `2026-10-01 00:00:00` 至 `2026-10-17 23:59:59`，按组织成员计费起点、离开时间及 `type=2` 过滤，在只读事务中临时设置 `max_parallel_workers_per_gather=0` 后成功汇总：

| 指标 | 结果 |
| --- | ---: |
| 渠道分组数 | 22 |
| `channel_id=0` 分组数 | 0 |
| 消费日志条数 | 846,817 |
| 整数 quota 总和 | 3,366,040,270 |
| 输入 Token 总和 | 8,182,087,451 |
| 输出 Token 总和 | 719,315,869 |

渠道分组再相加与此前组织总量核查一致。前四日的请求数、Token 总数也与用户截图逐项一致，包括 10 月 1 日的 50,910 条、112,250,398 Token。

这证明相同范围内渠道数据存在，不能将空表解释为没有消费。上述“条数”沿用原始消费日志统计，尚不是 Invoice 去重后的业务请求数或最终费用。

### 2.3 渠道为什么显示为空

实际链路：

```text
AdminOrganizationDetailPage
  → GET /api/admin/organizations/:id/billing/channels
  → AdminGetOrganizationBillingChannels
  → GetOrganizationBillingChannels
  → 逐成员查询 logs，GROUP BY channel_id
  → 任一查询错误即终止整个接口
  → HTTP 200，success=false，无 data
  → 前端读取 data?.data，空值进入“暂无数据”
```

代码依据：[渠道聚合](../../model/organization.go)、[控制器](../../controller/organization.go)、[请求封装](../../web/src/features/organizations/api.ts)、[页面与 DimensionTable](../../web/src/features/organizations/index.tsx)、[错误响应](../../common/gin.go)。

补充排除项：

- 这是系统管理员组织详情入口，有独立渠道查询；用户侧部分身份隐藏渠道的规则不能解释这次故障。
- 渠道名称由主库补全；名称查询失败保留原统计行，页面可用渠道 ID 展示，不会因此主动把全部金额删除。
- 查询当前按全部渠道分组，没有发现固定前 N 个渠道的展示截断。
- `channel_id=0` 或渠道已删除时也应保留分组；不能为了补名称而 INNER JOIN 掉这些历史记录。

### 2.4 查询与错误展示共同放大故障

1. 汇总、成员、模型、渠道和趋势各自查询，且逐成员执行 SQL。同一页面重复扫描相近数据。
2. 筛选选项额外同时调用成员、模型和渠道统计，传入空参数。用户即使选择本月，筛选选项仍读取成员计费起点以来的历史；任何一个选项接口失败又使整个选项响应失败。
3. 日志第一页先逐成员 COUNT，再逐个有记录的成员取最新记录，最后在 Go 中合并；不是数据库直接读取 20 条就结束。
4. 已观察到整段汇总约 82.6 秒、趋势约 88 秒，单成员 `LIMIT 1` 约 91 秒和 137.6 秒。耗时来自不同请求，不能相加当成一次页面耗时。
5. 实际计划中存在按时间索引扫描再过滤用户；缺少与所选查询匹配的访问路径。`idx_created_at_id` 实际为 `(id,created_at)`，与当前源码期望 `(created_at,id)` 不同。
6. 汇总及各维度等单接口请求封装直接返回响应，未将 `success=false` 转为查询失败。筛选选项组合函数是例外：它检查子响应并返回失败对象，但页面仍未据此正确呈现错误。页面未区分等待、失败与真实空结果；缺失金额补零，缺失列表显示空表，HTTP 200 不代表统计成功。
7. 这条普通计费链路没有接入 Invoice 的后台分片与语句预算。关闭页面或切换日期后，旧统计未必停止。

## 3. 优化方案

### 3.1 先固定统计含义，再选择复用边界

| 内容 | 普通计费／日志当前语义 | Invoice 当前语义 | 本方案处理 |
| --- | --- | --- | --- |
| 金额来源 | 默认原始 `type=2` quota 之和 | 普通确认费用与任务最终费用归并 | 分开标记语义，不能静默替换 |
| 请求数 | 符合条件的日志行数 | 按费用来源归并后的业务数量 | 保留各自合同，不强求两者相等 |
| 时间 | 日志 `created_at` 与成员有效窗口 | 原消费归属、费用确认及证据范围 | 使用明确的时间字段及版本 |
| 维度 | 成员、模型、渠道、输入／输出 Token | 现有消费片主要保留用户、模型、月份、quota、数量 | Invoice payload 不能恢复丢失维度 |
| 展示金额 | 原始 quota 按显示单位换算 | 另有分类结算系数、钱包分项 | 不再按当前模型单价重算日志 |
| 一致性 | 各接口在不同时点独立读取 | 有持久结果、构建代次和条件发布 | 复用发布方法，不复制金额算法 |

**本方案首版保留普通计费的原始日志用量语义。** 页面说明其与“最终结算账单”的区别；若后续要求普通计费也展示确认费用，必须作为显式业务变更评审，处理任务的渠道／Token 归属及历史缺失，不由缓存优化顺带改口径。

例如预扣 100、最终费用 10、退款 90 的任务，原始 `type=2` 汇总和 Invoice 的 10 可能不同。不能为了页面相等，把所有退款按渠道粗暴相减，或者把 Invoice 最终费用再减一次退款。

普通计费内部的汇总、趋势、成员、模型、渠道必须一致；普通计费与 Invoice 要求来源可解释，不要求金额机械相等。Invoice 的消费及确认规范只引用已有方案，不在本文建立第二份合同。

### 3.2 切片、缓存与一致性分别解决什么

| 机制 | 解决的问题 | 单独不能保证 |
| --- | --- | --- |
| 时间片与有界批次 | 单次工作量、超时后的恢复 | 索引不匹配时的物理扫描量；跨接口同版本 |
| 跨请求日结果缓存 | 不重复处理稳定历史 | 迟到、更正后仍有效 |
| 持久任务与租约 | 离页、重启和多实例恢复 | 查询一定低负载 |
| 来源／成员版本与覆盖清单 | 证明哪些片能组合 | 跨库全局事务快照 |
| 条件发布的完整快照 | 所有统计区域引用相同结果 | 原始来源本身完整或已人工确认账单 |

千万级持续写入场景推荐同时采用以上机制。不能只分别给五个接口缓存 60 秒，也不能每天重算整月后称作增量；不能以分片数量推断扫描量已经受控。

### 3.3 持久化原始用量日结果

建议新增独立的 `organization_usage_*` 模块及派生表，不扩写现有 `model/organization.go` 承载主体实现。以下名称为拟议结构，实施时核对现有能力后确定，尚非已创建的表。

| 派生对象 | 最少内容 | 用途 |
| --- | --- | --- |
| 用量片结果 | 北京时间半开范围、组织／成员归属依赖、来源身份及修订、计算版本、完成状态；按用户＋原始模型名＋渠道 ID＋日志类型聚合的 quota／行数／两种 Token | 稳定日期跨快照复用 |
| 构建记录与覆盖清单 | 请求范围、代次、来源边界、成员 hash、每片精确修订引用、进度和失败信息 | 重启恢复及无缺片组合 |
| 已发布视图 | 统计口径、实际覆盖、来源时点、快照 ID、各区域结果及完整性状态 | 页面一次读取完整一致结果 |

实施约束：

- 首版服务当前 UI 的默认消费日志类型；旧端点支持的其他类型／对账筛选继续保留，不能在新路径中忽略参数并假装支持。扩展类型时单列语义和回归；已存在的合法带符号调整不能套用 Invoice 的“所有消费片必须非负”条件误拒。
- 聚合粒度包含用户、模型和渠道的联合维度。只分别保存成员总量、模型总量、渠道总量，无法正确响应“指定用户＋模型＋渠道”的组合筛选。
- 时间使用 `[start,end)`，与成员精确秒级窗口取交集；跨日转组织、退出后重新加入不得双算。
- 整日不能覆盖的自定义边界须计算精确边界片；不把整日金额直接拼入部分日期范围。
- 累计使用有界整数／既有精度规则。保留零费用有 Token 或有行数的分组；禁止按天先换算舍入金额后相加。
- 汇总行数、Token 和 quota 为可加指标；“活跃用户”应按合并范围内用户集合求并集，不能把每天去重人数相加。现有 `active_member_count` 实际统计当前有效成员，与 UI“范围内有用量”文案并不相同；首版保留旧字段，新增用量用户指标或修正文案，不能静默改旧字段含义。
- 渠道 0、已删除渠道、空模型名仍参与守恒；名称和当前价格只用于展示。名称或当前价格变化不触发原始 quota 重算，当前价格不得冒充历史计价依据。
- 不保存逐笔 `other`、完整日志副本、钱包余额或新的费用权威。联合维度基数必须实测，最坏可能接近日志行数；结果按有界页／子片保存，不使用无限制整月 JSON 作为中间态。
- 持久结果为基础；Redis 和浏览器缓存仅加速读取。不能只在单进程内存保存任务进度或正确性所需版本。

### 3.4 同一版本构建与统一发布

```text
选择组织及日期
  → 规范化范围，固定日志用量语义及成员窗口
  → 命中有效已发布结果：直接返回全部统计区域
  → 缺失：登记唯一构建，返回 building 与进度
  → 既有任务框架调度，有界读取日片，必要时细分
  → 校验覆盖、依赖及各维度守恒
  → 以代次条件原子发布视图
  → 页面与统计导出固定读取该 snapshot_id
```

一致性要求：

1. 构建开始保存源库身份、口径版本、成员窗口 hash、覆盖截止、证据版本／修订以及适用的高水位。覆盖截止和证据到达时点分别保存，不能把昨天的数据日期当成所有记录已投递到齐的证明。
2. 每个已发布视图固定引用精确片修订。新片覆盖旧缓存行不能改变旧视图；采用不可变片修订或在视图发布时物化完整结果，两者以容量实测选定。首版优先物化最终统计结果并保留覆盖清单，避免读时再次组合可变中间态；各维度结果按有界页／行保存，不把高基数全结果塞进一个无限 JSON。
3. 完整覆盖目标范围后才进入 `ready`。缺片、查询失败、取消、来源不明和真实零行明确区分；进度百分比不是数据完整性证明。
4. 发布事务校验构建代次、租约和依赖修订；失败重试对同一片替换完成结果，不追加累计。失去租约的旧 worker 禁止发布。
5. 一个新端点返回汇总、趋势、成员、模型、渠道和元信息，消除五个接口各取最新版本的问题。响应过大时允许后续维度分页，但必须携带相同快照 ID，不能每页重新取最新结果。
6. 当前筛选后的 quota、行数、输入与输出 Token 均须满足：汇总＝各趋势日之和＝成员之和＝模型之和＝渠道之和。校验用原始整数，不比较已格式化金额。成员零用量行和展示 top N 必须保留完整合计或显式“其他”。
7. 刷新登记新代次，不原地改旧数值。可继续展示同一筛选范围的上一份结果并标明截止和更新状态；不能拿其他日期缓存当当前结果。来源更正已令旧结果失效时，明确标记待重建，不再声称有效完整。

缓存键／清单至少区分组织、规范化精确范围、原始日志口径版本、成员依赖、源库身份和来源修订。筛选后的视图还须区分用户、原始模型匹配语义、渠道及类型；分页参数不改变统计来源身份。既有 `%` 匹配与参数校验必须复用，不能悄悄改为前端字符串包含。

组织／范围相同而仅筛选变化时，优先对已准备的联合维度结果进行小表聚合，生成同来源版本的筛选视图；不因为选择了另一用户或渠道就重新扫描原始日志。对很长范围也需限制日结果合并与维度行数，超预算继续后台组装，不能把慢查询从 logs 平移到无限量缓存解码。

#### 3.4.1 当前日推进与请求复用

首版采用固定时间桶推进当前日截止，建议初始桶宽为 5 分钟，作为待验证的技术参数，不代表实时性已验收。实际参数在实施交付中记录；不得在每次 HTTP 请求中以当前秒生成新构建键。

- 请求范围已全部到达（包括当天自定义的历史时段）：使用请求的完整精确范围，稳定片保持有效；迟到／更正另走来源失效，不靠定时删除历史缓存发现变化。
- 范围包含当前时刻：实际覆盖截止取不晚于请求结束和当前已到达时间的最近桶边界，保存独立于请求日期的 `covered_until`；未覆盖的当前桶明确显示更新截止，不宣称覆盖到今天结束。
- 在当前桶内，相同组织、范围和来源依赖复用同一发布结果／构建。同范围仅筛选变化复用联合维度结果，不登记新的源扫描。
- 有活跃查看请求的范围，在桶推进后登记下一截止的唯一构建；后端读取状态即可幂等触发，不要求浏览器保持打开。需自动预热的组织由已有调度框架登记，未预热范围下次访问补登记，不默认重算全站所有自定义范围。
- 前端轮询状态时同时读取服务端目标截止，检测桶推进；后台受预算排队时显示实际已覆盖和等待状态，不能把 5 分钟桶宽描述成无条件 5 分钟完成承诺。
- 手动刷新在当前桶内校验来源修订并幂等登记必要工作；已有同目标构建时返回该构建，不取消后重开。未有来源变化且目标截止相同可复用结果。首版不因手动刷新改用当前秒、增添另一个实时模式。
- 用户指定的历史／部分日期范围不被桶边界扩大；当前桶尚无完成片时显示准备状态。跨北京时间午夜切换到新日目标，前日最后一片完成后作为完整日复用。

当前日数据继续写入而旧截止以前没有更正时，旧快照仍代表其已标明的覆盖范围；推进目标产生新版本，不回写旧结果。明确这一点，避免把“旧结果仍有效”错误理解成“以后无需更新”。

#### 3.4.2 日片依赖与快照退役

构建代次、来源候选水位与日片有效性是三个不同概念。日片至少以组织、精确时间范围、与该片相交的成员窗口、原始日志口径及源库身份识别；片修订记录该范围的更正依赖。全局来源水位用于限制候选读取，不能每增长一次就让所有日片失效。

成员变更计算新旧窗口差集，失效与其相交的片；单日补写更新受影响日／子片的修订，不使无关日期因完整成员 hash 或用户全局 revision 改变而全部失去复用。若复用现有用户级信号，必须补出受影响日期映射及其可靠恢复依据；范围未知时保守扩大失效并记录原因，不能声称已实现精准日级增量。建表前交付键定义、修订传播和发布校验样例。

已发布视图须有明确退役及引用释放：

- 同一逻辑查询只保留当前版和有限的上一版作为默认可读结果；更早版本退役。固定历史快照和临时筛选视图分别计量，不把任意筛选永久保存成审计记录。
- 登记／组装入口设置每组织待构建数量、视图存储字节和单响应行数／字节上限；首个构建上线前确定实际值并写入交付配置。重复目标合并，超过容量的新目标返回可解释的等待／容量状态，不开放无限队列。
- 查看／游标使用的旧视图给出有限保留窗口；持续分页不无限续存旧快照。退役后请求返回“快照已过期，请刷新”，不把游标解释成最新版本。
- 运行中导出、构建及恢复工作持有有期限、可恢复的引用；结束或取消后释放，进程崩溃后按租约回收，不能因临时引用永久保护所有结果。
- 视图先退役并停止被新请求引用，再释放片引用。清理只回收无有效引用、无恢复责任的旧修订；共享稳定日结果继续复用，源日志保留策略另行执行。

不把来源修订失效与物理回收混为一谈；容量策略不得删源日志来满足缓存上限。快照保留窗口与容量参数在上线前实测确定，不能由实现者采用无限保留默认值。

### 3.5 迟到、修订与跨库边界

**`MAX(id)` 只是候选读取边界，不是提交顺序或严格时间点快照。** 低 ID 事务可以晚提交；只推进最大 ID 会漏数据。按 `created_at` 留几天回看或给缓存加 TTL 同样不能证明不会遗漏更早补写。

现有 Invoice 已有来源覆盖登记、投递确认、成员游标修订、日志保留边界和条件失效，见[来源完整性实现](../../model/organization_invoice_source_integrity.go)。但当前失效代码只更新 Invoice 表，且只覆盖列出的日志类型；新用量表不会自动获得这些保证。

#### 3.5.1 来源入口、最小接线与恢复责任

代码核查发现，[`createLogWithInvoiceAcknowledgement`](../../model/organization_invoice_source_integrity.go) 先写日志库，再确认主库失效。带 OperationId／journal 的 [`RecordTaskBillingLog`](../../model/log.go) 可通过[已有结算恢复](../../service/billing_recovery.go)重试；仍被 Midjourney 等入口调用的 `RecordConsumeLog` 返回 void，失败时只记日志，不能据主路径具备 journal 推断全部来源可恢复。

因此必须覆盖“日志已提交、主库失效确认失败、进程重启”的场景。最终一致需要可持久追踪的恢复责任，不能只增添一次失效调用、打印错误后继续使用旧缓存。

| 事件／现有边界 | 影响与拟议最小接线 | 恢复及验证要求 |
| --- | --- | --- |
| 日志投递确认：`acknowledgeOrganizationInvoiceLog` | 根据原始日志的类型、用户、created_at 和受覆盖范围使用量片／视图失效；保留 Invoice 自己的归属规则 | 明确投递成功与失效确认之间的责任转移；已存日志重试不能重复插入 |
| 日志清理：`prepareOrganizationInvoiceLogCleanup` | 删除前登记保留边界，失效依赖已清理范围的用量结果 | 中断后不能将历史缺失重建为完整零值 |
| 任务证据：`invalidateOrganizationInvoiceUserEvidenceTx` | 仅当原始日志或其有效归属确有变化时接入用量失效；纯任务最终费用证据改变继续只影响 Invoice | 不因 Invoice 费用确认就机械重算原始 type=2 用量，更不能将最终费用写入原始用量片 |
| 成员新增／退出／计费起点回填：`model/organization.go` 中已有成员变更事务及失效调用 | 在同一已验证边界登记受影响的原始成员窗口，联动用量依赖 | 验证变更后旧代不能发布，新旧窗口差集外的片仍可复用 |
| 受控补写、更正、导入、源库替换 | 操作前登记影响范围与来源身份；大操作与重建受同一资源预算约束 | 无法观测的外部 SQL 不承诺自动识别；需明确维护入口及完成后恢复责任 |

前三处是重要候选，不是允许触碰的唯一清单；以事件实际影响和成员窗口调用链决定最小接线，禁止为表面统一而复制所有 Invoice 失效动作。

P1 前交付逐入口清单，列明生产调用方、日志类型、是否已有持久恢复、确认失败落点、重启发现方式、失效粒度及回归样例。优先复用已覆盖的 journal／确认机制；未覆盖入口必须给出最小可靠恢复方案及成本，不能扩写成新的资金账本，也不能以统计失败新增一次扣款。

若某入口尚无可证明的持久恢复落点，不得将其范围宣称为自动保持完整的缓存：需先补齐并验证责任链，或明确暂不开放该范围的完整发布能力。不能以定期 TTL 或仅推进 MAX(id) 代替该门槛。具体恢复承载尚未实现，必须在接线前评审，不在本文假定已有通用持久失效队列。

#### 3.5.2 构建期间与发布后的修订

首版接入路线：

- 复用现有持久来源依赖与可靠投递／恢复信号，给新视图增加最小失效适配；不新增逐请求实时累计，不同步更新组织月总额热点行，不复制普通消费事实。
- 先登记本次覆盖，再捕获高水位；分片完成及发布前校验依赖修订。已覆盖日期有投递、补写或已知更正时，后台重算受影响片并发布新版本。
- 新用量片必须有自己的完成进度和口径版本，不能借用 Invoice 的“已扫描 ID”宣称模型、渠道和 Token 也已统计；是否读取现有来源游标只作为失效依赖，需明确所有权，不能改写 Invoice 游标破坏其恢复。
- 最小适配落在现有来源确认／更正／清理边界，派生失效动作可恢复、幂等并有预算；禁止将统计重算或新的统计失败变成用户扣费必须等待的新步骤。额外写入成本列为上线门槛。
- 成员新增、退出、计费起点回填按受影响区间失效；历史补写、日志原地更正、导入、源库替换或清理也须有受控登记。仅凭现有新增投递信号不能覆盖外部直接 SQL 修改；无法观测的操作必须先失效再执行，不能宣称自动识别任意外部改写。
- 原始日缓存保留稳定修订，不因新一天或仅分类系数变化而全部失效。按影响范围重算；无法精确定位的修订可以扩大失效范围，不能缩小到遗漏数据。
- 已清理的日志使覆盖不足时，标识历史证据不可再重建。普通缓存不自动升级为永久审计账本，不能清空后以零数据重建并声称完整。

SQLite／MySQL／PostgreSQL 的主库与独立日志库之间不存在天然全局事务。采用短事务、依赖修订及可恢复失效实现已发布派生结果的版本一致与最终收敛；不持有整月长事务来伪装跨库强一致。

即使单库 PostgreSQL 的默认 READ COMMITTED 在相邻语句间也可能看到不同提交。若某片需多语句一致读取，在该片范围内明确采用适用隔离或经过验证的修订校验，不能只调用 `Begin` 就视为统一来源快照。

“同一统计快照所有维度相等”和“底层跨库每个时刻完全原子可见”是不同保证。来源投递与失效间的窗口、pending settlement、外部写入可见性须有回归和状态说明；未满足来源覆盖门槛时仅展示已知日志用量，不标为最终消费完整。

ClickHouse 原生日志没有可靠唯一单调 ID，不能使用界面显示序号作为水位或稳定游标。参考当前 Invoice 的保守处理：完整快照可复用，新的快照对受影响源日期保守重算；需要真实稳定行身份／修订来源后才能承诺同等级增量和严格翻页。该降级必须可见，未验收前不开放其严格快照明细能力。

### 3.6 日志明细采用独立分页策略

聚合缓存不能恢复逐笔明细，因此日志页不按“每个日期保存全部日志 JSON”实现。

- 为当前 UI 新增独立游标端点，旧 `p/page_size/total` 合同继续保留。新端点返回 `items/next_cursor/has_more`、精确筛选范围及适用的来源版本，不用近似数冒充旧 `total`。
- 默认读取 `page_size+1` 条判断下一页，不为展示首页先统计每个成员的全部条数。需要精确总数时，只有匹配同一口径、范围、来源版本的 ready 聚合可以提供；否则单列准备状态，不前台同步全量 COUNT。
- PostgreSQL／MySQL／SQLite 以 `(created_at,id)` 做稳定 keyset 排序，携带组织、筛选、来源身份及上界；游标必须绑定筛选，防止被解释为另一个范围。
- 候选查询优先将有限成员窗口批量表达在 LOG_DB 查询中，不对每个成员先取一条。独立库不能跨库 JOIN 成员表；在主库读取窗口后构造有界条件或有限批次归并，再依真实计划选择。
- 只读页面所需列，不默认传输 `other/content`；导出另走已有脱敏、权限和有界流式读取。不要因缩减列表列而改变旧导出合同。
- 迟到提交可能在高水位以内插入新可见行，所以水位不能单独冻结分页。固定快照浏览须校验来源修订；版本变化时返回需刷新，不静默拼接两代。源记录被更正／删除或来源修订不可验证时，明确降级为实时列表。
- 保证日志列表和聚合使用同一筛选与覆盖规则，但不要声称实时明细天然与某份历史统计逐笔同快照。若产品要求不可变逐笔快照导出，须额外冻结行身份／读取快照及保留条件，测量存储成本后单独交付，不能借聚合缓存虚构该能力。
- ClickHouse 的 `(created_at,request_id)` 只有在实际唯一且稳定的前提下才能作严格游标；重复或空 request_id、日志清理和合并必须验证。无可靠行身份时，旧列表可保留，新的严格能力明确不支持。

复用前先读 [`organizationInvoiceKeysetPage`／`forEachOrganizationInvoiceKeysetBatch`](../../model/organization_invoice_heavy_query.go) 和 [Vantage 游标实现](../../service/vantage_token_quota.go)。前者已经是泛型，采用升序、全候选迭代并绑定 Invoice 预算／上下文；后者的 HMAC 游标以单 ID 和高水位为边界。它们均不能直接替代本页的降序单页、复合排序、筛选及来源版本合同。

优先复用可兼容的单页读取能力、已有 HMAC 原语与验证用例；先证明顺序、范围、版本及取消语义一致，再做最窄兼容扩展。不把“再泛型化整个迭代器”列为任务，也不为几行谓词建立通用分页框架。新外部游标的版本、降序边界、查询绑定及过期行为须有独立合同和回归，不能直接沿用 Vantage 的高水位就宣称冻结来源。

### 3.7 筛选、错误和用户状态

| 场景 | 方案 |
| --- | --- |
| 当前范围内可选用户／模型／渠道 | 从同一 ready 用量结果的维度目录读取，不再用无日期统计接口发现选项 |
| 保留选项但当前组合没有结果 | 区分范围内目录与当前组合，不因筛选自己而把选中值丢掉 |
| 确需“历史使用过”选项 | 依赖尚待实施的结算系数历史模型准备专题；按已证明覆盖的集合复用，不在打开页面时临时扫描全历史，也不先假设有现成任务 |
| 首次 building 且无目录 | 日期、刷新和离开操作仍可用；维度控件显示准备状态并暂不可选，不默认切换成全历史发现 |
| 更新中已有同范围目录 | 可显示同组织／范围／权限且未失效的旧目录并标明其版本；保留已选值，结果就绪后整体切到新版本 |
| 日期或组织切换后的 building | 不复用其他范围目录冒充当前选项；已选值保留为待验证条件，不因目录未到齐自动清空或发起无筛选重查询 |
| building | 显示进度、实际覆盖和刷新状态，不补零 |
| failed | 保留具体可安全展示的错误与重试；真实空结果才显示“暂无数据” |
| ready 且空 | 仅在覆盖完成、依赖有效且指标确为零时显示零／空 |
| 更新中有旧结果 | 明确旧版本及截止，只有相同筛选可保留，所有区域保持同一代 |

先修复 API 业务失败检查及页面错误状态，再切换新快照入口。React Query key 包含组织、规范化筛选、查看范围与 snapshot_id；不同时携带多代各自的最新结果。复用现有 ErrorState、LoadingState、表格／分页等业务组件；新增文案只维护 en、zh。

渠道权限按现有服务端规则在缓存读取／结果投影前执行。服务端共享底层原始聚合不代表可以共享不同权限的最终响应；渠道信息不能通过缓存、导出、游标或合计旁路暴露。每次请求仍按当前权限判断，不把快照 ID 当访问许可。

默认日期可以评审是否与 Invoice 一致采用“月初至昨天”，但不能借优化静默缩短用户自定义日期。首版新路径始终展示请求范围及实际覆盖截止；明确查询今天时生成冻结截止的部分日，不将整天结束时间当成未来数据已经覆盖。原无日期合同保留，全历史重查询迁移到显式后台准备能力。

现有导出默认值不一致：汇总 CSV 的 `exportOrganizationBilling` 没有补默认时间范围，而日志 CSV 的 `defaultOrganizationBillingLogExportRange` 在起止都为空时补为导出时区的当月。新页面与统计导出必须显式传递同一规范化范围、时区和适用的 snapshot_id，不能靠两个后端默认值碰巧相等。旧导出端点的默认值与列合同保持兼容；P0 暴露范围、P2 验证新页面／日志导出边界。原始日志导出是否固定逐笔版本仍按 3.6 的保证处理，不以统计 snapshot_id 冒充不可变明细快照。

### 3.8 资源、索引与调度

1. **先恢复资源容量。** 开发 Compose 为 postgres 服务配置可调 `shm_size`，建议以 512 MB 为初始验证值；这不是测得的最低值，也不是所有生产环境的固定推荐。重建容器前核对持久卷和其他使用方。生产环境先独立核对是否容器化、共享内存和并发，不能照搬本地根因。
2. 对后台统计复用短事务 `SET LOCAL statement_timeout`、应用 context、受控全局并发、暂停和断点恢复。是否对统计连接临时限制 `max_parallel_workers_per_gather` 由实测决定，不修改通用连接池会话、不要把降低并行等同于性能提升。
3. 复用 SystemTask 框架，但当前租约按任务类型互斥，[调度器](../../service/system_task.go)还会并发启动不同类型；`waitOrganizationInvoiceReadBudget` 仅为 Invoice 暂停及批间延迟，不是跨任务全局许可。跨统计资源许可属于待建能力，未来历史模型准备同样接入，不能把尚未实施的专题当接线前置。
4. 北京时间日片在超时或容量超限后分小时，仍超限则继续细分／按稳定 keyset 有界读取。限制单批行数、字节及多维聚合内存；`LIMIT` 和时间片都不能替代物理扫描量核查。
5. 索引先核对实际有序列与有效性。复用[现有漂移检查](../../model/organization_invoice_index_check.go)，独立低峰维护漂移，不靠重启 AutoMigrate 在线重建大索引。
6. `(user_id,type,created_at,id)` 等只是待验证候选。按整组织与单用户、冷热月份、模型／渠道过滤及游标后续页分别 EXPLAIN，评估行数、过滤、排序、buffer、写放大和磁盘预算；不一次性建立所有维度排列的索引。
7. 按 3.4.2 先退役旧视图并释放引用，再清理无引用旧代次／中间态；正在构建、可恢复及仍在保留窗口内的视图引用受保护。不能把“已发布过”当成永久引用，缓存回收不删除源日志。

新增重任务上线前必须落实共同许可：按实际日志数据源划分资源域，跨实例初始只允许一个重统计执行单元；Invoice 与用量先接入，历史模型准备实现后使用同一许可。任务类型租约继续负责各自任务生命周期，不代替资源域互斥。

许可须有明确 owner、持久租约／期限、续租、等待和取消行为；不能只用单进程 mutex。获取失败时等待并保存已有进度，不绕过限制。失租立即取消在途查询；若取消尚未完成，不得未经核验就启动另一条重 SQL；旧 owner 不能继续写片或发布。长历史任务在有界单元间让出执行机会，使短查询、其他组织及日常推进能取得预算，不独占资源直到整月重建结束。

许可保护范围覆盖来源发现、用量片计算及其他实际重读，不能只包最后一个聚合。数据库语句超时、批间延迟与许可分别验收，不以其中之一代替另外两项。P1 接线前给出资源域键、获取／释放与失租时序、现有任务取消能力适配及并发回归；复用现有租约方法时不得直接把资源行伪装成另一个业务任务。具体实现尚待交付，不预设现有 SystemTaskLock 已具备该资源合同。

只扩大共享内存可以缓解直接失败，仍不能解决重复扫描；只加缓存不能解决第一次生成；只加索引不能消除同页多次聚合。三项按成本分别验收。

### 3.9 独立实现与接口兼容

拟议主体放在新的 `model/organization_usage_*.go`、`service/organization_usage_*.go`、`controller/organization_usage_*.go` 和组织 feature 下的独立组件／API 文件。原路由、迁移和任务注册只作必要接线，不重构个人扣费、预扣、退款或 Relay。

使用新端点承载 `building/ready/failed/invalidated`、快照 ID 和游标合同；不得让旧数组接口突然返回任务状态对象，或令旧 `total` 变近似值。先明确必要调用接线，再按组织开关灰度；关闭新功能应能停新构建并保留可读旧结果与失败说明，不触发前台无界重算。

## 4. 实施顺序与验收

### 4.1 分阶段交付

| 阶段 | 工作 | 完成门槛 |
| --- | --- | --- |
| P0 故障止血 | 错误状态与业务失败检查；核对／调整共享内存；避免筛选选项无日期全量查询；暴露页面／导出范围差异 | 渠道、汇总、日志失败可见；不再误报零消费；资源调整有前后对照；保留旧接口范围合同 |
| P1 日结果与统计快照 | 先确定来源恢复清单、共同资源许可、当前日推进及日片键；再实现多维片、同版发布、迟到失效、后台任务及统一读取 | 新重任务受许可保护；日志成功但失效失败可恢复；五类统计守恒；桶推进不制造请求风暴；稳定日复用；首次 building 的筛选行为明确 |
| P2 日志有界查询 | 游标端点、必要列、查询访问路径及同来源计数；导出显式范围；旧视图退役及过期游标 | 第一页无成员全量 COUNT，无逐成员 LIMIT 1；后续页无漏重或明确版本变化；列表和导出范围可核对 |
| P3 容量与持续运行验收 | 持续写入／跨日对照，缓存容量及回收，多组织共享预算实测，响应大小、导出、故障恢复与生产灰度 | 新一天不重扫全部旧日；更新不混代；引用可释放且在用结果不误删；生产规模预算通过 |

最终方案须完成 P0–P3 才能宣称完整交付。P0 不能代替千万级容量方案，P1 也不能自动代表日志分页已优化。

P1 接线前须有可评审的入口／恢复表、资源许可时序、当前日目标计算及日片依赖键；不要求先建设通用平台，但不能以“复用现有能力”为名跳过不存在的机制。P3 是持续运行验收，不是首次补上可靠失效、资源互斥或跨快照复用的阶段。

### 4.2 正确性与恢复用例

- 相同来源版本，汇总／趋势／成员／模型／渠道在 quota、日志行数及两类 Token 上逐项相等；指定用户、模型和渠道组合后仍成立。
- 多渠道／零渠道、渠道已删除、空模型、零金额有 Token、无使用成员、同用户多段关系及北京时间边界均有精确预期；分组数与 fixture 的源数据一致。“22 个渠道”只保留为本地诊断证据，不让通用回归依赖真实数据库恰有该数量。
- 预扣、补扣、部分退款、零最终费用等样本证明原始日志语义未被缓存层改成 Invoice；二者差额可解释，未更改扣费结果。
- 旧代 worker、重复执行、片写入后崩溃、发布前失败、租约转移、清理并发均不漏不重，未完成片不发布为完整。
- 构建期间及完成后低 ID 晚提交、历史补写、导入、成员起点回填、日志清理与源库替换使正确范围失效；没有仅靠 MAX(id)／TTL 的漏记。
- 独立主／日志库下模拟日志已落库但失效确认延迟／失败，验证恢复信号、旧视图有效性标识和重建；不以单库测试替代。
- 按入口清单分别覆盖带 journal 与非 journal 调用的来源责任；日志已提交后确认失败并重启，重试只能确认失效，不能重复消费日志。无可靠恢复的入口不得错误发布完整缓存。
- 同时触发 Invoice、用量及已实施的模型准备任务，跨节点重 SQL 并发符合共同许可；owner 失租、取消未完成、节点退出及后续接管均有确定性回归，不靠 sleep 或耗时猜测互斥成立。
- 固定时钟验证同桶复用、跨桶推进、当日已结束的精确时段不被截短、手动刷新去重和跨午夜；持续有新日志时旧截止可解释，新目标能推进，排队不伪装成已覆盖。
- 单日补写／局部成员窗口更正只使必要片重建；普通追加 ID 不使全部历史日失效。来源未知导致扩大失效时保留原因，不能误报精准增量。
- 日志第一页与后续页覆盖同秒不同 ID、迟到插入、删除、更正、筛选变更、来源失效；固定版本不可用时明确要求刷新，不静默混页。
- HTTP 200 + success=false、真正零结果、轮询失败、旧快照更新及组织切换均验证可见状态；后台失败不触发资金写入。
- 首次无目录、同范围目录更新、范围切换和失败均验证筛选控件状态；目录尚未到齐不自动清空用户条件，不转而扫描全历史。
- 页面及两类导出在空日期、只填一端、明确起止、时区偏移及北京时间午夜场景下核对规范化范围；旧默认合同不被新页面的显式参数改写。
- 高频切换筛选、重复刷新及多查看者不制造无限任务／视图；容量拒绝、旧视图退役、游标过期、导出引用释放和崩溃租约回收均验证，稳定共享片不得误删。

### 4.3 千万级性能与数据库验收

**以下是建议验收目标，尚未实测达成。** 实施前记录实际资源、数据分布、并发、目标账期行数和容量；按线上预算调整阈值并留存理由，不把本地一次查询成功当压测通过。

| 场景 | 初始验收目标／必须记录 |
| --- | --- |
| ready 统计读取 | P95 ≤ 1 秒；业务路径不查询 logs，不重跑源发现；大维度分页时固定 snapshot_id |
| 单响应及视图容量 | 首版必须交付首屏最大行数／序列化字节上限、实测结果及超限同版分页行为；不允许无限响应或静默截断；记录每组织视图存储／待构建上限及选值依据 |
| 冷启动登记与状态查询 | P95 ≤ 1 秒；后台重查询不占住 HTTP 请求 |
| 日志第一页及后续页 | P95 ≤ 2 秒；记录实际计划、扫描量、排序和返回字节；不得依靠全量精确 COUNT 达标 |
| 第一次历史构建 | 单语句／单批有上限；阶段耗时、扫描行数／字节、内存、共享内存和 IO 可解释；离页／重启后继续 |
| 新一天与迟到更正 | 稳定日命中，主要处理新增／受影响范围；输出实际复用率、重扫量、目标截止与实际截止；验证时间桶推进规则 |
| 持续网关流量对照 | 相同可比负载下网关 P95 增幅建议不超过 10%，错误率不恶化；CPU、IO、连接池及共享内存留余量 |
| 多组织／多查看者 | 相同构建去重，Invoice 与用量共同资源许可有效；记录重 SQL 峰值并发、等待／让出次数及最长等待，无冷缓存并发风暴 |
| 导出及清理 | 统计导出绑定同范围／版本，明细版本保证按 3.6；客户端或任务取消有界；视图退役后引用释放，在用结果不误删；过期游标显式失败 |

至少覆盖与线上规模相当的 1,430 万以上代表性分布及持续写入，不要求用随机大循环伪造性能测试。合成数据须披露与真实模型／渠道／成员倾斜、行宽及索引的差别。

生产版本和资源必须单独记录。涉及持久模型、SQL、索引和事务时，实跑 SQLite、MySQL、PostgreSQL；涉及版本能力时覆盖最低支持边界。独立日志库与 ClickHouse 按受影响能力验证或明确未支持／降级。Schema 变化验证新库、代表性已发布旧库升级、重复启动迁移及数据／约束保护。历史 Invoice 已有矩阵不能替代本次新缓存和分页验证。

后端回归优先扩展既有合适测试；确需新增时按聚焦工作包合并关键合同，避免跨层重复 fixture。前端修改按项目要求执行回归、typecheck、涉及文件 lint 和构建。本轮只有文档与只读 SQL，不宣称已完成上述实施验证。

### 4.4 灰度与回退

先在隔离库完成来源一致性、三库及恢复验证，再灰度单组织、单个重查询预算。先采集旧查询与新快照在相同冻结范围的原始整数对照，禁止拿持续变化的两个时刻比较“误差”。

出现金额／数量不守恒、来源修订漏失效、资源阈值超限或线上请求退化时，停新构建并取消当前有界工作，保留进度和已发布结果；错误旧结果明确标识。回退不修改客户余额、原日志和 Invoice 已确认凭据，不通过删除历史日志或清空所有缓存制造“恢复正常”。

- 原始查询的 `EXPLAIN`：单成员最新记录使用时间索引再过滤用户；汇总出现 BitmapAnd 等访问路径。本轮未建候选索引，也未宣称候选性能已经验证。
- 以下只读验证成功返回 2.2 的 22 个渠道分组及合计；`SET LOCAL` 随事务结束恢复，没有改全局设置：

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '20s';
SET LOCAL max_parallel_workers_per_gather = 0;
WITH grouped AS (
  SELECT l.channel_id,
         COUNT(*) AS requests,
         SUM(l.quota) AS quota,
         SUM(l.prompt_tokens) AS prompt_tokens,
         SUM(l.completion_tokens) AS completion_tokens
  FROM logs l
  WHERE l.type = 2
    AND l.created_at >= 1790784000
    AND l.created_at <= 1792252799
    AND EXISTS (
      SELECT 1 FROM organization_members m
      WHERE m.organization_id = 1 AND m.user_id = l.user_id
        AND l.created_at >= COALESCE(NULLIF(m.billing_start_at, 0), m.joined_at)
        AND (m.left_at = 0 OR l.created_at < m.left_at)
    )
  GROUP BY l.channel_id
)
SELECT COUNT(*) AS channel_groups,
       COUNT(*) FILTER (WHERE channel_id = 0) AS unassigned_groups,
       SUM(requests), SUM(quota), SUM(prompt_tokens), SUM(completion_tokens)
FROM grouped;
COMMIT;
```

该 SQL 是本地 PostgreSQL 同库诊断命令，不是拟议生产跨数据库实现；不能在独立日志库直接 JOIN 主库成员表，也不能把 PostgreSQL FILTER 语法带入跨库业务代码。此处保留实际执行的整数秒闭区间，`created_at <= 1792252799` 等价于半开边界 `created_at < 1792252800`；拟议内部范围继续统一使用 `[start,end)`。
