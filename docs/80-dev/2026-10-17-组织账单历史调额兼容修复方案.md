# 组织账单实际消费汇总与加载修复方案

> 本文是当前修复方向的唯一评审入口。正文第 1–6 节为本次实现遵循的设计，当前计算版本为 10；第 7.1–7.5 节保留版本 9 交付记录，第 7.6 节记录版本 10，第 7.7 节记录联合评审修复及本轮复跑证据；附录 A 保留版本 7/8 的历史修复和测试记录，附录 B 保留退款及消费基数证据。历史测试通过、快照 ready 或 Finalized，均不证明新方案已实现、消费金额全部正确或管理员已确认结算。
>
> 本次已实现代码、回归测试及隔离测试库验证，未操作线上数据库、修复线上索引、重启正在使用的应用或变更客户余额。保留原文件名以维持链接。原性能方案作为诊断及性能工作包引用；当前业务口径以本文为准。代码落地不代表生产规模或正式对账已通过。

推荐路线：**复用现有结算及原始记录核算消费与资金收支，补足任务费用确认依据，缓存消费和钱包两侧的日结果及完整账单。** 有效账单重复查询直接读取，不重新统计；新增或更正只更新必要范围。终态确认是业务语义，日结果是可重建缓存，均不要求另建消费账本。1430 多万条记录下的核验、扫描成本和资源验收见第 4、6 节。

## 1. 问题与目标

### 1.1 已确认目标与边界

交付一张金额有依据、资金差异可解释、千万级数据下能够生成和复用的对账单。解决消费基数错误、重复扫描和单账户异常阻断整个组织查看的问题；允许首次生成较慢，之后读取已保存结果。计算完成、消费完整、余额已核验及管理员已确认分别表达，不能把“页面能显示”作为“对账已通过”的证明。

| 用户已确认事项 | 本方案边界 |
| --- | --- |
| 可以慢，但需要查询到 | 后台可恢复生成；可靠小计可查看，未知金额不能补零或冒充完整结果 |
| 月中核对、月后整月结算 | 默认月初至昨天的固定截止快照；月后使用整月数据 |
| 管理员手动确认 | 不新增自动确认、自动锁账；技术状态不代替人工确认 |
| 已结算金额不回改 | 有依据的后续差额进入后续账期，且只处理一次 |
| 保持简洁、保留已有业务规则 | 沿用定价、折扣、成员归属及分类系数；修正已实证的错误消费基数，不重写计价或钱包机制 |

不在首版建设通用资金账本、核销审批、异常工单平台、自动宽限期或自动转期系统。人工差异处理可先沿用已有工作方式并留存依据。

解释证据时遵守以下边界：

- 账单消费基数、应用组织分类系数后的结算金额、钱包资金变动是不同量。钱包核对排除订阅消费，而消费统计另有范围；同源可追溯，不要求三个总额恒等。
- 任务 2820 的 8.236116 USD 与 0.347618 USD 证明基数错误。是否产生实际对客多收，必须核对结算、导出及收付款记录。
- 预扣可能低于最终费用。“待结算预扣占用”只能作为参考，不能叫敞口上界、最终应收或最大损失。

## 3. 唯一业务口径

### 3.1 费用确认、账单确认与资金到账

**费用已确认：现行计价完成，并可靠保存最终费用及可恢复的资金处理依据，包含零费用。** 其确认时点由现有结算入口的持久化成功定义，不能仅凭任务 SUCCESS、非零 quota 或出现退款日志推断。失败重试必须能恢复，不能用不可恢复的内存状态宣称确认。

“可靠保存”不要求每笔普通请求再新增一份明细：已验证的最终消费日志可承担该职责。异步任务需补足终态费用，普通记录和任务结果最终进入同一汇总及系数计算路径。

“费用已确认”“管理员已确认账单”“扣款/退款已完成”分别回答不同问题。费用结果已可靠确定时，资金处理在途不使费用重新变为未知；相关资金操作继续按已有机制恢复，不能绕过结算一致性要求。仅有日志或只有当前 task.quota 不足以自动确认所有历史费用。

| 业务情况 | 消费汇总 | 独立提示 |
| --- | --- | --- |
| 只有预扣，费用未确定 | 不计入已确认金额，计为待结算 | 可展示有明确依据的预扣占用 |
| 最终费用可靠保存 | 同一业务只计一次最终费用 | 保留业务标识和确认来源 |
| 按既有规则确认全额退费 | 最终费用为零，有明确确认依据 | 退款在途属于资金状态，不计为费用待结算 |
| 补扣、部分退款、部分完成 | 取确认后的最终费用 | 不根据成功/失败状态猜金额，不再二次扣退款 |
| 历史依据不足 | 单列待核对，可靠小计仍可查 | 未知不当零，不宣称整单完整 |
| 钱包异常但费用明确 | 不阻断可靠消费展示 | 保留差额或核对依据不足说明 |

任务 2820 的最终消费基数应为 173,809 quota，即 0.347618 USD；不能继续计 4,118,058，也不能在最终费用基础上再减一次退款。金额继续使用整数 quota 累计、安全边界及既有 decimal/精度规则，组织分类系数只应用一次。[现有分类结算算法](../../model/organization_invoice.go)继续复用。

费用确认必须用以下证据样本验收，不由实现者根据字段名猜测：

| 证据组合 | 确认结论 |
| --- | --- |
| 明确最终费用、稳定业务关联及计价/调整依据一致 | 确认最终费用；任务 2820 的预扣、actual_quota、退款及任务结果互相印证 |
| 仅 SUCCESS、当前 tasks.quota、task_sync 或“没有退款” | 单独均不足以证明最终费用；零差额也不能因此漏确认 |
| 固定费用成功，提交快照及现有结算依据明确 | 确认固定费用，不要求必须存在差额日志 |
| 按既有规则明确全退，零费用及可恢复处理依据可靠保存 | 确认零费用；退款在途独立显示，不据此重复退款 |
| 无实际用量、表达式结算失败保留预扣，或多份依据冲突 | 标记待结算/待核对，不把保留的预扣自动当实际消费 |

`task_sync` 表达交付方式，不是确认凭证：[立即返回任务的结算分支](../../relay/relay_task.go)在求值失败时可保留预扣，[日志标记](../../service/task_billing.go)仍可能表示同步交付。此类情况和零费用、零差额必须各有精确预期样本。

### 3.2 可查看与可确认分开

费用缺失、来源重复无法判定、非法 quota、溢出或组织归属不明，影响相关消费的完整性；钱包单独有差额，不自动等同于消费不完整。页面及导出必须共用消费来源与完整性标识，可靠小计不能包装成完整应收或正式已确认结果。

钱包核对独立后，已知占用/释放错配应修正诊断；尚不能可靠还原的情形显示“核对依据不足”，保留账户及原始证据，不能输出看似精确的假差额。无需先补齐全部历史钱包回放，才允许查看可靠消费；也不能删除核对能力或全部隐藏告警。

现有历史截止的 `derived` 仅表示按期初和流水推导余额，不表示已有该截止时刻的独立余额核验。只有有效同期余额证据才可用于余额一致性判断；没有时如实显示推导或待核对，不拿今天余额核对昨天结果，不生成虚假的历史余额。`ready`/Finalized 不代替这些结论。

钱包出资的消费与钱包消费类净扣款，只在范围、资金来源、占用变化及资金处理时点对齐后作金额一致性自检。充值/调额等总资金净变动、组织系数后金额不能直接与实际消费恒等比较。预扣 100、费用确认 10、退款 90 在途时，差额有明确时序原因；不能把它误判为多收或已丢款。未知差异仍保留，不能把所有差异都归为在途。

### 3.3 日期、归属与系数

默认月中使用北京时间月初至昨天，月后使用完整月份；每月 1 日尚无当月完整自然日，沿用已确认的边界提示。请求范围、实际覆盖截止及事实版本应可区分；跨午夜构建不扩大冻结范围，自定义日期不静默改写，旧快照不贴新日期。截止日不保证投递已全部到齐，完整性还需识别待处理事实。

区分两个时间维度：**覆盖截止**表示统计哪个业务日期范围；**计算所用证据版本**表示本次采用了哪些已获得的结算依据。不能只查询当前非终态任务来复现历史：9 月未完成、10 月完成的任务当前已是终态。生成时冻结证据范围/版本，后续结算按既定规则使未结算账期及受影响日结果失效；原快照不可在不改变版本的情况下静默变数。已人工结算的账期仍不回改。

**建议默认保留原消费归属时点、对应历史成员窗口及该归属月份系数；费用确认时间另记，用于判断结果何时可用。** 不因异步完成或退款到账跨月，就直接改变原组织和月份。已确认账期之后的调整，需区分原业务归属与调整展示账期，避免按后续新价格重新计价。

实施前用“9 月 30 日创建、10 月 2 日确认”“期间转组织”“跨月退款”核对既有行为，明确原消费归属时点具体对应哪个持久字段及系数取值，并写入验收样本；未核实前不得由开发者任意选任务创建月、完成月或退款月。若现有入口并无一致规则，需明确业务决定后再实施该分支，不能声称已解决。

### 3.4 月末待结算与人工处理

首版建议：存在影响当月费用的待结算/待核对项时，允许查看已确认金额，暂不宣称整月完整，由负责账单的管理员跟进，留存未决清单及处理结论。已确定零费用而退款在途不属于这类费用未决项。此建议待业务评审，不是已存在的月末自动处理能力。

不自动增加 N 天宽限期、自动把未决项归零或自动转月。如果业务要求有未决项也必须按期确认，则必须另外确定“确认已知部分并附未决清单、后续调整”的政策及输出合同；未确定前不能在代码中默认允许。

已人工确认结算的金额保留，后续查证差额仅处理一次。对客结算以人工确认留存的账单及调整依据为准；钱包用于余额、资金流和异常核对，不将未经确认的动态小计作为正式收款依据。现有系统缺正式确认/调整接口的部分先采用可追溯人工记录，不将 ready/Finalized 当作人工确认。

## 4. 最小实现与性能控制

### 4.1 复用原始依据，修正同一条对账路径

```text
现有日志、任务及结算记录
  → 现有对账路径：消费按确认费用归并，资金沿既有归属核算
  → 可重建日缓存：消费 quota ＋ 钱包收支分项 ＋ 核验状态
  → 账期合并、应用原系数、判断对账结论并保存快照
  → 页面和导出直接读有效快照
```

| 工作 | 改动及复用 | 不扩展的范围 |
| --- | --- | --- |
| A 消费口径修正 | 普通请求复用可靠最终日志；任务按已有结算证据归并，缺失处补最少确认字段，覆盖第 3.1 节样本 | 不默认新增任务事实表、复制普通消费或全量重写历史日志；不形成两套计价算法 |
| B 消费与钱包解耦 | 调整当前构建的费用完整性判断及钱包失败隔离；必要的页面/导出提示 | 不把所有异常都转成成功，不先开发完整财务工作流 |
| C 两侧日结果和账单快照 | 复用持久任务、租约、条件发布和只读缓存；消费和钱包分项均复用日结果，历史按需归并 | 新增物限必要确认信息和可重建缓存，不新增资金权威、通用队列或流式平台 |

[普通结算入口](../../service/billing.go)已有最终 quota 与可恢复日志投递；[任务重算](../../service/task_billing.go)差额为零时会直接返回；[恢复机制](../../service/billing_recovery.go)完成后清理 journal。因此需要逐项核对真正的完成入口，不能只订阅调整日志、对可变 tasks.quota 求和，或把临时 journal 当永久消费来源。

普通来源复用的前提是：所选范围的结算入口已覆盖、投递失败可恢复、日志保留足够长且可明确区分任务记录。日志关闭、已清理或历史语义不明确时，账单标记不完整，不能以“没有退款”或“没有任务标识”直接证明这是普通最终消费。配置约束和保留策略应明确告知，不能静默变更已有设置。

任务最终费用优先从已有记录取得；核验确有表达缺口时，在现有任务/结算持久化边界补最少确认信息，不先新增独立明细。稳定业务身份、最终整数 quota、确认时点、真实资金来源、原归属及来源关联必须可追溯；零费用与未知须区分。任务提交仍只产生预扣，退款失败继续恢复而不重复确认费用；journal 清理或任务删除不能成为抹除已确认账单依据的理由。

汇总的必要条件是**输入互斥**：所有已识别任务的预扣、补扣和退款日志均不再作为普通最终消费输入；任务只计确认结果。仍在执行或费用未知的任务也必须排除预扣，而非只替换已完成任务。请求数按业务身份计算，不能把任务追加扣款日志计作新请求。原始退款仍供钱包核对，不从当月模型总额无差别相减。

新增任务提交/终态写入明确的业务关联及计费阶段；历史候选在有界后台处理中核验并保存可复用分类/关联及日结果。结构化承载方式须覆盖日志库差异，不预设跨库 JOIN 或专属 JSON 运算；不为排除少量任务而在每次月查询对全部 other 做 LIKE/JSON 解析。历史首次识别若确需读取大量 other，应单独测量字节量与耗时、限速保存进度，不声称任务少就一定能廉价定位。

只有核验表明普通消费来源普遍不可靠、保留策略不满足正式账单要求，或持续增量无法可靠交付时，才重新评估统一消费事实表。届时需列明额外写入、索引、存储、历史迁移和一致性成本；不能把“统一来源”自动等同于“复制所有记录”。

消费视图不得以缺失钱包基线、旧钱包依赖月失败为必然阻塞条件；费用来源或归属本身缺失仍明确标记。保留后台目标推进及钱包侧历史依赖恢复，不凭空填平历史余额，也不要求先读取全部历史模型矩阵才能显示本期可靠消费。旧整期计算器仅对未受已知缺陷影响的规则作对照，不能作为金额正确性的唯一依据。

#### 4.1.1 分类守恒与业务遗漏核验

同一组织/账期、同一来源版本内，对原有 type=2 记录作互斥分类，**笔数和整数 quota 均须满足**：

```text
全部 type=2 ＝ 已核验普通最终消费 ＋ 任务类消费日志 ＋ 未分类
```

任务桶包含预扣、追加扣款以及提交时已完成最终结算的任务消费日志，不能把所有任务提交记录一律解释为预扣。每条原记录只归一桶；未分类存在时不得宣称该范围费用完整，已确认小计仍可查看。该式证明已有日志未被分类过程漏掉或重算，不能证明日志本身没有缺失，也不能单独发现“任务被误归普通”的情况。

另从现有任务、预扣/结算记录反向核验已知业务覆盖：覆盖期内相关任务及仍影响该期占用、消费或退款的跨期任务，均有“已确认、待结算、明确零费用、依据不足”之一的可解释结论。不能只枚举已有消费日志或当前非终态任务。140 的任务即使没有原 type=2，也应从业务记录中被识别；关联缺失不自动生成消费或退款。这个核验增强证据，不对不可观测的全部历史缺失作绝对完整性承诺。

守恒、反向覆盖与精确费用样本共同验收。核验随有界生成执行并缓存，重复查询不重做；按片保存笔数、金额、未决计数和必要异常引用，不永久复制千万条分桶明细。

#### 4.1.2 入口清单与业务关联交付物

实施前交付一份入口核验表，逐项明确费用是否最终、日志语义、业务关联、持久化/恢复及对应回归。不能以主入口有 journal 推断旧回退同样具备保证。

| 必须枚举的入口 | 核验重点 |
| --- | --- |
| 普通最终结算及一次性扣费 | 最终 quota、消费日志投递与重复处理 |
| SettleBilling 的旧 PostConsumeQuota 回退 | 实际调用方、日志落点及失败恢复，不直接视为已覆盖 |
| 异步提交、轮询终态及用量补核 | 预扣不计最终；确认、零差额、补扣、退款及恢复重放 |
| inline/task_sync 与图片同步交付 | 交付完成不等于费用确认；立即返回求值失败保留预扣要单列 |
| 固定费用和零费用 | 没有调整日志仍能根据明确依据确认，不从缺行推断零消费 |
| 钱包/订阅及 Midjourney 独立任务路径 | 保留来源差异及两类任务主体，不能只覆盖 tasks 表 |

同时交付可持久追溯的关联：业务主体 → 原预扣/消费及调整记录 → 原日期/归属组织和月份 → 费用确认及更正依据。优先复用现有字段和记录，缺口只补必要信息；不要求新表。终态/更正与关联更新须可恢复，重试幂等，避免费用已变而原日缓存一直有效。跨月更新按此关联定位失效范围，不能靠每次扫描全部历史猜测。

### 4.2 持续请求下的资源预算

当前统计与在线请求共享 LOG_DB 资源；后台异步、单 worker 和超时均不等于低负载。成本分别评估：在线补足确认依据的写入、历史首次归并、每日统计、快照读取和导出。

- 请求链路只可靠保存费用依据，不逐笔扫描账单，也不让所有请求同步更新同一组织月汇总行。确认写入失败沿用结算恢复要求；统计失败不增加扣费。
- 从单组织、全局受控的单 worker 灰度开始；限制有界批次、批间节奏和执行窗口，提供暂停/续跑开关。单 worker 仍可能吃满数据库；增大连接数或超时不能替代限速。
- 历史补算与日常任务分配预算，避免互相饿死；达到业务延迟、错误率或资源阈值时暂停后台工作，持久保留进度。首版可采用人工监控和暂停，不要求先建自动伸缩系统。
- 数据库语句兜底与应用取消继续复用现有机制。PostgreSQL 的 SET LOCAL 必须在实际重查询连接的短事务内生效，不修改通用会话参数；其他数据库验证各自取消边界。
- 固定截止只减少重复访问。同一构建的片恢复不等于跨日快照已复用；每天全月累计重算仍反复扫描旧数据。

持续高流量下推荐消费和钱包两侧都采用可复用日结果：稳定日期复用，只处理新增日期或重算受更正影响范围，不先建设逐请求实时累计系统。当前片的 summary_id/revision 属于构建身份，不能直接当跨快照稳定键；复用须核对来源、成员窗口及必要规则依赖，不能仅复制旧 payload。保留迟到投递、跨月任务完成、更正、转组织的失效传播。不能只筛昨天创建的业务，也不能只推进最大 ID 而遗漏迟提交事实。

进度、结果和有效性更新须可恢复，失败重放不重计、进度推进不漏计；日结果保存原始 quota，按月合并后再应用系数，不先按天舍入金额。当天转组织仍按精确时间边界确定归属，不以日期桶代替成员窗口。自定义日期不能直接拼入范围外日数据；只有全覆盖且依赖有效的日片可复用，边界范围按原请求重新核算。

钱包日缓存保存当前对账算法的**分项结果**，而非只存一个 NetDeltaQuota：

| 日结果内容 | 合并及核对要求 |
| --- | --- |
| 充值、管理增加、其他已识别流入（保留退款分项） | 保留来源归类，按原规则去重和排除订阅订单；退款不改成新的消费确认 |
| 钱包消费类扣款、管理减少、其他扣减 | 与最终消费分开，包含的预扣和释放依原始资金事实解释，不重复净额化 |
| 来源完整性、未决/异常计数及必要引用 | 合并不能掩盖未知来源；缺失日期不视为零变动，空结果不自动证明来源完整 |
| 实际覆盖、来源版本和归属依赖 | 只有已完成且仍有效的结果参与合并，更正或迟到使相关范围失效 |

NetDeltaQuota 由入账/出账分项推导；期初、期末及独立余额核验在账期层处理，当前余额另行读取，不写回历史期末。现有钱包三路 keyset 按来源互斥分区，不等于每条记录读取三遍，但仍可能遍历整期；应分别测量扫描量和传输量。来源明确且归属可等价表达的部分优先数据库聚合，旧格式才分批解析；复用已有调额事实和结转，避免重复全站旧格式扫描及历史矩阵解码。资金归属不直接替换成消费成员窗口。

仅组织分类结算系数变化时，账户/模型原始 quota 日缓存和钱包分项无需重扫，重新合并月账单并应用系数即可；若缓存已经包含分类映射，须另校验映射依赖。来源、成员归属及实际费用更正仍按受影响范围重算。日复用、数据库内聚合、索引访问路径和减少 other 传输共同降低成本，不把日缓存称为唯一性能手段。

为保持实现简洁，每日累计重算仍可作备选，但必须先通过第 6 节业务影响与每日完成窗口验收；不满足时日片复用/增量成为上线前置条件。索引修复按真实 SQL 和访问计划决定；保留原性能方案 5.4 的列序漂移核验、独立维护及写入成本验证，不能用增加索引代替减少无效重复扫描。

### 4.3 1430 万条记录下的工作量与选择门槛

| 阶段 | 推荐处理范围 | 不应成为默认行为 |
| --- | --- | --- |
| 首次历史生成 | 请求涉及的组织、账期与必要来源核验；有界处理、慢速归并、保留进度 | 为查看一个账期先复制所有历史消费或回写整张 logs |
| 每日生成 | 消费及钱包分项只处理新增日期与迟到/更正范围，复用其他有效日结果 | 只缓存用量，钱包仍每天遍历整月；新一天使全部分片失效 |
| 重复查看/导出 | 读已持久化的快照及必要状态 | 重新解析全部任务生命周期或扫描全量原始日志 |
| 普通在线请求 | 沿用原最终消费写入及恢复；必要标记随原写入，评估额外字节/索引成本 | 每请求默认多写一份同义消费明细，或更新组织月总额热点行 |
| 异步任务终态 | 仅补任务的可靠确认结果、关联及恢复 | 把任务数量视为全部日志数量，或把当前任务额度当历史事实 |

1430 万总量不能直接推导耗时：还取决于目标账期有效行数、other 大小、任务比例、历史关联可定位程度、执行计划及数据库资源余量。分片只限制请求时间范围，不保证物理扫描量有界；逐日查询也可能反复检查大量历史数据，必须核对实际计划和扫描/过滤行数。

实施前补齐三组证据：消费/退款/其他日志及任务构成；真实应用 SQL 的访问计划、扫描量和阶段耗时；持续请求下的资源余量与开关对照。优先用现有统计、已采集结果和受控样本，必要聚合安排有界低峰任务，不为采集占比立即执行无期限全表 JSON 扫描。任务记录少只能说明新增结果可能较少，不能据此保证日志分类便宜。

## 5. 历史处理、责任与上线

### 5.1 一次性历史处理与差异出口

历史记录按可信程度区分：已核验的普通最终消费、可确认的任务终态/可据原始事实归并的任务、依据不足。普通日志直接复用；任务做受控归并，分类与汇总结果可复用，不能把同一预扣同时留在普通输入。按实际需要的账期推进，不预先复制全部消费明细，不强制全表回填任务标记；原始日志、钱包、冻结基线和既有结算依据不被覆盖。

上线前产出“账单金额修正候选清单”：组织、原归属月份、受影响业务、原基数、最终基数、系数/版本、结算金额差异及来源。另核对该月份是否实际对客结算；未核实收付款前，不把高估基数统称为已多收。

未结算月份可按已核验事实重建；已结算月份不回改，按人工核验结论处理后续调整。是否需要退款、抵扣及对客说明属于实际影响核实后的商业处置，不由技术回填自动执行。没有正式调整接口时先保留人工凭证，不伪造一笔消费、充值或退款来消差。

由负责该组织账单的管理员跟进费用未决项和钱包差异，首版可复用现有记录或人工清单。最低记录为组织/账户、原账期与业务来源、差额及计算口径、首次发现时间、处理人、状态和结论/后续凭证；无法精确算差额时记录依据缺失而非补零。重复检查不反复创建同一问题，金额随进度变化时保留变动说明。待处理状态不是已解决，不能自动核销。

钱包差异登记与消费查看分离；是否影响某次人工结算，要看该差异是否影响已确认消费及处置结论，不重新要求钱包总差额为零才能查看或确认可靠消费。已知 140 诊断修正与费用汇总并行处理，91/107 的未知事件继续留存核查。

### 5.2 上线顺序与待评审事项

1. 完成入口枚举、确认样本和原业务关联核验，补齐 4.3 三组证据；同时核对跨月/未决口径及历史余额证据。
2. 修正同一对账路径的任务消费基数，缺口处仅补必要确认信息；验证分类守恒、已知业务反向覆盖及错误费用不混入可靠小计。
3. 小组织验证消费及钱包两侧日缓存、账单快照和统一页面/导出结论；新一天只处理必要范围，重复查询不重新统计；持续请求下验证限速、暂停和恢复。
4. 按需补历史并产出候选清单，逐步扩大范围；以 1430 万以上代表性分布验证首次处理及日常重复成本，另行完成线上索引维护验收。
5. 保留原结算/资金机制及人工确认依据。失败时暂停新统计、取消有界工作并保留进度；可回退程序路径，但有已知金额缺陷的旧结果只能标识为旧版参考，不能恢复成正确的正式收款依据。

本次实现沿用原消费日志的 created_at 归属，以 InvoiceOriginAt 固化既有边界，仍按原归属月应用系数。月末未决项供管理员核清，不自动确认部分金额；未新增宽限期或调账审批。结果承载与资源参数的当前实现见第 7 节，生产阈值仍须实测。代码及文档落地不等于已上线或已正式确认账单。

独立核验的最终费用及精确预期值是金额基准；旧计算器已存在退款基数缺陷，不能仅以“新旧一致”验收。未受修正影响的定价、折扣、成员规则及系数继续等价。扩展现有合适测试，使用确定性 fixture、testify 和真实回归场景，不用随机大循环或日志堆量冒充性能测试。

### 7.1 唯一计算路径与最小接线

### 7.2 性能、恢复及缓存边界

- 完整账单命中只读快照和必要当前余额；不在 HTTP 请求中归并 logs。版本升级为 9，旧版账单不会被贴成新口径结果。
- 每次后台构建冻结覆盖截止、证据时间与关系库日志 ID 上界。两侧稳定日缓存可跨快照复用；新日志、跨月任务完成、原日更正、成员/归属变化或明确刷新使必要范围失效。归属和原始日志的维护性改写必须配套失效，不能只改原表。
- 关系库首轮来源核验仍有一次必要的成员历史 ID 元数据读取，页大小默认 5000；不复制普通消费，不全表回写 logs。来源候选字节、候选行、页扫描量和各阶段毫秒数写入 summary.metrics。它是可恢复的一次性成本，不是每次查看成本。
- 消费片超时或候选任务超过 5000 时，从日切小时并继续二分至秒；只合并完整且互斥的叶片。每个片保留有界任务集合和最多 128 条任务事件引用，超界而无可靠最终确认时保留未决，不猜金额。钱包本期及期初范围共用持久细分、现金分项缓存，失败可复用已经完成的子范围。
- 钱包完整性与费用完整性分开；现金缺口、原扣款缺失、退款在途或期初不可用不阻断可靠费用。没有独立同期余额时显示 derived/待核对；不拿当前余额验证历史截止。
- PostgreSQL 重语句在同连接短事务内 `SET LOCAL statement_timeout`，默认 60000 ms；片预算默认 150 秒，超时细分，不能简单延长整月事务。MySQL/SQLite/ClickHouse 保留驱动 context 取消边界，不能宣称具有相同的数据库服务端超时保证。
- 默认批间延迟 25 ms，`ORGANIZATION_INVOICE_BATCH_DELAY_MS` 可调；`ORGANIZATION_INVOICE_PAUSED=true` 停止领取并在读批次/工作项边界暂停。环境变量由部署配置生效，首版没有新增在线控制台或自动保护器；暂停/恢复不清除进度。
- 每日自动快照沿用 `ORGANIZATION_INVOICE_DAILY_ORGS` 组织白名单，默认关闭；部署后先只启用组织 1。后台单 worker 仍共享数据库资源，不能据此承诺在线请求零影响。
- ClickHouse 原生历史日志没有可用唯一递增 ID，不能伪造关系库式证据冻结和迟到游标。当前保留完整快照读取、有限批次原生读取和原语义聚合；新快照保守重算来源日、不做跨快照日结果复用，并明确标识来源快照尚未核验。不能以这项降级宣称完成千万行 ClickHouse 性能验收。

缓存是派生数据，但任务关联缓存与游标必须成套维护：人工删除关联时同时删除该组织/版本的 source cursor、作废相应日结果与快照，再重建；不能只删关联、留下已推进的游标。清理旧版本时也须遵守这条约束。当前没有在在线路径新增自动历史日志清理；原生成片保留其租约/代次保护清理机制。

线上 `idx_created_at_id` 的 `(id,created_at)` 漂移仍是独立维护项：代码检测但不在启动时自动删建大索引。必须按真实 SQL 的访问计划另行核验/修复，不能把本次开发环境索引状态当线上已经解决；必要 `(user_id,type,created_at)` 候选索引仍须验证读写成本。

#### A.2.1 单一解析与有界读取

| 旧中文加额日志 | 保持现有兼容路径 |

SQL 候选只扩大到这三种 action，支持 JSON 空白差异；解析时校验精确 action，再依既有成员计费时间和离开时间过滤，不能用管理操作人的 `logs.user_id` 代替目标账户。

金额只接受明确 USD 前缀、额度后缀和普通十进制。覆盖允许零余额及合法负余额；加额、减额的输入幅度必须为正。用 decimal 运算，校验单位有效、余额边界及转换后整数 quota；不能靠截断、四舍五入、饱和或补零推测历史事实。覆盖无变化时不产生候选事实。历史单位如曾改变，且没有足够证据还原，应继续阻塞并人工核验。

#### A.2.2 去重与历史事实回填

携带 `adjustment_id` 或结构化 `quota_value` 的管理日志由结构化调额事实负责，必须在解码金额之前跳过，避免将现代数字 quota 按旧 USD 字符串解码。已核验旧事实以 `source_log_id` 去重；预览标识 AlreadyApplied，财务计算不重复累计。

现有旧事实表已使用有符号 bigint，无需改表。核验回填允许合法负差额，保留管理员核验、来源唯一约束及幂等写入；仍拒绝零差额、越界和无来源候选。正常读取可直接使用明确的旧日志，不要求先运行回填 API。

### B.2. 140：钱包预扣占用与账单资金回放没有对齐

### B.3. 91：新退款到账，另有旧差额；模型汇总还发现退款未净额化

退款前，历史账单推导余额为 186,646,977，备份钱包为 186,392,868，差额已为 254,109。新退款使推导值和钱包都增加 104,514，故差额保持 254,109，并非这 19 笔未退。旧差额对应的具体资金事件仍未找到，不能由差额反推一笔充值。
