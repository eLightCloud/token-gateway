# 计费与账单刷新语义及亿级数据性能优化方案（本轮目标：五千万条）

## 1. 问题与目标

组织详情的“计费”和“计费账单”存在长时间等待、账单提前显示 100%、已完成结果再次查询却重建、历史资金流水反复扫描等问题。用户于本轮实施时将规模上限调整为 **50,000,000 条源日志**，目标资源为 **8 核、16GB**，目前没有真实业务数据可供对账。本轮优化必须同时解决交互语义、缓存生命周期、有限预算内的有效推进和原始数据扫描成本。

本文是本次问题的后续实施方案。首批查询／重算分离、版本去重、上一版展示、消费成员窗口合并及计费用量固定目标自动跟踪已实施，验证记录见第 7、8 节；运行进程是否加载仍须独立核对。钱包预算修复已在此前本地运行中完成 9 月续算。本轮已实施分页访问、来源分类缓存、前缀补扫、资金批读、目标级推进保护和迁移前检查，新增验证与边界见第 9 节；完整构建、接口、数据库及生产灰度分别记录，不混用完成状态。

用户部署使用 PostgreSQL 18，性能优化以其实际访问路径为重点；数据库实测来自本地 PostgreSQL 18.4 导入样本，不代表生产配置。第 2.9 节补充 22:19—22:45 的日志及构建跟踪，第 2.10 节记录外部评审与源码核对后的取舍；第 3、4 节为最终实施顺序，第 6 节统一列状态。第 9 节记录本轮实际实现及独立测试，不将源码保存、构建通过解释为生产已发布。

### 1.1 用户已确认的交互要求

“计费”和“计费账单”均提供两个独立按钮：

| 按钮 | 用户意图 | 行为 |
| --- | --- | --- |
| 查询 | 查询当前筛选范围的最新可用结果和任务状态 | 命中有效结果即返回；缺失或已失效时按既有入口幂等登记必要计算；正在计算则查询同一任务，不重置版本、不清缓存 |
| 强制重新计算 | 明确要求重新生成当前范围的派生结果 | 先二次确认；确认后提交独立重建操作；服务端去重并管理新代次，不能因重复点击反复作废在途计算 |

二次确认必须明确组织、页面类型、日期范围和生效筛选，说明计算可能需要较长时间；取消确认不提交重建、不清空现有结果。确认不能只依赖前端禁用按钮，服务端仍须校验操作权限、范围和并发状态。

### 1.3 整体判断与下一步重点

最终方案保留现有账务口径、持久任务、共享许可和条件发布架构，先减少查询及缓存复用中的重复工作，再完善来源分类，最后按剩余瓶颈决定索引和参数。前台首屏、用量缓存投影及账单冷构建是不同路径，不能用同一条慢 SQL 或一次总耗时解释全部等待。首批已完成的交互不重复建设。

| 顺序 | 重点 | 当前依据与边界 |
| --- | --- | --- |
| 1 | 补观测、推进保护和部署前检查 | 区分正常让出与连续零进度；记录排队／许可／资金哈希阶段；阻止既有日志表缺索引时启动隐式重建 |
| 2 | 首屏／深页及缓存批量化 | 首屏全局 Top N 和深页行比较已有样本对照；缓存复用仍有逐日事务，六类资金哈希优先按有界范围批量读取 |
| 3 | 来源分类与历史缺口复用 | 7 月账单已完成有效续算，来源准备仍有成本；更早范围只补未覆盖依据，保留已验证事实，核查新增写入来源完整性 |
| 4 | 按瓶颈选择索引、扫描粒度和参数 | 日志头覆盖、结构化来源部分索引和历史多日扫描均为条件实验；不默认同时建设全部候选，参数在最终 SQL 上重测 |
| 5 | 独立正确性、五千万条负载和灰度验收 | 真实三库及受影响日志库、独立源对照、恢复与并发回归、预先冻结容量预算后再发布 |

月中资金前缀是独立能力补足，不作为性能收益计入。按 8 核、16GB 目标资源进行的五千万条混合负载与生产灰度验收仍须独立完成；分区、BRIN 等物理结构调整只有在前述优化后仍有明确瓶颈时进入专项评估。

### 2.2 早期已确认的问题链及后续对应

以下描述第 2.1 节诊断窗口中的行为。查询误重建和旧结果展示已由第 7 节改造，计费用量结果同步已由第 8 节补足；不能把下列各项全部解释为当前源码仍未修复。

1. 账单刷新参数进入[服务入口](../../service/organization_invoice_summary.go)后，先调用失效，再尝试读取 ready 缓存。
2. [失效实现](../../model/organization_invoice_summary.go)会清空月结果及重叠范围的日用量、钱包、覆盖缓存，没有在该更新中排除 building。
3. 新版本不复用旧代次的账单分片；[前端刷新逻辑](../../web/src/features/organizations/use-organization-invoice-query.ts)依赖本地是否已有 generating 结果，不能阻止其他标签页、旧客户端或首次选择范围触发重建。
4. 原资金流水可保存单元预算为 150 秒，外层工作轮只有 30 秒；外层先取消时，日结果及拆分状态来不及保存，内存分页游标下一轮重新开始。
5. 历史来源仍依赖读取 `other` 并解析 JSON；重建及重复读取放大数据库、传输和应用解析成本。
6. 共用重查询许可限制并行扫描是必要保护，但目前交互构建可能长时间等候；同组织不同月份主要按月份顺序选择，跨组织轮转不等于同组织内公平调度。
7. 截图骨架屏的说明文字仅在 `sr-only` 中，视觉上不能区分请求中、排队、计算和失败；源码与运行产物的状态同步策略还不一致。

### 2.3 SQL 计划验证

早期对下列候选进行只读 `EXPLAIN` 对照，当时未执行这些重查询。消费成员窗口合并现已落地，见第 7 节；分页后续的真实执行重放见第 2.8 节，不能继续将其描述为只有计划证据。

| 候选 | 本地 PostgreSQL 18.4 计划 | 判断 |
| --- | --- | --- |
| 当前 OR 游标 | `idx_created_at_type`；游标位于 Filter；有 Incremental Sort | 返回 5,000 行不代表仅检查 5,000 行，深页可能重复过滤前缀 |
| 等价行比较游标 | `idx_created_at_id`；`ROW(created_at,id) > ROW(...)` 进入 Index Cond；排序节点消失 | 早期计划证据；后续一个真实页的扫描量及耗时对照已补充于第 2.8 节 |
| 钱包聚合另加全局时间条件 | 原计划已推导出时间边界；增加条件后未改善 | 不列为已证明有效的优化，不机械套用 |
| 账单消费聚合逐成员 OR | 81 个成员、实际上只有两组时间窗；143 个计划节点、81 个用户索引子扫描、28 个时间索引子扫描 | 单条 SQL 内存在重复索引工作，不能误写成额外执行了 109 条 SQL |
| 同一账单消费聚合合并相同窗口 | 保留两个窗口并各自使用 IN 后，计划缩为 2 个节点、1 个时间索引子扫描 | 已完成代码及三库等价回归；生产规模耗时收益尚未验收 |

索引条件、Filter 与实际扫描量的区别见 [PostgreSQL 18 EXPLAIN 文档](https://www.postgresql.org/docs/18/using-explain.html)。不把计划 cost 当毫秒，也不根据计划变化承诺加速比例。

### 2.5 二十分钟复核：重复工作与必要工作的区分

固定窗口为 21:19:52—21:39:52：29 轮账单构建累计约 731 秒；构建观测记录 4,070 条 SQL、7,400,287 返回行、21 次 SQL 错误。6 轮计费用量构建累计约 2.9 秒，无 SQL 错误。账单接口 119 次请求最高约 1.69 秒；日志明细 6 次最高约 3.65 秒。

- 历史 JSON 分页的一个指纹在 9 轮内执行 863 次、返回约 426 万行、累计约 189 秒；其中包含正常分页，但游标回退证明存在重读前缀，不能把 863 次全部判成重复 SQL。
- 21:33 之后窗口内完成的 13 个账单任务均记录正进度；后半段不能再归为连续零进度循环。
- 资金日缓存命中前，`organizationInvoiceWalletSourceHash` 仍查询六类来源并序列化计算哈希；多轮遍历已完成日期会重复这些校验。可按单轮批量读取及可靠来源修订优化，不能直接删除失效检测。
- 请求月份未 ready 时，[快速读取](../../service/organization_invoice_read.go)失败后，[依赖遍历](../../service/organization_invoice_summary.go)可能再次查同一月记录；可在单次请求内复用读取结果，优先级低于源 SQL。
- 当时[账单消费窗口](../../model/organization_invoice_shard.go)仍逐成员拼 OR，而计费用量已合并相同窗口。当前已接入[消费窗口合并](../../model/organization_invoice_member_filter.go)，见第 7 节；[钱包所有权窗口](../../model/organization_invoice_wallet_aggregate.go)仍须单独评估等价合并，不能照搬消费有效期规则。
- 旧直接聚合实现当前主要被测试参考路径使用，未发现它与生产分片构建同时执行的证据；不能仅因代码相似就删除独立参考计算。
- 21:38 重启覆盖了旧控制台 SQL；构建观测未覆盖所有主库元数据查询，相同指纹也不代表相同参数。上述统计不是全库全部 SQL 的精确计数。PostgreSQL 并行 worker 退出可重复打印同一语句，诊断人员的错误查询也不能计为应用计算错误。

### 2.7 专家意见合并后的修正

1. “8 月服务端完成、前端可能定格”“普通查询误发强制标记”“旧钱包预算造成重做”的根因成立。但当前后端已加载修复并完成 9 月，不能继续把“9 月仍卡死”“现在需要重启”列为现状。
2. 当时前端禁止自动重取，可能缓存 generating 直到手动刷新；但 21:29 后日志仍有多次普通 GET，存在前端版本切换，不能断言整段历史完全没有重取。计费用量现已按第 8 节补足固定目标自动跟踪，账单仍沿用手动查询；不能把早期两页行为继续统一描述为当前状态。
3. `wallet_source_hash` 只覆盖六类充值／调额等资金事实，未覆盖消费日志本身。不能仅凭该哈希决定所有日缓存有效性，必须保留日志来源修订、投递、成员窗口和版本栅栏。
4. “494 万返回行 / 299 秒”包含重复读取及混合开销，不是独立源扫描吞吐；由此推算“一亿行必需约 1.7 小时”不能成为容量结论。总库一亿行、单月一亿行、单组织一亿行是不同负载。
5. 默认 60 秒 statement timeout 并非实际始终为 60 秒。[执行封装](../../model/organization_stats_query.go)会取配置上限与当前剩余期限的最小值；10 秒单元中 SQL 通常已受更短期限约束。
6. 预分片可减少试探浪费，但不默认先做精确 COUNT；COUNT 本身可能昂贵。优先利用已有密度、分片耗时和来源游标决定初始粒度，测量后再引入额外统计。

## 3. 优化方案

### 3.1 P0：拆分查询与强制重建

两个页面统一遵循以下动作表，日期和筛选先作为草稿编辑，点击按钮后才提交；页签切换、聚焦、重连不能隐式强制重建。

| 当前状态 | 查询 | 强制重新计算并确认 |
| --- | --- | --- |
| 有效历史 ready | 返回相同可用代次；允许既有的当前余额补充；零源日志扫描 | 登记新重建目标，保留上一版可读结果 |
| 当前日 ready | 显示已覆盖截止；若已跨完成桶，只补必要缺口并幂等登记 | 为确认时冻结的目标范围登记重建，不追逐持续变化的截止 |
| queued / building | 返回同一任务及进度，不增加代次、不清已完成工作 | 相同范围已有满足目标的重建则返回该任务；不反复重置；有必要的新来源修订合并成待办后继 |
| 无结果 / 已失效 | 登记缺失或确需修复的范围，复用仍有效依据 | 明确登记新的计算代次及重建范围 |
| failed / paused | 返回原因、允许的恢复动作及已有结果；不无条件重试确定性数据错误 | 可重试的失败按服务端规则重新登记；暂停和资源准入不能被绕过；数据缺口不能被当作已解决 |

实施要求：

- 普通查询不再携带账单 `refresh=1` 或用量 `refresh=true/1` 等现有重建标记；两类旧参数在两个页面的调用方均需核对。
- 普通查询连月级 summary 也不主动作废；“仅清 summary、保留日缓存”仍是重建，不是普通查询。首次提交新范围时，本地缓存不存在不能成为强制重建依据。
- 重建采用独立 POST 入口，管理员和用户侧路由及目标版本前提已实施，具体路径见第 7.1 节。普通 GET 路径保持兼容；旧 `refresh=1/true` 没有目标版本，无法同时保证“强制重建”及完成后的重试去重，因此明确拒绝并提示迁移到带版本的 POST，不能静默降级或继续清缓存。
- 二次确认复用项目共享 ConfirmDialog；需要展示重建组织、范围、筛选及预计排队影响，不承诺未经测量的完成时间。按钮文案分别为“查询”“强制重新计算”，仅维护 en/zh。
- 构建中重复提交、跨标签页、HTTP 重试均由服务端按组织、类型、范围、筛选、目标来源修订去重。使用幂等标识和条件更新，前端判断仅用于交互。
- 重建身份只包含业务计算身份；目录请求、页码和 UI 展示状态不得制造额外重建。筛选计费只能影响所选范围，不能连带清空整个组织的基础目录与其他筛选缓存。

### 3.2 P0：保留已发布结果，构建状态独立表达

不能再通过清空唯一可读 payload 表示“正在更新”。沿用现有代次、条件发布和物化结果能力，补足账单上一版结果保留边界，不另建进程内金额缓存。

- 将“当前计算任务”和“最后成功发布结果”明确分开；重建中可返回两者，但旧结果必须标明代次、数据截止、生成时间和“上一版结果／重建中”。
- 无有效旧结果时展示明确排队、阶段、已保存单元和最近有效推进时间；不要只展示无限骨架屏。
- 一旦旧结果因实际来源变化被判为不再准确，必须标明失效，不得仍标为当前有效。页面可按现有权限展示参考，正式导出不得默默使用它。
- 来源修订、成员窗口、覆盖完整性、租约 owner 和计算版本全部满足时才原子切换发布结果；旧 worker 不得覆盖新代次。
- 新代次失败时保留上一版及失败原因；不能把未完成资金流水或超时产生的空财务值包装为财务完整。消费结果发布状态与资金完整性分别表达，保留现有不完整诊断。
- 不同精确范围不混用：9 月 1—29 日不能冒充 1—30 日完整结果；允许复用有效日片后补齐剩余范围。
- 保持当前余额为查询时动态字段的现有口径；不得将其误标为历史快照余额。

### 3.3 P0：保证有限预算内有可保存进度

复用[资金流水范围缓存](../../model/organization_invoice_wallet_cache.go)、[工作轮预算](../../service/heavy_stats_permit.go)和[进度边界](../../model/organization_stats_budget.go)。本地修复已加载并以 9 月完成续算验证有效，后续重点是取消、来源变化和各数据库下的恢复回归，不再把重复重启作为修复步骤。

| 层级 | 本轮设计 | 完成条件 |
| --- | --- | --- |
| 重任务工作轮 | 初始沿用 30 秒上限；受许可租约约束 | 在边界主动让出，及时释放资源，不依赖硬取消完成正常交接 |
| 可保存单元 | 初始最多 10 秒，且小于剩余轮次预算并预留持久化时间 | 超时前后能保存 split 或完成子范围；没有足够预算则不启动 |
| 单条数据库查询 | 受单元剩余时间约束 | PostgreSQL 事务内 statement timeout；其他方言验证驱动 context 取消行为，不声称等同服务端超时 |
| 结果保存与发布 | 在有效 owner、代次及来源栅栏内执行 | 未完成不能发布；保存必须计入总预算，不能为躲超时改成无界后台写入 |

资金流水当前沿用日范围自适应拆分、保存拆分树和已完成子范围的机制，先验证优化后的单元能否在预算内提交。如果实测仍有不可接受的页内重做，再扩展同一路径，将分页游标与累计结果保存为同一原子检查点，不并行维护第二套计算器。只有记录游标而未原子保存累计结果，会漏算；只保存累计结果而游标未推进，会重复记数，均不允许。

正常取消、进程退出、来源变化和真实数据错误分别处理。当前固定约 15 秒节流仅是准入保护，不等于连续阻塞已经得到治理；新增策略按组织、任务类型、精确范围／筛选及来源修订识别业务目标，复用现有任务持久状态，不另建队列：

- 有已提交进度且未被来源变化阻断时正常续作；第 2.9 节 7 月账单的三次让出属于此类，不因轮次耗时约 20 秒就增加退避。
- 连续零进度记录原因及可恢复位置，使用有上限的递增退避；若原因为同一单元超时，按已有机制缩小范围并保存前沿，不能只加等待时间。
- 数据错误进入确定性失败，不因轮询自动重试；暂停、许可忙、来源变更与数据缺口分开处理。依赖或来源修订变化后重新评估该目标，不将一个阻塞月份的退避施加到全组织／任务类型。
- 同原因长期无进展须返回明确阻塞及允许的恢复动作，不无限创建无效任务；具体退避上限及升级阈值在基线阶段冻结，再以故障恢复及公平性回归验证。

`progress_units` 仅统计已提交的可恢复业务工作，不计心跳、认领或任务状态写入；正常结束的 SystemTask 也不等于账单已发布。

10 秒和 30 秒是本地初始预算，不是生产 SLA。验证后按实际单元耗时、保存余量和网关资源影响调整，不能用扩大超时掩盖重复扫描。

超大日的初始切片可参考已保存的来源密度、历史耗时和稳定日志范围，必要时从小时或更小范围起步；保留自适应拆分作为兜底，但避免逐层耗尽预算才发现重日。不能为分片默认增加全量 COUNT 或依赖 ID 与业务时间严格单调；导入、迟到记录和有效期仍须受相同证据约束。

### 3.4 P1：首屏全局 Top N、深页访问及批数一起优化

消费聚合相同窗口合并已完成，后续不重复计算其收益。当前 SQL 首项是组织日志首屏：第 2.9 节慢请求没有游标，单改行比较无效。优先验证在有界成员窗口规模下，把完整有效窗口合并为一条 SQL，按 `(created_at,id)` 全局排序取 `limit+1`，避免各成员批次分别读取和排序后再等待最慢批次。它只改变消费日志访问，不扩大成员权限或资金归属。

- 回归当前 173 窗口样本及更大／更小组织、稀疏匹配、历史成员段、空范围、模型和渠道筛选；所有窗口仍按真实有效期裁剪。全局 Top N 的身份、顺序及 has_more 与既有全批次归并精确一致。
- 合并不是无限扩张 SQL：记录窗口数、参数数、规划时间和内存，在基线阶段确定有界处理规模；超出规模时选定可验证的有界访问方案，不能静默截断成员或只返回部分批次。若必须分批，仍需证明全局前 N 完整，并单列批数成本。
- [账单分页](../../model/organization_invoice_heavy_query.go)候选使用 `(created_at,id) > (?,?)`；[组织日志倒序分页](../../model/organization_usage_logs.go)对应 `<`。保持全部成员／来源筛选、冻结 ID 上限、时间上界和稳定排序；不能假设 ID 与业务时间严格单调。
- 回归首／中／深／尾页、同秒高密度、边界零值、空页、非连续 ID、导入及迟到日志；在冻结同一来源时，完整遍历的有序身份无漏无重，资金累计与独立参考值精确一致。单页摘要一致不能代替完整遍历。
- 实测真实 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6；PG 18 为目标部署额外采样。各方言优化器对行比较的使用可能不同，分支只处理有证据的访问差异，不能复制资金计算逻辑或默认保留两套计算器。ClickHouse 保留已有独立游标合同。
- 使用 `Rows Removed by Filter`、实际行数及 loops、缓冲页、排序／临时块、成员批数和分页深度评估；同时报告规划、SQL 累计及完整 HTTP 耗时，不把单批计划收益等同全请求收益。不以 `LIMIT 5000` 或固定索引名断言性能。
- 账单和前台日志分别测量；覆盖小组织／大组织、模型／渠道筛选和空匹配，保留前台读取预算，不引入逐成员 COUNT。历史日志最高约 3.65 秒只是诊断样本，不是当前 p95。
- 钱包所有权窗口可按完全相同的实际归属起止合并为 IN；须单独证明离组、跨组织、重叠归属和加入前资金等价。消费窗口合并已验证不代表资金窗口已验证。
- 消费窗口的两处实现先通过同一组业务边界用例保护，不为减少局部重复扩大重构；只有发现真实行为漂移才实施最小统一。不能把钱包所有权纳入这一统一。
- 若查询改写后仍有大量回表或空结果扫描，再进入第 3.9 节索引对照，不先同时建设全部候选。

### 3.5 P1：历史 JSON 来源一次解析、按证据复用

建立或扩展独立、可追溯、可重建的来源分类派生依据，复用已有任务关联、来源游标、窄类历史调额事实及投递恢复，不新建第二套扣费账本。核查新增来源完整性与历史分类并行：以实际扣费／订阅／退款路径的权威来源写入，发现遗漏才补齐；不能把缺失信息一律填 wallet。现有 Midjourney 和 journal 已有来源记录，不重复实施。

1. 明确记录源日志身份、来源版本／投递证据、归一化分类、解析状态以及计算所需最小事实；避免持久复制完整 `other`。
2. wallet、subscription、未提供来源、未知来源、损坏 JSON 分别处理；保持原有合法默认语义，但不能为了性能把未知或错误直接判为 wallet。
3. 历史解析按有界页推进，派生事实与游标原子提交；相同源记录重试不重复计算、不重复写事实；事实校验后才供资金汇总使用。
4. 同一有效来源证据重复计算时，重用分类和稳定事实；强制重新计算应重新生成目标派生结果，但不默认删除全组织来源索引或重新解析所有历史 JSON。
5. 迟到、回填、删除、同 ID 变化等情况沿现有来源修订和投递协议失效；全局最大 ID 不能单独证明没有迟到或改动。
6. 无法确认的范围标记缺口并保留审计依据，不将源扫描中断解释为“零消费”或财务已完整。

来源覆盖与账单范围解耦：后续查询更早月份只补尚未分类的历史缺口，保留已验证的后缀事实；新增日志仍沿既有投递和增量游标处理。不能简单删除当前较早起点会重置游标的保护，再假定旧依据已包含新范围。补齐历史的检查点、分类覆盖及源修订必须一起验证，避免两个前沿各自声称完整。

同一有界解析流程为钱包分类和现有任务关联产出最小事实，避免两条路径分别重读完整 JSON；保持两类业务归属规则独立。稳定身份至少区分来源实例、日志身份和解析版本，唯一性／幂等模式可参考 `UserQuotaAdjustmentLegacyFact`，但不能只照搬正整数 SourceLogId：来源替换、同 ID 变更及 ClickHouse 无稳定 ID 场景必须遵循原合同或保留明确限制。

本项同时治理历史 `other LIKE` 分页和 `other NOT LIKE` 聚合，避免只改善一条路径后仍反复读取宽字段。归一化分类的完整覆盖证据须先于汇总复用；派生事实尚未覆盖的范围继续按原有正确语义读取，不能把缺失分类当空结果。验证首次分类、同证据重复重建和迟到失效后的解析行数／字节量，分别报告必要增量与重复读取。

不默认将亿级 `other` 全量改为 JSONB，也不把 PG18 默认的虚拟生成列当作“一次解析”：虚拟列读取时仍计算。若后续评估存储生成列或表达式索引，应另列历史重写、非法 JSON、锁及维护成本；不能绕过本项来源版本和跨库合同。

若需要新表、索引或历史迁移，单列存储膨胀、回填速度、暂停恢复和清理预算；先评审最小方案，再跑三库新建、历史升级及重复启动。不得直接对生产一亿行执行无界回填。

### 3.6 P1：增量更新、精准失效与调度公平

- 保持源日志、标准化证据、日／子范围结果、筛选投影、月快照的失效边界清晰；强制某个视图重算不等于全组织全部派生依据失效。
- 钱包来源哈希只作为资金事实的一项证据；日志新增／迟到／退款的失效仍走来源修订和投递链路，哈希未变不代表日志没变。缺失或无法核验的证据保持保守失效，不能以缓存命中率替代准确性。
- 当前日仅推进已完成桶；历史已封闭范围没有来源变化时稳定读取。确认任务时冻结截止，后续新事实通过既有修订机制处理。
- 成员有效期、任务原始归属及系数变化沿既有入口传播；系数调整继续优先采用已有轻量重算，不能重新播放全部钱包流水。
- 保留跨任务共享重查询许可，不能通过增加 worker 数直接放大数据库压力。
- 区分用户当前请求的必要构建、历史资金修复和模型准备；在持久化边界给短任务执行机会，并在同一组织内轮转范围，避免一个旧月份长期占据所有轮次。
- 复用现有 SystemTask、许可和待办发现；持久化待办顺序／等待年龄，验证去重、恢复和防饥饿。无需新增第二套队列。
- 许可等待、调度等待、计算耗时和无进度退避分别记录；不能将 `SystemTask=succeeded` 当作账单发布成功。
- 用量投影缓存优先治理逐日事务：[依赖加载](../../model/organization_usage_dependencies.go)有界批量读取日修订、覆盖及切片，对已完整覆盖的日期批量验证；只为缺失或扩展范围执行覆盖登记。复用已有日修订批量锁定能力，扫描前登记、保存及发布前的成员／来源／owner 栅栏均保留，不能以只读快路径跳过晚到投递检测。
- [钱包来源哈希](../../model/organization_invoice_wallet_cache.go)目前在日缓存命中前读取六类资金来源。默认每个有界范围各类分别批量读取一次，再按精确日期／子范围生成原等价哈希，把查询增长从逐日六次改为按有界批块增长；保留原字段、来源标识、确定性顺序及空值／数值序列化语义，不默认改为跨表 UNION ALL。
- 多条资金读取须明确一致读视图，并继续在保存／发布时核对相应修订；PG Read Committed 的同一事务并不保证各条 SELECT 是同一快照。跨库验证实际隔离语义，不以事务包装或 max(updated_at) 水位替代完整性。跨轮不无限缓存；旧记录原地修改、删除、退款、成员变更、空日及拆分子范围都须回归。[PG 隔离级别说明](https://www.postgresql.org/docs/18/transaction-iso.html)
- 请求内复用已读取的月记录和依赖，避免 ready 快读未命中后再次查同一行；优先级低于重源 SQL。元数据查询次数、序列化字节及阶段耗时单列，不能将减少往返写成原始日志扫描量下降。

历史用量多日扫描在缓存批量化之后按证据实验：当前合并仅覆盖同日五分钟桶，历史日片仍逐日。若阶段计时证明历史逐日源读取是剩余主因，可在执行时间、cell 及内存上限内一次读取相邻日，按现有日切片落库；先登记各日覆盖，保存及发布分别校验修订，超限缩小范围且不截断结果。此项未实测收益，不以合并次数直接推算输入行数减少。

### 3.8 P1：单列月中区间的资金完整性

- 本项按第 9 节实现及测试；771 当时的发布不构成本项的验收证据，不改变原确认费用与钱包收支的唯一业务依据。

| 剩余主因 | 候选 | 适用边界 |
| --- | --- | --- |
| 来源日志头分页回表 | `(user_id,id) INCLUDE(created_at,type)` | 第 2.9 节已有真实读取成本；只优化轻量日志头，任务候选 LIKE 与资金分类仍有独立成本 |
| 结构化来源空结果及回表 | 下列部分覆盖索引 | 第 2.8 节已有空聚合样本；只有该路径仍占主因且读写对照有净收益时采用 |

结构化来源候选仅覆盖[钱包聚合](../../model/organization_invoice_wallet_aggregate.go)，不包含宽 `other`：

```sql
CREATE INDEX CONCURRENTLY idx_logs_structured_wallet_candidate
ON logs (user_id, type, created_at, id)
INCLUDE (quota, billing_source)
WHERE billing_source IS NOT NULL AND billing_source <> '';
```

这是 PG18 对照候选，不是部署指令。`INCLUDE` 字段覆盖金额和来源读取；是否真正采用 Index Only Scan、减少回表，仍取决于选择率、成员窗口、来源上限、可见性及实际计划。日志头候选遵循同样限制，均需比较是否替代已有普通索引，但不删除主键或唯一性保证。[官方覆盖索引说明](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

- 对照无索引与该候选，覆盖有结果／空结果、大小组织、历史日／当前日、结构化来源密集／稀疏和混合读写；记录候选过滤、Heap Fetches、索引及总关系大小、WAL、写入吞吐和前台 p95／p99。若主要成本是用户条件缺乏选择率，重新比较时间优先列序，不强制保留此候选。
- 部分索引的谓词必须能由真实查询推导，使用应用实际驱动／代理方式检查计划；不能仅测试手写常量 SQL。当前 PG 连接使用 `PreferSimpleProtocol: true`，不将泛化计划问题直接当作已复现根因。[官方部分索引说明](https://www.postgresql.org/docs/18/indexes-partial.html)
- 本地 `type=2` 占约 95.77%，仅排除其他 type 的部分索引不作为优先缩小方案；也不直接加入全部模型／渠道／Token 字段建立通用宽索引。
- 保留独立维护、短锁窗口、有效性检查及回退流程，不在启动 AutoMigrate 中创建大表索引。原 `organization-log-index` 工具仅维护时间索引；本轮新增覆盖候选入口与中断恢复，见第 9.4 节。
- 若计划替代已有索引，维护及漂移校验须分别识别 key 与 INCLUDE 列，不能把普通列序检查直接用于新结构；同名替换前验证所有实际调用及唯一性，保留回退依据。
- `INCLUDE` 不适用于最低 PG 9.6，MySQL 也不支持此部分索引语法。该候选是部署侧 PG18 物理优化；默认跨库查询保持同一业务合同，其他引擎按其实际访问路径验证，无需复制资金算法。

#### 3.9.2 统计信息按估算偏差处理

先比较 Actual Rows／Plan Rows 和分组估算，评估 `user_id/type/billing_source` 的 MCV／依赖统计，以及用量分组列的 ndistinct；不为每种筛选组合创建统计对象。相关机制存在版本差异，应限定于目标 PG18 部署维护。

本地 analyze 后修改计数为 0，不把“重跑 ANALYZE”当作已证实修复；真实持续写入的亿级库再按修改量评估每表自动分析阈值。依赖统计不能普遍修复时间范围、LIKE 或不兼容条件导致的估算问题。[官方统计信息说明](https://www.postgresql.org/docs/18/planner-stats.html)

#### 3.9.3 内存、JIT 与 AIO 以修正后的查询对照

- `shared_buffers=128MB` 是本地观测，不直接推广到生产。记录容器／主机实际可用内存、其他进程、OS 缓存和连接数后设置预算；`effective_cache_size` 只是规划估计，不是分配缓存。
- 复用现有 `ORGANIZATION_STATS_POSTGRES_DISABLE_JIT` 和 `ORGANIZATION_STATS_POSTGRES_WORK_MEM_KB`，默认维持原设置。以交叉顺序比较默认、仅关闭 JIT、关闭 JIT 加局部内存；记录 JIT 时间、排序／哈希落盘、CPU 和内存。第 2.8 节两个空聚合无落盘，提高内存不能消除它们的候选扫描。
- `work_mem` 按执行算子、并行 worker 及同时活动查询累计，哈希还受 `hash_mem_multiplier` 影响。维持共享重查询许可，不以增加并行或扩大工作轮超时代替优化。
- 本地 `io_method=worker` 已启用异步 I/O。只有观测证明相关顺序／位图扫描等受存储读取限制时，才比较 I/O 并发；`io_uring` 依赖构建及平台支持，不默认要求切换。AIO 不消除多读的行，skip scan 也不替代合适的索引列序。[官方资源参数](https://www.postgresql.org/docs/18/runtime-config-resource.html)、[PG18 发布说明](https://www.postgresql.org/docs/18/release-18.html)

#### 3.9.4 先补足数据库观测，再采集收益

在授权目标环境启用 `pg_stat_statements`，记录统计起止而不重置共享统计；增补 SQL 总执行时间、调用次数、每次返回行、缓冲命中／读取、临时块和 WAL，并按应用已有指纹与阶段关联。其加载可能需要重启，应列入运维窗口。`track_io_timing` 先评估采样开销，再结合 PG18 的 `pg_stat_io` 区分 I/O 时间与 CPU／缓存成本；不能把缓冲 read 或进程累计值当成本工作包的物理磁盘读取。[官方 pg_stat_statements 说明](https://www.postgresql.org/docs/18/pgstatstatements.html)

保留快速 SQL、连接池等待、许可等待和调度等待。源查询、来源分类、资金依赖、持久化、发布分别计量；层级阶段墙钟和 SQL 累计时间不直接相加。诊断材料不记录可用凭据或完整敏感 `other`。

应用侧复用 observation 和 SystemTask 补齐登记、首次认领、许可竞争、最近有效推进及发布的时间点，记录等待次数／时长、yield 原因、连续零进度及 `continuation_deferred`；钱包哈希设独立阶段。当前获取许可是忙则返回，不把函数内等待时间冒充整个排队时间。指标按业务目标和轮次关联，多个等待阶段可能重叠，不能直接相加。无调用等待函数的清理与性能工作分开，不引入阻塞等待或新监控平台。

#### 3.9.5 分区、BRIN 与全表维护暂不列入首批

`created_at` 的高物理相关性使 BRIN 值得在超大时间范围扫描时评估，但不能替代有序深分页 B-tree，也不能减少必须聚合的范围内事实。只有前述 SQL／分类／缓存优化后，仍出现可重复的时间范围 I/O 或保留期清理瓶颈，才进入独立实验。

按时间分区前必须处理 `id` 主键及 `billing_operation_id` 全局幂等唯一性；PG 分区表主键／唯一约束需要包含分区键，不能直接附加 `created_at` 后声称原唯一合同不变。另列迁移、迟到分区、按 ID 查询、清理及三库兼容方案，不在本轮直接重建历史大表。[官方分区限制](https://www.postgresql.org/docs/18/ddl-partitioning.html)

### 3.10 P0：部署前索引检查及后续超时兼容边界

[主库及日志库迁移](../../model/main.go)均可能 AutoMigrate Log，现有标签声明的 `(created_at,id)`、`(created_at,type)`、`(user_id,id)` 在完全缺失时仍有普通创建通道；[只读漂移检查](../../model/organization_invoice_index_check.go)不会拦截此前 DDL。最终方案要求在迁移前区分新表与既有表：新建空库正常初始化；既有日志表缺失或错序索引进入明确的独立维护流程，阻止启动顺手补建大索引，不通过全表 COUNT 决定是否保护。保留必要主键及唯一索引，不能以跳过全部迁移规避问题。[GORM 索引说明](https://gorm.io/docs/indexes.html)、[PG 普通与并发建索引](https://www.postgresql.org/docs/18/sql-createindex.html)

此保护已按第 9 节实施，实测主／独立日志库、既有表缺索引、索引正确／错序／无效、新建库、升级及重复启动；显式维护保留 prepare、结构及真实负载验证、激活、中断恢复和回退边界，不能把当前时间索引 CLI 当成任意候选索引工具。

MySQL 服务器端超时作为 P2 兼容增强：对适用的只读 SELECT 可按剩余预算使用 `MAX_EXECUTION_TIME` 提示，先验证实际生成 SQL、驱动／代理、取消后连接恢复及最低支持版本；不默认修改连接池会话设置，不宣称其约束 UPDATE、写事务或整个构建轮次。SQLite 保留驱动 context 及取消回归。当前 PG18 已有事务局部超时，不为此延后其主要查询优化。[MySQL 5.7 官方说明](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/optimizer-hints.html)

### 7.1 已落地行为

- 管理员与用户侧两页均显示【查询】【强制重新计算】。编辑筛选仍只修改草稿；查询才应用草稿。强制操作仅针对已查询并确认的范围，确认框展示组织、页面类型、日期、筛选与数据覆盖截止，说明可能耗时较长；取消不会提交。计费用量构建中会跟踪已提交的固定目标并自动显示结果，ready 后停止；仍可通过【查询】主动读取，未引入全局自动轮询。

修正查询后的局部参数交叉对照保持数据库全局 `jit=on`／`work_mem=4MB`。固定历史候选页默认 2849.571／636.328ms，单关 JIT 为 2691.196／369.270ms，关 JIT 加事务局部 8MB 为 353.659／241.388ms；4MB 临时读 484 块、写 3380 块，8MB 样本无临时块，默认 JIT 编译约 40—49ms。说明该页存在排序内存瓶颈，但冷暖差异仍明显，不能只归因于参数。复用已有 `ORGANIZATION_STATS_POSTGRES_DISABLE_JIT`、`ORGANIZATION_STATS_POSTGRES_WORK_MEM_KB=8192` 供目标环境再验证；本轮不改默认值、不扩大并发。全局参数在事务结束后仍为 on／4MB，源码矩阵也检查局部设置不泄漏。

完整构建与恢复记录（源库始终只读，派生主库为隔离 SQLite，原始 50,000,000 行未由构建器写入）。首建的“冷”指派生表和应用缓存为空；未清空宿主机／数据库 OS 缓存，不能当成物理磁盘全冷实验：

- 9 月第一次以更严格 20 秒工作轮／5 秒单元运行，在十分钟诊断窗口仍未结束。初版验收脚本在总时限边界仍发起空轮，误触八次无进度停止；这属于验收脚本错误，已修正为提前保存检查点退出并遵守持久退避。该次运行不作为容量通过证据，保留原日志。

### 9.4 显式启用及回退

先在目标环境核对已有三项日志索引；缺失、错序或无效时先维护再启动，检查本身不会执行建索引。既有 `time` 工具仅处理时间索引，其他缺失索引按各数据库显式维护，不声称一个命令能修复所有结构。

日志头覆盖候选使用新增维护入口，DSN 从环境变量读取，不写入文档或命令日志：

```sh
go run ./cmd/organization-log-index -database-type postgres -dsn-env LOG_INDEX_DSN -candidate source-header -phase prepare -timeout 30m
go run ./cmd/organization-log-index -database-type postgres -dsn-env LOG_INDEX_DSN -candidate source-header -phase verify
# 在真实读写负载比较后确认保留；不会移除原 (user_id,id) 索引。
go run ./cmd/organization-log-index -database-type postgres -dsn-env LOG_INDEX_DSN -candidate source-header -phase activate
# 中断产生无效候选时恢复；性能无收益时明确回退。
go run ./cmd/organization-log-index -database-type postgres -dsn-env LOG_INDEX_DSN -candidate source-header -phase recover
go run ./cmd/organization-log-index -database-type postgres -dsn-env LOG_INDEX_DSN -candidate source-header -phase drop
```

实际维护索引名为 `idx_org_source_header`、`idx_org_wallet_structured`、`idx_org_wallet_unmarked`、`idx_org_wallet_legacy`。钱包来源候选分别使用 `-candidate wallet-structured`、`wallet-unmarked`、`wallet-legacy`，阶段与 source-header 相同；按剩余瓶颈逐项验证，只对收益已确认的项执行 prepare。`activate` 表示结构验证通过后的运维确认，本身不强迫优化器选索引、不删除原索引，净读写收益仍需实测。`recover` 仅删除已识别的无效候选，保留有效候选；`drop` 才明确删除已验证结构的有效候选。

维护会核对目标表、键／INCLUDE、有效性、唯一性和约束；拒绝删除同名异常结构或唯一约束。只在隔离库验证和实验，未对业务库执行此命令。回退不是直接启动旧二进制：本轮把日缓存 `scope_hash` 从 64 扩至 128，并增加前缀检查点，旧 worker 不认识未完成前缀。应先停止全部相关 worker、保留数据库及构建备份；回退前清掉派生的 `task-source-associations:<user>:prefix:*` 关联块，并将来源游标标为需重建（`version=0`），使旧实现重建其任务关联；确认没有超过 64 字符的缓存 key，再让旧迁移处理列宽。也可先把兼容列宽及前缀处理回移到回退版本。清理只针对可重建派生依据，不能删除原始日志、余额、账务事实或唯一约束。旧版会恢复原来的调度／读取特性，回退后须复核任务及资源预算。生产前仍需目标硬件混合流量、真实数据对账及发布指纹确认。

现有已 ready 的月中账单不会被普通查询偷偷重建；需要明确重算才应用新的前缀余额能力。旧结果标为 incomplete 的事实不冒充新验收。
