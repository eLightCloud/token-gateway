## 问题与目标

用户已授权两仓开发、测试和联调。本轮完成工作树实现及隔离合成环境验证；未执行生产充值、生产开户／代购、生产迁移或部署。下表保留开工基线，当前结果见本轮证据，不用历史计数替代本次验证。

### 必要数据与存量处理

- 操作存储复用现有幂等规范或在专用模块补最小购买意图／回执，与原生财务事务关联；不能把 Vantage 人员和租户角色写成 Gateway 另一套身份模型。
- 对存量每个受管账户盘点有效套餐、Key 策略、已有额度操作、赠送／充值／消费事实及汇率覆盖。新默认只应用首建；不得重置历史消费，或把已明确限制的员工自动放开。
- 多有效套餐存量不能自动退款、删除或转换成新套餐。切换前形成受影响清单和人工处理步骤；解决后才开放该账户 v2 代购。
- 对原默认零且无法判断是否被管理员明确设置的 Key，保留并列入迁移清单，不能猜测为未配置。清单由 Vantage 关联人员并由业务 owner 确认执行范围。
- 旧历史金额只有可验证汇率／原始凭据时才显式回填，无法还原则保留未提供；必须区分旧数据与新写入缺快照，后者是功能缺陷。
- 升级／回退保留新订单、原生余额、操作回执与金额快照。暂停代购及调额写入口、核对未知操作后回退兼容消费者，不回滚已提交的资金事实。

### 本轮实现与验证

本轮实现（2026-10-28）：

- 提供方 OpenAPI 为 `pkg/vantagequota/model-service-2.openapi.json`，Go 类型由 `scripts/generate_vantage_model_service.py` 生成；生产 `/api/integrations/vantage/v2/model-service-contract` 发布原文。路径／参数、Idempotency-Key、账户归属、币种、有限／无限、金额缺失及安全成功投影由该 owner schema 定义。v1 累计 USD 语义保持独立。
- v2 补资金、汇率、套餐报价／权益／购买记录、个人钱包代购、企业 Key 剩余／无限、消费／退款、充值／赠送／调额及操作查询。集成仍经专用 Bearer、来源 IPv4 白名单和无缓存边界，未开放用户自助支付。
- 管理员代购与普通原生钱包购买共用 `purchaseSubscriptionWithBalanceTx`；钱包、权益、原生订单和集成回执同一数据库事务，新订单保留换算快照。受管入口限制一个有效套餐，开通时使用原生 `subscription_first`，之后由原生钱包后备。报价同时约束当前套餐配置与换算设置。
- `VantageServiceOperation` 只保存接口幂等回执及换算依据，非第二资金账本；同 ID 同输入回放，跨目标或不同输入冲突。员工有限设置写原生 Key 当前 RemainQuota 并保留 UsedQuota；配置 revision 继续由原生策略归属，提交后修复缓存。新 v2 创建默认无限；对既有零／有限／无限 Key 的 ensure 不重设。
- 消费的接受汇率随现有 BillingSession／任务 PrivateData 和原生可靠 journal 的日志 payload 保存；结算、日志失败恢复和异步任务退款继承原快照。一次性结算同样保存新事实快照。管理员调额、TopUp 和原生套餐订单在既有事实增加快照。旧记录无证据保持未提供；现有组织账单／原生计费定价链没有新增资金 writer。

### 续作边界修复与补测（2026-10-28）

1. 报价后套餐删除、达到原生历史购买次数上限时，同事务保留 `rejected / plan_unavailable` 回执；余额、订单及权益均不部分生效，后续汇率／支付配置改变仍恢复原拒绝。
2. 受管代购与原生订阅创建的数据库时间复用当前事务连接，避免单连接池等待。原生购买上限使用类型化错误，不复制规则或匹配中文错误字符串。
3. 专项增加并发设零、在途预扣后管理员设置剩余与最终结算／退款、到期钱包后备／原生每日重置、关联退款原汇率与重复退款保护；子进程在原子提交后立即退出，重启以同 ID 恢复原金额，只留一订单／订阅。
4. 消费方补显式原操作恢复，Gateway 沿原有保留幂等回执提供恢复依据，无新增远端重试合同或财务 writer。

### 评审修复与复验（2026-10-28）

消费者外部评审未访问本仓，其提供方判断仍需本仓证据。此次直接复核发现原 ClickHouse fixture 手工填入非零日志 ID，虽然测试通过，却未覆盖原生日志 id=0 的实际行为；此前表格不能作为该原生路径正确的证据。现已替换该夹具并修复 v2 查询。其他原生资金 writer、事务与幂等回执不另建实现。

- `model/vantage_model_service_clickhouse.go` 只读取原有日志事实，沿 billing_operation_id 或唯一旧 request 引用分页；相同明确操作重复投递只显示一次，冲突／缺引用／重复旧请求明确失败。按账户、Key、模型和半开时间范围先限域，再读取；游标限定已记录日志水位，迟到投递需刷新。
- SQL 日志元数据补查再次绑定账户及限定 Key。记录引用保持不透明，ClickHouse 对外引用使用账户和原操作引用的摘要，不改变金额、原生日志 ID 或归属。
