# 微软应用身份邮件实施方案

## 问题与目标

让系统以 Microsoft 365 应用身份无人值守发信，同时交付系统配置 UI，形成“配置 → 整体保存 → 二次验证 → 测试发信 → 错误排查”的完整操作链路。

产品合同见[产品设计](../10-product/微软应用身份邮件产品设计.md)，配置、接口、秘密保护及运行行为唯一见[架构设计](../20-architecture/微软应用身份邮件架构设计.md)。本文只维护代码接线、执行顺序与验证，不复制另一套字段或状态机。后端和系统配置 UI 已实现，本地回归、构建及三库验证通过；真实租户 SMTP 认证未通过，发布验收保持未完成。

## 当前实际情况

### 改造前基线（已核对）

| 位置 | 当前实现与差距 |
| --- | --- |
| `common/email.go` | 统一 SMTP 发信、TLS 开关；认证依赖账号及 SMTPToken 均非空，无 Token 生命周期 |
| `common/email_ntlm_auth.go` | PLAIN/LOGIN/NTLM，无 XOAUTH2 |
| `model/option.go` | 原 SMTP 配置按 key 加载；存在事务批量更新，但邮件尚无独立原子快照或版本控制 |
| `controller/option.go` | 普通读取按 key 名过滤秘密；新复合配置必须显式保护 |
| `main.go`、`model/option.go` | `SyncOptions` 定时同步配置，多实例配置生效有同步窗口 |
| `router/api-router.go` | `/api/option` 为 Root 入口，可注册专题设置路由 |
| `web/src/features/system-settings/integrations/email-settings-section.tsx` | 原邮件表单逐项调用 `useUpdateOption`，一次保存可能出现多个请求和部分成功 |
| `web/src/features/system-settings/operations/section-registry.tsx` | `email` section 注册点，现有邮件页面路径应继续使用 |
| `web/src/features/system-settings/vantage-integration/` | 已有独立配置 API、密钥 configured 标志、安全验证、清除确认和设置布局组合可参考 |
| `common/email_test.go` | 已有本地 SMTP 边界、STARTTLS、隐式 TLS、认证与证书验证测试，可优先扩展 |
| `go.mod` | 已有 `golang.org/x/oauth2`，无须为首版引入 Graph SDK |

当前工作树存在与本专题无关的未提交代码和文档修改；实施时不得清理、覆盖或混入本专题。本文不把现有 SMTP 测试视作 OAuth 验证。

### 已选择目标与未验证条件

已选择：应用身份、Client Secret、国际版单租户、SMTP XOAUTH2、原 UI 原位接入、整体配置保存、只写凭据、Root 敏感证明。

改造前待验证条件：目标租户 SMTP AUTH、应用与邮箱权限、真实投递、部署密钥、数据库版本及多实例同步。实际已完成项和仍未关闭的外部门禁见文末验证记录。

## 优化方案

### P0：接口、安全与 UI 合同落地准备

- 再核对产品与架构合同，记录新增字段、错误码、测试阶段及兼容读取条件；API DTO 只表达一个权威合同。
- 实施前读取适用 OWASP Authentication、Session Management、OAuth2、CSRF 指南及 ASVS 5.0.0；在实际变更说明记录具体适用 requirement ID、验证命令与未决缺口，不凭记忆写编号。
- 核对 existing 敏感操作上下文的规范化、证明消费、Root、Origin 与限流入口；新增邮件 scope 的全部分支必须纳入权限判断，不能只登记名称。
- 确认部署提供 `EMAIL_DELIVERY_STORAGE_KEY`；准备隔离的三库与真实租户，不在文档、命令历史或日志粘贴秘密。
- 完成门槛：实现者能够按架构合同写出严格请求／脱敏响应 DTO 和前端类型；不允许直接把原逐 key 保存扩展为更多字段。

### P1：配置、持久化与安全 API

主要实现放在新增 `model/email_delivery_config.go`、`service/email_delivery_settings.go`、`controller/email_delivery_settings.go`、`router/email_delivery_settings.go` 及必要的专题 DTO 文件。

- 实现单行配置、版本冲突、密钥保留／轮换／清除及部署密钥加密。使用现有 options TEXT，不新增方言专有列、SQL 或 GORM 依赖。
- 新增 common 的独立配置结构及快照发布能力，避免 common 反向依赖 service/model。
- 接入配置加载与多实例整组刷新；专用新行存在后不再回退旧 SMTP options。
- 在 `GetOptions` 排除敏感复合键，在模型配置验证层封堵通用单项和批量入口；专用更新有独立事务，不通过可被绕过的公共逐 key 更新。
- 注册三条邮件配置／测试路由，接入两个新敏感操作 scope、Root、Origin、请求体限制及测试限流。测试 API 的实际 SMTP 编排依赖 P2，不能留假成功实现。
- 完成门槛：非法配置、数据库失败、并发冲突均不改变旧快照；接口和审计不暴露秘密；保存行为不依赖微软网络。

### P2：Token、XOAUTH2 与发送入口

主要实现放在新增 `common/email_delivery_config.go`、`common/email_oauth2.go`、`common/email_xoauth2_auth.go`，仅在 `common/email.go` 接入配置捕获和认证选择。参数化现有传输辅助函数时控制在读取配置快照所必需的范围，不重构业务邮件调用方。

- 复用现有 OAuth2 依赖，实现固定 Tenant Token Endpoint、Scope、有效期余量、并发刷新与配置版本隔离；核查默认 HTTP 客户端、重定向和错误文本，不能直接依赖其默认安全性。
- 实现 `smtp.Auth` XOAUTH2 回调，检查库的 Base64 编码边界和服务端错误挑战处理。
- Microsoft 分支不依赖旧 `SMTPToken` 非空；运行时强制安全传输，拒绝降级。
- 统一入口一次捕获配置；保留旧认证选择和免认证中继能力，旧配置只在尚未创建新配置时作兼容来源。
- 实现有界 SMTP／Token 超时和分阶段错误；认证阶段最多一次重取 Token，禁止 DATA 后自动重发。
- 完成门槛：本地 Token 服务边界和 SMTP 边界验证成功、失败与缓存更新；现有邮件测试通过；未修改业务验证码／恢复／通知合同。

### P3：系统配置 UI（必交付）

在 `web/src/features/system-settings/email-delivery/` 新增专题 `settings-section.tsx`、`api.ts`、`schema.ts` 和 `types.ts` 等必要文件；原 operations section 只调整组件接线和移除已不使用的 defaultValues 传递。不再扩张旧邮件表单，也不保留两个同时可编辑的邮件配置页；旧文件若无引用应按真实引用关系删除或保留有说明的兼容入口，禁止死代码。

组件复用清单与已核对调用案例：

| 能力 | 现有候选与使用方式 |
| --- | --- |
| 设置页结构与保存区 | `SettingsSection`、`SettingsForm`、`SettingsPageFormActions`；沿用旧 email 和 Vantage section 布局 |
| 应用密钥输入 | `PasswordInput`；复用显隐、禁用能力。实施时核对其现有硬编码显隐按钮无障碍标签，以最小兼容扩展支持 i18n，不能自建另一套 |
| 密钥清除确认 | `ConfirmDialog`；已在 Vantage settings 使用，不能手写 AlertDialog 替代 |
| 敏感验证 | `useSecureVerification`、`SecureVerificationDialog`；取消时无副作用，提交前冻结待验证操作 |
| 加载与错误 | `LoadingState`、`ErrorState`、既有字段错误及 `handleServerError` |
| 基础表单 | 现有 Form、Input、RadioGroup／Select、Alert 与 Button；按项目 Base UI 组合方式使用 |

现有旧邮件表单缺少按模式字段、专用整体 API、configured 标志和测试结果，是新增专题业务组合的具体能力缺口；并不构成新建通用表单／对话框／密码组件的理由。

- 实现模式切换草稿、条件字段、部署能力说明、密钥三动作及应用变更校验，schema 与后端一致。
- 保存只发一次 PUT，绑定已读取 revision；409 保留草稿并提示重新读取比对，不自动覆盖其他操作者的新配置。
- 使用安全证明并绑定同一提交意图；配置在证明后变化则重新验证，不能拿旧证明提交新草稿。
- 测试按钮仅使用已保存版本，填写一个收件邮箱，显示真实副作用。界面未保存、请求进行中或权限不足时不可操作，并有可访问说明。
- 实现架构规定的测试结果、时间与版本；保存失败不清空输入，成功后清除秘密临时对象；禁止秘密进入查询／浏览器持久存储。
- 明确本地保存成功不等于微软连通；错误区包含下一步操作，异步结果可被读屏读取。检查中英文、键盘、窄屏、浅色与深色主题。
- 新增文案前读取项目 i18n skill，遵守用户优先的仅 en/zh 约束；只修改两个维护语言包，不向其他旧语言新增 key。
- 完成门槛：浏览器内完成首次配置、刷新、空白保留、轮换、清除、取消验证、切回 legacy、测试失败及成功，所有路径均经真实前端请求。

### P4：回归与真实环境验收

后端优先扩展 `common/email_test.go` 的协议用例；配置与 API 权限用例优先放入已有适合的 settings/security 测试文件。若确需新后端测试文件，本专题至多新增一个，集中配置与 API 合同，避免按层重复夹具。新增断言使用 testify require/assert。

| 范围 | 必须保护的可观察行为 |
| --- | --- |
| Token／SMTP | XOAUTH2 成功、错误 challenge、过期刷新、并发刷新、配置切换期间刷新、不支持 STARTTLS、证书不可信、Token 超时、密钥错误、权限不足及无降级 |
| 配置／API | Root 与非 Root、Origin/CSRF、证明缺失／过期／重放／意图不匹配、版本冲突、事务回滚、通用入口绕过、keep/replace/clear、解密失败及信息不泄露 |
| 测试 API | 单收件人、固定正文、限流、版本冲突、不依赖未保存值、各阶段失败、提交不确定不重发 |
| 兼容 | 旧 options 首次读取、原 SMTP 模式、免认证中继、通知邮箱选择、身份邮件仍走统一发送入口 |
| UI | 真实组件交互验证条件字段、错误定位、密钥不回显、取消验证、一次整体提交、409 保留草稿、测试结果版本失效及中英文切换 |
| 三数据库 | 新库和最新发布版代表性旧库、连续两次启动、配置首次接入、重复保存、并发冲突、失败回滚、重启解密与旧数据保留 |
| 真实 O365 | 应用授权与专用邮箱可发送、未授权邮箱被拒绝、Token 更新后仍可发、测试与一类身份业务邮件真实收件、轮换及多实例同步 |

多实例测试记录保存节点和其他节点看到的 revision、同步周期与实际收敛结果；多副本必须共享部署密钥。当前配置不走独立日志数据库，新配置持久化矩阵覆盖主库；若实施改动共享日志库路径，补对应引擎验证。

### P5：发布、回滚与收敛

1. 部署加密密钥至全部实例，备份配置与数据库，先验证新代码读取旧 SMTP 配置。
2. 租户管理员配置应用权限、Exchange 服务主体及专用邮箱，完成邮件页面配置与测试，再验证身份业务邮件。
3. 按多实例同步窗口检查各节点发信和 revision，观察已脱敏的权限／限流／超时错误；邮件提交失败不能自动切回旧 Basic。
4. 如需回退，在新版本先显式恢复经过测试的 legacy 配置并协调副本；旧二进制只理解旧 options，回滚前必须核对两者有效值，不能承诺无操作回滚。若旧通道已不可用，停发并前向修复。
5. 通过全部门禁后，再更新产品、架构的实现状态。按仓库文档维护约定，实施记录收敛／归档前先展示清单并取得相应授权；当前不归档任何文件。
