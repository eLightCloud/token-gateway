# 组织、模型折扣与邮件手动回归测试用例

## 问题与目标

为当前候选版本提供可以逐项执行、留证和复测的手动回归清单，覆盖组织管理、组织用量与 Invoice、用户及组织实时模型折扣、旧组织渠道折扣、邮件配置、业务邮件、每日摘要和运维告警。

**本文所有用例初始状态均为“未执行”。** 编写依据是当前工作树的代码及专题文档，不代表本轮已经完成浏览器验收、真实邮件投递、三数据库验证或生产发布。文中预期是验收标准；实际不符合时登记缺陷，不以当前实现替代预期。

### 三种配置必须分开验证

| 配置 | 合法值 | 作用与权限 |
|---|---|---|
| 用户／组织实时模型倍率 | `0 < ratio ≤ 5`，最多两位小数；0.01、1、5 合法 | 每主体每模型一条，多渠道范围；用户规则沿既有资源权限，组织规则及历史、成员预览仅 Root |
| 旧组织渠道倍率 | `0 < ratio < 10`，最多六位小数 | 继续按旧合同参与适用计费链路；仅 Root 管理，不能随新功能自动清除 |
| Invoice 月度结算系数 | `0.0000～10.0000`，最多四位小数，默认 1 | 组织 Admin／系统管理员配置，改变 Invoice 展示结算金额，不修改个人历史扣费 |

## 优化方案

### 一、执行准备

1. 使用隔离验收环境、专用测试用户和测试邮箱。保存可恢复的数据库与配置基线；故障注入、重启、迁移、密钥错误和资源负载只在隔离实例执行。真实微软租户验收另行使用受控邮箱，不在记录中保存凭据。
2. 记录应用版本、工作树差异、前后端版本、浏览器、站点 URL、币种、quota 换算常量、时区、主库／日志库版本、Redis 状态、实例数、通知开关及 SMTP 模式。多实例共享必要配置和邮件存储密钥。
3. 建立下表测试对象，账号之间使用独立浏览器配置或隐私会话，避免串用 Cookie。记录实际 ID，文中的 A/B/C/D 均为测试别名。
4. 打开浏览器 Network 并保留请求、响应及请求 ID；涉及资金时另记录变更前后钱包、订阅、Token 额度和消费日志，等待正常结算及后台缓存刷新后比较。导出文件与邮件 `.eml` 留在仓库外的验收附件目录，脱敏后引用。
5. 先验证邮件接收端和确定性上游可观测，再执行负向用例。没有对应真实渠道、订阅、微软租户或数据库时标为“阻塞”，写明缺失条件，不能标为通过。

| 对象 | 准备内容 |
|---|---|
| R：平台 Root | 可管理组织实时规则、邮件及通知；已设置可完成敏感操作验证的认证方式 |
| S：平台普通 Admin | 有组织管理及必要用户配置权限，但不是 Root；单独记录其 Casbin 权限 |
| A：组织甲 Admin | 普通平台用户，组织角色 Admin；不能误用平台 Admin 账号替代 |
| U：组织甲 Member | 普通钱包用户、独立 API Key；用于个人覆盖与低额度边界 |
| V／W | V 为组织甲另一成员；W 为组织乙成员或组织外用户；各有独立 Key |
| Z／Q | Z 为禁用用户；Q 为待添加的启用用户 |
| P／K | P 为有有效订阅的用户；K 为代理及其客户（部署启用代理能力时准备） |
| 模型 M／N | M 在渠道 B/C/D/E 可用，N 为另一模型；各渠道可独立控制成功、失败和响应延迟 |
| 邮箱 | 用户主邮箱、用户通知邮箱、管理员收件邮箱分别可收件；另有未授权微软发件邮箱 |
| 通知样本 | 有消费、仅最终失败、仅重试后成功、仅余额风险、仅订阅临期、静默无风险、无有效邮箱、禁用账号各一组 |

**如何控制计费与渠道：** 通过测试渠道优先级／分组和受控上游制造实际渠道，且每次以日志里的实际渠道核实；不要假定预览等于真实路由。选择确定的输入、输出用量及固定配置，让无新实时倍率时的最终基础消费恰好为 `10,000 quota`，并单独记录预估基础预扣值。优先使用确定性上游，金额预期以原始 quota 为准；真实模型输出不固定时，以日志实际 usage 按原引擎计算基础费用，不能直接比较两次不同输出的账单。

主折扣组把旧组织渠道倍率、分组及其他倍率固定为 1。另建旧配置兼容组，防止改变主组基数。主组配置为：组织甲 M 的 C/D 倍率 0.80；U 的 M 的 B/C 倍率 0.90。除指定步骤外，不变更价格、用量和资金来源。

| 实际渠道 | 生效来源 | 选中实时倍率 | 基础最终消费 10,000 时的最终 quota |
|---|---|---:|---:|
| B | 用户 | 0.90 | 9,000 |
| C | 用户优先 | 0.90 | 9,000 |
| D | 组织 | 0.80 | 8,000 |
| E | 系统默认 | 1 | 10,000 |

“预扣”与“最终消费”分别核对，不能拿最终 10,000 的示例推定所有协议预扣也为 10,000。需要准确观察预扣时，令上游延迟返回，在请求受理后、结算前读取额度；对非信任账号执行，并记录原信任判定条件。

### 二、建议执行顺序与判定

- **第一轮 P0 冒烟：** ORG-01、ORG-04、ORG-08、BILL-01、BILL-07、RT-01、RT-07～RT-10、PAY-01～PAY-03、MAIL-01、MAIL-03、MAIL-09、MSG-01、OPS-01、OPS-03、OPS-07、CROSS-01。冒烟失败先排查环境和关键缺陷。
- **第二轮完整功能：** 执行下面全部适用用例，P0 为资金、权限、秘密或核心链路阻断，P1 为主要功能，P2 为显示和体验。P0/P1 未通过或阻塞均应保留为未完成项。
- **第三轮专项：** 真实租户、多实例、跨日、故障恢复、升级及数据库矩阵。没有条件时保留阻塞，不用本地模拟结果替代。
- **每条结果：** 必须记录 Pass／Fail／Blocked／N/A、执行人、时间、实际结果与证据；N/A 写明部署范围理由。修复后重跑失败用例及关联链路。

### 三、组织管理与权限

| 编号 | 优先级 | 前置／操作步骤 | 预期结果与取证 |
|---|---|---|---|
| ORG-01 | P0 | R 进入组织管理，新建组织甲；打开详情及成员列表 | 创建成功且为空组织；不自动加入创建人；记录组织 ID、成员响应 |
| ORG-02 | P1 | 分别提交空名称、纯空白及超出当前界面／接口限制的名称；再用合法中文、英文名称保存刷新 | 非法值不入库；合法名称保存一致；失败无半份更新 |
| ORG-03 | P1 | 添加 A 为 Admin、U/V 为 Member；搜索 Q、Z 及不存在用户 | 启用用户可添加；禁用／不存在用户拒绝；角色保存刷新一致 |
| ORG-04 | P0 | U 已在组织甲，再向甲重复添加、向乙添加；同时由两个管理员提交添加 | 同一用户最多一个活动成员关系；失败方不产生重复记录 |
| ORG-05 | P0 | 用 A/U/W 会话分别打开组织列表、详情、成员、账单，重放读取及修改请求并替换组织 ID／用户 ID | A 仅按本组织权限操作；U 不得管理；W 不能读甲数据；服务端拒绝越权，不能只隐藏按钮 |
| ORG-06 | P1 | A 修改组织名称、添加 Q、调整 Q 角色并移除；U 重复上述操作 | A 的本组织操作生效；U 全部被拒绝；审计可定位操作者和对象 |
| ORG-07 | P0 | 仅剩 A 为组织 Admin，尝试自退、移除和降为 Member；再增加另一 Admin 后重试自退 | 最后一个组织 Admin 不得自行退出／降级；有其他 Admin 时按合同允许自退 |
| ORG-08 | P0 | 记录 U 钱包、订阅、group、资金偏好、Key 归属及额度；加入、改角色、移除后复查 | 成员管理不改变以上个人状态；组织不生成钱包、Key 或自动消费 |
| ORG-09 | P1 | R 停用／恢复组织，刷新各角色会话，再尝试成员管理、账单查询与实时预览／调用 | 状态准确持久化；按组织状态校验反馈；不得越权或误改个人账号状态；另记录实际折扣行为与产品确认结果，不能自行推断“停用=删除规则” |
| ORG-10 | P1 | U 离开甲后再次加入，期间及重新加入后各产生一条消费 | 形成独立有效期；历史记录保留，离开期间消费不因重新加入自动纳入；多段关系不重复统计 |

| OPS-14 | P1 | 发送途中关闭日报或改为预览／移除管理员收件人，等待配置同步 | 后续发送按最新有效配置停止或跳过，无额外批量发送；已受理SMTP结果如实记录，不伪装撤回 |
| OPS-15 | P1 | 专用实例依次只提高磁盘／CPU／内存，其他两项低于阈值；持续满足窗口后再恢复 | 任一项可独立触发管理员应急；当前阈值磁盘≥90%持续30秒，CPU≥80%／内存≥70%持续2分钟；以采样时间计并记录实际延迟 |
| OPS-16 | P1 | 越界短于持续窗口、阈值附近抖动、采样失败、恢复后再次持续越界 | 不因瞬时抖动反复告警；无效样本不当正常零值；当前恢复线磁盘85%、CPU70%、内存65%，核对实际恢复判定；日报在高负载／无效采样时可暂停 |
| OPS-17 | P1 | 同一告警持续、短时间反复；分别让原告警发送成功、失败、unknown后恢复 | 合并／冷却限制重复告警；失败／unknown告警不能产生误导恢复邮件；明确已结束事件与再次发生能区分，核对恢复收件对象 |
| OPS-18 | P1 | 隔离环境准备>15分钟结算／日志补写积压、>30分钟未完成任务、持续服务失败及关键模型无可用渠道 | 当前已实现检测项告警只发管理员，含可追踪排障线索；需通过各自持续窗口；不为个人另发逐次故障／退款／充值邮件 |
| OPS-19 | P1 | 准备超过通知处理容量样本或限制查询预算，观察日报、警告与正常API调用 | 超限跳过／不完整状态可见，不无限扫库；重跑不反复全量扫描；通知不改变核心调用、路由、账务和过载拒绝阈值 |
| OPS-20 | P1 | 查看资源邮件的CPU／内存范围、磁盘路径与采样时间；停邮件服务或停应用 | 指标含实际作用范围与路径，不能冒称容器配额／全磁盘；邮件／应用不可用属于能力边界，不把“没告警”判为系统健康 |
