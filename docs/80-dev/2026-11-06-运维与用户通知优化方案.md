# 运维与用户通知优化方案

## 问题与目标

加强管理员运维与个人用户通知，复用现有系统能力，不改变调用、路由、重试、扣费、结算和退款行为。用户无需配置或订阅，即可获得简洁的每日账户摘要；管理员能够发现异常、了解影响范围并进入现有日志排查。邮件属于辅助能力；允许漏发或跳过，优先避免反复查询、重复投递和增加核心业务负担。

### 已确认范围

- 以个人账户为主，组织对账主要在线下进行，本期不建设组织技术、财务联系人分工。
- 用户账户摘要固定每天一次，不提供周期选择或用户通知设置页面。
- 用户账户摘要与管理员日报每天北京时间 06:00 后开始分批处理，统计前一自然日；不要求准点启动或固定完成时间，优先减少业务影响，允许因业务繁忙延后或暂停。
- 仅向统计日有消费、发生错误，或生成时存在余额及到期风险的用户发送；无活动、无风险的账户不发送。
- 服务故障、异步任务、充值与退款不向个人发送独立通知，相关运维异常只通知管理员。
- 用户自己的调用错误纳入每日摘要，不逐次发信；服务侧失败作为调用结果呈现，不另发个人故障及恢复通知。
- 重大紧急事件只向管理员发应急邮件，不受 06:00 日报时间限制；仅建设应用仍运行且邮件通道可用时的应用内通知，不依赖或建设外部监控。
- 资源告警阈值已确认：磁盘使用率达到 90%、CPU 使用率达到 80%、内存使用率达到 70%，任一项达到条件均应通知，不要求同时超限或已有调用失败。
- 本文件包含方案及本地实施验证记录，不代表相关能力已上线或通过生产验证；后续收敛取舍见第 10 节。

## 当前实际情况

以下事实来自当前工作树代码检查，生产配置、邮箱覆盖率和日志完整性尚未核实。

| 能力 | 当前实现与可复用部分 | 缺口或边界 |
|---|---|---|
| 用户通知 | `service/user_notify.go` 支持 Email、Webhook、Bark、Gotify；`service/notify-limit.go` 提供通知限流 | 当前按用户设置选择一种通道；未发现统一持久化投递台账、日报去重和失败补发；缺少接收地址时可能跳过并返回成功 |
| 邮件投递 | `common/email.go`、`common/email_delivery.go` 及 `controller/email_delivery_settings.go` 提供配置发送、分阶段诊断和测试接口 | 常规发送未保留完整诊断报告；邮件服务器接受不等于用户收件成功；真实目标环境可用性需要核实 |
| 账户风险 | `service/quota.go` 已有消费相关的钱包与订阅低额度提醒，支持用户阈值 | 缺少每日账户筛选、周期摘要和到期检查；风险判断需结合实际可用资金来源 |
| 使用与错误日志 | `model/log.go`、`service/relay_error.go`、`controller/log.go` 已有错误信息、模型、渠道、用户、本地及上游请求 ID 和筛选查询 | `common/init.go` 中 `ERROR_LOG_ENABLED` 默认关闭；部分业务拒绝不记录错误日志；渠道尝试错误不等于用户最终失败 |
| 详情排查 | `web/src/features/usage-logs/` 已展示请求 ID、上游请求 ID 和管理员路由决策记录 | 邮件需复用实际支持的筛选参数和权限，不能承诺仅凭现有错误记录覆盖全部失败 |
| 审计日志 | `model/audit_log.go` 独立记录操作与安全事件，具备请求关联和分级可见性，独立于使用日志清理 | 用于操作追溯，不替代调用错误数据源；本期不改认证流程或安全通知策略 |
| 调用健康 | `pkg/perf_metrics/metrics.go`、`outcome.go` 已按最终请求结果采集模型、分组成功率和延迟等指标 | 有意排除部分业务拒绝及客户端取消；不能当作全部请求成功率，也不能替代全部用户错误统计 |
| 渠道运维 | `service/channel.go`、`controller/channel-test.go`、`controller/channel_upstream_update.go` 已有测试、停用恢复及模型变更通知 | 停用恢复主要通知 root；缺少统一影响汇总、持续异常和抖动合并 |
| 后台任务 | `service/system_task*.go`、`model/system_task.go`、`controller/system_task_handlers.go` 已有调度、数据库租约、执行历史与恢复任务 | 可增加专用任务类型，但必须验证新任务不会抢占现有轮询、结算与退款资源 |
| 系统资源 | `common/system_monitor.go`、`controller/performance.go` 已有 CPU、内存、磁盘和缓存相关采集 | 采集受现有性能监控开关控制；采集失败可能返回零值，缺少时间戳与逐项有效状态；本期只覆盖应用内可检测、可发信的事件 |

调度补充事实：`service/system_task.go` 的周期任务按上次任务更新时间与间隔判断到期；不同任务类型可并行执行，但仍共享进程和数据库。可复用现有轮询判断当日是否已到 06:00 且尚未处理，无需新增精确定时器。数据库租约防止同类任务并发，资源竞争仍需单独限制。

资源补充事实：现有采集启用时约每 5 秒更新一次，CPU 使用 `cpu.Percent(0, false)`，内存使用 `mem.VirtualMemory().UsedPercent`；Unix/Windows 磁盘实现只检查缓存目录（未设置时为临时目录）所在文件系统，不代表所有业务磁盘。`middleware/performance.go` 直接使用同一性能配置判断是否拒绝请求，因此通知阈值不能写入现有过载保护配置。容器部署下指标实际作用范围需验证，不能将现有系统百分比直接标成应用进程或容器配额使用率。

## 优化方案

### 1. 三类通知

| 通知 | 接收人 | 内容与触发 |
|---|---|---|
| 每日账户摘要 | 符合条件的个人用户 | 当前钱包余额、订阅剩余额度及到期时间、统计日消费及调用次数、最终失败次数与主要原因、风险提示、查看日志入口 |
| 每日运维报告 | 管理员 | 首期汇总调用与使用错误、影响账户及模型、渠道状态数量、失败系统任务、本地资源快照和投递情况；不承诺完整覆盖所有未恢复事件与积压状态 |
| 重要异常告警 | 管理员 | 持续故障、关键模型无可用渠道、任务长期积压、结算退款异常、资源不足等及时告警，重复合并，恢复后通知 |

同一用户每日只生成一封合并摘要，不拆成余额、消费和错误邮件。不额外建设组织通知、复杂规则编辑器、逐用户通知策略或事件工单流转。

用户摘要按账户实际情况展示，未购买订阅不展示订阅栏目。错误摘要说明哪些需要用户调整请求、哪些属于服务侧失败，避免只有错误数量而没有解释。

### 2. 统计与风险口径

- 每天北京时间 06:00 后由现有调度轮询择机启动，统计区间为前一日 00:00（含）至当日 00:00（不含），明确使用 `Asia/Shanghai`，不依赖宿主机时区。
- 仅增加日期、时间下限及处理状态判断，复用现有任务执行与租约，不建设准点调度能力，也不为补偿启动延迟增加轮询频率或发送并发。
- 聚合可在发送前分批准备，06:00 后限速投递，不集中启动全量查询与发信。重启只补约定窗口内最近一期，不连发多个历史日期。
- 历史统计窗口与当前快照分开：消费、调用、错误对应统计日；余额、剩余额度和到期风险对应生成时，并标注时间。
- 消费复用既有已结算事实和金额格式，不重新计价、不将预扣作为实际消费，不从通知流程修改账务。
- 余额风险结合钱包、有效订阅、剩余额度与实际扣费来源判断，不能把钱包低余额直接解释为服务即将中断。
- 复用已有余额阈值；订阅到期预警窗口、管理员告警阈值和持续时间在试运行前固定。预计可用天数不作为首期必需内容，避免引入不可靠预测。
- 用户最终失败按请求统计；上游尝试失败、重试挽救成功分别进入管理员统计，不能按错误日志行数直接推算最终失败率。
- 使用问题（参数、上下文、额度、权限）与服务问题（上游失败、超时、断流）分开；不能只按 HTTP 状态码推断原因或流式完整成功。
- 错误应归属实际调用账户；无法可靠归属的错误只进入管理员汇总，不推测接收人。
- 补齐已识别的采集缺口，并核对异步提交、流式结束与同步请求的统计边界，避免任务状态与请求错误重复计算。
- 数据缺失、延迟或汇总失败必须标记“统计不完整”或跳过，不能报告“零错误”；不为辅助通知扩大扫描、补偿或重试能力。报告保留统计窗口及快照时间。
- 统计日按请求结束或账务事实落地的既有时间字段确定，实施时固定对应口径；不把尚未完成的长任务认定为失败。迟到日志不自动重发已发送摘要，记录数据截止时间并在管理员侧暴露缺口。
- 管理员每日运维报告展示前一日投递结果与生成时的待发送数量，不把本轮尚未完成的用户投递计为成功；本轮失败由后续检查和下一日报覆盖。

### 3. 复用方式与新增功能

1. **独立通知模块：** 新文件实现账户筛选、摘要聚合、模板和事件规则；现有文件仅增加必要采集、注册和路由接线。
2. **专用后台任务：** 复用系统任务框架，新增日报生成和异常检查任务；按自然日、通知类型与接收人确定唯一业务标识。
3. **统一投递台账：** 保存触发原因、统计日期、接收对象、模板版本、数据截止时间、发送次数和结果；状态区分待发送、服务器已接受、失败、结果未知、跳过。
4. **受控发送：** 复用邮件配置和投递实现；日报不要求用户更改已有通道设置。已有通知限流不能直接充当日报去重或可靠队列，需要单独验证兼容。
5. **自动恢复：** 已明确失败的投递有限重试；结果未知不盲目重发；多实例与重启依靠持久标识防止正常重复生成和发送，不承诺 SMTP 端到端严格恰好一次。
6. **管理入口：** 在现有系统任务及邮件设置入口增加最小必要的预览、投递结果和失败原因展示，支持管理员受控补发；不建设独立通知中心。配置限于独立总开关、管理员收件人和必要风险阈值，每天北京时间 06:00 后择机处理，不增加用户操作要求。
7. **详情复用：** 邮件通过现有日志入口定位时间、模型和请求 ID；进入页面仍校验身份与权限。管理员内部诊断不得直接出现在个人摘要中。

缺少有效收件邮箱的账户跳过，在管理员报告汇总跳过数量与原因，不强制绑邮箱或改变现有登录流程。邮箱有效性及接收地址优先级复用现有规则，生产覆盖率待核实。

### 4. 不影响现有业务的约束

- 通知失败不改变调用结果、路由、重试、渠道状态、扣费、结算或退款；管理员告警只观察和通知，不新增自动业务处置。
- 业务请求中不发邮件、不执行报表查询；新增采集不引入同步网络发送、无界队列或无界等待，采集失败可观测且不阻断业务。
- 聚合按统计窗口和批次执行，限制扫描量、并发、查询超时和发送速率；避免每位用户重复扫描全站日志。
- 按日期窗口批量聚合消费和错误，按用户分组复用同一份结果生成两类日报；风险账户单独按分页读取账户与订阅，禁止逐用户重复查全日日志或跨主库、独立日志库做应用端无界关联。
- 不新增逐请求全量镜像日志，也不全量解析历史 `other` JSON。必要采集优先复用既有最终结果入口与紧凑计数；持久化、刷新和失败可观测性必须有界，进程重启丢失的数据应标记缺口，不能用静默丢失换取“无影响”。
- 默认聚合并发 1、邮件发送并发 1，均作为试运行保守起点；邮件每分钟上限、批次大小和查询时限根据供应商配额及代表性数据验证确定。待发堆积时减速或暂停，不通过增大并发追赶。
- 报表与投递设置独立资源上限，验证共享调度器、数据库与邮件通道的竞争；不能挤占轮询、结算、退款和验证码等现有邮件资源。
- 保留已有低余额即时提醒与其他现有通知行为，本期不迁移或关闭；每日摘要独立去重，暂不新增个人即时风险提醒。
- 首次启用不补发历史用户邮件；日常漏跑的补发范围及过期策略在试运行前固定，防止恢复后集中发送过期内容。
- 摘要生成时读取最新风险状态，避免继续提示已充值或已续费的问题；每日消费仍保持原统计日口径。
- 邮件与台账只保存必要信息，不保存密钥、原始请求或敏感业务内容；台账保留周期与清理上限在上线前确定。
- 摘要台账按接收人和日期保存，不按请求保存；仅为满足发送条件的账户生成投递行。管理员异常检查复用已有状态及计数，不每轮重扫全天明细、主动调用上游或重复启动渠道测试。
- 新功能可独立关闭。关闭后停止新增通知与发送，不影响现有任务和已有通知路径，也不通过删除业务数据回滚。

### 5. 用户、管理员与负载复评

评审结论：范围整体合理，新增负担客观存在；异步执行只能移出请求链路，不能消除数据库扫描、采集写入、内存、SMTP 连接和台账存储成本。必须以限额和代表性负载验证控制影响，当前不能承诺“零负担”或性能已达标。

| 角度 | 风险 | 修订后的设计要求 |
|---|---|---|
| 用户理解 | 昨日消费与当前余额混排，用户误以为两者应直接相减闭合 | 分别标注统计日和余额时间；摘要是使用概览，不充当完整对账单 |
| 用户打扰 | 长期闲置但零余额的账户每天收信 | 风险发送限于启用且具备相关使用资格的账户；无订阅、无使用记录的默认零余额不自动当成风险；具体资格需按现有账户模型核实 |
| 用户及时性 | 06:00 排队较久，风险状态可能已改变 | 在有界批次发送前复核风险；仅靠风险入选且风险已解除的账户跳过，仍有昨日消费或错误的继续发送摘要 |
| 用户消息数量 | 已有即时低余额提醒与每日摘要会同时存在 | 保留既有提醒，摘要合并风险提示；不新增第三类个人提醒。持续真实风险仍按已确认规则每日发送 |
| 管理员可行动性 | 大量单次错误和低流量模型的高失败率造成误报 | 及时告警需同时考虑最小样本数、持续时间或明确不可用状态；日报展示主要类别、影响人数及少量样例，详情链接查询 |
| 管理员排障 | 邮件失败时仍依赖邮件报告失败 | 正常时在现有管理入口查看投递状态；应急发送不能依赖数据库写入成功。进程退出、机器宕机、网络或邮件服务完全不可用不承诺发信，本期无外部监控依赖 |
| 应用负载 | 06:00 全量聚合、全量发信与现有任务竞争 | 提前分批聚合、06:00 起限速发送；独立限额、负载超预算暂停、按批次检查开关与取消 |
| 实施复杂度 | 为通知再建一套监控平台、明细数据仓库或复杂队列 | 复用现有状态与执行框架，仅增加专用任务、必要汇总和投递台账；缺少可靠数据的指标标记不完整或延后上线 |

容量评估至少记录：统计日日志量 R、收件人数 U、风险检查账户数 A、邮件限速 M（封/分钟）。日志聚合成本应主要随 R 增长，不能成为 U 次扫描 R；发信窗口至少约 U/M 分钟且实际可能更长，不能把 06:00 理解为统一送达时刻。逐请求新写入量、数据库连接池等待、调用延迟、既有任务积压和 SMTP 配额竞争均需实测。

### 6. 管理员应急邮件

#### 6.1 应通知的事件

| 事件 | 触发依据与边界 |
|---|---|
| 磁盘使用率达到 90% | 独立触发资源告警，不等待业务写入失败；附磁盘路径、使用率与可用空间 |
| CPU 使用率达到 80% | 持续达到阈值即告警，不以最终失败率异常作为前置条件 |
| 内存使用率达到 70% | 持续达到阈值即告警；明确为资源预警，不等同已发生内存耗尽 |
| 大范围调用失败 | 最终失败持续超过影响与样本门槛；排除余额、参数等使用问题，重试成功不计最终失败 |
| 关键模型不可用 | 对实际请求的模型、分组已无可用渠道且持续出现失败；不主动增加付费探测 |
| 账务异常或严重积压 | 复用已有明确异常、待结算/退款及恢复状态；自动恢复持续无效或积压超过门槛，不另建全量对账扫描 |
| 关键后台任务停滞 | 有待处理业务，但轮询或恢复任务长期未成功执行且积压增长；检测独立于被监测任务的执行路径 |
| 关键记录持续写入失败 | 消费、账务、审计等必要记录连续失败，且现有补偿无法及时恢复 |

数据库与 Redis 故障优先按上述实际影响合并成同一事件，避免同一根因重复发信；应用还能取得可靠故障信号时可尝试发送。单渠道失败但能正常承接、单次超时、普通用户使用错误及普通通知失败进入日报。其他事件门槛需结合生产基线固定；不宣称目前已有所有必要检测信号。

#### 6.2 资源规则与防抖

下表阈值由用户确认；持续时长、恢复线和冷却时间作为首期默认值已完成本地实现与规则测试，仍需在目标环境试运行。

| 指标 | 触发线（含等于） | 建议持续条件 | 建议恢复条件 |
|---|---|---|---|
| 磁盘 | ≥90% | 连续有效采样达到阈值 30 秒 | <85% 持续 5 分钟 |
| CPU | ≥80% | 连续有效采样达到阈值 2 分钟 | <70% 持续 5 分钟 |
| 内存 | ≥70% | 连续有效采样达到阈值 2 分钟 | <65% 持续 5 分钟 |

- 任一指标独立触发；不同指标同时发生时可合并到同一封节点告警，并逐项保留状态。资源线是主动预警，不再沿用“仅在已影响请求时才通知”的限制。
- CPU 和内存使用持续条件过滤瞬时峰值；磁盘通常变化较慢且接近写入风险，使用更短确认窗口。明确磁盘写入失败等既有重大事件不等待资源窗口。
- 第一次确认即发送；建议同一节点、资源事件每 60 分钟最多一次持续提醒。新指标首次触发或明确严重程度升级可追加合并通知，但仍受全局应急发送限额约束。
- 已成功或结果未知的异常邮件所对应指标达到恢复条件后，尽力发送一次恢复通知；恢复邮件完成有限尝试后结束该事件，即使失败或结果未知也不跨轮补发。其他指标仍异常时不得宣称节点全部恢复。短暂回落不重置事件和冷却期。
- 超限判断直接比较有效百分比，不先转整数；采集失败、过期样本、初始零值和 CPU 首次不稳定样本均不能判定正常或恢复，采集缺口单独可观测。
- 尽量复用现有采样并在独立轻量状态中记录采样时间与有效性，不提高全局采样频率、不做历史磁盘遍历；原采集关闭时，应急资源采集也应能够低频运行，不能为启用告警打开请求过载拒绝功能。具体接线通过独立文件和最小入口变更完成。
- 首期必须标明缓存目录所在磁盘的覆盖边界；W0 核实本地数据库、日志与缓存是否分盘。若分盘，将已知实际业务路径纳入有界采样，当前仅按绝对路径去重，同盘不同路径可能分别提示，不扫描全部挂载点；远程数据库磁盘不属于本应用可见范围。
- 多实例邮件标明实例与采样范围，按节点、指标或文件系统识别事件；同一共享磁盘的重复抑制可在数据库健康时复用共享协调，数据库故障时不为等待全局去重阻止必要发送，允许有界重复并明确该限制。

#### 6.3 应急发送与业务隔离

- 不等待日报或依赖数据库调度任务：应用内轻量检测将事件送入小容量应急通道，发送并发建议 1；摘要限流或暂停不阻止应急尝试，现有验证码等必要邮件仍保留资源。
- 提前加载并随有效配置更新缓存管理员收件人和邮件配置；避免临发邮件查询用户表、Redis 限流或等待故障中的数据库租约。没有有效配置时记录受限失败状态，不自行寻找收件人或绕过凭据校验。
- 复用当前邮件投递能力，但应急调用必须覆盖所有实际启用发送分支的连接、认证和提交超时；不能仅因当前 `SendEmail` 可调用就认定整个链路都有界。
- 去重、待发送和有限重试在内存有界执行；台账写入只作尽力记录，失败不阻止发信，也不无限缓存待落库记录。持续故障的提醒冷却与单次投递重试分开，结果未知不盲目重发。
- 节点资源告警不依赖仅 master 运行的系统任务框架；各实例轻量检测自身可见资源。跨实例聚合优先复用现有汇总，不因本期另建协调系统。
- 资源达到告警线时暂停新的摘要重查询和批量发送，已有批次在安全边界退出；恢复稳定后再低速继续。只约束新增通知工作，不自动清盘、重启、停渠道或修改业务过载保护。
- 邮件包含事件、节点、首次与最近发生时间、实际指标/阈值、持续时间、影响及排查入口；不附原始请求或秘密。监测循环不等待 SMTP，队列满时合并同类事件并记录缺口，不能无界扩容。
- 只承诺应用仍运行、资源尚可执行检测与发送、网络及邮件认证/服务可用时尽力发送。进程退出、机器宕机、网络隔离、邮件通道不可用或内存耗尽到无法执行时均不保证送达；本期不建设或依赖外部监控。

| 阶段 | 工作与完成门槛 |
|---|---|
| W0 基线核实 | 核实生产错误日志开关、数据留存与延迟、实际扣费来源、有效邮箱覆盖、管理员收件人、现有任务容量和邮件可用性；记录 R/U/A、发送配额及既有负载，核对节点/容器指标范围与业务磁盘路径，固定防抖、风险资格、补发及保留策略 |

| W2 可靠投递 | 完成专用任务、持久去重、投递台账、限流、重试和开关；验证并发、重启、断点恢复、邮箱缺失、结果未知及邮件故障 |
| W3 管理员试运行 | 每日保持预览，仅启用管理员应急邮件；检查日报预览、资源规则、投递超时与负载。不新增管理员日报单独发送开关 |
| W4 启用每日发送 | 预览核对与容量确认后再关闭预览；现有开关同时适用于用户摘要与管理员日报，不宣称支持个人用户白名单或小范围灰度。无法接受该范围时继续预览 |

验收必须证明：

- 摘要与现有明细可核对；不串户、不泄露管理员信息，静默账户不会误收摘要。
- 低余额但订阅仍可用、充值后恢复、续费后恢复等场景提示准确。
- 重试成功不被算为用户失败；流式失败不因 HTTP 200 被漏算；数据缺失不伪装成零错误。
- 多实例、重启、超时、重试与管理员补发遵循去重规则，未知投递结果不会自动刷屏。
- 宿主机时区变化、06:00 前后重启、执行跨日和多实例竞争不改变已绑定的北京时间统计日期；06:00 前不发送该期日报，之后允许延后、暂停及按批次恢复，不设准点启动或固定完成期限。
- 聚合、采集或邮件故障下，现有调用与账务结果不变；生产代表性数据量下，延迟、数据库负载与既有任务积压符合预先约定的预算。
- 用显式采样序列验证磁盘 90%、CPU 80%、内存 70% 的等于边界、独立触发、防抖、冷却和逐项恢复；无效/过期采样不误报恢复。使用可注入时钟，不用真实长时间等待或随机压力替代规则测试。
- 应急发送在主库、Redis 或日报任务不可用时仍能使用已加载配置尝试；邮件超时、队列满、持续高负载和资源采集关闭时新增工作保持有界，资源告警线不改变现有过载拒绝阈值。
- 新增存储、迁移或查询需完成真实 SQLite、MySQL、PostgreSQL 验证；迁移覆盖新库、已发布版本代表性旧库及重复启动；涉及日志路径时同时覆盖独立日志库及受影响的 ClickHouse 路径。记录实际版本、命令与结果后再宣称兼容。
