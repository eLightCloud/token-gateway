# 使用日志高并发读写与本月统计优化方案

## 问题与目标

客户频繁刷新使用日志，主要为了确认刚才的请求是否已经记录、用了多少 token、扣了多少额度。本月消费和本月明细是第二个主要场景，更早的明细通常只在排查或对账时查询。日志持续写入，页面查询必须给鉴权、结算和日志持久化留出数据库资源。

### 已确认约束

- 线上原始日志全部保留。禁止删除、归档迁出和按保留期自动清理。磁盘容量治理另行处理。
- 持续写入优先。首期沿用逐笔日志、计费和结算投递链路，优先减少重复读取与聚合工作。
- 优先优化最新明细、实时 RPM/TPM 与本月消费；历史查询和导出仍可用，使用独立查询预算。
- 保持现有接口和权限兼容。游标分页及拆分后的统计使用新增接口，保留原有 `p`、`page_size`、`total` 契约。

### 评审后收敛的交付范围

- 第一批交付关系型日志库的个人最新页、按请求 ID 定位及游标分页。「本月」明细复用分页能力，可独立于本月消费卡片上线。管理员游标按实际索引和查询计划灰度。
- ClickHouse 继续使用现有列表和分页合同。新页面按日志存储能力启用游标。为 ClickHouse 提供新游标时，再单独验证能覆盖存量的稳定记录标识及写入成本。
- RPM/TPM 与本月卡片分别灰度，共用统计状态合同。整月原表聚合不随页面刷新自动执行。
- 生产禁删与新旧读入口的总执行预算先于流量切换验证。完整月汇总先在目标 PostgreSQL 环境验证回填、增量与迟到修正；未满足覆盖门槛时维持待汇总或明确标注部分数据的影子结果。

### 建议的页面形态

| 用户任务 | 页面行为 | 查询路径 |
|---|---|---|
| 确认刚才的调用 | 默认打开「最新」，刷新只更新最新一页；支持通过请求 ID 定位 | 原始日志库的有界明细查询 |
| 连续翻页、查看详情 | 保留上一页、下一页、回到最新和每页条数；查看旧页或详情时保留位置 | 固定筛选范围，按游标顺序读取 |
| 查看当前流量 | RPM/TPM 标注最近 60 秒及统计截至时间，独立于列表刷新 | 有界聚合与短时共享结果 |
| 查看本月用量 | 卡片显示本月消费及数据截至时间；「本月」明细仍可逐页查阅 | 后台日汇总与原始日志明细 |
| 排查旧记录或核对某天、某模型 | 通过日期范围、请求 ID 等条件定位；「统计所选范围」、精确总数和导出由用户主动发起 | 独立限并发的历史查询 |

## 当前实际情况

### 线上记录与容量换算

以下生产数据来自 2026-11-21 的用户记录。本次分析未连接生产环境。慢查询的实际执行计划、读块和等待事件待取得。

| 项目 | 记录 |
|---|---|
| 环境 | `os-mtr-postgres`，PostgreSQL 18.4，数据库 `app`，容器 1 核 CPU / 2 GB 内存 |
| 日志规模 | `logs` 共 18,988,516 行，最近 24 小时新增 141,740 条消费记录 |
| 慢查询 | 最近 24 小时 `type=2` 的计数与 token 聚合实测超过 60 秒 |
| 已记录索引 | `idx_created_at_type (created_at, type)`、`idx_created_at_id (id, created_at)`，实际定义与有效状态待核验 |
| 容量目标 | 3,000 RPM / 30M TPM。按每请求一条消费日志持续满载估算，约 50 条/秒、432 万条/天、30 天新增 1.296 亿条。重试、异步任务与其他日志类型会使实际写入结构有所不同。 |

表总行数本身无法解释这次慢查询。候选原因包括实际计划回表、读块放大、统计估算偏差、锁或连接等待，以及并发写入下的 CPU/I/O 竞争。30M TPM 反映 token 数值规模，明细扫描行数由实际记录条数决定。若同一统计口径连续满载 30 天，token 累计约 1.296 万亿，聚合和存储使用 64 位整数。

现有页面刷新在列表和统计都重新计算时，主路径涉及四条 `logs` 查询：`COUNT`、列表明细、区间 `SUM(quota)` 和 60 秒的计数/token 聚合。管理员渠道名补齐等查询另外计算。线上记录中的 24 小时 token 聚合与页面的额度查询口径不同，取证和验收分别执行。

### 已做的隔离验证

在本地独立 PostgreSQL 18.4 容器上，以 1 核 / 2 GB、70 万条合成记录验证 SQL 行为。`COUNT(*) LIMIT 10000` 对 630,000 条匹配记录返回 630,000；对 `LIMIT 10000` 的子查询计数才返回 10,000。测试中的时间窗口约命中 13.5 万条消费记录，基线走 `Bitmap Heap Scan`。创建覆盖索引并执行 `ANALYZE` 后仍走同类计划；实验执行 `VACUUM (ANALYZE)` 后出现 `Index Only Scan`，`Heap Fetches` 为零。该实验用于证明计划和可见性相关，未复现线上的 60 秒延迟，也未测得生产写入开销。 [PostgreSQL 覆盖索引与可见性](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

## 优化方案

### 1. 最新明细与本月分页

1. 为普通使用日志添加游标模式。个人「最新」默认取配置查询范围内该用户最近 N 条已提交记录，保留按 `id DESC` 的展示顺序。使用 `(user_id, id)`，默认不附加浏览器当天或整月的业务时间过滤。显式选「本月」或自定义范围时使用选中的日期。管理员沿用 `(created_at, id)` 的降序。每页取 `limit+1` 条，返回 `items`、`has_more` 和可选 `next_cursor`，用最后一条实际返回记录生成游标。已有每页上限、查询范围和可见字段规则继续生效。
2. 后端签发游标时绑定存储能力、排序位置、认证主体及实际可见范围、筛选区间、页大小和有效期。每次请求重新鉴权后才使用游标。个人旧接口的 `id` 是展示序号；新接口从格式化之前的真实数据库键生成游标及独立的稳定记录标识。`request_id` 用于查询所有匹配记录，用户获得可见的多条关联日志时可逐条查看。前端用稳定记录标识保持详情身份、处理重复返回和缓存页面。 [展示序号](../../model/log.go#L118) · [仓库内的组织日志游标](../../model/organization_usage_logs.go#L177) · [跨数据库游标条件](../../model/organization_log_keyset.go#L13)
3. 「最新」首页主动刷新时只重查一页。连续翻页以首次查询的筛选范围和首屏排序上界为浏览锚点，后续页再按上一页末条继续；返回上一页优先复用当轮已加载结果。修改筛选或页大小、点击「回到最新」均开启新一轮。查看详情或旧页时保持位置；可用轻量的「有新日志」提示，自动刷新仅在前台最新页启用并合并重复请求。
4. 游标保证按确定顺序继续读取，顶部新插入的记录不会把已浏览的行挤进下一页。独立短查询期间，迟到提交仍可能插入锚点之内，已经翻过的区间可重新打开或按请求 ID 定位。页面说明连续浏览的边界，无需维持跨页数据库事务。关系型场景验证同秒同请求 ID 多条记录仍可逐条定位。
5. 新页面用前后翻页、日期定位、请求 ID 和可选「从最早开始」承接数字跳页用途。「统计所选范围」独立处理当前区间的消费核对，可在原接口语义允许的范围内沿用已有筛选；精确总数也只在显式请求时计算并标明截至时间。兼容期继续支持旧页码链接、请求参数和响应字段，旧入口纳入同一执行预算。
6. ClickHouse 当前使用 `(created_at, request_id)` 排序，存储 `id` 默认 0，匹配键相同的行可并存。关系型游标只在支持稳定行键的日志库启用。ClickHouse 用户继续使用原有分页，包括旧详情定位和权限行为；新游标扩展须先证明包括存量在内的排序键和行身份稳定，并实测新增键的写入成本。 [ClickHouse 表定义](../../model/main.go#L514) · [当前游标能力限制](../../model/organization_usage_logs.go#L68) · [MergeTree 排序键](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree)

每页 100 条时，旧模式跳到第 10,000 页需要跳过 999,900 条匹配记录，再承担总数查询。用户读完首屏后顶部插入 10 条，第二页使用原偏移量可能重复首屏末尾 10 条。`LIMIT` 限制返回量，筛选查询按日期、稀有模型和模糊匹配分别检查实际扫描量；长期无活跃记录、零匹配和高活跃用户都要纳入验证。超时时保留当前页并标注查询未完成。

### 2. 实时 RPM / TPM 与统计状态合同

- 保留消费日志口径。RPM 为 60 秒窗口内的 `type=2` 条数，TPM 为同一窗口的 `prompt_tokens` 与 `completion_tokens` 之和，使用统一的 `[截止时间-60秒, 截止时间)`。卡片标明「最近 60 秒已记录消费」。失败请求、未落库流式请求和一笔请求关联多条记录均会影响与网关入口流量的可比性。
- 默认实时卡片采用个人账户或管理员全站范围，明确标注范围。页面历史区间与翻页不触发该查询。复杂筛选统计由用户主动发起，并受查询预算限制。个人明细、实时指标和本月汇总均使用认证后的 `user_id`，缓存命中之前执行权限检查和有效筛选归一化，包括代理客户的渠道限制。旧统计接口按用户名的现有行为在兼容期保留；新接口验收改名后仍能覆盖改名前后的原始记录。 [个人统计入口](../../controller/log.go#L256) · [代理客户渠道限制](../../controller/reseller_visibility.go#L149)
- 传递请求上下文并设置语句预算，使用现有索引读 60 秒窗口。同口径并发合并建议先用 5–10 秒复用周期；前台轮询分散请求启动时间，后台标签页暂停。缓存键由指标、实际授权范围和有效筛选组成。缓存未命中同样执行跨节点总预算；例如 1,000 个不同用户每 10 秒刷新一次，仍可能有约 100 次/秒的独立聚合，单靠同口径合并无法吸收这类流量。
- 若短窗口聚合仍显著挤占写入，可将适度延迟的查询分流至只读副本，或由后台对已落库记录维护秒级/短桶汇总。保留精确滚动窗口时使用秒级桶或补算边缘，整分钟桶适合分钟趋势与较长范围聚合。进入该工作包前先取得生产形态压测结果。

实时与本月接口使用同一套元数据，前端按两个独立维度展示新鲜度和完整性。初始阈值在压测计划中校准。

| 字段 | 含义 |
|---|---|
| `range_start`、`range_end`、`timezone` | 要展示的业务时间区间，半开边界与自然月时区明确 |
| `as_of`、`generated_at` | `as_of` 是结果所依据的源数据截至时间，`generated_at` 是生成这份结果的时间。滚动 60 秒使用实际计算的窗口结束时间作为 `range_end`。旧缓存沿用原时间字段。 |
| `coverage`、`covered_ranges` | `coverage` 取 `complete`、`partial`、`pending`。`covered_ranges` 列出结果实际覆盖的业务时间段，月内缺口明确暴露。`complete` 表示在已证实的源水位下，覆盖了本次要求统计的时间区间，含义限于已记录消费。存在已知日志缺口时使用 `partial`，尚未生成结果时使用 `pending`。 |
| `freshness` | `fresh`、`stale`、`unavailable`。超时、回填追赶或副本落后时可返回上一版本并标记 `stale`；无可用版本或超过旧值最长展示期限时返回 `unavailable`。 |

前端同时支持「数据陈旧且覆盖部分」等组合。尚在构建和暂不可用显示状态，只有得到有效计算的零才显示为零。切月不能把上月结果用于新月卡片。缓存和合并按授权后的当前有效范围计算，不共用不同主体、范围或筛选的结果。

### 3. 本月消费与迟到修正

- 本月归属采用统一业务时区的 `[月初, 下月月初)`，进行中的月份只计算至卡片声明的业务时间上界。方案推荐与现有组织账单使用同一 `Asia/Shanghai` 月界，灰度前由产品与财务确认。卡片汇总 `type=2` 的额度、条数与输入输出 token，四项使用 64 位整数。退款及净额继续由现有账单能力处理。 [现有账期时区](../../model/organization_invoice.go#L21)
- 派生汇总维护自然日 × 用户以及全站日总计。以一次批次扫描处理该批次的所有用户，避免逐用户重复扫原始时间片。查询月累计时按主体读取该月日汇总。卡片标明覆盖全部模型和渠道，日期或模型等筛选通过「统计所选范围」单独处理。新增模型、渠道、令牌汇总维度由实际使用量和存储基数决定。
- 权威来源为已提交的 `LOG_DB.logs`。当前结算 journal 和组织用量投递记录会在确认后清理，不能提供独立的完整回放。`quota_data` 保持现有仪表盘口径。首个完整汇总试点锁定在目标 PostgreSQL 上，以同源一致性快照与逻辑解码的已提交 `logs` 变更为输入。该路径默认关闭，作为 PostgreSQL 专用适配器单独验证，首期明细和实时统计没有复制依赖。SQLite、MySQL、其他 PostgreSQL 版本和 ClickHouse 继续使用现有兼容入口，未接入可证明来源的部署不显示完整月汇总。 [结算日志确认](../../service/billing_recovery.go#L105) · [组织用量投递确认](../../model/organization_usage_stats.go#L810) · [逻辑解码与导出快照](https://www.postgresql.org/docs/18/logicaldecoding-explanation.html)

#### PostgreSQL 试点的回填、提交与恢复

| 环节 | 实施约束 |
|---|---|
| 建立基线 | 以目标日志库导出的同一快照和逻辑复制起点启动一次构建。限并发、限时扫描当月业务时间片，分片结果按本轮版本及分片键幂等提交。启动前估算快照持有时长和 WAL 保留额度。快照失效时重建候选版本，避免用新快照补写旧版本的分片。 |
| 消费增量 | 从配对的复制起点按源事务提交顺序消费。只对完整已提交事务生效，以源实例及流代际、事务结束 LSN 建立可比较的检查点。先在派生库事务中落完汇总和检查点，再向源确认；重放已提交批次时不重复加和。进度按源顺序推进，不能仅取 `MAX(id)` 或最大 `created_at`。 |
| 归属与修正 | 用日志 `created_at` 决定自然日与月份。迟到插入通过源变更定位到所属分片，已有基线的上月记录可修正上月。初次部署前的历史月份若未建立基线，仍标为未完整；启用后的新月份也需证明初始快照与持续增量覆盖其范围。发现涉及统计字段的非追加变更、流断点或来源切换时，标记受影响范围待核对，以同源快照重算后再发布。 |
| 发布与回退 | 当所声明范围需要的分片全部覆盖、增量连续追平至可证明的源水位，且同水位原始日志的条数、额度和两类 token 均对齐时，才发布完整版本。核对和发布使用可比较的源快照或明确的水位，避免拿继续增长的原表与固定版本做误判。故障时维持上一已验证版本并标注陈旧、显示部分覆盖或待汇总。浏览器请求不触发原表整月扫描。 |

从首期验证就跟踪源检查点停滞、消费积压、复制槽 WAL 保留和长快照对实例的影响。在发布前按实测速率设置槽保留预算、告警阈值及超限时的受控停用和重新建基线流程。遇到槽失效或无法证明连续性时，冻结覆盖声明并保留上一个结果。该处的 WAL 界限仅服务统计试点的写入保护。 [事务结束 LSN](https://www.postgresql.org/docs/18/protocol-logicalrep-message-formats.html) · [复制槽 WAL 保留](https://www.postgresql.org/docs/18/runtime-config-replication.html#GUC-MAX-SLOT-WAL-KEEP-SIZE)

若目标环境承受不了一致性回填或变更读取的负荷，继续提供「本月」明细。产品如果接受滞后结果，可灰度明确标注覆盖范围的按日统计。此时只有核实覆盖的日分片参与展示，状态保持 `partial`，超窗迟到通过限速对账和定向修正处理。完整发布仍需可验证的连续覆盖。后续为运维日报复用日汇总时沿用同一覆盖标准。

### 4. 写入保护和运维选项

- 首期保持逐笔日志、结算幂等、错误与审计记录，以及现有索引集合。按**实际承载查询的数据库实例**分配读执行预算，覆盖新旧日志列表和统计、导出、回填及共享同一实例的其他重统计。进入连接池前约束总并发和等待时长，SQL 接收请求取消并设置执行超时。旧 API 保留参数和返回结构，超预算走现有错误合同。并发上限应按整组节点验证，单实例连接池或各节点自己的上限只能约束各自的连接数。后台预算可参考现有跨任务重统计租约。 [旧日志路由](../../router/api-router.go#L413) · [共享重统计租约](../../model/heavy_stats_permit.go#L13)
- 超过写入告警阈值时，优先暂停回填及宽历史统计、限制导出，再限制实时聚合回源。最新明细保有独立的短查询和排队预算。为后台读取设置每批时间和扫描量目标；后台生成速度落后时对用户显示统计陈旧或部分覆盖。多节点缓存失效、旧客户端持续刷新、功能回退均执行同一套限额。
- 确认主库和 `LOG_DB` 的拓扑。压力持续时，把允许延迟的历史查询和回填放到具备独立资源的只读副本，并监控复制延迟。提交后尽快可见的最新明细优先从日志主库读取。
- 先查看真实索引定义及有效状态。仓库要求 `idx_created_at_id` 为 `(created_at, id)`，线上的记录是 `(id, created_at)`。如确认漂移且管理员排序或时间片查询确实受影响，走现有 `organization-log-index` 显式维护流程，在低峰逐步校验。避免在应用启动 `AutoMigrate` 中建大索引。 [列顺序检查](../../model/organization_invoice_index_check.go#L12) · [显式维护工具](../../cmd/organization-log-index/main.go#L20)
- 若高频统计仍需原表查询，可对 PostgreSQL 18.4 单独评估 `(type, created_at) INCLUDE (quota, prompt_tokens, completion_tokens)`。部分索引还需验证参数化查询的实际计划能匹配谓词。压测时同时记录读块、`Heap Fetches`、索引体积、WAL、插入和结算延迟。`ANALYZE` 有助于统计估算，可见性映射影响 index-only scan；持续插入下要实际检查自动清理状态与执行计划。并发建索引仍会扫描表并消耗资源，特性也受 PostgreSQL 版本限制。 [部分索引](https://www.postgresql.org/docs/18/indexes-partial.html) · [例行维护](https://www.postgresql.org/docs/18/routine-vacuuming.html) · [并发索引](https://www.postgresql.org/docs/18/sql-createindex.html)
- 消费日志同时供账单和结算恢复使用，保持 `LogConsumeEnabled` 及日志逐笔持久化策略。后续若写放大成为主瓶颈，先测各类型和来源占比，再评估可合并的非关键诊断事件。批量写入可降低往返或事务开销，不能降低保存的原始明细行数；要保持原有幂等和确认语义。分区或更换日志存储留给单独评估，需先解决现有 `billing_operation_id` 全局唯一性、跨存储读取和兼容问题。 [日志幂等键](../../model/log.go#L79) · [PostgreSQL 分区约束](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)
- 将线上禁删作为 P0 发布门槛。任务创建、领取恢复及进入删除批次前均受生产禁删策略约束。已有排队任务保留任务记录并进入明确的停止状态；上线前核验进行中的任务已经停止，以及所有可消费旧任务的节点都受保护。对适用日志存储核验有效的 TTL 和外部清理配置。页面灰度、切换旧入口或应用回滚期间，生产禁删策略需要持续生效。相关验证仅在隔离环境构造待清理记录。本次方案修订未触发任何清理、迁移或数据库变更。 [清理任务入口](../../router/api-router.go#L425) · [清理执行器](../../service/system_task.go#L320) · [ClickHouse 日志 TTL](../../model/main.go#L477)

## 验证与观测计划

1. **固定负载，再做对照。** 在同一拓扑、数据分布和写入流量下，至少跑纯写入、写入叠加多用户首页刷新和连续翻页、再叠加旧 API、宽历史查询及本月回填三组。目标 3,000 RPM / 30M TPM 包含稳定期和流式请求集中完成的突发期，另记实际 `logs` 写入速率。并发人数用生产采样确定，分别跑常态、已观测峰值和超峰降级；覆盖冷缓存、多节点同时过期、同用户重复刷新及大量不同用户。建议稳定期至少 30 分钟，并覆盖一轮回填检查点；最终时长、用户数、筛选比例和队列限制在 P0 固定。
2. **量化写入与读取门槛。** 以重复运行的纯写入基线确定鉴权、结算和日志提交 P95/P99 的允许波动。建议先用 P99 相对增幅不超过 5% 作为评审初值，同时要求无新增结算或日志丢失错误、无持续增长的日志重试积压；若基线噪声或业务能力无法支持该值，发布前重新确认阈值并记录依据。预先固定池等待、最老待重试时长、历史队列上限和复制槽的暂停阈值。记录提交到页面可见、首页/翻页延迟、统计生成及覆盖滞后、扫描行数与 CPU/I/O/WAL。实时结果的短缓存复用建议 5–10 秒、旧值最长展示建议 60 秒；本月更新建议 1–5 分钟，旧值最长展示建议 30 分钟，均需根据实测和业务容忍度确认。
3. **行为与权限回归。** 覆盖空页、恰好一页、末页、同秒且同请求 ID 多条、上下翻页、筛选/页大小变化、迟到插入、过期或跨用户游标、旧页码深链接、跨角色缓存和代理渠道权限。验证改名前后，个人明细、RPM/TPM、本月汇总按 `user_id` 得到相同主体的记录。覆盖超时保留旧明细、真正空页、真实零值、旧统计过期、切月待汇总和新旧接口取消。
4. **月汇总故障测试。** 制造 ID 先分配而后提交、跨月补写、重复投递、累计写入前后中断、检查点重放、回填时快照中断、复制断点和源切换。对照同水位的原始明细，分别核对全站及每用户的条数、额度和输入输出 token，验证小时仪表盘继续使用现有口径。追不上或无法证明覆盖时断言 UI 状态，测停用、重新建基线和追平恢复的时长与写入影响。
5. **真实数据库矩阵。** 实现影响 SQL、索引、模型或迁移时验证真实 SQLite、MySQL 和 PostgreSQL；依赖版本特性时覆盖最低支持版本。覆盖独立 `LOG_SQL_DSN`、ClickHouse 原分页兼容及不支持新能力时的页面退回。PostgreSQL 专用增量适配器在目标 18.4 及选定拓扑单独压测。新增派生表或迁移需验证新库、最新发布版本升级、至少两次启动迁移、旧数据和索引约束。记录数据库版本、命令及结果。

待补证据包括生产实际查询计划、在线刷新并发、活跃用户分布、日志种类和每请求写入数量、结算日志迟到分布、常见筛选维度、数据库拓扑，以及自然月时区和统计延迟的业务预期。PostgreSQL 增量适配、建议数值与生产降级阈值仍待实测确认。

## P0/P1 本地实施记录

- 禁删保护默认生效。`LOG_ALLOW_DELETION=true` 是允许清理的显式选择，生产部署需保持未设置或 `false`。新建清理任务、已领取任务和模型删除入口使用同一判断。受保护的 ClickHouse 初始化将有效日志 TTL 置为零并移除已有表 TTL。生产执行节点、实际 TTL 以及可绕过本程序的运维任务仍需独立核验。回滚到旧二进制时应保有独立于旧程序的线上禁删保护。

## P1 写入尾延迟复查与共享读取预算

### 排查证据

- 复跑使用相同的 1 核 / 2 GB PostgreSQL 18.4，基础数据 35 万行，每种负载约 12 秒、600 次应用日志投递。两轮仅写入 P99 分别约 37 ms、862 ms，两轮叠加 P1 首页 P99 分别约 10 ms、831 ms。四轮写入全部提交，应用池等待计数均为零。此前单次的 32% 无法稳定复现为 P1 首页导致的固定增幅。
- 慢轮中，纯写入同样出现 `WALWrite` 和 `WalSync` 等等待，慢语句分布在操作 ID 查询、组织投递/确认及日志插入。说明尾延迟在多个写入阶段同时出现。没有证据把波动唯一归因于首页查询或 WAL；数据库执行资源及持久化等待需一并纳入容量判断。 [PostgreSQL 等待事件](https://www.postgresql.org/docs/18/monitoring-stats.html)
- 加入尚无共享预算的管理统计入口，按约 20 次/秒重复请求无日期的原表统计。该轮 600 次写入只观测到 376 条提交，报错包括 `SQLSTATE 53300` 连接上限和 Docker 环境的 `53100` 共享内存不足。该试验是隔离环境中的过载复现。它证明旧查询可以拖垮写入，未证明线上发生了同样失败。应用连接池未排队也无法排除数据库已经耗尽连接；原配置的每进程连接上限大于实验库可接受的连接数。

### 已接入的预算

- 普通日志的旧管理员和个人列表、统计、导出、按令牌查看，以及新个人游标页使用同一个准入点。默认每进程最多 2 个在途读取，最多 1 个重查询。旧列表包含精确计数，归入重查询。新分页默认首页和精确请求 ID 走轻量读取，复杂筛选进入重查询。轻量、普通历史/统计、导出的读取期限分别为 2 秒、5 秒、30 秒，取消传递到数据库。过载保持旧 API 的失败响应格式。

### 业务优化顺序

1. **把调用确认和报表查询分开。** 用户刚完成请求时优先给请求 ID 和最新日志。需要进一步缩短感知时间时，按这个 ID 显示有可靠凭据的「待结算／已记账」状态，减少反复刷新整页。尚无落库证据时保留待确认状态。
2. **让页眉统计可以延迟。** RPM/TPM 显示最后成功的统计时间。本月消费只读有覆盖证明的后台汇总。后台标签页暂停刷新。统计拥塞时复用上一结果，避免缓存失效后集体回源。
3. **把早期历史查询变成显式操作。** 日期和请求 ID 定位优先。精确总数、宽范围统计和大导出可独立调度，并显示等待、超时和重试状态。报表允许延迟后，再按实际收益迁到独立副本。新索引或汇总写入先验证整体写成本。
4. **按业务事实验收写入保障。** 已接受的调用应有可恢复的结算记录，内部重放按 `billing_operation_id` 幂等，多节点重启后核对日志行数、失败数和最老积压时长。查询侧先退让。若承载结算的存储本身不可用，业务需要在发起更多有成本的上游调用前执行故障准入策略。这项策略尚待实施，隔离故障复现见下文。

### 已确认的写入保障缺口

- **结算事实提交边界。** 非流式 OpenAI Chat 处理先经 `IOCopyBytesGracefully` 发送并刷新成功响应，随后调用 `PostTextConsumeQuota`。隔离库拒绝首次 `settle:` journal 写入时，客户端已收到完整 200，最终结算和消费日志均缺失，钱包和 Token 各保留 9 个额度单位的预扣，恢复任务读不到该次结算事实。成功响应应以持久化的结算事实为前提。独立日志库此后短暂失败可以由现有恢复任务补投。流式响应需另行验证终止帧、部分响应以及已发生成本的异常处理。
- **客户请求重发的幂等边界。** 网关给每次 HTTP 请求生成新的请求 ID，内部恢复使用 `settle:<请求 ID>`。相同 `Idempotency-Key` 重发相同 Chat 请求实测产生两次上游调用、两条消费日志，钱包和 Token 各扣了 20,000 额度单位。要把客户超时重发纳入单次计费，需为同一认证主体、接口、键和请求摘要定义持久幂等合同，确定进行中和已完成请求的响应，以及同键异内容的冲突处理。原有日志读取 API 无需因此变更。

资金确认、用量日志投递和查询应继续独立验收。上线前要求成功调用可恢复、每次业务调用只扣一次，分阶段压测覆盖流式、真实载荷、带缓存的部署形态、多节点恢复与接近生产的历史规模。全链路验收因基线和上述两项正确性检查返回非零，P1 继续默认关闭。各轮仅访问合成数据，旧 API、运行时代码和线上数据库本轮均无改动。

## 结算确认与客户端重试修复

修复接入 OpenAI 兼容的 `/v1/chat/completions` 和 `/v1/completions` HTTP 路径。普通 JSON 响应在结算 journal 事务提交后才返回成功。流式输出保留增量事件，成功终止帧 `[DONE]` 等到提交后发出。已持久化结算后，单独的日志写入或完成标记失败仍由既有 `billing_recovery` 重放。可确定的 journal 写入失败阻止成功并触发既有预扣退款。提交结果不明确时保留原操作，避免同时提交结算和退款。现有日志读取 API 和 P1 默认关闭状态保持原有合同。

带 `Idempotency-Key` 的请求通过现有 Token 鉴权和限流后，按用户、Token 和接口声明一个持久操作。相同请求读取原请求 ID、状态和响应正文；并发重试收到 `409` 与 `Retry-After`；同键异请求收到 `409` 冲突。成功响应副本和结算 journal 在同一主库事务提交。重试复用已记录的失败结果；遇到重启等造成的未决操作保留 `409`，避免再次向上游发起相同操作。重放正文加密保存，Key 只保存摘要，单次响应副本上限 4 MiB。多实例和重启需使用一致的 `CRYPTO_SECRET` 或其回退 `SESSION_SECRET`。用例覆盖 Token 间隔离和禁用 Token 无法重放。授权设计参考 [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 和 [ASVS 5.0.0](https://asvs.owasp.org/)。
