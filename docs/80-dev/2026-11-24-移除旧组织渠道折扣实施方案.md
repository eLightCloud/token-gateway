# 组织旧渠道折扣与月度结算系数退役实施方案

## 问题与目标

同一次请求命中个人计价规则和旧组织「渠道折扣」时，旧折扣先进入费用基数，随后结算再次应用个人倍率。移除旧组织渠道折扣的配置入口及新请求计费链路。组织消费倍率统一由「实时模型计价」提供，按实际执行渠道选择用户规则、组织规则或系统默认 1。

## 当前实际情况

- 新实时规则本身已按用户优先互斥解析。旧渠道折扣是独立的基础费用乘数，在实时计价启用后仍被读取。
- 本地用截图的单价与 Token 用量通过 HTTP 动态计费复现了个人 2 × 旧渠道 0.5 和个人 0.2 × 旧渠道 1.5，扣费分别为 $0.000184 和 $0.000236。本地没有对应线上日志。
- 组织详情同时提供新版计价编辑器和旧渠道折扣编辑器。旧管理 API 单独提供配置、历史和渠道选项。
- 旧异步任务已持久化实际应用的渠道倍率，轮询结算和日志审计使用提交快照。

## 优化方案

1. 移除旧组织渠道折扣编辑器及管理 API。组织折扣页使用现有实时模型计价编辑器。
2. 新请求停止加载和应用旧组织渠道折扣。覆盖同步转发、重试、WebSocket、图片及异步任务的预扣和结算。实时模型计价仍按既有迁移阶段启用。
3. 保留已存储的旧配置与消费日志供核账，保留在途任务按提交快照完成结算的能力。已有旧渠道配置不自动映射到模型规则。第一阶段保持旧个人倍率的迁移合同和 Invoice 原有计算。月度结算系数由下文第二阶段退役。
4. 用留有非 1 旧快照的组织验证用户覆盖、组织继承及系统默认三种实际扣费，核对钱包、Token 额度和日志。验证旧快照损坏也不影响新请求，以及已提交任务继续按原快照结算。
5. 在 SQLite、MySQL 和 PostgreSQL 验证新请求的定价读取，运行相关网关计费回归及前端类型和构建检查，记录结果。

渠道规则与新版模型×渠道规则的适用范围不同，批量映射可能改变未约定模型的扣费。旧配置快照没有管理查询接口，核账时由运维从保留的数据库记录提取。历史双重折扣差额先按请求日志列出原扣费、预期倍率和价差，由财务决定是否单独作可审计的调账。发布、账单刷新和重下载均不自动追溯扣款或退款。

## 月度结算系数退役

方案已于 2026-11-24 确认，代码已实施并完成本地验证。目标环境的交付记录盘点、原版 CSV 归档、商业条款确认、部署和上线对账待执行。

### 目标与历史口径

- 「实时模型计价」是消费折扣唯一入口。请求按实际模型和渠道依次匹配用户、组织、系统默认 `1×`，结算结果作为账务事实。
- 保留组织「计费账单」页面和 CSV，按账期、成员和模型汇总已确认消费。在页面、接口和 CSV 使用单一「消费合计」，移除「折前合计」「结算系数」「结算后金额」及配置入口。成员归属、任务费用确认、退款和账户财务行沿用各自的账务口径。
- 发布前单独归档已对外发送的原版 CSV。退役后重新下载任意账期，使用当时实际入账的金额。曾乘月度系数的历史月份可能与原版 CSV 金额不同。钱包、Token 和历史消费日志以原结算事实为准。
- 月度规则与生成时的旧账单数据保留供审计，退出运行时计价和导出。月度按类别配置的商业条件逐项核对，有继续履行需求的条件按新版模型和渠道配置。

### 已核对的基线

- 现有本地 PostgreSQL 18.4 中，1 个组织有 37 条非 `1×` 的月度规则，其中 7 条为折扣，30 条为加价。当前版本的 15 份 `ready` 汇总中，8 份结算后金额与实际消费合计不同，8 份均已标记 `finalized`。该标记表示系统已完成汇总，原版对外发送情况须以实际交付记录为准。
- 旧系数在 Invoice 构建、发布和跨月合并中参与计算。已生成快照保存实际消费额度及旧结算结果，普通计费和日志 CSV 已读取实际消费额度。目标环境需独立盘点规则及受影响账期。

### 实施与切换顺序

1. 产品与财务按组织盘点非 `1×` 规则、受影响账期、要继续履行的条款和旧 CSV 下游。以实际交付记录识别已发送的原版 CSV，按组织、账期和交付版本独立归档并验证可恢复。运维在目标库逐份核对可复用的历史快照，校验实际消费整数额度在总计、账户、分类和模型明细中均存在且勾稽。旧版本或字段缺失的快照按留存源事实重建，证据不足的账期登记待核。
2. 移除组织端和平台管理端的月度系数编辑界面、`settlement-rules` 查询与保存路由以及系数专用重算分支。账单代码可在 `legacy` 或 `active` 使用已入账消费。对外切换前先部署第一阶段，并由产品与财务确认旧条款已结束或已用实时计价承接。新版组织规则在 `active` 后人工配置并核验用户覆盖、组织继承和实际扣费。待承接条款生效前，由运维协调受影响消费和账单交付。财务确认无需承接的条款可在 `legacy` 切换账单。
3. 统一构建、发布、快照读取、跨月合并、页面和 CSV，按现有单位换算快照的实际消费整数额度。复用字段完备的当前版本 `ready` 快照。旧系数重算和常规刷新共用构建任务类型，按汇总的旧重算负载识别遗留工作。未领取的汇总由常规刷新按源事实完整构建。已领取的旧汇总须重新获取源证据边界，并使用领取版本和租约阻止旧工作者发布。迟到日志、异步任务费用和其他源事实变更继续触发常规刷新。
4. 运维在同一窗口协调 API、前端和账单工作者，等旧工作者退出后开放新下载。窗口前验证原版归档，并验证回滚时旧读端能否读取已经由新版发布的快照。若不兼容，暂停受影响账单交付并前向修复。第一阶段回退会重新引入旧渠道折扣，须先评估实际扣费影响。实时计价已激活后的恢复按其迁移架构处理。已产生的账务记录保留。
5. 保留旧规则表、历史快照、旧重算负载列及旧渠道快照指针列。旧重算负载在任何清空操作前，原样保留到同一汇总记录的独立审计列，涵盖未对外发送的账单。该列随普通启动迁移新增。财务与运维完成新旧账期对账、归档恢复演练和留存期确认后，另行评估物理清理。

旧编辑器专用的模型发现扫描停止调度。队列中已有的模型发现任务领取后记录为退役，释放任务锁。保留历史模型集合的存储结构，移除消费日志确认和日志清理对该表的依赖。账单与用量工作者继续运行。

### 验收

- 用含非 `1×` 规则的旧 `ready` 快照校验页面和 CSV。例如系统基础费用 ¥100，个人实时倍率 `0.8×`，旧月度系数 `0.9×`。实际消费 ¥80，归档的旧结算金额可以是 ¥72，现行页面和重下载的 CSV 均应显示消费 ¥80。
- 在同一范围按整数 quota 核对分类、模型和账户用量分别与确认消费总额相等，再比较组织端、平台端与 CSV 的显示值。验收包括跨切换边界的合并账期，前段为旧版本逻辑已完成的账期，后段为退役后构建的账期。验证旧接口和旧任务发布路径均已退役。
- 覆盖已提交任务补结算、退款、迟到日志、账期成员归属及按资金来源统计的账户明细。按各资金来源核对期初余额加已确认流入减已确认扣减等于账期结束余额，当前余额按查询时点核对，退款与订阅单列。核对下载与刷新前后钱包、Token 和消费日志无变化。财务记录快照范围、源数据和差异，超出同口径舍入的差异须逐笔解释。
- 对涉及数据库行为的改动使用真实 SQLite、MySQL 和 PostgreSQL 验证。浏览器验收通过 `./start.sh` 连接现有本地 PostgreSQL，核对页面、CSV 与实际消费记录，并记录数据库版本、命令和结果。

### 复审修复

- 复用当前版本快照前验证总计、账户、分类、模型和交叉单元的整数额度，核对各层次合计。显式零额度有效。检测到不完整或不平的快照时，按读取版本标记失效，由常规队列按源事实重建。账期证据不足时沿用费用待核对提示，重建期间不开放 CSV。
- 回归覆盖快照缺字段、明细不平、合法零额度、旧发布内容归档和重试、跨切换账期以及现有日志留存路径。验证 Responses WebSocket 复用连接时忽略旧渠道配置，并用实际路由注册验证退役入口。
- 费用待核对时使用「已确认消费小计」提示，移除旧结算金额文案。部署前仍须在目标 PostgreSQL 完成数据盘点、实际交付 CSV 归档和恢复演练，并确认旧读端遇到新版快照时的处置。

旧重算原始快照可按组织和账期在 `organization_invoice_period_summaries` 核账。已领取的快照在 `legacy_rule_publication`，待领取的快照仍在 `rule_recalc_payload`。上线前同时盘点两列，核对原始字节、账期与归档索引。已交付 CSV 继续按原文件和交付版本复原。
