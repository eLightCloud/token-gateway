# 组织 Invoice 余额闭合评审与修复方案

## 问题与目标

本文件是《2026-08-24-组织Invoice全部账户与入账对账优化方案》的评审与后续修复权威说明。前一份文档保留已实施事实；本文件统一记录业务口径、评审问题、按需月度汇总方案和验收门槛。

业务目标不是建设新的中心化钱包流水，而是利用现有业务事实，使组织 Invoice 对每个账户满足：

```text
期初余额 + 全部入账 - 全部扣减 = 期末余额
```

系统不硬编码某个月份为统一首账期。每个组织的每个月份在用户第一次查看账单时检查月度汇总：不存在则按需回算并保存，已存在且版本有效则直接使用，不重复回算。中关村学院的账务起算月是 2026 年 8 月，但账户余额从更早时间结转，因此 8 月期初不能统一视为 `0`。

本次修复同时保证：

1. 零消费、未登录、只入账未消费的全部组织账户都展示和导出；
2. `$17,040` 历史管理员增加进入 8 月全部入账，其中 `renxiaom` 为 `$13,500`；
3. 不新增中心化钱包流水，但每条余额变动必须有可结构化追溯的业务事实；
4. 月度汇总是按需生成、可删除、可重建的派生数据，不是不可修正的权威余额快照；
5. Invoice 日常查询不扫描原始日志，不允许拖累核心网关业务；
6. 页面、JSON 和 CSV 共用同一财务事实和同一计算版本。

## 已确认的设计决策

### 1. 任意月份首次查询时按需回算

- 月度汇总以“组织 + 账户 + 月份 + 计算版本”唯一定位；
- 用户首次查看某月账单时，如果该月汇总不存在，则触发该月的按需回算；
- 该月汇总已存在且版本有效时直接使用，不重复查询原始事实；
- 每个组织需要一个可配置的账务起算月，并为该月每个范围账户确定起算余额，用于计算第一个月的绝对期初；
- 中关村学院的账务起算月为 `2026-08`，账户起算余额必须按 8 月之前的已识别事实回放，不得统一写为零；
- 后续月份的期初累加账务起算月以来每个月独立的净变动，不依赖不可修正的“上月期末快照”；
- 某月原始事实或口径修正时，该月及之后已发布的展示 payload 一并标记失效；后续月的净变动仍由各自月份的独立事实按需重建，错误不会被当作不可修正的上月快照继续传递。

```text
monthly_net_delta = monthly_inflow - monthly_deduction

某月期初
= 该账户起算余额 + SUM(账务起算月至上月 monthly_net_delta)

某月期末
= 某月期初 + 当月 monthly_net_delta
```

### 2. 原始事实是真相，月度汇总是缓存

不新建一套中心化钱包流水。充值订单、兑换码、管理员调额、历史已核验调额、钱包资金来源的消费与退款等现有业务表仍是原始事实。

月度汇总必须：

- 可由原始事实完全重建；
- 每个月的入账、扣减、净变动相互独立；
- 不把上月保存的 `closing_balance` 当作本月唯一输入；
- 口径变更或事实补录后，通过 `calculation_version` 或 `revision` 失效并重建；
- 汇总缺失或过期时，Invoice 不得静默回退到同步全量日志查询。

### 3. 月度汇总按需惰性生成

不实时、不定时反复更新月度汇总。只有用户查询 Invoice 时检查所需月份：

1. 查询目标月汇总，以及从组织账务起算月到目标月上月的必要汇总；
2. 已存在且版本有效的汇总直接使用；
3. 缺少哪个已结束月份，就只触发该月份的后台汇总；
4. 汇总未完成时返回“账单生成中”，不在 HTTP 请求内同步执行重查询；
5. 历史月份汇总完成后仅写入一次，除非明确失效或提高计算版本；
6. 目标月已结束且汇总不存在时，同样由后台生成并保存；
7. 目标月尚未结束时，后台以统一 `as_of` 计算一次性 Invoice 结果；已存在时直接复用并显示其 `as_of`，不随每笔充值或消费更新；如需最新结果，由明确的“刷新/重新生成”操作使旧结果失效后再计算；账期结束后首次查询必须生成覆盖正式结束时间的月度汇总，不能把未结束时的结果直接当成正式月度汇总。

同一组织、月份和计算版本只能有一个生成任务。重复请求复用已有任务，不得并发重放同一月份。

### 4. Invoice 不能影响核心网关

惰性汇总只减少执行次数，不会自动消除首次汇总的 CPU、IO 和连接池成本。因此：

- Invoice API 日常路径只读月度汇总或已生成的一次性结果；
- 原始事实聚合由后台任务执行，设置独立并发限制、超时和取消；
- 聚合任务不使用 `FOR UPDATE`，不在长事务内生成 CSV；
- 已确认当前生产 `LOG_DB` 与主库没有物理隔离；
- 当前数据量较小，第一阶段接受使用同一物理数据库的受限后台惰性汇总，不将只读副本或报表库作为本次上线前置条件；
- 同库阶段仍保留后台执行、独立并发限制、查询超时与取消，不得把重聚合放回 HTTP 同步路径；
- 只有后续出现实际性能不足时，再评估物理独立日志库、只读副本或报表库；
- 汇总生成失败或超时时明确失败，不得回退全量查询。

### 5. 中关村学院 2026 年 8 月范围已确认

- 不存在兑换码、签到/邀请奖励、钱包退款等其他正向余额来源；
- 42 个范围账户在 8 月没有发生跨组织转移；
- 充值或调额发生在用户加入组织前、但属于同一账期且后续只加入一个组织时，归属于后续加入的该组织；
- 因本期无跨组织转移，上述归属口径不会导致中关村学院 8 月事实跨组织重复。

## 代码与数据口径问题

### S1：现有“钱包净变动”名称超过实际范围

当前“钱包净变动 = 支付充值 + 管理员增加 - 管理员扣减”，未包含 AI 钱包消费、钱包购买订阅及其他扣减。修复后净变动必须是独立事实汇总的入账减扣减，或删除该字段。

### S2：按公式反推后再校验会恒为零

不得使用：

```text
total_deduction = opening + inflow - closing
reconciliation_difference = opening + inflow - total_deduction - closing
```

上述差异恒为零。修复后独立汇总入账和扣减事实：

```text
reconciliation_difference
= opening + recorded_inflow - recorded_deduction - observed_closing
```

只有开放账期或存在独立观测余额时，该差异才是有效校验。已结束账期的期末如果由事实重放得到，必须标记为 `derived`，不得输出误导性“已平衡”。

### S3：当前日志不是完整的钱包事实源

- 普通充值日志将额度写在 `content` 文本中，没有结构化保存实际入账 quota；
- 消费日志可被配置关闭；
- `IncreaseUserQuota` / `DecreaseUserQuota` 不强制产生对应业务事实；
- 通用日志和余额变更不具备普通跨库原子性；
- `billing_source` 当前在 `Other` JSON 中，不便可靠区分钱包/订阅消费，也不适合高效聚合。

不能把当前 `logs` 表整体直接宣布为权威钱包流水。应补齐现有业务事实的结构化字段和不可绕过的写入契约。

### S4：已结束账期没有独立期末观测值

本方案不保存权威月结余额快照。历史期末由组织的账务起算余额加月度事实净变动推导，语义是 `derived`。不存在独立快照时，历史期末不能与自身重放结果做有意义的差异校验。

### S5：成员和财务归属边界不完整

当前充值和调额可能按完整自然账期读取，存在离开组织后事件进入原组织、跨组织重复和历史回填预览边界不一致的风险。必须排除 `created_at >= LeftAt` 的事件，并为跨组织事件定义唯一归属。

### S6：当前消费聚合存在 N 次查询和索引缺口

当前 Invoice 按成员逐个聚合消费。日志索引缺少与组织月度汇总相匹配的组合索引。后台聚合必须改为批量或分块查询，并用 SQLite、MySQL、PostgreSQL 真实 `EXPLAIN` 结果确定索引。

### S7：`as_of` 一致性和长事务风险

开放账期的账户、充值、调额应在同一短读事务和一致性视图中读取。MySQL/PostgreSQL 显式使用能保证事务内一致视图的隔离级别，SQLite 使用普通短读事务。不在该事务中执行大量日志聚合或 CSV 生成。

### S8：充值的实际入账 quota 不能用当前汇率重算

不同支付渠道存储语义不同。不得在 Invoice 时使用当前 `QuotaPerUnit` 重算历史 USD。最低要求是在现有成功充值事实上保存实际 `credited_quota`，历史数据按支付完成时的渠道规则严格回填。

### S9：退款和订阅资金来源必须分离

- 正常退款是正 quota 的 `LogTypeRefund`，负数 `LogTypeConsume` 继续视为异常；
- AI 钱包扣减只统计 `billing_source=wallet` 的消费，排除订阅额度消费；
- 采用总额口径时，退款作为独立正向来源，钱包消费保留毛额；
- 跨期退款按实际退回钱包的发生月归属。

### S10：历史回填复核权限可被绕过

仅在 CLI 校验不足以防止其他调用方绕过。原始持久化能力应收窄为非导出实现，只暴露一个接收组织 ID 和复核人的受控业务入口，校验用户存在、启用且具有对应权限。回填预览、应用和 Invoice 必须复用同一成员/财务归属边界。

## 目标月度汇总模型

### 账户月度财务汇总

| 字段 | 含义 |
| --- | --- |
| `organization_id` | 事件的唯一组织归属 |
| `user_id` | 账户 |
| `period_month` | 自然月 |
| `payment_top_up_quota` | 成功支付实际入账 quota |
| `admin_increase_quota` | 当前与已核验历史管理员增加 |
| `other_inflow_quota` | 兑换、退款等其他已确认入账 |
| `wallet_consume_quota` | 钱包资金来源的 AI 消费 |
| `admin_decrease_quota` | 管理员扣减 |
| `other_deduction_quota` | 其他已识别钱包扣减 |
| `total_inflow_quota` | 入账来源之和 |
| `total_deduction_quota` | 扣减来源之和 |
| `net_delta_quota` | `total_inflow_quota - total_deduction_quota` |
| `source_record_count` | 本次聚合的源记录数 |
| `source_as_of` | 源事实截止点 |
| `calculation_version` | 计算口径版本 |
| `revision` | 同口径下的重建版本 |
| `status` | `building` / `ready` / `failed` / `invalidated` |
| `computed_at` | 生成时间 |

对外只读取已原子发布的 `ready` 版本。不得让 Invoice 读到同一组织月份部分账户已完成、部分未完成的中间状态。

### 账户模型月度用量汇总

Invoice 仍需按模型类别导出消费。为避免日常查询再扫描消费日志，需要按：

```text
(organization_id, user_id, period_month, model_category)
```

保存月度用量汇总，至少包含 `gross_quota`、请求数、计算版本和源截止点。财务汇总和模型用量汇总使用同一任务版本原子发布。

## Invoice 计算与状态

所有汇总和闭合先使用 `int64 quota`，最后才换算为 USD 字符串。

```text
recorded_inflow_quota
= payment_top_up_quota
+ admin_increase_quota
+ other_inflow_quota

recorded_deduction_quota
= wallet_consume_quota
+ admin_decrease_quota
+ other_deduction_quota

monthly_net_delta_quota
= recorded_inflow_quota - recorded_deduction_quota

reconciliation_difference_quota
= opening_quota
+ recorded_inflow_quota
- recorded_deduction_quota
- observed_closing_quota
```

| 状态 | 含义 |
| --- | --- |
| `generating` | 缺少所需汇总，后台正在生成 |
| `derived` | 历史期末由基线和事实汇总推导，没有独立余额观测 |
| `reconciled` | 独立观测余额与记录事实差异为零 |
| `incomplete` | 差异非零、源事实不完整或汇总异常 |

`reconciled` 只表示独立记录可闭合，不声称不存在互相抵消的漏记。如果存在负数总入账、负数总扣减、负数“其他扣减”或溢出，直接标记 `incomplete`。

| `payment_top_up_amount_usd` | 成功支付实际入账 |

| `total_inflow_amount_usd` | 已记录入账之和 |
| `ai_wallet_deduction_amount_usd` | 仅钱包资金来源的 AI 消费 |
| `admin_decrease_amount_usd` | 管理员负向调额 |
| `other_deduction_amount_usd` | 其他已记录扣减 |

## 按需生成流程

```text
用户查询组织某月 Invoice
        ↓
读取目标月和计算期初所需的 ready 汇总
        ↓
是否缺少月份或计算版本过期？
   ├─ 否 → 累加月度净变动并返回 Invoice
   └─ 是 → 获取组织+月份+版本的唯一生成权
              ├─ 已有任务 → 复用任务，返回 generating
              └─ 无任务 → 创建后台任务，返回 generating
                              ↓
                    后台批量读取原始事实
                              ↓
                    完整校验后原子发布 ready 版本
```

开放月份的一次性计算同样使用后台任务。不对正式月度汇总进行每次充值或消费后的实时更新。

## 验证方案

### 核心财务用例

| 场景 | 期初 | 入账 | 扣减 | 期末 | 预期状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| `renxiaom` | 0 | 13,500 | 3,787.491108 | 9,712.508892 | `reconciled` |
| 已入账无消费 | 0 | 1,000 | 0 | 1,000 | `reconciled` |
| 已入账后管理员扣减 | 0 | 1,000 | 200 | 800 | `reconciled` |
| 漏入账或期初错误 | 0 | 0 | 0 | 100 | `incomplete` |
| 历史无独立期末观测 | 派生 | 已记录 | 已记录 | 派生 | `derived` |

### 惰性汇总用例

- 所需历史月份都有 `ready` 汇总时，Invoice 不读取原始日志；
- 缺少一个月份时只创建该月后台任务，HTTP 返回 `generating`；
- 多个并发请求只生成一个组织+月份+版本任务；
- 任务失败、超时时不回退全量日志查询；
- 修正 8 月原始事实后，8 月及其后已发布的展示 payload 失效；各月仍按自身原始事实惰性重建，不复制上月期末快照；
- 旧 `calculation_version` 不会与新版本混用；
- 原子发布前 Invoice 读不到部分汇总。

### 账户、归属和事实用例

- 零消费、零入账账户仍出现在页面和 CSV；
- `jackson_5515` 充值后无消费，仍显示全部入账且扣减为零；
- 离开组织后的事件不进入原组织，同月跨组织事件不重复；
- 充值使用支付时实际 `credited_quota`，不受后续 `QuotaPerUnit` 变更影响；
- 订阅资金来源的消费不进入钱包扣减；
- 正常退款以 `LogTypeRefund` 入账，负数 `LogTypeConsume` 继续拒绝。

### 回填与权限用例

- 预览仍得到 `16` 笔、合计 `$17,040`；
- `renxiaom` 为 `$13,500`；
- 首次应用写入 `16` 笔，第二次写入 `0` 笔；
- 不存在、禁用或无权限的复核人被拒绝；
- 预览和应用共用正式财务成员边界。

### 性能与数据库用例

- 聚合任务不使用 `FOR UPDATE`，不在主库长事务内查询日志或生成 CSV；
- 第一阶段验证 SQLite 功能路径、超时和单并发保护；MySQL/PostgreSQL 真实查询计划在出现性能压力时再执行；
- 组织成员聚合为批量/分块查询，不按成员 N 次聚合；

### 汇总表的物理实现说明

目标模型中的“账户月度财务汇总”和“账户模型月度用量汇总”在第一阶段采用一个原子发布的二进制 JSON payload 保存，而不是拆成两组逐账户明细表。payload 内直接保存页面、JSON 和 CSV 共用的账户财务 DTO、模型用量 DTO、计算版本和截止点。

该选择是对“最小侵入 new-api 原始代码”和“不得读取部分发布结果”的实现收敛：

- 每个组织月份只有一个发布点，不存在部分账户已 ready、部分账户未 ready；
- payload 使用跨 SQLite、MySQL、PostgreSQL 的二进制大字段，避免 MySQL `TEXT` 的 64 KiB 上限；
- 日常查询只解码已 ready payload，不访问充值、调额或日志原始表；
- payload 是可删除、可按 calculation version 重建的派生缓存，不是钱包流水或权威余额快照；
- 后续只有在需要按账户直接 SQL 分析或单月 payload 体积成为实际瓶颈时，再无损拆分为明细汇总表。

## 2026-08-25 第二次 CSV 闭合诊断

### 结论

第二次导出的 `v3` 汇总截止时间为 `2026-08-25 12:49:33`。其中 8 个“当期充值为 0，但有消费和当前余额”的账户并没有漏掉 8 月充值。这些账户都在 8 月 1 日之前由管理员加过额度，8 月消费使用的是结转余额。

- “用户当期充值金额 = 0”是正确的账期口径；

### 代码根因

当前数据库没有组织 1 的 `organization_invoice_baselines` 和 `organization_invoice_account_baselines` 记录。`organizationInvoiceOpeningQuotas` 在基线不存在时直接返回空 map，后续格式化为全部零值。

所谓“首次查询回算上期数据”目前只在已经存在组织基线时才会从基线月向后生成月度汇总；基线缺失时并不会自动建立真实期初。因此这个产品链路尚未完成。

`v3` 汇总已经识别出问题：42 个账户全部为 `incomplete`。上述 8 个账户的 `reconciliation_difference_amount_usd` 分别等于其漏掉期初余额的负数。但 CSV 没有展示该状态，而是直接把不完整的期初零值当作最终结果导出。

### 产品上的最小正确修复

1. 当目标月份没有可用期初基线时，首次查账的受限后台任务应自动回放目标月份之前的已识别余额事实，生成每个账户在月初的真实余额。
2. 中关村学院已确认历史正向来源为管理员加额；回放时需同时兼容 2026-07-18 之前的旧中文审计格式和之后的结构化 `user.quota_add`。
3. 基线生成与月度汇总一样只在缺失时执行一次，以后直接使用已发布汇总；不在每次查询扫描历史日志，也不要求运维执行命令。
4. 期初基线生成并发布后，再构建 8 月汇总；已有的错误 `v3` 汇总必须通过计算版本升级自动淘汰，不要依赖人工删除或命令回填。
5. 不应把 8 月之前的加额挪到“8 月当期充值”来伪造闭合；这会破坏账期语义。CSV 四行口径无需再改，需要修正的是期初基线生成。
6. 期初基线未完成或对账仍为 `incomplete` 时，账单不得以 `ready` 状态导出会计数据；应保持生成中或明确报错，避免再把占位零值当作真实期初。
