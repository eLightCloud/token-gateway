# 输出 Token 为 0：代码业务目标、问题分析与优化方案

> 本文覆盖责任矩阵、取消传播、异步结算和渠道治理等宽范围，已被[客户侧超时 Token 对账最小方案](2026-08-08-客户侧超时Token对账最小方案.md)取代，不作为当前实施依据；仍保留作业务目标扩大时的备选设计。

本文定义 Token 核销的业务目标、现行代码问题和改造方案。线上数据、跨系统请求证据和受控测试结果见[输出 Token 为 0：日志事实分析](2026-08-07-输出Token为0日志事实分析.md)。

本文统一使用以下链路角色：

- **客户侧**：调用网关的用户应用、CLI/SDK 及其所在网络或代理链路；
- **网关**：承接客户侧请求并转发上游的 API 网关；
- **上游**：网关转发请求的上游服务。

## 问题与目标

### 业务目标

在保持 New API 正常请求语义和 API 中转基本原则的前提下，网关需要同时做到：

1. 正常完成请求继续按已有终态 usage 结算，不改变客户侧协议输出；
2. 客户侧 Context 结束后及时取消仍在执行的上游请求，避免无边界地继续生成；
3. 如果上游已经形成可关联的最终账单 Token，按责任归属决定由客户承担、网关吸收或向上游争议；
4. 不能取得流中终态或上游账单 Token 时，不把本地估算伪装成已对齐值；
5. 每个网关请求、每次上游尝试和每个 Token 分项均可追踪、可重试、可幂等核销。

本文只解决 **Token 数量及 Token 类型的核销**，不要求网关与上游的金额、单价、倍率、汇率或总成本相等。现有计费引擎仍可在 Token 确认后按网关自身价格规则结算，但金额不属于本文的跨系统对齐目标。

### Token 对齐口径

不能只对比 `prompt_tokens` 和 `completion_tokens` 两个汇总值。至少要按协议语义保留以下分项：

| 协议语义         | 需要核销的 Token 字段                                | 关系                                                                 |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| Anthropic/Claude | 未缓存输入、缓存读取、缓存创建 5m、缓存创建 1h、输出 | 输入分项可相加形成总输入；不能用一个本地 prompt 估算覆盖这些分项     |
| OpenAI/Responses | 总输入、缓存输入、总输出、推理输出                   | 缓存输入通常是总输入的子集，推理输出通常是总输出的子集，不能重复相加 |
| 其他协议         | 原始 usage + 明确的标准化字段                        | 必须记录字段是“可相加分项”还是“总量的子集”                       |

每个 Token 分项都应满足以下核销恒等式：

```text
上游账单 Token
  = 客户已确认计费
  + 网关承担
  + 上游争议
  + 待核销
  + 明确记录的口径差异
```

“两端 Token 对齐”不等于每一笔上游消耗都转嫁给客户。内部重试、网关故障等上游消耗可以由网关承担，但必须进入差异分类，不能消失在无法解释的汇总差额中。

### 客户侧问题的业务规则

客户侧 Context 结束不是免费条件，也不是立即按本地输入估算结算的充分条件。建议规则是：

> 客户侧原因结束请求时，网关及时取消上游执行；上游已经形成且能确定关联的最终账单 Token 由客户按分项承担。尚未取得流中终态或上游账单 Token 时，只有存在可恢复的账单查询来源才进入待核销；否则执行明确的估算或退款政策，且不得标为已对齐。

只有当合同明确允许且上游账单 Token 永远无法取得时，才可在核销超时后启用“估算结算”。估算值必须单独标记为 `estimated`，不能计入“已与上游对齐”的指标。

### 原始关联请求的目标结果

对于上游请求 ID `202608071431478508552328268d9d6CaRSU7ju`，现有上游展示记录为：

| 未缓存输入 | 缓存读取 | 缓存创建 5m | 输出 |
| ---------: | -------: | ----------: | ---: |
|          2 |  721,216 |       5,422 |    6 |

截图已经证明这组数据属于上游客户账单中按请求 ID 展示的 Token 分项，可作为该请求的人工核销基准。若责任最终判定为客户侧，目标结果就是按 `2 / 721,216 / 5,422 / 6` 结算，而不是继续使用网关本地估算的 `280,287 / 0`。自动结算前仍需确认截图页面背后的详情接口、记录终态和稳定性；本文不要求两端金额相同。

## 当前实际情况

### 现行正常语义可以保留

现有代码已具备“预扣费 → 取得 usage → 按实际结果结算”的主链路：

- [`controller/relay.go`](../../controller/relay.go) 在转发前估算输入并调用 `PreConsumeBilling`；
- [`service/billing_session.go`](../../service/billing_session.go) 封装单次请求的 `Settle/Refund` 幂等状态；
- [`service/text_quota.go`](../../service/text_quota.go) 将协议 usage 标准化后结算并记录消费日志；
- 正常 Claude 流在收到完整 usage 时能够保留普通输入、缓存读取、缓存创建和输出分项。

因此改造不应重写正常完成路径。新增逻辑只处理“客户侧已结束，但流中终态 usage 未被网关取得、上游事后可能形成账单 Token”的异常窗口。

### 问题 1：异常流结束仍进入普通成功结算

[`relay/channel/claude/relay-claude.go`](../../relay/channel/claude/relay-claude.go) 中，`ClaudeStreamHandler` 在扫描器返回后，只要协议处理回调没有返回显式错误，就继续调用 `HandleStreamFinalResponse`。后者在 completion 为 0 或现行 `Done` 未设置时调用 `ResponseText2Usage` 补齐缺失字段。

[`relay/claude_handler.go`](../../relay/claude_handler.go) 随后无条件调用 `PostTextConsumeQuota`。因此 0 帧 `client_gone` 虽然已经记录为异常传输结束，仍可能得到“本地估算输入 + 0 输出”的 usage，并进入普通消费日志和结算路径。

直接后果是：

- 网关消费日志看起来像一次已确定的成功结算；
- 本地 prompt 估算被误当成可与上游核销的输入 Token；
- 客户侧责任、上游账单 Token 和 Token 证据质量没有独立状态。

### 问题 2：上游请求在响应头前不感知客户侧取消

[`relay/channel/api_request.go`](../../relay/channel/api_request.go) 使用 `http.NewRequest` 创建通用上游请求，没有把客户侧请求 Context 绑定到上游 HTTP 请求。当前流扫描器能在已经取得 `resp.Body` 后因 `client_gone` 执行清理，但客户侧在上游响应头返回前结束时，`client.Do(req)` 仍可能继续等待。

线上 `RELAY_TIMEOUT=0`，而该默认值不会设置 `http.Client.Timeout`。除连接和 TLS 等 Transport 阶段超时外，等待上游响应头没有默认的全请求超时兜底。

这既浪费上游计算，也制造了一个无法可靠核销的窗口：客户侧已经离开，上游仍可能完成并计 Token，而网关没有终态 usage。

### 问题 3：Token 证据与责任归属混在一起

当前日志主要表达 `prompt_tokens/completion_tokens`、`local_count_tokens` 和 `usage_billing_path`，但没有独立表达：

- Token 是流中终态确认、上游账单确认、流中部分值、本地估算还是完全缺失；
- 请求由客户侧、网关、上游还是未知原因结束；
- Token 是待核销、已确认、网关承担还是上游争议。

[`service/billing_usage.go`](../../service/billing_usage.go) 现行常量没有 `missing`。当 usage 全零、未设置本地计数、也没有结构化 `BillingUsage` 时，日志仍可能默认写成 `usage_billing_path=upstream`。这里的 `missing` 是方案拟新增值，不是现行行为。

### 问题 4：传输结束、协议终态和输出类型未分开

[`relay/common/stream_status.go`](../../relay/common/stream_status.go) 现有结束原因完整集合为：

- `client_gone`、`timeout`、`scanner_error`、`eof`；
- `done`、`handler_stop`、`panic`、`ping_fail`；
- 未设置时的空值。

但上层没有统一消费这些状态来决定协议是否完整和是否可以最终结算。尤其是：

- Claude 的现行 `Done` 不能替代“已经收到 `message_stop`”；
- Responses 的传输 EOF 不能替代“已经收到 `response.completed/response.done`”；
- Claude 的本地输出缓冲不覆盖完整 `tool_use` 参数；
- Responses 的本地输出缓冲主要覆盖文本，不能证明 reasoning/tool 输出为 0。

因此 `eof`、`completion_tokens=0` 和“成功响应”之间不存在现行代码所暗示的一一对应关系。

### 问题 5：只有单个上游请求 ID，没有尝试树

[`relay/channel/api_request.go`](../../relay/channel/api_request.go) 从响应头取得上游请求 ID 后写入 Gin Context 的单个字符串，消费日志也只有一个 `upstream_request_id`。一个网关逻辑请求发生渠道重试时，现有数据结构无法完整表达：

- 第几次 attempt 命中了哪个渠道；
- 每次 attempt 的上游请求 ID；
- 哪次 attempt 产生了 Token；
- 哪些 Token 是网关重试成本，哪些属于客户最终请求。

如果只保存最后一个 ID，按请求核销可能漏掉前序 attempt 的上游消耗。

### 问题 6：现有 BillingSession 不能直接跨请求异步核销

[`service/billing_session.go`](../../service/billing_session.go) 的结算状态保存在进程内对象中。它适合同一请求内的预扣、结算和退款，但不能在进程重启后由后台任务恢复。

因此不能只做“`client_gone` 时跳过结算，稍后再调 `Settle`”。正确实现必须先把预扣所有权、资金来源引用、Token 证据和核销状态持久化，再允许请求处理结束；否则会产生永久预扣、重复退款或无法补扣。

现有组织账单只聚合普通消费日志。为避免临时估算日志和后续反向修正造成报表歧义，待核销期间不应先写一条伪最终消费日志；应在状态最终确定后写一次最终消费记录，过程状态进入独立核销表和审计日志。

### 问题 7：清理阶段 scanner error 只是日志噪声

[`relay/common/stream_status.go`](../../relay/common/stream_status.go) 的 `SetEndReason` 已使用 `sync.Once`，第一个结束原因一旦写入就不会被覆盖。[`relay/helper/stream_scanner.go`](../../relay/helper/stream_scanner.go) 也先写 `client_gone`，再关闭上游响应体。

因此“清理错误把 `client_gone` 覆盖成 `scanner_error`”不成立。真实残留问题是：关闭响应体后 scanner 返回的预期错误仍以 error 级别打印，人工查看原始日志时可能误判为上游主动断流。该问题只需修正日志级别和故障分类。

## 优化方案

### 总体设计

将“客户侧连接生命周期”和“Token 核销生命周期”解耦：

```text
客户请求
  -> 网关预扣并创建逻辑请求
  -> 为每次上游转发创建 attempt 和关联 ID
  -> 正常取得终态 usage：沿用同步结算
  -> 客户侧先结束：立即取消上游请求
       -> 已有终态 usage：同步最终结算
       -> 已知上游请求 ID：先只读核销；详情接口成立后可持久化 pending
            -> 取得最终账单 Token：按责任归类并幂等结算
            -> 上游明确未消耗：退款
            -> 超过核销期限仍无账单值：执行显式的 unresolved/estimated 业务政策
       -> 没有上游请求 ID：执行显式估算/退款政策，不标记为已对齐
```

不能为了等待终态 usage 而在客户侧离开后无期限继续读取或继续生成。最佳路径是立即取消上游执行，并依赖上游独立于流连接的账单详情完成后续核销。

### 1. 建立两个正交状态

#### 责任归属

| 值           | 含义                                                       |
| ------------ | ---------------------------------------------------------- |
| `customer` | 客户侧 Context/等待边界导致请求结束，且没有网关故障证据    |
| `gateway`  | 网关超时、协议处理错误、内部重试或网关基础设施导致额外消耗 |
| `upstream` | 上游明确错误、协议不完整或上游账单查询异常                 |
| `unknown`  | 现有证据不足，等待后续核对                                 |

`client_gone` 只能作为 `customer` 的重要证据，不能独自证明用户主观操作；责任规则还要排除网关先发生的超时、写错误或内部取消。首事件时间阈值只用于 SLO、告警或补偿政策，不能单独决定责任；定责必须基于请求上传、网关处理、上游等待和客户侧等待的分段证据及各自服务边界。

#### Token 证据质量

从高到低采用固定优先级：

| 值                   | 证据                                          | 是否可作为“已对齐”  |
| -------------------- | --------------------------------------------- | --------------------- |
| `stream_confirmed` | 网关收到协议终态及完整上游 usage              | 是                    |
| `upstream_billed`  | 上游最终客户账单按请求 ID 返回完整 Token 分项 | 是                    |
| `partial`          | 流中只取得部分累计 usage 或部分输出           | 否，只能作为下界/审计 |
| `estimated`        | 官方 count 接口或网关本地 tokenizer 估算      | 否                    |
| `missing`          | 没有可用 Token 证据                           | 否                    |

`upstream_billed` 对齐的是上游最终计入账单的 Token，不要求网关证明上游内部 tokenizer 的实现；但必须确认记录终态、字段语义和稳定性。本地估算字段必须写入 `estimated_*`，不得回填流中终态或上游账单字段。受控测试中 280,018 与 212,810 相差约 24%，已经证明本地估算不能承担账单核销语义。

### 2. 明确业务结算矩阵

| 责任         | Token 证据                                            | 客户 Token 处理                       | 上游 Token 差异归类          |
| ------------ | ----------------------------------------------------- | ------------------------------------- | ---------------------------- |
| 正常完成     | `stream_confirmed`                                  | 按现行同步路径结算                    | 客户已确认计费               |
| `customer` | `stream_confirmed` 或 `upstream_billed`           | 按已确认分项结算                      | 客户已确认计费               |
| `customer` | `partial/estimated/missing`，且有可恢复账单查询来源 | 保持预扣为待核销，不写最终消费日志    | 待核销                       |
| `customer` | `partial/estimated/missing`，且无可恢复账单查询来源 | 执行审批后的估算或退款政策            | 估算结算或网关承担           |
| `gateway`  | 任意已确认上游 Token                                  | 客户退款或不补扣                      | 网关承担                     |
| `upstream` | 上游已确认 Token 但请求失败                           | 客户退款；按合同向上游争议            | 上游争议或网关承担           |
| `unknown`  | 非最终证据且有可恢复账单查询来源                      | 保持待核销，等待责任和 Token 一起收口 | 待核销                       |
| `unknown`  | 非最终证据且无可恢复账单查询来源                      | 执行审批后的估算、退款或人工审核政策  | 估算结算、网关承担或人工审核 |

若待核销超过业务期限仍只有估算值，必须在下列政策中显式选定一种并写入配置，不能静默回落：

1. 退款并将上游消耗归为网关承担；
2. 按保守估算结算，但标记 `estimated`，不计入已对齐率；
3. 人工审核后结算。

默认建议是：在上游账单详情不可稳定查询前，不把尚未取得账单记录的客户侧取消请求宣称为“已精确对齐”。已经按请求 ID 取得最终账单分项的请求可以标记为 `upstream_billed`。

### 3. 定义可核销的 Token 快照

每份 usage 同时保留：

- `usage_semantic`：`anthropic/openai/gemini/...`；
- 上游原始 usage 的脱敏 JSON 或字段快照；
- 标准化 Token 分项；
- 每个字段的 `additive/subset` 关系；
- `evidence_source`、`evidence_quality`、`final`；
- 上游模型、网关请求 ID、attempt ID、上游请求 ID；
- 证据生成时间和核销版本。

Anthropic 标准化字段至少包括：

```text
input_uncached_tokens
cache_read_input_tokens
cache_creation_input_tokens_5m
cache_creation_input_tokens_1h
output_tokens
```

OpenAI/Responses 至少包括：

```text
input_tokens_total
cached_input_tokens        # input_tokens_total 的子集
output_tokens_total
reasoning_output_tokens    # output_tokens_total 的子集
```

禁止把不同语义下的缓存字段直接相加，也禁止把 Claude 的分项输入压成一个无法反解的 `prompt_tokens` 后再做跨系统比较。

#### 两个真实消费者只共享最小证据模型

受控测试已经确认 Claude Messages 与 GPT Responses 是两个真实消费者：两者都有独立的协议终态和 usage 累加逻辑，也都可能在客户侧首帧前取消后缺少终态 usage，并继续写 `type=2` 消费日志；差别是 Claude 会落本地输入估算，Responses 会落全零 Token。OpenAI Chat 兼容入口最终仍使用 Claude Messages 的 usage 和结算链路，不算第二个消费者。

因此可以在新的专用文件中定义具体的 `StreamUsageEvidence`（名称可在实现时调整），只包含结束原因、协议终态、usage 证据质量和输出类型，不承载估算、退款或核销政策。Claude 与 Responses 各自保留协议解析和累加器，只在现有 handler 增加一次构造证据的窄接入点；结算处置由 service 层的唯一判定入口完成。

这不构成引入 Provider Hook、Strategy、Registry 或账单 Adapter 的理由。两个消费者只证明它们需要相同的流证据结构和 service 层唯一结算判定，不证明“供应商账单查询”相同；后者仍要等第二个上游提供同一契约后再抽象。

### 4. 按账单获取能力分层实施核销

原关联截图已经证明上游账单 Token 存在，并且上游请求 ID 可以作为确定性关联键。原关联请求可以人工核销；其他请求还需要先取得对应账单记录。当前未确认的是截图页面背后的账单详情接口能否被程序稳定调用，而不是上游是否存在 Token 数据。

#### 4.1 立即实施已知请求 ID 的只读核销

先在新的独立模块或管理命令中实现只读核销，不接入请求热路径：

1. 读取网关日志中的 `upstream_request_id`；
2. 读取人工导出或详情接口返回的上游账单 Token；
3. 按请求 ID 确定性关联并比较未缓存输入、缓存读取、缓存创建和输出；
4. 输出已对齐、网关少记、网关多记、本地估算、上游记录缺失和无上游请求 ID；
5. 不修改余额、预扣、消费日志或历史记录。

该工具及原关联请求的复核已经具备实施条件；批量覆盖范围取决于能否取得相应的上游账单导出或详情数据。它不要求建立 pending 表、attempt 树或 worker，也不把截图数据复制成第二套账单事实。

#### 4.2 详情接口确认后启用已知请求 ID 的自动核销

只有确认截图页面实际使用的接口支持按请求 ID 精确查询、完整分项、记录终态与稳定版本后，才为已知 `upstream_request_id` 的异常请求增加持久化状态和自动结算。主体实现放在新的独立模块中，现有 New API 文件只保留必要的创建、状态提交和查询调用。

响应头前取消且没有上游请求 ID 的请求仍不能进入自动核销；必须等上游支持预置客户关联 ID 或其他确定性关联键。多 attempt 自动核销则必须先让网关保存每次真实重试的上游请求 ID。

建议至少拆成两类记录：

1. **逻辑请求核销记录**：网关请求 ID、用户/令牌引用、模型、责任、核销状态、最终 Token 快照、预扣状态引用、创建/截止/完成时间；
2. **上游 attempt 记录**：逻辑请求 ID、attempt 序号、渠道 ID、上游请求 ID、客户侧关联 ID、传输结束、协议终态、Token 证据及查询状态。

关键约束：

- attempt 记录以 `(gateway_request_id, attempt_index)` 唯一；
- 最终客户结算以 `gateway_request_id` 唯一；只有允许追加调整时才引入独立 `settlement_version`；
- 上游请求 ID 非空时建立索引，但不能假设跨上游全局唯一；
- worker 抢占优先使用 GORM `Where("status = ?", "pending").Updates(...)` 条件更新并检查 `RowsAffected`；需要多行事务锁时统一使用 `model.lockForUpdate`；
- 最终结算以业务幂等、有效一次为目标，不宣称跨主数据库、日志数据库和外部副作用的物理“恰好一次”；
- 不保存 API 密钥、原始 prompt、模型输出或工具参数；
- SQLite、MySQL 和 PostgreSQL 使用同一套 GORM 语义；
- 记录只能从低质量证据升级到高质量证据，已确认的流中终态或上游账单 Token 不被估算覆盖。

建议状态机：

```text
streaming -> confirmed -> settled
         \-> pending -> confirmed -> settled
                     \-> no_usage -> refunded
                     \-> disputed
                     \-> estimated_settled   # 仅显式业务政策允许
```

### 5. 让上游请求感知客户侧取消

通用上游请求应通过 `http.NewRequestWithContext` 或 `req.WithContext` 绑定受控 Context：

- 客户侧在响应头前结束时，立即取消 `client.Do`；
- 客户侧在响应头后结束时，流扫描器关闭响应体并停止继续生成；
- 持久化核销使用独立、短时后台 Context，不把 Gin Context 传入异步任务；
- `RELAY_TIMEOUT=0` 的默认无全请求超时语义必须在配置说明和日志中可见。

取消上游和核销 Token 不冲突：取消负责控制后续资源消耗，上游账单详情负责确认取消生效前已经计入账单的 Token。输入解析和缓存读取通常在首个输出前已经发生，取消传播不能逆转这部分 Token；对于原始关联请求，它主要用于阻止尚未发生的输出/非缓存生成并释放连接资源，不是追回已发生缓存 Token 的手段。

### 6. 确认上游账单详情查询契约

原截图已经证明 `api02.ananops.com` 存在独立于 SSE 连接的账单 Token。下一步不是证明数据存在，而是检查截图页面实际使用的详情接口，确认它能否成为自动核销的稳定数据源。已验证的 `/api/log/token` 只是最近日志接口，不能替代该检查。

每次 attempt 至少需要查询：

- 上游请求 ID，或网关在请求发出前生成且上游可回查的 `client_request_id`；
- 上游最终账单状态或等价的稳定完成标识；
- 未缓存输入、缓存读取、缓存创建和输出等完整 Token 分项；
- 模型、创建时间、完成时间、更新时间和记录版本；
- 认证方式、分页、查询频率、记录生成延迟和保留期。

本业务对齐的是上游最终账单 Token，因此不强制上游提供其内部 `actual/estimated` 算法标签。只要记录确定属于最终客户账单、字段稳定且可审计，即可标记为 `upstream_billed`；未证明属于最终账单的本地计数仍只能标记为 `estimated`。

响应头返回前就可能发生取消，所以只依赖上游响应头中的请求 ID 仍有盲区。优先与上游约定：网关在发起请求时发送稳定的客户关联 ID，上游按该 ID 查询请求级账单。

对于已经取得上游请求 ID 的请求，截图已经证明可以人工核销，详情接口确认后可以自动核销。对于响应头前取消且没有上游请求 ID 的请求，网关仍无法自动取得对应账单 Token，只能执行明确的估算/退款政策；不建议为了拿终态 usage 而在客户侧离开后继续完整生成。

### 7. 在详情接口确认后实现异步核销器

核销器只处理 `pending` attempt：

1. 按指数退避查询上游请求级账单详情；
2. 验证模型、关联 ID、Token 语义和账单终态；
3. 将上游原始分项标准化，但保留原始快照；
4. 汇总一个逻辑请求的所有 attempt；
5. 按责任矩阵分配到客户计费、网关承担、上游争议或继续待核销；
6. 通过幂等键执行一次最终结算并写一次最终消费日志；
7. 对明确无消耗或应由网关承担的请求释放预扣；
8. 超过截止时间后进入配置好的 `unresolved` 政策，不静默选择本地估算。

核销器必须配置单请求最大轮询次数、退避上限、每渠道查询 QPS 和全局 pending 上限。达到上限后进入明确的 `unresolved` 政策，不允许无限轮询或无限堆积。

现有进程内 `BillingSession` 不能直接被后台恢复。因此启用异步核销时必须新增可持久化的预扣接管/延期结算能力；在持久化记录提交成功之前，不能让请求处理函数返回 `pending`。进程在“创建 pending”和“接管预扣”之间崩溃时，也必须能够由恢复任务判定是退款还是继续核销。

### 8. 定义重试的 Token 责任

一个客户 HTTP 请求内的网关自动重试必须形成 attempt 树：

- 每个 attempt 分别记录上游请求 ID 和 Token；
- 最终成功 attempt 按正常业务规则处理；
- 因网关路由、超时或内部重试产生的额外上游 Token 默认归为网关承担；
- 客户侧自行发起的第二个 HTTP 请求是新的逻辑请求，不与前一个请求合并；
- 不允许只用最后一次 attempt 的上游请求 ID 做整笔核销。

这样即使客户账单 Token 与上游总 Token 不相等，差额也能按责任解释，而不是成为无法核对的缺口。

### 9. 修正流结束和日志语义

流扫描层输出结构化结果，覆盖现行全部结束原因和空值，并与协议层结果正交记录：

- `end_reason`、响应头/首原始字节/首 SSE/首业务输出时间；
- `protocol_terminal_seen/type/status`；
- `output_kinds`：text、thinking/reasoning、tool、none；
- `usage_evidence_source/quality/final`；
- `billing_state`：pending、settled、refunded、absorbed、disputed；
- `responsibility`；
- 逻辑请求 ID、attempt 序号和上游请求 ID。

新增 `usage_billing_path=missing`，用于“没有有效上游 usage 且没有执行本地估算”的情况。它必须明确标注为新增常量。

Claude 只有收到 `message_stop` 才表示协议完整；Responses 只有收到明确终态事件才表示协议完成。EOF 只表示传输结束。

Claude 根模块已经解析每个 `ClaudeResponse.Type`，优先在该位置记录 `message_stop`，避免仅为终态标记修改 `relaykit` 控制流。只有确需改变跨模块公开结构时才修改 `relaykit`，并执行其独立构建验证。

清理阶段预期的 `response body closed/file already closed`：

- 保留到 debug 诊断字段；
- 不作为新的 scanner 故障和上游告警；
- 不改动 `sync.Once` 已保护的第一个 `EndReason`。

### 10. 本地估算只做降级证据

正常完整响应若上游缺失 usage，可以继续保留 New API 现有的协议级降级能力，但必须：

- 标记 `estimated`；
- 记录估算覆盖了 text、thinking/reasoning、tool 参数中的哪些类型；
- 有效上游 usage 到达后只补缺失字段，不重复累计；
- 不能用 tool/reasoning 未进入文本缓冲来推断真实输出为 0；
- 不将估算值计入 Token 已对齐率。

对于 0 帧 `client_gone`，本地 prompt 估算只能保留作预扣参考和审计，不能直接成为流中终态或上游账单 Token。

### 11. 渠道能力保护作为独立可靠性措施

受控测试证明 280k 请求可以正常完成，因此不能把 100k 写成已确认硬上限。渠道保护应基于：

- 上下文长度分桶下的端到端首事件 P95/P99；
- 客户侧最短等待边界；
- 渠道成功率和协议完整率；
- 已确认的供应商能力限制。

渠道上限和 `/compact` 提示可以减少 `client_gone`，但它们不是 Token 核销机制，不能替代按请求 ID 关联的上游账单。

5. 取消只阻止后续消耗，不能把已经发生但未知的 Token 变成精确值。

#### 阶段三：按可关联范围分步核销

1. **阶段三 A，立即实施**：用网关日志和上游账单导出/详情记录做已知 `upstream_request_id` 的只读核销，不修改任何账单；

3. **阶段三 C，关联 ID 成立后实施**：覆盖响应头前取消且原先没有上游请求 ID 的请求；
4. **阶段三 D，attempt 记录成立后实施**：仅为真实发生重试的请求保存并核销完整 attempt，不为所有正常请求建立树；

1. **阶段四 A，可独立实施**：分开两种协议的传输 EOF、协议终态和输出类型，完善 tool/reasoning 的本地降级统计，协议解析和 fallback 不合并；
2. **阶段四 B，立即排查**：定位已停用渠道仍被路由命中的数据库、缓存、多实例或亲和性原因，优先修复运行配置，不新增特殊路由分支；
3. **阶段四 C，先观测**：建立端到端首事件分桶 SLO；在形成基线和独立业务决策前，不自动停用、降权或切换渠道；
4. **Provider 抽象，继续冻结**：只有第二个上游也提供相同请求级账单查询契约后，才抽象 Provider 账单查询接口。

### 服务器端和上游仍需验证的内容

上游账单数据存在性已经由截图确认。服务器端和上游后续验证聚焦于“如何稳定自动取得和关联”，而不是再次证明 Token 是否存在：

1. 检查截图页面的网络请求，确认账单详情接口、认证方式和按请求 ID 精确查询能力；
2. 确认接口返回未缓存输入、缓存读取、缓存创建 5m/1h 和输出，并明确字段之间的可加关系；
3. 确认账单记录的完成标识、更新时间、是否会被后续修订、生成延迟和保留期限；
4. 确认分页、限流和受控账号权限，保证只读核销不会依赖页面抓取或保存账号密码；
5. 响应头前取消时，验证上游能否保存请求发出前的客户关联 ID；
6. 同一逻辑请求多 attempt 的请求 ID 和账单 Token 是否都可查询；
7. 上游明确取消且无计账时，是否返回可证明的最终零值，而不是 `missing`；
8. “渠道已下线”但受控测试仍命中 105/116 的数据库、缓存、多实例和 affinity 原因；
9. 线上入口、CDN、负载均衡和出口代理的实际等待边界，以排除网关责任误判。

#### 本次决策门结论

决策门当前是“部分通过”：

- **已通过**：上游存在按请求 ID 展示的分项账单 Token；原关联请求具备人工和只读核销条件，其他已知上游请求 ID 可在取得对应账单记录后确定性关联；
- **未通过**：现有 `/api/log/token` 不支持请求 ID 精确过滤，也不保留客户侧预置关联 ID，不能直接作为自动核销详情接口；
- **待验证**：截图页面实际使用的详情接口是否返回稳定的最终账单分项；
- **仍受阻**：响应头前取消且没有上游请求 ID 的自动关联，以及多 attempt 完整核销。

因此不再把整个阶段三判定为阻塞。阶段三 A 可以立即实施；阶段三 B 只等待账单详情接口验证；阶段三 C、D 分别等待稳定关联 ID 和 attempt 记录。长期 `pending`、预扣接管和自动结算仍不能早于阶段三 B。

GPT Responses 的实测只打开 `StreamUsageEvidence` 这一最小公共抽象，不打开 Provider 账单抽象。只读核销也先为 `api02.ananops.com` 使用具体实现或导入格式，不为单个上游设计通用 Hook/Registry。

### 测试方案

现阶段新增确定性测试，保护业务结果而不是内部实现：

- 只读核销按同一 `upstream_request_id` 将原关联请求匹配为上游账单 `2 / 721,216 / 5,422 / 6` 与网关 `280,287 / 0`，且不产生余额、预扣或消费日志写入；
- 无上游请求 ID、重复上游记录、字段缺失和记录未终态时只输出明确分类，不做模糊匹配；
- 正常 Claude text、thinking、tool 和缓存命中请求的 Token 分项与现行结果一致；
- 正常 Responses 文本、reasoning 和工具请求在终态 usage 存在时不改变结果；
- 客户侧在响应头前取消，上游请求随即取消，日志只记录真实证据质量；
- 客户侧在响应头后、首业务输出前取消，不把估算或全零 usage 标为流中终态或上游账单值；
- Claude 与 Responses 对相同证据得到相同的处置类别，但协议解析和 Token 累加仍分别验证；
- `client_gone` 后的预期 body close 错误不覆盖结束原因，也不记为上游故障；
- `timeout/scanner_error/handler_stop/panic/ping_fail/eof/done/空值` 都有明确结算语义。

账单详情接口确认并启用阶段三 B 后，再增加以下测试：

- 客户侧取消后原子创建可恢复的 pending 并接管预扣；
- 上游账单详情稍后返回最终缓存/输出分项，网关只结算一次；
- worker 重试、并发领取、进程崩溃和重启后不重复结算或退款；
- 上游记录尚未达到账单终态时保持 pending；
- 上游明确最终零 Token 时退款，不与 `missing` 混淆；
- 一个逻辑请求多 attempt 时，客户计费、网关承担和上游争议分别汇总；
- attempt 唯一键与最终结算幂等键分别生效；条件更新抢占失败时不执行任何结算副作用；
- pending 轮询遵守单请求次数、退避、渠道 QPS 和全局堆积上限；
- SQLite、MySQL、PostgreSQL 下的唯一约束、条件更新和状态恢复一致；
- 异步结算复用现有 `BillingUsage`、`common.QuotaFrom*Checked`/`QuotaRoundChecked` 和 quota saturation 审计路径，不产生负扣费或裸 `int` 转换。

### 对现有报表的影响

账单详情接口确认并启用异步核销后，pending、网关承担和上游争议不是最终客户消费，不进入现有 `LogTypeConsume` 组织账单。它们通过独立核销视图向管理员展示；只有最终客户结算完成后写一次普通消费日志。阶段三 A 的只读核销只生成差异报告，不改变任何现有报表。

实施前必须验证组织账单、用量趋势、模型/渠道统计和数据导出在 pending 延迟窗口内的口径：客户消费报表允许延迟出现，但不能先写估算消费再用负数日志冲销。若产品需要展示“处理中”，优先读取核销表，不新增另一套消费日志语义。

建议验证命令：

```bash
go test ./relay/helper ./relay/channel/claude ./relay/channel/openai ./service ./controller ./model
go test -race ./relay/helper ./relay/channel/claude ./relay/channel/openai ./service
task docs:check
```

若修改 `relaykit/` 或其公开 API，还必须独立验证：

```bash
cd relaykit && GOWORK=off go build ./...
```

- 网关 absorbed
- 上游 disputed

### 验收标准

决策门已完成：

- [X] 已确认上游存在按请求 ID 展示的分项账单 Token，原关联请求具备人工和只读核销条件。
- [X] 已确认现有 `/api/log/token` 不是截图页面所需的精确账单详情接口。
- [X] 已确认 GPT Responses 是第二个真实消费者，公共抽象仅限最小 `StreamUsageEvidence`；OpenAI Chat 兼容入口不重复抽象。
- [ ] 已确认截图页面实际使用的详情接口、认证方式、账单终态、字段稳定性和保留期。

后续实现验收：

- [ ] 正常完成请求的客户侧流式协议和现行 Token 结算结果不变。
- [ ] 上游 HTTP 请求在响应头前和响应头后都能感知客户侧取消。
- [ ] 0 帧 `client_gone` 的本地 prompt 估算或全零 usage 明确标为 `estimated/missing`，不再伪装为流中终态或上游账单值。
- [ ] Claude 与 Responses 只共享纯证据模型，协议解析、累加器和 service 层唯一结算入口没有被复制。
- [ ] 只读核销可按已知上游请求 ID 输出 Token 分项差异，且对余额、预扣、消费日志和历史记录零写入。

账单详情接口确认并启用自动核销后的验收：

- [ ] 待核销记录与预扣状态能够跨进程恢复，且只结算或退款一次。
- [ ] 每个逻辑请求保存完整 attempt 树，不只保存最后一个上游请求 ID。
- [ ] 流中终态、上游账单、部分值、本地估算和缺失五种 Token 证据不会互相覆盖。
- [ ] Claude 缓存读取、缓存创建 5m/1h、未缓存输入和输出可逐项核销。
- [ ] OpenAI/Responses 的总量与子集字段不会重复相加。
- [ ] 原始关联请求可按上游最终账单核销为 `2 / 721,216 / 5,422 / 6` 分项，而不是 `280,287 / 0`。
- [ ] 客户侧责任请求按已确认上游账单 Token 结算；网关责任的上游 Token 进入网关承担。
- [ ] `estimated` 和 `missing` 不计入已对齐率。
- [ ] 清理阶段的预期 scanner 错误只作为 debug 信息，`EndReason` 保持第一个已确定值。
- [ ] 每日每个 Token 分项均能用核销恒等式解释，且不依赖金额对齐。

### 发布与回滚

发布顺序必须是“先证据、后行为、再结算”：

1. 先发布最小流证据、证据质量和责任观测字段，不改变结算；
2. 独立发布已知上游请求 ID 的只读核销，不接入请求热路径或账单写入；
3. 再发布上游取消传播和已经审批的估算/退款临时政策；
4. 账单详情接口确认后，才发布已知上游请求 ID 的异常核销状态、持久化 pending 和只读 worker；
5. 用受控账号验证账单分项，再灰度启用异步最终结算；
6. 最后依次覆盖响应头前关联、多 attempt、核销超时政策和渠道 SLO。

回滚不得删除核销记录或重写历史 Token 事实。行为回滚后保留新增证据字段；已经完成的历史修正采用追加式、可审计记录，不直接覆盖原始日志。
