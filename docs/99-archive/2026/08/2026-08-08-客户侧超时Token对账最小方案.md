# 客户侧超时后获取上游 Token 的通用方案

本文是当前业务目标下的唯一实施方案。线上事实、跨系统请求证据和受控测试结果见[输出 Token 为 0：日志事实分析](2026-08-07-输出Token为0日志事实分析.md)，修复后接口验收见[客户断开续读接口回归问题分析](2026-08-08-客户断开续读接口回归问题分析.md)。此前的[输出 Token 为 0：代码业务目标、问题分析与优化方案](2026-08-07-输出Token为0代码业务优化方案.md)覆盖异步核销、责任矩阵和渠道治理等更宽范围，现仅作为备选设计，不作为本次实施依据。

本文统一使用以下链路角色：

- **客户侧**：调用网关的用户应用、CLI/SDK 及其网络或代理链路；
- **网关**：承接客户侧请求并转发上游的 API 网关；
- **上游**：网关转发请求的服务；`api02.ananops.com` 是本问题的事实样本和首个线上验收对象，不是代码特例。

## 一、业务目标与边界

### 1. 核心业务结论

> 问题本质是客户侧等待时间短于请求的端到端首事件时间。客户侧超时属于客户侧需要修复的问题；网关在确认客户侧已经离开后，应停止向客户侧写数据，但继续读取当前已经建立的上游响应，尽量取得协议终态和完整 usage，再沿用现有结算链路记录真实 Token。

修复前问题不是上游没有 Token，而是网关在客户侧 Context 结束后立即终止已建立的上游流读取：HTTP 路径关闭响应体，部分 SDK 路径则由绑定的 Context 直接取消。协议处理器因此没有机会取得随后到达的输入、缓存和输出 Token。

所有按 Token 计费的文本生成流式渠道统一遵循：

```text
客户侧 Context 结束
  -> 网关记录 client_gone，并停止向客户侧写入
  -> 网关保持当前已建立的上游流可读
  -> 继续解析上游流
       -> 成功终态且 usage 完整：复用现有结算入口，只结算一次
       -> 上游失败、异常 EOF、读取/解析错误或超时：立即进入现有错误路径
```

该行为是文本生成流的统一业务语义，不按上游域名、渠道 ID、Provider 或模型建立不同的计费政策，也不增加渠道开关。实现上允许 HTTP body、SDK event stream、WebSocket 和 buffered read 按传输机制做最小接入。是否适用只由请求是否属于“按 Token 计费的文本生成流”决定；`api02` 只用于复现和验收。

### 2. Token 对齐口径

本次只要求取得并记录上游协议实际返回的 Token 分项：

- 输入 Token；
- 输出 Token；
- 缓存读取 Token（协议支持时）；
- 缓存创建 Token（协议支持时，包括 Claude 5m/1h 分项）。

不要求金额、单价、倍率、汇率或供应商成本一致。客户侧断开后取得的完整上游 usage 仍通过 New API 各协议现有计费语义和结算入口处理，不建设第二套账本或第二套结算逻辑。

### 3. 人工核对只是最后手段

只有网关继续读取后仍未取得终态 usage，才由支持人员按同一 `upstream_request_id` 手工查看网关日志和上游账单页面，判断差异并向客户解释。

人工核对仅指人工查看和比较，不建设 JSON/CSV 导入、截图 OCR、账单抓取或独立对账器，也绝不通过人工方式补录、补扣、退款、覆盖消费日志或改写历史账单。

### 4. 续读失败时的账务取舍

客户侧已经离开后，如果继续读取仍因协议失败、异常 EOF、读取/解析错误、usage 缺失或超时而失败，网关沿用 New API 现有错误、预扣退款及违规费处理，不以本地估算写普通成功消费日志。

上游可能已经计算缓存或部分输出 Token，但网关没有取得可用于结算的终态 usage。此时上游成本由网关承担，不向客户事后补收，也不通过人工方式改账。这是当前最小方案的明确业务取舍：优先保证客户账务不使用无法证明的估算值；自动追补、责任分摊和异步核销均不在本次范围。

## 二、已确认事实与通用实施条件

### 1. 修复前失败机制

修复前共享流扫描器在客户侧 Context 结束后执行：

```text
SetEndReason(client_gone)
  -> cleanup()
  -> 关闭上游 resp.Body
  -> scanner 解除阻塞并结束
  -> 协议处理器未取得终态 usage
  -> 回退为本地估算或全零 Token
```

Claude 原关联请求因此出现网关 `280,287 / 0`，而上游账单为未缓存输入 `2`、缓存读取 `721,216`、缓存创建 5m `5,422`、输出 `6`。Responses 受控取消样本也出现了全零 Token，说明问题不应通过 Claude/api02 特例修复。

该机制仅作为修复前验收基线。当前实现已将客户侧输出状态与上游读取状态分离，并在消费日志中分别记录 `end_reason` 和 `upstream_result`。

### 2. 当前链路具备继续读取条件

- 受控测试已经证明，同类 280k Claude 请求只要继续等待，就能收到完整 `message_stop` 和 usage；
- 当前通用 HTTP 上游请求由 `http.NewRequest` 创建，没有直接绑定客户侧 Context；响应头已经返回后，上游响应不会仅因客户侧 Context 结束而自动取消；
- 各协议流处理器本来就负责解析终态事件并累计 usage；
- 通用写出辅助函数能够检测客户侧 Context，客户侧结束后可以停止写出；
- 各协议现有结算入口位于流处理完成之后，请求处理函数继续等待扫描结束即可沿用原结算路径；
- `StreamStatus.SetEndReason` 使用 `sync.Once`，继续读取不会覆盖已经确定的 `client_gone`。

因此，优先解决方式是修正流读取生命周期，而不是先建设上游账单查询、异步 worker 或人工数据导入。

实现前上述 Context 条件不适用于所有传输：AWS SDK 事件流继承客户侧 Context，讯飞使用 WebSocket 和 channel，PaLM 流式入口通过 goroutine 整包读取。当前实现已按各自传输生命周期接入同一业务规则，不能把这些路径误写成只依赖共享 HTTP scanner。

### 3. 适用范围

本方案处理所有渠道中同时满足以下条件的请求：

```text
按 Token 计费的文本生成流
上游流已经建立并进入 HTTP body、SDK event、WebSocket 或 buffered read 处理
客户侧 Context 在协议终态 usage 到达前结束
```

范围包括 Claude Messages、OpenAI Chat Completions、OpenAI Responses 的文本/reasoning/tool 请求、Gemini 文本生成，以及 AWS Bedrock、讯飞、PaLM 等其他文本生成渠道。独立图片、视频和音频端点不进入本方案；Responses 中非 Token 计费的图片生成部分也不由本方案改变结算。

正常完成请求、非流式请求和响应头返回前的取消不改变现行行为。若某个上游协议本身不返回终态 usage，继续读取也不能创造真实 Token；客户侧已经离开的场景在到达终止条件后按 `usage_missing` 进入错误路径，不能把估算值宣称为已对齐。

### 4. 非目标

本次不实施：

- 图片、视频、TTS、音频生成、语音识别、模型下载和异步任务等非文本生成流；
- 独立只读对账器或 JSON/CSV 导入；
- 上游账单页面抓取、自动登录或账单详情 API 集成；
- 人工或自动重写历史账单；
- 响应头返回前取消的关联和核销；
- 通用 Provider Hook、Strategy、Registry 或完整证据状态机；
- pending 表、预扣接管、异步结算 worker 或 attempt 树；
- 客户侧取消传播、渠道 SLO、自动降权和路由治理；
- tool/reasoning 本地 Token fallback 重构。

## 三、通用代码方案

### 1. 统一流生命周期

客户侧 Context 结束不再等同于上游读取结束。文本生成流生命周期统一为两个正交维度：

- **客户侧输出状态**：客户侧结束后立即停止 SSE、PING 和任何其他响应写入；
- **上游结束状态**：独立记录 `terminal_success`、`protocol_failure`、`usage_missing`、`incomplete_eof`、`scanner_error`、`handler_error`、`idle_timeout` 或 `drain_timeout`。

现有 `end_reason=client_gone` 继续表示客户侧先结束。由于 `SetEndReason` 使用 `sync.Once`，不能再用同一个字段表达随后发生的上游结果；实现必须增加独立的上游结束结果，不能让 `client_gone` 吞掉上游错误，也不能改写第一个客户侧结束原因。这只是两个正交结果，不扩展为完整责任状态机。

新增上游结果必须通过并发安全的方法写入和读取，不增加可被任意直接读写的公开字段。现有 `EndReason` 读取发生在 scanner goroutine 汇合之后，尚无证据证明已经存在数据竞争；本次要求访问器是为了不给新并发状态复制潜在风险，不顺带重构无关读侧。

客户侧结束时执行：

1. 首次记录 `end_reason=client_gone`；
2. 停止 ping 和所有客户侧写入；
3. 不因客户取消立即关闭当前上游 `resp.Body`、event stream 或 WebSocket；
4. scanner 和协议 data handler 继续读取、解析事件和累计 usage；
5. 收到成功终态、明确失败、EOF、读取/解析错误或任一超时后，立即统一关闭对应上游资源并等待 goroutine 退出；
6. 请求处理函数等待上述过程完成后再返回，不把 Gin Context 交给脱离请求生命周期的后台任务。

以下新计时规则只作用于 `client_gone` 后的续读窗口。客户侧仍在线时维持现行流超时语义，包括上游注释、PING、空行和 keepalive 对现有空闲计时的续期；本次不顺带改变正常流或普通 timeout 的结算行为。

断开后续读同时受两个边界约束：

- **流空闲超时**：只在收到有效业务 SSE 事件后重置；注释、PING、空行和无法识别的数据不能续期；
- **断开后绝对上限**：从 `client_gone` 起启动不可重置的计时器。为保持当天上线的最小改动，第一版直接复用 `STREAMING_TIMEOUT` 的值，不新增配置项。

即使上游持续发送心跳或无效行，也必须在绝对上限到达时以 `drain_timeout` 结束，不能无限占用请求 goroutine 和连接。

`STREAMING_TIMEOUT` 当前默认值为 300 秒。断开后绝对上限不允许被关闭；如果有效配置小于等于 0，实现必须使用 300 秒的安全默认值并记录配置告警，不能退化为无限等待。该值只是第一版的有界策略，不保证覆盖所有长输出 tail；超过绝对上限的请求会进入错误路径，并可能形成由网关承担的上游成本。上线前必须实测 api02 原问题场景从 `client_gone` 到终态 usage 的耗时，确认显著小于 300 秒，否则不得发布。

### 2. 统一业务规则，按传输方式窄接入

主实现放在新的独立流生命周期文件中，负责客户侧输出状态、断开后计时和上游结束结果。所有文本生成路径遵循同一业务规则，但允许按传输机制做必要的窄接入；“不存在特例”指不存在不同的客户计费政策，不表示 HTTP body、SDK event stream 和 WebSocket 必须使用完全相同的读取代码。

上线前必须覆盖以下真实传输类型：

| 传输类型 | 现有代表路径 | 最小接入要求 |
| --- | --- | --- |
| 共享 `StreamScannerHandler` | Claude、OpenAI Chat/Responses、Gemini、xAI、Baidu、Dify | 共享接入断开后续读；同 helper 中图片和音频调用点不启用 |
| 同步直接 `NewStreamScanner` | Ollama 文本、Coze、Tencent、Cloudflare、`OaiResponsesToChatBufferedStreamHandler` | 接入相同的客户侧状态、续读终止条件和上游结果 |
| scanner + channel + `c.Stream` | Cohere、Zhipu | 客户离开后由请求 goroutine 继续消费内部 channel，不再写客户侧；防止 scanner goroutine 向无人接收的 channel 发送而永久阻塞 |
| AWS SDK event stream | Bedrock `InvokeModelWithResponseStream` | 使用受控 Invoke Context：调用建立前仍响应客户取消，事件流建立后不再被客户 Context 直接取消，并受续读绝对上限控制 |
| WebSocket + channel | 讯飞 | 客户侧离开后 handler 继续消费 data channel、累计 usage；确保 reader goroutine 不因无人接收而阻塞，并可在终态、错误或超时时关闭 WebSocket |
| buffered whole-body read | PaLM 流式兼容入口 | 请求处理函数继续等待读取完成，客户离开后停止写出；读取/解析失败立即返回，不能让 goroutine 阻塞在无人接收的 channel |

AWS 当前的 Invoke Context 继承客户侧 Context，不能直接满足续读。最小实现应创建独立的受控 Context，并在 `InvokeModelWithResponseStream` 建立前监听客户取消；调用成功取得 event stream 后停止该取消转发，后续只由上游终态、错误、Relay 限制和断开后绝对计时取消。这样保持“响应建立前取消仍生效、响应建立后继续取得 usage”的业务边界。

Cohere、Zhipu、讯飞和 PaLM 现有路径都含有非缓冲 channel，客户离开后不能再依赖 `c.Stream` 继续消费。必须让请求生命周期接管后续消费，并消除 reader goroutine 向无人接收的 channel 写入而阻塞的风险。PaLM 上游若不返回真实 usage，读取完成后仍按 `usage_missing` 进入断开后错误路径，不能把文本估算标为上游终态 Token。

上线前必须以代码搜索重新生成调用点清单并按业务类型、传输类型分类。不能只修改 `StreamScannerHandler` 后就宣称覆盖所有文本渠道，也不能因为共用 helper 而把图片、视频或音频纳入本次改造。

### 3. 客户侧写失败不得终止 usage 解析

客户侧 Context 已结束后：

- 所有写出函数直接跳过写入；
- 已知的客户侧断开或写失败不记为上游错误；
- 协议 handler 不因客户侧写失败调用 `Stop` 或提前返回；
- usage、协议终态和工具调用等内部解析继续进行；
- 真正的上游解析错误仍按现有错误语义结束。

这是通用方案能否成立的必要条件，不能只保留响应体却让 handler 因写失败提前停止。

### 4. 上游异常必须立即结束

继续读取不是忽略上游错误。以下判定只控制 `client_gone` 后的续读结果；客户侧仍在线时的普通 timeout、EOF、fallback 和结算语义保持现行，不由本次改造。

断开后续读的结束判定固定为：

| 上游事件 | 网关处理 | 上游结果 |
| --- | --- | --- |
| 协议成功终态且 usage 完整 | 立即停止读取，进入现有成功结算 | `terminal_success` |
| 协议明确失败终态 | 立即停止读取，返回现有 `NewAPIError` | `protocol_failure` |
| 收到协议终态，但协议未提供或未完整提供 usage | 立即停止读取，按 usage 不可用报错 | `usage_missing` |
| EOF 且未见协议成功终态或 usage 不完整 | 不等待超时，立即按不完整上游流报错 | `incomplete_eof` |
| scanner 非 EOF 错误 | 立即停止并返回读取错误 | `scanner_error` |
| handler 解析、协议校验错误或 panic | 立即停止并返回处理错误 | `handler_error` |
| 未收到有效业务事件达到空闲上限 | 关闭响应体并返回超时错误 | `idle_timeout` |
| 客户侧断开后达到绝对上限 | 关闭响应体并返回超时错误 | `drain_timeout` |

EOF 只代表传输结束，不能继续作为所有协议的正常成功条件。成功必须由协议 handler 明确确认，例如 Claude `message_stop`、Responses 成功终态、OpenAI Chat `[DONE]` 与可用 usage、Gemini 完成状态与 usage metadata。上游明确失败事件应调用现有 `Stop(error)`；合法但非 completed 的终态是否可结算，按协议状态、原因和 usage 完整性判断，不能只按事件名称统一处理。

客户侧已经离开时无法再通知客户，但网关仍必须结束处理、记录错误并进入现有错误/退款路径。客户侧仍在线时不进入本表的新判定，继续沿用各协议现有的流错误响应和 fallback 行为。

### 5. 区分客户侧结束与 usage 完整性

`end_reason=client_gone` 表示客户侧连接先结束，不能被后续 EOF、DONE 或清理错误覆盖。Token 是否可用于结算继续使用各协议现有 usage 证据：

- 收到完整协议终态和非估算 usage：沿用真实 usage 结算；
- 继续读取超时、上游报错或终态 usage 仍缺失：不得把本地估算描述成已与上游对齐，只保留现有估算来源标识和失败证据。

同一请求可以同时是 `client_gone`，并最终取得完整上游 usage。

### 6. 只复用现有结算入口

完整 usage 仍由各协议现有入口结算；Claude 路径继续使用 `PostTextConsumeQuota`。统一约束为：

- 不新增异步结算入口；
- 不新增第二条消费日志写入路径；
- 不重新执行预扣；
- 不在客户侧结束时先结算、终态到达后再调整；
- 不修改正常请求和非流式请求的计费语义。

正确结果是“同一请求晚一些完成原有结算”，不是“先落错误账单，再补账或调账”。

只有 `terminal_success` 且 usage 完整时才能进入成功结算。其余上游结果返回错误，不调用普通成功消费日志路径，也不把本地估算冒充为上游终态 Token。

## 四、今天的实施与上线顺序

### 阶段一：先用测试固定共享契约

1. 构造可控上游流：客户侧取消后，上游继续返回业务事件、终态 usage 和协议完成事件；
2. 验证客户侧取消后不再产生任何响应写入；

## 五、测试与验收

2026-08-08 验收结果：真实 Claude Messages、OpenAI Responses 断开场景取得非零终态 usage；Claude 缓存读取分项在断开后完整落库；消费日志能够同时表达 `client_gone + terminal_success`；全量相关 Go 测试和根模块构建通过。没有真实供应商账号的传输使用协议级可控流测试验收。

### 1. 必须新增的回归测试

- 客户侧取消不会立即关闭已建立的上游响应体、event stream 或 WebSocket；
- 取消后到达的业务事件、终态 usage 和完成事件仍被解析；
- 取消后不再写入 SSE、PING 或终态响应；
- 支持缓存的协议保留缓存读取和缓存创建分项；
- `end_reason` 保持 `client_gone`，上游成功或异常结果记录在独立字段；
- 协议失败、usage 缺失、异常 EOF、scanner 错误和 handler 错误会立即结束，不等待计时器；
- `client_gone` 后空行、PING、注释和无效数据不能重置续读空闲计时；客户仍在线时保持现行每行续期；
- 上游持续发送心跳但没有终态时，仍会触发不可重置的断开后绝对超时；
- 完整上游 usage 只经过一次协议现有结算入口；
- 非 `terminal_success` 或 usage 不完整时不进入普通成功消费日志路径；
- 继续读取超时后对应上游资源关闭、goroutine 全部退出，不泄漏 Gin Context；
- 共享 scanner、同步直接 scanner、scanner + channel、AWS SDK event stream、讯飞 WebSocket/channel 和 PaLM buffered read 遵循相同业务结果；
- 正常完成、非流式、图片、视频和音频路径保持不变。

### 2. 验收标准

- [x] 所有按 Token 计费的文本生成流在客户侧取消后，不再因客户取消而立即终止已建立的上游流读取。
- [x] 网关停止客户侧写入，但继续解析上游流并取得协议可提供的完整终态 usage。
- [x] 原问题场景不再因为立即关闭上游响应体而固定落为本地估算输入和 0 输出。
- [x] 完整 usage 复用 New API 原有预扣、结算和消费日志语义，只结算一次。
- [x] `client_gone` 与上游 `terminal_success/error/timeout` 能够同时被准确表达。
- [x] 协议失败、异常 EOF、读取/解析错误立即结束并进入现有错误路径，不等待空闲或绝对超时。
- [x] 上游静默或持续心跳但没有终态时，分别受空闲超时和不可重置的绝对上限约束。
- [x] 新空闲和绝对计时只作用于 `client_gone` 后续读；客户仍在线时的普通 timeout、EOF、fallback 和结算保持现行语义。
- [x] 失败、usage 缺失或超时情况下的本地估算不会被标记为已与上游 Token 对齐，也不会进入普通成功消费日志路径。
- [x] 续读失败但上游已经产生费用时，由网关承担差额，不人工或自动补收客户账务。
- [x] 日常流程不依赖人工对账、JSON/CSV、截图 OCR 或上游页面抓取。
- [x] 支持人员手工核对只作为最后手段，且不会产生任何人工账务写入。
- [x] 不存在按域名、渠道 ID、Provider 或模型划分的计费政策；适用性只按文本生成业务类型判定，传输层只保留必要接入差异。
- [x] 共享 scanner、同步直接 scanner、scanner + channel、AWS SDK event stream、WebSocket/channel 和 buffered read 均有确定性回归覆盖。
- [x] 图片、视频、音频和其他非文本流的生命周期及结算保持不变。
- [x] 不引入数据库迁移、pending worker、异步结算或第二套账务逻辑。

## 六、发布与回滚

该能力随新版本对所有按 Token 计费的文本生成渠道统一生效，不增加运行时开关。发布可以先经过单实例验证，但每个升级实例的文本生成业务语义完全一致；图片、视频、音频和其他非文本流不受影响。

若上线后出现连接无法释放、goroutine 增长、空闲/绝对超时异常、上游错误未及时结束或重复结算，立即回滚到上一版本，恢复客户侧结束后关闭上游响应体的旧行为。回滚不涉及数据库、历史账单或人工调账。

任何上游账单自动查询、人工数据导入、异步核销、响应头前关联和多 attempt 汇总均不属于本文实施范围；如业务目标变化，必须另立项目评审，不能从当前通用流生命周期方案隐式扩张。
