# 组织账单充值与余额导出最小实施方案

## 问题与目标

组织 Invoice 专用 CSV 已完成组织名称、真实姓名与用户名双表头、内部时间字段删除、规则明细删除和原始 quota 删除。当前还需在“模型归类结算汇总”的合计行之后增加两行：

```csv
用户当期成功充值订单金额,...
用户导出时剩余金额,...
```

本方案以最小入侵为第一约束：只扩展 Invoice 导出读取和 CSV 投影，不新增钱包总账，不记录所有 `users.quota` 变动，不修改充值、消费、预扣、结算、退款、订阅和缓存核心链路。

## 当前实际情况

### 已验证事实

- Invoice 导出账号列来自当前聚合结果 `invoice.Accounts`，因此补充行只覆盖已经出现在 Invoice 交叉表中的用户；账期内没有消费、未进入交叉表的组织成员不新增为 CSV 列。
- 用户当前钱包余额保存在主数据库 `users.quota`，可在导出时按账号 ID 批量读取。
- 成功充值订单保存在主数据库 `top_ups`，可以通过 `user_id`、`status=success` 和 `complete_time` 按账期筛选。
- 钱包充值与订阅购买可能同时留下充值相关记录，不能仅按 `status=success` 汇总；必须排除订阅订单和余额购买订阅。
- `top_ups` 没有统一存储“实际入账 quota”：Stripe、Creem、Waffo 和 Waffo Pancake 的 `Amount`、`Money` 字段语义不同，导出计算必须使用显式支付渠道白名单和与现有充值代码一致的渠道换算规则。
- EPay 正常成功回调只更新订单状态，不写入可用于账期归属的 `complete_time`；在不修改 new-api 充值核心路径的约束下，导出层不能精确统计 EPay 订单。
- 现有 `LogTypeTopup` 不是可靠的余额入账流水：它包含订阅购买，部分日志 `quota=0`，额度可能只存在于文本内容中；本方案不得解析日志文本补数。

### 已接受决策

- “用户当期充值金额”收窄为“用户当期成功充值订单金额”，不再承诺覆盖全部钱包正向增加。
- “用户当期剩余金额”使用导出时主数据库中的当前 `users.quota`，不是账期结束时历史余额。
- 不为该导出新增余额流水表，不改造 `IncreaseUserQuota`、`DecreaseUserQuota` 或任何消费/退款主链路。
- EPay 不在“当期成功充值订单金额”的支持渠道内；不使用 `create_time`、日志文本或订单号猜测完成时间。

### 明确不覆盖

最小方案不统计以下余额增加：

- 管理员直接修改用户余额；
- 兑换码充值；
- 消费退款、预扣退款和差额退款；
- 签到奖励；
- 注册赠送和邀请奖励；
- 邀请额度转入钱包；
- 脚本、人工 SQL 或其他直接额度修正；
- 没有可识别成功充值订单的历史数据。
- EPay 充值订单，包括少数具有 `complete_time` 的补单记录；为避免同一渠道只统计部分订单，导出统一排除 EPay。

不统计订阅套餐购买和使用余额购买订阅；它们不是钱包充值，即使存在充值类型日志或关联订单记录也必须排除。

## 优化方案

### 1. 接线边界

主实现放入新的 Invoice 导出补充查询文件，负责一次性读取：

- 交叉表账号在所选账期内的成功钱包充值订单；
- 同一批账号在导出时的当前 `users.quota`。

现有文件只做最小接线：

- `model/organization_invoice_export.go` 仅扩展导出上下文或调用新的补充查询；
- `controller/organization_invoice_csv.go` 仅在类别合计行后追加两行；
- 不修改 `model/organization_invoice.go` 的消费聚合、分类和结算逻辑；
- 不修改任何充值回调、钱包扣减、退款、订阅或 Relay 代码。

### 2. 成功充值订单筛选

查询条件固定为：

```text
user_id IN Invoice 账号 ID
status = success
complete_time >= 账期开始时间戳
complete_time < 账期结束时间戳 + 1 秒
payment_provider IN (stripe, creem, waffo, waffo_pancake)
```

还必须排除：

- 与订阅订单使用相同 `trade_no` 的记录；
- `payment_provider=balance`；
- `payment_provider` 为空、未知或不在白名单中的历史记录；
- pending、failed、expired 等非成功订单；
- `complete_time=0` 或不在账期内的订单。

未知和无法判定的记录宁可不计，不通过日志内容、订单号字符串或模糊规则猜测。

### 3. 充值金额换算

按当前钱包充值实现使用显式渠道分支，把订单还原为钱包入账 quota，再统一使用 Invoice 的 USD 金额格式化规则输出六位小数：

| 支付渠道 | 当前入账依据 | 导出换算 |
| --- | --- | --- |
| Stripe | `Money * QuotaPerUnit` | `Money` 的 USD 等值 |
| Waffo | `Amount * QuotaPerUnit` | `Amount` 的 USD 等值 |
| Waffo Pancake | `Amount * QuotaPerUnit` | `Amount` 的 USD 等值 |
| Creem | `Amount` 直接作为 quota | `Amount / QuotaPerUnit` |

换算只用于只读报表，不调用充值逻辑，不重放订单，不更新用户余额。金额累计使用 decimal，禁止用不受控的浮点转整数或裸 `int` 转换。

未知或不支持渠道在 SQL 白名单层静默排除；已知渠道的字段异常订单排除并记录服务端告警，不猜测入账金额。已知渠道按当前正常回调公式还原，因此不承诺覆盖历史公式变更。现有 `top_ups` 也没有结构化标记区分正常回调与管理员补单；最小方案会按原订单 `payment_provider` 的正常公式处理支持渠道的成功补单，无法保证采用过特殊补单公式的历史记录绝对精确，本方案不为消除此限制而修改充值核心链路。

### 4. 导出时剩余金额

导出上下文按交叉表账号 ID 从主数据库批量查询 `users.quota`，不读取 Redis 缓存。每个值按以下公式转为 USD 并保留六位小数：

```text
剩余金额 = users.quota / QuotaPerUnit
```

这是生成 CSV 时的即时值，不回溯到账期结束时间，也不保证与稍后再次导出一致。查询不到用户时导出失败，不使用 `0` 静默掩盖数据缺失。

### 5. CSV 结构

两行仅追加在“模型归类结算汇总”的合计行之后，不重复添加到“AI 模型消费汇总”：

```csv
真实姓名,张宇,李明,,,,
模型类别,zhangyu,harper_k5,折前合计,结算系数,结算后金额
Claude,...
GPT,...
合计,...
用户当期成功充值订单金额,100.000000,50.000000,,,
用户导出时剩余金额,26.500000,18.000000,,,
```

两个补充行与账号列严格一一对应；“折前合计、结算系数、结算后金额”只属于模型结算，因此对应单元格全部留空，不把充值或余额总数塞入语义不匹配的列。

### 6. 数据库兼容与性能

- 查询使用 GORM 和现有字段，不新增迁移、索引、触发器或数据库专有函数。
- 主数据库查询必须兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。
- 用户余额使用一次批量查询；充值订单按用户集合、状态、完成时间和支付渠道一次查询，使用数据库侧 `NOT EXISTS` 排除订阅订单，不将全部 `trade_no` 展开为参数列表，禁止逐用户 N+1。
- Invoice 消费聚合仍从现有日志数据库读取，充值和余额只从主数据库读取，不改变双数据库职责。

### 7. 测试与验收

新增或扩展测试必须使用 `testify/require` 和 `testify/assert`，至少保护以下业务合同：

- CSV 两个补充行位置正确，用户列顺序与真实姓名/用户名表头一致，尾部结算列为空；
- 成功钱包充值订单计入，pending/failed/账期外订单不计入；
- 订阅购买、余额购买订阅、未知渠道和空渠道记录不计入；
- Stripe、Creem、Waffo、Waffo Pancake 按各自字段语义换算；EPay 即使为成功状态也不计入；
- 同一用户多笔订单正确累计，不同用户不串账；
- Invoice 的 `end_timestamp` 表示账期最后一秒；查询采用 `[start_timestamp, end_timestamp + 1)`，最后一秒计入，下一秒不计入；
- 当前余额从主数据库读取并正确换算，缺失用户返回错误；
- 兑换码、退款、奖励和直接调额不会被误算为成功充值订单；
- 原有组织名称、双表头、类别金额、结算系数和结算后金额合同保持不变。

建议验证命令：

```bash
go test ./controller ./model
task docs:check
git diff --check
```

## 完成门槛与待收敛事项

完成必须同时满足：

- 只读补充查询和 CSV 两行已实现；
- 未修改任何余额变更和计费结算路径；
- 全量 controller/model 测试与文档校验通过；
- 人工导出的用户顺序、成功充值订单金额和即时余额可与主数据库记录核对；
- 产品验收明确接受“成功充值订单金额不等于全部钱包入账金额”以及“EPay 不在支持渠道内”的限制。

实施与自证已于 2026-08-10 完成：

- 新增独立的 Invoice 财务补充查询文件，批量读取成功充值订单和导出时用户余额；
- 原有 Invoice 导出上下文、导出调用点和 CSV 写入器只增加必要接线；
- 没有修改充值回调、余额变更、消费、预扣、结算、退款、订阅或 Relay 路径；
- 评审后移除 EPay 的不准确覆盖承诺，并将订阅排除收敛为数据库侧 `NOT EXISTS`；
