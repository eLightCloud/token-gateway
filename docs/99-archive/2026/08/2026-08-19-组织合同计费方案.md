# 组织合同计费方案

## 问题与目标

组织需要拥有一份合同，使组织成员默认继承该合同的计费规则：

1. 组织成员使用组织当前生效合同；
2. 合同可以在现有用户组倍率之上增加一个组织级倍率；
3. 合同可以针对指定渠道配置独立折扣；
4. 成员产生的所有使用账单都体现合同折扣；
5. 合同变更、请求重试、异步任务和组织发票不能产生重复折扣或历史账单漂移。

本方案将合同定义为独立的计费层，不修改用户的 `Group` 字段，也不把合同逻辑分散到渠道适配器中。

## 当前实际情况

### 已验证事实

1. 组织已经有 `Organization`、`OrganizationMember`、成员生效/离职时间和组织账单查询能力。组织模型位于 [`model/organization.go`](../../model/organization.go)。
2. 组织发票目前通过日志中的 `Log.Quota` 聚合消费额度，发票逻辑位于 [`model/organization_invoice.go`](../../model/organization_invoice.go)。
3. 普通模型价格和预扣额度主要由 [`relay/helper/price.go`](../../relay/helper/price.go) 计算。
4. 统一预扣、补扣、结算和退款由 [`service/billing_session.go`](../../service/billing_session.go) 管理。
5. 文本、音频和部分实时计费逻辑位于 [`service/text_quota.go`](../../service/text_quota.go) 和 [`service/quota.go`](../../service/quota.go)。
6. 按次任务和异步任务会将计费上下文写入 `TaskPrivateData.BillingContext`，相关代码位于 [`relay/relay_task.go`](../../relay/relay_task.go) 和 [`service/task_billing.go`](../../service/task_billing.go)。
7. 现有用户组倍率由 `ratio_setting` 提供，用户组特殊倍率和自动分组会影响最终 `GroupRatio`。
8. 当前普通请求的价格预估发生在最终渠道选择之前，因此渠道专属合同折扣不能简单地只在初次价格计算中读取。
9. 组织已有 `OrganizationBillingSettlementRule`，它是发票阶段的月度/分类结算因子，不等同于请求级合同折扣。
10. quota 转换已有 `common.QuotaFrom*Checked` 等饱和保护函数，新的合同倍率必须继续使用这些函数，不能使用未经约束的浮点到 `int` 转换。

### 未实现事实

- 当前没有组织合同数据模型、合同版本、渠道合同倍率或用户合同计费快照。
- 当前组织成员关系不会自动进入 RelayInfo 的计费上下文。
- 当前日志没有合同 ID、版本和合同倍率字段。

## 设计决策与假设

以下是本方案的推荐默认口径；产品若选择不同语义，应在实现前明确记录：

1. 一个组织同一时刻只有一个当前生效合同，但保留不可变历史版本。
2. 合同倍率与当前用户组倍率相乘，而不是替换用户组倍率。
3. 合同全局倍率与渠道倍率相乘，而不是渠道倍率覆盖全局倍率。
4. 全局倍率允许大于 1（合同加价或组织级倍率）；“渠道折扣”默认限制为 `0 < ratio <= 1`。
5. 合同只影响 AI 使用账单，默认不影响充值价格；违规费用是否折扣需要产品单独确认。
6. 合同按请求或任务创建时确定快照；合同后续变更不影响已开始的请求和已提交的异步任务。

## 优化方案

### 一、数据模型

新增独立合同表，并保留组织当前合同引用：

```go
type OrganizationContract struct {
    Id                int
    OrganizationId    int
    Version           int
    Name              string
    Status            int
    GlobalRatioScaled int64
    EffectiveFrom     int64
    EffectiveTo       int64
    CreatedAt         int64
    UpdatedAt         int64
}
```

渠道倍率使用子表，而不是数据库 JSON：

```go
type OrganizationContractChannelRatio struct {
    Id          int
    ContractId  int
    ChannelId   int
    RatioScaled int64
    CreatedAt   int64
    UpdatedAt   int64
}
```

组织增加：

```go
ActiveContractId int
```

倍率使用整数缩放保存，例如 `0.8 -> 800000`，避免 SQLite、MySQL、PostgreSQL 间的浮点精度差异。合同更新采用事务：创建新版本、写入渠道倍率、切换 `ActiveContractId` 一次完成。旧版本不覆盖、不删除。

建议对子表建立唯一约束：

```text
unique(contract_id, channel_id)
```

### 二、合同解析与计费快照

新增独立的合同服务模块，例如：

```text
model/organization_contract.go
service/organization_contract.go
```

负责：

- 根据 `user_id` 找到当前有效组织成员；
- 读取组织当前合同和生效时间；
- 查询指定渠道倍率；
- 校验倍率边界；
- 生成不可变的合同计费快照；
- 在合同更新后失效相关缓存。

在 `RelayInfo` 增加合同快照，建议至少包含：

```text
contract_id
contract_version
global_ratio
channel_ratio
effective_ratio
channel_id
```

`PriceData` 或其关联结构同时保留原始用户组倍率、合同全局倍率、合同渠道倍率和最终有效倍率。不能只覆盖现有 `GroupRatio`，否则日志无法解释合同折扣，也无法排查重试时的计费差异。

最终倍率公式：

```text
effective_ratio
  = current_user_group_ratio
  × contract_global_ratio
  × contract_channel_ratio
```

未配置渠道倍率时使用 `1.0`。

### 三、渠道选择和预扣费

当前请求在初次预扣后才确定最终渠道。推荐采用以下流程：

```text
初次价格计算
→ 应用用户组倍率和合同全局倍率
→ 初次预扣
→ 选择渠道
→ 应用渠道合同倍率
→ 必要时通过 BillingSession.Reserve 补扣
→ 请求上游
→ 使用最终合同快照结算
```

这样可以处理自动分组和渠道重试：

- 渠道折扣小于 1 时，初次预扣可能多于最终消费，结算时退回差额；
- 渠道倍率大于 1 时，确定渠道后必须补扣差额；
- 重试切换渠道时，重新计算渠道倍率，但不能重复叠加合同倍率；
- 同一个请求始终只保留当前尝试的合同渠道快照。

如果产品只需要“折扣”而不需要渠道加价，建议将渠道倍率限制为 `0 < ratio <= 1`，可以减少预扣不足风险。

### 四、所有计费路径的接入范围

合同倍率必须进入实际 quota 计算，而不是只修改日志展示。需要覆盖：

1. 普通文本、Responses、Claude、Gemini；
2. Tiered Expression 计费；
3. 图片、音频、Embedding、Rerank；
4. WebSocket 实时文本和音频；
5. 按次任务、视频任务和异步任务；
6. 任务失败退款、差额结算和重试；
7. 如产品确认需要，接入违规费用。

Tiered Expression 的建议顺序是：

```text
表达式计算基础价格
→ 合同倍率
→ common.QuotaFrom*Checked
→ 预扣/结算
```

不要将组织合同隐式写进 billing expression，否则同一个模型表达式会因组织不同而失去可解释性。

异步任务提交时必须把合同信息写入 `TaskPrivateData.BillingContext`，轮询结算使用提交时的合同版本，不重新读取当前合同。

### 五、日志和组织发票

`Log.Quota` 应记录已经应用合同折扣后的最终消费额度：

```text
Log.Quota = 合同折后实际消费额度
```

现有组织账单和发票直接聚合 `Log.Quota`，因此不需要在发票生成阶段再次应用合同倍率。否则会出现重复折扣：

```text
请求结算已打折
→ 日志写入折后 quota
→ 发票再次乘合同倍率
→ 被重复折扣
```

消费日志 `Other` 建议增加普通可见的合同摘要：

```json
{
  "contract": {
    "id": 7,
    "version": 3,
    "global_ratio": 0.8,
    "channel_ratio": 0.5,
    "effective_ratio": 0.4
  }
}
```

日志至少应能追溯合同 ID、合同版本、全局倍率、渠道倍率和最终倍率。商业敏感的完整合同内容可以仅放在管理员字段，但最终消费金额和折扣结果必须可解释。

现有 `OrganizationBillingSettlementRule` 继续作为发票阶段规则，顺序应保持为：

```text
模型价格
→ 用户组倍率
→ 合同倍率
→ Log.Quota
→ 组织发票聚合
→ 发票结算因子（如配置）
```

### 六、缓存和一致性

合同解析可以使用用户/组织维度缓存，但必须满足：

- 合同更新后失效组织合同缓存；
- 成员加入、退出组织后失效对应用户缓存；
- 请求开始后使用不可变快照，不受后续缓存更新影响；
- 多节点部署时通过现有 Redis 或分布式失效机制同步。

## 接口规划

组织管理员接口：

```text
GET  /api/organization/current/contract
POST /api/organization/current/contract
PUT  /api/organization/current/contract
GET  /api/organization/current/contract/preview
```

系统管理员接口：

```text
GET  /api/admin/organizations/:id/contract
POST /api/admin/organizations/:id/contract
PUT  /api/admin/organizations/:id/contract
GET  /api/admin/organizations/:id/contract/versions
```

接口应支持查看当前合同、创建新版本、配置全局/渠道倍率、设置生效时间、按模型和渠道预览最终价格、查看历史版本及禁用合同。更新请求应携带 `expected_version`，并在事务中执行乐观锁校验。

## 校验和安全约束

合同配置必须拒绝：

- `NaN`、正无穷和负数；
- `global_ratio <= 0`；
- 渠道折扣 `ratio <= 0`；
- 超过产品允许上限的倍率；
- 不存在的渠道 ID；
- 同一合同重复配置同一渠道；
- 重叠的生效时间版本。

所有合同倍率产生的 quota 转换必须使用 `common.QuotaFromFloatChecked`、`common.QuotaRoundChecked` 或 `common.QuotaFromDecimalChecked`，并沿用现有饱和审计逻辑。

## 实施工作包

### 工作包 A：合同模型和版本

- 新增合同模型、渠道倍率模型；
- 增加组织当前合同引用；
- 完成三种数据库迁移和 AutoMigrate 注册；
- 增加版本、生效时间和唯一约束。

### 工作包 B：计费解析和快照

- 实现用户当前合同解析；
- 扩展 `RelayInfo`、`PriceData` 和任务计费上下文；
- 实现缓存和失效；
- 实现合同倍率组合函数。

### 工作包 C：同步和异步计费接入

- 接入普通文本、Responses、音频、图片等路径；
- 接入实时 WebSocket；
- 接入按次任务和异步任务；
- 接入渠道重试、补扣、退款和结算。

### 工作包 D：日志和发票

- 消费日志写入合同快照；
- 组织账单展示折后额度和合同摘要；
- 确认发票不重复应用合同倍率；
- 增加 CSV 和数据导出的合同字段策略。

### 工作包 E：管理接口和前端

- 组织管理员合同页面；
- 系统管理员合同管理页面；
- 合同版本历史；
- 模型/渠道价格预览；
- 合同变更审计日志。

## 验证门槛

### 单元测试

- 用户组倍率、全局合同倍率、渠道倍率的组合结果；
- 未配置合同和已过期合同回退到原有计费；
- 合同倍率边界、NaN、Inf 和超范围值；
- 渠道倍率缺省值为 `1.0`；
- quota 饱和时不会产生负数或整数溢出。

### 集成测试

- 普通请求预扣和结算使用同一合同快照；
- 渠道重试不会重复叠加合同倍率；
- 渠道折扣变化能够正确退费或补扣；
- 异步任务使用提交时合同版本；
- WebSocket、图片、音频和按次任务均应用合同；
- 合同更新不会改变已完成日志和历史发票；
- 组织发票不会对 `Log.Quota` 二次折扣；
- 组织管理员和系统管理员可以查看合同摘要，普通成员的可见字段符合产品权限。

### 数据库和构建验证

至少验证：

```bash
go test ./model ./service ./relay/helper ./controller -count=1
go test ./... -count=1
```

并分别使用 SQLite、MySQL 和 PostgreSQL 执行迁移与合同 CRUD 测试。若改动 `relaykit/`，还必须单独执行：

```bash
cd relaykit && GOWORK=off go build ./...
```
