# Seedance 视频增强实施计划

## 目标与状态

将已讨论的 Seedance 2.0 / 2.5 增强服务落成可配置、可恢复、可正确计费的能力，仅覆盖火山官方与 runyyitd。产品合同、界面简图、计价公式及取舍统一见 [Seedance 视频增强方案](../80-dev/2026-10-15-Seedance视频增强方案.md)，本计划不维护第二套价格或接口合同。

当前状态：P0–P4 的核心代码与后台界面已实现，并完成本地合同、账务、权限和三库验证；P5 的真实火山、MediaKit、OSS 与 runyyitd 联调尚未完成，功能默认关闭，未部署。实际入口、验证结果和外部限制见文末“本次实施与验证记录”。原始官方资料见 [调研文档](../70-research/Seedance视频增强与火山AIMediaKit接入调研.md)。

用户已确认增强模型整项服务按最终成片秒数收费，原片 tokens 仅用于内部成本核算；时长粒度遵循火山 MediaKit 官方毫秒计量，不向上取整为整秒或整分钟。用户已明确 OSS 保存期限、自动清理和存储分层暂缓；不再以这些问题阻塞实施设计。测试先火山官方，runyyitd 待真实合同明确后跟进，不擅自替换成 CodeYY 或 Zapgogo。

## 实施前基线与主要风险

| 事实 | 必须处理的风险 |
| --- | --- |
| 本地 doubao 覆盖负责生成，当前无增强状态机 | 新功能应独立编排，不能扩写整份生成插件 |
| 增强模型可能映射到基础模型 | 渠道候选识别、schema、权限和价格不能丢失增强身份 |
| 终态 polling 会触发结算/退款 | 原片完成不能提前终结客户任务 |
| 现有产物存储实现禁用 | 不能只增加后台表单而没有真实 OSS 写入/读取 |
| 原生、Videos、Responses 有不同结果投影 | 任何公开入口都不能提前返回原片或内部重试细节 |
| 目前缺少可读取的官方测试凭据和 runyyitd 合同 | 对应实测保持待执行，不能以静态检查宣称成功 |

## 工作包与完成门槛

### P0：验证边界与接线方案

产出：最小接线清单、增强合同/schema 选择路径、正式生成驱动复用方式和可验证样例。先做可撤销的技术验证，不把实验代码直接扩散到各层。

- 核对 fire-and-poll 生成调用的三个入口及当前插件加载优先级，定位提交、结果解析与终态收尾的唯一接触点。
- 验证 `...-enhance` 在渠道分发前可识别，客户模型名和生成机器模型名能分别固定，普通映射链仍只解析一次。
- 证明完整增强 schema 在价格保存、预览、预扣、混合任务轮询和最终结算中一致；不能让 `UsageForModels` 先选到基础模型 profile。
- 对 runyyitd 收集官方 Base URL、协议、准确模型 ID、生成 usage、原片下载方式及计费单位；未知项明确阻塞该供应商上线，不凭 Runy 注释推测。
- 确定宿主专用编排/适配器包装的最小接线方式。不占用原插件已拥有的 channelTypes，不增加第二条扣费链，不通过内部 HTTP 重新调用普通模型 API。

完成门槛：增强别名示例可在不修改原生分辨率能力的条件下路由并选择完整计量合同；对不能独立扩展的公共入口逐一写出原因与最小变更点。此门槛不通过，不直接进入大范围开发。

### P1：独立配置、公开模型与后台入口

建议新增独立模块：

| 职责 | 建议放置位置 | 既有文件只做的接线 |
| --- | --- | --- |
| 增强配置/合同解析 | 独立 `pkg/seedanceenhance/` 与宿主设置文件 | 渠道保存校验、路由代际发布与配置注册 |
| 全局 MediaKit/OSS 配置 API | 新 controller/service/config 文件 | 管理 API 路由注册 |
| 渠道增强表单 | `web/src/features/channels/components/drawers/` 下新组件 | 现有抽屉“其他设置”附近注册、表单序列化接线 |
| 全局配置页 | `web/src/features/system-settings/` 下独立功能目录 | 运维设置 section registry 注册 |
| 增强模型价格元数据 | 独立增强合同与既有定价入口的连接 | 完整 schema/示例的注册或解析接线 |

具体文件名在 P0 完成后落实，不能为了“复用”重构上游热点文件。若确需改 `relaykit` 公开 DTO，先说明本地扩展不足并保留模块独立性。

完成要求：

- 开关只对确认供应商和 2.0/2.5 生效；候选模型、别名预览和实际路由由同一合同派生。
- 按方案验证 54/45、绑定 doubao 的 61，以及绑定 doubao 扩展的 60 四种载体；类型匹配不能替代供应商与基础模型合同检查。runyyitd 的实际载体待其合同核实，不以名称猜测。
- 原模型、其他供应商、分组权限和 Token 模型限制保持既有行为；增强模型单独检查授权。
- 新建、编辑、批量更新及关闭开关均不覆盖其他 channel setting；已有任务不随配置编辑重解释。
- 可保存未就绪草稿；就绪状态与服务端提交检查一致，不靠前端按钮代替约束。
- 全局秘密值不回显；凭据读写、管理员权限与 CSRF 控制经服务端验证，操作日志不含可用秘密。
- OSS 只提供连接、对象读写和测试所需配置；不自动修改现有 Bucket 生命周期。
- 复用现有设置布局、保存交互、PasswordInput、LoadingState、ErrorState 等；没有能力缺口不另造同类组件。新增 UI 文案只维护 en/zh，动 locale 前读取 i18n skill。

### P2：持久状态、生成与存储阶段

建议新增独立增强执行表、尝试表及模型文件，按方案保存可恢复状态和对象引用。通过唯一约束与 CAS 固定一条公开任务和最多三次增强尝试；网络请求不占用长事务。

完成要求：

- 提交时固定生成渠道、基础模型、目标规格、增强合同、配置引用与价格快照。
- 复用既有生成驱动发送 720p 原片请求，并保留真实生成用量；不写死推测的 runyyitd 协议。
- 原片通过服务端授权方式下载、流式上传私有 OSS，不向 MediaKit 暴露渠道 Key。
- 重启/多实例能够恢复 generating/source_storing 阶段，既不重新生成也不遗失原片。
- 客户查询/列表/下载在此阶段不返回原片；公开状态仍为处理中。
- 提前完成本阶段涉及的真实数据库矩阵，不能到全部功能结束才发现迁移不兼容。

### P3：MediaKit 增强、恢复与最终交付

新增独立 MediaKit HTTP 客户端和增强阶段驱动，使用官方异步接口及同一轮尝试的稳定 `client_token`。

完成要求：

- `resolution=1080p/2k` 只控制最终增强；最终值不能覆盖原片生成规格。未传参数按方案建议默认 1080p。
- 第一次明确失败后，最多新建第二、第三次增强；成功即停止。同一原片不变。
- 提交结果未知先恢复既有尝试，不因轮询次数或网络超时就新建上游任务；各次幂等键在发请求前持久化。
- 原片读取、OSS 上传和增强尝试分别处理可恢复错误；存储失败不消耗真正的增强尝试次数，不重新运行已成功增强。
- 成片写入 OSS 后才能公开成功；普通任务 API 只显示最终成片。Metadata、Responses 文本、content、artifacts 与列表不能漏出原片。
- 全部尝试失败或整体不可恢复时，报告安全、可定位的最终原因；内部保留每次上游请求 ID 和错误信息。
- 取消/删除/草稿等特殊请求必须有明确支持边界。不能用原片生成任务的 DELETE 冒充取消 MediaKit；不能可靠执行时返回能力错误。

### P4：计价与正式结算接线

计价依据统一见方案“如何计价”，不增加另一份动态附加费配置或裸写余额逻辑。

- 注册增强专用计量 schema、完整表达式和显示用量示例；字段标签符合 numeric“计费主体 + 单价”的插件约定。
- 增强价格缺失时提交前拒绝，不能降级到原模型价；明确零价须保留。
- 预扣一次组合服务的估算金额，冻结表达式与计价上下文；自动时长等情况有已验证上界，否则明确拒绝，不能零估算放行。
- 客户只按成功交付成片的秒数及合同价档结算，不再拆收生成 tokens；时长与 fps/分辨率从可信成功结果校验，不按用户声明或默认估算伪造实际用量。按官方毫秒粒度保存真实成片时长，并以毫秒除以 1000 得到小数秒，同步到估算、结算与日志；保留原始回包，不能先向上取整为整秒。
- 原片 tokens、原片规格、各次增强用量和实付成本仅用于内部成本核算，供应商真实计量单位与客户按秒合同分开记录。
- 客户不为第二、第三次尝试额外付费；平台成本仍记录每次真实发生的用量及对账状态。
- 原片完成不触发普通模型成功扣费；最终交付成功才沿既有 task settlement 收尾。
- 缺少可信成片时长或价档时，增强模型使用 `usage_pending` 等待对账；仅缺原片 tokens 不阻塞客户结算，内部成本单独对账。普通模型原对账不变；最终失败仍全额退款。
- 消费日志复用预扣、差额补扣、退款流水，用公开 task ID 关联，详情展示成片计费时长、综合秒价、生效折扣与最终净消费，不将流水变化量重复当成服务总价。退款完成前不显示“已退还”。
- 客户公开字段不含生成 tokens、原片 URL、尝试次数和内部错误；管理员/root 诊断按现有权限在后端投影，检查 usage_facts、Content、表达式详情与任务响应各出口。
- 对最终失败、重复回调、轮询竞争、重启和迟到结果验证 journal 幂等、钱包/订阅与 Token 额度一致、任务 quota 归零。
- 使用 checked quota 转换和既有饱和审计，边界检查覆盖 metadata、multipart、参数覆盖与映射后的实际字段。

### P5：回归、真实服务验证与发布

后端优先扩展现有合适测试，按可观察合同组织，不因跨层而散建测试文件。若确需新文件，集中到至多一个新的后端回归文件；不要在 controller/service/setting 分别复制 fixture。新写 Go 测试使用 testify require/assert。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 普通模型、非范围供应商、1.0/1.5 | 无新增增强行为，原合同不变 |
| 2.0 标准/fast/mini 与 2.5 | 目标别名正确，生成仍为正确基础模型 |
| 最终 1080p / 2K | 生成与增强分辨率分别固定，计价条件无混用 |
| 首次成功与第三次成功 | 相同成片秒数与规格对应相同客户金额，不叠加 tokens 或重试费用 |
| 不同生成 tokens、相同成片与价档 | 客户金额相同，内部成本可不同 |
| 小数秒与金额精度 | 10.2 秒按 10.2 秒、10.234 秒按 10.234 秒计费，不进位到整秒/整分钟；显示舍入不反向决定收费 |
| 生成 tokens 缺失、成片计量可信 | 客户正常按秒结算，内部成本等待对账 |
| 消费、差额与退款日志 | 同 task ID 可对账，最终净消费正确，客户看不到内部用量和重试 |
| 三次失败 | 最终失败、全额退款、原片仅内部可见 |
| 并发 poll、重复通知、重启 | 不重复生成、增强、结算或退款 |
| 增强提交结果未知 | 恢复同一上游任务，不额外消耗次数 |
| 原片/成片 OSS 上传失败 | 只恢复存储，不重复生成或增强 |
| 已退款后收到迟到成功 | 不重新扣费，不恢复终态，不启动额外尝试 |
| schema 选择、模型映射及价格改动 | 新增增强字段可保存/预览/执行，进行中任务仍用旧快照 |
| 缺价、缺凭据、OSS 不可用 | 在付费上游工作开始前给出明确拒绝 |
| 用量缺失、异常、越界或 NaN | 不当作实际结算，不产生负收费，按现有规则对账/审计 |
| 三个客户入口与全部结果投影 | 状态一致，原片和内部尝试不泄漏 |
| 非管理员访问配置、跨用户下载 | 服务端拒绝，秘密值与对象均不可越权取得 |

前端在相应功能的 `__tests__/` 内覆盖开关、供应商/模型限制、别名预览、缺配置状态、保存失败、锁定与中英文切换。文本简图不代替真实界面的键盘和窄屏验证。

## 数据库兼容性验证矩阵

新增持久状态及迁移必须在真实 SQLite、MySQL ≥5.7.8、PostgreSQL ≥9.6 上验证。若所用 SQL 或 driver 行为涉及最低版本能力，追加最低版本覆盖。不是 mocks 或 Go build 能替代的检查。

每个数据库均执行：

1. 记录实际数据库版本及完整执行命令，DSN/密码从秘密配置读取，不写入文档或日志。
2. 空库首次启动迁移，核对新表、唯一约束和查询索引。
3. 用实施时最新发布版创建含代表数据的旧库，再升级到新代码。
4. 至少再启动/迁移一次，证明幂等，已有任务、渠道设置、余额、订阅及账务 journal 保持完整。
5. 在同一后端回归 fixture 中验证并发 CAS、恢复及退款唯一性，而不是为每个 dialect 重写断言。
6. 涉及共享日志写入路径时覆盖独立 log database 配置；若受影响路径实际使用 ClickHouse，也要单列相应验证结果。

三库验证已执行，实际版本、升级基线、独立日志数据库和结果见文末记录。真实上游验证仍待配置凭据后执行。

真实服务先在火山官方以最小样例验证权限和单次增强，再验证四类基础模型的组合；记录实际 model ID、源/目标宽高、fps、时长、音轨、处理耗时、usage 与实付账单。runyyitd 单独记录其合同和回包证据。未取得可读取凭据前不得声称实测完成。

## 发布与回退

先发布默认关闭的全局功能与渠道开关，用户配置 MediaKit、OSS 和增强模型完整价格后，再逐个渠道开放。发布顺序先官方小流量，再 runyyitd；不通过配置删除其他供应商原有普通模型。

出现问题时关闭新增入口，保留新表、既有任务执行器、对象引用及结算恢复任务，让在途任务完成或安全退款。不能直接回退到不认识新阶段的旧 worker，让已生成原片被当成增强完成；也不能通过删除表或 OSS 对象回退。

后台普通配置修改不影响已固定任务合同。数据库回滚与凭据轮换单独设计，不使用破坏性脚本作为功能关闭手段。
