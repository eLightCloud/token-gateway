# 组织账单性能与账务完整性优化方案

> 2026-10-17 来源核查修正：用户 105 的资金来源实际存在于 `logs.id=23070` 的旧 `user.quota_override` 日志，原加额筛选漏掉了它。本文 2.3/2.4 的“未找到来源”和相关“独立数据缺口”描述是修复前的有限核查结果，不能作为当前根因。历史修复与验收记录见[完整修复方案附录 A](./2026-10-17-组织账单历史调额兼容修复方案.md)。

> 文档定位：本文保留原性能工作包、诊断基线与实施验收记录，不再独立定义新修复的业务口径。当前完整方案及实施交付统一见[组织账单实际消费汇总与加载修复方案](./2026-10-17-组织账单历史调额兼容修复方案.md)：第 3 节区分费用确认、资金处理和独立余额核验，4.1 明确分类守恒、业务反向覆盖、确认入口及原归属关联，4.2–4.3 定义消费/钱包两侧日缓存及 1430 万规模边界，第 5–6 节定义历史处置及验收。不预设新增任务事实表或全量消费账本；本文已有性能机制可复用，但旧金额等价和钱包阻断不作为新对账结果的验收合同。版本 9 已实施并完成开发环境验证，当前交付、降级与上线门槛统一见完整方案第 7 节；线上索引和生产规模仍未验收。

## 1. 问题与目标

组织页 `/admin/organizations/1` 的账单在数据量大时生成失败。线上已有 8 月构建超过应用 60 秒期限的证据；本地 9 月、10 月则在历史期初初始化阶段因旧覆盖调额日志未识别而失败（2026-10-17 已补充核查，见下方修正）。两种原因分别处理，不把它们合并为同一个性能故障。

本性能专项的原始目标是保留 new-api 已有账单计算口径，让有效数据下的大账期即使计算较慢也能最终完成，并且后续查询直接读取缓存。后续发现退款未抵扣模型消费基数，不能继续把保持旧错误结果当作优化目标；消费修正、查看与确认边界以当前完整方案第 3 节为准，定价和分类系数算法继续复用。

### 1.1 用户已确认的要求

| 要求 | 本方案的落实边界 |
| --- | --- |
| 可以接受生成较慢，重点是能查询到结果 | 首次或失效重建在后台执行，分片保存进度；页面不因整期超过 60 秒就永久失败 |
| 月中用于核对，月结束后使用整月账单结算 | 当月默认读取月初至昨天的累计快照；历史月份读取整月结果 |
| 月中每天更新一次、截至昨天可以接受 | 默认以北京时间完整自然日为截止，显示实际覆盖日期和生成状态 |
| 当前账单逻辑已有，目标是解决大数据量加载出错 | 未受已知缺陷影响的规则继续等价；退款基数修正按独立核验的最终费用验收，不保留旧错误金额 |

讨论中提到的管理员手动确认、已结算金额保留及后续差额调整仅作为使用背景和边界；不据此认定代码已经具有锁账能力，也不在本次新增或重构确认结算、锁账、跨期调账功能。

### 1.2 核心技术方向与非目标

首批采用“固定截止累计快照＋后台可恢复生成＋只读缓存查询”。固定截止缓存减少重复计算，时间分片、有界读取和租约解决首次计算可能超时或内存失控的问题，二者不能相互替代。

本方案在设计上覆盖目前已知失效链，尚未证明生产问题已经解决。首批必须同时验收数据库侧超时隔离、历史依赖自动推进、日期接口一致性、来源覆盖测量和中间片清理；不能只以任务能够入队或页面命中一次缓存作为完成依据。

原性能专项允许每日累计重算作为较小实现。1430 万以上且持续写入的环境，当前建议消费和钱包分项均优先补跨快照日缓存，现有绑定 summary_id/revision 的用量片并不自动具备此能力。累计重算仅在完整方案 6.2 的各阶段预算及每日窗口对照通过时采用；不能只验用量加速，忽略钱包回放、旧调额和历史结转。缓存只保存派生计算结果，不增加扣费或退款权威。

新方案区分可靠消费、未知费用及钱包核对异常：钱包缺口不阻断可靠消费查看，未知费用不补零、不冒充完整账单；钱包异常仍留存处置。不无限重试、不伪造入账、不置零期初，具体发布条件只在当前完整方案第 3 节定义。

### 1.3 状态、环境与证据边界

- 主体实现及本轮评审修复已落地于未提交工作区，当前计算版本为 10（见独立修复方案第 7.6–7.7 节）；性能专项验证时的版本 6、历史调额修复时的版本 7 仅为历史证据；隔离 fixture、真实三库及专项恢复验证已有通过记录，见 7.5。生产规模、线上历史重建和灰度尚未验收，因此本文仍为 draft。
- 源码核对基线为 `ea7f21e8c` 及 2026-10-16 工作区；其他未提交改动不归为本方案产物。
- 线上证据由用户提供，本轮未直连生产；附件中猜测的 SQL 与真实查询结果区分使用。
- 本地默认排查库为 PostgreSQL `127.0.0.1:53702/oneapi_import_verified`，版本 16.15，连接秘密不写入文档。
- 本地组织 1 是获授权创建的 76 名启用普通账户测试组织，计费起点为北京时间 2026-04-01，与线上中关村学院成员映射不同。
- 优化范围是账单读取和派生结果，不新增钱包扣费、退款、资金补记或 relay 结算入口。

构建日志中的 `/build/model/organization_invoice_aggregate_batch.go:72` 表明错误发生在消费聚合调用处。基线处理与聚合共用 60 秒 context，因此不能认定这条 SQL 自身独占了完整 60 秒。

### 2.2 线上采集解释与源码差异

| 采集附件中的判断 | 当前源码事实 | 处理要求 |
| --- | --- | --- |
| 逐用户聚合，没有成员 OR | 每批最多 100 段成员关系，拼接 OR 和各自时间边界 | 核对线上构建身份，捕获真实 SQL；二进制片段缺失不能证明没有 OR |
| 聚合不限制 type | 显式 `type = LogTypeConsume`，数值为 2 | 无类型过滤的试验 SQL 不能直接用于选索引 |
| 月份推测为 to_char/to_timestamp | 参数化 CASE，月份键为整数 YYYYMM | 不替换为依赖会话时区的日期函数 |
| 当前成员集合等同于账期成员 | 同时读取历史成员，使用 BillingStartAt 和 LeftAt | 仅筛选 left_at=0 的试验不等价 |
| revision 44 表示 44 次成员变更 | revision 在重新领取构建时递增，失效本身不递增 | 不从 revision 反推成员变更次数 |
| 固定 274 字节 HTTP 200 是错误体 | 生成中的占位账单也返回 HTTP 200 | 依据 success、generation_status、message 判断 |
| 计划中的并行、哈希分区表示已实际执行 | 普通 EXPLAIN 是估算和计划 | 不宣称已经并行、磁盘溢写或扫描了某个实际行数 |

聚合代码见 [成员批量聚合](../../model/organization_invoice_aggregate_batch.go)，月份表达式见 [账单计算](../../model/organization_invoice.go)。实际 SQL 的月份表达式、成员边界、类型和账期必须全部对齐，才能进行有效对比。[PostgreSQL EXPLAIN 说明](https://www.postgresql.org/docs/18/using-explain.html)

用户通过 pg_index 补证的结构差异是：线上 `idx_created_at_id` 为 `(id,created_at)`，当前 [Log 模型](../../model/log.go) 的 priority 定义为 `(created_at,id)`；另外两个被核对的索引列序一致。这是已由线上反馈确认的结构漂移，本轮未独立连接生产重查。具体发生于旧版本建库、迁移还是历史操作尚无证据，不臆测原因。纠正流程及验收见 5.4.1–5.4.3，不再仅作为一般索引候选处理。

日志捕获到的真实查询形态为 `SELECT user_id,created_at,type,quota,billing_source,other FROM logs WHERE user_id IN (...) AND created_at >= ... AND created_at < ... AND type IN (...)`；日志将参数记录为占位符。按当前成员和截止 10/1 的基线历史条件只读计数，结果同为 139,015 行。

这次路径是“10 月请求 → 尚无基线 → 读取 10/1 之前的历史资金事实 → 推导期初失败”，尚未进入后续模型用量聚合。它不是线上“已有 8 月基线 → 8 月汇总聚合超时”的复现，也没有捕获到该线上消费聚合 SQL。

用户 105 的来源核查结果：

- 8 月 14 条钱包消费，377,418 quota；9 月 2 条钱包消费，109,027 quota；10/1 之前合计 486,445 quota。
- 16 条均由旧 JSON 识别为 wallet，没有退款；结构化 billing_source 为 NULL。
- 充值、结构化调额、旧调额事实、签到、已使用兑换及订阅订单中均无该用户记录；对同期全站 75 条旧调额候选解析后，没有目标为用户 105 的记录。
- 只有一段组织成员关系，计费起点为 4/1；按现有唯一归属规则，这些资金事实都归该组织。可识别流入为 0，推导期初为 -486,445，因此代码拒绝建立基线。
- 当前 quota=49,513,555、used_quota=486,445，算术合计为 50,000,000；这与未记录的初始资金相容，但不能据此认定初始额度来源、入账时间或补写历史事实。

本地修复前置是取得有依据的历史资金事实或经核验的基线快照。可在隔离测试 fixture 中建立明确的初始入账验证完整链路，但不能把它当成真实资金修复，更不能直接回写当前默认样本来绕过校验。性能优化仍应实施有界读取：此次近 14 万条历史读取已证明用户选择一个月，后台可能加载此前多月数据。

用户随后补充已触发 9 月，实际日志确认 23:12:40 请求、23:12:42 轮询；汇总 #1 在 23:12:41 变为 failed，revision 从 1 增至 2，仍为用户 105 负期初。该次历史钱包查询读取 45,978 条，耗时 279.593 ms；对应 other 为 42,919,471 字节。截止 9/1，用户 105 有 14 条消费、377,418 quota，推导期初为 -377,418。两个月均约一秒内在无基线的历史资金推导阶段失败，不能用本地这两次操作证明线上聚合超时；9 月期初与 10 月期初也不能混用。

### 2.5 优化前调用链与故障放大

当前链路为“页面请求 → 逐月检查历史 → 领取首个未就绪汇总 → 内存队列 → 单 worker → 基线处理 → 消费聚合 → 钱包等资金事实 → 完整性检查 → 条件发布”。

- 历史依赖：从基线逐月检查，遇到首个未就绪月份立即返回，因此 8 月失败能够阻塞 9 月、10 月。线上基线已由用户确认是 202608；本地尚无基线，必须区分两条路径。
- 调度：每次请求最多触发一个依赖月份；worker 完成后不主动推进下一月。后续推进依赖再次请求，用户离开页面可能中断整条恢复链的推进。
- 执行：已有异步生成，内存队列长度 32、每进程单 worker；持久状态不能保证排队任务在重启后继续执行。
- 期限：基线与账单计算共用 60 秒；building 两分钟未更新可被重领，目前没有运行中心跳。只增加构建期限可能令旧结果因 revision 已变化而无法发布。
- 资源：消费按成员批次查询后，钱包再次读取整期消费/退款和 other；首次基线还可能追溯多年历史。
- 重复工作：缓存读取也尝试插入、加写锁；历史结转读取完整账单 JSON；旧调额每次解析全站候选管理日志。
- 发布：任一账户财务状态 incomplete 都阻止正式发布，不能删除该检查来消除错误。

## 3. 优化前查询机制与必须保留的计算口径

当前是“缓存汇总＋按需异步生成＋部分实时读取”，不是每次页面请求都全量实时计算：

| 路径 | 当前行为 | 当前限制 |
| --- | --- | --- |
| ready 缓存有效 | 解码已有账单，组合后返回 | Prepare 仍尝试插入并加写锁，服务还检查历史月份 |
| 缺失、失效、明确刷新 | 内存队列异步构建 | 单次 60 秒、单 worker、重启恢复及心跳不足 |
| 当月初次/刷新生成 | SourceAsOf 截止任务启动时间 | 截止随触发时间变化，不是固定截至昨天 |
| 同月再次查询 | 有效 ready 可继续复用 | 没有按天推进截止的机制，缓存命中不等于数据已更新 |
| 当前余额 | 查询/导出时单独读取用户 quota | 与历史期末是不同含义，保留现有字段和行为 |

当前代码依据：[生成服务](../../service/organization_invoice_summary.go)、[缓存领取](../../model/organization_invoice_summary.go)、[当前余额刷新](../../model/organization_invoice_current_balances.go)。

需要明确：现有缓存已能复用，唯一范围为组织、请求账期和计算版本，SourceAsOf 不在唯一键中。“重建截止随时间变化”不等于“每次请求缓存键都变化”。固定截止方案主要补足按天推进覆盖范围和数据新鲜度的规则，同时优化命中路径，不把它描述为首次引入账单缓存。

## 4. 优化方案：固定截止快照与读取流程

### 4.1 日期范围和截止时间

默认按以下方式请求现有计算器，不改变原金额算法：

| 场景 | 默认实际计算范围 | 展示与边界 |
| --- | --- | --- |
| 2026-10-16 查看本月 | 10/1 00:00 至 10/16 00:00 前，即截至 10/15 | 显示“数据截至 10/15”，不是截至当前时刻 |
| 2026-11-01 查看 10 月 | 10/1 至 11/1 前的完整月份 | ready 仅代表计算成功，不代表管理员已确认结算 |
| 查看历史月份 | 该月完整范围 | 复用有效整月缓存，按现有失效规则必要重建 |
| 每月 1 日查看当月 | 当月还没有完整自然日 | 显示明确说明并提供现有上月入口，不构造结束早于开始的范围，不伪造零金额账单 |
| 自定义范围 | 保留原显式起止日期及现有计算语义 | 默认策略不静默改写已有自定义请求；同一标准范围可复用相同快照 |

内部建议统一半开区间 `[start,endExclusive)`，日期展示仍采用现有格式。调度触发时冻结该任务的实际范围，跨午夜或重试不自动扩大截止；新一天由新范围的任务处理。

默认日快照应使用真实覆盖的 EndDate/EndTimestamp 调用既有计算逻辑，不能只裁剪日志查询却保留未来月底 EndDate，导致仍以当月实时余额校验历史截止值。历史期末和 CurrentBalanceAmountUSD 沿用原含义，当前余额继续独立刷新；技术字段 Finalized 不充当人工结算状态。

这不认定原实时当月查询的余额分支本身错误。原语义下展示当前钱包余额有既有用途；日快照选择了过去完整日期范围，应使用对应截止的计算分支。原性能对照采用相同 10/1–10/15 范围，不与旧 10/1–10/31 的实时结果混比；新费用口径另外依完整方案第 6 节独立验证，不以该旧对照证明金额正确。

快照截止昨天是新的默认数据时效策略，不证明昨天的所有事实已经入库。迟到记录与历史更正仍需失效重建，见 4.5。

#### 4.1.1 Period 与接口日期合同

首版优先让默认页面直接请求真实覆盖范围，例如 start_date=2026-10-01、end_date=2026-10-15；请求、计算、缓存及响应 Period 使用同一范围，避免为默认路径无条件增加两套账期字段。

| 返回场景 | 日期合同 |
| --- | --- |
| 默认快照已完成 | Period 为实际覆盖的 10/1–10/15；StartDate/EndDate 与时间戳一致；SourceAsOf 不超过范围终点 |
| 默认快照生成中、尚无账单数据 | Period 表示目标快照范围；若实际先处理 8 月依赖，阻塞月份作为任务信息另行表达，不能将 8 月误当成所请求账期 |
| 展示更早的有效快照 | 账单 Period 跟随旧结果真实范围，例如 10/1–10/14；目标 10/1–10/15 和生成状态单独表达，不能给旧数据贴上新截止标签 |
| CSV 导出 | 标题、账期行、数据范围和所读取快照一致，不显示 10/31 却只导出截至 10/15 的默认快照 |
| 旧自定义当前月请求 | 保留原显式日期和 Period/SourceAsOf 合同，不静默转成默认日快照，也不能与不同实际截止的日快照混用缓存 |

若实施选择继续以整月请求表示默认日快照，必须明确请求范围和实际覆盖范围的独立字段、前端及 CSV 行为，并完成接口兼容验证；不能仅在后端修改 Period 或只改展示文字。生成中、完成、回退读取、跨午夜和导出均按上述合同验收。

### 4.2 缓存范围、版本与读取

复用现有 organization_invoice_period_summaries 作为完整结果缓存，组织、实际起止日期和 calculation_version 是基础唯一范围。成员归属、结算规则和基线依赖的有效性沿用现有规则；若增加内部依赖标识，须验证对应失效与发布保护。

同一天重复请求同一范围优先只读命中，不先 INSERT ON CONFLICT、不锁 ready 行、不解码全部历史模型矩阵。命中后仅执行所需组合和既有当前余额刷新。

区分三种时间信息：实际覆盖截止、生成完成时间、当前余额读取时间。不得用任务执行时间冒充数据覆盖时间。现有 SourceAsOf 与 Period 能准确表达时优先复用，确需新增字段再做接口兼容验证。

不要只给当前整月 key 加一个 24 小时 TTL：TTL 不能表示结果到底覆盖到哪天，也不能保证日期推进。按实际覆盖范围识别快照，日任务生成新截止的结果。

### 4.3 生成状态与查询体验

1. 首次或失效查询只登记持久工作并返回 generating；页面显示正在处理的账期、阶段与进度，不等待一个长 HTTP 请求。
2. 状态轮询只读任务状态，不领取新代次、不触发重新计算、不加载完整 payload。
3. 完成后原子发布完整 ready 快照，后续请求直接读取。
4. 昨天的新快照尚在生成时，可以显示仍有效的更早截止结果，但显著标明其实际日期和更新中状态；不能冒充已覆盖昨天。
5. 已因事实或规则更正失效的旧结果，不能继续作为当前有效账单或正式导出结果。生成失败保留明确阶段和原因，区分可重试故障与需补数据的缺口。

保留现有 generation_status 和金额字段；新增任务字段/接口需兼容测试。页面文案、日期默认值和状态展示是最小必要前端接线，复用已有组件和 i18n，仅维护 en/zh。

### 4.4 每日生成和整月衔接

每日低峰在上游结算与日志回写有足够时间后，触发“月初至昨天”的目标快照；具体时刻和完成期限按实际写入延迟与构建耗时确定，不预设凌晨某时必须已完成。

先灰度组织 1，再扩展到确有账单需求的组织，避免上线即扫描全站全部月份。重复调度同范围、同版本只产生一个有效生成任务；调度中断后可补任务，不补造业务事实。按需查询也可登记缺失工作，二者共用同一持久工作入口。

新一天快照是新截止结果。首版可完整重算该累计范围一次，再用分片限制每步工作并保存进度；这减少页面重复扫描，但并未消除每天重复处理月初旧数据的成本。日增量复用待测后实施，不作为首版上线前提。

次月首日可使用覆盖前月完整范围的同一快照，供既有人工核对流程使用；不新增自动确认、自动锁账或跨期调账。数据更正和已有确认流程的交互遵循当前业务流程，不能借缓存刷新改写已确认结算依据。

### 4.5 迟到数据、失效和保留

固定截止不等于永久不变。新日志带较早时间、回写滞后、退款、更正、成员计费起点和规则变化，均可能影响旧范围；按现有归属及失效规则识别并重建，不直接把“过了昨天”当成永远正确。

记录覆盖边界与可用水位，必要时回看最近范围并重建受影响任务；具体回看天数由真实迟到分布决定。时间戳或 MAX(id) 单独都不保证一致快照，不为每条消费更新一个组织热点版本行。

新代次准备期间和最终发布都要校验有效性；检查和发布之间的配置变化不能让旧结果覆盖新结果。发布保护不代替跨库迟到事实检测。

历史未变更范围继续复用，不因新增一天就清空全部月份。保留必要审计版本和用于结算的结果；仅对可重建、中间及未被依赖的派生数据制定清理策略，不随意删除源日志或原有唯一约束。

#### 4.5.1 分片与旧代次的最小清理闭环

清理属于 P1-C 必须验证的资源边界。保留天数和批次上限按恢复/审计需求及实测确定，但下列条件不能留空：

- 当前有效代次、有效租约正在处理或仍被恢复任务/快照引用的片结果必须保留；任务显示 failed 或 revision 较旧，不单独构成可删除依据。
- 已被替代、完成后不再依赖、明确放弃或孤立的中间片，只有满足保留期限且无有效引用/租约时才可回收。整份 ready 快照、结算依据、资金源事实和日志不混入片清理。
- 判定与删除之间须有并发保护，避免恢复任务刚取得引用就被清理；使用短事务/条件删除及现有锁辅助方式，不持有跨整个清理过程的长锁。
- 按有限批次清理，记录删除数、剩余量和错误，可中断续跑；不能逐次生成无限积累旧片，也不能每次启动全表删除。
- 验证运行中保护、恢复引用保护、到期回收、重复执行、孤立片及与恢复并发的情况；单独记录清理对在线数据库的影响。

## 5. 优化方案：首次计算可完成、可恢复

### 5.1 持久请求、调度、租约

已有异步生成，问题在执行和恢复能力。先持久保存组织、实际范围、计算版本、revision 和处理进度，再唤醒 worker；用户关闭页面或进程重启后仍能推进。

请求 10 月而基线从 8 月开始时，持久工作必须表达“最终需要 10 月结果”及其必要历史依赖，由后台按 8 月、9 月、目标截止推进，不能只保存本次碰巧领取的 8 月任务。可以一次登记依赖月份，也可以保存目标请求后由调度器解析依赖，不强制展开所有月份；两种实现都必须在离开页面、重启后继续，且前月失败能显示阻塞账期和原因。

优先评估已有 [SystemTask](../../model/system_task.go) 和 [runner](../../service/system_task.go)。首版以共享数据库全局一个重型账单构建为待测起点，可由一个固定类型的调度器扫描持久账单工作并公平轮转。现有类型级去重只能约束调度器，不能用不同组织 payload 调用同一类型而认为请求都已排队。

须验证 master/slave 运行角色、重启补扫、调度器退出与新请求并发的空窗、原内存 worker 与新路径互斥。旧框架不适配时再确定账单专用最小状态，避免先扩展通用队列。

将排队等待、单片期限、租约及整任务期限分开。用户接受慢，整任务可以超过 60 秒，但不无限占用连接、长事务或挂死。任务运行中心跳续租，失去租约取消旧执行；保留 revision 条件发布，心跳不扩大实际数据截止。

“把 60 秒改成五分钟”不能单独上线：当前 building 两分钟未更新就可重领，需要同时修正心跳与过期判断。参数在测量后确定，不能把任意分钟数作为已确认 SLA。

#### 5.1.1 依赖推进与执行先后

P1-A 先具备持久目标、领取互斥、心跳/租约与恢复，再允许长于旧期限的分片长跑。可以先开发分片代码，但不能在没有有效租约保护时放大线上执行期限。

前月完成后由后台推进下一依赖，不等待新页面请求；前月暂时故障重试已有片，确定性数据缺口明确阻塞该目标，不阻塞其他无依赖组织。相同前月被多个目标引用时只安排一个有效工作，目标进度与依赖进度区分，引用也受 4.5.1 清理保护。

#### 5.1.2 数据库侧兜底超时与连接隔离

应用 context、租约和单片预算是主要控制，再对重型 SQL 增加数据库侧兜底。PostgreSQL statement_timeout 限制服务器执行单条语句，必要时另设锁等待限制；它不是整账期期限，也不覆盖 Go 中的解析/合并。任务可由多片组成并运行数分钟，不能重新用全局 60 秒 SQL 期限代替恢复设计。[PostgreSQL 超时说明](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-STATEMENT-TIMEOUT)

当前 LOG_SQL_DSN 为空时 LOG_DB 直接指向主库 DB。不得未经隔离就修改通用账号、全库或共享池的会话参数，误伤网关查询、钱包写入及其他任务。实施可比较独立且有连接上限的构建读取连接与每片短事务内的 SET LOCAL；不要求先增加新的数据库角色。

设置必须与重型 SQL 在同一实际连接/事务上生效。不能先通过连接池 Exec SET，再假定后续 Query 会取得同一连接；也不能只设置主库事务，而日志 SQL 在另一连接执行。采用 SET LOCAL 时放在短事务内，提交/回滚后恢复；普通会话 SET 不得泄漏给后续网关请求。[PostgreSQL SET](https://www.postgresql.org/docs/18/sql-set.html)、[Go 连接管理](https://go.dev/doc/database/manage-connections)

参数以单片正常执行、取消和回滚的余量确定，记录应用单片期限、数据库语句期限、锁等待和总任务期限的配合关系，不预设任意数值。SQL 超时后取消当前片、回滚并恢复有限重试；确认数据库语句已停止、连接可恢复或被丢弃，才能视为释放资源。

各数据库按能力配置并验证，不能向 MySQL、SQLite 或 ClickHouse 发送 PostgreSQL 参数，也不能用只限制锁等待的参数冒充 SQL 执行期限；不具备同等机制的路径须明确并验证 context/驱动取消和资源回收边界。生产版支持的较新超时参数不能无分支用于最低支持版本。

### 5.2 消费用量按时间分片

100 个成员一批不能约束单用户几百万行。按北京时间自然日作为初始时间片，热点片再拆小时；每片与各成员有效窗口取交集，保留历史关系、离组排他边界和零消费账户。

每片保存账户、模型、月份、原始 quota、请求数及负值检测信息。片结果和完成标记在主库同一短事务提交，使用稳定片标识和 revision/持有者保护；重试不重复累加，拆片后父片不参与最终合并。

冻结任务范围和必要依赖，不跨整个构建持有长事务。保留已完成且仍有效的片结果，失败只恢复未完成工作；跨 revision 复用需要验证数据依赖，不能简单改写代次。

最终按原月份合并 quota，再应用既有分类系数与 decimal 算法，不能先按天舍入金额再求和。单片仍扫描过多时需配合访问路径优化，不能声称只拆循环就已解决超时。

### 5.3 钱包、旧数据与基线有界读取

将整期 Find(&walletFacts) 改为分片内 Rows 流式累计，或有稳定游标的有限批次；正确处理 NULL、游标关闭、rows.Err()、取消及重试，禁止 OFFSET 深分页。

结构化来源明确时不读取大型 other，需回退解析的旧记录单独有界读取，保证两条路径不漏不重。资金归属继续使用原唯一归属规则，不能直接复用消费成员窗口。

明确来源且归属等价范围已验证时，可评估数据库内聚合，只返回账户结果；否则先维持原判断逐行累计。负消费、退款符号、未知来源和整数溢出保护不变。不为合并扫描而把原本 SQL 聚合的模型明细全传入 Go。

基线与当期计算拆成可恢复执行阶段，保持相同校验、相同资金事实和原历史依赖，不改变业务结果。没有可信期初仍返回明确数据错误；不要求本次新增资金快照业务或人工补款功能。稀疏历史按实际范围分段，避免从 1970 年机械创建海量空片。

本地 9/10 月用户 105 的旧覆盖日志漏识别，按独立历史调额方案修复；该故障与性能问题分别验收。性能测试可分别测现有数据的读取阶段，以及使用资金完整 fixture 的完整生成链路；不能通过修改默认数据库的余额或入账来制造成功。

#### 5.3.1 结构化来源覆盖核验前移至 P1-C

不必将全部历史来源回填提前到首批，但首批必须知道免读 other 的实际收益边界。RecordTaskBillingLog 写 BillingSource，旧 RecordConsumeLog 没有赋值且仍有任务/Midjourney 调用路径，因此不能假定所有新消费都已结构化。结构化比例仅表示字段已填写，不代表资金来源已经审计：旧入口的空来源默认 wallet 在优化前已经存在，历史默认值需独立核验。本轮让已知 journal 来源随日志持久化，并在旧 outbox 重放时沿用 journal 来源；不批量修改已写入的历史日志。

对真实构建覆盖范围记录：消费/退款候选数、结构化来源数及比例、空/未知来源数、旧 JSON 回退条数、读取的 other 字节量和解析耗时。尽量在正常分片处理时累计，避免为统计覆盖率额外重扫全表。

核对仍写空的入口及其实际业务来源；不能统一补 wallet 来凑覆盖率。旧路径兜底保留，结果与原解释一致。P1-C 交付入口清单与覆盖测量，实际写入修复和大规模回填若涉及语义/迁移继续按范围放入 P2，不将“收益有限”误判为“金额错误”。

### 5.4 查询与索引

以真实应用 SQL 决策：消费有 type=2 和成员 OR 窗口，候选优先比较 (user_id,type,created_at) 与 (user_id,created_at)，同时评估已有 (created_at,type) 对时间片的访问效果。增加明确外层时间范围，窗口一致的账户可合并 IN，不同窗口不粗略合并，重叠关系不重复累计。

本地已存在用户/类型/时间联合索引，不能重复添加。线上 idx_created_at_id 列序漂移核验后通过独立部署修正或替换，不假定 AutoMigrate 自动重排；不删除仍被其他路径使用的索引，也不一次创建所有候选。

组织 1 占该月平台约 99.7%，顺序扫描不必然错误。验收比较实际时间、数据页、内存和传输，不强制 Index Scan，不把 other 加入大覆盖索引。大表建索引与应用启动分开，验证锁、资源、空间和失败恢复；三库均有可用路径。

#### 5.4.1 已确认列序漂移及实际影响

| 索引 | 用户线上 pg_index 实测 | 当前源码期望 | 处置 |
| --- | --- | --- | --- |
| idx_created_at_id | `(id,created_at)` | `(created_at,id)` | 独立修复列序漂移，并检查影响该索引的其他日志查询 |
| idx_created_at_type | `(created_at,type)` | `(created_at,type)` | 已匹配，不为本次问题重复重建 |
| idx_user_id_id | `(user_id,id)` | `(user_id,id)` | 已匹配；不能替代用户＋时间索引 |

源码位于 model/log.go:60–63，created_at 的 priority 为 1，id 为 2。以近乎唯一 id 为前导的索引，无法像预期的 `(created_at,id)` 一样高效支撑仅由时间范围驱动的扫描及同时间下按 id 排序。除了账单，还需回归日志列表中的时间过滤与 created_at/id 倒序，以及按时间清理路径。

但不能将其解释为“所有时间查询完全无法用索引，所以聚合只能全表扫描”：已有 `(created_at,type)` 本身具有时间前导列；PostgreSQL 18 对部分后列约束还可能在索引内过滤或进行 skip scan，收益取决于前列分布。需要处理当月大部分数据时，顺序扫描仍可能更便宜。[PostgreSQL 18 复合索引说明](https://www.postgresql.org/docs/18/indexes-multicolumn.html)

必须分清两件事：修复 `(created_at,id)` 恢复的是预期时间访问/排序能力；为账单筛选账户、类型和时间，仍需独立评估 `(user_id,type,created_at)` 等候选。前者不能代替后者，也不能保证整期计算进入原有 60 秒以内。

当前项目依赖 GORM v1.25.12、PostgreSQL driver v1.5.9。本机依赖源码显示，AutoMigrate 对每个索引仅在 HasIndex 为假时创建；该 driver 的 HasIndex 以 schema、表名、索引名查询 pg_indexes，不比较列序。因此本地新库建对、线上升级库保留同名反序索引可以同时存在。此机制解释漂移为何可能延续，不证明首次漂移的具体来源。

改 Go tag 后重启、同名 CREATE INDEX IF NOT EXISTS 或 REINDEX 原索引都不能作为列序修复方法：前两者不会保证替换既有定义，REINDEX 按原定义重建，不会把列顺序换过来。[CREATE INDEX 说明](https://www.postgresql.org/docs/18/sql-createindex.html)、[REINDEX 说明](https://www.postgresql.org/docs/18/sql-reindex.html)

#### 5.4.2 线上独立修复步骤（待执行）

1. 保存 schema、索引 OID、完整定义、列序、有效/可写状态、大小及相关约束；检查等价正确索引是否已存在，区分名称与结构。留存相同查询及数据范围的性能基线。
2. 若没有正确等价索引，以新临时名称创建 `(created_at,id)`。PostgreSQL 生产部署优先评估 CREATE INDEX CONCURRENTLY，不先删除旧索引，不在应用启动事务中建大索引。它不能放在事务块中，且仍需额外 CPU/IO、空间和等待，低配库避免同时进行月账单重建或多个重型建索引任务。
3. 创建结束后核对实际有序列、indisvalid、indisready 和定义，不能只看命令已提交或索引名存在。失败留下 INVALID 索引时按专用恢复步骤处理，避免 IF NOT EXISTS 将无效残留当成成功。
4. 新索引有效且查询验证完成后，在有界锁等待的独立维护步骤中评估名称切换：旧索引改备份名，新索引取得规范名；涉及多次改名时用短事务保持名称映射原子性。此步骤与前面的并发创建分开，不承诺完全无锁。
5. 暂保留旧索引以供观察与必要回退，确认其他日志路径无回退后再单独决定清理，避免永久维持重复写入开销。应用回退通常不要求删除正确索引；若必须切回名称映射，使用已留存定义和有界维护步骤。主键与 billing_operation_id 唯一索引不在本次替换范围。

并发创建比普通创建工作更多，可能留下无效索引且不能在事务块执行，以上部署要求依据 PostgreSQL 文档，不作为已执行记录。[并发建索引限制](https://www.postgresql.org/docs/18/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)

#### 5.4.3 防复发与验收

- 结构检查必须比较有序列、访问方法、唯一性、有效性及必要的谓词/包含列，不仅比较名称；主库与独立日志库分别检查。发现漂移告警并给出修复入口，不在服务启动时悄悄删建大表索引。
- 迁移用真实“同名但列序相反”旧库 fixture 验证检测、修复、重复运行和两次启动，并覆盖新库；至少覆盖实际使用的三种主库/日志方言，版本专属在线部署另验证支持边界。
- PostgreSQL 验收以 pg_index/pg_get_indexdef 的实际结构和有效状态为准；再测真实账单 SQL、日志时间排序及时间清理路径的计划/耗时/数据页，不用“必须出现 Index Scan”替代性能结果。
- 修复之后仍保持分片、有界钱包读取、可恢复任务和固定截止缓存。结构正确、查询有效、整期能完成和账务结果一致是四项独立门槛，不以其中一项替代其他项。

### 5.5 观测、取消与错误

按组织、实际范围、计算版本、revision 关联排队、基线、用量片、钱包、旧解析、组合、序列化和发布各阶段。应用记录处理行数、返回行数及分配；数据库扫描行数和数据页须来自实际测量，不能用输出行数冒充。

context 传至成员、规则、旧调额、基线及历史读取。请求只控制请求读取，后台有独立生命周期；失败状态写入使用独立有界 context，不依赖已取消的执行 context。

数据库暂时故障按有限退避恢复已有片进度；资金缺口、非法来源、负消费或溢出明确定位，事实未变化时不按 30 秒退避反复重扫。进度包含当前依赖月份和处理阶段，动态拆片后的百分比不能伪装为精确剩余时间。
