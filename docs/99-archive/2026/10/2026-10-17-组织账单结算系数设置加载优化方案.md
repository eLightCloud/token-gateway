# 组织账单结算系数设置加载优化方案

## 1. 问题与目标

管理员打开组织 1 的“结算系数设置”，长期停留在骨架加载状态。已从本地请求日志、PostgreSQL 活动查询和当前代码确认：读取设置前会逐成员同步扫描历史消费日志，属于此前账单主查询优化未覆盖的配套入口。

目标是让设置读取和保存复用小规模分类依据，不因每次打开、切换月份或保存系数重新扫描历史日志；首次准备可以较慢，但必须有明确状态、可恢复且不阻塞在线请求。同时覆盖保存后的账单刷新：仅系数变化时复用有效消费及钱包依据，重新套用现有系数计算，不重新回放全期流水。保持账单准确性和原业务边界，不改变个人消费、预扣、退款、成员归属、系数继承和版本冲突规则。

推荐方案明确为：**按成员有效范围持久化已使用的原始模型名集合，在组织层合并并归类，所选月份的系数仍读取现有规则表。** 首次后台准备，后续增量推进；不按月份重复缓存历史模型，不依靠 TTL 到期全量重算。

本文同时记录设计与当前实现，模型集合缓存、轻量重算及本轮竞态修复已落地；验证及限制见第 4、5 节。第 2 节同步全扫链路为优化前诊断基线，不是当前请求路径。账单消费及缓存口径继续以[实际消费汇总与加载修复方案](./2026-10-17-组织账单历史调额兼容修复方案.md)为准；前一轮已完成的[财务表头与口径说明优化](./2026-10-17-组织账单财务表头与口径说明优化方案.md)不代表本入口已优化。

## 2. 当前实际情况

### 2.1 本地证据

| 检查项 | 已确认结果 |
| --- | --- |
| 组织 1 成员关系 | 174 条，涉及 174 个用户 |
| 组织 1 系数记录 | 37 条；设置加载成本并非来自系数表本身 |
| 2026-10 设置读取 | 2026-10-17 22:27:48 返回 HTTP 200，耗时 `1m25.188565042s` |
| 2026-09 设置读取 | 同日 22:28:00 返回 HTTP 200，耗时 `47.598680916s` |
| 单成员模型查询 | 日志记录约 23.3 秒、8.6 秒、5.4 秒等慢查询 |
| PostgreSQL 等待 | 实际捕获到 `SELECT DISTINCT model_name FROM logs ...`，存在数据文件读取等待 |
| 账单快照 | 9 月整月及 10 月截至 16 日的版本 10 快照均为 `ready`；设置不复用其查询链路 |

两次请求都是实际观测，不是压力测试。不能将 85 秒作为每次必然耗时，也不能将 47.6 秒归因于应用缓存命中；不同月份仍走相同的历史模型发现逻辑，数据库页面缓存、并发及 IO 状态可能影响耗时。

### 2.2 代码链路

```text
打开设置 / 切换生效月份
  → GET .../invoice/settlement-rules
  → GetOrganizationSettlementRuleOptions
  → organizationUsedInvoiceCategories
  → 按成员串行查询历史日志的 DISTINCT model_name
  → 模型归类
  → 读取小规模系数表，计算所选月份的继承及版本
```

[模型发现实现](../../model/organization_invoice.go)中的 `organizationUsedInvoiceCategories` 遍历当前及历史成员，为每条有效成员关系执行独立查询。时间边界来自成员归属及计费起点；生效月份没有传入该模型发现函数，不会将历史扫描限制为所选月份。

[保存入口](../../model/organization_invoice.go)中的 `UpdateOrganizationSettlementRule` 同样先调用该函数，验证分类是否被组织使用。因此，仅优化弹窗 GET 或增加浏览器缓存，不能解决 PUT 保存前的历史扫描。

[控制器](../../controller/organization_invoice.go)没有将请求上下文传入这条发现链路；现有发现函数也未接收上下文或使用账单重查询预算。关闭弹窗或客户端停止等待不能保证数据库工作随即停止。

当前保存的分类资格检查发生在组织加锁事务之前，不能直接沿用这一顺序作为新缓存的有效性保证。[普通业务错误](../../common/gin.go)实际返回 HTTP 200、`success:false`，版本冲突在控制器中单独返回 HTTP 409；不能将普通错误合同描述为 HTTP 400。

现有[读取预算](../../model/organization_invoice_resource_budget.go)提供暂停检查和查询前延迟，不是全局并发限制器。[重查询包装](../../model/organization_invoice_heavy_query.go)提供上下文预算，并在 PostgreSQL 中以同连接事务内的 `SET LOCAL statement_timeout` 增加数据库侧保护；其他日志库不能据此宣称具有相同数据库侧超时保证。

截图骨架对应[设置组件](../../web/src/features/organizations/invoice.tsx)的 `rulesQuery.isLoading`。请求最终成功前，前端没有数据可以展示；本次已观察到成功响应，不能将骨架本身理解为权限失败或账单生成失败。

### 2.3 是否每次都会这么慢

**每个真正到达后端的设置读取请求，目前都会重新执行历史模型发现；耗时不固定，但重复重查询确实存在。** 后端没有对该集合做业务缓存。

前端已有 React Query 内存缓存，不能据此认为打开必然重新等待 85 秒，也不能认为重查询问题已经解决：

| 操作 | 当前行为 |
| --- | --- |
| 相同页面、组织、登录用户和月份，成功结果仍在 10 秒新鲜期内重新打开 | 可直接复用浏览器内存中的结果，通常不触发新请求 |
| 相同条件，结果已过新鲜期后重新打开 | 通常先显示旧结果，再后台请求；请求仍可能扫描历史，不一定再次显示骨架 |
| 停留页面超过 10 秒但不进行操作 | `staleTime` 只标记结果过期，不是每 10 秒自动轮询 |
| 切换尚未缓存的生效月份 | 查询 key 改变，触发请求；月份不同仍重复发现相同历史模型集合 |
| 刷新页面、新浏览器页面或浏览器缓存已回收 | 可能没有可复用结果，需要重新请求并等待 |
| 保存系数 | 保存前本身会扫描历史；成功后又会失效前端查询，引发设置刷新 |
| 多人访问 | 浏览器缓存彼此独立，不能在服务端合并历史扫描 |

依据：[查询 key 与请求封装](../../web/src/features/organizations/invoice-api.ts)、[全局 QueryClient](../../web/src/lib/query-client.ts)。当前设置没有单独覆盖全局 `staleTime: 10 * 1000`，key 包含组织范围、登录用户和生效月份。

### 2.4 保存系数后，现有账单如何刷新

当前 `UpdateOrganizationSettlementRule` 在同一事务中保存规则，并调用[汇总失效函数](../../model/organization_invoice_summary.go)，将该组织 `period_end >= 生效月起点` 的汇总置为 `invalidated`，清除整单 `payload`。这一操作未清空消费日缓存、钱包日缓存及 `wallet_payload`；同值幂等保存不触发已有规则的更新和失效，首次创建显式规则仍沿用现有创建语义。

下次[账单查询](../../service/organization_invoice_summary.go)登记持久工作，由后台重建。[构建器](../../model/organization_invoice_build.go)仍经过来源准备、期初处理、消费分片、钱包处理及账单组装，消费日片有命中复用能力，但没有“仅系数变更”的专属轻量路径。因此当前不能宣称保存系数后一定不读日志、不回放钱包；本次设置列表缓存也不会自动解决此问题。

当前账单 `Finalized` 表示账期已经结束，不代表管理员正式确认结算。[已确认结算不回改的业务边界](./2026-10-17-组织账单历史调额兼容修复方案.md)继续有效，不能把重建动态核对缓存等同于重新确认正式结算。

## 3. 优化方案

### 3.1 将“组织使用过的模型集合”与“某月份的系数”分开复用

当前设置输出由两部分组成：

- **组织模型／分类依据**：相对稳定、获取成本高，沿用当前历史及成员有效期规则。
- **月份系数**：数据少，需要保留所选月份的继承、生效版本和并发校验。

服务端缓存第一部分，读取与保存共用；月份变化只重新读取及组装小规模规则。保存系数成功后使受影响的系数响应及账单失效；模型集合保留，账单按 3.10 区分仅系数重算和事实变化重建，不能因系数数值变化无条件清空底层依据、重新扫描原始日志。

缓存只保存有限的模型名集合、必要归属／来源版本和准备进度，不保存逐笔金额，不新增消费账本，不接入每次在线扣款路径。

| 数据 | 处理方式 | 不作为替代依据 |
| --- | --- | --- |
| 每条成员关系有效范围内的原始模型名集合 | 服务端持久化、跨请求复用 | 不复制逐笔消费日志 |
| 集合的范围、来源、准备状态及进度 | 与集合一起保存 | 不以“已经缓存”冒充同范围完整 |
| 组织分类及分类中的模型列表 | 合并当前有效缓存，复用原分类函数 | 不维护另一套模型分类规则 |
| 所选月份的系数、继承和版本 | 每次读取现有小规模规则表并组装 | 不以长效缓存返回过期版本 |
| 消费金额、预扣、退款、余额 | 沿用原账单及资金机制 | 不写入本专项缓存 |

### 3.2 先证明覆盖，再复用已有派生结果

现有能力已核对如下，实施时复用已证明可用的部分，不将已有表或游标的存在当作完整覆盖：

- [消费日缓存](../../model/organization_invoice_day_cache.go)保存修正后的消费及覆盖结果，可能排除预扣、未分类或待确认费用，不能直接等同于当前 `type=2` 模型发现。
- [来源扫描](../../model/organization_invoice_source_scan.go)的普通日志头只读取 `id,user_id,created_at,type`，没有持久化普通模型名。可以复用扫描、限速及进度保护机制，但不能直接继承其 `LogId` 并宣称模型已经扫过。
- [来源完整性机制](../../model/organization_invoice_source_integrity.go)已有日志清理及迟到投递处理；模型集合也须正确接入或验证相应修正信号，不能只用新增 ID 推断历史不变。

必须保留当前“组织历史使用过的分类＋成员有效期”的规则：

1. 不能只读取当前月份快照，遗漏历史使用过的模型。
2. 已确认消费缓存可能排除了任务预扣、未分类或费用待确认记录，不能未经核验就与当前 `type=2` 模型发现语义等同。
3. 成员归属或计费起点变化、日志保留范围变化、日志库替换，必须能使受影响的集合重新验证；分类映射变化时用已缓存的原始模型名重新归类，不因此重扫原始日志。
4. 全部分类字典、全平台模型列表和已配置系数记录均不能直接当作“该组织使用过的分类”。

保留全历史语义，是为了继续维护历史月份及较早使用过的分类。“近 N 个月”会隐藏旧分类，“仅已有系数配置”会遗漏尚未配置的新分类；两者属于产品范围变更，本专项不采用。

因此需要一个用途明确、可重建的小型模型集合缓存。已有账单模型可作为已知候选，但 `ready` 快照包含模型行不代表其月份的原始 `type=2` 已完整覆盖：费用待确认任务可能已从消费汇总中排除。只有额外证明原始来源及当前成员范围匹配，候选才能作为有效正向依据；只有证明完整覆盖，才能跳过对应原始范围。首版不以快照种子为必做项，不为此另建覆盖映射或补扫平台；若首次准备实测成为主要瓶颈，再单独评估收益。

ClickHouse 沿用现有保守原则，而非关系数据库游标：[来源准备](../../model/organization_invoice_day_cache.go)明确跳过 ClickHouse 的 ID 增量扫描，新快照的日结果保守重算，[独立读取路径](../../model/organization_invoice_clickhouse_read.go)使用流式批读。新模型缓存同样不得依赖未经证明唯一、单调的 ID。无可靠修正信号时，按受控刷新重建受影响成员范围、完成后替换；读取已有结果时标明依据时间和更新状态，不承诺与关系数据库相同的持续增量完整性。这是增量能力的显式降级，不能套用关系库的刷新间隔、在前台同步重建或高频全历史刷新；若预算内无法持续刷新，必须说明限制，不能宣称持续更新及规模验收已完成。该降级的首扫、刷新成本及迟到记录回归须实测，不能仅因复用已有表就视为兼容完成。

### 3.3 缓存粒度和持久化内容

按“组织＋成员关系＋有效计费范围＋日志来源版本＋发现算法版本”识别一份模型集合。这里的成员关系包含归属窗口，不只是 `user_id`；同一用户多次加入或转组织的窗口不能混用。

计费范围复用 `effectiveBillingStart`／`logMembershipBounds` 的现有边界规则。未退出成员使用稳定的开放结束标识，不把每次请求的当前时间放进缓存键；本次扫描固定截止属于准备进度。来源标识不得包含明文连接凭据；同地址恢复或替换数据库也须更新来源代次或显式重置缓存，不能仅靠 DSN 不变或 `MAX(id)` 未缩小判断可复用。

每份结果保存以下最小信息，具体列名在实现时按项目模型约定确定：

| 信息 | 用途 |
| --- | --- |
| 组织、成员关系及范围标识 | 验证缓存适用于哪个用户的哪段有效归属 |
| 去重后的原始模型名 | 合并组织集合、调用原分类函数 |
| 日志来源标识及发现版本 | 避免日志库替换或算法变化后误复用；不保存带密码的 DSN |
| 已处理进度、本次固定的来源边界及构建代次 | 断点恢复和条件发布，不混淆“已读到哪里”与“目标到哪里” |
| 准备状态、更新时间及必要失败原因 | 明确完整、准备中和失败，不以空集合代替未完成 |

采用主库上的专用小型派生存储，优先每个有效成员范围一份紧凑结果，不持久化逐日志或逐金额明细。结果与进度在同一主库事务中提交；日志库独立部署时，不能把跨库读取描述成跨库原子事务。使用现有任务租约，不再为每个成员建立一套独立调度系统。

组织层仅合并当前来源及范围版本匹配的结果，去重后生成分类。集合不以月份或登录用户重复存储；请求仍须先按现有权限确定组织，不能因共享缓存绕过组织隔离。

新增一个成员只补其有效范围；退出、修改计费起点或修正历史窗口时重新验证受影响成员，不清空其余成员。若新增成员尚未完成准备，已有合法模型可以继续展示，但组织列表必须标记“分类更新中”。范围已失效的旧模型不能继续作为该范围的保存资格依据。

### 3.4 首次准备、增量更新及并发

首次流程：

```text
请求读取设置
  → 读取成员范围缓存和小规模系数表
  → 缓存完整：合并、归类并返回
  → 缺失或更新中：登记共享后台工作，返回明确准备状态

后台准备
  → 固定成员范围、来源边界和构建代次
  → 有界读取必要日志元数据，累计去重模型名
  → 每批提交本代集合及进度
  → 核验代次及范围仍有效，发布该范围结果
```

- 同一组织的准备由共享任务推进，多人打开、切换月份或重试不能各自启动历史扫描；跨节点沿用任务租约，进程内合并请求不能代替跨节点互斥。
- 优先按实际 SQL 验证能减少扫描的聚合方式；不能把“按 174 人并发查询”或“加大 LIMIT”当作工作量有界的证明。只读必要的模型名、时间及游标元数据，不读取 `other` 或完整日志对象。
- 已有结果和已完成分片跨请求、月份及重启保留；任务中断后继续，不能因页面离开丢弃已完成工作。
- 有可靠增量依据时，后续后台只处理新到达或被修正的数据。同模型继续使用只推进进度；发现新模型才增补集合。不得每天重新扫描全部历史，也不得在普通消费请求中逐笔写本专项缓存；ClickHouse 无此依据时执行 3.2 的显式降级，不冒充同等增量能力。
- 日志 ID 分配顺序不等于提交顺序。ID 小于已读进度的迟到记录、历史更正及来源更换须由已验证的修正机制触发受影响范围重读，不能仅凭 `MAX(id)` 或总行数不变判定完整。
- 每次工作固定目标边界；新请求和持续新增日志不能不断扩大正在执行的目标，完成后再登记后续增量，避免永远准备不完。
- 普通追加允许合并；删除、更正、窗口收缩或来源替换必须重新计算受影响范围，并在完成后原子替换其结果。重扫后不能仍与旧集合无条件取并集，否则已删除模型会永久残留。
- 重建结果与进度属于新代次。每批提交及最终发布均校验当前租约、范围、来源和构建代次，旧任务不能回写或覆盖新结果；替换发布不暴露半成品为完整结果。仍有效的已发布范围可继续展示和提供正向依据，已被明确失效的旧范围不能授权保存。
- 普通追加、准备中、失效和失败分别表达，接口按 3.8 执行；不能将未完成表达为完整空列表。

上述历史修正须接入现有清理／迟到信号，并提供受控历史修改及恢复数据库后的缓存重置入口。无法自动发现的库外直接修改必须执行显式失效，文档和实现不得承诺自动感知任意外部改库。

### 3.5 更新与失效规则

| 变化 | 应有行为 | 禁止的重复工作 |
| --- | --- | --- |
| 已有模型产生新消费 | 增量推进来源进度，集合可保持不变 | 每次消费清空集合 |
| 出现新模型 | 增补受影响成员范围的模型集合 | 重扫全组织历史 |
| 新增成员 | 准备新成员的有效范围，其他结果继续复用 | 全组织缓存失效 |
| 成员退出、计费起点或历史归属改变 | 重新验证变更范围，发布新范围版本 | 将窗口外的旧模型直接带入新范围 |
| 修改系数 | 模型缓存不动；受影响账单按 3.10 重算，事实有效时复用消费及钱包结果 | 因系数值变化清空底层缓存、回放全期流水 |
| 修改分类映射 | 使用原始模型集合重新归类 | 重新读取所有消费日志 |
| 日志清理、替换或历史修正 | 按 3.4 重建并替换受影响范围，移除不再存在的模型 | 重扫后仍无条件合并旧集合，或忽略删除／更正 |
| 应用重启、多人打开或切换月份 | 读取持久结果，任务按进度恢复 | 回到无缓存状态、每月重复准备历史 |

**时间只用于安排刷新，不作为删除有效结果的理由。** 不采用“缓存五分钟，到期后同步全量重算”。存储清理只删除已被替代且没有有效任务依赖的旧范围／版本，不能把正在使用的结果按短 TTL 清掉。

### 3.6 保存同样走共享依据

保存前从同一模型集合验证组织分类资格，并沿用当前事务、乐观版本冲突、零系数及继承规则。不能只优化 GET，而让 PUT 保留逐成员历史扫描。

复用现有组织锁，在保存事务内复核提供正向依据的成员范围、来源及缓存代次仍有效，并沿用原系数版本校验。范围变更、失效与发布须有一致的锁定或条件版本保护；失效先发生时不得使用旧证据提交保存。事务内只检查小规模主库元数据，不持锁扫描日志；发生竞态时返回更新中或重新读取依据，不绕过校验。

| 缓存证据 | 保存行为 |
| --- | --- |
| 当前有效范围的结果已经证明该分类使用过 | 正常执行原规则保存，不等待无关成员的首次准备 |
| 缓存未命中，但对应来源尚未完整处理 | 返回明确的依据更新中状态，推进到本次校验固定的来源边界后再判断；不误报未使用 |
| 已完成对应范围及来源边界校验，仍无该分类 | 沿用原“不属于组织已使用分类”的校验失败 |
| 范围或日志来源版本已失效 | 先更新依据，不用失效结果授权保存 |

有可靠且有界的定位依据时可针对性校验；否则等待共享任务并给出明确状态。禁止未命中后偷偷回退到无界历史扫描，也不能因为有未完成成员就阻塞所有已经有正向依据的分类保存。

### 3.7 请求等待、前端缓存与同步延迟

- 请求上下文传至模型读取；同步查询及后台分片分别设置合理的数据库和应用预算，复用现有重查询限速与暂停机制。
- 普通请求取消应停止属于该请求的数据库工作。共享后台准备任务具有独立生命周期，不能因一个管理员关闭弹窗就取消其他人的准备，也不能因此重复创建任务。
- 前端请求接入取消信号，并在设置关闭、组织／月份切换时按现有查询能力处理取消；不能只设置 `enabled=false` 就假定已取消所有在途工作。
- 已有结果时保持可读，用明确的后台更新提示；首次准备或错误时提供说明与重试，不无限骨架。轮询若有必要，只读取轻量状态，不重复发现模型。
- 增加前端新鲜期可减少重复访问，但只作为补充；不修改全站 QueryClient 默认值，不靠隐藏加载状态来掩盖服务端成本。

增量维护也有扫描成本，不能只测单次弹窗。优先评估在现有必要来源扫描中以窄接线采集模型名；必须有本专项覆盖记录，不能继承过去未读取模型名的游标。若独立扫描更简单，需单独记录与账单来源扫描的重复读取量，并与账单任务统筹总并发和 IO 预算；仅调用现有查询前延迟函数不代表已经限住总负载。不为此建设通用扫描平台。

刷新首先覆盖已请求准备的组织，不默认高频轮询所有组织；无新增数据时退避，退出且无新证据的窗口不反复扫描。活跃组织按可配置间隔处理新边界；首次补齐、增量维护与账单生成共同验证资源上限，多节点租约只防同一任务重复执行，不能替代跨任务的容量控制。

新模型建议以分钟级后台刷新出现在设置列表，避免给持续在线消费增加同步缓存写入；具体间隔应可配置并经实测确定，当前未作为已确认 SLA 或验收结果。管理员只看到同步前模型时，通过“分类更新中”及刷新状态理解这一延迟。保存未命中的情况按 3.6 严格核验，不用列表短暂滞后来断言组织未使用，也不影响模型的实际调用和原扣费。

前端继续按组织、登录用户及月份隔离规则响应，保存后刷新受影响规则响应及账单。历史系数会被后续月份继承，不能只使所选月份的浏览器规则结果失效而保留错误的后续继承结果；首版可按本组织规则查询前缀失效。服务端模型集合跨月份复用，但不缓存一份长期不更新的完整设置响应。浏览器刷新、缓存回收或新用户访问，不应再使服务端历史集合消失。

### 3.8 设置读取与保存的接口合同

GET 保留 HTTP 200、`success:true` 及原 `data` 选项数组，在响应顶层增加 `discovery` 元数据。准备状态不塞入单个选项，不改变原系数及版本字段含义；实施时同步扩展本接口类型及设置组件。

| `discovery.status` | 返回与用户行为 |
| --- | --- |
| `preparing` | 首次没有有效依据，`data` 可为空；显示正在准备，不显示“组织未使用分类” |
| `updating` | 返回有效的已知分类，说明列表更新中；有正向依据的分类仍可按 3.6 保存 |
| `ready` | 已完成本次固定来源边界；空数组才表示该边界内没有符合条件的历史分类 |
| `failed` | 准备失败；仍有效的分类可继续展示，提供重试入口，不能把未完整的列表标记为完整 |

元数据包含 `evidence_as_of`（已发布依据的时间，无结果时为空）及必要的稳定失败码；不回传 SQL、DSN 或内部异常详情。`ready` 表示截至已处理边界完整，不是保证覆盖响应时刻所有并发提交；发现后续待处理范围时标记 `updating`。普通读取、鉴权等失败沿用原错误合同，不伪装为准备成功。状态刷新只读轻量状态及小集合，重试只登记／推进同一共享任务。

PUT 的新增等待合同固定如下：

- 依据不足但可以继续准备：HTTP 200、`success:false`、`code:"settlement_category_preparing"`、`retryable:true`，附可读提示；本次不写入系数，不失效账单。
- 准备已失败且当前分类无有效正向依据：HTTP 200、`success:false`、`code:"settlement_category_discovery_failed"`、`retryable:true`，先重试准备，再由管理员保存。
- 已完成核验仍不属于组织已使用分类：沿用现有普通业务错误；版本冲突仍为 HTTP 409 及现有版本信息，成功结构不变。

`retryable` 表示条件恢复后允许重试，不授权自动提交。前端显式识别上述业务状态，保留当前月份和输入，提示等待或重试准备；不自动重放 PUT、不弹保存成功提示。准备完成后由管理员再次保存，并继续执行原版本冲突校验，不能后台静默覆盖期间他人的修改。

### 3.9 实施顺序及过渡保护

1. **先保护当前入口**：将前端取消信号、请求上下文接通至 SQL，接入现有暂停及重查询超时能力，减少相同组织的重复在途工作。GET、PUT 均覆盖。此阶段只限制失控及取消后的资源消耗，不消除扫描量；取消或超时必须明确返回，不能记录为“加载问题已解决”。
2. **落地唯一缓存路径**：实现成员范围集合、共享准备及条件发布，再让 GET、PUT 同时切换到共享依据，完成 3.8 的界面状态；同时实现 3.10 的系数变更轻量重算及持久登记。过渡代码不得留下缓存未命中就同步全量扫描的长期旁路。
3. **验证持续负载后启用刷新**：验证初次补齐、持续追加、修正及重启，并覆盖保存系数后的完整账单／CSV 更新链路，再确定刷新间隔、总并发和读取预算。记录最终参数及测量结果。

过渡阶段默认保持保守并发；不把按成员并发查询列为必做优化。仅在隔离实测证明在线请求延迟、连接及 IO 可接受后，再评估小幅并发。增加超时、加 worker 或提高并发均不能替代减少重复扫描。

### 3.10 系数变更后的账单重算与缓存刷新

本节只处理组织结算系数变化；个人模型价格、消费确认算法、成员归属或原始事实改变，仍按其实际影响范围进入原有重建机制，不能套用“只改系数”的快速路径。

#### 3.10.1 分层复用，不重新计价原始请求

| 缓存层 | 仅系数变化时的处理 |
| --- | --- |
| 本专项的组织原始模型集合 | 保留，不触发重新发现 |
| 按账户、模型／分类及归属月的原始整数 quota 聚合 | 消费依据、归属及计算版本仍有效时复用，不因系数变化失效 |
| 钱包收支、余额及原完整性结论 | 资金依据未变时复用，不因系数变化重新推导期初或回放流水 |
| 应用系数后的分类金额、账单快照及 CSV | 依受影响月份更新，页面与导出使用同一新快照 |

复用现有日结果及汇总能力，仍由 `buildOrganizationInvoiceCategoryRows` 等现有函数应用规则，保留整数 quota、decimal 精度、归属月、分段系数及舍入口径。不得从已舍入的结算金额反推消费，或将跨月合计简单乘一个新系数；不得重新按当前个人模型价格计算历史请求。新逻辑仅负责复用条件、任务衔接及发布保护，不复制一套金额计算器。

清除旧 `payload` 前，必须保证重算所需原始聚合及其证据标识仍可取得。优先引用现有有效日聚合和保留的钱包结果；不足时仅在现有可重建汇总存储中补最少的原始聚合缓存或引用及版本信息，不新增逐笔消费表、资金账本或长期并行账单系统。旧结果仅用作受保护的重算输入，不作为新系数下的有效账单继续提供下载。

#### 3.10.2 冻结消费依据，单独更新规则版本

轻量重算保留原请求范围、实际覆盖截止、消费证据时间／水位、成员归属、计算版本、完整性标识及钱包结果，单独记录本次采用的规则集合版本或指纹；不能只记录一个分类的版本而忽略同账期其他适用规则。用现有小规模主库元数据验证原始聚合和资金依据仍有效，不先调用完整来源准备或钱包计算来证明“可以不算”。

只有上述依据可证明有效且输入完整可取得，才走轻量重算。若成员窗口、任务确认、退款资金依据、来源／保留范围或算法版本已经改变，或无法证明有效，则登记正常异步重建，明确原因；不能把缺失聚合当零，也不能隐瞒该分支的扫描成本。正常重建仍使用原定覆盖范围，证据版本变化须有记录；扩大覆盖范围必须是独立的快照请求，不能随系数保存静默发生。

ClickHouse 无法提供同等来源验证时沿用 3.2 的降级边界，不把已有日结果的存在当作轻量复用已验证。正常重建与轻量重算共享调度及读取预算，不能出现两个不受控制的执行入口。

#### 3.10.3 影响范围、持久登记及并发发布

保存规则、标记受影响动态账单和登记可恢复的重算工作在同一主库事务中完成；事务只处理规则及缓存元数据，不执行历史日志扫描或同步账单重算。复用已有汇总工作记录及任务调度，不新增通用队列。提交后唤醒任务失败，也须可由已有调度重新发现待处理工作，离开页面不影响推进。

范围按既有继承语义确定：某分类从修改月份起，至该分类下一条显式生效规则之前。例：9 月规则改为 0.9、11 月已有显式 0.8，则主要影响 9、10 月及覆盖这些月份的自定义账单，11 月起不再继承本次修改。首版允许保留当前“生效月起向后”的保守失效范围，但超范围月份也必须复用有效底层依据，不能因此全期扫描；更精确的范围裁剪在同等正确性下按实测收益决定。其他组织及修改月份之前的账单不受影响，同值幂等行为继续沿用现有合同。

同一组织、账期的重复修改合并到当前待处理工作，保留最新有效规则；已失效的旧任务不得持续覆盖或反复重建。发布事务须与规则修改遵循一致的组织锁定顺序，并校验汇总代次、消费依据版本及适用规则版本／指纹仍匹配。不匹配时放弃旧结果并推进最新工作，不能仅依靠最初读取到的系数。规则变更与发布同时发生时，提交顺序必须保证旧规则结果不能作为当前 `ready` 缓存留存。

#### 3.10.4 用户行为及已确认结算边界

PUT 成功表示规则已保存、受影响重算已持久登记，不表示所有账单已经更新完成。保留原成功结构，通过明确提示区分“系数已保存”和“账单更新中”；账单沿用生成状态与轻量轮询，轮询不重新登记重复计算。任务重启后继续，失败时给出重试及原因，不能无限骨架或把旧金额当新结果导出。

已人工确认结算的金额及留存账单不回改，后续有依据的差额按既定人工调整规则处理。本专项不新建确认或跨期调账流程。实施前核验真实确认依据及保护入口：`ready`／`Finalized` 不能作为确认标志；只有外部人工记录时，须保护留存正式账单，并区分动态核对结果与正式结算，不能宣称动态缓存重算已经解决正式结算锁定。该边界未核实前，不得将“已结算不回改”记为代码验收通过。

## 4. 实施边界与验证

主体放入专用扩展文件，原模型／控制器仅保留必要调用接线。读取和保存必须使用唯一的模型发现依据；不保留一个走缓存、另一个走全量日志的平行实现。

| 验收项 | 完成标准 |
| --- | --- |
| 历史范围等价 | 成员有效期、计费起点、历史与新增模型、退出或转组织成员、未决任务及 fallback 分类与现行规则一致 |
| 系数业务不变 | 月份继承、已配置版本、冲突返回、零系数、账单失效边界、个人扣费不受影响均保留 |
| 系数变更轻量重算 | 已有完整、有效缓存时修改系数，原始 quota、消费证据和钱包数据不变，金额与原计算器同依据结果一致；快路径不扫描历史 logs、不调用全期钱包回放或期初重算；页面和 CSV 同一新快照 |
| 重算影响范围 | 覆盖跨月、分类下一条显式规则、零系数、同值幂等及不同组织；未受影响账期仍命中缓存；保守失效的额外月份不得导致全历史重扫；前端后续月份继承结果同步失效 |
| 重算竞态与恢复 | 覆盖任务构建中连续修改系数、发布时并发保存、页面离开、提交后唤醒失败和进程重启；旧规则结果不能发布为当前 ready，任务最终按最新规则完成；数据同时修正时不得误走系数快路径 |
| 确认边界 | 已确认正式账单留存金额不被动态重算覆盖；未核实真实确认依据时明确交付限制，不以 Finalized 或缓存 ready 替代确认 |
| 真正复用 | 首次准备后连续打开、切换月份和正常保存，不再执行逐成员全历史 `DISTINCT model_name` |
| 成员粒度与重启 | 新增成员只准备新范围；窗口修正只处理受影响范围；同用户不同归属不混用；重启及多人访问复用持久结果 |
| 首次可完成 | 无缓存时准备有界、进度可恢复；多人或重试只推进共享任务，客户端能理解当前状态 |
| 更新正确 | 新模型、低 ID 迟到提交、历史修正、成员窗口、来源更换及清理使缓存按受影响范围更新；删除唯一一条某模型日志后，该模型退出集合；旧代任务不得回写；集合与进度一起提交，不继承未采集模型名的旧进度冒充完整 |
| 开放窗口与固定截止 | 请求时间变化不使同一在职成员缓存键变化；持续写入及重复打开不扩大本轮目标，已冻结边界可以完成，后续增量另行推进 |
| 保存资格 | 有有效正向依据的分类可保存；未命中且依据未完整时明确更新中；完整核验仍未命中才拒绝；不因无关成员准备中阻塞已有资格；并发范围修改或来源失效不能使事务使用过期资格 |

## 5. 当前交付状态

### 5.1 已落地机制及本轮修复（2026-10-18）

- 模型集合仍是唯一分类依据：GET／PUT 不回退到逐成员同步全历史 DISTINCT；规则现读现算，缓存不保存金额。缺缓存登记后台准备，原 HTTP 等待码与 409 冲突合同保持不变。
- 发现版本升为 2：旧版本行和真实数据保留，旧游标不再复用。版本升级首次需要后台准备；不得把旧版本的时间游标当作新 ID 游标已完成。迁移及版本隔离纳入三库用例。
- 代次与游标保护：采用 ID 序有界分页；冻结本轮头及覆盖截止，重试保留目标；完成空范围也推进到冻结头，避免到期刷新反复检查同一历史范围。迟到低 ID 投递按覆盖范围回退并提升代次，不依赖 ID 与业务时间同序。成员窗口修正、清理均提升代次，旧扫描不能提交进度或发布；ClickHouse 发布保留原扫描身份，不重新绑定新代次。
- 清理及保存资格：标记待清理即停止用旧集合授权保存；扫描即使先于物理删除，也按持久保留边界排除旧日志；已知保留边界覆盖全部已发布范围时，允许在日志头缩小后重建空集合，不误报数据库替换。未知来源倒退仍明确失败并要求受控重置。PUT 在同一事务内锁定并核验真实成员窗口和当前集合；清理按集合→汇总的顺序锁定，避免与保存形成锁环。
- 系数轻量重算：捕获 ready payload 时锁定汇总行，与事实失效串行；连续修改系数保留同一份有效输入，事实修改清除输入。领取任务保留原覆盖、证据时间及水位。正常构建和轻量重算共用发布入口，在组织锁及汇总代次保护下，用当时有效的小规则表调用既有金额计算器；不允许旧规则结果成为当前 ready，旧事实输入被拒绝后也不能落回重扫并覆盖新任务。
- 资源控制：模型发现接入现有跨任务／跨节点重查询许可，与组织用量及账单任务共享；许可占用时让出后续调度，丢失时取消扫描。每轮刷新资格时间固定，不在长轮次中追逐不断过期的窗口；仍采用默认单路、批次延迟、暂停及数据库侧语句超时。
- 前端：准备中、更新中、失败时不显示“没有分类”；完整空结果才显示空态。PUT 等待后轻量刷新、保留输入且不自动重放保存；关闭面板取消请求专属查询，共享后台任务继续。
