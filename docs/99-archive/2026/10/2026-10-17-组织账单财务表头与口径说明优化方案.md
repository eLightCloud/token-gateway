# 组织账单财务表头与口径说明优化方案

## 1. 问题与目标

用户已确认：将“AI 钱包扣减”改为 **“钱包扣款（退款前）”**，明确该列可能包含已记录的任务预扣，但不等于未结算预扣余额，也不等于最终消费金额。围绕组织账单对账，用简短表头和说明区分消费金额、钱包收支及余额状态。

用户进一步确认：**核对明细仅在存在待确认或异常时展示具体账户、任务及原因；其他正常诊断信息不展示。** 没有待确认或异常时，省略整个附加区，主表也不逐账户输出“按流水推导；未独立核验”、正常核验状态或空差额。

本文展示优化已完成代码实施和本地回归，交付证据见第 6 节，未操作线上发布。金额计算、任务确认、日缓存及账单快照仍以[组织账单实际消费汇总与加载修复方案](./2026-10-17-组织账单历史调额兼容修复方案.md)为准；本文不另立账务规则。

核心目标是消费金额准确、依据可追溯、已计算结果可缓存复用；钱包收支用于解释资金变化。独立历史余额核验不作为本次账单生成或结算的必要条件，本次不为此补建新系统。不增加新的统计列、消费账本、预扣查询或对账流程，也不将正常的余额推算状态当成异常。

## 2. 当前实际情况与实施前基线

下表记录本轮实施前核对的字段及展示问题；重复状态、零退款和缺失覆盖提示等问题已按第 3 节修复，当前实现与回归结果见第 6 节。字段金额含义及 2.1 的快照路径保持不变。

| 展示或计算位置 | 当前事实 | 用户容易产生的误解 |
| --- | --- | --- |
| 账号财务表的“用量” | 展示 `account.gross_amount_usd`，是消费金额，不是 Token 数或调用次数 | 把金额当成使用数量，或把它当作组织系数处理后的应结算金额 |
| “AI 钱包扣减” | 展示 `financials.ai_wallet_deduction_amount_usd`；汇总归属于该账期及成员有效期的消费扣款流水，排除已识别的订阅出资 | 以为是最终净消费，或者全部都是任务预扣 |
| 钱包退款 | 另存 `wallet_refund_amount_usd`，同时已经包含在 `other_identified_inflow_amount_usd` 和入账合计中 | 找不到退款，或者把“其中退款”再次加到入账合计 |
| 管理员与其他扣减 | 独立于上述消费扣款列，参与扣款合计 | 以为“钱包扣款”已经包含所有扣款，又与其他列重复相加 |
| “期末余额”与“当前余额” | 前者对应快照覆盖截止的余额推算，后者是读取时的钱包余额 | 将昨日截止值和今日实时值直接比较并认定差额错误 |
| `derived` 状态 | 表示根据历史收支推算，不代表已经与独立余额记录比较一致 | 把“派生”或“生成完成”当成“对账通过” |
| CSV 附加区 | 目前逐账户写一行核对状态，再在退款字段非空时写一行退款；字符串形式的零也满足非空条件 | 正常用户重复出现，多行容易被误解为多笔费用或多项异常 |
| 页面问题提示 | 已按费用及钱包问题分别提示，已有“账户＋任务＋原因”去重；但 `expense_coverage` 缺失时目前不会提示费用不完整 | 不能将“多数已实现”当成缺失依据也能正确提示 |
| CSV 主体 | 当前为分类结算矩阵、账户金额行和模型消费矩阵，并非页面同款的完整财务表 | 不能假设已有“其他入账”列，或为同步页面表头重新建设导出表 |

代码依据：

- [账号财务表](../../web/src/features/organizations/invoice-financial-summary.tsx)：字段绑定、退款子项和状态展示。
- [钱包流水计算](../../model/organization_invoice_export_financials.go)：消费扣款与退款分别累计，订阅来源排除，退款计入其他入账。
- [钱包日缓存与余额组装](../../model/organization_invoice_wallet_cache.go)：复用钱包分项，计算入账、扣款及截止余额。
- [CSV 对账说明](../../controller/organization_invoice_csv_reconciliation.go)：已有完整性、退款和推导余额说明。
- [页面及导出入口](../../controller/organization_invoice.go)、[快照读取服务](../../service/organization_invoice_summary.go)、[快照构建](../../model/organization_invoice_build.go)：当前入口统一走后台构建及快照读取。
- [费用分类归并](../../model/organization_invoice_expense.go)：已识别的任务预扣、补扣及未分类日志从原消费聚合移出；有歧义的原始桶归入未分类，不留在已确认消费小计中。
- [页面问题提示](../../web/src/features/organizations/invoice-reconciliation.tsx)：已有异常提示和去重，实施时优先复用并补齐覆盖信息缺失的分支。
- [CSV 主体](../../controller/organization_invoice_csv.go)：现有导出结构、固定金额行和格式。

“钱包扣款（退款前）”中可能同时包含普通请求最终扣款、任务预扣和任务补扣，以已记录且纳入当前统计范围的流水为准。不能据此声称所有真实资金变动均有完整记录；现有缺失及待核对标识必须保留。

### 2.1 当前入口与历史计算器的边界

当前页面查询和 CSV 导出均调用 `service.GetOrganizationInvoice`，后台准备来源上下文并构建快照，钱包计算走缓存分项合并。正常状态为 `derived`，依据不足时为 `incomplete`，钱包计算失败时可为 `unavailable`；该快照路径不做同期独立钱包余额比较，也不生成核对差额。

月中显式选择到月底，仍走上述快照路径：构建按 `SourceAsOf` 冻结实际覆盖范围，用户请求期与实际覆盖期分别保留，不能因此宣称已经覆盖月底，也不能统一写成“截至昨天”。完整自然日截止可展示日期；截止到当日某一时刻时，使用现有 `CoveragePeriod.EndTimestamp` 展示北京时间及具体时刻。

源码中的 `model.GetOrganizationInvoiceWithContext` 裸上下文计算器仍保留未终期实时余额比较和 `reconciled` 分支，当前检索到的直接使用主要是测试对照；它不是本方案页面或导出的实时分流入口。关联方案附录 A 的历史实时行为不作为当前入口依据。本次保留既有接口状态兼容，不启用旧实时路径、不新增按状态切换的余额计算或提示体系。

## 3. 优化方案

### 3.1 表头与字段绑定

主表保留现有账号及金额列的相对顺序、字段和数值，调整文案；“余额核对状态”和“核对差额”退出常驻主表，仅在异常区按已有依据展示，不以空列或正常状态重复占位。以下为页面字段对应，不是新增 CSV 列的清单。

| 当前表头 | 调整后表头 | 现有字段或展示约束 |
| --- | --- | --- |
| 账号 | 账号 | 继续显示账号及已有姓名信息 |
| 用量 | 已确认消费金额 | `gross_amount_usd`；费用未完整确认时须表达为小计，见 3.2 |
| 期初余额 | 期初余额 | `opening_balance_amount_usd` |
| 支付充值 | 充值入账 | `payment_top_up_amount_usd` |
| 管理员增加 | 管理员调增 | `admin_increase_amount_usd` |
| 其他入账 | 其他入账（含退款） | `other_identified_inflow_amount_usd`；保留“其中退款”子项 |
| 全部入账 | 入账合计 | `total_inflow_amount_usd` |
| AI 钱包扣减 | 钱包扣款（退款前） | `ai_wallet_deduction_amount_usd`；仅该消费扣款分类，不包含后面的管理员调减和其他扣款 |
| 管理员扣减 | 管理员调减 | `admin_decrease_amount_usd` |
| 其他扣减 | 其他扣款 | `other_deduction_amount_usd` |
| 全部扣减 | 扣款合计 | `total_deduction_amount_usd` |
| 期末余额 | 截止日余额 | `closing_balance_amount_usd`；日期取实际覆盖截止，不取尚未覆盖的请求月底 |
| 当前余额 | 当前余额（查询时） | `current_balance_amount_usd`；导出时为导出读取的余额，不代表页面持续刷新 |
| 余额核对 | 退出常驻主表 | `reconciliation_status` 保留在 API；仅异常区显示相关原因，不输出正常状态 |
| 差额（如已展示） | 退出常驻主表 | 仅异常区存在已有核对差额时展示；缺失不能补成 0，也不输出正常账户的空差额行 |

金额单位沿用当前账单展示及既有换算规则，不通过改名改变币种、精度或舍入。已确认消费金额是现有分类结算系数处理前的金额；组织应结算金额继续使用既有结算汇总，不能直接替换为本列。

用户阅读顺序为“实际覆盖范围 → 现有结算汇总及应结算金额 → 消费明细 → 钱包辅助收支”。复用现有布局和汇总，保持应结算金额的显著性，不另加总额卡片或计算新的应付金额。“已确认”指最终费用已经确定，不等于管理员已确认账单或已完成付款。

### 3.2 最少必要说明

表格附近保留一句可直接看到的说明，避免用户必须悬停才知道核心区别：

> 钱包扣款为 AI 使用相关扣款，含已记录的任务预扣和补扣，未减去退款；扣款合计还包括管理员调减和其他扣款。

通过已有说明或提示组件补充三个字段的解释，不新增专用交互体系：

| 字段 | 说明文案 |
| --- | --- |
| 已确认消费金额 | 最终费用已确定的消费金额，尚未应用组织分类结算系数；费用待确认的任务不计入，其他依据不足的影响见费用待核对提示。 |
| 钱包扣款（退款前） | AI 使用相关的钱包扣款累计，含已记录的任务预扣和补扣，未减去退款；不含管理员调减和其他扣款。 |
| 截止日余额 | 根据期初余额和期间收支推算，截至 {{cutoff}}。 |

`{{cutoff}}` 使用实际覆盖截止，日期或时刻格式遵循 2.1。当前余额说明为“本次查询时读取的钱包余额，后续资金变动不会自动刷新本页”。不逐账户重复提示独立核验缺失；也不宣称推算余额已核验。

“已确认小计”与“仍有费用待核对”可以同时成立：前者是已能确定的部分，后者表示还有未确定或尚未纳入的部分。当前明确标记为未分类的记录及歧义桶不会留在已确认小计内，不应写成“未分类金额仍计入小计”。

若 `expense_coverage` 不是 `complete` 或缺失，保留现有完整性提示，并在金额列附近显示“已确认消费小计，仍有费用待核对”；不能用新表头掩盖未知费用，更不能把待确认费用当作零。若只有组织级完整性信息，按组织级提示，不虚构账户级结论。

页面非零退款继续在“其他入账（含退款）”单元格中显示“其中退款：金额”，其金额已包含在其他入账和入账合计中，不再相加。CSV 的具体位置见 3.6。零退款不显示子项，也不在附加区逐账户输出；正常退款本身不是异常，不因此生成异常明细。

### 3.3 余额状态语义

下表用于保持现有字段含义，不保留常驻状态列，也不逐账户展示正常状态。页面与导出统一遵循 3.5，仅费用或钱包问题进入相应异常区。

| 状态 | 业务含义及兼容边界 | 展示约束 |
| --- | --- | --- |
| `derived` | 当前快照路径正常的流水推算状态 | 不属于异常，不展示正常状态行，也不改标为“核对通过” |
| `reconciled` | 旧计算器等保留合同中的核对一致状态，非当前快照路径正常产物 | 保留 API 兼容，不新增展示分支，不自行计算或升级；正常状态不生成明细 |
| `incomplete` | 钱包核对依据不足 | 在钱包问题区列已有具体原因；缺少细节时如实使用账户级通用原因 |
| `unavailable` | 钱包信息暂不可用 | 在钱包问题区说明，缺失金额不补成 0 |

整单 `generation_status=generating` 沿用现有加载状态。前端账户状态类型或标签映射中的 `generating` 仅为防御性兼容保留，当前后端不会把它写作账户核对结论，不作为第五种业务核对状态介绍。

负余额保留真实值。查询时余额与截止日余额对应不同时间，不要求两者相等，也不新增两值相减作为“核对差额”的计算。

### 3.4 业务示例与边界

以下金额仅为说明口径，假设任务使用钱包出资、预扣和退款均有完整记录；已确认消费不考虑组织分类结算系数。

| 场景 | 钱包扣款（退款前） | 其他入账中的退款 | 已确认消费金额 |
| --- | --- | --- | --- |
| 普通请求最终扣款 20 | 20 | 0 | 20 |
| 任务预扣 100，最终消费 20，同期退回 80 | 100 | 80 | 20 |
| 任务预扣 100，最终消费 120，同期补扣 20 | 120 | 0 | 120 |
| 任务预扣 100，最终费用尚未确认 | 100 | 0 | 该任务不纳入已确认金额，保留待确认标识 |
| 任务最终费用已确认 20，但退款 80 仍在途 | 100 | 0 | 按既有费用确认依据判断；已确认则计 20，不能仅凭任务成功推断确认，钱包保留在途提示 |

预扣与退款跨账期时，各自按现有资金流水归属落在相应账期；消费归属继续使用既有规则。本方案不要求单个账期“钱包扣款减退款”必然等于“已确认消费金额”：跨期、订阅出资和资金在途等均可能造成合理差异。

此列也不能计算“当前仍被占用的预扣余额”。本次不新增该指标，不查询任务状态补凑一个预扣数。

### 3.5 仅展示待确认或异常明细

本节约束页面及 CSV 的附加核对说明区，不删除主账单的账号、金额、收支、余额、账期及实际覆盖信息，也不取消 3.2 中理解金额所必需的字段说明。

| 情况 | 附加区处理 | 金额及状态边界 |
| --- | --- | --- |
| 最终费用待确认 | 展示受影响账户、任务及原因 | 只展示可靠的已确认消费小计，保留待确认提示 |
| 消费记录未分类、缺失或待投递 | 展示已有依据能定位的账户、任务及原因 | 不将未知费用补零，不宣称消费完整 |
| 已发现扣款、退款异常或资金处理在途 | 展示具体对象及原因 | 明确是钱包侧问题；除非费用依据也不足，不直接判定消费金额错误 |
| 期初或收支依据缺失，余额不能可靠推算 | 展示受影响账户及缺失原因 | 保留缺失余额，不补零；不阻断可靠消费的查看 |
| 正常 `derived`、正常 `reconciled`、零退款 | 不输出附加明细 | 不因未独立核验就视为异常，也不以隐藏状态代替真实核验 |
| 普通非零退款 | 页面保留其他入账中的退款子项，CSV 按 3.6 输出一个可选退款分项行，不生成异常明细 | 已计入流入金额，不重复计入总额 |

展示要求：

1. 没有待确认或异常时，省略“对账依据与完整性”“钱包核对”等附加区及空明细表头，不再输出正常状态、全零计数或零退款。账期、实际覆盖截止等基础信息由主账单提供，不在附加区重复；主账单尚未提供实际覆盖信息时，应复用现有快照字段补到主账单说明处。
2. 有待确认或异常时，只列受影响对象及必要原因；同一“账户＋任务＋原因”不重复输出。不同原因不得合并成无法追查的“有问题”。没有任务关联时留空任务，不伪造任务号；只有组织级问题时展示组织级原因，不虚构账户归属。
3. 费用问题统一标题为“费用待确认”，在页面消费金额及既有结算汇总附近、CSV 金额区前明确标注“已确认消费小计，仍有费用待核对”；存在该提示时，现有结算金额也只是按已确认部分计算的结果，不能描述成完整整月最终应收。钱包问题统一标题为“钱包收支待核对”，不将两类问题混成“账单错误”。费用完整性正常且只有钱包问题时，可说明“该问题不改变当前已确认消费金额”；两类问题同时存在时分别提示，不笼统宣称账单金额不受影响。
4. `expense_coverage` 缺失或不完整，即使没有可列举的逐笔 issue，也不能隐藏风险或当作正常结果；至少保留组织级“消费完整性依据不足”或现有具体原因。已有费用问题引用或非零未决计数也不能仅因状态字段写成 `complete` 就被隐藏，按已有依据提示待核对，不在展示层重新分类日志或估算金额。
5. 负余额保留原值，但不能仅凭余额为负、当前余额不同于历史截止余额，或“扣款减退款”不同于消费金额，就自行推断一项新异常。只展示后台已识别的问题。
6. 隐藏正常信息仅改变呈现，保留后台完整性检查、异常数据及 API 状态。不新增自动核验、自动消差或管理员确认；“没有待确认或异常明细”不等于管理员已确认结算，也不证明不可观测的历史缺失不存在。

页面已有分别提示、问题去重和对象定位，保留并复用，不另写第二套异常判断组件。必须补齐 `expense_coverage` 缺失时不提示的问题，并在只有账户级 `incomplete` / `unavailable` 而没有逐笔 issue 时列出受影响账户及通用原因。已有具体原因优先；不能直接把内部 SQL、连接错误或其他技术诊断原文作为对客说明。

### 3.6 CSV 布局与兼容合同

CSV 继续使用已有分类结算及模型消费矩阵，不新增页面同款的完整财务表。现有列名、列序、原有账户金额行及其金额含义不变；页面措辞与保留的旧 CSV 名称不同属于兼容取舍，“页面与导出一致”指来源、覆盖范围、金额含义及异常结论一致，不要求字面相同。

确定输出位置如下，全部取现有快照字段：

1. **文件开头的说明区**：在“组织名称／账期／币种”之后补充“实际覆盖”，然后进入原分类汇总。完整自然日范围展示日期，当日部分范围展示北京时间及时刻；若覆盖字段缺失，明确“实际覆盖依据不足”，不拿请求月底冒充实际截止。有费用问题时，在此处追加“金额说明：已确认消费小计，仍有费用待核对”。正常时不输出“消费完整”“未独立核验”或全零诊断计数。
2. **账户金额行之后、模型消费汇总之前**：仅当至少一个账户有非零退款时，追加一个横向行，行名为“其中退款（已含在当期流入中）”；账户列与现有账号列对齐，已有非零退款按现有金额格式输出，零或缺失值留空，尾部结算相关列留空。不新增退款统计或第二份合计，不改变原“用户当期流入金额”。这是已有退款字段的展示，不是新增财务表或异常明细。
3. **原有矩阵之后**：仅有问题时输出“# 费用待确认”和／或“# 钱包收支待核对”。每个实际存在的问题区使用固定列“账号、任务、原因”；有已有可用核对差额时附在该问题的原因说明中，不新增常驻差额列。账号使用快照中的用户名，找不到时用账户 ID；组织级问题不强填账号或任务。

同一账户可以因不同任务或不同原因出现多条问题，但不再出现“一个正常用户固定两行”的输出。已有问题明细可能有数量上限：计数明确表明尚有未展示问题时，保留对应非零计数或“明细未全部列出”提示，不为补齐明细重扫日志。不得借此输出无关的全零统计。

不在正常账单中重复输出技术证据时间、水位、核验状态等后台诊断信息；它们继续保留在已有快照/API 中。必要字段释义只在对应内容首次出现处提供一次，不追加逐账户说明。

### 3.7 最小实施范围及性能边界

1. 在现有组织账单财务组件中调整局部表头和说明，移除主表常驻状态及差额列；复用已有问题提示组件并补齐缺失覆盖和账户级问题。主体改动集中于 CSV 正常诊断行清理及 3.6 的最小布局接线，不重写账单页面。实现前遵循 `web/AGENTS.md`、项目 `shadcn-ui` 和 i18n 技能。
2. 仅在 `en.json`、`zh.json` 增加组织账单专用文案。不得全局替换共享的 `Usage`、`Derived` 等翻译，避免影响其他页面；不维护旧语言文件。
3. 保留 API 字段名、数值、状态枚举、缓存键及计算版本，不修改计价、扣款、退款、任务确认和组织系数。此次展示修改不触发历史账单失效或重建。
4. 页面使用现有消费完整性、退款金额及覆盖日期；不为解释表头新增 SQL、任务扫描、日志解析或逐账户接口。千万级数据下仍读取已有账单快照，本次不会增加日志扫描量或后台生成工作量。

6. 异常筛选与必要去重只使用已有快照中的覆盖状态、问题引用及账户状态，在内存完成；不能为判断是否展示而新增 SQL、扫描原始日志、触发余额核验或重建快照。缺少详细原因时如实使用已有通用原因，不另建异常工单或历史核验体系。
